# 01 模块详解

> rm 的架构是 **"一个插件壳 + 多个功能 crate"** 的模式。插件壳负责把功能 crate 组装起来，向 ling 内核注册 `resources-manager.*` 方法；功能 crate 各自独立，不直接依赖 ling-sdk。

---

## 总体架构图

```
                    ling kernel (broker/bus/caps)
                          │
               Context.register_method / emit / call
                          │
            ┌─────────────▼──────────────┐
            │      rm-plugin (插件壳)      │  ← 唯一依赖 ling-sdk
            │  methods.rs / events.rs /    │
            │  state.rs / lib.rs           │
            └───────┬──────────┬─────────┘
                    │          │
         ┌──────────┴──┐   ┌───┴──────────┐
         │ rm-catalog   │   │  rm-transfer  │
         │ (SQLite)     │   │  (LAN 传输)    │
         └──────┬───────┘   └──────┬────────┘
                │                   │
    ┌───────────┼───────────┐       │
    │           │           │       │
rm-scan    rm-dedup    rm-store   rm-sync
(扫描哈希)  (内容去重)   (存储压缩)  (op-log)
    │           │           │       │
    └───────────┴─────┬─────┘       │
                      │             │
                   rm-proto ◄───────┘
              (消息/错误/常量)
                      │
                   rm-fs
              (跨平台元数据)
```

## 1. rm-plugin — 插件壳

### src/lib.rs — Plugin 实现

**一句话**：实现 `Plugin` trait，在 `activate` 里打开 catalog、初始化 `RmState`、启动 LAN/流服务、注册方法、贡献 UI 页面。

```rust
impl Plugin for RmPlugin {
    fn id(&self) -> &str { "resources-manager" }

    fn activate(&mut self, ctx: Context) -> Result<(), ActivateError> {
        // 1. 打开 catalog
        let data_dir = ctx.data_dir();
        let catalog = rm_catalog::open(&data_dir.join("catalog.db"))?;

        // 2. 初始化运行时状态
        let mut state = RmState::new(ctx.clone(), catalog, data_dir);

        // 3. 启动 LAN 同步 + 流服务
        state.start_lan_service()?;
        state.start_stream_service()?;

        // 4. 注册所有 resources-manager.* 方法
        methods::register_all(&ctx, &state)?;

        // 5. 订阅事件（如 kernel.plugin.state）
        // ...

        // 6. 贡献 UI 页面到 core-ui
        ctx.call("core-ui", "ui.contribute", json!({...}))?;

        self.state = Some(state);
        Ok(())
    }

    fn deactivate(&mut self) {
        // 收敛线程、停 LAN 服务、落盘
        // 撤销账本由内核自动执行
    }
}
```

### src/state.rs — 运行时共享状态

**一句话**：`RmState` 持有所有模块共享的运行时状态——SQLite 连接、设备 ID、取消令牌、LAN 服务句柄等。

```rust
pub struct RmState {
    pub ctx: Context,
    pub catalog: Catalog,              // SQLite 连接
    pub device_id: String,             // 本机设备 ID（ED25519 公钥）
    pub data_dir: PathBuf,
    pub cancel_tokens: Mutex<HashMap<String, CancellationToken>>,  // job_id → 取消令牌
    pub identity: ed25519::Keypair,    // 配对/传输用
    pub pairing: RwLock<PairingState>,
    pub lan_server: Option<LanServerHandle>,
    pub stream_server: Option<StreamServerHandle>,
}
```

**为什么 State 用了 Mutex/RwLock**：多个方法处理器可能并发访问（broker 不保证串行）。State 里的字段需要线程安全。

### src/methods.rs — 方法注册

**一句话**：`register_all(ctx, state)` 批量注册所有 `resources-manager.*` 方法。每个方法是一个闭包，闭包里调用 rm-* crate 的功能 + 通过 ctx 广播事件。

**注册的全部方法**（按 M1-M5 里程碑分组）：

### src/events.rs — 事件广播

**一句话**：封装 `ctx.emit` 调用，所有事件主题集中在 `rm-proto` 定义，rm-plugin 只是传 payload。

| 事件主题 | 载荷 | 广播时机 |
|---|---|---|
| `resources-manager.job.progress` | `{ job_id, plugin, current, total }` | 扫描/传输等长任务进度 |
| `resources-manager.job.done` | `{ job_id, status, result }` | 长任务完成 |
| `resources-manager.scan.done` | `{ location_id, new_content_count, dup_count }` | 扫描完成 |
| `resources-manager.catalog.changed` | `{ type: "entry"\|"tag"\|"placement", id }` | 目录数据变更 |
| `resources-manager.sync.started` / `sync.completed` / `sync.conflict` | `{ peer, ... }` | 同步相关 |
| `resources-manager.ai.suggest.created` | `{ suggest_id, type, confidence }` | AI 产生新建议 |

## 2. rm-catalog — SQLite 目录库

**一句话**：所有持久化数据的唯一来源。打开 SQLite 连接（WAL + 外键），执行 schema 迁移，提供仓储层（repo）CRUD。

### lib.rs — 打开与初始化

```rust
pub fn open(path: &Path) -> Result<Catalog> {
    let conn = Connection::open(path)?;
    conn.execute_batch("PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;")?;
    migrations::setup(&conn)?;  // 按版本从 V1→V5 迁移
    Ok(Catalog { conn })
}
```

### migrations.rs — Schema 版本

| 版本 | 新增内容 |
|---|---|
| V1 | 物理层：`device`、`location`、`content`（BLAKE3 哈希）、`placement`（内容放哪）、`pool`（存储池） |
| V2 | 语义层：`entry`（词条）、`version`（版本）、`version_file`（版本包含哪些 content）、`instance`（版本在某位置的目录） |
| V3 | 标签：`tag` + `entry_tag` + `version_tag`（多对多） + `tag_domain`（分域） + `tag_parent`（层级） |
| V4 | 关系：`connection`（词条间有向关系） + `connection_type` |
| V5 | 同步 & AI：`op_log`（操作日志） + `tombstone`（墓碑） + `ai_suggestion` + `external_source` + `suggestion` |

### repo/ — 仓储层

```
repo/
├── mod.rs            // 导出所有子模块 + txn!/optional! 宏
├── content.rs        // content 表 CRUD（BLAKE3 哈希）
├── placement.rs      // placement 表 CRUD（内容放哪台设备哪个路径）
├── location.rs       // location 表 CRUD（位置 = 根目录 + 状态）
├── device.rs         // device 表
├── pool.rs           // pool 表 + 池路径布局
├── entry.rs          // entry 表（词条）+ alias + external_source
├── version.rs        // version 表 + version_file（多文件版本）
├── instance.rs       // instance 表（版本在某位置的落地目录）
├── tag.rs            // tag + tag_domain + tag_parent
├── connection.rs     // connection（词条间关系）
├── op.rs             // op_log（同步用）
├── tombstone.rs      // 墓碑（删除缓冲）
├── job.rs            // 作业记录
└── suggestion.rs     // AI 建议
```

**事务宏**：`repo::txn!(catalog, |txn| { ... })` 自动开事务，闭包返回 `Result<(), E>` 时 `?` 回滚。

## 3. rm-scan — 扫描与哈希

**一句话**：遍历位置根目录，用**分层哈希**（比大小→比首尾→全文）判断内容重复，把新内容写入 catalog。

### 关键函数

| 函数 | 说明 |
|---|---|
| `scan_location(catalog, location_id, progress_cb)` | 扫描某位置，回调进度 |
| `ScanOutcome` | `{ new_contents, duplicates, total_files, total_bytes }` |
| `ScanProgress` | `{ current, total, path, stage }` |

### 分层哈希（`hash_tier.rs`）

```
Tier 0: 比文件大小 → 大小不同直接跳过
Tier 1: 比首尾各 64KB → 相同才进入 Tier 2
Tier 2: 全文算 BLAKE3 → 最终哈希
```

绝大多数文件在 Tier 0 就被筛掉了，只有同大小的文件才需要读盘。

## 4. rm-fs — 跨平台文件系统

**一句话**：封装跨平台的文件元数据读取，让 rm-scan 不用关心 Windows vs Linux 的差异。

```rust
pub struct FileMeta {
    pub path: PathBuf,
    pub size: u64,
    pub mtime: SystemTime,
    pub inode: Option<u64>,   // Linux 有，Windows None
}
```

| 函数 | 说明 |
|---|---|
| `walk_dir(root, filter)` | 跨平台目录遍历 |
| `stat(path)` | 跨平台元数据 |

### platform.rs — 条件编译

```rust
#[cfg(unix)] fn inode_of(meta: &fs::Metadata) -> Option<u64> { ... }
#[cfg(not(unix))] fn inode_of(_: &fs::Metadata) -> Option<u64> { None }
```

## 5. rm-dedup — 去重

**一句话**：扫描完成后，按 content 哈希分组，找出重复的 placement，推荐合并方案（硬链接 / 删除冗余）。

```rust
pub struct DedupGroup {
    pub content_hash: String,
    pub placements: Vec<Placement>,    // 这个内容在多少个位置有副本
    pub keep_one: bool,                // 是否建议合并
}
```

## 6. rm-store — 存储池与压缩

**一句话**：内容入库池（按哈希命名），支持 zstd 试压/压缩/解压，三档存储策略（原始/压缩/外置）。

### 池路径布局

```
<pool_root>/
├── blake3/ab12/34cd/xxxx...        # 按哈希前 2 段分目录
│   └── ab1234cd...xxxx             # 内容文件本身（按哈希命名）
```

| 函数 | 说明 |
|---|---|
| `import_content(pool_root, source_path)` | 复制或硬链接到池，返回内容哈希 |
| `export_content(pool_root, hash, dest_path)` | 从池导出 |
| `compress(pool_root, hash)` | zstd 试压 → 压缩（体积比 > 1.2 才值得） |
| `decompress(pool_root, hash)` | 解压 |

## 7. rm-sync — 记录同步

**一句话**：两台设备交换 catalog 的 op-log（操作日志），合并记录，处理冲突，用墓碑缓冲删除。

```rust
pub struct OpLogEntry {
    pub id: i64,
    pub op_type: OpType,           // Insert / Update / Delete
    pub table: String,
    pub row_id: String,
    pub payload: Value,
    pub timestamp: i64,
    pub device_id: String,
}
```

| 模块 | 说明 |
|---|---|
| `oplog.rs` | op_log 表 CRUD |
| `conflict.rs` | 冲突解决策略（LWW / 人工 / 保留双方） |
| `merge.rs` | 接收对方 op-log，应用到自己的 catalog |
| `tombstone.rs` | 墓碑管理：删除先立墓碑，30 天宽限期后才真删 |

## 8. rm-transfer — 数据同步（文件本体传输）

**一句话**：局域网 HTTP 传输层。配对（ED25519 握手）、断点续传、分块、进度回调。

### 协议

```
Client → Server: GET /transfer/{hash}?token=xxx&range=bytes=0-
Server → Client: HTTP 206 Partial Content + 数据块
```

| 模块 | 说明 |
|---|---|
| `pairing.rs` | 配对流程：握手 → 交换公钥 → 生成 session |
| `http.rs` | 传输 HTTP server（tokio） |
| `client.rs` | 传输 HTTP client |
| `identity.rs` | ED25519 密钥管理 |
| `policy.rs` | 传输策略（允许/拒绝哪些 peer、哪些内容类型） |

## 9. rm-proto — 协议层（共享常量/错误/消息）

**一句话**：所有 rm-* crate 共享的常量定义——错误码、事件主题、消息结构、枚举。

| 文件 | 内容 |
|---|---|
| `msg.rs` | 方法请求/响应的 JSON 结构（M1 的全部） |
| `event.rs` | 所有事件主题字符串常量 |
| `codes.rs` | rm 专属错误码（`E_RM_SCAN_CANCELLED`、`E_RM_PAIR_REJECTED` 等） |

**为什么 rm-proto 独立**：rm-plugin、rm-transfer、rm-sync 都需要引用同一个错误码和事件主题，但不想互相依赖。rm-proto 是"没有业务逻辑的纯数据 crate"。

## 10. rm-ai — AI 功能

**一句话**：AI 能力的插件。调用本地或云端模型打标签、建关系、刮削作品信息、生成建议。

| 模块 | 说明 |
|---|---|
| `provider.rs` | AI provider 抽象（本地 Ollama / 云端 API） |
| `suggest.rs` | 生成建议（草稿，不直接写数据库） |
| `extract.rs` | 从文件名/路径提取候选标签 |
| `cache.rs` | AI 结果缓存（相同输入不重复调模型） |
| `privacy.rs` | 隐私三档（local/cloud/hybrid）判定 |
| `cost.rs` | 调用成本统计 |

---

## 11. rm-classify / rm-semantic

**rm-classify**：基于规则的自动分类（纯本地，不需要 AI），比如按文件扩展名/目录名打 `document`/`video` 标签。

**rm-semantic**：词条/版本/标签/关系的高层业务逻辑。目前大部分在 rm-plugin 的 methods.rs 里直接调用 repo，未来可能抽成独立语义层。
