# 03 同步与传输

> rm 的同步分两层：**记录同步**（交换 op-log，不碰文件本体）和**数据同步**（按需传输文件本体）。设计层面的完整协议见 `docs/resources-manager/03-接口与协议.md`，本文档侧重代码实现。

---

## 1. 同步架构总览

```
设备 A (台式机)              设备 B (笔记本)
    │                            │
    │  op-log 增量同步           │
    │ ────────────────────────▶ │  rm-sync::merge
    │                            │  应用对方的 op_log
    │                            │
    │ ◀──────────────────────── │
    │  自己的 op-log 增量回传    │
    │                            │
    │                            │
    │  文件本体按需传输           │
    │ ─────── HTTP Range ─────▶ │  rm-transfer::fetch
    │                            │  分段写入 + 断点续传
    │                            │
```

## 2. 记录同步（rm-sync）

### 2.1 op-log 机制

每次 catalog 写操作（insert / update / delete）都会自动向 `op_log` 表追加一条：

```sql
CREATE TABLE op_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    op_type TEXT NOT NULL,       -- 'Insert' / 'Update' / 'Delete'
    table  TEXT NOT NULL,
    row_id TEXT NOT NULL,
    payload TEXT NOT NULL,       -- JSON 序列化后的完整行
    timestamp INTEGER NOT NULL,  -- unix timestamp
    device_id TEXT NOT NULL
);
```

### 2.2 同步流程

```
sync.start(peer_device_id)
  │
  ├─ 1. 读对方的 op_log(last_id 起)
  │     rm-transfer::http::get_op_logs(peer_url, since_id)
  │
  ├─ 2. rm-sync::merge(peer_ops, &catalog)
  │     逐条应用到自己的 catalog
  │     ├─ 无冲突 → 直接应用
  │     ├─ 有冲突 → conflict::resolve()
  │     │     策略：LWW (最后写入者赢)
  │     │     或人工标记 (manual)
  │     │     或保留双方 (keep-both)
  │     └─ 记 conflict 日志
  │
  ├─ 3. 把自己的 op_log(last_id 起) 回传给对方
  │
  └─ 4. 广播 events::sync.completed
```

### 2.3 冲突解决（conflict.rs）

```rust
pub fn resolve(
    local_op: &OpLogEntry,
    remote_op: &OpLogEntry,
    strategy: ConflictStrategy,
) -> ConflictResolution
```

| 策略 | 说明 | 使用场景 |
|---|---|---|
| `LastWriteWins` | 时间戳靠后的赢 | 大多数普通字段 |
| `Manual` | 标记冲突，等用户决策 | 关键字段（如 title 被改了） |
| `KeepBoth` | 两边都保留（entry 拆成两个） | 极端场景 |
| `RemoteWins` | 远端总是赢 | 从"主设备"同步时 |

### 2.4 墓碑与宽限期（tombstone.rs）

**为什么需要墓碑**：如果 A 删了一个条目并记录 `op_log.Delete`，但 B 还没同步到这条记录就先同步到了 B 自己的修改（比如给同一个 entry 加了标签）——如果 A 的 delete 直接生效，B 的标签就白加了。

**墓碑机制**：
1. 删除时**不立刻真删**，而是在 `tombstone` 表插一条 + 写 `op_log.Delete`
2. `tombstone.created_at` 记录立碑时间
3. 宽限期 30 天内，墓碑阻止新的 insert/update（检测冲突）
4. 30 天后，清理任务真删条目 + 删墓碑

```sql
CREATE TABLE tombstone (
    id INTEGER PRIMARY KEY,
    table TEXT NOT NULL,
    row_id TEXT NOT NULL,
    created_at INTEGER NOT NULL  -- 立碑时间
);

-- 清理（在 reconcile 里定期执行）
DELETE FROM tombstone WHERE created_at < (now - 30 days);
DELETE FROM entry WHERE id IN (SELECT row_id FROM tombstone WHERE ...);
```

## 3. 数据同步（rm-transfer）

### 3.1 配对（Pairing）

两台设备第一次连接需要配对——交换 ED25519 公钥：

```
Client                              Server
  │                                    │
  │  GET /pair                         │
  │  Body: { client_pub_key }          │
  │ ────────────────────────────────▶ │
  │                                    │
  │  服务器端:                          │
  │  1. 验证 client_pub_key 未被拒绝    │
  │  2. 生成 session token             │
  │  3. 存 peer 关系到 catalog         │
  │                                    │
  │  200 OK                            │
  │  Body: { server_pub_key, session_token }
  │ ◀──────────────────────────────── │
```

配对后双方都能看到对方的 device_id 和公钥。

### 3.2 传输协议（HTTP Range）

```
Client                                    Server
  │                                        │
  │  GET /transfer/{content_hash}           │
  │  Authorization: Bearer <session_token> │
  │  Range: bytes=0-                       │
  │ ─────────────────────────────────────▶ │
  │                                        │
  │  1. 验证 token（ED25519 签名）          │
  │  2. 查 content/placement，确认存在      │
  │  3. 206 Partial Content                 │
  │  4. 分段发送（默认 128KB/段）           │
  │                                        │
  │  206 Partial Content                   │
  │  Content-Length: 1073741824            │
  │  Body: [chunk1][chunk2]...              │
  │ ◀──────────────────────────────────── │
  │                                        │
  │  断点续传                               │
  │  Range: bytes=2147483648-              │  ← 从已下载位置继续
  │ ─────────────────────────────────────▶ │
  │  206 + 后续数据块                       │
  │ ◀──────────────────────────────────── │
```

### 3.3 传输客户端（client.rs）

```rust
pub async fn fetch_content(
    client: &TransferClient,
    peer_url: &str,
    hash: &str,
    dest: &Path,
    progress_cb: impl Fn(u64, u64),  // (received, total)
) -> Result<(), TransferError>
```

| 特性 | 实现 |
|---|---|
| 断点续传 | HTTP Range 头；客户端记录已下载字节数 |
| 进度回调 | 每收到数据块触发 progress_cb |
| 并发 | 多个内容可并发 fetch（tokio JoinHandle） |
| 取消 | CancellationToken 中断连接 + 删临时文件 |
| 完整性校验 | 下载完成后本地算一次 BLAKE3，和 hash 比对 |

### 3.4 传输服务端（server.rs）

rm-plugin 激活时启动 `LanServer`（tokio TCP listener），监听端口 7913：

```
rm_plugin activate
  └─ RmState::start_lan_service()
       └─ LanServer::bind("0.0.0.0:7913")
            └─ tokio::spawn(accept_loop)
                 ├─ 配对端点 /pair
                 ├─ op-log 端点 /sync/op-log
                 ├─ 内容传输端点 /transfer/{hash}
                 └─ 流交付端点 /s/{placement_id}  ← 给 player 用
```

### 3.5 安全

| 措施 | 说明 |
|---|---|
| 配对必须 | 未配对设备不能传输 |
| session token | 配对后下发短期 token，每次请求带 `Authorization` |
| 签名验证 | 传输请求带 ED25519 签名，服务端验证来自已配对设备 |
| 局域网限定 | 传输端口绑 `0.0.0.0`，但安全上只信任已配对 |

## 4. 流交付接口（player 对接）

player 需要文件字节，但不想自己管"文件在哪台设备上、路径是什么"——rm 提供两个接口：

### 4.1 stream.open — 返回带 token 的流 URL

```rust
// 方法签名
fn stream_open(state: &RmState, args: Value) -> Result<Value, CallError> {
    let placement_id = args["placement_id"].as_i64().ok_or(...)?;
    let state = args.get("prefer_offline").and_then(|v| v.as_bool());

    // 查 placement → 确认存在 → 生成临时 token
    let url = format!(
        "http://127.0.0.1:7913/s/st_{}/token_{}",
        placement_id, token
    );

    Ok(json!({
        "url": url,
        "content_hash": content.hash,
        "mime_type": content.mime_type,
        "size": content.size,
        "token_ttl": 3600,  // token 1 小时有效
    }))
}
```

player 拿到 URL 后自己发 HTTP Range 请求拿字节。rm 的 `/s/` 端点和传输端点**共用** LanServer，token 是临时的。

### 4.2 stream.get_local_path — 直接给路径

如果 player 和 rm 在同一台设备上，文件就在本地磁盘上，没必要绕 HTTP：

```rust
fn stream_get_local_path(state: &RmState, args: Value) -> Result<Value, CallError> {
    let placement_id = args["placement_id"].as_i64().ok_or(...)?;
    let placement = repo::placement::get(&state.catalog, placement_id)?;

    Ok(json!({
        "local_path": placement.path,
        "content_hash": placement.content_hash,
    }))
}
```

### 4.3 player 侧调用链

```
player 要播放 placement_id=42 的内容
  │
  ├─ 先问 rm：stream.get_local_path
  │   └─ 如果返回了本地路径 → 直接 load_path，省事 ✅
  │
  └─ 如果没返回 / 文件不在本地：stream.open
      └─ 拿到 http://.../s/st_42/token_xxx
          └─ player 自己发 HTTP Range 请求给 rm 的流端点
```

## 5. 同步 vs 传输 vs 流交付 三者对比

| 方面 | 记录同步 | 数据同步 | 流交付 |
|---|---|---|---|
| 做什么 | 交换 op-log | 传输文件本体 | 按需给 player 提供字节 |
| 谁主动 | 两端都可能 | 客户端主动 fetch | player 主动 open |
| 内容 | JSON 行 | 二进制流 | 二进制流 |
| 存储影响 | 写 catalog.op_log + merge 到各表 | 写 placement 到本地磁盘 | 不落盘，流式播放 |
| 典型时机 | 两台设备同时在线时 | 用户显式发起 "取回这个内容" | 每次播放 |

## 6. 同步/传输相关事件

| 事件主题 | 广播方 | 载荷 |
|---|---|---|
| `resources-manager.sync.started` | rm-plugin | `{ peer, timestamp }` |
| `resources-manager.sync.completed` | rm-plugin | `{ peer, local_ops, remote_ops, conflicts }` |
| `resources-manager.sync.conflict` | rm-plugin | `{ peer, entry_id, local_payload, remote_payload, resolution }` |
| `resources-manager.transfer.progress` | rm-plugin | `{ transfer_id, hash, received, total }` |
| `resources-manager.transfer.done` | rm-plugin | `{ transfer_id, hash, destination }` |
