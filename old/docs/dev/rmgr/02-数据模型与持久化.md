# 02 数据模型与持久化

> rm 的所有持久化数据都在**一个 SQLite 文件**里：`ling/plugins/resources-manager/data/catalog.db`。数据库 schema 版本化迁移，仓储层 repo/* 提供类型安全的 CRUD。
> 
> 设计层面的完整数据字典见 `docs/resources-manager/02-数据字典.md`，本文档侧重**代码结构**和**使用方式**。

---

## 1. 数据库初始化

```rust
// rm-plugin activate 里
let data_dir = ctx.data_dir();
let catalog = rm_catalog::open(&data_dir.join("catalog.db"))?;

// rm-catalog::open 内部做了：
// 1. Connection::open(path)
// 2. PRAGMA journal_mode=WAL;  ← 读写并发不阻塞
// 3. PRAGMA foreign_keys=ON;   ← 外键约束强制
// 4. migrations::setup(&conn)  ← 按 schema_meta.version 逐步迁移到最新
```

### 迁移表

| schema_meta.version | 包含的表 |
|---|---|
| V1 | device, location, content, placement, pool |
| V2 | entry, version, version_file, instance |
| V3 | tag, tag_domain, tag_parent, entry_tag, version_tag |
| V4 | connection, connection_type |
| V5 | op_log, tombstone, ai_suggestion, external_source, suggestion |

迁移是**幂等**的——已有版本不重复执行。

## 2. 核心数据模型（代码层）

### 2.1 物理层（V1）— 存"文件在哪"

```rust
// content — 按 BLAKE3 哈希唯一标识一段文件内容
pub struct Content {
    pub hash: String,           // "blake3:ab1234..."
    pub size: i64,
    pub mime_type: Option<String>,
    pub created_at: i64,
}

// placement — 某段内容放在哪台设备的哪个路径
pub struct Placement {
    pub id: i64,
    pub content_hash: String,
    pub location_id: i64,
    pub path: String,           // 绝对路径
    pub state: PlacementState,  // present / missing / offline
    pub mode: PlacementMode,    // managed / scattered
    pub verified_at: Option<i64>,
}

// location — 一台设备上的一个根目录
pub struct Location {
    pub id: i64,
    pub device_id: String,
    pub root: String,
    pub state: LocationState,   // online / offline / cold
    pub managed: bool,          // 是否入池管理
}

// device — 一台设备
pub struct Device {
    pub id: String,             // ED25519 公钥 hex
    pub name: String,
    pub paired_at: Option<i64>,
}

// pool — 存储池（按哈希命名的内容仓库）
pub struct Pool {
    pub id: i64,
    pub location_id: i64,
    pub root: String,
    pub policy: CompressPolicy, // none / compress / external
}
```

### 2.2 语义层（V2）— 存"这是什么作品"

```rust
// entry — 词条（一部电影、一本书、一个题材）

pub struct Version {

    pub codec: Option<String>,         // "hevc"
    pub container: Option<String>,     // "mkv"

// version_file — 一个版本包含哪些 content（多文件版本）
pub struct VersionFile {

pub struct Instance {

    pub dir_path: String,

}
```

## 3. 仓储层使用方式

所有 repo 模块都接受 `&Catalog` 作为第一个参数。

### 3.1 基本 CRUD

```rust
use rm_catalog::repo;

// 读
let entries = repo::entry::list(&catalog)?;
let entry = repo::entry::get(&catalog, entry_id)?;

// 写（自动开事务）
let new_id = repo::entry::create(&catalog, "深空旅人", EntryType::Movie)?;

// 带事务的批量操作
repo::txn!(&catalog, |txn| {
    repo::entry::create_in_txn(txn, "旧港疑云", EntryType::Book)?;
    repo::tag::apply_in_txn(txn, entry_id, tag_id)?;
    Ok::<_, rm_catalog::Error>(())
})?;
```


## 4. 内容寻址与存储池

### 4.1 扫描 → 入库

```
scan.start(location_id)
  │
  ├─ walker 遍历目录
  ├─ 对每个文件：
  │   ├─ rm_fs::stat → 取 size/mtime
  │   ├─ 查 content 表：(size, mtime) 有没有相同的？
  │   │   ├─ 没有 → 分层哈希（Tier0: size → Tier1: 首尾 64KB → Tier2: BLAKE3）
  │   │   ├─ 有   → 可能重复，进 Tier1 确认
  │   ├─ content 表不存在 → INSERT content
  │   └─ placement 表不存在 → INSERT placement
  │
  └─ rm-proto::Emit scan.done
```

### 4.2 池路径布局

```
location.root = "D:\media"    (managed=true)
pool.root     = "D:\media\.pool"

池内部：
.pool/blake3/ab/12/ab1234cd5678...          ← 按哈希前 2 段分目录
.pool/blake3/ef/90/ef901234...
```

**导入流程**：`import_content(pool_root, source)` → 计算 hash → 检查池里有没有 → 硬链接（同盘符）或复制 → 返回 hash。

**压缩决策**：试压 → 体积比 > 1.2 才压缩（省下来的空间值得代价）。

## 5. 扫描长任务模式

扫描是长任务（可能几十分钟），rm 用以下模式：

```rust
// 1. scan.start 立即返回 job_id
fn scan_start(state: &RmState, args: Value) -> Result<Value, CallError> {
    let location_id = args["location_id"].as_i64().ok_or(...)?;
    let job_id = generate_job_id();

    // 2. spawn 一个线程跑扫描
    let cancel = CancellationToken::new();
    state.cancel_tokens.lock().unwrap().insert(job_id, cancel.clone());
    std::thread::spawn(move || {
        let outcome = rm_scan::scan_location(&catalog, location_id, &progress_cb, cancel);
        events::emit_scan_done(&ctx, location_id, outcome);
    });

    Ok(json!({ "job_id": job_id }))
}

// 3. scan.cancel 用 cancel token 中断
fn scan_cancel(state: &RmState, args: Value) -> Result<Value, CallError> {
    let job_id = args["job_id"].as_u64().ok_or(...)?;
    if let Some(token) = state.cancel_tokens.lock().unwrap().remove(&job_id) {
        token.cancel();  // 扫描线程检测到后提前退出
    }
    Ok(json!({ "ok": true }))
}

// 4. scan.stats 查询进度
fn scan_stats(state: &RmState, args: Value) -> Result<Value, CallError> {
    // 从 catalog.job 表读进度快照
    Ok(json!({ "current": ..., "total": ..., "files": ... }))
}
```

**为什么用 std::thread 而不是 tokio::spawn**：rm-scan 里有大量同步 rusqlite 操作（事务、批量 insert），和 tokio runtime 混在一起反而容易出问题。单独线程更干净。

## 6. 数据完整性保证

| 机制 | 代码位置 | 说明 |
|---|---|---|
| WAL 模式 | `rm-catalog::open` | 读写并发不阻塞，读取不锁库 |
| 外键约束 | `PRAGMA foreign_keys=ON` | placement 不能引用不存在的 location |
| 事务批量操作 | `repo::txn!` | 要么全成，要么全不成 |
| 墓碑缓冲 | `tombstone.rs` | 删除先立墓碑，30 天宽限期 |
| op-log 递增 | `op_log.id` 自增 | 同步时按 id 排序应用 |
