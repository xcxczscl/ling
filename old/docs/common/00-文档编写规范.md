# 00 文档编写规范

> 适用范围：ling 与 resources-manager 的**所有**文档（含以后新增的）。
> 地位：评审时请监督执行；违反本规范的文档不算完成。

---

## 1. 十条规矩

| # | 规矩 | 具体要求 | 反例 → 正例 |
|---|---|---|---|
| 1 | **术语首次出现必须解释** | 格式固定：「白话定义 + 例子 + 它不是什么」。术语表见 `01-公共术语与约定.md` 及各项目自己的术语章节 | 直接写"放置（Placement）"而不解释 → 先给一句定义再用 |
| 2 | **概念中英对照** | 首次写"放置（Placement）"，之后固定用中文；表名、字段名、命令、代码标识符保持英文 | 全文混用 placement/放置 交替 → 首次对照后统一用中文 |
| 3 | **禁用模糊词** | 高效、适当、尽量、快速、合理、优化、良好、若干……一律换成数字或具体行为 | "性能良好" → "扫描 10 TB 约 28 小时" |
| 4 | **数字必须带前提** | 每个性能数字写明测量条件 | "100 MB/s" → "100 MB/s（单块机械硬盘顺序读取时实测）" |
| 5 | **贯穿示例** | 各项目维护自己的贯穿示例，抽象概念都在它上面讲一遍 | resources-manager 用"用户与三台设备"；ling 用"用户装/卸插件" |
| 6 | **表格优先** | 长段落拆成表格；定义类内容用「是什么 / 不是什么 / 例子」三段式 | 一大段散文描述状态取值 → 改成状态一览表 |
| 7 | **统一骨架** | 每份文档：本文回答什么 → 读者是谁 → 正文（编号章节）→ 相关文档 → 变更记录 | 缺"变更记录"表 → 必须补 |
| 8 | **决策统一格式** | 背景 → 备选方案 → 最终决定 → 付出的代价 → 理由 → 影响章节 | 只写"选了 A" → 必须写清代价与理由 |
| 9 | **先改文档再改代码** | 实现中发现文档错误：先提出文档变更 → 批准 → 改文档 → 改代码 → 在变更记录登记 | 直接改代码事后补文档 → 不允许 |
| 10 | **评审可追溯** | 评审意见登记在对应项目的"总体设计"附录 B：意见 → 采纳与否 → 理由 → 改了哪些章节 | 口头说"改过了" → 必须落表 |

## 2. 文档的权威顺序（冲突时听谁的）

```
项目自己的「总体设计」文档  >  本目录  >  其他文档
```

- 例：ling 的《01-宿主设计》与本目录冲突 → 以《01-宿主设计》为准，然后回头修订本目录。
- 例：resources-manager 的数据字典与接口文档冲突 → 数据字典为准（字段含义是源头）。

---

## 3. 文档目录组织约定

| 约定 | 说明 |
|---|---|
| 编号前缀 | `00`、`01`… 用于推荐阅读顺序，不是重要性排序 |
| 每份文档单一职责 | 一份文档只回答一类问题；宁可多分文件，不要写成巨石文档 |
| 交叉引用用相对路径 | 如 `[02-数据字典](02-数据字典.md)`；跨项目引用写 `../../ling/docs/…` |
| 变更记录表 | 每份文档末尾必须有：日期 / 版本 / 变更摘要 |
| 评审记录区 | 只有各项目的"总体设计"类文档带附录 B |

---

## 4. 语言与格式约定

| 项 | 约定 |
|---|---|
| 正文语言 | 简体中文；专有名词（Rust、SQLite、WebSocket）保持原文 |
| 标题层级 | 每份文档最多三级标题；更细的内容拆表或拆文件 |
| 代码块 | 标注语言（```toml、```json、```text）；配置示例必须是可运行的完整片段 |
| 命令示例 | 用 `$` 开头表示输入，紧跟输出示例 |
| 占位符 | 用 `<尖括号>`，如 `<插件编号>` |
| 禁止 | 使用 emoji 作为正式内容（文档标题装饰除外）；使用未定义的缩写 |
