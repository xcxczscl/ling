# 02 时空可组合性机制说明

> 本文用白话解释论文《A Programming Paradigm for Spatiotemporal Composability》讲了什么，
> 以及 ling 从中采纳了什么、没采纳什么。不要求读者有编程语言理论背景。
> 详细设计见 `ling/docs/02-上下文与可逆效应.md` 与 `ling/docs/03-协效应与依赖解析.md`。

## 1. 论文信息

| 项 | 内容 |
|---|---|
| 标题 | A Programming Paradigm for Spatiotemporal Composability（时空可组合性的编程范式） |
| 作者 | Yifan Shi、Wei Zhang（北京大学），Tianyi Cui（DeepSeek-AI） |
| 发表 | arXiv 预印本，2026 年 8 月 26 日，编号 2608.25512 |
| 配套实现 | Cordis —— 一个"时空可组合性元框架"，含效应追踪库、协效应解析器、声明式组件加载器、配置调和、热更新 |
| 链接 | https://arxiv.org/abs/2608.25512 ；代码与论文仓库 https://github.com/cordiverse/paper |

**它研究的问题**：现代软件越来越多地需要"动态组装"——插件随时装、随时卸、互相依赖。但目前的做法很粗糙：改了配置就整体重启、卸载插件经常留一堆垃圾（没注销的回调、没释放的资源、失效的依赖）。论文给出了一套理论和机制，让"随便装卸、互不干扰"成为**结构性保证**，而不是靠插件作者自觉。

---

## 2. 论文的两个核心维度（白话）

论文把"插件随便装卸不打架"拆成两个互不相干的问题：

### 2.1 时间维：卸载能不能还原干净（时间可组合性）

**白话问题**：插件 A 装上时改了 10 处环境（注册了 3 个方法、订阅了 2 个事件、开了 1 个端口、写了 4 条配置）。现在要把 A 卸掉——这 10 处改动能不能**一处不落地恢复原样**？

**论文的机制：可逆效应（revertible effect）**

- 规定：插件对环境的每次修改，都必须**连同"怎么撤销这次修改"一起**，交给运行时保管。
- 运行时把撤销方法按顺序存成一本账（账本）。
- 卸载时，运行时**按倒序**逐条执行撤销 → 环境精确恢复到装它之前的样子。
- 因为"撤销"是结构性强制的（不提供撤销方法就无法修改环境），所以**不存在卸载不干净的可能**。

> 生活类比：装修队进你家干活，规定每动一处必须同时交出"复原方案"存进物业档案；退场时物业按档案倒着恢复。装修队自己跑了也没用，物业手里有全套方案。

### 2.2 空间维：依赖变了怎么自动应对（空间可组合性）

**白话问题**：插件 B 声明"我依赖插件 A 的某个接口"。现在 A 被卸载了，或者 A 升级后接口变了，B 该怎么办？总不能让 B 挂着一个空转的依赖继续跑，或者每次都要人工重启整个程序。

**论文的机制：响应式协效应（reactive coeffect）**

- 规定：插件在装载时必须提交一份**需求清单**（我需要谁的什么能力、什么版本）。
- 环境每次发生变化（有插件装上/卸下/升级），运行时**拿每个插件的需求清单重新比对一遍**，得出三种判定：
  - **激活（activating）**：需求满足了 → 让插件开始工作；
  - **停用（deactivating）**：需求不再满足 → 让插件暂停工作（不是卸载，是挂起）；
  - **中性（neutral）**：需求状态没变 → 不动它。
- 这样依赖的出现与消失都会**自动**传导到相关插件，不需要重启。

> 生活类比：剧组拍戏，每个演员贴一张"我需要和谁对戏"的表；换角时剧务拿新名单逐个核对，缺对手戏的演员先停拍，补上后再开拍——而不是全剧组解散重来。

### 2.3 两者合起来：上下文范式

两个机制要共存且不打架，论文的办法是：插件**不许直接碰环境**，所有读写必须经过一个受控的中间对象——**上下文（Context）**。

- 插件对环境的修改（效应）必然经过上下文 → 上下文才能记账、才能要求提供撤销方法。
- 插件对环境的需求（协效应）也登记在上下文 → 上下文变化时才能逐个比对。
- 由此还得到一个性质：**各插件的改动互相不可见干扰**（论文术语叫"观测等价"），A 的改动不会意外影响 B 的判断。

## 3. 论文还给了什么工程红利

| 红利 | 白话 | 对我们的用处 |
|---|---|---|
| **热更新（HMR）** | 换插件新版本时：停用旧版 → 按账本撤销其全部效应 → 加载新版 → 按需求清单重新激活。宿主和其他插件不停机 | 开发 resources-manager 时改一行代码秒级生效，不用重启整个宿主 |
| **配置调和（Reconciliation）** | 改了配置（装/卸插件、改版本要求）后，框架自动推导出"该激活谁、该停用谁"的执行计划，逐步执行，可中途取消 | `ling install xxx` 之后的一连串激活/停用自动完成 |
| **崩溃边界清晰** | 因为所有改动都记账，即使插件中途崩溃，宿主也能按账本把它留下的痕迹清掉 | 卸载/重装更可靠 |

## 4. ling 采纳了什么、没采纳什么

### 4.1 采纳（务实子集）

| 论文机制 | ling 的落地 | 对应文档 |
|---|---|---|
| 可逆效应 | 插件注册的每样东西（接口方法、事件订阅、界面贡献、配置条目、侧车进程）都登记"撤销方法"；卸载时倒序自动还原 | `ling/docs/02` |
| 响应式协效应 | 插件清单增加 `requires` 字段；装/卸/升级插件后，宿主重算依赖图，自动激活/停用 | `ling/docs/03` |
| 上下文范式 | 插件禁止直接碰全局状态，一切经 `Context` 对象；这是对插件作者的强制纪律 | `ling/docs/02`、`ling/docs/04` |
| 热更新 | `ling reload <插件>`：停用 → 撤销效应 → 装新版 → 重新激活。**首轮即实现** | `ling/docs/05` |
| 配置调和 | 装/卸插件后的激活停用计划自动推导与执行 | `ling/docs/03` |

### 4.2 没采纳（明确不做）

| 论文内容 | 为什么不做 |
|---|---|
| 形式化演算与元理论证明（类型论、操作语义那一套） | 我们要的是工程机制，不是理论完备性；论文的机制部分已足够指导实现 |
| 通用"上下文类型"的数学抽象 | ling 的上下文是具体接口，不做通用类型系统 |
| 自进化智能体（agent harness）场景 | 与本项目无关 |

### 4.3 采纳后的约束（插件作者必须知道）

1. **一切修改经上下文**：直接改全局变量、直接开线程不登记 → 视为违规，热更新与卸载不保证干净。
2. **注册必伴随撤销**：上下文的注册函数要求成对提供撤销手段；无法撤销的资源（如不可中断的外部进程）必须登记为"可强杀"类型。
3. **状态放持久文件**：插件内存里不留跨调用的状态（热更新会丢弃旧内存）；状态写进自己的数据目录 `ling/plugins/<编号>/data/`。
4. **需求写进清单**：依赖别的插件或能力，必须写 `requires`，宿主据此自动激活/停用。

## 5. 为什么这套机制适合 ling

| 我们的需求 | 论文机制如何满足 |
|---|---|
| 一切皆插件，宿主零内容 | 上下文范式天然要求"宿主只做中介"，与零内容定位一致 |
| 插件之间可互访 | 互访经上下文的调用路由，调用本身也是被登记的效应 |
| 以后有大量插件（记账、网站管理…） | 依赖图 + 自动激活停用，插件多了也不会互相拖累 |
| 插件管理页要能安全卸载 | 可逆效应账本就是"安全卸载"的技术基础 |
| 开发期迭代要快 | 热更新让单插件开发不用重启宿主 |
