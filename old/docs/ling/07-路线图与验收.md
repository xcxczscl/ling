# ling 07 路线图与验收

> 版本：v0.4 ｜ 状态：已封档（终审通过）
> 本文回答：**ling 分几个阶段交付、每阶段做完的判断标准是什么。**
> 各阶段的技术设计见 `01`–`06`；resources-manager 插件自己的里程碑见 `../../resources-manager/docs/01-总体设计.md`（那是另一条线）。

---

## 1. 阶段总览

| 阶段 | 名称 | 交付物 | 依赖 |
|---|---|---|---|
| L0 | 设计评审 | 本套 9 份文档，评审通过 | —— |
| L1 | 内核骨架 | 清单解析、装载、调用路由、事件广播、能力门禁 | L0 |
| L2 | 上下文与账本 | 效应登记、卸载干净还原 | L1 |
| L3 | 依赖与调和 | requires、依赖图、自动激活/停用、配置调和 | L2 |
| L4 | 热更新 + 命令行 | reload、管理端口、`ling` 命令行 | L3 |
| L5 | 内置插件 | core-ui / core-settings / core-plugin-manager（默认安装三件套）+ core-job / core-log（可选） | L4 |
| L6 | 侧车双轨 | 非 Rust 插件接入 | L5 |

**L0–L4 是"机制完整"，L5–L6 是"可用体验"。** 首轮设计评审只针对 L0；写代码从 L1 开始，顺序推进，不并行跳级。

---

## 2. 每阶段的验收标准

### L0 设计评审

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 9 份文档齐备，符合 `../../docs-common/00-文档编写规范.md` | 逐条对照规范 |
| 2 | `01` 附录 B 的评审意见全部关闭（采纳并改完，或不采纳且理由记录） | 附录 B 表格无"未处理"行 |
| 3 | 术语首次出现均有解释 | 抽查 |
| 4 | 决策记录 A1–A7 齐全，格式符合"背景/备选/决定/代价/理由" | 目检 |

### L1 内核骨架

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 示例插件（测试用 `demo-a`、`demo-b`）可装载，清单校验生效 | `ling install` 成功/失败用例 |
| 2 | demo-a 可通过路由调用 demo-b 的方法，结果正确 | 集成测试 |
| 3 | demo-a 广播事件，demo-b 收到 | 集成测试 |
| 4 | 未声明能力的插件调用被拒，返回 `E_CAPABILITY_DENIED` | 集成测试 |
| 5 | 方法名/主题未带前缀被拒，返回 `E_NAMESPACE_VIOLATION` | 集成测试 |

### L2 上下文与账本

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 卸载 demo-a 后，demo-b 调用其方法返回 `E_METHOD_MISSING` | 集成测试 |
| 2 | 卸载后广播其订阅的事件，其回调不再被调用 | 集成测试 |
| 3 | 账本条目数与注册数一致；倒序执行正确 | 单元测试 |
| 4 | 某条撤销故意失败时，其余继续执行，最终报告"卸载不完整 + 清单" | 故障注入测试 |

### L3 依赖与调和

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 装上 resources-manager 后，依赖它的 ledger 自动激活（无需重启） | 集成测试 |
| 2 | 卸载 resources-manager 后，ledger 自动停用，其方法消失 | 集成测试 |
| 3 | 循环依赖被拒绝，报出环路 | 集成测试 |
| 4 | 版本不匹配时插件进入"待激活"，装上兼容版本后自动激活 | 集成测试 |
| 5 | 调和过程每步广播 `kernel.plan.step` | 事件录制断言 |

### L4 热更新 + 命令行

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | `ling reload demo-a` 后新版本生效，demo-b 无感知（订阅关系自动重建） | 集成测试 |
| 2 | 连续 100 次 reload 压力测试，无崩溃、无状态串味 | 压力测试 |
| 3 | reload 失败自动回滚旧版，宿主状态与 reload 前一致 | 故障注入 |
| 4 | `ling plugins/install/uninstall/enable/disable/restart` 全部可用 | 命令行 e2e |
| 5 | 管理端口仅本机可连，错误 token 被拒 | 网络测试 |

### L5 内置插件

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 首次启动（plugins/ 为空）自动安装三件套：core-ui / core-settings / core-plugin-manager | 启动后 `ling plugins` 断言三者已激活 |
| 2 | 浏览器打开 `127.0.0.1:7910` 能看到插件列表、状态、启停按钮 | 手工 + 截图归档 |
| 3 | 卸载 core-ui 后宿主不崩，界面消失但命令行仍能管理插件（三件套均可卸载） | 手工 |
| 4 | 内置插件（core-job / core-log）不自动安装，插件管理页可见"可安装"列表，按需安装后可用 | 命令行 + 界面 e2e |
| 5 | 插件贡献的页面能正常打开、调用后端方法 | demo 插件带一个测试页 |
| 6 | 设置页能读写 resources-manager 的设置（schema 校验生效） | 集成测试 |

### L6 侧车双轨

| # | 标准 | 验证方式 |
|---|---|---|
| 1 | 一个 Python 侧车示例插件可装载、可注册方法、可被 Rust 插件调用 | 集成测试 |
| 2 | 侧车崩溃后内核注销其效应并广播 crashed；`restart=on-crash` 时自动重启 | 故障注入 |
| 3 | 侧车的热更新（终止旧进程、启动新进程）成功 | 集成测试 |
| 4 | Rust 插件之间调用开销不受侧车影响（对照 L1 基准 < 1 微秒） | 基准测试 |

## 3. 基准性能（预设目标，非承诺）

| 指标 | 目标 | 前提条件 |
|---|---|---|
| 同进程方法调用 | < 1 微秒 | 空处理函数，release 构建，单线程 |
| 事件广播（10 订阅者） | < 10 微秒 | 空回调，release 构建 |
| 装载一个动态库插件 | < 50 毫秒 | 本地 SSD，插件 activate 不做重活 |
| 依赖图重算（50 插件） | < 1 毫秒 | 全量重建，现代桌面 CPU |
| 侧车控制面单次往返 | < 100 微秒 | 本地 Unix socket，空载荷 |

> 实测达不到时：更新此表并写明实际数字与条件，**不删目标**（诚实记录比掩盖重要）。

## 4. 与 resources-manager 的协作节奏

| 时点 | ling | resources-manager |
|---|---|---|
| 现在（L0） | 设计评审 | 文档已迁入独立目录，宿主相关章节改为引用 ling |
| L1–L2 完成 | 内核可装载示例插件 | 可开始搭 rm-* 代码骨架，按 `04` 规范写 |
| L4 完成 | 有热更新和命令行 | 开发期可用 `ling reload resources-manager` 提效 |
| L5 完成 | 有界面壳 | 可贡献"资源管理"页面 |
| 两侧齐备后 | —— | M1（整理）→ M2（同步）等业务里程碑按自己文档推进 |

## 5. L6 之后的待办（封档不阻塞，有真实需求再立项）

| # | 待办 | 为什么现在不做 |
|---|---|---|
| 1 | 窗口壳（Tauri）与安卓壳的详细设计 | 它们只是"指向 core-ui 端口的壳"，机制上无新依赖；等 L5 有界面后再设计 |
| 2 | 文件监视自动重载（watch mode） | 手动 `reload` 已覆盖开发期主场景（05 §5） |
| 3 | 插件市场 / 在线安装 | 明确的非目标（01 §1.2），有分发需求时由插件实现 |
| 4 | 侧车端点优化（Unix socket / 命名管道） | 首版统一 TCP 已够用（04 §6），协议不变只换端点 |
| 5 | 流数据面例外的审计与限速策略 | resources-manager 的回环流端口（其 03 §2.6 契约）实现排在其 M3+；届时补宿主侧审计说明 |
