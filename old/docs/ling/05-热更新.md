# ling 05 热更新

> 版本：v0.3 ｜ 状态：已封档（终审通过）
> 本文回答：**换一个插件的新版本时，宿主怎么做到不停机、其他插件无感；Rust 动态库装卸载有哪些已知的坑，怎么绕。**
> 账本机制见 `02-上下文与可逆效应.md`；依赖解析见 `03-协效应与依赖解析.md`。

---

## 1. 为什么需要热更新

| 场景 | 没有热更新 | 有热更新 |
|---|---|---|
| 开发 resources-manager，改一行代码 | 重启整个宿主 → 所有插件重新装载 → 十几秒 | `ling reload resources-manager` → 秒级，只有它自己重来 |
| 线上修一个业务插件的 bug | 重启 → 其他插件的作业中断 | 只重载这一个 |
| 试验一个新版本 | 全量重启，失败了难回退 | 失败自动回滚旧版 |

热更新的价值集中在**开发期**和**局部修复**；它不是"不停机集群"那种企业级能力，只保证"宿主进程不退"。

## 2. 重载流程（Reload）

```
ling reload resources-manager   （前提：新版本产物已替换到插件目录）
  │
  ├─ 1. 校验新清单（04 §2）——失败 → 报错结束，旧版不动
  │
  ├─ 2. 暂停调和（防止重载途中依赖图变动干扰）
  │
  ├─ 3. 停用当前版本
  │     ├─ 找出依赖 resources-manager 的下游插件（如 ledger）→ 先停用它们
  │     ├─ 调 resources-manager 的 deactivate()
  │     └─ 倒序执行其账本（注销方法/退订/删配置/停侧车）
  │
  ├─ 4. 卸载旧动态库（dlclose / FreeLibrary）
  │     └─ 失败 → 见 §3.3 回滚旧版并报告
  │
  ├─ 5. 装载新动态库 → activate(ctx) → 重新记账
  │     └─ 失败 → 回滚：用旧产物重新装载 → 恢复下游激活 → 报告 E_RELOAD_FAILED
  │
  ├─ 6. 恢复调和 → 重算依赖图 → 重新激活下游（ledger 等）
  │
  └─ 7. 广播 kernel.plugin.state
```

**关键约束**：
- 新旧版本的**插件编号必须相同**（热更新≠换插件）。编号变了走"卸载+安装"。
- **重载窗口内的在途调用**：步骤 3–5 之间该插件处于"未激活"，经路由的调用一律返回 `E_PLUGIN_MISSING`（不排队、不阻塞调用方）；订阅者视角同理——它的回调已随账本撤销。调用方按既有错误处理路径自行重试即可。

## 3. Rust 动态库装卸载的坑与对策

> 这是 L4 阶段最大的实现风险，决策记录见 `01` 附录 A-4、§8 风险 1。

### 3.0 先说清楚：动态库装卸载是什么（白话）

**动态库**（Linux 上是 `.so` 文件，Windows 上是 `.dll`）就是一个可以被别的程序"临时借来用"的代码包。插件编译产物就是动态库。

| 操作 | 系统调用 | 白话 |
|---|---|---|
| 装载 | `dlopen("resources_manager.so")` | "把这份代码借进来"——系统读入文件、把函数编排好，返回一个"句柄"（钥匙） |
| 查符号 | `dlsym(句柄, "ling_plugin_entry")` | "这份代码里有没有我要的那个函数"——按名字查，查到就拿到函数指针 |
| 卸载 | `dlclose(句柄)` | "把借的代码还回去"——系统应释放这份代码占用的内存 |

**类比**：把插件想成一个**工具箱**。dlopen = 把工具箱搬进车间开工；dlclose = 收工把工具箱搬走。**坑在于**：搬走工具箱时，工人可能把几件工具（static 变量）留在了车间桌上；或者还有学徒（线程）正在用里面的工具——这时搬走箱子就会出事。下面四个坑全是这两类问题的变体。

### 3.1 坑一：静态变量残留

**现象**：动态库被 dlclose 后，库内的 `static` 变量所占内存**可能不被释放**；再次 dlopen 同一路径时，新库实例可能读到旧的静态值（取决于操作系统与加载器实现）。

**例子**：resources-manager 里写了
```rust
static SCAN_CACHE: Mutex<Vec<FileEntry>> = Mutex::new(Vec::new());
```
热更新后，新版本的代码被装载，但 `SCAN_CACHE` 里的旧扫描结果还在——新版本以为这是"空缓存"逻辑的一部分，数据串味，轻则统计错乱，重则删错文件。

**对策**：
1. **纪律**：插件禁止用 `static`、`lazy_static`、`once_cell` 持有业务状态（`04` §9 纪律 4）。要状态放持久文件，见 §3.5。
2. **内核侧**：每次重载时若可能，改用**新文件名**（如 `resources_manager.<时间戳>.so`）加载，避免加载器缓存命中；旧文件在成功后删除。
3. **测试**：L4 验收包含"连续 100 次 reload，断言状态不串味"的压力测试。

### 3.2 坑二：类型布局不兼容

**现象**：内核与插件如果共享同一个 Rust 类型（如自定义结构体），编译器版本/编译选项不同可能导致内存布局不一致 → 跨边界读写崩溃。

**对策**：**序列化边界纪律**（`01` §8 风险 1、`04` §3.2）——内核与插件之间只传 `serde_json::Value` 或纯数据标量，**不传**引用、闭包、自定义结构体实例。`Context` 句柄本身也不跨动态库边界复制，由内核持有的注册表代理。

### 3.3 坑三：dlclose 失败或悬挂线程

**现象**：若插件还有线程在跑，dlclose 要么失败，要么卸掉了代码而线程继续执行 → 立即崩溃。

**对策**：
1. **纪律**：`deactivate()` 必须等待或取消所有自开线程（`04` §9 纪律 5）。
2. **内核侧**：dlclose 失败 → 中止 reload → 按旧版重新装载（回滚）→ 报告 `E_UNDO_FAILED`，提示插件可能有未收敛线程。
3. **侧车轨道无此问题**：终止进程天然干净，这也是"难以收敛的插件改用侧车"的理由之一。

### 3.4 坑四：新旧版本依赖接口不匹配

**现象**：新版 resources-manager 要求 `core-ui@2`，旧版只要求 `core-ui@1`，宿主只有 core-ui 1.x → 新版无法激活。

**对策**：重载第 5 步激活失败 → 自动回滚旧版 → 报告 `E_DEPENDENCY_UNMET`。**不会**把插件留在"装了但用不了"的中间态。

### 3.5 持久文件（决策 A-5 的展开）：状态放哪、热更新时怎么读

上面四个坑的共同答案是：**插件的业务状态一律不放内存（不放 static、不放全局变量），放自己目录下的持久文件**。这就是决策 A-5"状态放持久文件，内存不留"。

#### 目录结构

```
ling/plugins/resources-manager/
├── resources_manager.so          # 代码（每次热更新替换的只是它）
└── data/                    # 持久状态（热更新前后都保留，内核不碰）
    ├── catalog.db           # SQLite：扫描目录、分类、记录（resources-manager 的唯一真源）
    ├── settings.json        # 少量杂项设置（走 core-settings 的除外）
    └── backups/             # 数据库快照（M4 之后启用）
```

**规则**：`data/` 归插件自己所有；内核不读、不写、不迁移里面的格式——格式演进是插件自己的事（`04` §9 纪律 9）。

#### 热更新时的四步流程

```
1. 停用旧版：调它的 on_deactivate → 收尾（落盘、等线程结束）
2. 卸载旧版：dlclose（或杀侧车进程）；此时旧版从内存消失，data/ 完好无损
3. 装载新版：dlopen → activate
4. 新版重读 data/catalog.db → 从上次的扫描结果继续工作
```

关键在第 2 步和第 4 步之间：**内存清零了，磁盘没动**。新版插件代码是全新的，它读磁盘文件得到上次的状态，就像什么都没发生过。

#### 手机换机类比

换手机时，通讯录不在旧手机的"内存"里（关机就没了），而在云端/备份里。新手机开机 → 登录 → 从云端拉取 → 通讯录完整恢复。插件的 `data/` 就是它的"云端"，热更新就是"换手机"。如果通讯录只存在内存里（旧手机关机），换机必然丢失——这就是禁止 static 状态的原因。

#### 为什么选"持久文件"而不是"内存状态序列化迁移"

| 方案 | 做法 | 弃用理由 |
|---|---|---|
| 内存状态序列化 | 停用时把内存里的状态 dump 成文件，装载时加载回来 | 每个插件要写一套序列化/反序列化 + 版本迁移代码；一旦新版字段变了，迁移代码极易出 bug；且 static 残留问题使"dump 的是哪个版本的状态"不可靠 |
| **持久文件（选定）** | 状态本来就在磁盘上，内存里只是"缓存" | 插件只需遵守一条纪律（不藏状态于内存）；格式迁移插件自己在读文件时做（成熟模式，SQLite 本身就这么干） |

代价：每次激活多一次磁盘读（毫秒级，可接受）；内存里不能有"必须跨激活保留"的计算中间态（要保留就先落盘）。

## 4. 侧车插件的热更新

比动态库简单，因为进程边界天然干净：

```
1. 校验新清单
2. 发 deactivate → 等 deactivated（5 秒）→ 发 shutdown → 等进程退出（5 秒，超时强杀）
3. 注销其全部效应（账本）
4. 启动新版本可执行文件 → activate
5. 失败 → 回滚：启动旧版本可执行文件 → 恢复效应
```

**注意**：侧车的 `data/` 目录在重载之间保留，插件自己负责格式迁移（`04` §9 纪律 9）。

## 5. 开发工作流（以 resources-manager 为例）

| 步骤 | 命令/动作 |
|---|---|
| 1 | 在 `resources-manager/` 下 `cargo build`（或对应语言的构建） |
| 2 | 把新产物拷到 `ling/plugins/resources-manager/`（可用构建脚本自动做） |
| 3 | `ling reload resources-manager` |
| 4 | 看输出：`ok` → 新版已激活；`error` → 已回滚，看错误信息改 |
| 5 | 观察 `ling logs resources-manager --follow` |

**首版不做**：文件监视自动重载（watch mode）。先手动 reload，稳定后再加。
