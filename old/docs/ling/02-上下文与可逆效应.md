## 1. 什么是上下文（白话拆解）

### 1.1 没有它会怎样（先看反例）

假设插件可以随手改全局状态：resources-manager 加载时直接往"全局方法表"塞了一个 `scan.start`，还直接挂了一个系统回调，又偷偷开了 3 条线程。现在用户卸载 resources-manager——**没人知道要清理这三样东西**：

- 方法表里残留一个死方法，别的插件一调就崩；
- 回调还在响应事件，往已卸载的代码里跳；
- 线程还在跑，卸载代码的瞬间整个程序崩溃。

上下文（Context）就是为消灭这种"随手改全局"而设的**唯一通道**：插件想动共享环境，只能通过它。

> 类比：物业规定业主装修必须通过物业申报，物业现场登记"动了哪面墙"并保存复原图。业主绕过物业私自拆墙，物业就无法在退租时恢复——这就是"违规效应"。

### 1.2 它具体是什么（拆开黑箱）

Context 不神秘，在 Rust 里就是一个普通的结构体，由内核在装载插件时创建、交给插件。它里面只有四样东西：

| 字段 | 是什么 | 类比 |
|---|---|---|
| `plugin_id` | "你是谁"（如 resources-manager） | 身份证 |
| `ledger` | 指向**你自己那本账**（效应登记表）的引用 | 你的办事档案 |
| `broker` | 指向内核两张共享大表的引用：方法表、订阅表 | 全局的"通讯录 + 广播名单" |
| `caps` | 从你清单里读出的能力集合（fs、network…） | 你的许可证 |

所以"黑箱"里没有魔法，每个操作都是**查表 + 写表 + 记一笔账**。

### 1.3 一次注册的 5 步内部流程（以 register_method 为例）

插件调用 `ctx.register_method("resources-manager.scan.start", 处理函数, 撤销函数)`，内核内部按顺序做 5 件事：

```
1. 查你的身份：名字必须以 "resources-manager." 开头？ 不是 → 拒绝（E_NAMESPACE_VIOLATION）
2. 查能力标注：这个方法声明了需要 fs，你清单里声明 fs 了吗？ 没有 → 拒绝（E_CAPABILITY_DENIED）
   （调用时还会再查一次：目标插件的**生效**能力 = 清单声明 − 用户撤销黑名单，见 01 §5）
3. 写共享方法表：方法表 += ("resources-manager.scan.start" → 你的处理函数，requires=fs)
4. 记一笔账：你的账本 += 第 1 条，undo = "把 scan.start 从方法表里删掉"
5. 返回成功
```

### 1.4 完整例子：用户装 resources-manager 的四步

| 步骤 | 插件调用 | 内核内部做了什么 | 账本新增 |
|---|---|---|---|
| 1 | `ctx.register_method("resources-manager.scan.start", f, un_f)` | 校验前缀→查能力→写方法表 | 第 1 条：可注销 scan.start |
| 2 | `ctx.register_method("resources-manager.dup.delete", f2, un_f2)` | 同上 | 第 2 条 |
| 3 | `ctx.subscribe("kernel.plugin.state", cb, un_cb)` | 写订阅表 | 第 3 条：可退订 |
| 4 | 用户执行 `ling uninstall resources-manager` | **倒序**执行：第 3 条退订 → 第 2 条注销 dup.delete → 第 1 条注销 scan.start → 卸载动态库 | 账本清空 |

卸载完，方法表里查不到任何 `resources-manager.*`，订阅表里没有它的回调——**和它从未来过一模一样**。这就是"卸载干净"的全部原理，没有更多了。

### 1.5 它不是什么

| 不是 | 说明 |
|---|---|
| 不是"上帝对象" | 它只有上面列的那几个能力，碰不到别的插件的内存 |
| 不是插件 | 它没有自己的业务逻辑，只是内核伸出的一只手 |
| 不落盘、不跨重启 | 每次装载新造一个，卸载就丢弃 |
| 不是状态保存机制 | 插件的业务状态放自己的持久文件（见 `05` §3.2）；Context 只管"对共享环境的修改" |

### 1.6 为什么非要这么麻烦（好处对应）

| 内核多做的一步 | 换来的能力 |
|---|---|
| 每次修改都记账 | 卸载可精确还原（目标 G2）；热更新 = 撤销旧账 + 重记新账（G4） |
| 每次注册都查前缀与能力 | 插件间隔离、权限门禁 |
| 所有互调经过内核的路由表 | 内核随时知道"谁提供了什么"，`ling doctor` 可检查、超时可统一控制 |

## 2. 上下文接口（插件视角）

### 2.1 Rust 接口（进程内插件）

```rust
// 插件装载时由内核注入，插件只持有这个句柄
pub struct Context { /* 内核私有字段，插件不可直接构造 */ }

impl Context {
    // —— 方法注册（效应种类 1）——
    // 撤销函数不可省略：编译期强制（P3 纪律的落地）
    // requires：本方法需要的能力（如 fs）；注册时校验 ⊆ 本插件清单 capabilities，
    //           调用时由门禁核对目标插件的生效能力（01 §5、04 §3.2）
    pub fn register_method(
        &self,
        name: &str,                       // 必须带本插件编号前缀，如 "resources-manager.scan.start"
        handler: Box<dyn Fn(Value) -> Result<Value, CallError> + Send + Sync>,
        unregister: Box<dyn FnOnce() + Send>,   // ← 撤销函数
        requires: Option<Capability>,          // ← 可选：方法所需能力标注
    ) -> Result<(), ContextError>;

    // —— 跨插件调用（不产生新效应，只是使用路由）——
    pub fn call(&self, plugin: &str, method: &str, args: Value)
        -> Result<Value, CallError>;
    pub fn call_async(&self, plugin: &str, method: &str, args: Value)
        -> BoxFuture<'static, Result<Value, CallError>>;

    // —— 事件（效应种类 2：订阅；广播不记账）——
    pub fn subscribe(
        &self,
        topic_pattern: &str,              // 如 "core-ui.*" 或 "ledger.file.archived"
        callback: Box<dyn Fn(Value) + Send + Sync>,
        unsubscribe: Box<dyn FnOnce() + Send>,
    ) -> Result<(), ContextError>;
    pub fn emit(&self, topic: &str, payload: Value) -> Result<(), ContextError>;

    // —— 能力查询（读自己清单）——
    pub fn has_capability(&self, cap: Capability) -> bool;

    // —— 自己的数据目录（ling/plugins/<编号>/data/，内核保证存在）——
    // 持久状态一律放这里（A-5 纪律）；路径知识属内核，插件不该自己拼
    pub fn data_dir(&self) -> PathBuf;

    // —— 停用/卸载收尾回调（效应种类 5）——
    pub fn on_deactivate(&self, callback: Box<dyn FnOnce() + Send>);

    // —— 调试：查看自己的账本 ——
    pub fn ledger(&self) -> &[LedgerEntry];
}
```

### 2.2 界面贡献为什么不放在上下文里

界面贡献（页面、菜单）由 **core-ui 插件**提供接口，插件通过 `context.call("core-ui", "ui.contribute", …)` 登记。

原因：极简内核决策（`01` 附录 A-2）——**凡是"没有 core-ui 也该能跑"的东西，都不能进内核**。服务器场景不装 core-ui，插件照样能装载、互调，只是没界面。

内核层面，这次调用本身不记账；**记账发生在 core-ui 那一侧**：core-ui 收到贡献请求后，把它自己的"移除该贡献"记入自己的账本，并在收到"某插件被卸载"的内核事件时自动撤下对应界面。

### 2.3 侧车插件（非 Rust）的等价接口

侧车通过本地套接字收到同样的语义，帧格式见 `04-插件接口规范.md` §6：

| 本地 Rust 方法 | 侧车帧（JSON） |
|---|---|
| `register_method` | `{"op":"register_method","name":...,"unregister":...}`（侧车注销时由宿主代为执行注销） |
| `subscribe` | `{"op":"subscribe","pattern":...}` |
| `call` | `{"op":"call","plugin":...,"method":...}` |
| 宿主 → 侧车 | `{"op":"invoke","method":...,"args":...}` |

**差异说明**：进程内插件交出的是撤销**函数**；侧车无法交函数，改为**语义声明**——"我注册了 X"，宿主知道怎么替它撤销 X（注销方法、退订事件）。这是双轨下对 P3 的等价实现。

## 3. 效应账本（Effect Ledger）

### 3.1 数据结构

每个插件一条账本，只增不改，卸载时倒序消费：

```rust
struct LedgerEntry {
    seq: u64,                    // 递增序号，卸载按此倒序执行
    kind: EffectKind,             // 效应种类
    desc: String,                 // 人可读描述（用于 ling doctor 与错误报告）
    undo: Box<dyn FnOnce() -> Result<(), UndoError>>,
}

enum EffectKind {
    MethodRegistered,     // 注册了接口方法
    EventSubscribed,      // 订阅了事件
    ConfigWritten,        // 写了配置条目（经 context 的配置代理，见 §3.3）
    SidecarStarted,       // 启动了侧车进程
    DeactivateCallback,   // 登记了停用回调
}
```

### 3.2 五类效应与对应的撤销手段

| 效应种类 | 触发动作 | 撤销手段 | 撤销失败的后果 |
|---|---|---|---|
| MethodRegistered | 插件注册接口方法 | 内核从路由表删除该方法 | 残留一个可被调用的方法（严重） |
| EventSubscribed | 插件订阅事件 | 内核移除订阅项 | 残留回调，广播时被调用（严重） |
| ConfigWritten | 插件经上下文写配置 | 删除该键 | 残留配置（轻微） |
| SidecarStarted | 插件启动侧车进程 | 终止进程并等待退出（超时 5 秒后强制结束） | 进程残留（中等） |
| DeactivateCallback | 插件登记停用回调 | 丢弃该回调 | 无 |

> **注**：开线程、开文件句柄不单独入账，因为它们**属于插件自身的内存资源**——插件被卸载时动态库整体卸出，线程必须在 `on_deactivate` 里自行收敛（等待结束或取消）。侧车插件则是整个进程被终止。这条边界在 `04` 的插件作者纪律里写明。

### 3.3 配置条目为什么经上下文

插件可能需要跨调用保存少量设置（开关、路径）。按极简决策内核不提供配置存储，但**插件若直接写自己的文件**，卸载时无法区分"临时状态"与"用户配置"。

折中方案：
- 插件**运行时状态** → 自己的数据目录 `ling/plugins/<编号>/data/`，卸载时**保留**（用户数据）。
- 插件**需要内核知晓的设置**（如"是否随宿主自启"）→ 经 `context.set_config(key, value)` 写入，**卸载时删除**（进账本）。存储位置：**`ling/config.json`**（内核拥有的键值文件，键带插件编号前缀；与 `registry.json`、`session.json` 平级，路径约定见 `../../docs-common/01` §2.3）。

两者区别用注释写清：**状态是插件的私产，配置是宿主管辖的登记**。

### 3.4 账本的操作规则

| 规则 | 说明 |
|---|---|
| 只追加 | 运行期不修改已有序号；热更新时旧账本整体作废（新版本重新记） |
| 倒序执行 | 卸载时从最大序号向 1 执行，保证"后注册的先注销"（例如先注销依赖后注册方法的回调） |
| 单条失败不停止 | 一条撤销报错 → 记录 → 继续下一条；全部执行完汇报"卸载是否完整 + 失败清单" |
| 卸载前先停下游 | 依赖本插件的其他插件先被停用（它们各撤各的账），再撤本插件的账 |
| 不落盘 | 账本在内存中；进程崩溃后账本丢失——**重启时内核以"空装载表"启动**，插件重新装载、重新记账，天然自洽 |

## 4. 卸载流程（完整时序）

以卸载 `resources-manager` 为例，假设 `ledger`（记账插件）依赖它：

```
ling uninstall resources-manager
  │
  ├─ 1. 依赖图重算：发现 ledger 因失去依赖必须停用
  │
  ├─ 2. 停用 ledger
  │     ├─ 调用 ledger 的 on_deactivate 回调（落盘收尾）
  │     └─ 倒序执行 ledger 的账本 → 撤销它的全部效应
  │
  ├─ 3. 停用 resources-manager 本体
  │     ├─ 调用其 on_deactivate 回调
  │     └─ 倒序执行 resources-manager 的账本：
  │          第 5 条 ← 停止它的侧车（如有）
  │          第 4 条 ← 删除配置条目
  │          第 3 条 ← 退订 topic "core-ui.*"
  │          第 2 条 ← 退订 topic "kernel.plugin.state"
  │          第 1 条 ← 注销方法 resources-manager.scan.start / dup.list / …
  │
  ├─ 4. 卸载动态库（Linux dlclose / Windows FreeLibrary）
  │     └─ 失败 → 记录，标记"卸载不完整"，但继续（不卡死宿主）
  │
  ├─ 5. 装载表移除 resources-manager；移除安装工件（plugin.toml、动态库），`data/`
  │     文件保留在插件目录（uninstall 可选 --purge 连数据删除）
  │
  └─ 6. 触发配置调和 → 重算依赖图 → 可能有等待中的插件被激活
```

**验收断言**（写进 L2 的测试）：卸载后，向内核查询 `resources-manager.*` 的任何方法都返回"方法不存在"；广播任意事件，resources-manager 的回调不再被调用；`ling plugins` 不再列出它。

## 5. 热更新如何复用同一套账本

热更新不是新机制，而是**账本的两次完整消费**：

```
ling reload resources-manager
  1. 停用当前版本 → 倒序执行账本（和卸载第 2、3 步完全一样）
  2. 卸载旧动态库
  3. 用新版本的清单 + 新动态库走装载流程 → 重新记一本新账
  4. 依赖解析 → 激活 → 广播状态事件
  失败分支：第 3 步失败 → 用旧动态库重新装载（回滚）→ 报告失败原因
```

细节与 Rust 动态库的坑见 `05-热更新.md`。

## 6. 违规效应：为什么禁止、如何发现

| 违规行为 | 举例 | 后果 |
|---|---|---|
| 直接注册全局回调 | 不经 Context 直接挂系统钩子 | 卸载后残留，无法撤销 |
| 绕过路由调用别的插件内部函数 | 直接调用 resources-manager 的库函数 | 绕过能力门禁与命名空间隔离 |
| 静态变量持有状态 | `static CACHE: Mutex<…>` | 热更新时新旧版本共享同一静态区（见 05 §3），导致未定义行为 |
| 自开线程且不在 on_deactivate 里收敛 | 扫描线程永远跑着 | 卸载动态库时线程仍在执行该库代码 → 崩溃 |

**发现手段**：
1. 代码审查清单（`04` §9）；
2. L4 后提供 `ling doctor <插件>`：检查方法/订阅是否带前缀、是否经上下文登记、是否有未收敛线程的迹象；
3. 卸载时账本为空但插件运行过 → 警告"该插件可能从未正确登记效应"。
