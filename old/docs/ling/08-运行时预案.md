# ling 08 运行时预案

> 版本：v0.1 ｜ 状态：已封档（终审通过）
> 本文是**运维手册**：ling 运行过程中出了问题，照着哪一行做。
> 与 `01-宿主设计.md` §8 的分工：§8 是**设计时**的风险登记册（"什么可能出错、怎么预防"）；本文是**运行时**的处置步骤（"已经出错了、现在怎么办"）。
> 公共术语见 `../../docs-common/01-公共术语与约定.md`。

## 0. 怎么用这份手册

| 你的情况 | 看哪 |

| 热更新失败 | §2.3 |

---

## 1. 通用排查三步（先做这三步，再查具体条目）

| # | 步骤 | 命令 / 动作 |
|---|---|---|
| 1 | 看状态 | `ling plugins` —— 哪些插件是"已激活"、哪些"已停用"、哪些"崩溃"？ |
| 2 | 看日志 | `ling logs <插件编号> --follow` —— 最后一条错误是什么？没有日志插件时看终端输出 |
| 3 | 看依赖 | `ling doctor` —— 依赖图是否健康？有没有"待激活（依赖未满足）"的插件？ |

> 三步之后仍不明朗 → 按下面的具体条目逐条对照；都不匹配 → 带着这三步的输出报 issue。

## 2. 具体预案

### 2.1 界面白屏 / 某插件界面没反应

| 项 | 内容 |
|---|---|
| **现象** | 浏览器打开 `127.0.0.1:7910` 白屏；或某插件的页面打不开、按钮点了没反应 |
| **可能原因** | ① core-ui 插件未激活/崩溃；② 该插件未激活；③ 浏览器缓存了旧页面；④ 会话口令不对 |
| **处置步骤** | 1. `ling plugins` 看 core-ui 和目标插件状态<br>2. 崩溃 → `ling restart core-ui`（或 `ling restart <插件>`）<br>3. 停用 → `ling enable <插件>`<br>4. 状态正常 → 浏览器强制刷新（Ctrl+Shift+R）<br>5. 仍白屏 → `ling logs core-ui` 看错误 |
| **预防** | 无特殊预防；此问题不丢数据 |

### 2.2 插件反复崩溃

| 项 | 内容 |
|---|---|
| **现象** | `ling plugins` 显示某插件"崩溃"；`kernel.plugin.state crashed` 事件反复出现 |
| **可能原因** | ① 插件代码 bug；② data/ 目录权限问题；③ 侧车插件的可执行文件损坏 |
| **处置步骤** | 1. `ling disable <插件>` —— 先停用，防止崩溃风暴<br>2. `ling logs <插件>` 定位崩溃点<br>3. 权限问题 → 检查 `ling/plugins/<编号>/data/` 属主与权限<br>4. 修复后 `ling enable <插件>`<br>5. 无法修复 → `ling uninstall <插件>`（崩溃不影响卸载，账本会清理） |
| **预防** | 写插件时遵守 `04` §9 作者纪律（禁 static 状态、deactivate 收敛线程） |

### 2.3 热更新失败

| 项 | 内容 |
|---|---|
| **现象** | `ling reload <插件>` 返回 `E_RELOAD_FAILED`；或成功但插件行为异常 |
| **可能原因** | ① 新版本清单校验失败；② 新动态库装载失败（符号缺失、编译不兼容）；③ 新版本 activate 返回错误；④ 旧动态库 dlclose 失败（有未收敛线程） |
| **处置步骤** | 1. 读错误信息：内核**已自动回滚旧版**（设计保证），宿主状态与 reload 前一致<br>2. 清单错误 → 改 plugin.toml 后重试<br>3. 装载/激活错误 → 检查新动态库编译目标、api 版本<br>4. dlclose 失败 → 旧版插件有未收敛线程，查 `04` §9 纪律 5；必要时 `ling restart <插件>` 而非 reload<br>5. 反复失败 → 放弃该版本，换回上一个可用版本 |
| **预防** | 遵守 `05` §3 的四个坑位对策；开发期先单插件 reload 验证再全量 |

### 2.4 卸载报"卸载不完整"

| 项 | 内容 |
|---|---|
| **现象** | `ling uninstall <插件>` 输出"卸载不完整：第 N 条撤销失败（…）" |
| **可能原因** | ① 某个撤销函数内部出错（如方法表已被手动清空）；② 侧车进程 5 秒内未退出被强杀；③ 内核 bug |
| **处置步骤** | 1. 读失败清单：哪一条效应、什么错误<br>2. 立即影响评估：残留的是方法（还能被调用）还是订阅（还会被广播）？<br>3. `ling doctor <插件>` 列出未撤销项<br>4. 重启 ling（`ling shutdown` 后重新 `ling serve`）—— **重启后装载表清空，残留效应自然消失**<br>5. 报 issue：附失败清单和插件版本 |
| **预防** | 插件作者保证撤销函数正确（`02` §3.2）；内核逐条容错设计已保证"一条失败不影响其余" |

### 2.5 装插件时报依赖错误

| 项 | 内容 |
|---|---|
| **现象** | `ling install` 返回 `E_DEPENDENCY_UNMET` 或 `E_DEPENDENCY_CYCLE` |
| **可能原因** | ① 依赖的插件未安装；② 版本不匹配（主版本不同）；③ 依赖成环 |
| **处置步骤** | 1. `E_DEPENDENCY_UNMET` → 看缺哪个插件、要什么版本 → 安装它<br>2. 版本不匹配 → 升级被依赖方，或换用兼容版本的依赖方<br>3. `E_DEPENDENCY_CYCLE` → 错误信息里有环路（如 `a → b → a`）→ 手动禁用环上一个插件打破循环<br>4. 以上都不是 → `ling doctor` 查看完整依赖图 |
| **预防** | 设计插件时避免循环依赖；版本要求用主版本匹配（`@1`）而非精确版本 |

### 2.6 端口被占用 / 连不上

| 项 | 内容 |
|---|---|
| **现象** | 启动报端口占用；或浏览器/命令行连不上 7910/7900 |
| **可能原因** | ① 端口被其他程序占用（ling 会自动顺延）；② 实际端口已顺延但客户端读了旧端口；③ 只监听 127.0.0.1，外部访问当然不通 |
| **处置步骤** | 1. 查实际端口：`cat ling/registry.json`<br>2. 客户端（浏览器/窗口壳/rmgr 命令行）都从 registry.json 读端口——若手动指定了旧端口，改掉<br>3. 确认访问的是 `127.0.0.1`（不是局域网地址）<br>4. registry.json 损坏 → 删除它，重启 ling 重新生成 |
| **预防** | 无；自动顺延 + registry.json 已是完整方案 |

### 2.7 会话口令丢失

| 项 | 内容 |
|---|---|
| **现象** | HTTP 请求返回 401 / `E_AUTH`；找不到或弄丢了 `ling/session.json` |
| **可能原因** | ① 文件被删；② 权限不对（非 0600）导致 ling 拒绝使用；③ 复制到别的机器导致口令不匹配 |
| **处置步骤** | 1. `ling shutdown` 停止宿主<br>2. 删除 `ling/session.json`<br>3. 重新 `ling serve` —— 启动时自动生成新口令<br>4. 浏览器重新粘贴新口令；窗口壳/命令行自动读取新文件 |
| **预防** | 不要把 session.json 复制到别的机器；它只对本机的 ling 实例有效 |

### 2.8 内核升级后插件全部加载失败

| 项 | 内容 |
|---|---|
| **现象** | 替换新版 ling 二进制后启动，`ling plugins` 显示所有插件"装载失败"，错误提示 api 不匹配 |
| **可能原因** | ① 新内核 api 主版本升高，插件清单的 `api` 字段指向旧版本；② 新内核移除了插件用到的接口 |
| **处置步骤** | 1. 读错误信息确认 api 要求（"插件面向 api=1，宿主提供 api=2"）<br>2. **短期**：换回旧版 ling 二进制（插件数据在持久文件，不受影响）<br>3. **正解**：等插件发布兼容新 api 的版本，`ling install` 升级插件<br>4. 若只有个别插件不兼容 → 升级那几个插件即可 |
| **预防** | 内核升级遵循 N/N-1 兼容策略（见 `01` §9 内核更新策略）；升级前备份 ling 目录 |

### 2.9 数据库损坏 / 数据异常

| 项 | 内容 |
|---|---|
| **现象** | 插件报数据库错误；扫描统计数字明显不对；记录同步后数据错乱 |
| **可能原因** | ① 断电导致 SQLite 文件损坏；② 插件版本回退后表结构不兼容；③ 磁盘故障 |
| **处置步骤** | 1. 停止相关插件（`ling disable <插件>`）避免进一步写入<br>2. 备份当前 `data/` 目录（保留现场）<br>3. SQLite 自带恢复：`sqlite3 catalog.db ".recover" | sqlite3 catalog.recovered.db`<br>4. 用恢复后的文件替换原文件，重新 enable<br>5. 无法恢复 → 从更早的备份恢复（见 resources-manager 的备份设计）<br>6. 记录同步场景：另一台设备的记录可重新同步回来（记录同步是幂等的） |
| **预防** | 保持 SQLite WAL 模式；定期备份 data/ 目录；升级插件前自动快照（resources-manager M4 的 snapshot 机制） |
