## 1. 需求声明（Requires）

### 1.1 两种需求

| 需求类型 | 白话 | 例子（记账插件的清单片段） |
|---|---|---|
| **能力需求** | 我需要宿主给我开某项权限 | `capability:fs`（读写文件）、`capability:network`（访问局域网） |
| **插件需求** | 我需要某个插件提供某方法，且版本兼容 | `plugin:resources-manager@1`（主版本 1 的 resources-manager） |

```toml
# ledger/plugin.toml 片段
[plugin]
id = "ledger"
version = "0.1.0"
api = "1"

[requires]
capabilities = ["fs"]
plugins = ["resources-manager@1"]      # 主版本匹配即可，不要求精确小版本
```

### 1.2 版本匹配规则

| 写法 | 含义 | 例 |
|---|---|---|
| `resources-manager@1` | 主版本 1，任意次版本 | 匹配 1.0.0、1.4.2 |
| `resources-manager@1.2` | 主 1 次 2，任意修订 | 匹配 1.2.0、1.2.9 |
| `resources-manager@1.2.3` | 精确版本 | 仅匹配 1.2.3 |
| `resources-manager` | 任意版本（不推荐，留给开发调试） | 匹配任何版本 |

**规则**：按段前缀相等判定——约束段数 1–3，须与目标版本的对应前缀段逐一相等（`@1` 匹配 `1.x.y`，`@1.2` 匹配 `1.2.x`，`@1.2.3` 精确）。主版本不同 = 不兼容，拒绝激活。次版本不同 = 兼容（遵循语义化版本惯例：次版本只增不破）。

### 1.3 能力清单（首版固定集）

| 能力编号 | 白话 | 内核如何校验 |
|---|---|---|
| `fs` | 读写用户文件系统 | 只校验清单声明了它（内核不拦具体文件路径，靠插件自律；门禁管的是"有没有资格"不是"具体动哪个文件"） |
| `network` | 访问局域网或公网 | 同上 |
| `ui` | 向界面贡献页面/菜单 | 调 core-ui 时校验 |
| `shell` | 执行外部命令 | 同上 |

> 能力集以后可能扩展；新增能力由内核版本升级引入，插件清单里出现未知能力 → 装载失败并提示"宿主版本过旧"。

## 2. 依赖图

### 2.1 节点与边

| 元素 | 说明 |
|---|---|
| 节点 | 每个**已安装**插件一个节点；每个**已声明**的能力一个节点 |
| 边 | 插件 → 能力（需要该能力）；插件 → 插件（需要该插件） |
| 方向 | 从"需求方"指向"被需求方"。读作"我指着你，你倒了我也会倒" |

```
ledger ──requires──▶ resources-manager ──requires──▶ core-ui
  │                      │
  └──requires──▶ [capability:fs]  └──requires──▶ [capability:ui]
```

### 2.2 校验规则（装载前）

| # | 检查 | 失败处理 |
|---|---|---|
| 1 | 所有 `requires` 指向的目标**已安装** | 缺失 → 该插件标记为"待激活（未满足）"，不报错；安装是允许的，只是不激活 |
| 2 | 版本匹配 | 不匹配 → 同上，待激活 |
| 3 | **无循环依赖** | 成环 → 拒绝安装，报出环路（`a → b → a`） |
| 4 | 能力在已知集内 | 未知能力 → 拒绝安装（宿主版本过旧） |

### 2.3 三种判定状态

对每个**已安装**插件，每次配置变化后重新判定：

| 状态 | 条件 | 执行动作 |
|---|---|---|
| **activating（激活中→已激活）** | 全部 `requires` 满足，且当前未激活 | 装载动态库/启动侧车 → 注册效应 → 标记已激活 |
| **deactivating（停用中→已停用）** | 任一 `requires` 不再满足，且当前已激活 | on_deactivate → 倒序撤销账本 → 标记已停用（文件保留） |
| **neutral（不动）** | 满足状态与当前激活状态一致 | 什么都不做 |

## 3. 激活顺序与停用顺序

### 3.1 拓扑排序

- **激活**：按依赖图拓扑序（被依赖者先激活）。例：core-ui → resources-manager → ledger。
- **停用**：**反向**拓扑序（依赖者先停用）。例：ledger → resources-manager → core-ui。

理由：激活时先备好"被依赖方"，停用时先撤走"使用方"，保证任何时刻都不会有插件指向一个已被拆除的目标。

### 3.2 激活计划（Activation Plan）

配置调和算出的一次性有序清单：

```json
{
  "plan_id": "20261015-001",
  "steps": [
    {"action": "activate", "plugin": "core-ui",     "reason": "被 resources-manager 依赖"},
    {"action": "activate", "plugin": "resources-manager","reason": "新安装"},
    {"action": "activate", "plugin": "ledger",      "reason": "依赖已满足"}
  ]
}
```

| 性质 | 含义 |
|---|---|
| 原子性 | 任何一步失败 → 已执行步骤按账本倒序回滚；装载表恢复到调和前 |
| 可观察 | 每步完成后广播 `kernel.plugin.state` 事件（载荷：插件编号、新状态、原因） |
| 可取消 | 执行中可取消；取消 = 回滚已执行步骤 |
| 防抖 | 200 毫秒内连续多次配置变化只触发一次调和（默认值，可通过管理端口调整） |

## 4. 配置调和全流程

```
触发（install / uninstall / enable / disable / upgrade / requires 变更）
  │
  ├─ 等待防抖窗口（200ms）
  │
  ├─ 重建依赖图（全量，不增量——插件数量级为几十，全量 <1ms）
  │
  ├─ 校验（§2.2 四条）
  │    └─ 失败 → 整体回滚配置，报告错误，结束
  │
  ├─ 判定每个插件（§2.3）
  │
  ├─ 生成激活计划（拓扑序，§3.1）
  │
  └─ 逐步执行
       ├─ 每步：激活 or 停用（内部走 02 文档的账本流程）
       ├─ 每步完成 → 广播 kernel.plugin.state
       ├─ 失败 → 回滚已执行步骤 → 报告
       └─ 完成 → 报告最终装载表
```

## 5. 边界情况

| 情况 | 处理 |
|---|---|
| 插件 A 声明依赖 B，但 B 尚未安装 | A 标记"待激活"；B 安装后下次调和自动激活 A |
| 升级 B 后 A 的需求不再满足 | 调和判定 A 为 deactivating → 停用 A；B 升级失败则回滚 |
| 循环依赖 | 拒绝安装新插件；已有插件的 requires 改动导致成环 → 拒绝该改动并回滚 |
| 某插件激活失败（动态库损坏） | 该步失败 → 整个计划回滚；不影响未参与计划的插件 |
| 侧车进程启动失败 | 同上，按激活失败处理 |
| 插件自己崩溃（运行中） | 内核广播 `kernel.plugin.state`（state=crashed）；core-plugin-manager 显示"崩溃"；不自动重启（避免风暴），用户手动重启或 `ling restart <插件>` |
| 极端：核心插件 core-ui 自身被卸载 | 允许，但管理界面消失；命令行与管理端口仍可用 |
