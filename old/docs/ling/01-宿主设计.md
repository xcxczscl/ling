## 1. 目标与非目标

### 1.1 目标

| # | 目标 | 可验证的表述 |
|---|---|---|
| G1 | 一切皆插件 | 卸掉所有插件后，ling 主程序仍能启动，且不提供任何用户可感知功能 |
| G2 | 卸载干净 | 卸载任意插件后，环境与"该插件从未装过"在观测上无法区分（效应账本保证） |
| G3 | 依赖自动传导 | 装/卸插件后，受影响的其他插件自动激活/停用，**不需要重启宿主** |
| G4 | 热更新 | 更换单个插件版本时，宿主与其他插件不停机 |
| G5 | 跨语言 | 支持非 Rust 插件，且**不降低 Rust 插件的调用性能** |
| G6 | 崩溃不扩散 | 单个侧车插件崩溃，宿主与其他插件照常工作；账本可清理其遗留效应 |
| G7 | 极简内核 | 内核只有 4 项服务，其余能力由插件提供 |

### 1.2 非目标（明确不做）

| 非目标 | 理由 |
|---|---|
| 不做用户界面 | 界面是 core-ui 插件的事 |
| 不做配置存储、作业调度、日志框架 | 极简决策：这三样做成**内置插件**（core-settings / core-job / core-log），不进内核（见附录 A-2、`06`） |
| 不做插件市场/在线安装 | 以后可由插件实现 |
| 不做进程内安全沙箱 | 插件是自己写的第一方代码；内存隔离只在侧车轨道天然存在 |
| 不做形式化验证 | 采纳论文的工程机制，不实现其数学演算（见 `../../docs-common/02-时空可组合性机制说明.md` §4.2） |
| 第一轮不做跨平台打包 | 先在 Linux/Windows 开发环境跑通 |

## 2. 四条设计原则

| # | 原则 | 白话 | 违反后果 |
|---|---|---|---|
| P1 | **零内容** | 宿主只提供机制，不提供任何用户能感知的功能 | 宿主变成又一个"什么都有"的大程序，插件失去存在意义 |
| P2 | **一切经上下文** | 插件对共享环境的任何修改必须通过 `Context` 对象 | 无法记账 → 卸载不干净、热更新不可用 |
| P3 | **修改必可逆** | 每次修改必须同时提供撤销方法 | 同上 |
| P4 | **需求必声明** | 依赖必须写进清单的 `requires`，宿主据此自动激活/停用 | 依赖变化要靠人工重启，插件多了管不过来 |

P2–P4 合起来就是论文的"时空可组合性"在工程上的三条纪律，见 `../../docs-common/02-时空可组合性机制说明.md`。

## 3. 总体结构

### 3.1 分层图

```
┌────────────────────────── 表现层（全部由插件提供） ──────────────────┐
│  core-ui 插件：本机网页服务 + 界面壳        浏览器 / 窗口视图        │
│  ling 命令行：连接内核管理端口                                          │
├────────────────────────── 插件层 ────────────────────────────────┤
│  内置插件（builtin-plugins/，从属 ling，可卸载）：                   │
│    core-ui · core-settings · core-plugin-manager  （默认安装）      │
│    core-job · core-log                            （可选安装）      │
│  业务插件：resources-manager · player · ledger · sites …（用户自行安装）       │
│  插件之间：经内核调用路由互调；经事件总线互听                           │
├────────────────────────── ling 内核（只有 4 项服务 + 3 个机制） ──────┤
│  服务：① 接口方法路由  ② 事件广播  ③ 能力门禁  ④ 依赖解析与自动激活  │
│  机制：上下文 Context · 可逆效应账本 · 配置调和（属④的执行部分）       │
│  通道：管理端口（命令行专用）· 装载器（动态库/侧车）                    │
├────────────────────────── 平台层 ─────────────────────────────────┤
│  Rust 运行时 · 动态链接库装卸载 · 本地套接字 · TLS                     │
└────────────────────────────────────────────────────────────────────┘
```

### 3.2 内核 4 项服务的职责边界

| # | 服务 | 做什么 | **不做什么** |
|---|---|---|---|
| 1 | **接口方法路由** | 登记"哪个插件提供哪些方法"；把调用转给目标插件；同进程直调，跨进程走套接字 | 不理解方法的业务含义；不做参数校验之外的逻辑 |
| 2 | **事件广播** | 接收一个插件的广播，投递给所有订阅者；按主题模式匹配（如 `resources-manager.*`） | 不落盘、不重投、不保证投递成功（订阅者崩溃就跳过并记录） |
| 3 | **能力门禁** | 方法可标注所需能力（注册时校验 ⊆ 本插件清单）；**调用瞬间**核对目标插件的**生效**能力（清单声明 − 用户撤销黑名单），不符即拒绝 | 不解释能力语义（"读写文件"具体指什么由插件自己实现）；授权 UI 属于 core-plugin-manager |
| 4 | **依赖解析与自动激活** | 读清单建依赖图 → 校验（版本匹配、无环）→ 计算激活计划 → 依次装载/激活/停用 | 不保存插件业务数据 |

> **配置调和**（论文术语）不是第 5 项服务，而是第 4 项服务的**执行方式**：任何配置变化（安装、卸载、启用、停用、升级）都会触发一次"重算激活计划并逐步执行"，可中途取消。

**四项服务全部留在内核，但代码按模块组织**：`broker.rs`（路由）/ `bus.rs`（事件）/ `caps.rs`（门禁）/ `deps.rs`（依赖与调和）。这样做的理由与边界：

| 决策 | 理由 |
|---|---|
| 路由、事件留在内核 | 它们是插件互调的**数据结构本身**（两张大表）；做成插件等于把"门"装在另一个插件里——每次调用多一跳，且该插件崩溃则全系统瘫痪 |
| 门禁、依赖解析留在内核 | 门禁与路由查同一张方法表，拆开无收益；依赖解析驱动装载器（内核特权操作），做成插件需要引入"特权插件"概念 + 鸡生蛋引导问题 |
| 未来可替换性 | 编译时可替换：真有需求时把某个模块抽成独立 crate 仍编译进内核。运行时不可替换——对个人工具足够 |

**内核全景（4 服务 + 3 机制 + 2 通道）**：

```
插件代码 ──只能碰到──▶ Context（机制①，唯一的门）
                          │ 门后：
                          ├─ 效应账本（机制②）：门每办一件事记的账
                          ├─ 方法路由（服务①）：大表"谁提供什么方法"
                          ├─ 事件广播（服务②）：大表"谁订阅了什么"
                          ├─ 能力门禁（服务③）：查方法表时顺手查许可证
                          ├─ 配置调和（机制③）：环境变了重算该激活谁
                          └─ 依赖解析（服务④）：调和用的图算法
                          │ 对外靠两条通道：
                          ├─ 装载通道（dlopen / 启动侧车）：代码怎么进来
                          └─ 管理端口（127.0.0.1:7900）：命令行怎么管理运行中的宿主
```

**每个组件"什么时候用上、没有它会怎样"**：

| 组件 | 什么时候你会撞上它 | 没有它会怎样 |
|---|---|---|
| 方法路由 | 记账插件调 `resources-manager.scan.stats`（它不知道 resources-manager 怎么实现，只交给路由） | 记账插件得直接链接 resources-manager 的代码——循环依赖、无法单独卸载 |
| 事件广播 | 扫描完成广播 `resources-manager.scan.done`；界面、记账、备份插件各自订阅，发的人不知道也不需要知道谁在听 | resources-manager 得维护"完成后通知谁"的名单，每加一个订阅者改一次代码 |
| 能力门禁 | 记账插件没声明 `fs` 却想调 `dup.delete`（真删文件）→ 调用瞬间被拒 | 插件一旦装载就无所不能，"装了 = 同意清单上写的事"失去意义 |
| 依赖解析 | 先装记账插件（依赖 resources-manager）、后装 resources-manager → 装上的瞬间记账插件自动激活，无需重启 | 插件多了以后，装卸引发的连锁反应全靠人脑，管不过来 |
| Context | 插件每次想注册方法/订阅事件 | 插件随手改全局，卸载无法还原（黑箱拆解见 `02`） |
| 效应账本 | 卸载/热更新时按账倒序还原 | 卸载留垃圾：死方法、残留回调、跑飞的线程 |
| 配置调和 | 装/卸/启停任何插件后，自动推导并执行激活计划 | 每次配置变化要人工重启或手动点启用 |
| 装载通道 | `ling install` 时代码进入进程 | 代码进不来 |
| 管理端口 | `ling plugins` / `ling reload` 连上运行中的宿主 | 只能杀进程重启 |

### 3.3 上下文（Context）——插件看到的 ling 全貌

插件被装载时拿到一个 `Context` 句柄，它只暴露这些操作：

| 分组 | 操作 | 说明 |
|---|---|---|
| 方法注册 | `register_method(名字, 处理函数, 撤销函数)` | 注册时**必须**同时给出撤销函数（P3 强制） |
| 方法调用 | `call(插件, 方法, 参数)` / `call_async(...)` | 跨插件调用；内核查目标插件是否已激活 |
| 事件 | `emit(主题, 载荷)` / `subscribe(主题模式, 回调, 撤销函数)` | 订阅同样必须给撤销函数 |
| 能力查询 | `has_capability(能力)` | 读自己清单声明 |
| 效应查询 | `ledger()` | 查看自己的账本（调试/日志用） |
| 停用通知 | 注册 `on_deactivate(回调)` | 停用/卸载前收到通知，用于落盘收尾（**不是**状态保存的替代） |

**插件拿不到的东西**：直接访问其他插件的内存、绕过上下文注册回调、修改清单、加载其他动态库。

### 3.4 效应账本的结构与卸载流程

**账本**：每个插件一份，是一条条有序记录，每条 = `{序号, 效应种类, 撤销闭包}`。

```
卸载插件 X 的流程：
  1. 按依赖图找出"因 X 存在才激活"的下游插件 → 先把它们停用（它们各自撤销自己的效应）
  2. 调用 X 的 on_deactivate 回调（让它落盘收尾）
  3. 取 X 的账本，按序号倒序逐条执行撤销闭包
     - 注销它注册的所有方法
     - 退订它的所有事件
     - 撤下它的界面贡献（由 core-ui 执行，通过调用路由）
     - 写入的配置条目删除
     - 停止它的侧车进程（如是侧车插件）
  4. 从装载表中移除 X，标记为"未安装"
     - 文件语义：移除安装工件（`plugin.toml`、动态库、侧车可执行文件），
       `data/` 用户数据保留在插件目录；`--purge` 连 `data/` 一并删除
     - "已安装"判定 = `plugin.toml` 存在（目录仅剩 `data/` 即未安装，可重装并合并原数据）
  5. 触发一次配置调和（重算依赖图，可能激活等待中的其他插件）
```

**保证**：第 3 步任何一条撤销失败 → 记录错误并继续执行其余（避免卡死），最后报告"卸载不完整"并给出清单；**正常情况下全部成功**，因为撤销方法是插件作者随注册一起提供的。

## 4. 进程与线程模型

### 4.1 进程布局

| 进程 | 内容 | 生命周期 |
|---|---|---|
| **ling 主进程** | 内核 + 全部 Rust 插件（进程内动态库） | 常驻，直到 `ling shutdown` |
| 侧车进程 ×N | 每个非 Rust 插件一个独立可执行文件 | 随该插件装载而启动，随卸载/停用而结束 |
| `ling` 命令行 | 独立小进程，连管理端口 | 执行一次命令即退出 |
| 窗口视图（可选） | 指向 core-ui 端口的系统 WebView | 用户开关，不影响宿主 |

### 4.2 线程（ling 主进程内）

| 线程 | 职责 | 数量 |
|---|---|---|
| 主线程 | 运行时事件循环：定时器、信号、动态库装卸载（**动态库的加载/卸载必须串行**） | 1 |
| 异步运行时线程池 | 方法路由、事件投递、管理端口、侧车套接字 | 按 CPU 核数 |
| 侧车监控线程 | 监视侧车进程退出、异常、重启策略 | 1（管理多个子进程） |

> 插件自己的重活（扫描、哈希、业务计算）在插件自己开的线程里跑，内核不干预——只要该插件在停用/卸载时能自行收敛（`on_deactivate` 里等待或取消自己的任务）。

### 4.3 内存与性能纪律

| 纪律 | 要求 |
|---|---|
| 方法调用开销 | 同进程 Rust 插件之间为一次函数调用 + 两次内核查表，目标 < 1 微秒；**侧车插件不影响这条路径** |
| 事件投递 | 同步派发；单个订阅者回调超时（默认 5 秒）则跳过并记录，不阻塞其他订阅者 |
| 负载隔离 | 侧车插件的重活在它自己进程，CPU/内存与主进程隔离 |

## 5. 安全设计

| # | 措施 | 具体做法 |
|---|---|---|
| 1 | 管理端口仅本机 | 只监听 `127.0.0.1`；连接需会话口令（`ling/session.json`，权限 0600） |
| 2 | 能力门禁 | 方法标注所需能力（注册时校验 ⊆ 清单）；**调用瞬间**核对目标插件的**生效**能力（清单声明 − 用户撤销黑名单），不符即拒绝（`E_CAPABILITY_DENIED`）；授权/撤销的界面由 core-plugin-manager 提供 |
| 3 | 命名空间隔离 | 插件注册的方法/事件必须带自己的插件编号前缀，内核校验，防止冒名注册 |
| 4 | 卸载完整性检查 | 卸载后逐条核对账本是否全部撤销成功，未成功的明确报告而不是静默忽略 |
| 5 | 侧车进程限制 | 侧车通过本地套接字通信，不对外监听；宿主只从受控目录启动侧车可执行文件 |
| 6 | 清单校验 | 插件编号格式、版本号格式、能力取值、路径穿越（插件目录之外的路径）全部拒绝 |

## 6. 配置调和（第 4 项服务的执行方式）

**触发时机**：安装插件、卸载插件、启用/停用、升级、修改依赖要求。

**执行流程**：

```
配置变化
  → 重建依赖图（节点=插件/能力，边=requires）
  → 校验：版本匹配？有无循环依赖？缺失依赖？
      ├─ 有错 → 拒绝本次配置变化，报告错误，图与装载状态回滚到变化前
      └─ 无错 → 计算激活计划
  → 激活计划 = 一个有序列表：先激活依赖在前者（拓扑序），
                          停用则反向（先停用被依赖者保护下游）
  → 逐步执行，每步完成后广播 kernel.plugin.state 事件
  → 执行完毕，装载状态收敛
```

**关键性质**：
- **原子性**：计划计算失败 → 配置完全回滚，不留半新半旧状态。
- **可观察**：每一步都发事件，core-plugin-manager 插件据此刷新界面。
- **可取消**：执行中用户可取消，已执行的步骤按账本倒序回滚。

## 8. 风险登记册（设计时分析）

> **分工**：本节是**设计时**的静态分析——"什么可能出错、设计上怎么预防"。**运行时已经出错了怎么办**（处置步骤、命令、回滚），见 [`08-运行时预案.md`](08-运行时预案.md)。

| # | 风险 | 影响 | 设计对策 | 运行时预案 |
|---|---|---|---|---|
| 1 | Rust 动态库反复装卸载（dlclose/dlopen）有已知坑：静态变量残留、类型布局变化导致崩溃 | 热更新不稳定 | ① 插件禁止持久内存状态（纪律，见 05）② 内核与插件间传递的数据全部经过序列化边界（JSON/MessagePack），不用跨动态库边界的引用类型 ③ 卸载失败时中止热更新并回滚旧版 | 08 §2.3 |
| 2 | 侧车协议与内核协议分裂成两套 | 维护成本翻倍 | 控制面帧格式统一（见 04 §6），同进程只是省掉序列化这一步 | 08 §2.2 |
| 3 | 插件作者（包括未来的我）绕过上下文 | 卸载不干净、热更新失效 | 代码审查清单 + 文档明示"违规效应"后果；提供 `ling doctor` 检查项（L4 后） | 08 §2.4 |

## 9. 内核更新策略

**内核更新 = 替换 ling 主程序二进制**。它不是热更新（热更新只针对插件），而是"宿主本身的升级"。

### 9.1 更新流程（第一轮：手动）

```
1. 用户备份 ling 目录（保险步骤）
2. 停止当前进程：ling shutdown
   （所有插件停用、效应账本撤销；插件状态早已在各自的持久文件里）
3. 替换 ling 二进制文件
4. 启动：ling serve
   → 装载表从空开始 → 依赖解析 → 插件按依赖序激活
   → 各插件从自己的 data/ 目录重读状态 → 恢复工作
```

### 9.2 为什么内核重启是安全的（设计保证）

| 保障 | 来源 |
|---|---|
| 插件状态在持久文件，不在内存 | 决策 A-5（状态放 data/，内存不留） |
| 效应账本不落盘、每次启动重建 | 装载表本来就从空开始，账本随装载重记（`02` §3.4） |
| 激活顺序每次启动重算 | 配置调和在启动时全量跑一遍（`03`） |

### 9.3 版本兼容（api 字段）

| 规则 | 说明 |
|---|---|
| 插件清单 `api` 字段 | 声明插件面向的宿主接口主版本（如 `api = "1"`） |
| 内核声明支持范围 | 内核支持 api N 与 N-1（过渡一个版本周期） |
| 不匹配的行为 | 拒绝装载该插件，明确报错（"插件面向 api=1，宿主提供 api=2"），**不影响其他插件** |
| 侧车协议 | 握手时带协议版本号，不匹配同样拒绝并报错（`04` §6） |
| 管理端口协议 | 带版本字段；`ling` 命令行与内核版本配套发行 |

### 9.4 第一轮不做

自动下载更新、灰度发布、双版本并行——个人工具场景收益低，等有真实需求再设计。

## 附录 A：决策记录

> 格式：背景 → 备选 → 决定 → 代价 → 理由 → 影响章节

### A-1 宿主语言与插件形态：Rust + 双轨加载

- **背景**：宿主语言；大部分插件用 Rust，但可能有非 Rust 插件。
- **备选**：(a) 全进程内动态库（非 Rust 语言受限）；(b) 全部进程外（Rust 插件也受损耗）；(c) **双轨**：Rust 走进程内动态库，其他语言走进程外侧车。
- **决定**：(c)。
- **代价**：装载器要维护两条路径；侧车插件的控制面调用有本地套接字开销（微秒~毫秒级）。
- **理由**：分"控制面"与"数据面"——侧车插件的重活在自己进程里干，只有注册/调用/事件经过套接字，**不影响 Rust 插件之间零开销的直调路径**；侧车还带来崩溃隔离。
- **影响章节**：§3.1、§4.1、`04-插件接口规范`

### A-2 内核只做 4 项服务（模块化）；配置/作业/日志为内置插件

- **背景**：内核该内置多少公共服务。
- **备选**：(a) 只做 4 项（路由/事件/能力/依赖），配置/作业/日志自理；(b) 4 项 + 把这三样也塞进内核；(c) 更极简只留路由与事件（能力/依赖也做成插件）。
- **决定**：(a) 的变体——四项服务留在内核但**模块化组织**；配置存储、作业调度、日志做成**内置插件**（core-settings 含存储、core-job、core-log，见 06），不进内核。(c) 经分析否决：做成插件后仍是"永远激活、不可卸载、不可热更新"的关键路径组件，且依赖解析需要内核特权接口，只会增加复杂度（评审轮结论，见 §3.2 决策表）。
- **代价**：内核不可运行时替换（只能编译时换模块）；内置插件未安装时相关功能降级。
- **理由**：路由/事件是互调的数据结构本身；门禁与路由共用方法表，拆开无收益；依赖解析驱动装载特权。而配置/作业/日志不在关键路径、无引导问题、多插件共享有价值——做成内置插件正合适。
- **影响章节**：§1.2、§3.2、`06-内置插件设计`、§8 风险 5、8

### A-3 内置插件放 ling 仓库 builtin-plugins/ 目录（从属关系）

- **背景**：内置插件（core-ui / core-settings / core-plugin-manager / core-job / core-log）放哪、怎么表达与 ling 的关系。
- **备选**：(a) ling 仓库下独立目录（从属）；(b) 各自独立仓库；(c) 混在内核代码里（包含）。
- **决定**：(a)——`ling/builtin-plugins/` 目录，每个插件一个子目录，与内核源码分离；首次启动默认安装三件套，其余按需安装。
- **代价**：ling 仓库不"纯粹"（含插件代码）；发行包体积略增。
- **理由**：(c) 会让内置插件获得内核特权通道，违背"同一规范"原则；(b) 版本匹配与发行管理复杂。目录从属表达"随 ling 发行、但彼此独立"，且新增内置插件只需加子目录。
- **影响章节**：`06-内置插件设计` §2、§3、§8 风险 8

### A-4 首轮即实现热更新

- **背景**：论文机制采纳范围里，热更新难度最高。
- **备选**：(a) 首轮做；(b) 首轮只做可逆效应与依赖解析，热更新后置。
- **决定**：(a)。
- **代价**：需正面处理 Rust 动态库装卸载的坑（风险 1），实现周期变长。
- **理由**：热更新的价值集中在开发期，越早有越早受益；且热更新与可逆效应是同一套账本机制，晚做反而要返工。
- **影响章节**：`05-热更新`、§8 风险 1

### A-5 插件状态纪律：状态放持久文件，内存不留

- **背景**：热更新会丢弃旧动态库的全部内存。
- **备选**：(a) 强制状态放插件自己的持久文件；(b) 允许内存状态并做序列化迁移。
- **决定**：(a)。
- **代价**：插件作者必须遵守；每次调用若需状态要从文件/缓存读。
- **理由**：(b) 要处理序列化兼容、失败恢复，复杂且易错；(a) 让"重载=干净重来"，天然正确，也符合"状态可持久、内存可丢弃"的健壮性通则。
- **影响章节**：`05-热更新`、`04-插件接口规范` §插件作者纪律

### A-6 命令行通道：内核自带管理端口

- **背景**：极简内核后，`ling` 命令行怎么管理运行中的宿主。
- **备选**：(a) 内核自带仅本机管理端口；(b) 走 core-ui 的网页端口；(c) 命令行自己拉起进程。
- **决定**：(a)。
- **代价**：内核多一个监听端口（不计入"4 项服务"，属于服务①的传输通道）。
- **理由**：(b) 在界面壳损坏时无法修复——修宿主的工具不能依赖被修对象；(c) 无法查询/控制已在运行的宿主。
- **影响章节**：§3.1、`04-插件接口规范` §管理端口

### A-7 采纳论文机制（务实子集）

- **背景**：参考 arXiv 2608.25512《A Programming Paradigm for Spatiotemporal Composability》。
- **备选**：(a) 采纳工程机制（可逆效应+响应式协效应+上下文范式）；(b) 完整形式化实现；(c) 不采纳。
- **决定**：(a)。
- **代价**：放弃形式化保证，卸载干净与否依赖实现正确性与测试覆盖。
- **理由**：论文的机制部分正好回答"一切皆插件"最难的三件事（卸载干净、依赖传导、热更新）；演算部分对工程无直接价值。
- **影响章节**：§2 全部、`02`、`03`、`05`
