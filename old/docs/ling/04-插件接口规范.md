# ling 04 插件接口规范

> 版本：v0.4 ｜ 状态：已封档（终审通过）；L6 侧车编码落地，登记见 01 附录 B 第 14 条
> 本文回答：**插件长什么样、怎么被装载、怎么和内核/其他插件/命令行通话、作者必须遵守什么纪律。**

## 1. 插件目录结构

```
ling/plugins/<插件编号>/
├── plugin.toml          # 清单（必须）
├── manifest 之外的产物：
│   ├── <编号>.dll       # Windows 动态库（Rust 插件），或
│   ├── <编号>.so        # Linux 动态库（Rust 插件），或
│   └── sidecar/         # 侧车可执行文件目录（非 Rust 插件）
│       └── <编号>[.exe]
└── data/                # 插件自己的持久状态（卸载时保留，--purge 时删除）
```

| 规则 | 说明 |
|---|---|
| 编号即目录名 | 目录名必须与 `plugin.toml` 的 `id` 完全一致 |
| 单一产物 | 一个插件要么是动态库，要么是侧车，不混合 |
| data/ 归插件 | 内核不读、不写、不清理 data/（除非 uninstall --purge） |
| 路径穿越拒绝 | 清单中出现 `..` 或绝对路径 → 拒绝装载 |
| 安装来源 | `ling install` 接受**插件目录**或 **zip 包**（zip 内必须含 `plugin.toml` 且在根部）；内核一律**拷贝**进 `ling/plugins/<编号>/`，不引用原位置（原目录删除不影响已装插件） |

## 2. 清单（plugin.toml）完整格式

```toml
[plugin]
id       = "resources-manager"        # 必填。小写字母/数字/短横线，全局唯一
version  = "0.1.0"               # 必填。语义化版本
api      = "1"                   # 必填。宿主接口主版本，不匹配则拒绝装载
name     = "资源管理"             # 可选。显示名
author   = "用户"                 # 可选
description = "本地文件去重与整理"  # 可选

[requires]                       # 可选。没有则视为无依赖
capabilities = ["fs", "network"]  # 能力需求，取值见 03 §1.3
plugins      = ["core-ui@1"]      # 插件需求，版本写法见 03 §1.2

[sidecar]                        # 仅侧车插件需要；Rust 动态库插件不写此段
executable   = "sidecar/resources-manager"  # 相对插件目录的可执行文件路径
protocol     = "jsonl"           # 控制面帧格式，首版固定 "jsonl"（每行一个 JSON）
restart      = "on-crash"        # 崩溃时是否自动重启：on-crash / never
```

**字段校验**（装载前，全部在内核完成）：

| 字段 | 校验规则 | 违反后果 |
|---|---|---|
| id | `^[a-z0-9][a-z0-9-]*$`，长度 ≤ 64 | 拒绝装载 |
| version | 三段式 `主.次.修`，各段 ≤ 65535 | 拒绝装载 |
| api | 整数，必须等于宿主当前 api 主版本 | 拒绝装载，提示"插件面向 api=1，宿主提供 api=2"之类 |
| capabilities 每项 | 必须在宿主已知能力集内 | 拒绝装载，提示宿主版本过旧 |
| plugins 每项 | 格式 `编号[@版本]` | 拒绝装载 |
| sidecar.executable | 文件存在、可执行、在插件目录内 | 拒绝装载 |

## 3. Rust 插件入口（进程内动态库）

### 3.1 Plugin trait

```rust
// ling-sdk 提供；插件实现这一个 trait 即可
pub trait Plugin: Send + Sync {
    /// 插件编号，必须与清单 id 一致（装载时核对）
    fn id(&self) -> &str;

    /// 装载时调用。所有注册/订阅都经 ctx，内核记入账本
    fn activate(&mut self, ctx: Context) -> Result<(), ActivateError>;

    /// 停用/卸载/热更新前调用。插件在此收敛自己的线程、落盘
    fn deactivate(&mut self);
}

// 动态库必须导出这个函数，内核据此拿到插件实例
// #[no_mangle] pub extern "C" fn ling_plugin_create() -> *mut dyn Plugin
```

### 3.2 内核装载动态库的步骤

| # | 步骤 | 失败处理 |
|---|---|---|
| 1 | 读清单、校验 | 拒绝装载，报告字段 |
| 2 | `dlopen`/`LoadLibrary` 打开动态库 | 报告加载器错误 |
| 3 | 取 `ling_plugin_create` 符号 | 报告"不是合法的 ling 插件" |
| 4 | 调 `id()` 核对与清单一致 | 不一致 → 拒绝 |
| 5 | 调 `activate(ctx)` | 失败 → 执行已记账本的倒序撤销 → 卸载动态库 → 报告 |
| 6 | 标记已激活，广播事件 | —— |

**序列化边界**：内核与插件之间传递的所有数据是 `serde_json::Value`（或等价的纯数据类型），**禁止**跨动态库边界传递字符串切片、闭包捕获的引用、静态区对象。这是热更新稳定性的关键（见 `05` §3）。

**方法能力标注**：`register_method` 可带 `requires`（如 `fs`）。**注册时**校验 requires ⊆ 本插件清单 `capabilities`（不符拒注册）；**调用时**门禁核对目标插件的**生效**能力集（清单声明 − 用户撤销黑名单）⊇ requires，不符返回 `E_CAPABILITY_DENIED`（`01` §5、`02` §1.3）。

**调用超时**：同步 `call` 默认超时 **30 秒**（返回 `E_TIMEOUT`）；`call_async` 不受此限，由调用方自行控制。热更新/停用窗口内，对未激活插件的调用返回 `E_PLUGIN_MISSING`（见 `05` §2）。

## 4. 双轨装载对比

| 项 | 轨道 A：Rust 动态库 | 轨道 B：进程外侧车 |
|---|---|---|
| 语言 | 仅 Rust（或能产出 C 接口的语言，暂不支持） | 任意（Python/Node/Go…） |
| 进程 | 与内核同进程 | 独立进程 |
| 方法调用开销 | 函数调用 + 两次查表，< 1 微秒 | 本地套接字一次往返，约几十微秒 |
| 崩溃影响 | 会拖垮整个宿主（无法隔离） | 只影响自己；内核标记崩溃并广播事件 |
| 热更新 | dlclose → dlopen（见 05 §3 的坑） | 终止进程 → 启动新进程 |
| 效应撤销 | 执行插件交出的撤销函数 | 内核按登记语义代为撤销（注销方法、退订、杀进程） |
| 数据面重活 | 插件自己开线程 | 在侧车自己进程内完成，不经过套接字传输文件内容 |

**选择建议**：默认写 Rust 动态库；只有在语言受限（必须用 Python 生态）或需要崩溃隔离时才用侧车。

## 5. 事件主题约定

| 主题 | 载荷 | 广播方 |
|---|---|---|
| `kernel.plugin.state` | `{plugin, state: "activated"\|"deactivated"\|"uninstalled"\|"crashed", reason}` | 内核（每次激活/停用/卸载/崩溃） |
| `kernel.plan.step` | `{plan_id, step, action, plugin, ok, error?}` | 内核（配置调和每步） |
| `<插件编号>.<对象>.<动作>` | 插件自定义 | 各插件，如 `resources-manager.job.progress` |

**命名空间规则**：插件只能广播以**自己的编号**开头的主题；内核校验，越权则拒绝并记录。

## 6. 侧车控制面协议（jsonl）

**传输**：宿主在启动侧车时传入环境变量 `LING_SOCKET=<端点>`；侧车连接后，每行一个 JSON 对象（jsonl = JSON Lines），UTF-8 编码，`\n` 结尾。
**端点形式（首版统一）**：`tcp:127.0.0.1:<随机空闲端口>`——Linux/Windows 通用，避免两套实现；Unix 域套接字/Windows 命名管道列为后续优化（协议不变，只换端点）。

### 6.1 宿主 → 侧车

| op | 字段 | 含义 |
|---|---|---|
| `activate` | —— | 装载完成，侧车可开始注册 |
| `invoke` | `id, method, args` | 宿主替别的插件调用侧车方法，侧车须回 `result` 或 `error` |
| `event` | `topic, payload` | 侧车订阅的事件到达 |
| `deactivate` | —— | 请求侧车收敛并准备退出；侧车须回 `deactivated` |
| `shutdown` | —— | 立即退出（5 秒未退出则强杀） |

### 6.2 侧车 → 宿主

| op | 字段 | 含义 |
|---|---|---|
| `register_method` | `name` | 注册方法；内核查命名空间前缀并记账（撤销=注销） |
| `subscribe` | `pattern` | 订阅事件；记账（撤销=退订） |
| `call` | `id, plugin, method, args` | 调用别的插件；宿主代为执行后回 `result`/`error` |
| `emit` | `topic, payload` | 广播；内核校验命名空间后转发 |
| `result` / `error` | `id, …` | 对 `invoke`/`call` 的应答 |
| `deactivated` | —— | 已完成收敛，可以退出 |

**规则**：
- 每条消息必须有 `op`；带 `id` 的请求必须最终得到一条 `result` 或 `error`（宿主侧超时 30 秒）。
- 侧车崩溃（进程退出/断连）→ 内核注销其全部效应（按账本）→ 广播 `kernel.plugin.state crashed` → 按 `restart` 策略决定是否重启。
- **数据面不走此协议**：侧车自己读写文件、算哈希，绝不要求宿主代劳。

## 7. 管理端口协议（命令行专用）

**传输**：`127.0.0.1:7900`（默认，占用则顺延），实际端口写在 `ling/registry.json`。
**认证**：首行发送 `{"op":"auth","token":"<ling/session.json 里的口令>"}`；失败即断开。

### 7.1 命令与方法对照

`ling` 命令行的每个子命令对应管理端口上的一个方法（走服务①的路由，内核内置命名空间 `kernel.*`）：

| 命令 | 方法 | 说明 |
|---|---|---|
| `ling serve` | —— | 前台启动宿主（不走端口，直接在进程内起内核） |
| `ling shutdown` | `kernel.shutdown` | 优雅停止宿主（各插件 deactivate → 账本撤销 → 退出） |
| `ling --version` | —— | 输出版本号（本地解析，不连端口） |
| `ling plugins` | `kernel.plugins.list` | 列出已安装插件及状态 |
| `ling install <路径>` | `kernel.plugins.install` | 安装并触发调和 |
| `ling uninstall <编号>` | `kernel.plugins.uninstall` | 卸载（可选 `--purge`） |
| `ling enable / disable <编号>` | `kernel.plugins.enable / disable` | 启停 |
| `ling reload <编号>` | `kernel.plugins.reload` | 热更新（新版本已在目录里） |
| `ling restart <编号>` | `kernel.plugins.restart` | 崩溃后重启 |
| `ling doctor [编号]` | `kernel.doctor` | 健康检查（L4 后）：依赖图健康度、未撤销效应、命名空间违规迹象、端口/口令文件状态 |
| `ling logs <编号> [--follow]` | `kernel.logs.read` / 订阅 `kernel.log` | 读插件日志 |

### 7.2 通用应答格式

```json
{"ok": true,  "result": { … }}
{"ok": false, "error": {"code": "E_DEPENDENCY_CYCLE", "message": "…", "detail": {…}}}
```

## 8. 错误码

| 码 | 含义 | 典型来源 |
|---|---|---|
| `E_MANIFEST_INVALID` | 清单字段缺失或格式错 | 装载校验 |
| `E_API_MISMATCH` | 插件 api 与宿主不一致 | 装载校验 |
| `E_CAPABILITY_UNKNOWN` | 清单声明了宿主不认识的能力 | 装载校验 |
| `E_CAPABILITY_DENIED` | 调用方未声明所需能力 | 服务③能力门禁 |
| `E_NAMESPACE_VIOLATION` | 方法名/事件主题未带本插件前缀，或越权广播 | 命名空间校验 |
| `E_PLUGIN_MISSING` | 调用目标插件不存在或未激活 | 服务① |
| `E_METHOD_MISSING` | 目标方法未注册 | 服务① |
| `E_DEPENDENCY_UNMET` | 依赖未满足，插件处于待激活 | 服务④ |
| `E_DEPENDENCY_CYCLE` | 依赖成环 | 服务④ |
| `E_ACTIVATE_FAILED` | 插件 activate 返回错误 | 装载 |
| `E_UNDO_FAILED` | 某条撤销执行失败 | 卸载/热更新 |
| `E_RELOAD_FAILED` | 热更新失败（已回滚旧版） | 热更新 |
| `E_TIMEOUT` | 调用/应答超时 | 服务①/侧车 |
| `E_SIDE_CRASHED` | 侧车进程崩溃 | 侧车监控 |
| `E_AUTH` | 管理端口认证失败 | 管理端口 |

## 9. 插件作者纪律（审查清单）

写完一个插件，对照此表逐项打勾：

| # | 纪律 | 检查方法 |
|---|---|---|
| 1 | 所有注册/订阅都经 `Context`，没有直接挂全局钩子 | 代码里搜 `register`/`subscribe` 只出现在 `ctx.` 上 |
| 2 | 注册时提供了正确的撤销函数 | 每个 `register_method`/`subscribe` 的最后一个参数是撤销闭包 |
| 3 | 方法名、事件主题都以本插件编号开头 | 形如 `resources-manager.scan.*` |
| 4 | 不用 `static`/`lazy_static` 持有跨调用状态 | 状态放 `data/` 目录的文件里 |
| 5 | `deactivate` 里收敛了所有自开线程 | 每个 `thread::spawn` 都有对应的取消/等待逻辑 |
| 6 | 重活（扫描/哈希）不阻塞方法处理函数本身 | 处理函数内部把任务交给自己的线程池并返回作业 id |
| 7 | 依赖都写进 `requires`，没有"隐式依赖" | 对别的插件的 `ctx.call` 都能对应到一条 requires |
| 8 | 侧车插件：数据面不经控制面传文件内容 | 协议里只有 JSON，没有二进制大块传输 |
| 9 | `data/` 里的文件格式有版本号，升级时能迁移 | 文件头或伴随 `_version` 键 |
| 10 | 清单里没有绝对路径、没有 `..` | 目检 |
