# ling 06 内置插件设计

> 版本：v0.4 ｜ 状态：已封档（终审通过）；L5 编码落地，登记见 01 附录 B 第 13 条
> **内置插件** = 随 ling 一起发行、但**与普通插件遵守完全相同规范**的插件。它们**从属**于 ling（源码放 ling 仓库的 `builtin-plugins/` 目录），但**不是内核的一部分**——卸掉之后宿主照样能跑。
> 与 v0.1（"内置三件套"）的差异：① 目录结构改为"从属文件夹"，表达从属而非包含；② 首次启动默认装三件套，其余内置插件按需安装；③ 新增 core-job / core-log 两个可选内置插件；④ core-settings 合并原计划的 core-config（存储+界面一体）。
> 公共术语见 `../../docs-common/01-公共术语与约定.md`。

---

## 1. 内置插件是什么、不是什么

| 是 | 不是 |
|---|---|
| 随 ling 发行包一起分发的插件 | 内核的一部分（卸掉宿主照常工作） |
| 源码在 ling 仓库 `builtin-plugins/` 目录（**从属**关系） | 被内核"包含"的特殊代码（没有内核特权通道） |
| 与普通插件一样：同一份清单格式、同一个 Plugin trait、同一套装载/卸载/热更新流程 | 只能由 ling 团队更新的封闭组件（用户可以自己编译替换） |
| 首次启动**默认安装三件套**（core-ui / core-settings / core-plugin-manager），其余按需安装 | 全部默认安装（core-job / core-log 是可选的） |

**唯一的"特权"**：内置插件随发行包分发，首次启动自动从随包目录安装，不需要用户手动拷贝。这不是内核特权，只是**发行方式**。

## 2. 仓库目录结构（从属关系的表达）

```
ling/
├── src/                        # 内核源码（ling-kernel）
├── sdk/                        # 插件开发包（ling-sdk）
├── builtin-plugins/            # ★ 内置插件目录：随 ling 发行，彼此独立
│   ├── core-ui/                #   界面壳（默认安装）
│   ├── core-settings/          #   配置存储 + 设置界面（默认安装，合并原 core-config）
│   ├── core-plugin-manager/    #   插件管理（默认安装）
│   ├── core-job/               #   作业调度（可选）
│   ├── core-log/               #   日志收集（可选）
│   └── (未来新增的内置插件往这里加子目录，不用改内核)
├── apps/                       # 可执行入口：ling、窗口壳、安卓壳
└── docs/
```

**安装后的运行目录**（与普通插件完全一致）：

```
ling/plugins/<插件编号>/        # 安装副本（首次启动从 builtin-plugins/ 拷贝）
└── data/                       # 插件自己的持久状态
```

| 规则 | 说明 |
|---|---|
| 源码与安装副本分离 | `builtin-plugins/` 是源码/发行物；`plugins/` 是安装位置。改内置插件 = 替换 `plugins/` 里的副本 |
| 新增内置插件 | 在 `builtin-plugins/` 加子目录即可，内核不用改；首次启动扫描该目录 |
| 用户可以不装 | 三件套也能被卸载；卸载后只剩命令行与管理端口可用 |

---

## 3. 安装策略

| 阶段 | 行为 |
|---|---|
| 首次启动（`plugins/` 目录为空） | 自动安装**三件套**：core-ui、core-settings、core-plugin-manager |
| 之后新增内置插件（如发行包带了 core-job） | **不自动安装**；用户在插件管理页看到"可安装"列表，按需安装 |
| 用户卸载三件套之一 | 允许。卸掉 core-ui → 界面消失，命令行与管理端口仍可用 |
| 卸载后再装回 | `ling install core-ui` 或插件管理页操作，与普通插件一致 |

**为什么默认装三件套**（而不是首次交互式勾选）：
- 开箱即用——装上 ling 就有界面和插件管理，不必先拼装；
- 反正可卸载——不需要的用户随时卸，不需要在第一次启动时做决定。

## 4. 各内置插件的职责

### 4.1 core-ui（界面壳）—— 默认安装

| # | 职责 | 实现要点 |
|---|---|---|
| 1 | 启动本机网页服务 | 监听 `127.0.0.1:7910`（默认，占用顺延）；实际端口写 `ling/registry.json` |
| 2 | 承载界面壳 | 导航栏、主题、图标、页面容器；插件的页面作为"贡献"挂进来 |
| 3 | 提供 `/rpc` 网关 | `POST` JSON `{id, plugin, method, params}` → 经内核路由转给目标插件（见 §6.3） |
| 4 | 提供界面贡献注册接口 | 方法 `core-ui.ui.contribute`（页面/菜单）、`core-ui.ui.retract`（撤下） |
| 5 | 监听卸载事件 | 订阅 `kernel.plugin.state`；某插件被停用/卸载（deactivated / uninstalled）→ 自动撤下其全部贡献 |
| 6 | 会话口令校验 | 网页请求需携带 `X-Ling-Token`（口令在 `ling/session.json`） |

**界面贡献模型**：

| 贡献类型 | 字段 | 说明 |
|---|---|---|
| 页面（page） | `path`（如 `/resources-manager`）、`title`、`icon`、`asset_dir` | 插件提供静态 HTML/JS 资源目录；core-ui 托管 |
| 菜单项（menu） | `label`、`path`、`order` | 挂在导航栏 |

**端到端请求链路**（举例：网页点"开始扫描"）：

```
浏览器 POST http://127.0.0.1:7910/rpc
        { "id": "1", "plugin": "resources-manager", "method": "scan.start", "params": {…} }
  → core-ui 网关：校验 X-Ling-Token
  → context.call("resources-manager", "scan.start", args)   （经内核路由）
  → resources-manager 的处理函数：返回 {job_id: 42}
  → core-ui 把结果以 JSON 还给浏览器
  → resources-manager 随后广播 resources-manager.job.progress
      → core-ui 订阅并转发给浏览器（首版：前端轮询；WebSocket 后置）
```

### 4.2 core-settings（配置存储 + 设置界面）—— 默认安装

> **合并说明**：v0.1 计划里存储（core-config）与界面（core-settings）是两个插件；现合并为一个——存储和展示本来就是一件事的两面，拆开只会多一个插件。

| # | 职责 |
|---|---|
| 1 | 提供配置读写接口：`core-settings.get` / `core-settings.set` |
| 2 | 每个插件的设置存自己的 SQLite（`ling/plugins/core-settings/data/settings.db`） |
| 3 | 设置项带**模式（schema）**：类型、默认值、取值范围；插件声明后 core-settings 负责校验 |
| 4 | 提供设置页面框架：core-ui 里渲染"设置"入口，按插件分组列出 |

**与内核配置的分界**（勿混淆）：

| | 内核配置（Context.set_config） | core-settings 的设置 |
|---|---|---|
| 谁拥有 | ling 内核 | core-settings 插件 |
| 存什么 | 宿主级登记（如插件自启开关） | 插件业务设置（如扫描排除目录） |
| 卸载时 | 删除（进账本） | 保留（属 core-settings 的 data/） |
| 谁读 | 内核 | 插件通过 `ctx.call("core-settings", "get", …)` |

**插件纪律**：要用设置一律走 core-settings（有 schema 校验和统一界面）；真正的运行时中间状态（扫描进度等）自己放 data/。

**依赖**：`requires core-ui@1`（设置界面需要界面壳承载）。

### 4.3 core-plugin-manager（插件管理）—— 默认安装

| # | 职责 | 委托给谁 |
|---|---|---|
| 1 | 界面：插件列表（编号、版本、状态、依赖是否满足、"可安装"列表含未装的内置插件） | 数据来自 `kernel.plugins.list` |
| 2 | 操作：安装/卸载/启停/重载 按钮 | 调内核对应方法（同 `ling` 命令行） |
| 3 | 授权界面：展示各插件声明的能力，用户可撤销授权 | 见 §4.5 |
| 4 | 崩溃状态展示与重启按钮 | `kernel.plugin.state crashed` 事件 |
| 5 | 调和进度展示 | 订阅 `kernel.plan.step` |

**能力授权模型（首版）**：

| 项 | 首版做法 |
|---|---|
| 默认 | 插件清单声明的能力**全部允许**（装了就算同意） |
| 撤销 | 界面撤销某项能力 → 内核写入黑名单 → 该插件调用该能力被门禁拒绝（`E_CAPABILITY_DENIED`） |
| 重新授予 | 界面重新打开 |
| 存储 | 内核启动时从 `ling/registry.json` 读入黑名单（宿主级登记，不归任何插件） |

**依赖**：`requires core-ui@1`。

### 4.4 core-job（作业调度）—— 可选安装

> **定位**：内核极简决策下内核不管作业；core-job 把"长任务登记"做成公共服务，多个插件共用，界面统一展示。

| # | 职责 |
|---|---|
| 1 | 接口：`core-job.register`（登记作业）、`core-job.progress`（上报进度）、`core-job.cancel`（取消）、`core-job.list` / `core-job.get`（查询） |
| 2 | 广播事件：`core-job.progress` / `core-job.done`（载荷含作业号、所属插件、百分比） |
| 3 | 界面贡献：core-ui 里一个"作业"页面，统一展示所有插件的作业与进度 |
| 4 | 作业数据存自己的 data/（作业历史保留 30 天，默认） |

**谁在用**：resources-manager 的扫描、分类、记录同步作业；以后备份插件的备份作业。

**降级路径**：core-job 未安装时，插件可以自己管理作业（进度只在自己的界面可见）；resources-manager 的处理方式见其 `docs/03`。插件清单若写 `requires core-job@1`，则 core-job 未装时该插件保持"待激活"。

### 4.5 core-log（日志收集）—— 可选安装

| # | 职责 |
|---|---|
| 1 | 提供接口：`core-log.write`（插件写日志）、`core-log.read`（查询） |
| 2 | 与 `ling logs` 命令行对接（管理端口 → core-log） |
| 3 | 日志轮转：单插件日志文件上限 10 MB，保留最近 5 个文件 |
| 4 | 界面贡献：日志查看页面（按插件过滤） |

**降级路径**：core-log 未安装时，`ling logs` 回退到读各插件 data/ 目录下的 stderr 重定向文件（内核在装载时为每个插件落一个最小 stderr 文件）。插件侧无需感知——写日志经 `ctx` 的日志桩，有 core-log 走 core-log，没有走 stderr。

## 5. 内置插件与内核的边界（总结）

| 属于内核（不可卸载） | 属于内置插件（可卸载） |
|---|---|
| 接口方法路由、事件广播、能力门禁、依赖解析（四项服务，模块化，见 `01` §3.2） | 界面（core-ui）、设置（core-settings）、插件管理界面（core-plugin-manager） |
| Context、效应账本、配置调和（三个机制） | 作业调度（core-job）、日志收集（core-log） |
| 装载通道、管理端口（两条通道） | —— |

**判断口诀**：少了它宿主就不叫宿主 → 内核；少了它用户少了某个用途但宿主照常跑 → 插件（哪怕它是内置的）。
