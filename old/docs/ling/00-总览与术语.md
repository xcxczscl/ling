## 1. ling 是什么

### 1.1 一句话

ling 是一个**零内容的宿主程序**：它自己什么都不做，只负责**让别人（插件）能安全地做事**。

### 1.2 "零内容"的边界（这条最重要）

| ling **有**（机制） | ling **没有**（内容） |
|---|---|
| 加载 / 卸载 / 热更新插件 | 窗口、导航、主题、图标 |
| 转发插件之间的调用 | 任何界面页面 |
| 广播事件 | 设置页面 |
| 检查插件声明的能力 | 插件管理的操作界面 |
| 解析依赖关系、自动激活/停用插件 | 任何业务概念（比如"什么是文件""什么是账单"） |
| 管理端口（供命令行连接） | 业务逻辑 |
| 可逆效应账本（保证卸载干净） | 文件存储、数据库、网络协议 |

**判断标准**：如果这个功能"少了它宿主就不叫宿主了"，那它属于 ling；如果它是"用户能感知到的某个用途"，那它属于插件。

### 1.3 谁在用 ling

- **插件作者**（比如我们自己写 resources-manager）：按 `docs/04-插件接口规范` 写一个动态库或侧车可执行文件，丢进插件目录即可被加载。
- **终端用户**：通过插件提供的界面（由 core-ui 插件承载的网页）操作；通过 `ling` 命令行管理宿主与插件。
- **其他插件**（比如记账、网站管理）：通过宿主互相调用、订阅彼此事件。

## 2. 贯穿示例（用户装插件的全过程）

后面所有章节都用这个例子：

| 步骤 | 用户做了什么 | 触发 ling 的什么机制 |
|---|---|---|
| 1 | 安装 ling，首次启动 | 内核启动、管理端口监听 |
| 2 | 内置插件（core-ui / core-settings / core-plugin-manager，首次默认安装）自动加载 | 清单解析 → 依赖解析 → 依次激活 |
| 3 | core-ui 在本机开网页服务，用户打开浏览器看到插件管理页 | 界面贡献由 core-ui 接管（ling 本体不开任何窗口） |
| 4 | 用户把 `resources-manager` 插件目录拷进去，执行 `ling install resources-manager` | 依赖解析发现新插件 → 激活 → 界面出现"资源管理"入口 |
| 5 | 记账插件（早已安装但一直"停用"）发现 resources-manager 可用了，自动激活 | 响应式协效应：依赖满足 → activating |
| 6 | 用户改了 resources-manager 的代码，执行 `ling reload resources-manager` | 热更新：停用旧版 → 按账本撤销其全部效应 → 装新版 → 重新激活。宿主不重启 |
| 7 | 用户执行 `ling uninstall ledger`（卸载记账插件） | 倒序执行效应账本：注销它注册的方法、退订事件、撤下界面贡献、停止侧车进程 → 环境恢复原样 |
| 8 | 用户发现 resources-manager 没装，记账插件的"归档文件"按钮消失了 | 依赖失效 → 自动停用（挂起，不是卸载）；装回 resources-manager 后自动恢复 |

**这个例子回答的核心问题**：
- "卸载插件会不会留垃圾？"——不会，账本保证逐条撤销。
- "装了新插件要不要重启？"——不用，依赖图重算后自动激活相关插件。
- "改插件代码要重启整个程序吗？"——不用，`ling reload` 只换那一个。

## 3. 术语表

> 格式：**白话定义 + 例子 + 它不是什么**。公共术语（宿主、插件、能力、调用路由、事件总线、侧车、上下文、效应、协效应、热更新、配置调和）见 `../../docs-common/01-公共术语与约定.md`，此处不重复。本表只收录 ling 文档里特有或需要更细解释的词。

### 3.1 与加载相关

| 术语 | 白话定义 | 例子 | 它不是什么 |
|---|---|---|---|
| **清单（Manifest）** | 插件目录里那个 `plugin.toml` 文件，写明插件编号、版本、需要的能力、依赖什么 | resources-manager 的清单声明"需要读写文件能力" | 不是 README，是机器解析的配置 |
| **动态库（cdylib / 动态链接库）** | 操作系统的一种可被别的程序在运行时打开的代码文件：Windows 上是 `.dll`，Linux 上是 `.so` | Rust 插件编译产物 `resources_manager.dll` | 不是可执行程序（`.exe`），它自己不能独立运行，必须被宿主打开 |
| **进程（Process）** | 正在运行的一个程序实例。ling 是一个进程；每个侧车插件是另一个进程 | `ling serve` 启动的主程序是一个进程 | 不是线程；进程之间内存隔离 |
| **线程（Thread）** | 进程内部的并行执行单元 | 扫描线程、哈希线程 | 进程之间不共享内存，线程共享 |
| **卸载（Uninstall）** | 把插件从系统中移除：按账本撤销全部效应 → 删除/停用其文件 | `ling uninstall ledger` | 不等于停用（停用只是暂停工作，文件还在） |
| **停用（Deactivate）** | 插件暂停工作但不移除：注销它的效应但保留安装 | resources-manager 没装时记账插件处于停用 | 不是卸载，随时可重新激活 |
| **激活（Activate）** | 停用的插件恢复工作：重新登记它的效应、恢复它的依赖 | 装上 resources-manager 后记账插件被激活 | 不是"启动"这个含糊词；ling 里启动=装载+激活，激活专指依赖满足后进入工作状态 |

### 3.2 与上下文相关

| 术语 | 白话定义 | 例子 | 它不是什么 |
|---|---|---|---|
| **效应登记表（Effect Ledger）** | 宿主为**每个插件**单独记的一本账：这个插件注册过什么、每项怎么撤销 | resources-manager 的账上有"第 1 条：注销方法 scan.start"、"第 2 条：退订 topic xxx" | 不是操作日志（日志给人看，账本给机器执行）；不落盘也可，卸载时在内存里倒序执行 |
| **逆操作（Inverse）** | 撤销某次修改的那个函数，随修改一起登记 | 注册方法时同时交出"注销该方法"的闭包 | 不是"删除数据"；是精确恢复到修改前状态的手段 |
| **效应种类（Effect Kind）** | 被登记的修改的类型枚举：注册方法 / 订阅事件 / 配置写入 / 启动侧车 / 登记停用回调 | 一个插件最多 5 类效应 | 不是业务动作；界面贡献不在此列——它记在 core-ui 自己的账上（见 `02` §2.2） |
| **隔离命名空间（Isolation Namespace）** | 每个插件的效应带自己的编号前缀，互不可见 | 记账插件注册的方法都在 `ledger.` 命名空间下 | 不是安全沙箱（内存仍共享），是逻辑隔离，保证"互不干扰" |
| **违规效应（Illegal Effect）** | 插件绕过上下文直接做的修改（直接开线程、直接改全局变量） | 插件直接 `std::fs::remove_file` 而不登记 | ling 无法检测到它 → 视为插件作者违约，热更新不保证干净 |

### 3.3 与依赖相关

| 术语 | 白话定义 | 例子 | 它不是什么 |
|---|---|---|---|
| **需求声明（Requires）** | 插件清单里的 `requires` 段：我需要哪些能力、需要哪个插件的哪个版本 | 记账插件：`requires = ["capability:fs", "plugin:resources-manager@1.x"]` | 不是编译期依赖（不是 Cargo 的依赖表）；是运行时可重判的需求 |
| **满足（Satisfied）** | 某条需求当前成立 | "resources-manager@1.x 已安装且已激活" → 满足 | —— |
| **依赖图（Dependency Graph）** | 所有插件需求连成的有向图，节点=插件/能力，边=依赖 | 装/卸插件后图变化 | 不是文件目录树 |
| **激活计划（Activation Plan）** | 配置调和算出的执行清单：按什么顺序激活谁、停用谁 | "先激活 core-ui，再激活 resources-manager，最后激活 ledger" | 不是任务队列；是一次性推导的有序步骤 |
| **传递依赖（Transitive Dependency）** | A 依赖 B、B 依赖 C，则 A 间接依赖 C | 记账 → resources-manager → core-ui | 卸载 core-ui 会连锁停用前两者 |
| **循环依赖（Cycle）** | A 依赖 B、B 又依赖 A，图上成环 | —— 检测到即拒绝加载并报错 | 不允许的错误状态 |

### 3.4 与热更新相关

| 术语 | 白话定义 | 例子 | 它不是什么 |
|---|---|---|---|
| **重载（Reload）** | 更换某插件新版本的完整流程：停用 → 撤销效应 → 替换产物 → 装载 → 重新激活 | `ling reload resources-manager` | 不是整程序重启；其他插件不受影响 |
| **持久文件（Persistent File）** | 插件自己在 `ling/plugins/<编号>/data/` 下存的状态文件（数据库、配置） | resources-manager 的目录数据库文件 | 不是插件的可执行产物本身 |
| **装载失败回滚** | 新版本装载出错时，把旧版本重新装回去，用户的系统回到重载前状态 | 新清单写错 → 自动回滚到旧版 | 不是留下半新半旧的中间状态 |
