## 1. 怎么读这份字典

### 1.1 通用约定

| 约定 | 说明 |
|---|---|
| 主键 `id` | 除"内容"表外，所有表都有一个 `id` 列，是全局唯一的编号（随机生成的 32 位字符），跨设备同步时不变 |
| 时间列 | 一律是整数，表示"从 1970 年 1 月 1 日 0 点至今经过的秒数"（ Unix 时间戳）。不用文本日期，为了排序和比较快 |
| 布尔列 | 用整数 0 表示否、1 表示是 |
| `*_json` 列 | 存一整段 JSON 文本，用于放结构灵活、事先说不准的字段（比如扩展信息） |
| 所有枚举列 | 取值在本文件 §7 有完整一览表 |

### 1.2 数据库技术参数

| 项目 | 值 |
|---|---|
| 数据库文件 | SQLite 单文件，默认在插件数据目录下 `ling/plugins/resources-manager/data/catalog.db`（见 `../../docs-common/01-公共术语与约定.md` §2.3） |
| 写入模式 | WAL（预写日志）：读不挡写、写不挡读 |
| 外键约束 | 开启（防止出现"指向不存在的词条"这类脏数据） |
| 等待锁超时 | 5000 毫秒（两个进程同时写时最多等 5 秒） |
| schema 版本 | 单调递增：V1 = M1 全量表；V2 = M2（connection/op/peer/sync_conflict）；V3 = M3（transfer/placement_policy）；V4 = M4（snapshot 表）；**V5 = M5（ai_suggestion 表 + ai_privacy 表）** |

## 2. 物理层表（数据实际在哪）

### 2.1 `device` 设备表

**用途**：登记用户的每台设备，是配对与同步的身份依据。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 文本 | 设备编号，全局唯一 | `dv_8f3a…` |
| `name` | 文本 | 用户起的名字，界面显示用 | `台式机` |
| `platform` | 文本 | 操作系统：`windows` / `linux` / `android` | `linux` |
| `fingerprint` | 文本 | 身份指纹：`sha256:` + 公钥 SHA-256 前 16 字节的 RFC 4648 Base32（大写无填充，26 字符）。配对时交换并固定。**唯一约束** | `sha256:K7QW5H2MZX4YTB3CJ6D8NQVRS9` |
| `last_seen` | 整数 | 最后一次联系上的时间（Unix 秒） | `1760500000` |
| `state` | 文本 | 设备状态：`online` 在线 / `offline` 离线 | `online` |

**常见疑问**
- *为什么需要指纹？* 防止别的设备冒充。配对时双方交换指纹，之后每次连接都核对；如果有人换了证书冒充，指纹对不上，直接拒绝。
- *私钥存在哪？* 不在本表：Ed25519 种子存 `data_dir/identity.key`（32 字节，文件权限 0600），本表只记派生出的公钥指纹（M3，见 `03` §5.2）。
- *移动硬盘算设备吗？* 算。它有自己的身份，插上来时状态变在线。

### 2.2 `location` 位置表

**用途**：登记一块可以放文件的存储空间（通常是某台设备上的一个根目录）。**这是"离线/冷备份"状态的归属地。**

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 文本 | 位置编号 | `lc_home` |
| `device_id` | 文本 | 属于哪台设备（外键） | `dv_8f3a…` |
| `root_path` | 文本 | 根路径 | `/data/media` |
| `kind` | 文本 | 位置类型：`local` 本地磁盘 / `saf` 安卓授权目录 / `nas` 网络共享 / `archive` 归档介质 | `local` |
| `state` | 文本 | **状态：`online` / `offline` / `cold` / `missing`** | `online` |
| `label` | 文本 | 用户起的标签，界面显示用 | `主媒体库` |

**状态取值详解**

| 值 | 白话含义 | 什么时候进入 | 什么时候离开 |
|---|---|---|---|
| `online` | 现在能读能写 | 刚添加、或设备连上了 | 设备断开、或用户手动标记 |
| `offline` | 设备暂时不在线（比如笔记本关机了） | 程序检测到设备失联超过阈值 | 设备重新连上 |
| `cold` | 冷备份：长期不联网的介质（比如锁在柜子里的移动硬盘） | 用户手动标记 | 用户手动改回在线 |
| `missing` | 记录还在，但实际找不到了（盘被格式化、目录被删） | 校验发现文件消失 | 用户确认后删除记录，或重新找到 |

**唯一约束**：（`device_id`, `root_path`）—— 同一台设备上同一个根路径只能登记一次。

**常见疑问**
- *`offline` 和 `cold` 有什么区别？* `offline` 是"暂时不在"，期待它回来；`cold` 是"故意长期不管"，程序不应主动去找它。两者在去重保护上待遇相同（都受保护），但在同步策略上不同：`offline` 的设备回连会自动同步记录，`cold` 的位置不参与任何自动行为。
- *改状态会改文件吗？* 不会。状态只是登记，改状态不碰磁盘。

### 2.3 `content` 内容表

**用途**：登记"一段文件数据本身"，用 BLAKE3 指纹作主键。**这一层的数据永远不变。**

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `blake3` | 文本 | 内容指纹（64 位十六进制字符），**主键** | `9f3c8a…` |
| `asset_type` | 文本 | 资产类型：`video` / `audio` / `image` / `app` / `game` / `doc` / `archive` / `other`（包罗万象的基础字段，筛选与未来播放插件按此分流） | `video` |
| `size` | 整数 | 原始字节数 | `42949672960`（= 40 GB） |
| `enc` | 文本 | 当前存储形态：`plain` 原始 / `zstd` 压缩（M4 实现） | `plain` |
| `enc_size` | 整数 | 压缩后的字节数（未压缩时为空） | 空 |
| `chunking` | 文本 | 去重方式：`none` 文件级（当前唯一取值）/ `cdc` 分块（**预留，尚未实现**） | `none` |
| `copy_count` | 整数 | **物化列**：该内容当前有多少条有效放置（不含已删/墓碑）。placement 增删时同事务维护；`doctor` 全量重算校正漂移；属性测试守护不变式（= 有效 placement 计数）。去重入口与池页高频查询直接读它，免 GROUP BY（见 01 附录 A-14、§8.3） | `3` |
| `verified_level` | 文本 | 上次校验程度：`none` 从未 / `partial` 抽样 / `full` 全量 | `partial` |
| `created` | 整数 | 首次登记时间（Unix 秒） | `1760000000` |

**常见疑问**
- *为什么主键是指纹不是编号？* 因为同一段数据全世界只该有一条记录。两台设备各自扫描出同一个文件，插入时指纹相同，自动识别为同一条内容，不会重复。
- *文件改了一个字节会怎样？* 算出的指纹完全不同 → 作为一条**新的**内容登记，旧内容在没有放置引用后才会被清除。这正是"内容不可变"的含义。
- *`verified_level` 谁来写？* 由校验作业维护（接口 `verify.run` / 命令 `rmgr verify`，见 03 §2.3）：抽样校验写 `partial`，全量写 `full`，发现文件变动则回落 `none` 并出报告。

### 2.4 `placement` 放置表

**用途**：登记"某个文件实际存放在哪个位置的哪个路径"。**这是去重统计的基础。**

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 整数 | 放置编号，自增 | `10241` |
| `location_id` | 文本 | 在哪个位置（外键） | `lc_hdd` |
| `rel_path` | 文本 | 相对于位置根路径的路径 | `深空旅人/4K/video.mkv` |
| `mode` | 文本 | 放置模式：`scattered` 散乱（用户自管原路径，待归纳）/ `managed` 受管（内容在存储池内，见 §2.5） | `managed` |
| `pool_id` | 文本 | 受管时指向所属存储池（外键，可为空；散乱时为空） | `pl_main` |
| `content_id` | 文本 | 对应哪条内容（外键，指向 content.blake3） | `9f3c8a…` |
| `size` | 整数 | 扫描时读到的字节数（冗余存一份，避免查询时连表） | `42949672960` |
| `mtime` | 整数 | 文件修改时间（Unix 秒），用于增量扫描判断 | `1759000000` |
| `inode` | 整数 | 文件系统内部编号（Linux/安卓有值，Windows 为空），用于识别硬链接 | `839201` |
| `state` | 文本 | 该放置的状态：`online` / `offline` / `cold` / `missing` | `cold` |
| `first_seen` | 整数 | 首次被扫描到的时间 | `1758000000` |
| `last_verified` | 整数 | 上次校验通过的时间（用于"近期校验过"的判断） | `1760000000` |
| `pinned` | 整数 | 是否被用户固定（1=永不作为删除候选） | `0` |
| `hash_state` | 文本 | 哈希进度：`none` 未算 / `partial` 只算了首尾 / `done` 算完 | `done` |

**唯一约束**：（`location_id`, `rel_path`）—— 同一位置下同一路径只能有一条放置。

**示例数据（用户的场景）**

| location | rel_path | content | state |
|---|---|---|---|
| 主媒体库（台式机） | `电影/深空旅人/1080p/video.mkv` | `aaa111…` | online |
| 移动硬盘 E 盘 | `深空旅人/4K/video.mkv` | `9f3c8a…` | cold |
| 笔记本 D 盘 | `books/旧港疑云.epub` | `bbb222…` | offline |

**常见疑问**
- *放置的状态和位置的状态会不一致吗？* 会，而且以放置为准做删除判断。比如位置整体在线，但里面某个子目录被用户删了，那个目录下文件的放置状态就是 `missing`。
- *`pinned` 是干什么的？* 用户手动指定"这份永远不许删"，比如某份文件是绝版扫描件，即使有重复也保留。
- *`mode` 和 `state` 什么区别？* `mode` 说"这份文件我管不管它在哪"（散乱=用户自管 / 受管=在池里）；`state` 说"它现在拿不拿得到"（在线/离线/冷/丢失）。一条受管放置可以是冷的（池所在盘未插）。

### 2.5 `pool` 存储池表（评审轮新增，附录 A-10）

**用途**：登记受管存储池——内容按 hash 入池、可压缩、天然去重。多池并存应对单分区空间不够（如 Windows C 盘池 + D 盘池）。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 文本 | 池编号 | `pl_main` |
| `location_id` | 文本 | 池挂在哪个位置下（外键） | `lc_home` |
| `rel_path` | 文本 | 池根目录（相对位置根路径） | `pool/main` |
| `capacity_hint` | 整数 | 容量提示（字节，用户填或自动探测），选池时参考 | `2199023255552`（2 TB） |
| `compression` | 文本 | 池级压缩策略：`off` / `auto` 抽样决定 / `always`（zstd） | `auto` |
| `last_verified` | 整数 | 池上次整体校验时间 | `1760000000` |
| `state` | 文本 | 池状态：`online` / `offline`（盘未插） | `online` |

**选池规则**：归纳/写入时默认选 `state=online` 且剩余空间最大的池；用户可指定固定池。跨池不去重压缩策略冲突——同 hash 内容每池最多一份。

**常见疑问**
- *池和位置什么关系？* 位置是"用户登记的一个根目录"（可以是整个盘）；池是位置下的一个受管子目录，带容量/压缩等池级属性。一个位置可以没有池（纯散乱位置），也可以有多个池。
- *为什么元数据不拆多库？* 见 `01-总体设计.md` §4.6——去重、全局查询、记录同步都靠单一 catalog，拆库复杂度爆炸。

## 3. 语义层表（这是什么作品）

### 3.1 `entry` 词条表

**用途**：登记一个"作品或主题"的身份。例：《深空旅人》。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 文本 | 词条编号 | `en_bladerunner` |
| `kind` | 文本 | 词条类型：`work` 作品 / `concept` 主题概念 / `collection` 合集 / `series` 系列 / `person` 人物 | `work` |
| `title` | 文本 | 主标题 | `深空旅人` |
| `sort_title` | 文本 | 排序用标题（处理"The xxx"、数字开头等） | `深空旅人` |
| `subtitle` | 文本 | 副标题 | `Blade Runner` |
| `attrs_json` | 文本 | 扩展属性（JSON）：年份、简介、评分等自由字段 | `{"year":1982}` |
| `created` | 整数 | 创建时间 | `1758000000` |
| `updated` | 整数 | 最后修改时间 | `1760000000` |

**常见疑问**
- *主题（concept）可以没有版本吗？* 可以。比如"赛博朋克"这个词条只是一个分类主题，没有任何文件，`kind=concept`，下面 0 个版本。这是**设计如此**，不是数据缺失。
- *什么时候建 work、什么时候建 concept？* 有具体数据（或预期会有数据）的作品建 `work`；纯分类用的主题建 `concept`。

### 3.2 `entry_alias` 词条别名表

**用途**：一个词条的其他叫法（译名、原名、常见错写）。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 整数 | 自增编号 | `7` |
| `entry_id` | 文本 | 属于哪个词条 | `en_bladerunner` |
| `alias` | 文本 | 别名 | `Blade Runner` |

**常见疑问**：*为什么需要别名？* 扫描时按文件名匹配词条，文件里写的是 `Blade Runner (1982)`，靠别名才能对上中文主标题。

### 3.3 `entry_ext` 词条外部资料表

**用途**：记录"这个词条对应资料站上的哪一条"。刮削的基础。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 整数 | 自增编号 | `3` |
| `entry_id` | 文本 | 属于哪个词条 | `en_bladerunner` |
| `source` | 文本 | 资料站名字：`tmdb` / `douban` / `bangumi` / `openlibrary` | `tmdb` |
| `external_id` | 文本 | 在该资料站的编号 | `78` |
| `url` | 文本 | 条目链接 | `https://www.themoviedb.org/movie/78` |
| `fetched_at` | 整数 | 抓取时间 | `1760000000` |

**唯一约束**：（`entry_id`, `source`）—— 一个词条在同一个资料站只对应一条。

### 3.4 `version` 版本表

**用途**：登记词条下的一种具体"版次"。例：《深空旅人》的"4K 高码率版"。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 文本 | 版本编号 | `vr_bladerunner_4k` |
| `entry_id` | 文本 | 属于哪个词条 | `en_bladerunner` |
| `title` | 文本 | 版本标题（用户可改） | `4K 高码率版` |
| `ordinal` | 整数 | 排序号（比如"第 2 版"） | `2` |
| `edition` | 文本 | 版次说明 | `导演剪辑版` |
| `resolution` | 整数 | 分辨率高度（**高频查询字段，做成列**） | `2160` |
| `codec` | 文本 | 编码格式（高频查询字段，做成列） | `hevc` |
| `language` | 文本 | 语言版本 | `国语` |
| `released_at` | 整数 | 发行时间 | `1483228800` |
| `source` | 文本 | 来源：`purchased` 购买 / `downloaded` 下载 / `ripped` 转录 / `scanned` 扫描 / `generated` 生成 / `unknown` 未知 | `downloaded` |
| `state` | 文本 | 版本状态：`draft` 草稿 / `final` 定稿 / `superseded` 已被新版本取代 / `archived` 已归档 | `final` |
| `attrs_json` | 文本 | 其他自由属性 | `{}` |
| `created` / `updated` | 整数 | 创建 / 修改时间 | —— |

**唯一约束**：（`entry_id`, `ordinal`）—— 同一词条下排序号不重复。

**常见疑问**
- *为什么分辨率、编码做成列而不是标签？* 因为这两个字段查询频率极高（"找出所有 4K"）、需要精确比对、需要排序。做成列比在几百万行的标签表里筛快得多。低频、自由的分类才用标签。
- *版本和内容是一对一吗？* 不是。一个版本包含多个文件（见下表），每个文件才对应一条内容。

### 3.5 `version_file` 版本文件清单表

**用途**：登记"这个版本**应该**包含哪些文件"。这是版本的**定义**，不是实际存在情况。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 整数 | 自增编号 | `55` |
| `version_id` | 文本 | 属于哪个版本 | `vr_bladerunner_4k` |
| `rel_path` | 文本 | 版本内相对路径 | `video.mkv` |
| `content_blake3` | 文本 | 该文件对应的内容指纹 | `9f3c8a…` |
| `size` | 整数 | 字节数 | `42949672960` |
| `role` | 文本 | 文件角色：`primary` 主文件 / `subtitle` 字幕 / `cover` 封面 / `nfo` 元信息 / `other` 其他 | `primary` |

**常见疑问**
- *这张表和 placement 表什么区别？* `version_file` 说"版本**应该**有哪些文件"（定义）；`placement` 说"文件**实际**在哪"（事实）。两者可以对不上——比如版本定义了 4 个文件，但某台设备上只落地了 3 个，这时实例状态就是"部分"。
- *为什么要有定义？* 有了定义才能回答"我应该从移动硬盘取回哪些文件才构成完整的一版"，也才能做完整性校验。

### 3.6 `instance` 实例表

**用途**：登记"某个版本实际落地在某个位置的某个目录"。**是备份、校验、按需取回的操作单位。**

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 文本 | 实例编号 | `in_4k_hdd` |
| `version_id` | 文本 | 哪个版本 | `vr_bladerunner_4k` |
| `location_id` | 文本 | 落在哪个位置 | `lc_hdd` |
| `path` | 文本 | 目录路径 | `深空旅人/4K` |
| `state` | 文本 | `complete` 完整 / `partial` 部分缺失 / `missing` 全部缺失 / `unverified` 未核对 | `complete` |
| `matched_by` | 文本 | 怎么认定的：`auto` 程序按文件指纹自动匹配 / `manual` 用户手工登记 | `manual` |
| `created` | 整数 | 登记时间 | `1758000000` |

**唯一约束**：（`version_id`, `location_id`, `path`）。

**常见疑问**

## 4. 同步与传输层表（记录同步与 M3 数据同步专用）

### 4.1 `op` 操作流水表

**用途**：本设备做过的每一笔登记变更，按顺序记在这里。同步时把对方缺的部分发过去。**这是记录同步的唯一载体。**

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `seq` | 整数 | 流水号，自增，**只增不减** | `90210` |
| `device_id` | 文本 | 谁做的这条操作 | `dv_desktop` |
| `op_id` | 文本 | 操作全局唯一编号（幂等键），**唯一约束** | `op_7c9e…` |
| `kind` | 文本 | 操作种类（见下表） | `placement_add` |
| `payload` | 文本 | 操作内容（JSON） | `{"location":"lc_home",...}` |
| `ts` | 整数 | 操作时间 | `1760500000` |

**操作种类一览**

| 值 | 白话含义 |
|---|---|
| `device_add` / `location_add` | 新增了设备 / 位置 |
| `content_add` | 新增了一条内容 |
| `placement_add` / `placement_del` | 新增了一条放置 / 删除了一条放置（立墓碑） |
| `state_change` | 某个位置或放置的状态变了 |
| `tag_add` / `tag_assign` / `tag_rename` | 新增标签 / 贴标签 / 标签改名 |
| `entry_add` / `entry_update` | 新增词条 / 修改词条 |
| `version_add` / `version_update` | 新增版本 / 修改版本 |
| `instance_add` / `instance_del` | 新增实例 / 删除实例 |
| `connection_add` / `connection_del` | 新增关系 / 删除关系 |
| `conflict_resolve` | 人工裁决了一次同步冲突（审核队列每条裁决生成一条**更晚的新 op**，携带获胜值，见 01 §7.5 / A-16） |
| `rule_change` | 分类规则变了 |

**常见疑问**
- *为什么删除是"立墓碑"而不是直接删行？* 因为长期离线的设备还不知道这次删除。如果直接删，那台设备回连后会把它自己的旧记录当作"新增"再同步回来（俗称"复活"）。立墓碑 + 30 天宽限期，给离线设备足够时间同步到这个删除。
- *`op_id` 为什么单独存在，不直接用 `seq`？* 因为两台设备各自的 `seq` 从 1 开始数，会撞车。`op_id` 是全局唯一编号，收到重复的直接跳过（幂等），同步可以放心重试。

### 4.3 `sync_conflict` 同步冲突队列表

**用途**：同步合并时发现的**字段级**冲突，双方值整份快照进表——离线、断网、对端关机都能看能审（见 01 §7.5 / 附录 A-16）。

| 列名 | 类型 | 含义 | 示例值 |
|---|---|---|---|
| `id` | 文本 | 冲突编号 | `cf_2f81` |
| `object_kind` | 文本 | 冲突对象类型：`entry` / `version` / `tag` / `connection` / `placement` / `instance` | `entry` |
| `object_id` | 文本 | 对象编号 | `en_bladerunner` |
| `field` | 文本 | 冲突字段名（字段级粒度）；`attrs_json` 按整体比对；删除-修改冲突用特殊值 `__tombstone__` | `title` |
| `my_value` | 文本 | 本机侧值快照（JSON；删除-修改冲突且本机为删方时为 `null`） | `"银翼杀手 2049"` |
| `their_value` | 文本 | 对端侧值快照 | `"Blade Runner 2049"` |

**常见疑问**
- *为什么快照进表，不直接引用对象当前值？* 冲突期间双方都可能继续改，引用"当前值"等于审的时候已经不是当时打架的那两个值。快照保证审核所见即所争。
- *裁决后冲突会复活吗？* 不会。每次裁决（resolve）生成时间戳更晚的新 `op`（`kind=conflict_resolve`），对端旧值在后续合并中永远打不过（01 §7.5 收敛保证）。
- *这张表会同步到别的设备吗？* **不会。** 冲突是每台设备各自视角的本地状态；双方按同一套 merge 规则各自发现、各自裁决，最终靠新 op 收敛到一致。

## 7. 状态取值总览（一处查全）

### 7.1 位置状态（location.state）

| 值 | 能读写文件 | 参与记录同步 | 可作删除候选 | 可作传输源 |
|---|---|---|---|---|
| `online` | 是 | 是 | 有条件可以 | 是 |
| `offline` | 否 | 回连后可以 | **永不** | 否 |
| `cold` | 否 | **不参与** | **永不** | **永不** |
| `missing` | 否 | 是（会同步"已消失"） | 否 | 否 |

### 7.2 放置状态（placement.state）

与位置状态取值相同，含义相同，但**以放置为粒度**：一个在线位置内部，个别文件可能已消失（`missing`）。

### 7.3 版本状态（version.state）

| 值 | 含义 |
|---|---|
| `draft` | 草稿：还在整理，数据可能不全 |
| `final` | 定稿：认为已经完整 |
| `superseded` | 已被更新版本取代（旧版仍保留数据） |
| `archived` | 已归档：不再主动维护 |

### 7.4 实例状态（instance.state）

| 值 | 含义 |
|---|---|
| `complete` | 版本清单里的文件都在 |
| `partial` | 部分文件缺失 |
| `missing` | 全部缺失（记录保留） |
| `unverified` | 刚登记，还没核对过 |

### 7.5 AI 建议状态（ai_suggestion.state）

| 值 | 含义 |
|---|---|
| `pending` | 待确认，等待人工审阅 |
| `accepted` | 已接受，已写入业务表 |
| `rejected` | 已拒绝，留档以便统计 |
| `stale` | 已过期：目标对象被改动，建议不再适用 |

### 7.6 传输任务状态（transfer.state）

| 值 | 含义 |
|---|---|
| `queued` | 已登记，尚未开始（等待空闲连接或对端可达） |
| `running` | 正在传输，`offset` 随块校验推进 |
| `done` | 完成：整文件 BLAKE3 复核通过，`.part` 已改名为目标路径并登记 placement |
| `failed` | 失败：`error` 记原因（F404 对端不可达 / F405 校验失败 / F403 被拒）；`.part` 与 `offset` 保留 |
| `cancelled` | 用户取消；`.part` 与 `offset` 保留，可续传 |

### 7.7 按需策略档（placement_policy.mode）

| 值 | 白话含义 | 程序据此做什么 |
|---|---|---|
| `local_only` | 只留在本机 | 不从对端拉取（`transfer.fetch` 拒绝 F403）；本机副本不可被驱逐 |
| `mirror` | 镜像 | 本机应持有与对端一致的本体：缺了可 `fetch`，`transfer.evict` 拒绝 |
| `evictable` | 允许驱逐（删本体留记录） | `transfer.evict` 允许（仍要过冗余副本检查）；**程序不自动驱逐** |
| `record_only` | 只记不存 | 不拉取（F403）、不保留本体、也**不作为数据源**对外提供 |

### 7.8 备份校验状态（M4 新增，供 `backup.verify` 报告与 `snapshot.stats_json` 使用）

| 值 | 白话含义 | 程序据此做什么 |
|---|---|---|
| `ok` | 正常 | 清单/索引/段数据全部比对通过，回写池 `last_verified` |
| `mismatch` | 不一致 | 段内数据 BLAKE3 与索引记录不符 → 报 F603，列出内容指纹 |
| `missing` | 缺失 | 索引有记录但段内找不到该内容 → 报 F604 |
| `unreachable` | 不可达 | 备份目标当前无法访问 → 作业 `queued`，目标上线后续跑（F601） |
| `pending_restore` | 待恢复 | 恢复时内容只在离线池 → 进"待恢复队列"，池上线自动继续（F605） |

> **实现说明**（M4 编码期补充）：`snapshot.stats_json` 里的统计字段固定为 `{files, bytes, new_contents, segs}`；备份/校验/恢复三种作业都登记在 `job` 表（`kind` = `backup`），不另设作业表。

## 8. 索引与性能说明（策略见 01 附录 A-14）

### 8.1 索引列序通则

1. 复合索引列序：**等值条件列在前 → 范围条件列居中 → 排序列殿后**。
2. 单条查询的热索引不超过 6 个；贴附类表（`entry_tag` 等）建正反双向覆盖索引，避免"翻转查询"退化成全表扫描。
3. 索引不是越多越好：每多一个索引，写入多一份维护成本——新增索引前先写清"服务哪条查询"。

### 8.2 索引一览

| 表 | 索引 | 为什么建这个索引 |
|---|---|---|
| `placement` | `UNIQUE(location_id, rel_path)` | 唯一约束 + 按目录浏览 |
| `placement` | `(content_id)` | 查"某内容有几份副本"（去重核心；入口查询直接读 content.copy_count 物化列，此索引服务明细展开） |
| `placement` | `(location_id, mode, state)` | 位置 × 待归纳 × 在线状态复合筛选（inbox 视图热路径） |
| `placement` | `(mode)` | 查"待归纳的散乱放置"（inbox 视图单条件入口） |
| `placement` | `(pool_id)` | 池内布局浏览与跨池统计 |
| `content` | `(asset_type)` | 按资产类型筛选（视频/音频/应用…） |
| `version` | `(resolution, codec)` | 属性筛选复合索引："找出所有 4K / HEVC"（等值→等值） |
| `version` | `(codec)` | 属性筛选单条件入口 |
| `op` | `UNIQUE(op_id)` | 同步幂等 |
| `op` | `(device_id, seq)` | 同步时按"某设备的某段流水"导出 |
| `content` | 主键 `blake3` | 插入前查重 |
| `version_file` | `(content_blake3)` | 查"哪些版本清单引用了这段内容"（删除前置检查第 4 条） |
| `transfer` | `UNIQUE(content_blake3, target_path)` | 同一内容取到同一路径只算一条任务（续传幂等） |
| `transfer` | `(state, updated)` | 传输列表按状态筛 + 最近优先 |
| `placement_policy` | `UNIQUE(scope_kind, scope_id)` | 一个作用域一条策略（set 即覆盖） |
| `snapshot` | `UNIQUE(location_id, target, created)` | 同一位置对同一目标的同一时刻快照只算一条（幂等） |
| `snapshot` | `(location_id, created)` | 按位置列快照历史、找最近一次备份 |

> 原 `(placement.size)` 单列索引取消：分层哈希第一级筛选实际以"位置 + 大小区间"为主，交给 `(location_id, mode, state)` 与目录索引组合覆盖；单独按字节数全局筛的场景低频，不值一个百万行索引。

### 8.3 `copy_count` 物化列的维护约定

- **不变式**：`content.copy_count` = 该内容**有效** placement 条数（不含已删/墓碑）。
- **维护点**：placement 增、删（含墓碑登记）与归纳改指，在**同一事务**内增减本列——不允许"先记文件、后补计数"的窗口期。
- **校正**：`doctor` 启动体检时全量重算比对，漂移则告警并修正；属性测试对随机增删序列断言不变式（03 §7.1）。

### 8.4 全文检索（FTS5）

- 仅对**词条标题、别名、版本名**三张小表建 FTS5 `trigram` 虚表——CJK 子串查询友好，不引入外部分词依赖。
- **文件名搜索 v1 不进 FTS**：placement 百万级，trigram 体积失控；走 `rel_path LIKE '前缀%'`（可用索引）或按目录/位置过滤。全量文件名模糊搜索列为后续专项。

### 8.5 分页双轨

| 场景 | 策略 |
|---|---|
| 跳页（"第 N 页"） | OFFSET，**硬上限 10 万行**；更深的位置提示"请用筛选缩小范围" |
| 无限滚动 / 同步导出 / 批量作业 | keyset 游标：`WHERE (sort_key, id) > (?, ?) ORDER BY sort_key, id`，无深偏移 |

### 8.6 EXPLAIN 断言（CI 强制）

回归测试对以下固定查询断言执行计划：**只许 `SEARCH USING INDEX`，禁止 `SCAN`**（03 §7.1）：

| 编号 | 查询 | 命中索引 |
|---|---|---|
| Q1 | 位置 × 资产类型 × 分辨率/编码筛选 | placement 复合 + version 属性复合 |
| Q2 | 词条标题 LIKE 前缀搜索 | 别名表前缀索引 / FTS |
| Q3 | 去重入口：按 copy_count 查内容 | content 主键 + 物化列直读 |
| Q4 | 同步流水段导出（某设备 seq 区间） | op `(device_id, seq)` |

### 8.7 性能预算与基准工具

| 查询 | p95 预算 | 前提条件 |
|---|---|---|
| Q1 属性筛选 | < 50 ms | 100 万 placement 量级库，固态盘、页缓存已热 |
| Q2 标题前缀搜索 | < 100 ms | 10 万词条量级，同上 |
| Q3 copy_count 直读 | < 20 ms | 物化列，免聚合 |
| Q4 流水段导出 1 万条 | < 500 ms | 批量顺序读 |
| 冷盘最坏情况 | 不设预算 | 冷 I/O 另计；界面必须有加载态，不允许假死 |

- 工具：`rmgr bench query` 一键跑 Q1–Q4，输出耗时 JSON。
- CI 每周与基线对比，p95 恶化超过 **50%** 告警——性能不可验收等于不存在，断言与预算一起进 CI 才不腐烂。

### 8.8 容量参考

- 100 万条放置 + 相关索引 ≈ 1–2 GB 数据库文件。
- 单事务写 1–2 万行时，固态盘上可达每秒 10 万行以上。
- 查询必须分页（默认每页 500 行），禁止一次性取回全部结果。
