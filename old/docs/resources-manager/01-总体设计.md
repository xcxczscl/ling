## 1. 项目要解决的问题

### 1.1 一句话描述

把用户（以及任何用户）散落在多台设备、多块硬盘、各种网盘目录里的文件，统一**归纳、整理、分类、按需同步、去重、压缩、备份**，并且**在设备离线、硬盘不插的时候，仍然记得这些数据的存在**。

### 1.2 用户故事（用贯穿示例描述）

| 编号 | 用户想做的事 |
|---|---|
| S1 | 我有 10 TB 以上的文件，散在台式机、笔记本、几块移动硬盘里，想知道"到底哪些是重复的、哪些只有一份" |
| S2 | 我想把文件按"作品"来组织：《深空旅人》下面有 1080p 版和 4K 版，而不是靠文件夹名字自己记 |
| S3 | 我的移动硬盘长期不插，但系统里必须记得"4K 版本存在那块盘上"，不然去重时会误删唯一副本 |
| S4 | 笔记本上只有《旧港疑云》的电子版，我想知道台式机上有没有，有的话一键取回来（走局域网，别走外网） |
| S5 | 我懒得手工整理，希望程序能自动打标签、自动告诉我《深空旅人2》是《深空旅人》的续集、自动从豆瓣/TMDB 拉简介和封面 |
| S6 | 我不希望自己的文件名、目录结构被上传到别人的服务器上 |
| S7 | 我在 Windows 上用图形界面，偶尔在 Linux 服务器上用命令行，手机上也想看看有什么文件 |
| S8 | 将来我还想装记账、网站管理等其他工具，它们最好能和文件管理共用一套框架 |

### 1.3 三条硬性要求（不可妥协）

| # | 要求 | 为什么 |
|---|---|---|
| H1 | **不架设服务器。** 跨设备只同步"文件清单记录"，文件本体的传输由用户显式发起 | 个人工具，不接受常驻云端服务；也避免数据出网 |
| H2 | **图形界面为主，同时提供网页和命令行**，三者功能等价 | 不同场合用不同入口，但不允许"命令行能做的界面做不了" |
| H3 | **程序本身是插件，宿主"大程序"零内容** | 以后的界面、设置、插件管理、记账、网站管理，全部做成插件 |

## 3. 技术选型

| 项目 | 最终选择 | 为什么选它 | 否掉了谁、为什么 |
|---|---|---|---|
| 核心语言 | **Rust** | 10 TB 扫描与哈希需要"内存占用不随数据量增长"和多核并行；同一份代码能编译成 Windows 的 `.dll`、Linux 的 `.so`、安卓的 `.so` | Python：手机上跑不动、扫描 10 TB 太慢<br>Go：性能够，但图形界面和安卓壳方案弱<br>C#：可行的备选，但安卓打包流程更繁琐 |
| 图形界面 | **Tauri 2** | 官方支持 Windows、Linux、安卓；窗口里放的就是网页，和"网页版"共用一套代码；安装包体积小（十几 MB 量级） | Electron：安装包 100 MB 起、内存占用高<br>Qt：手机端方案不成熟 |
| 前端 | **TypeScript + React + Vite** | 文件列表可能有几十万行，虚拟滚动（只渲染可见行）的现成方案最成熟 | Svelte：也可以，但资料少；以后可替换，不影响后端 |
| 数据库 | **SQLite（开启 WAL 模式）** | 嵌入在程序里，不需要装数据库服务；一个写线程 + 批量提交时，每秒可写 10 万行以上（前提：固态硬盘、每 1–2 万行一个事务） | MySQL/PostgreSQL：需要服务端，违反 H1 |
| 内容哈希算法 | **BLAKE3** | 单核心每秒可算 1–3 GB（前提：数据已在内存或固态盘缓存）；比 SHA-256 快 5 倍以上 | SHA-256：太慢<br>xxHash：速度快但抗碰撞性弱，不适合做去重依据 |
| 压缩算法 | **zstd** | 压缩速度可达每秒数百 MB，压缩比可调 | gzip：慢<br>xz：慢且吃内存 |
| 插件加载方式 | **双轨**：Rust 插件 = 进程内动态链接库；非 Rust 插件 = 进程外侧车 | 详见 ling 决策 A-1：双轨让 Rust 插件保持零开销直调，同时不排除其他语言；进程内轨道满足安卓不允许随意起进程的限制 | 全部进程内：语言受限；全部进程外：Rust 插件受损耗且安卓不可行 |
| 网络接口 | 本机回环 HTTP + WebSocket | 窗口壳、浏览器、命令行三种入口共用同一套接口，功能天然一致 | 各入口各写一套：功能会慢慢不一致 |

## 4. 核心概念详解（用贯穿示例讲透）

### 4.1 为什么需要"四层结构"

如果只按"文件夹"管理，用户会遇到这些做不到的事：

- 《深空旅人》的 1080p 版和 4K 版散在两个文件夹，无法回答"这部作品我一共有哪些版本"；
- 同一部电影在三台设备上有五份拷贝，文件夹结构看不出"哪份是多余的、哪份是唯一副本"；
- 移动硬盘不插的时候，系统里应该"知道"4K 版本存在那块盘上，否则去重时会把台式机上那份当作"唯一副本"而不敢清理，或者更糟——误删。

所以本项目把数据拆成**四层**：

```
语义层：词条 Entry ──┬── 版本 Version ── 版本文件清单 version_file
                    ├── 标签 Tag（分域，三层体系见 §4.4）
                    └── 关系 Connection（含 part_of / contains：系列包含作品）
内容层：内容 Content（BLAKE3 指纹标识，资产类型 asset_type，永远不变）
物理层：设备 Device ── 位置 Location ── 存储池 Pool ── 放置 Placement（受管/散乱）
操作层：实例 Instance（把"某个版本"和"某个位置上的某个目录"绑定起来）
```

### 4.2 逐层解释（每一层都用示例走一遍）

**第一层：语义层（这是什么作品）**

| 名词 | 在示例中的样子 |
|---|---|
| 词条 | 《深空旅人》是一个词条，类型为"作品"（`kind=work`）；"深空系列"是另一个词条，类型为"系列"（`kind=series`），它—[包含]→《深空旅人》《深空旅人2》（一部作品可属多个系列，用关系边表达，不用父子树） |
| 版本 | 词条下挂两个版本：版本 A（标题"1080p 普通版"，分辨率列=1080p）、版本 B（标题"4K 高码率版"，分辨率列=2160p） |
| 版本文件清单 | 版本 A 声明自己应当包含 3 个文件：`video.mkv`、`sub.srt`、`cover.jpg`；版本 B 声明包含 4 个文件 |
| 标签 | `赛博朋克`（题材域，贴在词条上）、`4K`（质量域，贴在版本 B 上）、`HDR`（质量域，贴在版本 B 上）；用户还建了主观标签 `喜欢`（心情域）——主观标签合法，就是普通用户标签（三层体系见 §4.4） |
| 关系 | 词条《深空旅人2》—[续集]→ 词条《深空旅人》；"深空系列"—[包含]→两部作品 |

> **关键点**：`4K` 是贴在**版本**上的，不是贴在词条上的。界面在词条页显示"本作品包含 4K 版本"时，是**当场从版本标签算出来的**（即"派生标签"），不写进数据库。这样就避免了"《深空旅人》既是 4K 又是 1080p"的自相矛盾。

**第二层：内容层（数据本身是什么）**

《深空旅人》4K 版里的 `video.mkv` 是一个 40 GB 的文件。程序读取它、算出一串指纹（比如 `blake3:9f3c…`），登记为一条"内容"，并标注**资产类型** `asset_type=video`（包罗万象的第一步：video / audio / image / app / game / doc / archive / other，类型专属元数据进扩展 JSON 列；未来播放/运行由独立插件经流交付接口消费，见附录 A-12、A-17）。内容一旦登记**永不改变**：只要文件改动一个字节，它就是一条全新的内容，拥有新的指纹。这就像人的身份证号——改了长相就等于换了个人。

**第三层：物理层（数据实际在哪）**

| 名词 | 在示例中的样子 |
|---|---|
| 设备 | 台式机（Linux）、笔记本（Windows）、移动硬盘 |
| 位置 | 台式机上的 `/data/media`；笔记本上的 `D:\media`；移动硬盘上的 `E:\` |
| 放置 | 内容 `blake3:9f3c…` 存放在"移动硬盘 E 盘"这个位置下的路径 `深空旅人\4K\video.mkv`，这条登记就是一条放置 |

**第四层：操作层（把语义和物理绑起来）**

| 名词 | 在示例中的样子 |
|---|---|
| 实例 | "版本 B 落地在移动硬盘 `E:\深空旅人\4K\` 这个目录"——这是一条实例登记。备份、校验、按需取回都以实例为单位操作 |

> **一个版本可以有 0 个实例**：比如用户只在资料站登记了某书的信息、文件还没下载，此时词条和版本存在，但一个实例都没有。这正是"我拥有这部作品的登记，但本地没有数据"的自然表达。

### 4.3 四层之间怎么对应（速查表）

| 你想知道 | 去查哪一层 |
|---|---|
| 这是什么作品？有哪些版本？ | 语义层：词条 + 版本 |
| 这部作品我总共有多少 GB？ | 语义层版本 → 内容层求和（跨设备不重复计算） |
| 这部作品现在在哪几台设备上？ | 版本 → 实例 → 位置 → 设备 |
| 有没有重复文件？ | 内容层：同一内容有多条放置 |
| 哪些数据现在拿不到（离线/冷备份）？ | 物理层：位置或放置的状态字段 |
| 两部作品是不是续集关系？ | 语义层：关系 |

### 4.4 标签体系：三层分离（属性 / 用户标签 / 派生）

> 决策依据：评审轮确认（附录 A-8）。核心原则：**客观的走列，主观的走标签，展示的临时算**。

**第一层：系统属性（客观，不是标签行）**

扫描/刮削时自动抽取的客观事实，存在版本/内容表的**结构化列**上（如 `resolution`、`codec`，见 `02` §3.4），建索引供筛选。界面的"属性筛选器"和标签筛选外观一致，底层各查各的。

| 为什么属性不物化成标签行 | |
|---|---|
| 存储 | 属性列压缩后几十字节；做成 tag 行 + 贴附行，存储翻倍 |
| 写入 | 属性随文件变（换编码即变）；标签行要删旧贴新，写放大 |
| 语义 | 属性是事实（2160 就是 2160）；标签是观点——混在一起，查询方无法区分"客观可筛选"与"主观分类" |

**第二层：用户标签（主观，分域且域可扩展）**

| 域（预置核心域） | 含义 | 贴在哪 | 例子 |
|---|---|---|---|
| `subject` 题材域 | 题材、主题、作者、类型 | **词条** | `赛博朋克`、`菲利普·迪克` |
| `format` 格式域 | 文件格式 | **版本** | `epub`、`PDF`、`remux` |
| `quality` 质量域 | 画质/音质/语言版本 | **版本** | `4K`、`HDR`、`国语` |
| `source` 来源域 | 数据从哪来 | **版本** | `购买`、`抓取`、`自压制` |
| `status` 状态域 | 处理状态 | 词条或版本 | `待整理`、`已归档` |
| `自建域`（如 `mood` 心情、`todo` 待办） | 用户自定义 | 用户指定 | `喜欢`、`待归纳` |

规则：
1. **一个标签只属于一个域**；同名不同域 = 两个标签（显示带域前缀，如"画质/4K"）。标签编号全局唯一。
2. **域本身可扩展**：预置五个核心域 + 用户可自建域；自建域显示时加用户命名空间前缀，避免撞名。
3. **主观标签允许且合法**（"喜欢""待整理"就是普通标签）——单用户产品，全设备同步后一致，不需要特殊机制。
4. 词条级默认只统计 `subject`、`status` 域；其他域落版本层。需要精确查询必须落到版本（如"找出所有 4K 版本"= 查质量域标签）。
5. 同义词表 `tag_alias` 用户可维护（改名/合并防离线复活）。

**第三层：派生标签（展示用，不落库）**

界面在词条页显示"本作品包含：4K、HDR"时，当场从版本标签/属性算出，不写数据库。派生标签不参与精确查询、不能被 AI 写入。

**属性列的扩展约定**：高频查询的属性做成列（分辨率、编码、时长、体积……）；低频、结构不定的属性进 `attrs_json`。哪些属性升列为"可筛选属性"，随 M1+ 迭代追加（索引细节另轮讨论）。

### 4.5 "记录"与"数据"的分离（贯穿全项目的原则）

| | 记录 | 数据 |
|---|---|---|
| 是什么 | 数据库里的登记行（词条、版本、放置、标签、关系…） | 磁盘上的实际文件字节 |
| 体积 | 100 万条记录约几百 MB | 10 TB |
| 能否跨设备同步 | **能，而且默认同步**（这就是"记录同步"） | 不自动同步；必须用户显式发起（"数据同步"） |
| 设备离线时 | 回连后照样能同步 | 拿不到 |
| 冷备份盘上 | 有完整记录 | 数据在盘上但长期不联网 |

**这一条是本项目所有安全规则的基础**：正因为记录和数据分离，我们才能做到"移动硬盘不插，系统仍然记得 4K 版本在那块盘上，因此不会把台式机上那份当成多余副本删掉"。

### 4.6 归纳、存储池与散乱文件（评审轮新增，附录 A-10）

**"归纳"的定义**：把散落的文件收进**受管存储池**（managed pool），获得：去重、有序布局、按需压缩、以内容为单位的备份/同步。

| 概念 | 设计 |
|---|---|
| 元数据目录 | **保持单一** `catalog.db`——去重、全局查询、记录同步都靠它；拆多个会让跨库去重和同步复杂度爆炸。catalog 只存元数据（GB 级），单库足够 |
| 受管存储池 | 内容按 hash 布局进池，可压缩（zstd）、天然去重；**多个池**并存（如 Windows 单分区不够时，C 盘池 + D 盘池），每池挂一个目录；内容放哪个池看剩余空间，读时按放置找回 |
| 散乱文件 | `placement.mode = scattered`：只登记原路径，文件归用户自己管理；界面有"待归纳"视图，提示择机归纳 |
| 归纳操作 | 用户显式发起：选中散乱放置 → 移入指定池（默认自动选有空间的池）→ 移动/硬链接到池内布局 → mode 切为 managed |

**一个诚实的边界**：归纳让**元数据查询**变快（在 DB 里），但**文件本体的读写速度不会因入库变快**（反而多一层）。入库的真实收益是去重省空间、结构有序、按需压缩、备份同步以内容为单位。

| 诚实的边界 | 归纳的收益 |
|---|---|
| ❌ "入库后读文件更快" | ✅ 元数据/检索/去重统计快（在 DB） |
| ❌ "归纳等于备份" | ✅ 省空间（去重+压缩）、有序、备份/同步以内容为单位 |
| —— | ✅ 散乱文件先登记后归纳：不强迫一次性整理完 |

**影响**：数据字典新增 `pool` 表、`placement.mode`/`pool_id` 列（见 `02` §2.4、§2.5）；M1 扫描流程增加"散乱登记"路径。

## 5. 系统分层与模块职责

### 5.1 分层图

```
┌────────────────── 表现层：三种入口，共用一套后端 ──────────────────┐
```

### 5.2 分层规则（强制执行）

1. 上层可以依赖下层，**禁止反向依赖**（例如领域核心不得调用界面代码）。
2. 插件之间**只能**通过宿主的调用路由和事件总线通信，不允许直接调用彼此的内部函数——否则权限门禁就形同虚设。
3. 表现层不写业务规则，只负责显示和调用。
4. 领域核心是**纯代码库**：没有窗口、不监听网络，可以在命令行、测试、插件里复用同一份。

## 6. 进程与线程模型

### 6.1 进程

| 进程 | 包含什么 | 说明 |
|---|---|---|
| ling 进程 | ling 内核 + 全部 Rust 插件（进程内加载） | 常驻；界面、网页、命令行都连它（见 ling/docs/04 §4） |
| 窗口程序 | 只是一个指向 `127.0.0.1:7910` 的窗口 | 关掉窗口不影响后台扫描与同步 |
| 手机程序 | 宿主 + 前台服务 + 网页视图 | 前台服务带常驻通知，防止系统杀进程 |
| 命令行 | 独立小进程 | 连接常驻宿主；或用 `--standalone` 参数在自己进程里直接跑一遍完整流程（适合服务器、脚本） |

### 6.2 线程

| 线程 | 职责 | 数量 |
|---|---|---|
| 主线程 | 平台事件循环（窗口、系统消息） | 1 |
| 异步运行时线程池 | 处理接口请求、调用转发、事件广播、同步任务 | 多（按 CPU 核数） |
| **数据库写线程** | 独占写权限，接收批量提交，单个事务写入 1–2 万行 | **严格 1 条** |
| 扫描线程 | 遍历目录、读取文件元数据 | 按磁盘分配（见下） |
| 哈希线程 | 读文件、算指纹 | 按磁盘分配 |

**磁盘调度规则（重要）**：
- **机械硬盘：每块盘只开 1 条顺序读取线程。** 原因：机械硬盘的磁头来回移动（寻道）会让速度从 100 MB/s 掉到几 MB/s，多线程并发读同一块机械盘反而更慢。
- **固态硬盘：可以多线程并发**，因为没有寻道问题。

### 6.3 内存纪律（强制）

任何环节都不得把整个目录树、整个文件、整个数据库结果集读进内存：
- 文件按 1–4 MB 一块流式处理；
- 数据库查询必须分页（每页默认 500 行）；
- 扫描进行中，整个程序常驻内存目标 **< 300 MB**（不含浏览器）。

## 7. 关键业务流程

> 每条流程都标注了涉及的模块，方便对照 `03-接口与协议.md` 查接口。

### 7.1 扫描（模块：rm-fs、rm-scan、rm-catalog）

**目的**：把一个位置（比如台式机的 `/data/media`）里的所有文件登记进数据库。

**步骤**：
1. 用户在界面或命令行发起扫描，系统创建一个"作业"（可查进度、可取消）：若 core-job 插件已安装则登记到它（统一作业界面）；未安装则 resources-manager 自管作业（进度仅在自己的界面可见）。
2. 遍历目录，跳过用户设置的忽略规则（比如 `.git`、`node_modules`、`@eaDir`）。
3. 对每个文件做**分层哈希**（见 §7.2），避免为明显不重复的文件读全盘。
4. 批量写入数据库：新内容一条、新放置一条（`mode=scattered`，除非目标路径在受管存储池内——见 §4.6）。每 1–2 万行提交一个事务。
5. 每提交一批，广播一次进度事件，界面刷新百分比、已发现文件数、已处理字节数。
6. 完成后写入统计：文件数、总字节、内容条数、重复组数、重复可回收字节；"待归纳"视图列出新增的散乱放置。

**增量重扫**：如果一个文件的路径、大小、修改时间都没变，就认为它的内容没变，**跳过重新算哈希**。因此第二次扫描同样 10 TB 只需要分钟级（只读元数据，不读文件内容）。

### 7.2 分层哈希（模块：rm-scan）

**目的**：用最省的读盘量，判断两个文件是否内容相同。

| 级别 | 做什么 | 读多少 | 结论 |
|---|---|---|---|
| 第一级 | 比较文件大小 | 0 字节（元数据） | 大小不同 → **肯定不同**，直接结束 |
| 第二级 | 比较文件开头和结尾各 64 KB 的快速指纹 | 128 KB | 不同 → 大概率不同，标记待定 |
| 第三级 | 读全文算 BLAKE3 指纹 | 全部 | 指纹相同 → 内容相同，算重复 |

**收益举例**：用户有 50 万张照片，大小各不相同。第一级就能排除 90% 以上的两两比较，实际需要读盘的文件大大减少。

### 7.3 去重与安全删除（模块：rm-dedup）

**目的**：找出重复文件，并且**保证任何情况下都不删掉唯一副本**。

**删除前必须通过的四道检查**（写死在代码里，不可配置绕过）：

| # | 检查 | 不通过的后果 |
|---|---|---|
| 1 | 该内容除了要删的这份，**至少还有 1 份在线且近期校验过的副本** | 拒绝删除，命令行退出码为 3 |
| 2 | 离线、冷备份状态的副本，**永远不作为删除候选**，只作为"存在第二份拷贝"的证据 | —— |
| 3 | 同一块磁盘上优先用**硬链接**合并（不占双份空间、不搬数据），而不是删除 | —— |
| 4 | 只有当某条内容的放置数归零、且没有任何版本清单引用、且没有作业正在使用它，才允许真正清除该内容 | —— |

**示例**：用户想删掉台式机上的《旧港疑云》扫描版（因为笔记本上也有一份）。系统检查发现：笔记本那份状态是"在线"且 3 天前校验过 → 允许。若笔记本长期离线，系统会拒绝并提示"目前唯一可访问的副本即将被删除"。

**删除后**：不是立刻真删，而是立一个"墓碑"，30 天宽限期后才允许物理清除（见 §7.5）。

### 7.4 分类与整理（模块：rm-classify、rm-semantic）

**目的**：按用户写的规则自动打标签、自动归入词条。

**规则格式**：`如果 符合条件 则 执行动作`

| 条件类型 | 例子 |
|---|---|
| 路径匹配 | 路径含 `/电影/` |
| 扩展名 | `.mkv`、`.epub` |
| 文件名模式 | 文件名含 `S01E02` 这样的剧集编号 |
| 大小/日期 | 大于 10 GB、2020 年前 |
| 已有标签 | 已带 `科幻` |

| 动作类型 | 例子 |
|---|---|
| 打标签 | 加上 `科幻`（题材域） |
| 归入词条 | 按文件名推断作品名，创建或匹配词条 |
| 排除扫描 | 该目录以后不再扫描 |
| 设定压缩级别 | 备份时用最高压缩 |

**重要约束**：规则只改**记录**（标签、词条归属），**不搬动磁盘上的文件**。真正移动文件是另一个显式的"整理执行"动作，必须二次确认——因为搬文件可能触发杀毒软件扫描、可能跨磁盘很慢、可能出错。

**示例**：用户写规则"路径含 `/电影/` 且扩展名 `.mkv` → 打上 `待整理` 标签（状态域）"。执行后，137 个文件被打上标签，磁盘上什么都没动。

### 7.5 记录同步（模块：rm-sync）

**目的**：两台设备交换"文件清单"，让彼此知道对方有什么。**不传输任何文件数据。**

**机制**：**纯点对点，无中心服务器**（评审轮确认，附录 A-11）——每台设备维护一条只增不减的操作流水（数据库表 `op`），每条操作有递增序号和一个全局唯一的操作编号（幂等键）。同步时双方交换"你还没有的那部分流水"。逻辑上是一张所有设备共有的资源表，物理上每设备一份本地副本，两两合并收敛；长期离线设备回连后做一次性大合并，合并幂等可重放。**界面"高亮自己拥有的数据"** = 按当前设备的 placement 归属渲染。

**合并规则**（防止同步出错的关键）：

| 情况 | 处理方式 |
|---|---|
| 同一内容被双方各登记一次 | 内容指纹相同 → 视为同一件事，忽略重复，**不会冲突** |
| 同一路径被双方各登记一次 | 以（位置 + 路径）为唯一键，后到的覆盖元数据 |
| 双方**无交集的修改**（A 改标签、B 改别名） | 自动合并，无需干预 |
| **冲突：edit-edit**（双方改同一字段且值不同） | **字段级比对**：只有同字段打架才构成冲突，非冲突字段各取所长自动合并；败方值快照进人工审核队列（详见 §7.9 冲突队列，附录 A-16） |
| **冲突：delete-edit**（一方删除、一方修改） | 删除默认胜（墓碑语义），修改进人工审核队列，可"撤销删除并恢复修改" |
| 位置状态（在线/离线/冷） | **只由该位置所属的设备自己上报**，别的设备无权改写——否则笔记本可能把用户标记为"冷备份"的移动硬盘错误地改成"在线" |
| 删除操作 | 写入墓碑，**30 天宽限期**内不物理清除；宽限期内设备回连不会误删，只会看到"该副本已被标记删除" |

**冲突收敛保证**：用户在审核队列的每一次裁决（resolve）都会生成一条**时间戳更晚的新操作**写回本机流水——对端的旧值在后续合并中永远打不过这条新 op，因此冲突不会复活、队列不会越审越多。长期离线设备回连时带回来的旧冲突，也按同一规则被 resolve 自动胜出。

**示例**：用户的笔记本 45 天没开机。开机后自动同步，发现台式机上曾删过一份重复文件（墓碑已过期，数据已清）；同时把《旧港疑云》电子版的放置记录同步给台式机。双方登记库收敛一致，没有任何文件被传输。

### 7.6 数据同步（模块：rm-transfer，M3 实现，格式先冻结）

**目的**：把文件本体从一台设备传到另一台，按需、可断点续传、走局域网。

| 项目 | 设计 |
|---|---|
| 设备身份 | 每台设备首次运行生成一把 Ed25519 密钥（相当于设备的身份证）+ 自签证书 |
| 配对 | 输入 8 位配对码或扫二维码，交换身份指纹，之后固定信任（换证书会被拒绝，防中间人） |
| 传输方式 | 拉取式：缺数据的设备向持有数据的设备请求；8 条并行连接；每 4 MB 一块附带校验值 |
| 断点续传 | 从最后一次确认的偏移继续，不用从头再来 |
| 实测速度 | 约 110 MB/s（前提：千兆网线 + 千兆交换机 + 8 并行连接；理论上限 125 MB/s） |
| 策略 | 按目录或标签设置四档，见下表；求值见 `02` §4.5 |
| 冷备份限制 | 状态为冷备份的位置**永远不作为数据源**——冷盘不联网，也不该被当作可传输对象 |

**策略四档**（`placement_policy` 表，`02` §4.5/§7.7；**程序只按策略行动，永不自动删除或驱逐**）：

| 档 | 白话 | 程序据此做什么 |
|---|---|---|
| `local_only` 只留在本机 | 这份数据本机自己管，不从对端拉 | `transfer.fetch` 拒绝（F403）；副本不可被驱逐 |
| `mirror` 镜像 | 本机应持有与对端一致的本体 | 缺了可取回；`transfer.evict` 拒绝 |
| `evictable` 允许驱逐 | 本机副本可以"删本体留记录" | `transfer.evict` 放行（仍过冗余副本检查）；**不自动执行** |
| `record_only` 只记不存 | 只留登记，不留字节 | 不拉取（F403）、不保留、**不作数据源** |

无匹配策略时默认 `local_only`。作用域冲突时 `priority` 大者胜（同分：标签域先于路径前缀）。

**示例**：用户在笔记本上看到《深空旅人》4K 版本"存在于移动硬盘，但本机没有"。插上移动硬盘，点"取回"，笔记本从移动硬盘以约 110 MB/s 的速度拉取 40 GB，约 6 分钟完成，中途拔线后重插可从 60% 处继续。

### 7.7 压缩与备份（模块：rm-store、rm-backup，M4 实现，格式先冻结）

**压缩**：
- 数据库里每条内容可以有两种形态：原始（供日常访问）和 zstd 压缩（供冷数据与备份）。
- 是否值得压缩由程序抽样判断：先压缩前 1 MB，如果压缩后没有小于原体积的 95%，就跳过（已经压缩过的视频、图片再压通常浪费时间）。

**备份**：

**目标策略：经典 3-2-1**（评审轮讨论，附录 A-13 背景）——3 份拷贝、2 种介质、1 份异地。在本系统的落法：

| 3-2-1 要素 | 落法 |
|---|---|
| 3 份 | 内容本体 + 备份池 A + 备份池 B；内容寻址天然去重：同一 hash 每池只存一份 |
| 2 种介质 | 本地盘（池 A）+ 移动盘/NAS（池 B 或异地池） |
| 1 异地 | 另一物理位置的移动盘/NAS 挂为异地池；**异地池可选密码加密（AEAD），密码丢失 = 备份不可用，界面明示** |

- 备份目标（外置盘、NAS 共享目录）上采用"段式存储"：把数据切成 **128 MB 一段**的文件，配一份索引和一份清单，全部带校验值。
- **已备份过的内容不会重复写入**——这是内容寻址带来的天然增量备份。
- 三种操作：备份（写入）、校验（抽样或全量核对，报告"正常/不一致/缺失"）、恢复（取回）。
- **离线目标（同记录同步的问题）**：备份池长期不插 → 备份作业排队，目标插上自动续传（复用 M3 传输机制）；每池记录 `last_verified`，界面显示"已 N 天未校验"。
- **从冷备份恢复**：如果要恢复的文件只在长期不插的移动硬盘上，系统不会报错失败，而是把它排进"待恢复队列"，等那块盘插上、状态变成在线后自动继续。

**同步与备份的分界一句话**：同步 = 让别的设备知道"有什么"（记录合并）；备份 = 灾难后能"拿回来"（内容副本 + 校验 + 恢复）。

### 7.8 AI 能力（模块：rm-ai + 插件族，M5 实现）

**定位：AI 只是"建议者"，不是"执行者"。** 这是不可协商的边界。

**7.8.1 三步流水线**

| 步骤 | 做什么 | 由谁做 |
|---|---|---|
| 第一步：确定性提取 | 读扩展名、用 ffprobe/exiftool 提取音视频与图片的内嵌信息、文件名模式识别（剧集编号、版本号、书号）、目录规则 | 纯代码，**不花钱、可复现** |
| 第二步：外部资料对齐 | 用标题/年份去 TMDB、豆瓣、Bangumi、OpenLibrary 等资料站查询候选记录（这一步就是"刮削"） | 资料站插件（声明"可访问网络"能力） |
| 第三步：语义判断 | 把"我的文件名 + 已提取信息 + 候选记录"交给大模型，让它判断匹配度、补题材标签、推断作品关系 | AI 插件，**只处理前两步剩下的部分** |

> 设计理由：10 TB 里绝大多数文件靠前两步就能处理完。大模型按调用次数计费，如果让它逐个文件分析，成本和耗时都不可接受。

**7.8.2 建议表机制（AI 不能直接改数据库）**

AI 的所有产出写入一张"建议表"，每条包含：目标对象、建议内容（打什么标签/建什么关系）、置信度、使用的模型、提示词指纹、输入指纹。状态在"待确认 / 已接受 / 已拒绝 / 已过期"之间流转。

界面提供一个"待审建议"页面，用户逐条看：接受 / 修改后接受 / 拒绝。

**7.8.3 分级确认规则**

| 风险级别 | 操作举例 | 处理方式 |
|---|---|---|
| 低风险 | 打题材标签（如"科幻"） | 置信度达到阈值时**可自动采纳**，但全部带"来源=AI"标记，支持一键整体撤销 |
| 高风险 | 建立作品关系、创建新词条、拆分版本 | **必须人工逐条确认**，AI 无权自动写入 |
| 禁止 | 删除、去重判定、备份决策 | **AI 永远无权参与**，安全规则保持纯代码实现 |

**7.8.4 隐私三档（用户可按目录设置）**

| 档位 | 行为 | 适用 |
|---|---|---|
| 本地（local） | 使用本机运行的模型（如 Ollama），任何数据都不出机器 | 敏感文档、工作文件 |
| 云端（cloud） | 调用云端大模型接口，但**只上传文件名与已提取的技术参数**，绝不上传文件内容；可按目录设黑名单 | 对隐私不敏感的影视、公开书籍 |
| 混合（hybrid，默认） | 分类和关系用本地模型；只有"外部资料对齐"才走云端 | 大多数场景 |

**7.8.5 成本控制**

| 手段 | 说明 |
|---|---|
| 按词条聚合 | 不是每个文件调用一次，而是一个词条（或一个目录）打包成一次请求 |
| 提示词缓存 | 提示词指纹相同的请求直接复用结果 |
| 预算上限 | 作业可设"最多调用次数/最多花费"，耗尽即自动停止并报告 |
| 可重跑 | 记录模型版本、提示词指纹、输入指纹，模型升级后可选择性重算 |

**7.8.6 防幻觉措施**

1. 所有 AI 产出带来源标记，支持按来源批量清除。
2. AI 只允许建议"建立别名关系"，**不允许直接合并两个词条**（合并一旦同步到多台设备很难回滚）；真合并需要人工二次确认，且自动先备份数据库。
3. 从资料站拉取的简介、封面等信息，一律带"来源地址 + 抓取时间"，与用户自己的笔记分开存放。

### 7.9 归纳与池管理（模块：rm-catalog、rm-fs，M1/M2 实现）

**归纳** = 散乱放置迁入受管存储池（概念见 §4.6）。本节定操作细则（附录 A-15）。

**7.9.1 迁移成本三档（自动判定，界面预告）**

| 档 | 条件 | 动作 | 成本 |
|---|---|---|---|
| A 同文件系统 | 源与目标池同一分区 | `rename` | 毫秒级零拷贝 |
| B 同设备跨分区 | 同机不同盘 | 拷贝→**全量校验**→删源 | 读写各一遍 |
| C 跨设备 | 源在别的设备 | 源需在线，走局域网传输→校验→删源 | 慢；任一端离线则排队 |

**7.9.2 删源铁律与顺序**

**池中副本 BLAKE3 全量校验通过之前，源文件一个字节都不删。** 顺序铁律：**文件先行（临时名 `.tmp` + 校验）→ DB 提交 → 删源**——DB 永远不比文件先变。

| 崩溃断点 | 状态 | 恢复 |
|---|---|---|
| A 档 rename 后、DB 提交前 | 源路径空、池里有正式文件、placement 还指向旧散乱路径 | 启动修复：placement=missing 且池内存在同指纹文件 → doctor 自动改指池路径（或进"待归纳重试"） |
| B/C 档 DB 提交前 | 源完好、池里只有 `.tmp` | 启动清理 `.tmp`，placement 原样 |
| B/C 档 DB 提交后、删源前 | 池有正式副本（已引用）、源多一份残留 | 无害；下轮扫描发现同指纹，提示可清理 |

**7.9.3 批量归纳**

| 环节 | 设计 |
|---|---|
| 入口 | "待归纳"视图：按位置/类型/体积筛选 → 全选或勾选 |
| 发起 | "归纳到池"：预估 N 件 / X GB / 三档各多少件 / 目标池空间是否够 |
| 执行 | 登记作业（core-job 可选接管）；进度 = 件数/字节/速率 |
| 取消 | 停在"文件安全点"：当前文件走完安全步骤，后续不再开始；**取消永不造成半删** |
| 部分失败 | 单文件失败不中断批次；结束出报告：成功 N / 失败 M / 原因分组 + 重试失败项 |
| 同指纹去重 | 目标池已存在该内容 → 跳过拷贝，直接切 placement |
| 空间预检 | 批次开始前核算"待拷字节 − 去重命中"，不足则**开工前拒绝**并列出缺口 |

**7.9.4 跨池迁移与腾退**

- `pool.move {from_pool, to_pool?}`：复用三档机制；目标缺省自动选有空间的池。
- 腾退整池：迁到空 → `pool.remove`（**仅允许空池**，非空拒绝）。
- 空间不够：迁移前核算，缺口明确报错；不做"边删边腾"。

**7.9.5 池满水位**

| 水位 | 行为 |
|---|---|
| ≥90% 容量 | 池管理页黄色告警 + 归纳发起时提示"该池将满" |
| ≥95% | 红色告警；写入前逐件检查，装不下的进失败清单（原因=空间），批次继续 |
| 选池 | 在线池中选剩余空间最大者；单件 > 最大剩余 × 90% → 直接拒绝该件并给出口建议 |

处理出口（池管理页三按钮，**不自动执行**）：看重复（copy_count 优先）／迁出去（pool.move）／调容量提示值。与安全删除的保守原则一致：**不自动删、不自动驱逐。**

## 8. 三端运行形态

### 8.1 Windows

| 项目 | 方案 |
|---|---|
| 后台常驻 | 注册为 Windows 服务，开机自启 |
| 图形界面 | 独立窗口程序，连接本机 `127.0.0.1:7910` |
| 文件访问 | 直接读写文件系统，无限制 |
| 命令行 | `rmgr.exe`，连接服务或用 `--standalone` |

### 8.2 Linux

| 项目 | 方案 |
|---|---|
| 后台常驻 | systemd 用户级服务，进程崩溃自动重启 |
| 图形界面 | 同 Windows，Tauri 窗口 |
| 服务器场景 | 不装图形界面，纯命令行 + 浏览器访问 |
| 文件访问 | 直接读写文件系统 |

### 8.3 安卓（三端中限制最多的，需重点评审）

| 项目 | 方案 |
|---|---|
| 后台常驻 | **前台服务 + 常驻通知**。不这样做，系统会在几分钟到几十分钟内回收进程，导致同步中断 |
| 图形界面 | 手机程序内的网页视图，访问同一应用内部的 `127.0.0.1`（应用内回环，系统允许） |
| 文件访问 | **系统授权方式（SAF）**：用户通过系统文件选择器，逐个授权某个目录。程序只能访问被授权的目录，不能随意浏览整个存储 |
| 性能差异 | SAF 的遍历速度明显低于直接文件访问。因此安卓上的扫描默认**降低并发**，并优先复用已有的哈希缓存 |

> **给评审的提醒**：SAF 是安卓系统近十年的强制要求（应用不能随意读取整个存储卡）。这意味着安卓端的"扫描整个手机存储"只能覆盖用户手动授权过的目录。备选方案是"安卓端只做浏览与接收，不主动扫描"。此决策已确认采用 SAF 方案。

### 8.4 三端一致性是怎么保证的

界面壳、浏览器、命令行三种入口，**全部连接同一个本机回环服务、调用同一套接口**。因此不存在"某个功能只有 Windows 能做"的问题——任何一端能做的事，另外两端也能做。

## 9. 安全设计

| # | 措施 | 具体做法 |
|---|---|---|
| 1 | 本机接口隔离 | 接口只监听 `127.0.0.1`（本机内部地址），外部设备无法访问；启动时生成一次性会话口令写入本地文件（权限 0600，仅本人可读） |
| 2 | 设备身份与配对 | 每台设备一把 Ed25519 密钥；首次配对交换指纹；之后固定信任，证书被替换会拒绝连接 |
| 3 | 插件权限门禁 | 插件必须在清单里声明所需能力（读写文件、访问网络等）；运行时强制检查，未声明即拒绝 |
| 4 | 删除保护 | 见 §7.3 四道检查，写死不可配置绕过 |
| 5 | 离线数据保护 | 离线、冷备份副本永不作为删除候选；墓碑 30 天宽限期 |
| 6 | AI 边界 | AI 永不参与删除/去重/备份决策；隐私三档可按目录设置 |
| 7 | 网络暴露最小化 | 局域网监听只在用户显式开启时启动；冷备份位置的数据永不作为传输源 |

## 10. 性能预算（每个数字都写明前提）

| 场景 | 预算 | 前提条件 |
|---|---|---|
| 10 TB 全量扫描 | 约 28 小时 | 单块机械硬盘顺序读取 100 MB/s（此时瓶颈是硬盘，不是处理器） |
| 10 TB 增量重扫 | 分钟级 | 所有文件的路径/大小/修改时间未变，跳过读文件内容 |
| 哈希计算 | 单核心 1–3 GB/s | 数据已在内存或固态盘缓存中；实际项目中通常被硬盘速度卡住 |
| 局域网传输 | 约 110 MB/s | 千兆网线 + 千兆交换机 + 8 条并行连接（理论上限 125 MB/s） |
| 10 TB 全量传输 | 约 22 小时 | 由此推出：**按需同步与增量是必需品，不是可选优化** |
| 数据库批量写 | 每秒 10 万行以上 | 固态硬盘、每 1–2 万行一个事务、WAL 模式 |
| 100 万条放置记录 | 数据库文件约 1–2 GB | 含索引 |
| 扫描时内存占用 | < 300 MB | 不含浏览器；流式处理，不整树加载 |

| A12 | Q1–Q4 查询执行计划全部 `SEARCH USING INDEX`（无 SCAN）；`rmgr bench query` p95 达 02 §8.7 预算 | CI 查询回归 + bench 基线 |
| A13 | 内容压缩后 `stream.open` 可播放（逻辑流解压透明）；放置删除后同 URL 立即 403；重启后旧 token 全部失效 | 构造 zstd 池 + 删除放置 + 重启插件三连测 |

## 附录 A：决策记录

> 格式：背景 → 备选方案 → 最终决定 → 付出的代价 → 影响章节。

### A-1 插件加载方式（**已移交 ling 项目**）

- **背景**：原决策"进程内动态链接库"属于宿主职责，项目拆分后随宿主移交。
- **现状**：ling 采用**双轨加载**（Rust 插件进程内动态库 + 非 Rust 插件进程外侧车），完整决策见 `../../ling/docs/01-宿主设计.md` 附录 A-1。
- **对本项目的影响**：resources-manager 只写 Rust 轨道；安卓限制（不随意起新进程）由进程内轨道满足。
- **影响章节**：§3、§6.1

### A-2 界面方案：本机回环网页服务

- **背景**：三种入口（窗口、浏览器、命令行）需要保持功能一致。
- **备选**：(a) 界面壳插件在本机开一个只监听本机的网页服务；(b) 窗口程序自带一套接口，命令行另写一套。
- **决定**：采用 (a)。
- **代价**：必须有一个常驻后台进程；端口可能被占用。
- **理由**：(b) 会导致三套代码慢慢不一致；(a) 让三种入口天然等价，命令行在无界面服务器上也能用。
- **保险措施**：端口被占用时自动顺延；命令行提供 `--standalone` 参数不依赖常驻进程。
- **影响章节**：§5.1、§8.4

### A-3 去重粒度：文件级，分块去重以后再说

- **背景**：去重可以按"整个文件"比，也可以把文件切成小块比。
- **备选**：(a) 文件级；(b) 分块（内容定义分块）。
- **决定**：v1 采用 (a)，数据结构预留 (b) 的扩展位。
- **代价**：一个文件只要改动一点点（比如 50 GB 的虚拟机镜像改了 1%），就认不出其中 49.5 GB 的重复部分。
- **理由**：分块需要多读一遍盘、数据库要多存几亿行、恢复文件时要拼块，出错点多；对照片/视频/文档类数据，文件级收益已接近分块。
- **影响章节**：§7.2、§7.3、`02-数据字典` 的 content 表

### A-4 标签分域，而非简单并集

- **背景**：原设想"词条的标签 = 它所有版本标签的并集"，但这会让《深空旅人》同时带上 4K 和 1080p。
- **备选**：(a) 标签分域（题材贴词条、质量贴版本）；(b) 保留并集、界面自行处理歧义。
- **决定**：采用 (a)。
- **代价**：查询"4K"时必须落到版本层，不能只查词条层；实现略复杂。
- **理由**：(b) 会让所有查询方（包括以后的其他插件）各自处理歧义，错误会扩散。
- **影响章节**：§4.4、`02-数据字典` 的 tag 相关表

### A-5 语义层排进首批交付（M1/M2）

- **背景**：新提出的词条/版本/标签/关系属于语义层，需要决定排期。
- **备选**：(a) 词条/版本/标签进 M1、关系进 M2；(b) 单独排一期；(c) 只设计不实现。
- **决定**：采用 (a)。
- **代价**：M1 交付内容变多，工作量上升约三成。
- **理由**：分类整理本来就需要标签，语义层不是锦上添花而是主干；关系数据天然适合随记录同步一起做。
- **影响章节**：§12.1

### A-6 AI 采用"混合形态 + 分级确认"

- **背景**：AI 要做打标、建关系、刮削，需要决定数据往哪送、结果怎么落地。
- **备选**：纯本地 / 纯云端 / 混合；全部人工确认 / 全部自动 / 分级。
- **决定**：混合形态（默认本地做分类与关系，云端只做外部资料对齐）+ 分级确认（低风险可自动采纳但可一键撤销，高风险必须人工确认）。
- **代价**：本地模型需要用户自行安装；自动采纳的标签仍可能出错（靠撤销兜底）。
- **理由**：纯本地质量受限于本地模型；纯云端有隐私与费用问题；全部人工确认在 10 TB 量级不现实；全部自动会污染数据库并同步扩散。
- **影响章节**：§7.8

### A-7 首次交付范围：M1–M2（原 M0 已移交 ling）

- **背景**：需要决定第一次写代码写到什么程度。
- **备选**：M1 / M2 / M4。
- **决定**：本插件交付 M1–M2；原 M0（宿主与骨架）随项目拆分移交 ling，见 `../../ling/docs/07-路线图与验收.md`。
- **代价**：首次交付不含文件传输与备份。
- **理由**：M2 已覆盖用户最关心的核心需求（扫描、查重、多设备记录、离线保护），体量可控、好验收；M3/M4 协议先冻结，避免返工。
- **影响章节**：§12

### A-8 标签体系三层分离（属性 / 用户标签 / 派生）

- **背景**：用户可自由添加词条/标签/版本；需要考虑可扩展性、无歧义性、主观标签如何归类、文件属性可否作标签做索引。
- **备选**：(a) 三层分离（客观属性走结构化列+索引，主观标签分域且域可扩展，派生标签不落库）；(b) 属性也物化为标签行。
- **决定**：(a)。
- **代价**：界面筛选器要同时对接属性列和标签表两套底层；属性列清单需随迭代追加。
- **理由**：属性物化成标签会存储翻倍、写放大，且主客观混淆导致查询方无法区分"事实"与"观点"。SQLite 百万行级加索引无性能压力（索引细节另轮讨论）。
- **影响章节**：§4.4、`02` §3.4、§3.7

### A-9 词条包含关系用关系边（series / part_of / contains）

- **背景**：系列中包含多个作品，词条要表达可包含关系。
- **备选**：(a) Connection 关系边（类型 contains/part_of）；(b) entry.parent_id 树。
- **决定**：(a)——系列本身是词条（`kind=series`），包含用关系边表达；一作品可属多系列。
- **代价**：查"某系列下所有作品"需递归查询（SQLite 递归 CTE，层级 <5 性能无忧）。
- **理由**：关系表 M2 已有，复用零成本；树形单父限制无法表达联动/多合集归属。
- **影响章节**：§4.2、`02` §3.1（kind 加 series）、§3.11

### A-10 归纳 = 单一 catalog + 多受管存储池；散乱文件标记待归纳

- **背景**："归纳"定义为把文件收进一个或多个数据库以供快速使用（Windows 单分区空间不够）；散乱文件允许记录但标记、择机归纳。
- **备选**：(a) 单 catalog.db + 多受管存储池；(b) 真拆多个 catalog.db。
- **决定**：(a)——元数据保持单一 catalog；"多数据库"实现为"多存储池"（内容按 hash 入池、可压缩）；散乱文件 `placement.mode=scattered`，界面"待归纳"视图提示。
- **代价**：诚实边界——归纳不加快文件本体读写；多池调度（选池、跨池校验）增加少量复杂度。
- **理由**：去重、全局查询、记录同步全靠元数据，多 catalog 会让跨库去重和同步复杂度爆炸；catalog 只存元数据（GB 级）单库足够。
- **影响章节**：§4.6、`02` §2.4、§2.5

### A-11 记录同步 = 纯点对点，无云端中继

- **背景**："所有设备共同维护一张表、合并取最新、冲突人工审核"的框架确认；是否首版就带可选中继。
- **备选**：(a) 纯点对点；(b) 点对点 + 可选中继（自建 VPS）。
- **决定**：(a)——首版纯点对点，离线优先，两两合并收敛；以后若有真实需求再加中继。
- **代价**：两台长期互不见面的设备无法交换记录（各自与见过的设备收敛）。
- **理由**：中继扩大首版范围、引入托管信任问题；点对点已覆盖家庭/个人场景。冲突处理明确为：无交集自动合并，edit-edit / delete-edit 进人工审核队列（M2 交付冲突 UI，工作量增项）。
- **影响章节**：§7.5

### A-12 播放/运行能力 = 独立插件（流交付契约见 A-17 / 03 §2.6）

- **背景**：数据包含视频、音频、图片、应用（exe/apk）、游戏、PDF、文档等；未来"随时使用"。两方案：独立串流插件（文件/应用在插件中运行并发送画面）vs 在本插件内实现。
- **备选**：(a) 独立插件；(b) 本插件内置。
- **决定**：(a)——本插件只做数据面（目录/同步/备份），消费方是未来的播放/运行插件（工作区占位目录 `../player/`，本质是执行器，各能力为其中模块；目录名与接口暂定）；本插件提供流交付接口（契约见 03 §2.6 与附录 A-17），首版按预留落盘。
- **代价**：多插件协作的接口维护；首版不交付任何播放能力。
- **理由**：播放/模拟器/转码崩溃率极高需隔离；**运行 exe/apk = 执行任意代码**，绝不能与全盘读写的资源管理插件同进程（侧车 + 沙箱）；编解码与平台集成体量是无底洞；热更新节奏解耦。M1 即需落 `asset_type` 列（video/audio/image/app/game/doc/archive/other）+ 类型专属元数据扩展 JSON。
- **影响章节**：§4.2、`02` §2.3、`03`（§2.6 流交付契约，见 A-17）

### A-13 备份目标策略：3-2-1（M4 协议细化）

- **背景**：备份采用经典 3 份 2 介质 1 异地；离线目标问题同记录同步。
- **决定**：3 份 = 本体 + 备份池 A + 备份池 B；2 介质 = 本地盘 + 移动盘/NAS；1 异地 = 另一物理位置的池；异地池可选 AEAD 加密（密码丢失 = 备份不可用，明示）；离线目标作业排队、插上续传、`last_verified` 可视化。
- **代价**：M4 实现时需处理池调度与加密密钥管理。
- **理由**：内容寻址天然增量去重，3-2-1 落在"多池"模型上零新概念；与同步分界清晰（同步=知道有什么，备份=能拿回来）。
- **影响章节**：§7.7

### A-14 索引与查询性能策略（copy_count 物化 / FTS5 / 分页双轨）

- **背景**：词条/标签/放置/同步流水都会到百万行量级；索引列序、搜索、大偏移分页是性能关键路径。
- **决定**：(1) 索引列序通则——等值列在前、范围列居中、排序列殿后，单查询热索引 ≤6；贴附表补反向覆盖索引。(2) `content.copy_count` 冗余列物化，placement 变更同事务维护，`doctor` 全量重算 + 属性测试守护不变式（copy_count = 该内容 placement 数）；(3) 全文检索仅对词条/别名/版本小表建 FTS5 trigram，文件名搜索 v1 只走 LIKE 前缀；(4) 分页双轨——跳页 OFFSET 硬上限 10 万，无限滚动走 keyset；(5) 回归测试用 EXPLAIN 断言 Q1–Q4 禁 SCAN（只许 SEARCH USING INDEX）。
- **代价**：copy_count 有写放大（每 placement 变更一次 UPDATE）；trigram 索引体积偏大；EXPLAIN 断言增加维护成本。
- **理由**：物化换掉最热的 GROUP BY count 子查询（去重入口与池页高频）；trigram 对 CJK 子串友好且不引外部分词依赖；性能不可验收即等于不存在，断言进 CI 才不腐烂。
- **影响章节**：`02` §8 重写、`02` §2.3 content 表、`03` §7 性能测试、§12 验收

### A-15 归纳与池管理细则（三档迁移 / 删源铁律 / 池满水位）

- **背景**：归纳（散乱 → 受管池）是 A-10 的核心操作，涉及真实文件的搬动与删除，做错即丢数据。
- **决定**：迁移按成本自动分三档（同文件系统 rename / 同设备跨分区拷贝 / 跨设备传输），界面预告档位与代价；**删源铁律**——池内副本校验通过前源文件零删除，顺序铁律"文件先行→DB 提交→删源"，三种崩溃断点各有确定恢复路径；批量归纳作业化（安全点取消、部分失败报告、同指纹跳拷、空间预检开工前拒绝）；`pool.move` 跨池迁移复用三档，`pool.remove` 仅限空池；池满水位 90% 黄 / 95% 红 + 逐件拒装，处理出口三按钮（看重复/迁出/调提示值），**不自动删、不自动驱逐**。
- **代价**：三档判定与恢复路径是实现复杂度大头；删源前的双份占用窗口；跨设备归纳强依赖源端在线。
- **理由**：数据安全是本插件存在的理由，归纳环节的任何"自动省事"都可能造成不可逆损失；水位与安全删除同守保守原则。
- **影响章节**：§7.9（新增）、§4.6 指向、`03` §2.3（pool.move/remove）、错误码 F801–F804

### A-16 冲突审核队列（字段级 merge / resolve=新 op / 冲突表快照）

- **背景**：A-11 定了点对点同步，edit-edit 与 delete-edit 需人工裁决；裁决体验与收敛正确性是 M2 的信任基石。
- **决定**：merge 按**字段级**比对（title/sort_title/tags/关系/墓碑逐字段；`attrs_json` 整体比对作妥协）；只有同字段双方修改才构成冲突，其余自动各取所长；冲突双方值整份快照进 `sync_conflict` 表（离线可审可看）；**resolve = 生成更晚的新 op**，对端旧值永远打不过，队列不复活；UI 走克制路线——徽标 + 同步完成汇总行（"N 条自动合并 / M 条待决"）、双栏 diff 卡片、保留左/右/手动/恢复删除、可改主意（重新 resolve）、方向性批量需二次确认；无弹窗、不阻塞任何作业；CLI 提供 `rmgr sync conflicts / resolve`。
- **代价**：字段级 merge 代码量；快照表冗余存储；UI 是 M2 新增工作量（评审已记为增项）。
- **理由**：记录级合并会把"各改各的"误报成冲突；裁决产生新 op 是最简收敛证明；快照换离线可审与可回看。
- **影响章节**：§7.5、`02` §4.3（sync_conflict）、`02` op.kind、`03` 事件目录 + CLI + §7.2 测试剧本

### A-17 get_stream 流交付契约（逻辑流 / 回环端口例外 / token 机制）

- **背景**：A-12 预留了流接口；消费场景（播放 seek、图片整读、PDF 页读、运行 exe/apk、外部程序）需要一等契约。
- **决定**：(1) 交付的是**逻辑流**——resources-manager 读池、按需解压，压缩对消费者透明，不默认给物理路径；(2) 通道为本插件自开的**本机回环流端口**（03 §1 "不开服务器"规则的唯一例外，业务 API 仍 100% 走 core-ui 网关），字节不经 ling 方法路由（JSON 不适合大字节）；(3) `stream.open {placement_id}` 换取带 token 的 URL，HTTP Range 语义（206/HEAD/整流），token 128-bit、内存态（重启全失效）、绑单 placement、仅 127.0.0.1、idle 10 分钟活跃续期、放置离线/删除实时 403；(4) 补 `get_local_path`（仅运行场景，要求 online+plain，压缩给 F503），文档明示"路径收不回、token 收得回"；(5) 错误码 F501–F504；(6) M3 局域网传输**不走** get_stream（既有 /blob 配对鉴权协议）。
- **代价**：端口例外与动态端口管理；重启断流需消费者重开；get_local_path 的路径交付天然不可收回（沙箱责任在消费插件）。
- **理由**：ling 内核不为字节流扩机制（A-2 四服务刚锁定）；自开端口 + URL 自带端口，发现成本为零；token 可收回、最小授权，是默认交付；路径仅在"必须执行"场景不可替代。
- **影响章节**：`03` §1 例外说明、`03` §2.6（新增）、A-12 影响章节
