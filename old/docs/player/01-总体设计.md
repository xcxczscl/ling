## 1. 项目要解决的问题

### 1.1 一句话描述

把 resources-manager 登记的内容（视频、音频、图片、PDF、应用程序）**用起来**——本机播放、查看、运行，必要时把画面串流到局域网另一台设备。

### 1.2 用户故事（用贯穿示例描述）

| 编号 | 用户想做的事 |
|---|---|
| S1 | 我在台式机上用 player 打开《深空旅人》4K 版，画面出现在 4K 显示器上，比例正确，无裁切 |
| S2 | 这部电影是 HEVC 编码，客厅电视盒子不支持硬解；player 应该自动改用重编码推流，或者告诉我可以选 |
| S3 | 我在书房 PC 看到 32:15 暂停，走到客厅电视打开同一内容，应该从 32:15 继续 |
| S4 | 我在手机上想运行一个 Windows 的 exe（比如安装向导），实际跑在书房的 Windows 机器上，画面投到手机 |
| S5 | 我想浏览旅行照片、翻阅 PDF 说明书，不需要下载到手机 |
| S6 | UI 风格在台式机、笔记本、手机上要统一，不要东一块西一块 |
| S7 | 沙箱运行时，程序不能读我整个硬盘，player 退出时程序也要跟着停 |
| S8 | 将来如果要在 Android 上直接跑 Windows 程序（翻译层/虚拟机），架构上要留出位置 |

### 1.3 三条硬性要求（不可妥协）

| # | 要求 | 为什么 |
|---|---|---|
| H1 | **player 是纯消费方**，不改 resources-manager（除非发现运行 bug） | rm 已封档 M1–M6；player 只通过已冻结的流接口消费 |
| H2 | **单插件原则**：能属于 player 内部的能力，不拆到其他插件 | 避免碎片化；唯一例外见 §7.3 影响点 |
| H3 | **运行任意代码必须沙箱隔离** | 运行 exe/apk 风险高；崩溃/安全问题不能影响 rm 或 ling |

## 3. 技术选型

| 项目 | 最终选择 | 为什么选它 | 否掉了谁、为什么 |
|---|---|---|---|
| 核心语言 | **Rust** | 与 ling/rm 同栈；解码库绑定成熟；同一代码构建 Windows/Linux/Android | C++：绑定复杂；Go：解码生态弱 |
| 视频解码/渲染 | **libmpv**（首选）或 FFmpeg + wgpu | libmpv（LGPL，动态链接合规）封装了 seek/字幕/音画同步；FFmpeg + wgpu 更可控但工作量大 | libVLC：同样 LGPL，否因 API 粒度粗、嵌入窗口集成文档少；GStreamer：Rust 绑定不成熟 |
| 控制界面 | **TypeScript + React + Vite**（与 rm 共用技术栈） | 与 rm 页面风格统一；走 core-ui 回环；虚拟列表等方案成熟 | 纯原生 UI：三端各写一套；Electron：体积大 |
| 视频渲染窗口 | **libmpv 嵌入原生窗口**（desktop）/ **libmpv + JNI Surface**（Android） | libmpv 有成熟的 wid 嵌入与 Android NDK 集成示例；wgpu 自渲染留作 libmpv 不可用时的退路 | wgpu 全自研：音画同步/字幕渲染工作量巨大；纯网页 `<video>`：4K/HDR 弱 |
| 流接收 | **HTTP Range 客户端**（复用 rm 流契约） | 不自造轮子；token 可收回 | 自定义 UDP：重复造轮子 |
| 串流发送 | **模式 A：player 本地代理转发**（见 §5.3.1）；**模式 B：FFmpeg 编码 + HTTP 分块推流** | A 需绕过 rm 流的 127.0.0.1 限制；B 成熟方案多 | 自定义 UDP：生态差、接收器难做 |
| 沙箱 | **独立进程 + OS 级隔离**（Linux: seccomp/namespace；Windows: Job Object；Android: 应用沙箱） | 不引入虚拟机依赖；性能损耗小 | Docker：太重；gVisor：安卓不可用 |
| 跨设备发现 | **复用 rm 的 peer 表**（只读）+ player 自建轻量心跳 | 不改 rm；不重复造配对机制 | mDNS/Bonjour：额外依赖；自建配对：重复造轮子 |
| 会话同步 | **player 自建对等协议**，经 **player 自开的局域网 HTTP 端口**（与 rm 流端口类似，默认 7914，占用顺延） | 不改 rm；player 自治；不经 ling 事件总线（事件是本机广播，出不了网） | 扩展 rm op 流水：违背「rm 冻结」 |
| 媒体元数据 | **rm 扩展 JSON 提供静态信息**（编码/分辨率等，扫描时探测写入）+ **player 运行时探测补充**（音轨/字幕轨/时长） | rm 扫描时已算哈希，顺带探测容器信息成本低；player 只做运行时补充 | 全靠 player 探测：每次打开都重扫一遍头部；全靠 rm：字幕轨等运行时才知的信息无法预知 |

## 4. 架构：五区模型

player 内部按职责拆成五个区。数据流是单向的：**Source → Capability → Sink**；Session 和 Discovery 横切所有区。

```
                    ┌─────────────────────────────────────────┐
                    │              player 插件                 │
                    │                                         │
   rm 流接口 ──────►│  ① 传输区（Source）                     │
   stream.open      │     调 rm 要 URL → HTTP Range 拿字节    │
                    │              │                          │
                    │              ▼                          │
                    │  ② 功能区（Capability）                 │
                    │     音视频解码 · 图片渲染 · PDF · 运行  │
                    │              │                          │
                    │              ▼                          │
                    │  ③ 输出区（Sink）                       │
                    │     本机屏幕/声卡 · 网络推流 · 电视协议 │
                    │                                         │
                    │  ④ 会话区（Session） ← 横切             │
                    │     进度/音量/字幕 → 跨设备接力         │
                    │                                         │
                    │  ⑤ 发现区（Discovery） ← 横切           │
                    │     本机输出设备 · 局域网接收器         │
                    └─────────────────────────────────────────┘
```

### 4.1 ① 传输区（Source）

**职责**：向 resources-manager 要字节。

| 项 | 说明 |
|---|---|
| 接口 | 调 rm 的 `stream.open {placement_id}` → 拿到 `{url, content_len, seekable}` |
| 字节获取 | 对 `url` 发 HTTP GET/HEAD，seek 时带 `Range: bytes=a-b` |
| 生命周期 | token 空闲 10 分钟过期；player 需在过期前续期或重开 |
| 错误处理 | rm 返回 F501（数据不可用）/ F502（token 无效）→ 向 UI 报错，不重试 |

**边界**：传输区**不读文件系统**。它只认 rm 给的 URL；rm 池内压缩、放置状态变化对它透明。

**举例**：《深空旅人》4K 版 40 GB，placement_id=`10241`。Source 调 `stream.open {placement_id: "10241"}`，得到 `http://127.0.0.1:7913/s/st_7c3f…/token…`。解码器 seek 到 32:15（约 12 GB 偏移）时，发 `Range: bytes=12884901888-`，rm 返回 206 Partial Content。

### 4.2 ② 功能区（Capability）

**职责**：把字节变成画面帧 / 声音样本 / 运行中的进程。

每个能力是独立模块，通过统一的 `Capability` trait 接口注册到 player：

| 能力 | 输入 | 输出 | 首版里程碑 |
|---|---|---|---|
| 音视频解码 | 流 URL + 媒体信息 | 视频帧 + 音频样本 + 时钟 | P0 |
| 图片渲染 | 流 URL | 位图（RGBA） | P1 |
| PDF 渲染 | 流 URL + 页码 | 位图（RGBA） | P1 |
| 进程运行 | 本地路径（`get_local_path`） | 进程句柄 + 窗口句柄 + 退出码 | P5 |

**分流规则**：按 rm 的 `asset_type` 字段路由：

```
asset_type=video/audio → 音视频解码
asset_type=image       → 图片渲染
asset_type=doc         → PDF 渲染（首版只支持 PDF）
asset_type=app/game    → 进程运行
asset_type=other       → 不支持，UI 提示
```

**扩展位**：未来加「翻译层运行」「虚拟机运行」时，新增 Capability 实现，不改现有架构。

### 4.3 ③ 输出区（Sink）

**职责**：把 Capability 的输出送到目的地。

| Sink 类型 | 说明 | 首版里程碑 |
|---|---|---|
| 本机 Sink | 直接显示到屏幕 + 输出到声卡 | P0 |
| 网络 Sink（字节转发） | 模式 A：player 本地代理，从 rm 流读字节转给对端（见 §5.3.1） | P3 |
| 网络 Sink（重编码） | 模式 B：解码→重编码→HTTP 分块推流给对端 | P4 |
| 网络 Sink（帧流） | 模式 C：解码帧 JPEG 压缩后推流 | P4 |
| 电视协议 Sink | Chromecast / AirPlay / Miracast 等系统级投屏 | P4 留接口，不实现 |

**Sink 选择逻辑**（自动优先，手动可覆盖）：

```
if 目标 == 本机:
    return 本机 Sink
else if 目标支持当前编码格式（HEVC/H.264/…）:
    return 网络 Sink（模式 A）  // 字节代理转发，效率最高
else if 带宽足够 且 目标能解 H.264:
    return 网络 Sink（模式 B）  // 重编码到兼容格式
else if 用户要求最低延迟（文档/远程桌面场景）:
    return 网络 Sink（模式 C）  // 帧流
else:
    return 网络 Sink（模式 B）  // 默认退到重编码
```

用户在 UI 里可以强制选 A/B/C/D 中的任意一个（手动覆盖自动结果）。模式 D（屏幕镜像）仅在用户显式选择或电视协议 Sink 可用时启用，不参与自动路由（捕获屏幕需要系统级权限，默认不给）。

### 4.4 ④ 会话区（Session）

**职责**：记录「当前播到哪了」，支撑跨设备接力。

| 会话字段 | 说明 | 举例 |
|---|---|---|
| `content_id` | rm 的内容指纹（blake3） | `blake3:9f3c…` |
| `position_sec` | 播放进度（秒） | `1935.2`（32:15.2） |
| `volume` | 音量（0.0–1.0） | `0.8` |
| `subtitle_track` | 字幕轨索引（-1=无） | `0`（第一条字幕轨） |
| `playback_rate` | 播放速度 | `1.0`（正常速度） |
| `updated_at` | 最后更新时间 | Unix 秒 |
| `device_id` | 最后更新的设备 | `dv_desktop` |

**存储**：player 自己的 SQLite 表（不进 rm 的 catalog）。

**同步**：player 自建对等协议，读 rm 的 peer 表发现对端，定期（或事件驱动）同步会话。**不改 rm**。

**接力流程**：

```
1. 用户在台式机播放《深空旅人》，会话表记录 position_sec=1935.2
2. 用户在客厅电视打开同内容
3. player 查本地会话表 → 找到 position_sec=1935.2
4. player 从 1935.2 秒开始播放
```

**优先级**：P6（本地持久化）→ P7（跨设备接力）。

### 4.5 ⑤ 发现区（Discovery）

**职责**：回答「本机能干什么」「对端有谁」。

| 发现类型 | 说明 | 数据来源 |
|---|---|---|
| 本机解码器 | 支持哪些编码格式（HEVC/H.264/VP9/…） | 运行时探测（libmpv/FFmpeg 能力查询） |
| 本机输出设备 | 显示器列表、声卡列表、蓝牙设备 | 操作系统 API |
| 局域网接收器 | 哪些设备能接收串流 | 读 rm 的 peer 表 + player 心跳协议 |

**不做的事**：不扫描局域网（那不是发现，是入侵）；只发现**已配对/已知**的设备。

## 5. 详细设计（各区展开）

### 5.1 Source 与 rm 的交互

**已冻结契约**（rm 03 §2.6）：

```jsonc
// 请求
{ "placement_id": "10241", "purpose": "play" }

// 响应
{
  "stream_id": "st_7c3f…",
  "url": "http://127.0.0.1:7913/s/st_7c3f…/<token>",
  "content_len": 42949672960,
  "seekable": true,
  "idle_ttl_sec": 600
}
```

**player 的责任**：

1. 调 `stream.open` 拿 URL；
2. 对 URL 发 HTTP 请求（Range 语义）；
3. token 过期或 403 时，重新调 `stream.open`；
4. 播放结束或关闭时，不主动调 `stream.close`（rm 侧 idle 10 分钟自动过期）。

**边界情况**：

| 情况 | 处理 |
|---|---|
| rm 返回 F501（数据不可用） | 向 UI 报错「内容当前不可用（离线/冷备份）」 |
| rm 返回 F503（压缩内容不支持路径） | 只影响「运行」场景；播放场景用流不受影响 |
| URL 返回 403（token 过期） | 重新调 `stream.open`，解码器 seek 到原偏移继续 |
| URL 返回 403（放置离线/删除） | 向 UI 报错，停止播放 |

### 5.2 Capability 与 rm 的交互（运行场景）

「运行 exe/apk」需要真实路径（`get_local_path`），不是流 URL。

**已冻结契约**（rm 03 §2.6.4）：

```jsonc
// 请求
{ "placement_id": "20480" }

// 响应（成功）
{ "path": "/data/media/apps/setup.exe" }

// 响应（失败）
// F501 数据当前不可用（离线/冷/丢失）
// F503 当前形态不支持路径交付（内容已压缩）
```

**player 的责任**：

1. 调 `get_local_path` 拿路径；
2. 启动独立子进程（沙箱内），传入该路径；
3. 监控进程生命周期（退出、崩溃）；
4. player 退出时，杀掉所有子进程。

**边界**：拿到路径 = 拿到无期限读权；沙箱与生命周期责任在 player（rm 无法收回）。

### 5.3 串流四模式详解

| 模式 | 流的是什么 | 适用场景 | 延迟 | 带宽 |
|---|---|---|---|---|
| **A 字节转发** | 原文件字节（经 player 本地代理），对端自己解码 | 对端支持当前编码格式 | 低 | 低（原文件大小） |
| **B 重编码** | 本机解码→重编码（如 H.264）→ HTTP 分块推流 | 对端不支持当前编码，但能解 H.264 | 中 | 中（重编码后大小） |
| **C 帧流** | 解码帧轻量压缩（JPEG）→ HTTP 分块推流 | 对端解码能力弱，或需要最低延迟 | 最低 | 高 |
| **D 屏幕镜像** | 捕获本机屏幕+硬件编码 | 系统级投屏（AirPlay/Miracast）；仅手动触发 | 低 | 高 |

#### 5.3.1 模式 A 的本地代理机制（关键设计）

**问题**：rm 的流 URL 绑定 `127.0.0.1`（rm 03 §2.6.3），对端设备无法直接访问发送端的 `127.0.0.1:7913`。**不能把 rm 的 URL 直接转给对端。**

**解决**：player 在发送端自开一个**局域网可达的代理端口**（默认 7914，占用顺延）：

```
对端接收器 ──HTTP──► player 代理端口 7914 ──HTTP──► rm 流端口 7913（127.0.0.1）
                       （转发 Range 请求）            （token 校验）
```

1. 发送端 player 调 rm `stream.open` 拿到 `127.0.0.1` URL；
2. 发送端 player 在 `0.0.0.0:7914` 起代理，收到对端请求后，向 rm URL 转发（保留 Range 头）；
3. 对端接收器从 `http://<发送端IP>:7914/s/<stream_id>` 拉流；
4. 代理转发完成后，对端拿到的字节与直接读 rm 流完全一致。

**代理端口鉴权**：与 rm 流 token 同机制——代理 URL 中拼 128-bit 随机 token，内存态，player 重启失效；token 由发送端 player 在投屏请求中带给接收器。

**为什么不让 rm 直接监听局域网**：rm 已封档，不改；且 rm 流端口设计为本机限定是安全决策（A-17）。

**模式 B/C 同理**：player 解码/重编码后，向自己的 `7914` 端口推流（或对端直接从 7914 拉分块流），接收器无需访问 rm。

#### 5.3.2 自动选择逻辑（伪代码）

```rust
fn auto_select_mode(target: &Receiver, content: &MediaInfo, bandwidth: &BandwidthInfo) -> Mode {
    if target.supports_codec(&content.codec) {
        Mode::A  // 字节代理转发，效率最高
    } else if target.supports_codec(Codec::H264) && bandwidth.estimated_mbps >= 20.0 {
        Mode::B  // 重编码到 H.264
    } else {
        Mode::C  // 帧流，牺牲画质保兼容
    }
}

// UI 永远可以手动覆盖：
fn user_override(mode: Mode) {
    // 用户在下拉菜单选了 Mode::B，忽略 auto_select 结果
}
// 模式 D 不参与自动路由，仅手动或电视协议 Sink 可用时启用
```

**带宽估算**（BandwidthEstimate）：P3 首版用**固定估值**（默认 100 Mbps 局域网），P4 起可选 ping 对端估算 RTT。不做主动带宽探测（避免惊群）。

**举例**：

| 场景 | 自动选择 | 理由 |
|---|---|---|
| HEVC 电影 → 支持 HEVC 的电视 | A | 经代理转发字节，电视自己解码 |
| HEVC 电影 → 只支持 H.264 的电视盒子 | B | 重编码到 H.264 |
| Windows 程序画面 → 手机 | B | 程序画面必须先渲染再编码 |
| 看文档 → 旧平板 | C | 帧流延迟最低，文档不需要高画质 |

### 5.4 接收器（Receiver）设计

**两套构建，同一代码库**：

| 构建目标 | 包含的区 | 体积（估） | 适用设备 |
|---|---|---|---|
| **完整 player** | Source + Capability + Sink + Session + Discovery | ~50 MB | PC、手机 |
| **lite 接收器** | Sink + 解码器 + Discovery（被动） | ~15 MB | 电视盒子、树莓派 |

### 5.5 画面比例处理（P0 核心）

**硬性规则**（用户 A3 拍板）：

| 规则 | 说明 | 举例 |
|---|---|---|
| 不拉伸 | 保持原始宽高比，禁止非等比缩放 | 21:9 电影不能拉成 16:9 |
| 不裁切 | 禁止裁掉画面内容 | 不能为了填满屏幕裁掉上下黑边里的字幕 |
| 允许单边黑边 | pillarbox 或 letterbox | 宽银幕电影在普通屏上左右留黑边 |
| **禁止四边黑边** | 上下左右同时留黑边 = 错误 | 说明缩放逻辑有问题 |

**正确做法**（等比缩放到最大内接矩形）：

```
输入：内容宽 content_w、内容高 content_h、屏幕宽 screen_w、屏幕高 screen_h

step 1: scale = min(screen_w / content_w, screen_h / content_h)
step 2: 显示宽 = content_w × scale，显示高 = content_h × scale
step 3: 水平居中、垂直居中；余量即黑边（仅一侧有余量，另一侧为 0）

断言（禁止四边黑边）：
  assert!(
      (screen_w - 显示宽 == 0) || (screen_h - 显示高 == 0),
      "缩放结果四边都有黑边，scale 计算错误"
  );
```

**举例**（21:9 电影在 4K 16:9 屏）：

| 量 | 值 |
|---|---|
| 内容 | 1920 × 823（约 21:9） |
| 屏幕 | 3840 × 2160（16:9） |
| scale = min(3840/1920, 2160/823) | min(2.0, 2.62) = **2.0** |
| 显示尺寸 | 3840 × 1646 |
| 余量 | 水平 0，垂直 514 → 上下黑边（letterbox） |
| 黑边类型 | **仅上下**，无左右黑边 → 合规 |

**反例**（错误的「同时限制宽和高」逻辑）：若先按宽缩放到 3840×1646，再按高缩放到某个更小尺寸，就会四边都留黑边 → 违规。正确做法是**一次取 min，永不二次缩放**。

**实现位置**：libmpv 自带 `keepaspect` 选项（默认开启）；若用 FFmpeg + wgpu 自渲染，需自己实现上述 scale 逻辑并加断言。

### 5.6 远程执行（P7）

**流程**：

```
1. 用户在手机上点「运行 setup.exe」
2. 手机 player 查 Discovery → 发现书房 Windows 机器支持「运行」
3. 手机 player 调书房 Windows player 的远程接口：
   a. 书房 player 调 rm 的 get_local_path 拿 exe 路径
   b. 书房 player 沙箱启动进程
   c. 书房 player 把进程画面编码（模式 B）
4. 画面串流回手机，手机显示
5. 手机上的按键/触摸输入回传给书房 player，转发给进程
```

**前提**：书房 Windows 机器常开、player 在运行、已与手机配对（rm peer 表有记录）。

**沙箱边界**：远程执行时，exe 跑在**书房机器的沙箱里**，不是手机的沙箱。手机只是显示器 + 输入设备。

**P7 实装备注（附录 B #69–#76）**：控制面落在 `control.rs` 自建 HTTP 平面——bind `0.0.0.0`，端口候选 **7917**（忙退 7918/7919/7920，全忙平面关闭并降级，**不报错阻塞插件**）；非阻塞 accept + 50ms 轮询 + `AtomicBool` 停机 + 每连接独立线程（读写 5s 超时），`ControlHandle`（`shutdown` join ≤~100ms，Drop 兜底）随 `PlayerState.control` 持有，`deactivate()`/`on_deactivate` 双入口 teardown（关平面 → flush → 拆会话 → 杀非 background，幂等）。**发现对端** = 读 rm `sync.status` 的 peer 表（只读）：`peer` 入参含 `:` → 直给 `host:port`（剥 http(s)://、尾 `/`）；不含 `:` → 按 device_id 查 peer 表取 host 拼 **7917**；缺省入参 = 单配对推导（0 对端 → **P303**、多对端未指定 → **P100**——P201 保留给 cast 对端不可达）。发起侧方法面 `player.remote.{caps,run,status,stop,input,log}` 经 `remote_request`（10s 超时；传输失败/对端报文畸形 → **P303**；对端 `{error:{code,message}}` 原码透传为 `CallError`）。`remote.run` 走接收侧 `run::run` **全链 P5 沙箱**（resolve_target 仅 app/game，其余 P103；video content 在**接收侧**产生 P103 后原码回传发起侧——§9「画面回传」在 headless 验收环境下**降级为日志尾**：`remote.log {run_id, stream}` 返回 stdout/stderr 沙箱文件 tail 8KB，`{data, bytes}`；逐帧画面回传/§6.3 Sink 写帧面/`rtt_ms` 因无逐帧消费者继续延后，#51/#52 立场不变）。**验收**：`p7_acceptance` e1–e3 绿（先 boot 接收侧占 7917、单向配对、字节相同 movie 同 content_id、直连 HTTP 断言、`sync_applied/ignored` 精确计数）。

### 5.7 UI 设计（混合方案）

| 层 | 技术 | 职责 |
|---|---|---|
| **控制面** | TypeScript + React + Vite，走 core-ui 回环网页 | 播放列表、进度条、音量、字幕选择、输出设备选择、模式选择 |
| **视频渲染层** | libmpv 嵌入原生窗口 | 实际解码 + 渲染画面到窗口 |

**为什么混合**：

- 纯网页：`<video>` 标签性能受限（4K/HDR 场景弱）；
- 纯原生：三端各写一套 UI，风格难统一；
- 混合：控制面一套代码三端复用（风格天然统一），视频层用 libmpv 保证性能。

**窗口集成**：

| 平台 | 视频窗口 | 控制面 |
|---|---|---|
| Windows/Linux | libmpv 嵌入 player 自建的原生窗口（独立于 ling 进程的辅助进程或 wid 嵌入）；控制面在浏览器/Tauri 壳 | 浏览器标签访问 core-ui；或 Tauri 壳（归 ling apps/，player 只提供页面） |
| Android | libmpv 使用 `ANativeWindow`（由壳层 Activity 提供 SurfaceView） | 同一 WebView（壳层提供） |

**Android 注意**：纯 Rust cdylib 插件无法直接创建 Java Activity/View。Android 上的视频窗口与 WebView 由 **ling 安卓壳**（`ling/apps/`，归宿主）创建并通过 JNI/NDK 把 Surface 句柄交给 player 插件。player 插件只提供「给定 Surface 播放」的能力，不自己起 Activity。**这是 player 与壳层的边界，已在 §7.2 登记。**

### 5.8 沙箱设计（P5）

**默认全隔离**：

| 隔离项 | 默认 | 说明 |
|---|---|---|
| 文件系统 | 只能访问沙箱目录 | 独立目录（如 `~/.player/sandbox/<run_id>/`） |
| 网络 | 禁止 | 运行的程序不能联网 |
| 进程生命周期 | player 退出即杀 | 所有子进程在 player 退出时被 kill |
| 系统 API | 限制 | 不给提权、不给访问系统注册表（Windows） |

**权限清单式授权**（用户显式勾选）：

| 权限 | 授权后效果 |
|---|---|
| 允许访问指定目录 | 沙箱可读写该目录（如游戏存档目录） |
| 允许联网 | 沙箱可以发起网络连接 |
| 允许后台运行 | player 退出后进程继续（不推荐） |

**沙箱实现**：

| 平台 | 技术 |
|---|---|
| Linux | **Landlock（文件系统）+ seccomp（网络/危险 API）+ prctl(NO_NEW_PRIVS) + setsid 杀组 + setrlimit**；namespace/cgroups 不用（容器与普通权限环境不可依赖，权限清单语义已由前四者覆盖）→ 隔离面如实上报（附录 B #57/#58） |
| Windows | Job Object + AppContainer（未落，环境无 Windows） |
| Android | 应用沙箱（本来就隔离） |

**落地要点（P5 实装，附录 B #57–#62）**：

- **pre_exec 顺序**（fork 后、exec 前）：`setsid`（独立会话/进程组 = 「退出即杀」承载）→ `prctl(NO_NEW_PRIVS)` → `landlock_restrict_self` → `prctl(PR_SET_SECCOMP=22, MODE_FILTER)` → `setrlimit`（`CORE=0` 不留内存快照、`NOFILE` 限句柄）；任一步失败 → spawn 冒泡 **P301**。
- **fs 面**：父进程构建 Landlock 规则集（沙箱目录 RW + `sandbox_opts.allow_dirs` 逐项规范化校验，系统根等 13 项拒绝清单 → **P302**）；非目录对象仅 `EXECUTE|WRITE_FILE|READ_FILE` 三权限合法（逐位探针实证掩码 `0x7`，否则 `landlock_add_rule` EINVAL）；隔离不可用 → `isolation.fs="degraded"` 如实降级，其他失败 → **P301**。
- **network 面**：seccomp BPF 按架构拦网络与 io_uring 调用（x86_64 `41/42/43/53/288/425–427`；aarch64 `198/203/199/202/242/425–427`），动作 `ERRNO|EPERM`（程序优雅失败不被杀）；非目标架构不装过滤器 → `network="degraded"`；`allow_network=true` → 不装（`network="granted"`）。
- **环境**：`env_clear` 后仅注入 PATH / HOME(沙箱) / TMPDIR(沙箱内 tmp) / LANG=C；CWD=沙箱；stdout/stderr 由父进程开好句柄落在沙箱 `stdout.log`/`stderr.log`（继承句柄绕开路径再校验）。
- **生命周期**：监控线程 100ms `try_wait`（reap + 状态翻转 + 广播 `player.run.exited`，信号杀 → `128+sig`，wait 失败 → `-1`）；停用/停机 `kill_non_background` 杀 `state=running && !allow_background` 全部进程组（deactivate 与 on_deactivate 双入口幂等）；显式 `player.run.stop` 杀任意组（含 background），未知 run_id → **P100**。

### 5.9 会话同步协议（P7，player 自建）

**不改 rm**；player 自建轻量对等协议。

**发现对端**：读 rm 的 peer 表（只读），拿到已配对设备列表 + 局域网地址。

**同步触发**：

| 触发 | 说明 |
|---|---|
| 播放进度变化 | 每 5 秒或每 1% 进度（取先到者） |
| 暂停/停止 | 立即同步 |
| 音量/字幕变化 | 立即同步 |

**同步报文**（player 自定义，经 ling 事件总线或直接 HTTP）：

```jsonc
{
  "type": "session.sync",
  "content_id": "blake3:9f3c…",
  "position_sec": 1935.2,
  "volume": 0.8,
  "subtitle_track": 0,
  "updated_at": 1729180800,
  "device_id": "dv_desktop"
}
```

**冲突处理**：后更新的覆盖先更新的（`updated_at` 更大者胜）。

**P7 实装备注（附录 B #71/#74）**：同步通道 = `POST /sync`（控制平面端点，报文严格照上表、无 aid/rate）；`SyncPayload::parse` 校验 type/content_id/device_id 非空、`position_sec` 有限 ≥0、`volume` 有限 0..=1、`subtitle_track` i32、`updated_at>0`，不过 → **P100**。落库 `Store::apply_sync`（`stamp` 以本机 now + 本机 `device_id` 盖戳）LWW 规则：**自报先查**（`device_id` == 本机 → `{applied:false, reason:"self"}` 不写，防自发回环）→ `p.updated_at < existing.updated_at` → `{applied:false, reason:"stale"}` → **同秒并列后到者胜**（严格小于才拒，防同秒先到吞掉后到的暂停报文，按到达序收敛）；合入行保留本机 `audio_track`/`playback_rate`（控制面未落，#63 口径），新行预置 0/1.0。触发清单照上表：pause/resume/set_volume/set_subtitle/stop、Paused/Finished 事件、停机 flush → **立即**；seek/Progress 心跳 → **节流**（5s 或 1% duration 先到者，`sync_marks` 按 content_id 记上次推送点，真变化才盖戳）；Failed 不推；store 缺失/查看器/无 content_id 跳过；**目标为空不推**（无自发外发）。推送在后台线程（2s 超时静默、不阻塞控制方法），`player.control.status` 报 `{enabled, port, device_id, sync_applied, sync_ignored, sync_targets}`（计数与目标可观测，e3 精确断言）。

`MediaInfo` 是 player 内部的核心结构，供 Capability probe 与 Sink prepare 使用。信息来源分两层：

**数据目录**（player 自己的，不进 rm catalog）：

**会话表 schema**（P6 落地；player.db，WAL 模式）：

```sql
CREATE TABLE session (
    content_id     TEXT PRIMARY KEY,   -- rm 内容指纹 blake3:…
    position_sec   REAL NOT NULL DEFAULT 0.0,
    volume         REAL NOT NULL DEFAULT 1.0,
    subtitle_track INTEGER NOT NULL DEFAULT -1,  -- -1=无字幕
    audio_track    INTEGER NOT NULL DEFAULT 0,
    playback_rate  REAL NOT NULL DEFAULT 1.0,
    updated_at     INTEGER NOT NULL,   -- Unix 秒
    device_id      TEXT NOT NULL       -- 最后更新设备
);

CREATE TABLE setting (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

**P6 实装备注（附录 B #63–#66）**：`store.rs` 开库即设 WAL + `busy_timeout 5s` + `CREATE TABLE IF NOT EXISTS` 照表建；`player_data_root` 落地为 `data_root(ctx)`——`PLAYER_DATA_DIR` 非空覆盖、否则内核插件数据目录（#19），**player.db 与 `sandbox/` 同源**（UI 资源页仍走 `ctx.data_dir()`）。开库失败 → `PlayerState.store=None` 纯内存降级（持久化是增强面，不阻塞装载/播放）；单次读写失败 best-effort 忽略。写穿钩子：pause/resume/seek/set_volume/set_subtitle 成功后 upsert、`player.stop` **先落库再停**（停后 time-pos 抓不到）、Progress（≈1s 心跳）/Paused 事件、Finished 事件与停机 flush（**Finished 相自动归 0**，播完下次从头看）；**Failed 不落**（瞬时错误会把 time-pos 打成 0，写下去反抹有效进度）。停机 flush 在 `deactivate()` 与 `on_deactivate` 双入口、均先于 `sessions.clear()`。播放侧：`backend.load_at` 等 `duration>0`（解复用就绪，≤3s）再绝对定位（seek/`sid` 回放都要求文件已装载）→ 音量/字幕尽力回放（内容变更轨对不上不阻断）→ 读回失败忽略。查看器会话与无 `content_id` 会话不入表；`audio_track`/`playback_rate` 两列按 schema 预置默认值但控制面未落（不回放，留后续）；`device_id` 为 setting 表 get-or-create（getrandom 8 字节 hex，跨重开稳定，P7 对等同步沿用）。

### 5.13 lite 接收器投屏请求协议

**触发**：发送端 player 选定目标后，向对端 lite 接收器的 player 发起投屏。

**通道**：接收器在局域网监听 HTTP 端口（默认 7915，与发送端代理 7914 区分）。发现靠：lite 启动后向已知 peer 广播心跳（复用 rm peer 地址列表，只读）。

**投屏请求**（发送端 → 接收器，POST `http://<receiver>:7915/cast`）：

```jsonc
{
  "mode": "A",                    // A/B/C
  "stream_url": "http://<sender_ip>:7914/s/<stream_id>/<token>",
  "media_info": {
    "codec": "hevc",
    "width": 3840,
    "height": 2160,
    "duration_sec": 7200.0
  },
  "autoplay": true
}
```

**接收器响应**：

```jsonc
{ "accepted": true, "reason": null }
// 或
{ "accepted": false, "reason": "unsupported_codec" }
```

**生命周期**：接收器播完或发送端断开 → 接收器回到待机，广播心跳继续。

### 5.14 音画同步与字幕渲染

**音画同步**：libmpv 内部已处理（音频时钟为主，视频对齐）；FFmpeg + wgpu 自渲染方案需自己实现（P0 用 libmpv 时不做额外工作）。

**字幕渲染**：

| 字幕类型 | P1 处理 | 说明 |
|---|---|---|
| 内嵌字幕（ass/ssa/srt in mkv） | libmpv 自动渲染 | `subtitle_track` 选择哪条 |
| 外挂字幕（同名 .srt/.ass） | P1 不做 | 需要文件路径关联，流交付场景拿不到外挂文件；留 P2+ |
| 图形字幕（PGS/VobSub） | libmpv 自动渲染 | 位图字幕，libmpv 原生支持 |

### 5.15 远程执行输入事件协议（P7）

手机/平板作为远程显示器时，触摸/按键需回传给远程进程。

**通道**：复用投屏连接（接收器 → 发送器反向 HTTP 或 WebSocket）。

**输入事件**：

```jsonc
{ "type": "input.touch",  "x": 0.5, "y": 0.3, "action": "down|move|up" }  // 归一化坐标 0.0–1.0
{ "type": "input.key",    "key": "Enter", "action": "down|up" }
{ "type": "input.text",   "text": "hello" }
{ "type": "input.back",   "action": "press" }  // Android 返回键
```

**安全**：输入事件仅在远程执行会话（`player.run` 发起的 cast）中启用；普通视频投屏不接受输入（防止对端被注入按键）。

**P7 实装备注（附录 B #72）**：**transport = 沙箱 stdin JSONL**（四类事件统一序列化为单行 JSON + `\n` 写 `remote.run` 持有的 `ChildStdin`，`text` 也不裸写——事件行可留痕于管道，接收侧按行解析）；**门禁 = `remote.run` 命名空间**——`player.run`/`player.remote.input`/`POST /remote/run/{id}/input` 三口同规则：`run_id` 必须在运行表（`valid_run_id` 先验字符集 `[A-Za-z0-9_-]`，防路径穿越），视频会话 id（`ps_*`）不在表 → **P100**（本机与跨机同径拒绝）；事件形状逐字段校验（touch x/y 0..=1 + `action ∈ down|move|up`、key 非空 + `down|up`、text ≤4096 字节、back 仅 `press`、未知 type → **P100**），校验在**发起侧先过**再发包（坏事件不占网络）。`remote.run` 响应含 `sandbox_dir`，e2 直读其下 `input.log` 实证落盘。

## 7. 与其他项目的边界

### 7.1 与 resources-manager 的边界

| 项 | rm 的职责 | player 的职责 |
|---|---|---|
| 内容字节 | 读池、按需解压、返回流 URL | 对 URL 发 HTTP 请求 |
| 运行场景 | 返回本地路径（`get_local_path`） | 沙箱启动进程、监控生命周期 |
| 媒体元数据 | 提供 `asset_type`、扩展 JSON（分辨率/编码格式等） | 按 `asset_type` 分流到 Capability |
| 播放会话 | **不参与** | player 自建 Session 表 |

**不改 rm**（除非发现运行 bug）。

### 7.2 与 ling 的边界

| 项 | ling 的职责 | player 的职责 |
|---|---|---|
| 插件加载 | 加载 player 的 `.so`/`.dll` | 提供 Plugin trait 实现 |
| 方法路由 | 把 UI 的调用转给 player | 实现 `player.*` 方法（§5.12） |
| 事件广播 | 广播 player 发出的事件 | 发出 `player.*` 事件（§5.12） |
| 网页服务 | core-ui 在 127.0.0.1:7910 起服务 | player 的控制面页面通过 `ui.contribute` 注册 |
| Android 壳 | 创建 Activity/WebView/Surface，把 Surface 句柄经 JNI 交给 player | 接收 Surface，用 libmpv 播放；不自己起 Java UI |

**插件清单**（`plugins/player/plugin.toml`）：

```toml
[plugin]
id = "player"
version = "0.1.0"
api = "1"
name = "内容执行器"
description = "播放、查看、运行 resources-manager 登记的内容；支持串流到局域网设备"

[requires]
capabilities = ["network", "shell"]  # network：局域网串流/流 URL；shell：P1 起子进程调 pdftoppm/pdfinfo/ffprobe（附录 B #28/#31）；ling 能力词表 fs/network/ui/shell，原稿 "net" 系笔误（附录 B #21）
plugins = ["resources-manager"] # 依赖 rm 的流接口
```

### 7.3 ⚠️ 影响点：会话接力放哪（唯一例外）

**问题**：跨设备播放进度接力需要同步会话状态。两个方案：

| 方案 | 做法 | 对单插件原则的影响 |
|---|---|---|
| **甲：player 自建对等同步**（本文采纳） | player 自己维护 Session 表 + 复用 rm 的 peer 列表（只读），自建轻量同步协议 | **不碰 rm**；player 代码多一套同步，但完全自治 |
| **乙：扩展 rm 的记录同步** | 在 rm 的 op 流水里带 player 会话数据 | **要改 rm**（加表/op kind），违背「rm 冻结」 |

**决定**：走 **甲**。理由：rm 已封档；player 单插件自治；会话数据量小（每次几百字节），自建同步成本可控。

**代价**：player 需要自己实现对等发现 + 同步协议（约几百行代码）；不能复用 rm 的 op 流水合并逻辑。

**如果未来发现会话同步需求复杂到需要 rm 级别的冲突合并**（比如多设备同时改进度、离线队列），再重新评估方案乙。届时需用户决断。

## 8. 错误码（P 族）

player 使用独立错误码族 **P**（rm 用 F 族，ling 用 E 族，不冲突）。经 ling 方法路由返回时，放在 `error.code` 字段。

| 码 | 含义 | 典型场景 |
|---|---|---|
| `P100` | 通用参数错误 | 缺 session_id/position_sec/volume、play 缺两种入参、未知页面（附录 B #22） |
| `P101` | 内容不可用 | rm 返回 F501（离线/冷/丢失） |
| `P102` | 流 token 失效 | rm 流 URL 403，重开失败 |
| `P103` | 不支持的资产类型 | `asset_type=other` 或无法识别 |
| `P104` | 无可用解码器 | 本机 libmpv/FFmpeg 无法解该编码 |
| `P105` | 无可用输出设备 | 声卡/显示器未就绪 |
| `P201` | 串流目标不可达 | 对端 lite 接收器无响应 |
| `P202` | 串流被拒绝 | 接收器返回 `unsupported_codec` |
| `P203` | 代理端口分配失败 | 7914 被占用且顺延失败 |
| `P301` | 沙箱启动失败 | OS 隔离 API 调用失败 |
| `P302` | 沙箱权限不足 | 试图访问未授权路径 |
| `P303` | 远程执行不可用 | 对端未运行/未配对/无运行能力 |
| `P401` | 会话不存在 | `session_id` 无效 |
| `P402` | 会话同步失败 | 对端无响应 |

**规约**：P100 = 通用参数；P1xx = 内容/解码；P2xx = 串流；P3xx = 运行/沙箱；P4xx = 会话。与 rm 的 F 族、ling 的 E 族互不重叠。

## 10. 风险与对策

| # | 风险 | 影响 | 对策 |
