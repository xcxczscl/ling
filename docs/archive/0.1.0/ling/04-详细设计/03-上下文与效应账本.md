## 2. 上下文对象

### 2.1 谁创建、什么时候注入

`Context` 由内核在激活前创建，经函数表的 `context_alloc` 交给插件。插件拿到的是一块不透明句柄（`void* ctx`），不能自己构造，也不能从别处获取（`LING-REQ-028`）。

| 时机 | 动作 |
|---|---|
| 激活前 | 内核创建 `Context`，绑定 `plugin_id` 与 `generation`，账本新开一代 |
| 激活中 | 插件经函数表调用，内核按 `ctx` 找到对应插件 |
| 停用后 | `Context` 标记失效；此后再用同一 `ctx` 调用，一律返回 `E_PLUGIN_MISSING` |

「停用后失效」这一条必须有：插件的异步回调会在停用后才触发，若 `ctx` 仍然有效，它会往已作废的账本里写条目。

### 2.2 完整方法表

| 方法 | 返回 | 是否产生账本条目 |
|---|---|---|
| `register_method(name, fn, undo_fn, requires_mask)` | 错误码 | 是，`MethodRegistered` |
| `unregister_method(name)` | 错误码 | 是，`MethodUnregistered`（撤销上面那条） |
| `subscribe(pattern, fn, undo_fn, out_sub_id)` | 错误码 | 是，`EventSubscribed` |
| `unsubscribe(sub_id)` | 错误码 | 是，`EventUnsubscribed` |
| `call(method, args, out)` | 错误码 | 否 |
| `emit(topic, payload)` | 错误码 | 否 |
| `write_config(key, value)` | 错误码 | 是，`ConfigWritten` |
| `data_dir()` | 路径字符串 | 否 |
| `ledger()` | 只读视图 | 否 |
| `last_error(out_message, out_detail)` | 错误码 | 否 |

「是否产生账本条目」这一列是本文的核心约束：**只有改共享状态的方法才入账，调用与广播不入账**（`LING-REQ-031`、`LING-REQ-020`）。

### 2.3 生命周期

```
装载 → 创建 Context（绑定 generation）→ activate → 正常使用
  → 停用：撤销账本 → Context 标记失效 → 释放
  → 卸载：停用流程 + 移出四张表 + 删文件
  → 重载：旧 Context 失效，新 Context 绑定新 generation
```

`generation` 随每次装载递增，与 `04/01` §3.4 装载表的 `generation` 是同一个值。旧 `ctx` 的 `generation` 与当前不符时直接拒绝，这是「旧回调拦截」在 `Context` 一侧的实现。

### 2.4 不能做什么

| 不能 | 后果 |
|---|---|
| 自己 new 一个 `Context` | 结构体不对外公开，构造入口不存在 |
| 拿别人的 `ctx` 调方法 | 内核按 `ctx` 反查插件编号，越权返回 `E_CAPABILITY_DENIED` |
| 绕过 `Context` 直接改全局状态 | 宿主检测不到，也不负责还原（`LING-REQ-038`） |
| 在 `ctx` 失效后继续调用 | 返回 `E_PLUGIN_MISSING`，不写账本 |
| 通过 `ledger()` 改账本 | 返回的是只读视图 |

## 3. 账本结构

### 3.1 条目字段

```c
typedef enum {
    LING_EFFECT_METHOD_REGISTERED = 1,
    LING_EFFECT_EVENT_SUBSCRIBED  = 2,
    LING_EFFECT_CONFIG_WRITTEN    = 3,
    LING_EFFECT_SIDECAR_STARTED   = 4,
    LING_EFFECT_DEACTIVATE_HOOK   = 5
} ling_effect_kind;

typedef struct {
    uint64_t        seq;        /* 段内递增，从 1 开始，严格不重复 */
    uint32_t        kind;       /* 五类之一 */
    const char*     desc;       /* 人可读，含被改对象的名字 */
    ling_undo_fn_t  undo;       /* 插件侧撤销函数，宿主代撤时为空 */
    void*           undo_ctx;   /* 撤销时原样传回 */
    uint32_t        undo_mode;  /* 0 = 调插件函数，1 = 宿主代撤 */
} ling_ledger_entry;
```

`desc` 是给人看的，例如「注册方法 demo-a.scan.start」。`undo_mode` 区分两种撤销方式：进程内插件自己交出撤销函数；侧车交不出可调用指针，由宿主代撤（`LING-REQ-064`）。

### 3.2 五类效应

| 类别 | 什么时候产生 | 撤销动作 | 谁执行 |
|---|---|---|---|
| `MethodRegistered` | `register_method` 成功 | 从路由表删该条目 | 宿主 |
| `EventSubscribed` | `subscribe` 成功 | 从订阅表删该 `sub_id` | 宿主 |
| `ConfigWritten` | `write_config` 成功 | 把该键恢复为写入前的值；原本不存在则删除该键 | 宿主调 core-settings |
| `SidecarStarted` | 侧车进程起来 | 结束进程 | 宿主 |
| `DeactivateHook` | 插件登记停用回调 | 调该回调 | 插件 |

前四类都是「宿主能自己完成的撤销」，第五类是唯一需要插件参与的一类。

**线程与文件句柄不单独入账**（`LING-REQ-031`）：插件开的线程随进程或库的生命周期结束，文件句柄随进程关闭，宿主无法代为管理。插件若在 `on_deactivate` 里不等待线程结束就返回，属于插件自己的缺陷，宿主不做兜底。

### 3.3 按激活代分段

同一个插件会被反复停用与激活（调和的正常结果、重载的必然结果）。如果账本只增不减，反复激活几十次就会撞上 10000 条上限，而每一代的效应其实都已经撤销完了。

所以账本按**激活代分段**：

```cpp
struct LedgerSegment {
    uint64_t generation;              // 与装载表一致
    std::array<LedgerEntry, 10000> entries;
    std::atomic<uint32_t> count{0};   // 已写入条目数
};

struct PluginLedger {
    LedgerSegment current;            // 只有当前代有效
    std::shared_mutex swap_mu;        // 仅在换段时短暂独占
};
```

规则：

| 规则 | 内容 |
|---|---|
| 新一代开始时 | 新建 `LedgerSegment`，`generation` 取当前装载代号，`count` 归零 |
| 撤销时 | 只撤当前段，倒序 |
| 撤销完成后 | 整段丢弃，不保留历史 |
| `seq` 范围 | 段内 1 至 10000，换段后重新从 1 开始 |
| 历史可查性 | 不保留。要查历史看内核日志，不看账本 |

段内 `seq` 从 1 重新开始是允许的：撤销只在段内进行，跨段比较序号没有意义。

### 3.4 容量与越界

每段上限 10000 条（`LING-REQ-100`）。第 10001 次登记效应时：

1. 返回 `E_LEDGER_FULL`。
2. 本次修改**不生效**——先检查容量再改表，不允许「改了但没记账」。
3. 已登记的前 10000 条不受影响，仍可正常撤销。

顺序很重要：若先改表再记账，容量满时表已改、账没记，这个效应就永远撤不掉。

### 3.5 单写多读

账本不进快照（理由见 `04/01` §4.2）。替代结构就是 §3.3 的「定长数组 + 原子计数」：

| 操作 | 谁做 | 怎么保证安全 |
|---|---|---|
| 追加 | 只有内核线程 | 先检查 `count < 10000`，写 `entries[count]`，再 `count.fetch_add(1, release)` |
| 读 | 任意线程（`ledger()`） | 先 `count.load(acquire)`，只读前 `count` 条 |
| 换段 | 内核线程 | 拿 `swap_mu` 独占，换完后释放 |

读者看到的是「某个时刻之前的全部条目」，不会看到写了一半的条目——因为 `count` 的递增在写入之后，且用 release 语义。

这套结构没有锁竞争：写只在注册、订阅、停用这些非热路径上发生，读是调试用途。

## 4. 撤销

### 4.1 倒序规则

严格按 `seq` 递减执行（`LING-REQ-012`、`LING-REQ-032`）。

倒序不是随意选择：效应之间有依赖。插件先注册方法、再在方法里引用某个配置键，正序撤销会先删配置、再删方法，中间窗口里方法指向一个不存在的键。倒序撤销保证「后建立的先拆除」。

### 4.2 单条失败

某条撤销返回非 0 时（`LING-REQ-013`）：

1. 记 `E_UNDO_FAILED` 与条目 `seq`、`desc` 到内核日志（error 级）。
2. **继续执行剩余条目**，不中断。
3. 全部执行完后，若有失败项，最终结果返回 `E_UNINSTALL_INCOMPLETE`，`detail` 列出未撤销条目。

不中断的理由：一条撤销失败通常是插件实现问题，让其余效应卡在那里，会让「停用」变成一个既没停干净也没恢复原状的状态。

### 4.3 重复撤销的行为

| 情形 | 行为 |
|---|---|
| 同一条目被撤两次 | 第二次检查 `seq` 是否已标记完成，已完成则直接返回成功 |
| 撤销期间插件再次登记效应 | 拒绝，返回 `E_PLUGIN_MISSING`（`ctx` 已失效） |
| 段已丢弃后再撤 | 返回成功（无条目可撤），不报错 |

### 4.4 停用、卸载、重载的差别

| 操作 | 撤销 | 段 | 文件 | 四张表 |
|---|---|---|---|---|
| 停用 | 全部撤销 | 丢弃 | 保留 | 保留条目，状态改 `Deactivated` |
| 卸载 | 全部撤销 | 丢弃 | 删工件保留 `data/` | 移出全部条目 |
| 重载 | 先按停用撤销，新版本装载后再建新段 | 旧段丢弃，新段新建 | 换产物 | 先移出旧条目再加新条目 |

三者共用同一套撤销实现，差别只在撤销之后做什么。

## 5. 撤销函数的三种表达

| 轨道 / 情形 | 撤销函数怎么来 | `undo_mode` |
|---|---|---|
| 进程内插件，注册方法或订阅 | 插件在调用时一并交出 `undo_fn` | 0，宿主回调插件 |
| 进程内插件，停用回调 | 插件登记一个函数，宿主在停用时调 | 0 |
| 侧车插件，注册方法或订阅 | 交不出函数指针，只做语义声明 | 1，宿主代撤 |
| 侧车插件，配置写入 | 由 core-settings 记录旧值 | 1 |
| 宿主自己启动侧车 | 结束进程 | 1 |

「交不出函数指针」是 `LING-REQ-064` 的直接后果：侧车是另一个进程，函数指针跨不过去。所以侧车的账本条目只记「这个侧车声明了 X」，撤销动作由宿主执行——从路由表删条目、从订阅表删条目，与进程内插件的效果完全相同。

对插件作者的影响：写侧车插件时，撤销不需要自己实现，只要在 `register_method` 里如实声明；但**清理自己的数据与线程仍要在 `deactivated` 消息里做**，宿主代撤的只是表里的登记。

## 6. 数据目录与配置写入

### 6.1 `data_dir()`

返回 `plugins/<编号>/data/` 的绝对路径，UTF-8 编码。

内核保证该目录在 `activate` 之前已存在（`LING-REQ-035`），插件拿到路径后直接写文件，不需要自己建目录。

跨调用状态必须放在这里，内存中不保留（`LING-REQ-057`）：

| 状态类型 | 该放哪 | 理由 |
|---|---|---|
| 索引、缓存、游标 | `data/` 下的文件 | 重载后仍在，且与版本无关 |
| 连接、句柄、线程 | 内存，随激活创建随停用释放 | 跨不过进程边界，也不该序列化 |
| 配置项 | 经 `write_config` 交给 core-settings | 需要被记账，才能撤销 |

### 6.2 配置写入

```c
int32_t (*write_config)(void* ctx, const char* key,
                        const uint8_t* value, size_t len);
```

语义：

1. 键名必须以 `<插件编号>.` 开头，越权返回 `E_NAMESPACE_VIOLATION`。
2. 写入前先读旧值（原本不存在时记为空），把旧值记进账本条目，再写新值。
3. 实际存储由 core-settings 完成；core-settings 被卸载时返回 `E_PLUGIN_MISSING`。
4. 值是不透明字节串，core-settings 不解析内容。

第 2 步是「可撤销」的关键：账本条目里存旧值，撤销时写回旧值；原本不存在则删键。

### 6.3 配置与数据的分界

| | `write_config` | `data/` 下的文件 |
|---|---|---|
| 谁管 | core-settings，可查询、可导出 | 插件自己 |
| 是否入账 | 是 | 否 |
| 卸载时 | 随账本撤销，键被还原 | 默认保留 |
| 跨插件可见 | 按编号前缀隔离 | 完全私有 |

判据：需要被别的组件看到、或需要可撤销的，走配置；只属于自己的中间状态，走文件。

## 7. 隔离与越权

### 7.1 账本互不可见

`ledger()` 只返回调用者自己的段，接口上没有任何「按编号查他人账本」的入口（`LING-REQ-034`）。要查别的插件的账，只能看内核日志。

### 7.2 命名空间隔离

| 对象 | 约束 | 违反 |
|---|---|---|
| 方法名 | 必以 `<编号>.` 开头 | `E_NAMESPACE_VIOLATION` |
| 事件主题 | 同上，`kernel.` 保留 | `E_NAMESPACE_VIOLATION` |
| 配置键 | 必以 `<编号>.` 开头 | `E_NAMESPACE_VIOLATION` |
| 注销他人方法 | 归属校验 | `E_CAPABILITY_DENIED` |

### 7.3 检测不到的情形

以下修改宿主**不检测、不还原，也不承诺**（`LING-REQ-038`）：

- 插件直接写文件、删文件
- 插件直接改全局变量或环境变量
- 插件自己起子进程
- 插件在 `data/` 之外建目录

`doctor` 只报告可观测的迹象：越权注册尝试的记录、卸载后仍未撤销的条目、命名空间违规。报告里不写「已还原手工文件操作」这类内容，因为做不到。

这条要写清楚，是因为它决定了项目边界：ling 不是沙箱，插件是可信代码。**若插件不遵守约定，宿主的能力仅限于「拒绝、记录、报告」，不包括「阻止与修复」。**

## 8. 时序

### 8.1 注册并登记

```
插件 → register_method(name, fn, undo_fn, requires)
  → 内核校验（见 04/01 §5.1 六步）
  → 检查账本容量：count == 10000 → 返回 E_LEDGER_FULL，表不变
  → 复制快照 → 插入 RouteEntry → 校验不变式 → 换快照
  → 追加账本条目（seq = ++count，kind = MethodRegistered，undo = undo_fn）
  → 返回 0
注意顺序：先改表后记账，但容量检查在两者之前
```

### 8.2 订阅并登记

```
插件 → subscribe(pattern, fn, undo_fn, out_sub_id)
  → 校验（见 04/01 §6.1 五步）
  → 容量检查
  → 分配 sub_id → 改订阅表 → 换快照
  → 追加账本条目（kind = EventSubscribed，desc 含 pattern 与 sub_id）
  → 返回 0 与 sub_id
```

### 8.3 停用撤销

```
内核线程 → 取当前段，count = n
  → for seq from n down to 1:
       按 undo_mode 分派：调插件函数 / 宿主代撤
       失败 → 记 E_UNDO_FAILED，继续
  → 全部完成后丢弃整段，count 归零（新建空段）
  → Context 标记失效
  → 有失败项则返回 E_UNINSTALL_INCOMPLETE，detail 列出失败条目
```

### 8.4 撤销失败

```
撤销 seq = 7 返回非 0
  → 内核日志 error：E_UNDO_FAILED、seq=7、desc="注册方法 demo-a.x"、插件编号
  → 继续 seq = 6
  → 最后汇总：{ "incomplete": true, "failed": [7] }
  → 状态仍改 Deactivated（或 Uninstalled）
```

「状态仍然改」是刻意的：如果因为一条撤销失败就把插件留在 `Deactivating`，它会一直占着依赖图里的位置，导致下游永远无法激活。宁可带着一条未撤干净的方法继续，也不要卡住整个系统。

## 9. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | `E_LEDGER_FULL` 已登记进 `04/02` §5.2 的错误码表 | 归入 `E_LEDGER_` 族，含义「账本条目达到上限」 | §3.4、04/02 §5.2 |
| 2 | 调用超时后处理函数仍会写效应，这些效应算不算 | 算。撤销按账本执行，不区分「调用是否超时」；超时只影响调用方拿到的结果 | §4.1 |
| 3 | 五类效应是否够用，将来若要加「注册定时任务」这类 | 加类别属于契约变更，要升 `api` 主版本。现在不加 | §3.2 |
| 4 | `DeactivateHook` 的撤销动作是「调该回调」，而回调本身会失败 | 按 §4.2 处理：记 `E_UNDO_FAILED` 并继续 | §3.2、§4.2 |
