# core-plugin-manager 01 需求与用例

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/builtin-plugins/core-plugin-manager/00-总览与边界.md`

本文回答：什么情况下会用到它、每种要成什么样、怎么判断做对了。

---

## 1. 需求从哪来

| 条目 | 本插件承担的部分 |
|---|---|
| `LING-REQ-078` | 内置插件不获得特权，方法经同一条路由与同一套门禁 |
| `LING-REQ-081` | 内置插件可卸载，卸掉后宿主仍能启动 |
| `LING-REQ-039` 至 `LING-REQ-051` | 依赖图与调和的存在，是「依赖树」「预演」两项的前提 |
| `LING-REQ-010` | 「只剩 `data/` 的目录算未安装」，孤儿扫描的判定依据 |

## 2. 场景

### 2.1 看某个插件牵连了谁

使用者想卸 `demo-base`，但不确定有没有别的插件依赖它。

要成什么样：

- 给出两层：它依赖谁（上游）、谁依赖它（下游）。
- 下游按传递闭包列出，不只是直接依赖。
- 缺依赖的标出来，说明缺哪个。

### 2.2 找出白占空间的数据

删掉几个插件之后，`plugins/` 下留着几个只有 `data/` 的目录。

要成什么样：

- 列出每个这样的目录：插件名、占用字节数。
- 给出合计。
- **只列不删**，删不删由使用者决定。

### 2.3 一次停掉一组插件

想临时关掉一组插件，一个个敲 `disable` 太慢，顺序错了还会因为下游先停而报错。

要成什么样：

- 给一组插件名，按依赖的拓扑序执行：先停下游，再停上游。
- 中途某一步失败，停在失败处并报告「已停哪几个、哪个失败、剩下的没动」。
- 不自动回滚已停的——回滚会引入更复杂的失败模式，报告清楚比假装干净更有用。

### 2.4 动手前先算一遍

不确定一次操作会影响几个人。

要成什么样：

- 给「我想停 `demo-base`」，返回「会连带停用 `demo-a`、`demo-b`，共 3 个」。
- **不执行任何动作**，只返回预演结果。

## 3. 用例与验收标准

编号 `CM-` 开头。

| 编号 | 场景 | 期望 | 怎么判 |
|---|---|---|---|
| CM-01 | 扫描孤儿目录 | 列出只有 `data/` 的目录 | 与手工 `ls plugins/` 的结论一致 |
| CM-02 | 没有孤儿 | 返回空列表与总数 0 | `orphans` 为空数组 |
| CM-03 | 占用统计 | 每个已安装插件一个条目，单位字节 | 与资源管理器看到的量级一致 |
| CM-04 | 依赖树（M3） | 上游与下游分开列出 | 下游含传递依赖 |
| CM-05 | 依赖树里的缺失项 | 标出「缺哪个」 | 条目里带 `missing` |
| CM-06 | 预演（M3） | 返回会激活、会停用的插件名 | 执行前后状态不变 |
| CM-07 | 批量停用（M3） | 按拓扑序执行 | 日志里的顺序是先下游后上游 |
| CM-08 | 批量中途失败（M3） | 报告停在哪一步、哪些已停 | 未执行的插件状态不变 |
| CM-09 | 卸掉本插件 | 宿主仍能启动，装卸命令仍可用 | 与 `LING-REQ-081` 同判据 |
| CM-10 | 孤儿目录里有大文件 | 大小统计含子目录 | 递归累加，不漏子目录 |

`CM-04` 至 `CM-08` 在 M3 之前无法验证，验收时标「本期不适用」并写明理由（`docs/ling/11-MVP 范围.md` §3.2 的口径）。

## 4. 本期明确不做的

| 不做 | 什么时候做 | 为什么现在不做 |
|---|---|---|
| 删除孤儿数据 | 不做 | 数据是使用者的，删除必须由人手动执行 |
| 依赖树、预演、批量 | M3 | 依赖 MVP 不含的依赖解析，且插件调不到内核写方法 |
| 插件市场、在线安装 | 不做 | 项目非目标，见 `docs/ling/00-总览与术语.md` |
| 版本对比、降级 | M3 之后 | 需要热更新与版本管理，那是另一块 |
