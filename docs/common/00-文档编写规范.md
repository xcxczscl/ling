# 00 文档编写规范

> 状态：初定
> 最后更新：2026-10-27
> 适用对象：`docs/` 下全部文档，以及仓库根 `README.md`、`AGENTS.md`
> 地位：本文件是文档的母本，其他文档的写法、结构、评审流程都以它为准

---

## 1. 这份文档管什么

管三件事：

1. 文档放在哪、叫什么名字；
2. 一份文档该写成什么样才算合格；
3. 一份文档从起草到定稿要走哪些步骤。

不管代码怎么写、功能做什么。那些分别由各项目的需求、架构、设计文档管。

---

## 2. 目录约定

### 2.1 仓库根目录

| 目录 | 放什么 |
|---|---|
| `docs/` | 全部文档 |
| `main/` | ling 宿主程序的代码 |
| `plugins/` | 各插件的代码，一个插件一个子目录 |
| `other/` | 脚本、资源、工具这类内容 |
| `old/` | 旧版本内容，只作参考，暂不处理 |

注意：`docs/plugins/` 放插件**文档**，`plugins/` 放插件**代码**，两者不同层，不要混。

`old/` 是历史遗留目录，不属于上述四类，不再扩展，也不在其中新增内容。

### 2.2 `docs/` 内部

| 目录 | 放什么 | 谁能改 |
|---|---|---|
| `docs/common/` | 公共文档：编写规范、术语表、跨项目约定 | 随项目演进修改 |
| `docs/ling/` | ling 宿主的设计文档 | 随设计推进修改 |
| `docs/plugins/` | 各插件文档，按插件名再分子目录 | 随设计推进修改 |
| `docs/log/` | 开发日志、决策记录 | 只增不改 |
| `docs/archive/` | 归档快照 | 非特定情况不修改 |
| `docs/other/` | 不属于以上任何一类的内容 | 按需 |

### 2.3 简要版的位置

每个项目目录下建 `brief/` 子目录，放该项目的简要版文档：

```
docs/ling/01-需求规格.md          详细版
docs/ling/brief/01-需求规格.md    简要版
```

`docs/plugins/<插件名>/` 同样规则。

### 2.4 日志与归档

**日志（`docs/log/`）按事件记**：一件事一个文件，只在事情发生或决策时写，不按天流水账。

- 命名：三位序号 + 事件名，如 `001-建立文档体系.md`；序号全目录连续递增。
- 内容：发生了什么、为什么这么定、影响了哪些文件或文档。
- 只增不改：已写的日志不回头编辑；后续有变化就新写一篇并互相引用。

**归档（`docs/archive/`）按里程碑**：一个里程碑一个子目录，如 `docs/archive/M1-文档体系/`。

- 存入即冻结：归档目录内的文件不再修改，即使发现错误也只新写勘误，不改原件。
- 归档时机：一个里程碑的文档全部定稿后，把定稿版本复制进去。

## 3. 文件命名

| 规则 | 说明 |
|---|---|
| 格式 | 两位数字序号 + 短横线 + 中文名，如 `01-需求规格.md` |
| 序号 | 从 `00` 开始，按阅读顺序递增；`00` 固定为总览或索引 |
| 扩展名 | 统一 `.md` |
| 禁止 | 空格、英文缩写做文件名、文件名里带日期、含义笼统的名字（如 `其他.md`） |
| 例外 | `README.md` 不带序号 |
| 日志 | `docs/log/` 下用三位序号 + 事件名，如 `001-建立文档体系.md` |

序号只在同一个目录内唯一。`docs/ling/01` 和 `docs/plugins/player/01` 互不影响。

## 4. 两种粒度

每份正式文档都写两份：**详细版**和**简要版**。

### 4.1 详细版

回答"为什么"和"具体怎么做"。包含：背景、取舍理由、备选方案、示例、边界情况、风险。

### 4.2 简要版

回答"结论是什么"。放 `brief/` 子目录，文件名与详细版完全一致。

### 4.3 两版必须一致的三条

1. **章节结构一致**：标题、层级、顺序完全相同，简版不允许增加或删除章节，只能缩短内容。
2. **结论一致**：同一个问题在两版里给出同一个答案，不允许简版说得更宽松或更绝对。
3. **约束不删**：数字、阈值、接口名、验收标准、禁止项，简版必须原样保留。

简版删掉的是：背景铺陈、理由论证、备选方案对比、示例代码。**不删的是结论本身。**

### 4.4 怎么核对一致

把两版的各级标题抓出来逐条比对，数量、顺序、文字必须完全对应。不一致就是不合格。

### 4.5 单份文档的篇幅

- 详细版以 **500 行左右**为参考，上下浮动 50 行属正常范围。
- 超过 550 行时，优先考虑拆分成多份。
- 拆完会破坏论述连贯性的（如时序推演、机制推导），不强行拆，也没有硬上限。判断标准是拆分后读者是否需要来回翻页才能理解一件事：需要就说明拆错了。
- 简要版不设行数要求，但应当明显短于详细版；以表格为主的文档允许两版篇幅接近，因为压缩表格会丢信息。
- 例外：`05-构造与开发指南` 是一份连续的操作手册（结构、顺序、命令、规范相互引用），按章组织在一份文件内，不因篇幅拆子目录。

## 5. 每个项目必备的文档序列

按软件工程的路子走。下表的"必备"指该项目进入编码前必须定稿。

| 序号 | 文档 | 回答什么问题 | 必备 |
|---|---|---|---|
| 00 | 总览与术语 | 这是什么、边界在哪、名词怎么理解 | 是 |
| 01 | 需求规格 | 做什么、给谁做、什么算做到 | 是 |
| 02 | 技术选型 | 用什么语言、什么运行时、插件形态与边界技术、为什么这么选 | 是 |
| 03 | 架构设计 | 分成哪几块、各块怎么配合、为什么这么分 | 是 |
| 04 | 详细设计 | 每块的接口、数据、流程、出错怎么办 | 是 |
| 05 | 构造与开发指南 | 代码落在哪些目录与模块、关键类型与函数签名、按什么顺序写、每步怎么验证、怎么构建运行 | 是 |
| 06 | 安全设计 | 有哪些威胁、权限怎么管、密钥和数据怎么保护 | 是 |
| 07 | 测试与验收 | 测什么、怎么测、什么算通过 | 是 |
| 08 | 部署与运维 | 怎么发布、怎么升级、出问题怎么回滚 | 按需 |

这是最低要求，不是上限。项目需要更多（如性能设计、兼容性说明、迁移方案）时按序号顺延补充。

项目需要面向使用者的说明时，在序号末尾追加一份**用户手册**：回答怎么装、怎么用、出问题先看哪。用户手册与设计文档受众不同，允许写得比设计文档口语化，但命令与参数必须与实际一致。何时写由项目定，代码未跑通之前写出来的操作步骤会与实际不符，通常放到可运行版本之后。

### 5.1 允许拆分子目录

某一份文档内容过大时，可以把它拆成子目录，子目录内用两位序号重新编号：

```
docs/ling/04-详细设计/
    01-内核四服务.md
    02-插件装载与接口.md
```

- 子目录只允许出现在 `04-详细设计` 这类"内容天然可分块"的位置；需求、架构、测试不拆。
- 子目录内文件的命名规则与父级相同。
- 简要版在 `brief/` 下保持同样层级，如 `docs/ling/brief/04-详细设计/01-内核四服务.md`。

### 5.2 引用格式

跨文档引用一律写完整路径加章节号，**禁止只写节号**：

```
正确：见 docs/ling/04-详细设计/04-依赖解析与调和.md §2
错误：见 §2（读者不知道是哪个文件的 §2）
错误：见上文、见前述章节（同一份文件内改用"见本节"或"见 §3.1"）
```

引用 `old/` 下的历史文档同样写完整路径，如 `old/docs/ling/01-宿主设计.md`，不写"old 的 01"。理由是简称需要读者自己检索，路径可以直接打开。

### 5.3 关于 05 构造与开发指南的时序

构造手册写的是"代码长什么样、按什么顺序写"，因此它分两部分，时序不同：

| 部分 | 内容 | 何时写 |
|---|---|---|
| 结构部分 | 目录与模块划分、模块清单与依赖方向、开发顺序与每步验证方式 | 04 详细设计定稿后、动手写代码前写完 |
| 签名与命令部分 | 关键类型与函数签名、构建与运行命令、调试方法 | 编码过程中逐块补齐，跑通一条写一条 |

构建命令依赖具体语言和工具链，代码未定之前写不出可执行的命令。处理办法：

- **编码前**：命令部分给**示例**并明确标注"示例，非本项目实际命令"。
- **编码开始后**：技术栈确定、命令跑通后，把示例替换为真实命令，删掉"示例"标注。
- 不允许凭空编造看起来像真的命令，也不允许因为写不出命令就跳过这份文档。

示例（标明语言，仅供格式参考）：

```bash
# 示例：C++ 项目常见形态，非本项目命令
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

语言差距大，示例只示范"要写清哪几件事"：装什么、怎么编、产物在哪、怎么跑。真实命令待技术栈确定后再补。

## 6. 写作硬要求

### 6.1 可验证

每条需求有唯一编号，格式 `项目代号-REQ-三位数`，每条都能回答"怎么判断做到了"。

项目代号固定如下，不得随意更改：

| 代号 | 对应项目 |
|---|---|
| `LING` | ling 宿主程序（`main/`） |
| `RM` | 资源管理插件（`plugins/resources-manager/`） |
| `PLR` | 内容执行器插件（`plugins/player/`） |

示例：`LING-REQ-001`、`RM-REQ-014`、`PLR-REQ-003`。新增插件时先在术语表登记代号，再开始写需求。

### 6.2 无歧义

以下词禁止单独使用，必须换成可判断的具体表述：

> 等、等等、尽量、可能、大概、适当、必要时、原则上、快速、高效、友好、合理、优化、较快、足够、若干

替换办法：给数字、给条件、给范围。例如"快速响应"改为"本机操作在 200 毫秒内返回"。

### 6.3 无错误

文中的数字、路径、命令、接口名必须与实际一致。暂时无法核实的，标注 `【待验证】` 并说明验证方式，不允许含糊带过。

### 6.4 术语统一

术语分两级登记：

| 级别 | 放哪里 | 收什么 |
|---|---|---|
| 公共术语 | `docs/common/01-术语表.md` | 跨项目通用的词，如宿主、插件、能力、事件、侧车、上下文、热更新 |
| 项目专属术语 | 该项目 `00-总览与术语.md` | 只有这个项目才有的词，如 ling 的清单、效应账本、重载 |

- 同一个概念全项目只用一个词，首次出现时给一句话定义。
- 每个术语只在一处定义，其他地方引用该处，不重复解释。
- 代码、命令、文件名、报错原文照写，不改写不翻译。

### 6.5 单一事实来源

同一个事实只在一处详细写，其他地方引用，格式：`见 docs/ling/03-架构设计.md §3.2`。禁止在两处各写一遍，那是矛盾的来源。

### 6.6 不写空话

每个段落要能回答：谁做什么、在什么条件下、结果是什么。写不出这三点的话就删掉。

### 6.7 优先用表格

对比、清单、参数、状态取值用表格。用图的必须在图下方配文字说明，保证不看图也能读懂。

### 6.8 语言

中文书写。专业名词首次出现时用一句话解释，例如"同一操作重复执行结果不变"这类表述可以直接沿用。

## 7. 状态与版本

每份文档头部必须有元信息块：

```markdown
> 状态：草案 | 初定 | 评审中 | 已定稿
> 最后更新：YYYY-MM-DD
> 依据：上游文档路径
```

### 7.1 状态含义

| 状态 | 含义 | 可否据此编码 |
|---|---|---|
| 草案 | 正在起草，内容会有大改 | 否 |
| 初定 | 已自审并经过用户过目，无已知异议；可作为后续文档的基础，但**不承诺稳定**——发现必要功能缺失或上游结论变动时可直接改 | 否 |
| 评审中 | 正在按某轮意见修改，待用户再次确认 | 否 |
| 已定稿 | 用户明确确认通过 | 是 |

状态只能由用户确认后转为已定稿，AI 不得自行标注。

### 7.1.1 本项目的定稿时机

本项目采用**整体定稿**：全部设计文档写完、彼此对照无冲突后，才统一由用户确认转为「已定稿」。在此之前所有文档停留在「初定」。

理由是设计未走完时会暴露必要功能的缺失（例如运行时日志就是写到一半才发现漏了）。若逐份定稿，前面标了定稿的文档反而成为改动的阻力，最后不得不反复撤销定稿状态。

「初定」不等于可以随意改：改动仍要写变更记录，且要检查它对下游文档的影响。

### 7.2 变更记录

文档末尾附变更记录表：

| 日期 | 改了什么 | 为什么 |
|---|---|---|

已定稿文档再修改，必须新增一行记录，不得覆盖历史。

## 8. 写-审-问-改 循环

每份文档都走这个循环，一轮不通过就再来一轮。

### 8.1 步骤

1. **写**：按第 5 节对应类型和第 9 节清单起草，状态标"草案"。
2. **自审**：逐条对照第 9 节清单检查，逐项记录结论。
3. **提问题**：把需要用户拍板的点整理成编号列表，一条一问，每条附我的建议和理由。不允许把未决问题藏在正文里。
4. **改**：按用户答复修改，状态转"评审中"。
5. **复审**：重新过一遍清单，确认改动没有引入新问题。
6. **再问**：复审后仍有疑问的，继续提问。
7. 重复 4–6，直到清单全部通过且用户明确表示可以。
8. **初定**：用户过目、无已知异议，但项目整体文档未写完时，状态转"初定"，继续写下一份。
9. **定稿**：全部文档写完并互相对照无冲突后，用户确认，状态转"已定稿"，写变更记录。
10. **同步简版**：按第 4 节写简版，简版同样要过清单，状态与详细版一致。
11. **再审**：简版与详细版做一致性核对。

### 8.2 出口条件

以下三条同时满足才算这一份完成：

- 第 9 节清单全部通过，且有逐条记录；
- 用户明确说"可以""定稿"或同义表述；
- 简要版已完成，且结构与详细版逐条对应。

### 8.3 禁止的做法

- 未经用户确认自行标为已定稿；
- 带着未解决问题交付，只说"后续再补"；
- 用"已按要求完成"这类说法替代实际检查；
- 为了通过检查而删掉难写的需求，那是改需求不是改文档。

## 9. 审查清单

自审和复审都用这张表，逐条给出通过或不通过，不通过的要写出具体位置。

### A. 正确性

- [ ] 文中数字、阈值、版本号可核对到出处
- [ ] 路径、命令与实际仓库一致
- [ ] 接口名、字段名与设计中对齐
- [ ] 交叉引用（`见 xxx §y`）指向的章节真实存在

### B. 完整性

- [ ] 第 5 节要求的章节都在
- [ ] 每条需求都有验收标准
- [ ] 异常、边界、失败情况有交代
- [ ] 未决事项已列成问题清单，未混在正文中
- [ ] 非目标写明（不做什么同样重要）

### C. 一致性

- [ ] 术语与 `docs/common/01-术语表.md` 或本项目 `00-总览与术语.md` 一致
- [ ] 与其他文档不矛盾；有冲突的已指出并记录待裁决
- [ ] 与 `AGENTS.md` 不冲突
- [ ] 详细版与简要版结论一致

### D. 可验证性

- [ ] 需求有唯一编号
- [ ] 每条需求都能判断真伪
- [ ] 测试文档中的用例能追溯到需求编号

### E. 语言与结构

- [ ] 无第 6.2 节禁用词
- [ ] 标题层级连续，不跳级
- [ ] 序号连续，无跳号、无重号
- [ ] 无空话段落

## 10. 与其他文件的关系

| 文件 | 管什么 |
|---|---|
| `AGENTS.md` | 协作行为：怎么沟通、怎么改代码、Git 规则 |
| 本文件 | 文档本身怎么组织、怎么写、怎么评审 |
| `docs/common/01-术语表.md` | 全项目统一术语 |

三者冲突时，以用户当下的明确指令为准；其次以 `AGENTS.md` 为准；本文件与术语表冲突时，先改本文件再改术语表。
