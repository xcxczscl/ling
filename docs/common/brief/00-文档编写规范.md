# 00 文档编写规范

> 状态：已定稿
> 最后更新：2026-11-03
> 依据：用户对文档体系的明确要求；本文为母本，无上游文档

本文是 `docs/common/00-文档编写规范.md` 的简版：只留规则本身，理由与示例见详细版。

## 1. 这份文档管什么

管三件事：文档放在哪、叫什么名字；一份文档写成什么样算合格；从起草到定稿走哪些步骤。不管代码怎么写、功能做什么。

## 2. 目录约定

### 2.1 仓库根目录

| 目录 | 放什么 |
|---|---|
| `docs/` | 全部文档 |
| `main/` | ling 宿主程序代码 |
| `plugins/` | 各插件代码，一个插件一个子目录 |
| `tools/` | 校验、打包与辅助工具 |
| `archive/` | 正式版发行归档（7z），不进版本库 |
| `other/` | 本地杂项，不进版本库，不登记 |
| `old/` | 旧内容，只作参考，不进版本库，不再扩展 |

`docs/plugins/` 放插件文档，`plugins/` 放插件代码，两者不同层。

### 2.2 `docs/` 内部

| 目录 | 放什么 |
|---|---|
| `docs/common/` | 公共文档：编写规范、术语表、跨项目约定 |
| `docs/ling/` | ling 宿主设计文档 |
| `docs/plugins/` | 各插件文档，按插件名再分子目录 |
| `docs/ling/log/` | ling 开发日志与决策记录，只增不改 |
| `docs/ling/archive/` | 宿主与内置插件版本归档快照，存入后不修改 |
| `docs/plugins/<插件名>/{log,archive}/` | 该插件自己的日志与归档 |

### 2.3 简要版的位置

每个项目目录下建 `brief/`，简版文件名与详细版完全一致；子目录文档在 `brief/` 下保持同样层级。

### 2.4 日志与归档

- 日志按事件记：一件事一个文件，三位序号 + 事件名，内容写发生了什么、为什么这么定、影响了哪些文件；只增不改。
- 归档按版本：宿主、内置插件、其他插件各自独立归档；存入即冻结，发现错误只写勘误，不改原件。
- 发行归档：每个正式版（版本号不带 `-bN`）生成一个 7z 放仓库根 `archive/`，用 `python tools/release_archive.py` 生成。

## 3. 文件命名

| 规则 | 说明 |
|---|---|
| 格式 | 两位数字序号 + 短横线 + 中文名，如 `01-需求规格.md` |
| 序号 | 从 `00` 起按阅读顺序递增，`00` 固定为总览或索引；只在同一目录内唯一 |
| 扩展名 | 统一 `.md` |
| 禁止 | 空格、英文缩写做文件名、文件名带日期、含义笼统的名字 |
| 例外 | `README.md` 不带序号 |
| 日志 | 三位序号 + 事件名，如 `001-建立文档体系.md` |
| 一次性材料 | 里程碑代号 + 名称，如 `M0-提审包.md`，放项目目录根，不占序号，不写简版 |

## 4. 两种粒度

### 4.1 详细版

回答「为什么」和「具体怎么做」：背景、取舍理由、备选方案、示例、边界情况、风险。

### 4.2 简要版

回答「结论是什么」，放 `brief/` 子目录，文件名与详细版一致。H1 不加「（简要版）」后缀，正文首段说明它是简版。

### 4.3 两版必须一致的三条

1. 章节结构一致：标题、层级、顺序完全相同，简版只缩短内容，不增删章节。
2. 结论一致：同一问题两版给同一答案，不允许更宽松或更绝对。
3. 约束不删：数字、阈值、接口名、验收标准、禁止项原样保留。

### 4.4 怎么核对一致

抓出两版各级标题逐条比对，数量、顺序、文字必须完全对应。

### 4.5 单份文档的篇幅

详细版以 500 行左右为参考，超 550 行优先考虑拆分；拆开会破坏论述连贯性的不强行拆。简版应明显短于详细版；以表格为主的文档允许两版接近。`05-构造与开发指南` 按章组织在一份文件内，不拆子目录。

### 4.6 索引类文档不设简版

只有纯索引（只列「取值 + 唯一定义位置」，无论证、推演、取舍）不写简版，典型是 `docs/common/03-常用取值速查.md`。判据：删掉解释性段落后内容不减半，就是索引。表格多但有验收标准与依据的文档仍要两版。

## 5. 每个项目必备的文档序列

| 序号 | 文档 | 必备 |
|---|---|---|
| 00 | 总览与术语 | 是 |
| 01 | 需求规格 | 是 |
| 02 | 技术选型 | 是 |
| 03 | 架构设计 | 是 |
| 04 | 详细设计 | 是 |
| 05 | 构造与开发指南 | 是 |
| 06 | 安全设计 | 是 |
| 07 | 测试与验收 | 是 |
| 08 | 部署与运维 | 按需 |

这是最低要求，需要更多时按序号顺延。面向使用者的用户手册追加在序号末尾，写于可运行版本之后，命令与参数必须与实际一致。

### 5.1 允许拆分子目录

只在内容天然可分块的位置拆，如 `04-详细设计/`，子目录内两位序号重新编号；需求、架构、测试不拆。简版在 `brief/` 下保持同样层级。

### 5.2 引用格式

跨文档引用一律写完整路径加章节号，禁止只写节号；禁止「见上文」这类说法，同文件引用写「本文 §X.Y」。引用 `old/` 同样写完整路径。改完跑 `python tools/check_refs.py` 校验。

### 5.3 关于 05 构造与开发指南的时序

| 部分 | 何时写 |
|---|---|
| 结构部分 | 04 定稿后、动手编码前写完 |
| 签名与命令部分 | 编码过程中逐块补齐 |

编码前命令只给示例并标「示例，非本项目实际命令」；跑通后替换为真实命令。不许编造命令，也不许跳过这份文档。

## 6. 写作硬要求

### 6.1 可验证

每条需求有唯一编号 `项目代号-REQ-三位数`，都能回答「怎么判断做到了」。代号固定：`LING`、`CUI`、`RM`、`PLR`，新插件先登记代号再写需求。

### 6.2 无歧义

禁用词：等、等等、尽量、可能、大概、适当、必要时、原则上、快速、高效、友好、合理、优化、较快、足够、若干。替换为数字、条件或范围。「等」仅禁列举未尽的用法。

### 6.3 无错误

数字、路径、命令、接口名必须与实际一致；无法核实的标 `【待验证】` 并写验证方式。

### 6.4 术语统一

公共术语登在 `docs/common/01-术语表.md`，项目专属术语登在该项目 `00-总览与术语.md`；一个概念只用一个词，只在一处定义。代码、命令、文件名、报错原文照写。

### 6.5 单一事实来源

同一事实只在一处详细写，其他地方引用完整路径加章节号。

### 6.6 不写空话

每段要能回答谁做什么、在什么条件下、结果是什么。

### 6.7 优先用表格

对比、清单、参数、状态取值用表格；用图的必须配文字说明。

### 6.8 语言

中文书写；专业名词首次出现时给一句话解释。

## 7. 状态与版本

每份文档头部写元信息块：状态、最后更新、依据。`README.md` 例外：只写现状、目录与入口，不写状态块与变更记录。

### 7.1 状态含义

| 状态 | 含义 | 可否据此编码 |
|---|---|---|
| 草案 | 正在起草，会有大改 | 否 |
| 初定 | 已自审并经用户过目、无已知异议，但不承诺稳定 | 否 |
| 评审中 | 正按某轮意见修改，待用户再次确认 | 否 |
| 已定稿 | 用户明确确认通过 | 是 |

状态只能由用户确认后转为已定稿，AI 不得自行标注。

### 7.1.1 本项目的定稿时机

采用整体定稿：全部设计文档写完、互相对照无冲突后，统一由用户确认转为已定稿；之前一律「初定」。初定仍要写变更记录并检查下游影响。

### 7.2 变更记录

文末附三列表：日期、改了什么、为什么。已定稿文档再改必须新增一行，不覆盖历史。

## 8. 写-审-问-改 循环

### 8.1 步骤

写（标草案）→ 自审（对照第 9 节清单逐项记录）→ 提问题（编号、一条一问、附建议与理由）→ 改（转评审中）→ 复审 → 再问，重复直到清单全过且用户确认 → 初定 → 全部文档完成后定稿 → 同步简版 → 再审两版一致性。

### 8.2 出口条件

三条同时满足：清单全部通过且有逐条记录；用户明确说可以或定稿；简版完成且结构与详细版对应。

### 8.3 禁止的做法

未经用户确认自行标已定稿；带着未解决问题交付；用「已按要求完成」替代实际检查；为通过检查删掉难写的需求。

## 9. 审查清单

### A. 正确性

数字与版本可核对到出处；路径命令与实际一致；接口字段与设计对齐；交叉引用指向真实章节。

### B. 完整性

必备章节都在；每条需求有验收标准；异常与边界有交代；未决事项列成问题清单；非目标写明。

### C. 一致性

术语与术语表或项目术语一致；与其他文档不矛盾；与 `RULES.md`、`AGENTS.md` 不冲突；详细版与简版结论一致。

### D. 可验证性

需求有唯一编号；每条可判真伪；测试用例可追溯到需求编号。

### E. 语言与结构

无禁用词；标题不跳级；序号不跳号不重号；无空话段落。

## 10. 与其他文件的关系

| 文件 | 管什么 |
|---|---|
| `RULES.md` | 硬规则：红线、改动边界、Git、依赖、测试、密钥、审核约束 |
| `AGENTS.md` | 协作方式：沟通、推进、提交推送、审核、汇报 |
| 本文件 | 文档怎么组织、怎么写、怎么评审 |
| `docs/common/01-术语表.md` | 全项目统一术语 |

冲突顺序：用户明确指令 > `RULES.md` > `AGENTS.md` > 本文件；本文件与术语表冲突时先改本文件。
