# 02 版本号与兼容约定

> 状态：已定稿
> 最后更新：2026-11-03
> 依据：`docs/common/00-文档编写规范.md` §7

本文是 `docs/common/02-版本号与兼容约定.md` 的简版，只留规则与取值；为什么这么定见详细版。

## 1 版本号格式

`大版本.首要版本.次版本`，发布前追加 `-bN`：`0.0.1-b3`。段义为：大版本约等于另一套软件；首要版本表示阶段推进；次版本对应功能变化；`bN` 是第几次构建，从 1 开始。每段 0–65535，纯数字，不带前导零；`bN` 只在项目完成前出现。

## 2 ling 宿主怎么递增

| 动作 | 版本变化 | 例子 |
|---|---|---|
| 修 bug | 只加 `bN` | `0.0.1-b3` → `0.0.1-b4` |
| 重新打包测试 | 只加 `bN` | `0.0.1-b4` → `0.0.1-b5` |
| 功能变化 | 次版本 +1，`bN` 归 1 | `0.0.1-b9` → `0.0.2-b1` |
| 阶段推进，含不兼容 | 首要版本 +1，由项目负责人决定 | `0.0.2-b5` → `0.1.0-b1` |
| 大改，接近另一套软件 | 大版本 +1，默认不兼容 | `0.1.0-b3` → `1.0.0-b1` |
| 项目完成 | 去掉 `-bN` | `0.1.0-b7` → `0.1.0` |

项目完成后（`-bN` 已去掉）简化为三条：不破坏兼容的修 bug或加功能 → 次版本 +1；阶段推进含不兼容 → 首要版本 +1；大改 → 大版本 +1。

两条要点：`bN` 是构建序号，不是 beta 版本；首要版本由项目负责人判断，次版本才机械递增。

## 3 插件的版本

宿主只校验格式，不限制递增方式，不强制语义。

| 项 | 规则 |
|---|---|
| 格式 | 三段式，每段 0–65535 |
| 递增方式 | 插件作者自行决定，宿主不校验、不警告 |
| 用途 | 依赖匹配（`@1`、`@1.2`、`@1.2.3` 三种写法） |
| 格式非法 | 拒绝装载，返回 `E_MANIFEST_INVALID` |
| 内置插件 | 同一条规则，版本写在各自 `plugin.toml`，不强制等于宿主版本；当前列表见 `docs/ling/README.md` §0.2 |

能否装上由 `api` 与 `min_host` 两个字段决定，不由版本号语义决定。

## 4 兼容判定：谁说了算

两条规则都满足才装得上。

| 规则 | 字段 | 判定 | 失败错误码 |
|---|---|---|---|
| 接口兼容 | 清单 `api` | 宿主支持主版本 N 与其前一版 N-1 | `E_API_MISMATCH` |
| 宿主够新 | 清单 `min_host`（选填） | 宿主版本 ≥ `min_host`；不写视为不限制 | `E_HOST_TOO_OLD` |

`api` 管接口长什么样，`min_host` 管宿主够不够新。

## 5 什么能改，什么改了就破坏兼容

### 5.1 可以直接改，只升次版本

新增方法、新增事件主题、新增清单可选字段、新增能力取值、新增 `ling` 子命令、修改日志内容与格式（字段不变）。

### 5.2 不加版本号也能改

修 bug（只加 `bN`）、改内部实现与重构、改文档、改 `data/` 之外的目录布局（运行时会重建）。

### 5.3 改了必须升 api 主版本

删除或重命名已发布的方法与事件主题、改变参数或返回值语义、改变 `Context` 已有方法签名或语义、把可选清单字段改成必填、改变侧车 jsonl 帧字段名或含义、改变管理端口请求或应答结构。

### 5.4 永远不能改的

已发布 api 主版本的接口语义；`data/` 目录的格式（`LING-REQ-088`）；插件编号的含义。

## 6 兼容窗口

| 维度 | 承诺 |
|---|---|
| api 主版本 | 同时支持 N 与 N-1，跨两个主版本不兼容 |
| 宿主版本 | 不承诺向前兼容，插件用 `min_host` 声明下限 |
| 协议版本 | 侧车与管理端口协议带版本字段，不匹配只拒绝该连接或该插件 |
| 数据格式 | 跨宿主版本保持，升级不转换 `data/` |

## 8 已定结论

| # | 事项 | 结论 |
|---|---|---|
| 1 | 宿主版本号写在哪个文件、谁读它 | 编译期常量，`ling --version` 与启动日志都输出 |
