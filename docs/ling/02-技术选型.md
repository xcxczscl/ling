# ling 02 技术选型

> 状态：草案 | 最后更新：2026-10-28

本文决定四件事：宿主用什么语言、进程内插件用什么语言、侧车插件用什么语言、插件与宿主之间的边界用什么技术。四个问题互相牵连，所以放在一份文档里定，不拆开。

结论在 §6。想直接看结果读简版，想知道为什么读本文。

---

## 1. 判定维度与权重

### 1.1 七个维度

| 维度 | 衡量什么 | 怎么判断 |
|---|---|---|
| 可读性 | 你不借助解释能否读懂内核代码 | 抽样读 200 行，能否说清它在做什么 |
| 热更新可靠性 | 改插件后不重启宿主，能否干净换上 | 100 次连续重载后内存与行为是否正常 |
| 三端支持确定性 | Windows / Linux / Android 是否都有明确可行的路径 | 是否有官方工具链与已知限制 |
| 崩溃可控性 | 插件出错时宿主是否还活着、错误是否可定位 | 故意让插件崩溃，看宿主存活与调用栈质量 |
| 生态对接 | 与 ffmpeg、mpv 这类 C 库的对接成本 | 是否需要自己写绑定层 |
| 构建复杂度 | 新人从零到跑起来的步骤数 | 依赖管理、交叉编译的配置量 |
| 工具链成熟度 | 调试器、性能分析、崩溃转储是否好用 | 三端是否有稳定调试手段 |

### 1.2 权重

| 维度 | 权重 | 理由 |
|---|---|---|
| 可读性 | 30% | 上一版失败的直接原因是「代码看不懂，只能全权交给 AI」 |
| 热更新可靠性 | 20% | 这是 ling 的核心卖点，`docs/ling/01-需求规格.md` §3.6 有 7 条硬需求 |
| 三端支持确定性 | 20% | `docs/ling/00-总览与术语.md` §2.4 把多平台列为目标，不是可选项 |
| 崩溃可控性 | 15% | 宿主被插件拖死，等于所有插件一起失效 |
| 生态对接 | 10% | 播放器插件必须调 C 媒体库，绑定层写不好会拖垮整个项目 |
| 构建复杂度 | 5% | 只影响起步阶段，不影响长期 |

可读性权重最高是本文最关键的一个判断。理由不是「方便」，是**可持续性**：一个自己读不懂的内核，每次改动都要重新理解一遍，改错的概率随代码量上升。这不是偏好问题。

## 2. 约束与前提

### 2.1 不变的约束

来自 `docs/ling/00-总览与术语.md` 与 `docs/ling/01-需求规格.md`，本文不重新讨论：

- 宿主零内容：只提供机制，不含业务功能
- 单机、单用户、几十个插件
- 多平台：Windows 主要平台、Linux 对齐、Android 受限降级
- 插件可独立装载、卸载、热更新
- 插件之间不直接链接，只经宿主互调

### 2.2 可信前提

**所有插件都由你自己编写。** 这一条决定了威胁模型的边界：

- 不需要防恶意插件（恶意代码、提权、逃逸沙箱归 `docs/ling/06-安全设计.md`，且明确不在本文讨论）
- 但需要防**意外崩溃**：自己写的插件也会有空指针、死循环、越界

这个前提允许一个关键简化：进程内执行的插件代码可以视为「可信但会出错」，因此设计重点从「隔离」转向「出错后能恢复、能定位」。

### 2.3 性能底线分档

不是所有调用都需要同样的速度。分三档，只有第一档不能妥协：

| 档位 | 场景 | 可接受上限 | 判断依据 |
|---|---|---|---|
| 交互式 | 界面点击后的响应、播放控制 | 50 毫秒 | 人感知延迟阈值约 100 毫秒，留一半余量 |
| 批量 | 文件扫描、哈希计算、批量转码 | 无上限要求 | 耗时由数据量决定，不是调用机制决定 |
| 管理 | 装插件、查状态、看日志 | 500 毫秒 | `docs/ling/01-需求规格.md` LING-REQ-096 已定 |

**关键的推论**：批量操作占实际耗时的绝大部分，而它们的耗时与「调用机制开销」无关——一次扫描几万个文件要几十秒，调用开销是 1 微秒还是 100 微秒都不影响结果。真正需要快的只有「交互式」这一档，而它有 50 毫秒预算。

这个推论直接决定 §3 的形态选择。

### 2.4 上一版失败的原因

上一版用 Rust 写了约 6300 行内核（`old/main/`，27 个文件），实际结果是「看不懂，出问题查不出」。原因按可信程度排序：

| 推测原因 | 依据 | 可验证性 |
|---|---|---|
| 异步代码与生命周期标注混在一起，阅读时要在脑内做两层推理 | old 文档提到异步运行时、跨进程调用、超时控制，这类逻辑在 Rust 里必然涉及 `async`、`Send + Sync` 约束、生命周期标注 | 读 `old/main/` 的任意调用路径即可确认 |
| 插件接口涉及 trait 对象与 `unsafe` FFI 层，两层抽象叠加 | old 的 `04-插件接口规范.md` 描述的是跨动态库的接口表 | 同左 |
| 没有前置设计文档，边写边改 | 上一轮之前 `old/docs/` 是事后补写的设计 | 仓库历史 |

**这条要你补一句**：具体是哪一类代码看不懂（异步、trait、生命周期、宏、还是全部）？这会影响 §8 的写法约定。已记入 §10 未决问题。

## 3. 插件形态

### 3.1 三种形态

| 形态 | 做法 | 插件与宿主的边界 |
|---|---|---|
| 纯进程内 | 插件编译成动态库（`.dll` / `.so`），`dlopen` 装入宿主进程 | 函数调用 |
| 纯侧车 | 每个插件是独立可执行文件，宿主启动它并用本地套接字通信 | 进程 + 消息 |
| 混合双轨 | 性能敏感的插件进程内，其余侧车 | 两者都有 |

### 3.2 对照

| 项 | 纯进程内 | 纯侧车 | 混合双轨 |
|---|---|---|---|
| 调用延迟 | 0.1–1 微秒 | 50–200 微秒 | 按插件分 |
| 崩溃隔离 | 无，插件崩则宿主崩 | 完全隔离 | 部分 |
| 热更新 | 难，见 §5.6 | 易，重启进程即可 | 按插件分 |
| 语言自由度 | 必须与宿主 ABI 兼容 | 任意语言 | 双轨各自受限 |
| 内核代码量 | 大（装载器、ABI 胶水、崩溃捕获） | 小（协议 + 进程管理） | 最大 |
| 调试难度 | 混合栈，跨语言断点 | 单独进程，可单独附加 | 都要会 |
| 内存共享 | 直接共享 | 必须序列化 | 都要会 |

延迟数字的估算依据：本地套接字一次往返包含两次系统调用、两次上下文切换、一次序列化与反序列化，实测常见区间是 30–100 微秒，加上 JSON 处理取 50–200 微秒。进程内函数调用是一次间接跳转加两次哈希查表，约 300–500 纳秒。

### 3.3 为什么选混合双轨

按 §2.3 的分档，混合双轨成立的逻辑是：

- **交互式场景必须快**，而这类场景的调用链短、频率高（界面每秒按几十次状态查询计），只有进程内能满足 50 毫秒预算里省下开销的诉求
- **批量场景不敏感**，而这类场景恰恰是最需要语言自由度的（扫描、转码、解析各类文件格式，Python 生态最方便）
- 纯侧车会让所有插件都背上 50–200 微秒，交互式场景在插件数量增加后会累积
- 纯进程内会强迫所有插件用同一门语言，等于放弃「小功能用 Python 直接写」这个最大便利

代价是内核要同时维护两套装载路径。§5 会说明如何把这两套的成本压到可接受。

### 3.4 混合双轨的收敛办法

成本主要来自「进程内插件」这一轨，因为要处理 ABI、崩溃、卸载。三条收敛规则：

1. **进程内插件只用于交互式热路径**，其余一律侧车。默认侧车，进程内是例外，需要理由。
2. **进程内插件的 ABI 只有一张函数表**，见 §5.2。整个系统的跨语言边界只有一个点，不是每加一个功能就多一个边界。
3. **进程内插件不允许卸载**，热更新改为「加载新版本、切换指针、旧版本留在内存」，见 §5.6。这条放弃了「彻底卸载」，换来「不需要处理 dlclose 的所有坑」。

第 3 条牺牲了一点内存（每次重载泄漏一个映射），换来的是可靠性。对个人工具，这个交换划算。

## 4. 语言对照

### 4.1 排除的候选

| 语言 | 排除理由 |
|---|---|
| Go | 标准库 `plugin` 包只在 Linux 与 macOS 可用，Windows 不支持；且要求插件与宿主用完全相同的依赖版本，实际无法分发 |
| Java / Kotlin | JVM 启动 300 毫秒起、常驻内存 100 MB 起，与 `docs/ling/01-需求规格.md` LING-REQ-094（冷启动 ≤ 300 毫秒）与 LING-REQ-099（常驻 ≤ 120 MB）冲突；Android 之外的三端分发要带 JRE |
| Node.js / Electron | 运行时内存百 MB 起；且适合做界面，不适合做需要直接操作文件与调用 C 库的宿主 |
| Zig | 生态与工具链成熟度不足，绑定 C 库可行但调试与文档资料少，风险高于收益 |

排除不等于永远不用：这些语言都可以作为**侧车插件**的语言，因为侧车只要求「能读写本地套接字、能处理 JSON」。

### 4.2 C++

**能否做宿主**：能，且是原生方案。`dlopen` / `LoadLibrary` 是它的标准能力。

**调用开销**：进程内虚函数调用或函数指针调用，约 1–10 纳秒。

**内存安全**：无。野指针、重复释放、越界会直接破坏宿主进程。这是最大短板。

**三端**：

| 平台 | 工具链 | 状态 |
|---|---|---|
| Windows | MSVC 2022 | 成熟 |
| Linux | GCC 或 Clang | 成熟 |
| Android | NDK（Clang） | 成熟，但需处理 ABI 与 STL 版本 |

**生态对接**：ffmpeg、mpv、libvlc 都是 C/C++，零绑定成本。这一项是四门语言里最好的。

**热更新**：`dlclose` 可用但不可靠，见 §5.6。

**可读性**：语法直白，但三样东西是阅读负担——模板（尤其标准库的错误信息）、指针与手动内存管理、宏。这三样都可以通过写法约定规避，见 §8。

**构建**：CMake + vcpkg（或 Conan）。配置文件比 Cargo 长，但内容直白：每个依赖一行，每个目标一段。对不熟的人反而比 Cargo 的 feature 解析好读。

### 4.3 Rust

**能否做宿主**：能，`libloading` 加载动态库。

**调用开销**：与 C++ 同量级。

**内存安全**：进程内的安全代码有编译器保证。但**跨 FFI 边界后这个保证失效**：`unsafe` 块、`transmute`、跨库传引用会引入未定义行为，且编译器不再检查。

这一点需要说清，因为它是常见的误解：Rust 的安全性止步于 `unsafe` 边界，而插件宿主的核心恰恰全是边界代码。`old/main/` 里如果为了传 trait 对象写了大量 `unsafe`，那 Rust 的主要优势在关键路径上并不存在。

**三端**：`cargo` 交叉编译成熟，Android 有 `cargo-ndk`。

**生态对接**：ffmpeg 有 `ffmpeg-next`，mpv 有 `libmpv-sys`，都是第三方维护的绑定层，版本跟随需要自己跟。

**热更新**：四门语言里最差，见 §5.6。

**可读性**：这是上一版失败的直接原因。三样东西叠加——所有权与生命周期标注、`async` 与 `Send + Sync` 约束、trait 对象与泛型。单独一样都能学，三样混在一条调用链上时，读一段代码要在脑内同时追踪这三层。

**构建**：Cargo 依赖管理最好，但 feature 与 target 配置的语义不直观（同一个 crate 在不同 feature 组合下行为不同）。

**结论**：技术上完全可行，但按 §1.2 的权重，可读性 30% 这一项上它得分最低，而这一项权重最高。不选它的理由是权重，不是能力。

### 4.4 C#

这条要分两条路说，因为「CIL 能不能高速」的答案是：**能，但高速的前提与插件化冲突**。

#### 4.4.1 路线 A：整个宿主用 C#（托管宿主）

宿主是 .NET 程序，插件是程序集（`.dll`），用 `AssemblyLoadContext` 加载。

| 项 | 情况 |
|---|---|
| 调用开销 | 委托调用 10–30 纳秒，比 C++ 慢一个数量级，但比侧车快三个数量级 |
| 计算性能 | JIT 编译后约为 C++ 的 50%–90%，热点循环差距更小；受 GC 影响，长时间运行有停顿 |
| 热更新 | **四门语言里最好**：`AssemblyLoadContext` 支持「可回收」模式，卸载时 GC 会回收全部类型与静态字段，官方支持真正卸载 |
| 崩溃可控性 | 内存安全，不会出现野指针崩溃；`StackOverflowException` 与 `OutOfMemoryException` 无法捕获，仍会杀进程 |
| 内存占用 | 空载自包含应用约 30–50 MB 常驻，加插件后上升。与 LING-REQ-099 的 120 MB 上限可以共存，但余量不大 |
| 启动 | 自包含 + ReadyToRun 约 100–200 毫秒，满足 LING-REQ-094 |
| 生态对接 | ffmpeg 需 `FFmpeg.AutoGen` 这类绑定，调用经 P/Invoke，每次约 20–50 纳秒；mpv 有 `LibVLCSharp` 但那是 VLC 不是 mpv |

**三端支持是这条路的问题所在**：

| 平台 | 运行时 | 动态加载插件 | 风险 |
|---|---|---|---|
| Windows / Linux | CoreCLR | 支持，`AssemblyLoadContext` 可回收 | 无 |
| Android | Mono（AOT + 解释器） | 支持，`.NET 6` 起 `AssemblyLoadContext` 已可用 | **中高**：未预编译的程序集走解释器，性能下降；且 .NET 11 起 Android 不再提供解释器 |

Android 这条要展开一句：Android 的 .NET 应用默认用 Mono，Release 模式下程序集被 AOT 预编译，符合 AOT 要求的走原生代码，未预编译的交给解释器执行。插件是后装的、无法预编译，所以必然走解释器——功能可用，但性能是解释执行的水平。而 `AndroidUseInterpreter` 这个开关在 .NET 11 及以后不再存在，说明这条路在收窄。

另外 **NativeAOT 这条路走不通**：官方文档明确列出「不支持运行时加载程序集」（`Assembly.LoadFile`、`Reflection.Emit` 都不可用）。而 NativeAOT 恰恰是 C# 启动快、内存小的唯一办法。**想要 NativeAOT 的性能，就要放弃插件动态加载**——这是「CIL 高速」这个设想最硬的一道墙。

#### 4.4.2 路线 B：C++ 宿主嵌入 CoreCLR

用 `hostfxr` 把 .NET 运行时加载进 C++ 进程，插件用 C# 写。

| 项 | 情况 |
|---|---|
| 复杂度 | 高。要处理运行时初始化、托管异常不能跨边界（必须用 `UnmanagedCallersOnly`）、GC 句柄与钉住、双向调用的胶水 |
| 调试 | 混合栈，C++ 与 C# 两套调试器，问题定位成本高 |
| 收益 | 一个：C++ 内核配 C# 插件 |

**结论**：不推荐。收益只有语言搭配上的偏好，代价是一整套双向边界胶水，而这个项目只有一个人维护。

#### 4.4.3 C# 的总结

如果按 §1.2 的权重打分，C# 在「可读性」和「热更新可靠性」两项上都是第一，在「三端支持确定性」上失分，在「生态对接」上得分居中。

它是四门语言里**技术上最优雅的宿主选择**，输在三件事：你不熟 C#、Android 路线在收窄、媒体库要经过绑定层。

### 4.5 Python

「通过 CPython 实现高速」这句话要拆成三个层次看，每层的答案不同。

#### 4.5.1 作为宿主

不可行。启动与内存都超标（CPython 空解释器约 8–15 MB，加上标准库与依赖后更高；启动约 50–150 毫秒），且 GIL 会让所有插件串行。不展开。

#### 4.5.2 嵌入宿主进程（C++ 链接 libpython）

C++ 宿主直接链接 CPython，`Py_Initialize` 之后用 `PyImport_ImportModule` 加载 `.py` 文件，用 `PyObject_Call` 调函数。

| 项 | 情况 |
|---|---|
| 调用开销（不含类型转换） | 约 0.1–0.5 微秒，比 C++ 慢，但比侧车快百倍 |
| **类型转换开销** | 这是真正的瓶颈，见下 |
| 并发 | 受 GIL 限制，同一时刻只有一个线程执行 Python 字节码 |
| 崩溃隔离 | 无。Python 的 C 扩展（numpy、lxml 这类）段错误会直接杀掉宿主进程 |
| 热更新 | 差。从 `sys.modules` 删模块不清循环引用、不清 C 扩展状态、不停后台线程，反复重载必然累积残留 |
| 打包 | Windows 带 `python314.dll` 约 5 MB 加裁剪后的标准库；Linux 带 `libpython`；Android 需要交叉编译 CPython（3.14 起有官方 Android 二进制，成本下降） |

**类型转换才是成本的主体，这一点常被忽略**：

| 载荷 | 转换方式 | 估算成本 |
|---|---|---|
| 5 个字段的小 dict | 逐个 `PyDict_SetItem` | 0.5–2 微秒 |
| 1 KB 字符串 | `PyUnicode_FromStringAndSize`，一次拷贝 | 1–3 微秒 |
| 1 MB 字节缓冲 | 一次内存拷贝 | 100–300 微秒 |
| 1 MB JSON | C++ 侧解析 + Python 侧 `json.loads` | 5–15 毫秒 |

估算依据：1 MB 内存拷贝在本地 SSD 桌面机上约 30–100 微秒，JSON 解析速度约 100–300 MB/s，两侧各解析一次再叠加。

结论很清楚：**嵌入 CPython 的「高速」只在小载荷、纯数值参数时成立**。一旦按 `docs/ling/01-需求规格.md` LING-REQ-097 允许 1 MB 载荷，转换成本就超过了侧车的套接字往返。

**GIL 是第二个硬约束**。三个 Python 插件嵌入同一个解释器时，它们不能真正并行；一个插件卡住 GIL，其他插件的调用全部排队。

3.14 起有两个相关变化：free-threaded 构建（`PEP 779`）已从实验性转为正式支持，但仍需单独构建且生态未完全适配；多解释器进标准库（`PEP 734`），可以给每个插件一个子解释器，配合 `PEP 684` 的独立 GIL 实现隔离。但子解释器对「不兼容多解释器的 C 扩展」有限制，而这类扩展很常见。

#### 4.5.3 侧车进程

Python 进程独立运行，通过本地套接字与宿主通信。

| 项 | 情况 |
|---|---|
| 调用开销 | 50–200 微秒，与语言无关，只与进程边界有关 |
| 并发 | 每个插件一个进程，独立 GIL，真正并行 |
| 崩溃隔离 | 完全隔离 |
| 热更新 | 最容易：杀掉进程、起新进程 |
| 打包 | 需要带 Python 运行时（约 15–30 MB 裁剪后），Android 上要处理运行时与权限 |

**结论**：Python 在 ling 里的正确位置是**侧车插件**，不是宿主，也不推荐嵌入宿主进程。按 §2.3 的分档，侧车的百微秒延迟在批量场景完全感觉不到，而批量场景正是 Python 的主场。

### 4.6 总表

评分 1–5，5 最好。权重见 §1.2。

| 维度 | 权重 | C++ | Rust | C# | Python |
|---|---|---|---|---|---|
| 可读性 | 30% | 3 | 2 | 5 | 4 |
| 热更新可靠性 | 20% | 2 | 1 | 5 | 3 |
| 三端支持确定性 | 20% | 5 | 5 | 3 | 3 |
| 崩溃可控性 | 15% | 2 | 3 | 4 | 2 |
| 生态对接 | 10% | 5 | 4 | 3 | 5 |
| 构建复杂度 | 5% | 3 | 4 | 4 | 2 |
| **加权总分** | 100% | **3.25** | **2.85** | **4.20** | **3.30** |

加权计算：

- C++ = 3×0.3 + 2×0.2 + 5×0.2 + 2×0.15 + 5×0.1 + 3×0.05 = 0.9 + 0.4 + 1.0 + 0.3 + 0.5 + 0.15 = 3.25
- Rust = 2×0.3 + 1×0.2 + 5×0.2 + 3×0.15 + 4×0.1 + 4×0.05 = 0.6 + 0.2 + 1.0 + 0.45 + 0.4 + 0.2 = 2.85
- C# = 5×0.3 + 5×0.2 + 3×0.2 + 4×0.15 + 3×0.1 + 4×0.05 = 1.5 + 1.0 + 0.6 + 0.6 + 0.3 + 0.2 = 4.20
- Python = 4×0.3 + 3×0.2 + 3×0.2 + 2×0.15 + 5×0.1 + 2×0.05 = 1.2 + 0.6 + 0.6 + 0.3 + 0.5 + 0.1 = 3.30

**这张表给出一个反直觉的结论：C# 得分最高。**

但评分不等于结论，原因有三条，都不在表里：

1. 可读性打分假设「你懂这门语言」。C# 的 5 分建立在会读 C# 之上，而你的背景是 C++ 用过但不算深。学一门新语言的成本，前三个月可读性按 0 计。
2. 三端确定性的 3 分掩盖了一个趋势：Android 的 C# 动态加载路线在收窄（.NET 11 去掉解释器），而 `docs/ling/00-总览与术语.md` §2.4 把 Android 列为长期目标。
3. 评分是静态的，不反映「将来想加新插件语言」这个自由度。C ABI 边界对任何语言开放，托管边界只对 .NET 开放。

所以 §6 的结论是：**按评分 C# 最高，按你的实际条件与长期路线选 C++。**

## 5. 插件边界技术

这是全篇对工程影响最大的一节。C++ 不深的人最容易在这里出「编译通过、运行崩溃」的问题，所以写细。

### 5.1 为什么必须用 C ABI

C++ 没有稳定的二进制接口。三个具体后果：

| 不一致的地方 | 后果 |
|---|---|
| 编译器不同（MSVC 与 Clang） | 名称修饰规则不同，链接时找不到符号 |
| 同一编译器的不同大版本 | 类布局与虚表布局会变化 |
| 运行时库不同（`/MD` 与 `/MT`） | 两份堆，一边申请一边释放，崩溃 |
| 异常模型不同（`/EHsc` 与 `/EHs`） | 跨边界抛异常时栈展开行为不一致，崩溃 |
| 标准库版本不同（不同 STL 实现） | `std::string` 的布局不同，跨边界传它会读错内存 |

规避办法只有一个：**跨动态库边界只用 C 语言的那部分**。C 的函数调用约定、结构体布局、基本类型，是各编译器共同遵守的稳定约定。这是 Qt、Chrome、LibreOffice 都在用的做法，不是权宜之计。

Rust 的处境相同：两个 Rust 动态库之间同样不能直接传 `String`、`Vec`、trait 对象，也要退化到 C ABI，或者引入 `abi_stable` 这类库来模拟稳定 ABI。**这一点上两种语言没有区别**，说「Rust 比 C++ 更安全」在边界这一层不成立。

### 5.2 唯一入口点

整个系统跨语言边界的地方只有一个：插件导出**一个**函数。

```c
/* 边界契约的示意，实际定义在 04-详细设计/02-插件装载与接口.md */
typedef struct {
    uint32_t abi_version;        /* 边界版本，不匹配则拒绝装载 */
    const char* plugin_id;       /* 插件编号，必须带命名空间前缀 */
    const char* plugin_version;
} ling_plugin_descriptor;

typedef struct {
    /* 函数指针表：宿主提供给插件的能力，全部是 C 函数指针 */
    void*  (*context_alloc)(void);
    int32_t (*register_method)(void* ctx, const char* name, void* fn, void* undo);
    int32_t (*call)(void* ctx, const char* target, const char* method, const uint8_t* args, size_t len, uint8_t** out, size_t* out_len);
    /* ...其余能力，见详细设计 */
} ling_host_api;

/* 插件唯一导出的符号 */
int32_t ling_plugin_entry(const ling_host_api* host, ling_plugin_descriptor* out);
```

这个设计的三个性质：

1. **一个符号**：跨边界的只有 `ling_plugin_entry`，其余全部通过函数表指针转发。加功能只需要扩 `ling_host_api`，不需要加新导出符号。
2. **版本可查**：`abi_version` 由宿主校验，不匹配直接拒绝，而不是崩在半路。
3. **语言中立**：任何能导出 C 函数的语言都能写进程内插件，包括 C、Rust、Zig。这为将来换插件语言留了口子，见 §7。

胶水代码规模估算：宿主侧装载器约 150 行，函数表定义与实现约 100 行，错误映射约 50 行。合计约 300 行，**只写一次，之后不再改动**。这是混合双轨方案成本可控的关键。

### 5.3 类型禁区

跨边界只允许这些类型：

| 允许 | 说明 |
|---|---|
| 定宽整数、浮点 | `int32_t`、`uint64_t`、`double`，布局确定 |
| 不透明句柄 | `void*`，指向谁只有提供方知道 |
| 指针 + 长度 | `const uint8_t* data, size_t len`，不用以 0 结尾的字符串表示含 0 字节的数据 |
| 定长结构体（纯数据） | 只用定宽字段，成员顺序与对齐由 `#pragma pack` 或显式填充固定 |
| 函数指针 | 带明确的调用约定 |

禁止跨边界的：

| 禁止 | 原因 |
|---|---|
| `std::string`、`std::vector`、`std::map` | 布局依编译器与 STL 实现而变 |
| 抛异常跨边界 | 异常模型不一致，栈展开行为未定义 |
| 跨边界用 RTTI（`dynamic_cast`、`typeid`） | 虚表布局与类型信息格式不保证一致 |
| 传递 C++ 对象的所有权 | 谁申请谁释放，不能跨边界移交 |
| 回调里持有引用超过调用期 | 宿主不保证对象在回调返回后仍存活 |

**内存归属的硬规则**：谁申请谁释放。跨边界返回的缓冲区必须由同一个模块提供释放函数，例如 `ling_host_api` 里有 `free_buffer`，插件用它释放宿主给的缓冲，不许调自己的 `free`。

这条规则在 Windows 上尤其重要：`/MD` 与 `/MT` 各有一份堆，混用会立刻崩。

### 5.4 编译器与运行时一致性

这是「编译通过但跑不起来」最常见的原因。硬约束：

| 约束 | Windows | Linux | Android |
|---|---|---|---|
| 编译器 | 统一用 MSVC 2022 | 统一用 Clang（不用 GCC 混编） | 统一用 NDK 里的 Clang |
| C++ 标准 | `/std:c++17` | `-std=c++17` | 同 Linux |
| 运行时库 | 统一 `/MD`（动态 CRT） | 不涉及 | 不涉及 |
| 异常模型 | 统一 `/EHsc` | 默认 | 默认 |
| 架构 | x64 与 arm64 各自一致 | 同左 | arm64-v8a |
| 构建类型 | Debug 插件不能装进 Release 宿主 | 同左 | 同左 |

落地办法：`05-构造与开发指南` 会提供一份统一的构建脚本，宿主与所有插件共用同一份编译选项定义。**插件作者不自己写编译选项**，这样约束不靠人记。

### 5.5 崩溃捕获

进程内插件崩溃必须挡住，否则一个插件的空指针会带走整个宿主。

| 平台 | 手段 | 可靠性 |
|---|---|---|
| Windows | `__try` / `__except`（MSVC 的结构化异常），或 `AddVectoredExceptionHandler` | 较高，能捕获访问违例与除零 |
| Linux | `signal` + `siglongjmp` | **低**。信号处理器里做长跳转会破坏栈状态，只能尽力而为 |
| Android | 同 Linux | 低 |

结论：**跨平台的「崩溃后继续运行」在进程内不可靠**。因此：

- Windows 上进程内插件崩溃 → 捕获、记录、把该插件标记为故障、拒绝后续调用
- Linux 与 Android 上进程内插件崩溃 → 宿主会一起退出，靠外部守护重启
- **真正可靠的隔离只能是侧车**。这是 §3.3 选混合双轨时必须接受的代价：进程内那一轨的崩溃隔离在非 Windows 平台上打折

### 5.6 热更新的三条现实路径

`docs/ling/01-需求规格.md` §3.6 要求改插件不重启宿主。四门语言的实际能力差别很大，必须说清。

#### 路径一：`dlclose` 卸载后重新加载（C++ 名义方案）

理论上可行，实际有四个坑：

1. **TLS 未释放则不会真正卸载**：动态链接器为库分配了线程局部存储槽，只要还有引用，`dlclose` 只减少引用计数，不解除映射
2. **同名文件重新 `dlopen` 返回旧句柄**：因为旧映射还在，加载器认为文件已加载
3. **静态对象析构顺序不可控**：库里若有指向其他库的引用，析构时那个库已经没了
4. **其他库持有指针**：任何跨库持有的函数指针在新版本加载后指向旧代码

#### 路径二：复制到新文件名再加载（工程实践）

绕开坑 2 的办法：每次重载把插件文件复制成新名字（`plugin_0001.dll`、`plugin_0002.dll`），用不同路径 `dlopen`。

结果：新版本能加载，旧版本留在内存不卸载。代价是每次重载泄漏一个代码映射——按典型插件 100–500 KB 估算，100 次重载泄漏 10–50 MB。

`docs/ling/01-需求规格.md` LING-REQ-101 定的是「100 次连续 reload 后内存增长 ≤ 10 MB」。**这两件事冲突**：要么放宽这条需求，要么在 100 次之后提示重启宿主。这条已记入 §10。

#### 路径三：侧车重启（可靠方案）

杀掉旧进程、起新进程。没有卸载问题，因为没有卸载——进程退出由操作系统回收全部资源。

代价是重载期间该插件不可用（约 100–500 毫秒），期间调用返回 `E_PLUGIN_MISSING`（`docs/ling/01-需求规格.md` LING-REQ-054 已规定这个行为）。

#### 四门语言的热更新能力对照

| 语言 | 路径一 | 路径二 | 路径三 | 综合 |
|---|---|---|---|---|
| C++ | 有坑 | 可行，泄漏 | 可行 | 2/5 |
| Rust | **本质不安全**，社区共识是不卸载 | 可行，泄漏 | 可行 | 1/5 |
| C# | 不需要：`AssemblyLoadContext` 可回收，GC 负责清理 | — | 可行 | 5/5 |
| Python | 嵌入模式下不可靠（`sys.modules` 清理不彻底） | — | 可行 | 3/5 |

Rust 得 1 分的原因要说明：Rust 官方与社区的共识是**不卸载动态库**。理由是一旦卸载，库里的 `&'static` 引用、字符串字面量、trait 对象的虚表指针全部变成悬垂指针，而 Rust 的类型系统无法表达「这个 `'static` 只在这个库加载期间有效」。这是语言层面的限制，不是实现缺陷。

**本文的取舍**：进程内插件放弃路径一，采用路径二（复制文件名 + 不卸载），并在账本里记录泄漏，达到阈值后提示重启。侧车插件走路径三。

## 6. 最终组合

### 6.1 结论

| 角色 | 选择 | 版本 |
|---|---|---|
| 宿主内核 | C++ | C++17，MSVC 2022 / Clang / NDK Clang |
| 进程内插件 | C++（同一套 ABI） | 同宿主 |
| 侧车插件（首选） | Python | 3.14 |
| 侧车插件（其他） | 任意能读写本地套接字的语言 | 不限制 |
| 边界技术 | 单个 `ling_entry` 导出函数 + C ABI 函数表 | `abi_version` 从 1 开始 |
| 构建系统 | CMake + vcpkg（Windows / Linux）、NDK 工具链（Android） | 最新稳定版 |

### 6.2 被否方案与理由

| 方案 | 否掉的理由 |
|---|---|
| Rust 内核 | 可读性权重最高而它该项最低（§4.3）；热更新最差 |
| C# 托管宿主 | 评分最高但你不熟 C#；Android 动态加载路线在收窄；NativeAOT 与动态插件二选一 |
| C++ 宿主 + Python 嵌入 | GIL 串行、C 扩展崩溃不隔离、热更新不可靠；大载荷转换成本超过侧车（§4.5.2） |
| 纯侧车 | 交互式场景的延迟预算会被插件数量摊薄（§3.3） |
| 纯进程内 | 放弃 Python 插件这个最大便利，且 Linux/Android 上崩溃不隔离 |
| Go / Java / Node 宿主 | 见 §4.1 |

## 7. 可替换性设计（防止返工）

你提出「不然要改就很麻烦了」。返工的最大来源不是选错语言，而是**把语言写进了契约定死**。为此有三条设计约束：

### 7.1 契约与实现分离

| 层 | 内容 | 换语言时是否重写 |
|---|---|---|
| 契约层 | 插件清单格式、方法名与事件名规则、错误码表、消息协议、`ling_host_api` 函数表定义 | **不重写**，与语言无关 |
| 内核实现 | 路由表、事件总线、门禁、依赖解析的具体代码 | 重写 |
| 插件实现 | 每个插件自己的业务逻辑 | 不重写（侧车插件完全不用改；进程内插件需重新编译） |

契约层的文件放在 `docs/ling/04-详细设计/` 与仓库的接口头文件中，用**语言中立的写法**描述：结构体字段用定宽类型，协议用 JSON schema 或表格，不用任何 C++ 特性表达契约。

### 7.2 换内核语言的代价估算

假设三年后想从 C++ 换成别的语言：

| 部分 | 工作量 |
|---|---|
| 内核 6000 行左右重写 | 大头 |
| 侧车插件（Python） | 零改动，协议没变 |
| 进程内插件（C++） | 不用改代码，但需按新宿主的装载方式重新编译 |
| 文档 | 契约部分不用改，实现部分要改 |

这个估算成立的前提是 §7.1 做到了。若契约里混进了 `std::string` 这类语言相关类型，侧车协议也要跟着改。

### 7.3 一个额外的口子

`ling_host_api` 是 C ABI，意味着**非 C++ 的进程内插件在技术上可行**。比如将来某个热点插件想用 Rust 写，只要它能导出 `ling_entry` 并填好函数表，就能装进同一个宿主。

这条不承诺、不测试、不写文档，但设计上不堵死。

## 8. 「不耍花招」写法约定

这一节直指上一版的失败原因。语言选对只是必要条件，写法约定才是「读得懂」的充分条件。

### 8.1 禁用

| 禁用项 | 原因 |
|---|---|
| 模板元编程（`std::enable_if`、SFINAE、变参模板递归） | 阅读时要在脑内展开，错误信息长达数百行 |
| 多继承 | 对象布局与指针调整难以推理 |
| 运算符重载（除 `==`、`<` 这类显然语义） | 读代码时看不出在做什么 |
| 宏定义控制流 | 调试器单步会跳过 |
| 异常跨模块传播 | 见 §5.3，行为未定义 |
| 全局可变状态 | 无法推理谁在什么时候改了它 |
| 单文件超过 500 行 | 超过说明职责不单一 |

### 8.2 允许并鼓励

| 允许项 | 说明 |
|---|---|
| RAII | 用析构函数管资源，这是 C++ 里减少出错的最有效手段 |
| `std::unique_ptr` / `std::shared_ptr` | 明确所有权，避免手写 `delete` |
| `const` 与 `constexpr` | 让编译器帮忙检查 |
| 简单模板（容器、`std::optional`、`std::variant`） | 只用不改语义的那部分 |
| 早期返回（`if (!ok) return err;`） | 减少嵌套层级，比多层 `if` 好读 |
| 每个函数单一职责、不超过 60 行 | 便于单独测试与阅读 |

### 8.3 命名与注释

| 类别 | 约定 |
|---|---|
| 类型 | `PascalCase`，如 `PluginRegistry` |
| 函数与方法 | `snake_case`，如 `register_method` |
| 成员变量 | 后缀下划线，如 `entries_` |
| 常量 | `k` 前缀，如 `kMaxPayloadBytes` |
| 文件 | `snake_case.cpp`，一个文件一个主要类型 |
| 注释 | 写「为什么这么做」，不写「这行在做什么」 |

命名规则不需要你记：`05-构造与开发指南` 会配一个 `clang-format` 配置与一份检查清单，格式问题由工具管。
