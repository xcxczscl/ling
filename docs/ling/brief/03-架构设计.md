## 2. 架构总览

### 2.1 五层

表现层（浏览器、窗口视图、命令行，全部由插件提供）→ 插件层（内置插件 + 业务插件）→ 内核层（4 服务 + 3 机制）→ 通道层（装载通道、管理端口）→ 平台层（C++17 运行时、动态库、本地 TCP、文件系统）。

### 2.2 组件全景

插件只碰 `Context`；门后是账本、路由表、订阅表、门禁、调和、依赖解析；对外两条通道：装载通道、管理端口。

### 2.3 组件清单

| 组件 | 层 | 没有它会怎样 |
|---|---|---|
| 方法路由 | 内核 | 插件得直接链接彼此，无法单独卸载 |
| 事件广播 | 内核 | 广播方要自己维护通知名单 |
| 能力门禁 | 内核 | 装上插件等于给了全部权限 |
| 依赖解析与调和 | 内核 | 装卸的连锁反应只能靠人工重启 |
| 上下文 | 内核机制 | 插件随手改全局，卸载无法还原 |
| 效应账本 | 内核机制 | 卸载留下死方法、残留订阅 |
| 装载通道 | 通道 | 代码进不来 |
| 管理端口 | 通道 | 只能杀进程重启 |
| core-ui 侧车 | 插件 | 无界面，命令行仍可用 |

## 3. 设计原则

### 3.1 四条基本原则

| # | 原则 | 违反后果 |
|---|---|---|
| P1 | 零内容：宿主只给机制 | 宿主变回大程序，插件失去意义 |
| P2 | 一切经上下文 | 记不了账，卸载不干净 |
| P3 | 修改必可逆 | 同 P2 |
| P4 | 需求必声明 | 依赖变化靠人工重启 |

P2 与 P3 是一对：能记账的前提是每次修改都带撤销。

### 3.2 两条补充原则

| # | 原则 | 违反后果 |
|---|---|---|
| P5 | 单一状态源：同一事实只存一处 | 两处不一致时无从判断谁对 |
| P6 | 失败可观测：失败留记录，不静默吞掉 | 只看到「没生效」，看不到为什么 |

## 4. 内核职责边界

### 4.1 四项服务

| # | 服务 | 不做什么 |
|---|---|---|
| 1 | 方法路由 | 不理解方法含义，不做业务参数校验 |
| 2 | 事件广播 | 不落盘、不重投、不保证送达 |
| 3 | 能力门禁 | 不解释能力语义，不限制具体路径 |
| 4 | 依赖解析与调和 | 不保存业务数据，不替插件迁移数据 |

四项留内核但按模块组织；模块化的意义在编译期可替换，不在运行期。

### 4.2 三项机制与两条通道

| 项 | 类型 | 说明 |
|---|---|---|
| 上下文 | 机制 | 插件访问共享环境的唯一入口，内核注入 |
| 效应账本 | 机制 | 每插件一份，只增不改，不落盘，倒序撤销 |
| 配置调和 | 机制 | 不是第五项服务，是服务④的执行方式 |
| 装载通道 | 通道 | `dlopen` 或拉起侧车；动态库装卸必须串行 |
| 管理端口 | 通道 | 只绑回环，首帧口令认证 |

### 4.3 为什么不把服务做成插件

路由与事件是互调用的数据结构本身，做成插件等于把门装在别的插件里；门禁与路由共用同一张方法表，拆开无收益；依赖解析驱动装载器，属特权操作，还要解决「谁先加载它」。代价是内核不可运行期替换，靠模块化缓解。

## 5. 进程与线程模型

### 5.1 四类进程

| 进程 | 生命周期 | 崩溃后果 |
|---|---|---|
| 主进程（内核 + 进程内插件） | 常驻 | 全部功能停止 |
| 侧车 ×N（含 core-ui） | 随插件装卸 | 只有该插件失效 |
| 命令行 | 一次命令即退出 | 无 |
| 窗口视图（可选） | 用户开关 | 无 |

core-ui 走侧车：界面是最常改、最易出 bug 的部分，放进最需要稳定的进程是反着来。

### 5.2 主进程内的线程

| 线程 | 数量 | 能否改内核状态 |
|---|---|---|
| 内核线程 | 1 | 唯一可以 |
| IO 线程 | 2 | 不能，请求投给内核线程 |
| 工作线程池 | CPU 核数 − 3，最少 2 | 不能，变更投给内核线程 |
| 侧车监控线程 | 1 | 不能，退出事件投给内核线程 |

**硬约束**：`dlopen` 与 `dlclose` 只在内核线程且串行——装载表只有内核线程能改。

### 5.3 读路径与写路径

| 路径 | 谁执行 | 加锁 | 延迟 |
|---|---|---|---|
| 读：查路由、查订阅、查能力、读自己的账本 | 任意线程 | 不加 | 纳秒到微秒 |
| 写：注册、订阅、记账、改装载表、装卸 | 只有内核线程，先入队 | 不加（单线程） | 微秒到毫秒 |

读不加锁靠**不可变快照**：内核线程改表时构造新表，原子换指针；读线程继续读旧快照。C++17 用 `shared_ptr` 配合 `atomic_load` / `atomic_store`。

一次同进程调用 = 一次原子读指针 + 两次哈希查找 + 一次函数指针调用，不跨线程。这解释了为什么不用「每服务一把锁」：加锁方案读操作要抢锁，热路径上会把 1 微秒吃掉。

C++20 取消了 `atomic_load(shared_ptr)` 这组自由函数。当前 C++17 可用；升级时改手写引用计数或 `shared_mutex`，后者要重测 LING-REQ-089。

### 5.4 崩溃与失效边界

| 失效点 | 连带 | 能否恢复 |
|---|---|---|
| 侧车崩溃 | 只有该插件 | 能，撤销效应后按策略重启 |
| 进程内插件崩溃 | Windows 可捕获记录；Linux 与 Android 只能终止整进程 | Windows 靠外部守护；其他平台整体退出 |
| 内核线程崩溃 | 全部停止 | 只能重启宿主 |
| 管理端口断开 | 无 | 重连 |
| 动态库卸载失败 | 标记「已卸载但内存未释放」 | 重启宿主才彻底释放 |

进程内崩溃在 Linux 与 Android 不可捕获，是平台事实。已定的三条措施：

| 措施 | 内容 |
|---|---|
| 外部守护 | systemd、计划任务或启动脚本看护，退出后自动拉起 |
| 易崩插件改侧车 | 处理二进制数据、解析外部输入、调用第三方库的插件优先走侧车 |
| 崩溃留证 | 崩溃时先把调用栈与插件编号写入 `logs/`，再终止进程 |

Windows 的捕获手段定为向量化异常处理（`AddVectoredExceptionHandler`），能在捕获点拿到线程与模块信息。LING-REQ-116 已补入 01。

## 6. 状态与数据布局

### 6.1 内存态

路由表、订阅表、能力表（三者都是快照）、装载表、依赖图、每插件一份的账本、调和计划。

插件不得在内存保留跨调用状态——这是热更新成立的前提。

### 6.2 落盘

| 位置 | 内容 |
|---|---|
| `registry.json` | 管理端口、禁用名单、能力撤销名单、ui_port |
| `session.json` | 管理端口口令，0600，每次启动重新生成 |
| `logs/kernel-YYYY-MM-DD.log` | 内核日志，按天分文件 |
| `plugins/<编号>/plugin.toml` | 清单；存在即视为已安装 |
| `plugins/<编号>/<编号>.so` 或 `.dll` | 插件原件，重载时从这里复制 |
| `plugins/<编号>/<编号>.<序号>.so` | 私有副本，装载时复制、卸载时删除 |
| `plugins/<编号>/data/` | 插件数据，卸载默认保留 |

宿主只写三处：`registry.json`、`session.json`、`logs/`。

### 6.3 数据根目录

| 平台 | 默认位置 |
|---|---|
| Windows | `%APPDATA%\ling` |
| Linux | `~/.local/share/ling` |
| Android | 应用私有目录 |

默认系统标准目录；`--data-dir` 可切到程序目录下的 `data/`，用于整个文件夹拷走即迁移。切换不自动迁移数据。

## 7. 关键流程的架构视图

### 7.1 安装插件

校验清单 → 拷贝到插件目录 → 建图查环 → 算计划 → 按拓扑序装载激活。成环则回滚到安装前；依赖缺失时插件停在待激活，安装本身仍算成功。

### 7.2 卸载插件

停下游 → 调 `on_deactivate` → 账本倒序撤销 → 移出装载表并删安装工件、保留 `data/` → 触发调和。撤销失败记录后继续，最后报「卸载不完整 + 清单」。

### 7.3 热更新

七步固定。三处要点：窗口内调用立即返回 `E_PLUGIN_MISSING` 不排队；复制私有文件名再打开、原件保留；新版失败则回滚旧版与下游。

### 7.4 调和与回滚

配置变化 → 重建依赖图 → 校验（版本、环、能力）→ 算计划 → 执行（激活按拓扑序、停用按反拓扑序）→ 收敛。三条性质：原子性、可观察、可取消；200 毫秒内连续变化合并成一次。

## 8. 横切关注点

### 8.1 六道闸门

| 闸门 | 位置 | 失败错误码 |
|---|---|---|
| 清单校验 | 装载通道 | `E_MANIFEST_INVALID`、`E_API_MISMATCH` |
| 能力取值校验 | 装载通道 | `E_CAPABILITY_UNKNOWN` |
| 命名空间校验 | 路由注册 | `E_NAMESPACE_VIOLATION` |
| 能力注册校验 | 门禁 | `E_CAPABILITY_DENIED` |
| 能力调用校验 | 门禁 | `E_CAPABILITY_DENIED` |
| 首帧认证 | 管理端口 | `E_AUTH` |

前五道都在内核线程串行执行，没有并发绕过的窗口。

### 8.2 可观测

日志分两层：

| 层 | 谁写 | 可卸载吗 | 谁看 | 依赖 |
|---|---|---|---|---|
| 内核日志 | 内核 | 不可 | `logs --kernel` 直读文件 | 不依赖插件 |
| 插件日志 | 插件经 `Context` 交出 | core-log 可卸 | `logs <编号>` 经 core-log | 未装时落 stderr 并带前缀 |

内核日志必记六类：启停、状态变化、装卸与调和每步、被拒操作与错误码、侧车启停退出、崩溃栈（118）。四级默认 info，debug 才记调用（121）。写入异步有界，满了丢弃并计数（123）。

错误码按来源分族；内核广播 `kernel.plugin.state` 与 `kernel.plan.step`。状态变化只以事件为准，不从日志推断（112）。

### 8.3 平台差异

三处：进程内崩溃捕获手段不同；动态库后缀与格式不同、不跨平台复用；Android 默认关闭管理端口与命令行。

## 9. 架构决策记录

### A-1 双向装载形态

进程内用 C++ 动态库，其他语言走侧车。被否：全进程内（非 C++ 无法参与）、全侧车（进程内调用退化到百微秒级）。形态不变，语言由 Rust 改为 C++。

### A-2 内核只做四项服务

配置存储、作业调度、日志做成内置插件。被否：全塞内核（违背 P1）、只留路由与事件（遇特权与引导问题）。

### A-3 内置插件从属宿主

源码放 `main/builtin-plugins/<编号>/`，同规范、可卸载。被否：各自独立仓库（版本匹配复杂）、混进内核（获得特权通道）。

### A-4 首轮即实现热更新

代价：要处理动态库重复装载的映射泄漏，内存阈值必须放宽。理由：与可逆效应共用账本，后做要返工。

### A-5 插件状态放持久文件

内存不保留跨调用状态。被否：内存状态加序列化迁移（格式兼容与失败恢复复杂）。

### A-6 命令行经管理端口

被否：走 core-ui 网页端口（界面坏了无法修界面）、命令行自己拉起进程（管不到已运行的宿主）。

### A-7 采纳论文机制的务实子集

采纳可逆效应、响应式调和、上下文范式，不做形式化演算。代价：卸载是否干净靠实现与测试，没有数学保证。

### A-8 core-ui 走侧车

用 C++ 写成独立可执行文件。被否：进程内（界面崩溃带走宿主，01 无条款可约束）、侧车用 Python（Android 要多带约 30 MB）。代价：取数据过一次套接字（50–200 微秒，界面场景可忽略）、多一个可执行目标、调试要 attach。

### A-9 多平台同一套插件接口

平台差异只在装载与产物层。代价：接口只能用三端都支持的能力。

### A-10 内核线程串行改状态，读路径走快照

被否：每服务一把锁（读也要抢锁，达不到 1 微秒，且死锁与锁顺序要自己保证）、全部操作排到内核线程（一次调用两次切换）。代价：写延迟升到微秒级，快照短暂多占一份内存。

## 10. 架构约束与风险

### 10.1 五条硬约束

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | 插件之间不直接链接 | 卸载一个会让另一个崩溃 |
| 2 | 动态库装卸只在内核线程且串行 | 装载表与内存状态不一致 |
| 3 | 插件不留跨调用内存状态 | 重载后状态丢失 |
| 4 | 宿主与进程内插件同编译器族、同运行时链接方式 | 链接成功但运行崩溃 |
| 5 | 状态变化只以事件为准，界面与命令行不各自维护副本 | 三处不一致，无从判断谁对 |

### 10.2 风险登记册

只做设计时分析；运行时处置归 09 运行时预案。

| # | 风险 | 设计对策 |
|---|---|---|
| 1 | 动态库重复装载的映射泄漏 | 私有文件名加载；阈值放宽并提示重启；长稳覆盖 |
| 2 | 进程内插件崩溃不可恢复 | 易崩插件改侧车；外部守护拉起 |
| 3 | 快照替换过于频繁 | 注册集中在激活期；调和合并 200 毫秒内变化 |
| 4 | 侧车与控制面协议分裂 | 帧格式统一定义，进程内只省掉序列化 |
| 5 | 插件绕过上下文 | 审查清单；`doctor` 检查可观测迹象 |
| 6 | 撤销函数写错导致卸载报错 | 账本逐条容错并报清单 |
| 7 | 内核升级导致插件不兼容 | 支持 api N 与 N-1，不匹配只影响该插件 |
| 8 | core-ui 崩溃后界面不自恢复 | 默认 `on-crash`；命令行不依赖界面 |

| 4 | Windows 崩溃捕获机制 | 向量化异常处理 |
| 5 | 快照替换在 C++20 的替代 | 当前用 C++17；升级时改手写引用计数或 `shared_mutex`，后者要重测 089 |
