## 2. 仓库布局

### 2.1 目录总览

```
ling/
├── CMakeLists.txt / CMakePresets.json / vcpkg.json / vcpkg-configuration.json
├── .clang-format / .clang-tidy
├── docs/          文档（含 brief/）
├── main/          宿主：include/ling/、src/（七个模块）、builtin-plugins/、app/
├── plugins/       业务插件源码（demo-a、demo-b）
├── tests/         unit/、acceptance/，与生产代码完全分离
├── other/         cmake/、tools/、stu/
├── run/           构建产物，不入库
└── old/           历史版本，只读
```

两个 `plugins/` 的区别：仓库里的是**源码**，`<数据根>/plugins/` 是**安装目录**。

### 2.2 内核七个模块

| 模块 | 职责 | 依赖 | 对应 04 |
|---|---|---|---|
| `kernel` | `Kernel` 对象、快照、请求队列、启停顺序 | 无 | 04/01 §2 至 §4 |
| `route` | 路由表、注册校验、调用分派 | `kernel` | 04/01 §5 |
| `event` | 订阅表、主题匹配、派发与超时 | `kernel` | 04/01 §6 |
| `gate` | 能力集、两处校验、撤销名单 | `kernel` | 04/01 §7 |
| `depend` | 依赖图、版本匹配、环检测、计划 | `kernel`、`loader` | 04/04 |
| `loader` | 清单校验、两轨装载、侧车客户端 | `kernel`、`route`、`event`、`gate` | 04/02、04/05 |
| `log` | 内核日志、异步队列、级别 | `kernel` | 04/01 §9 |

骨架单列，因为它被其余六个依赖；混进业务模块会退化成环。

### 2.3 依赖规则

单向，禁止成环：`kernel` ← 六个模块；额外允许 `depend → loader` 与 `loader → route/event/gate`。

由 CMake 在配置阶段检查，不靠人看目录。

### 2.4 文件与命名

类型 `PascalCase`、函数 `snake_case`、成员后缀下划线、常量 `k` 前缀、文件 `snake_case.cpp`、单文件不超过 500 行、单函数不超过 60 行、注释写为什么。内部实现放 `detail/`，不出现在对外头文件。

### 2.5 两个对外头文件

| 文件 | 语言 | 内容 |
|---|---|---|
| `include/ling/plugin_api.h` | 纯 C | 函数表、描述符、入口函数声明、能力位与错误码常量 |
| `include/ling/sdk.hpp` | C++17 | 薄封装：`ctx` 包成类、错误码转换、`LING_PLUGIN` 宏 |

`plugin_api.h` 不包含任何 C++ 头，要能被 `ctypes`、`bindgen`、`@cImport` 直接解析——这是「保留语言口子」的具体做法。

## 3. 构建系统

### 3.1 目标划分

| 目标 | 类型 | 产物 |
|---|---|---|
| `ling_core` | 静态库 | 七个模块合成一个库 |
| `ling` | 可执行 | 命令行入口 |
| `core-ui` | 可执行 | 侧车形态内置插件 |
| `core-settings` 至 `core-log` | 动态库 | 四个进程内内置插件 |
| `demo-a` | 动态库 | 最小示例 |
| `demo-b` | 可执行 | 侧车示例 |
| `ling_unit` / `ling_acceptance` | 可执行 | 测试运行器 |

`ling_core` 用静态库：宿主与插件不该各带一份内核代码。

### 3.2 统一编译选项

由 `other/cmake/LingOptions.cmake` 提供三个函数：`ling_set_standard`、`ling_set_warnings`、`ling_set_hardening`。所有目标必须调用。

| 项 | MSVC | Clang / NDK |
|---|---|---|
| 标准 | `/std:c++17` | `-std=c++17` |
| 警告 | `/W4` | `-Wall -Wextra -Wpedantic` |
| 视为错误 | `/WX` | `-Werror` |
| 运行时库 | `/MD` | 默认 |
| 异常模型 | `/EHsc` | 默认 |
| 帧指针 | `/Oy-` | `-fno-omit-frame-pointer` |
| 栈保护 | `/GS` | `-fstack-protector-strong` |

Debug 与 Release 只差三处：代码生成等级、调试信息、`NDEBUG`。其余完全一致。

不关闭 RTTI：`std::variant` 需要它，而请求队列用到了 `std::variant`。

### 3.3 依赖与锁文件

| 依赖 | 用途 |
|---|---|
| Catch2 v3 | 测试，只链接测试目标 |
| toml++ | 解析 `plugin.toml`，header-only |
| nlohmann/json | 协议帧、错误结构、日志行 |

三项在 `vcpkg.json` 声明，版本由 `vcpkg-configuration.json` 的 baseline 锁定。不锁版本会导致不同时间构建出不同依赖，出问题无法复现。

新增依赖先说明用途、体积、维护影响，获同意后写入。`core-ui` 的 HTTP 依赖到 S6 再定。

### 3.4 CMake Presets

| Preset | 平台 | 类型 | 说明 |
|---|---|---|---|
| `win-debug` | Windows | Debug | 默认开发，开 ASan |
| `win-release` | Windows | Release | 打包 |
| `linux-debug` | Linux | Debug | 开 ASan 与 UBSan |
| `linux-release` | Linux | Release | 打包 |
| `android-release` | Android | Release | NDK，只出产物 |

Presets 固定工具链、构建目录 `run/build/<preset>/`、导出 `compile_commands.json`。

### 3.5 产物落点

宿主与内置插件到 `run/<preset>/`；插件产物复制到 `run/<preset>/plugins/<编号>/`；侧车到该插件的 `sidecar/` 子目录；测试到 `run/<preset>/tests/`。

构建完直接 `run/<preset>/ling serve --data-dir run/<preset>/data` 可跑，不需手工拷文件。

## 4. 质量门

五项，由 `other/tools/precommit.sh` 串联。

### 4.1 警告视为错误

由 `ling_set_warnings` 提供，编译通过即零警告。触发警告只能改代码，或用局部 `#pragma` 并写明理由。

### 4.2 消毒器

ASan 查越界与释放后使用，UBSan 查未定义行为，只在 Debug 开。

| 平台 | 开启 | 限制 |
|---|---|---|
| Windows | `/fsanitize=address` | 无 UBSan |
| Linux | `-fsanitize=address,undefined -fno-sanitize-recover=all` | 全支持 |
| Android | 同 Linux，只在设备上跑 | —— |

`-fno-sanitize-recover=all` 让 UBSan 遇错即停，否则测试不会失败。Windows 缺 UBSan 的缺口靠 Linux 侧同名测试兜住。

### 4.3 静态分析

`clang-tidy` 启用两组规则：`bugprone-*`（悬垂引用、误用 `sizeof`、类型混用）与 `cppcoreguidelines-*`（所有权与生命周期）。

不启用 `modernize-*`（会要求尚未掌握的特性）与 `readability-*`（格式交给 clang-format）。

### 4.4 格式化

`clang-format`，4 空格缩进、列宽 100、左括号不换行、指针星号靠类型、include 按分组字母序。

不合规即失败：`clang-format --dry-run --Werror`。

### 4.5 提交前脚本

| 序 | 检查 |
|---|---|
| 1 | `check_docs.py`（两版一致、表格、禁用词、乱码） |
| 2 | `clang-format --dry-run --Werror` |
| 3 | Debug 构建 |
| 4 | `ling_unit` |
| 5 | `clang-tidy` |

验收脚本不进这一轮：它要起真实进程，放在切片完成时跑。

### 4.6 测试与生产代码的边界

| 规则 | 要求 |
|---|---|
| 生产代码不含测试框架 | `main/src/`、`main/include/` 里不出现 `catch2/` |
| 测试不进生产目录 | 全部放 `tests/` |
| 不为测试改可见性 | 不用 `friend`、不用 `#define private public`、不加 `#ifdef TESTING` |

测内部状态走公开只读接口：`Kernel::snapshot()` 已够用。

代价：内部函数（如不变式校验）只能通过公开行为间接测。这个代价接受——为可测性暴露私有实现，会长期把结构带偏。

纯函数例外：版本匹配、主题匹配、环检测、清单 id 校验放在独立头文件直接暴露，测试直接调。

## 5. 开发顺序

### 5.1 切片表

| 片 | 目标 | 验证方式 |
|---|---|---|
| S0 | 骨架能编能跑 | 三平台构建通过；故意写未使用变量，断言构建失败 |
| S1 | 最小闭环 | 装 `demo-a` → activated → 调 `demo-a.ping` 收到 `pong` |
| S2 | 上下文与账本 | 注册三个方法后卸载，账本倒序撤销，路由表清空 |
| S3 | 依赖与调和 | 先装依赖方再装被依赖方，前者自动激活；成环被拒且不留残件 |
| S4 | 热更新 | 100 次重载；新版 activate 失败时回滚 |
| S5 | 侧车 | 起 `demo-b` 调通；强杀断言 `crashed` 与 2 秒重启 |
| S6 | 内置插件与界面 | 界面里完成装卸启停；成环时 `doctor` 退出码 1 |

### 5.2 每片的出口条件

四条同时满足：验证跑通并记入 `docs/log/`；新增公开接口有测试且负向用例不少于正向的一半；`precommit.sh` 五项全过；实现与 04 一致。

第四条最容易松：代码写着发现 04 有问题时，回去改 04 并记变更，不许「代码这样更顺手」。

### 5.3 不做什么

按 `02` §8.1：不做模板元编程、多继承、运算符重载（除显然语义）、宏定义控制流、全局可变状态、单文件超 500 行。

「先做出来再整理」在这里不成立。

## 6. 关键类型落点

### 6.1 04 的类型对照

| 04 的类型 | 头文件 |
|---|---|
| `Kernel`、`Snapshot`、`Request`、`RequestQueue` | `src/kernel/` 下同名头文件 |
| `LedgerEntry`、`LedgerSegment`、`Context` 实现 | `src/kernel/ledger.hpp`、`context.hpp` |
| `RouteEntry`、`RouteTable`、注册与调用 | `src/route/route_table.hpp`、`method_router.hpp` |
| `SubEntry`、`SubTable`、匹配与派发 | `src/event/sub_table.hpp`、`event_bus.hpp` |
| `CapEntry`、`CapTable`、两处校验 | `src/gate/capability.hpp`、`gate.hpp` |
| `LoadEntry`、`PluginState`、`Track` | `src/loader/load_entry.hpp` |
| 清单解析、两轨装载、侧车客户端 | `src/loader/manifest.hpp`、`loader.hpp`、`sidecar_client.hpp` |
| `DepGraph`、`Plan`、版本匹配、调和 | `src/depend/plan.hpp`、`version.hpp`、`reconcile.hpp` |
| 日志器 | `src/log/logger.hpp` |

账本与 `Context` 放 `kernel` 模块：它们被三个模块共同依赖，单列会形成第二个「所有人都依赖」的模块。

### 6.2 头文件的三条规矩

头文件不写实现（除 `constexpr` 与内联小函数）；`detail/` 类型不出现在对外头文件；模块间只 include 对方的 `*.hpp`，不 include `detail/*.hpp`。

### 6.3 可单独测的纯函数

| 函数 | 位置 | 测什么 |
|---|---|---|
| `version_satisfies` | `src/depend/version.hpp` | 四种写法与边界 |
| `topic_matches` | `src/event/sub_table.hpp` | 精确、前缀通配、`*` |
| `find_cycle` | `src/depend/plan.hpp` | 有环、无环、多环 |
| `validate_manifest_id` | `src/loader/manifest.hpp` | 格式、长度、大小写、保留前缀 |

这四个在 S0 就能写完测试，是那时唯一有实际逻辑的代码。

## 8. 调试方法

### 8.1 日志

| 场景 | 参数 |
|---|---|
| 日常开发 | 默认 `info` |
| 查「调用没到」 | `--log-level debug`，记每次调用摘要 |
| 只看内核自身 | `logs --kernel`，不依赖插件 |
| 追一次操作全链 | `grep <trace id>` |

trace id 由命令行发起时生成，随请求传到侧车；`install` 输出里带该 id。

### 8.2 Windows 崩溃转储

异常处理器先写调用栈地址到内核日志，再 `MiniDumpWriteDump` 生成 `.dmp` 到 `<数据根>/logs/`，然后按 `02` §5.5 标记故障、拒调用、撤销效应。

解析：`cdb -z ling.dmp -y run/win-debug -c "kb; q"` `[未验证]`。pdb 必须与二进制匹配，所以打包时保留 pdb 并与版本号一起归档。

### 8.3 侧车附加调试

| 场景 | 做法 |
|---|---|
| C++ 侧车启动即崩 | `main()` 首行 `raise(SIGTRAP)`，用调试器启动 |
| 运行时看状态 | `gdb -p <pid>` 或 VS 附加到进程 |
| Python 侧车 | 入口加 `debugpy.listen(5678); debugpy.wait_for_client()` |

侧车 pid 写入 `registry.json` 的调试字段，不通过命令行暴露。

### 8.4 常见故障对照

| 现象 | 先查 |
|---|---|
| 装上但 `deactivated` | `plugins` 的「未满足原因」列 |
| `E_MANIFEST_INVALID` | `logs --kernel` 里 message 的字段名 |
| `E_METHOD_MISSING` | 方法名是否带前缀、注册是否在 activate 之后 |
| `E_CAPABILITY_DENIED` | `plugins --json` 的生效能力 |
| 链接通过但启动即崩 | 宿主与插件是否同一 Preset 构建 |
| 热更新后行为没变 | `plugins/<编号>/` 下副本序号是否递增 |
| 侧车起来又退出 | 侧车 stderr 与握手记录 |
| 内存持续增长 | `doctor` 看账本条目与副本数量 |
| 界面打不开 | `registry.json` 的 `ui_port`；core-ui 状态 |
| 命令行连不上 | 两侧 `--data-dir` 是否相同 |

## 9. 写一个最小插件

### 9.1 目录与清单

```
plugins/demo-a/
├── plugin.toml
└── demo_a.cpp
```

```toml
id = "demo-a"
version = "1.0.0"
api = "1"
name = "示例插件 A"
description = "最小可运行插件"
capabilities = []
```

### 9.2 入口函数

```cpp
#include <ling/sdk.hpp>

namespace {

int32_t ping(void* ctx, const uint8_t* args, size_t args_len,
             uint8_t** out, size_t* out_len) {
    static const char kPong[] = "pong";
    *out_len = sizeof(kPong) - 1;
    *out = reinterpret_cast<uint8_t*>(const_cast<char*>(kPong));
    return 0;
}

}  // namespace

LING_PLUGIN("demo-a", "1.0.0") {
    auto* c = ling::context();
    return c->register_method("demo-a.ping", &ping, nullptr, 0);
}
```

三个要点：方法名必须带 `demo-a.`；C ABI 层要求撤销函数非空，SDK 对 `nullptr` 会补一个「调 `unregister_method`」的代撤；返回的缓冲区由插件申请、插件释放。

### 9.3 构建

在 `plugins/CMakeLists.txt` 加一行：

```cmake
add_ling_plugin(demo-a SOURCES demo_a.cpp)
```

该宏自动做四件事：套用统一选项、命名产物为 `<编号>.dll` 或 `.so`、复制到 `run/<preset>/plugins/demo-a/`、同时复制 `plugin.toml`。

插件作者不写编译选项。

### 9.4 安装与验证

```bash
./run/linux-debug/ling serve --data-dir ./run/linux-debug/data &      # [未验证]
./run/linux-debug/ling install ./run/linux-debug/plugins/demo-a --data-dir ./run/linux-debug/data  # [未验证]
./run/linux-debug/ling plugins --data-dir ./run/linux-debug/data      # [未验证] 应为 activated
ctest -R l2_call   # [未验证] 命令行没有 call 子命令；调用由调用方插件发起，期望 pong
```

### 9.5 常见错误

| 现象 | 原因 |
|---|---|
| `E_MANIFEST_INVALID` 说缺字段 | 少写 `name` 或 `api` |
| `E_API_MISMATCH` | `api` 写成 `"2"` 而宿主支持 `"1"` |
| `E_NAMESPACE_VIOLATION` | 方法名写成 `ping` |
| 装载成功但 `call` 找不到 | 注册失败但没检查返回值 |
| 「不是有效的 Win32 程序」 | 插件与宿主位数不一致 |
| 崩溃在 `register_method` | `ctx` 不是宿主给的，或用了别人的 |
