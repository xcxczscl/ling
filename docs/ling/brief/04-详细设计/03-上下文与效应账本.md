## 2. 上下文对象

### 2.1 谁创建、什么时候注入

内核在激活前创建，经 `context_alloc` 交给插件，插件拿到的是不透明句柄 `void* ctx`。

| 时机 | 动作 |
|---|---|
| 激活前 | 创建并绑定 `plugin_id` 与 `generation`，账本新开一代 |
| 激活中 | 插件经函数表调用，内核按 `ctx` 找到插件 |
| 停用后 | 标记失效，再用同一 `ctx` 一律返回 `E_PLUGIN_MISSING` |

停用后必须失效：插件的异步回调会在停用后才触发，`ctx` 若仍有效，它会往已作废的账本里写条目。

### 2.2 完整方法表

| 方法 | 是否产生账本条目 |
|---|---|
| `register_method` / `unregister_method` | 是 |
| `subscribe` / `unsubscribe` | 是 |
| `write_config` | 是 |
| `call` / `emit` | 否 |
| `data_dir` | 否 |
| `ledger` | 否 |
| `last_error` | 否 |

核心约束：**只有改共享状态的方法入账，调用与广播不入账。**

### 2.3 生命周期

装载 → 创建 `Context` → activate → 使用 → 停用：撤销账本、`ctx` 失效、释放。

卸载 = 停用流程 + 移出四张表 + 删文件；重载 = 旧 `ctx` 失效 + 新 `ctx` 绑新 `generation`。

### 2.4 不能做什么

不能自己构造 `Context`；不能拿别人的 `ctx` 调方法（内核反查编号，越权返回 `E_CAPABILITY_DENIED`）；不能绕过 `Context` 改全局状态（宿主检测不到也不还原）；不能在失效后继续调用；不能通过 `ledger()` 改账本。

## 3. 账本结构

### 3.1 条目字段

| 字段 | 含义 |
|---|---|
| `seq` | 段内递增，从 1 开始，不重复 |
| `kind` | 五类效应之一 |
| `desc` | 人可读描述，含被改对象的名字 |
| `undo` / `undo_ctx` | 插件侧撤销函数与上下文，宿主代撤时为空 |
| `undo_mode` | 0 = 调插件函数，1 = 宿主代撤 |

### 3.2 五类效应

| 类别 | 何时产生 | 撤销动作 | 谁执行 |
|---|---|---|---|
| `MethodRegistered` | 注册方法成功 | 从路由表删条目 | 宿主 |
| `EventSubscribed` | 订阅成功 | 从订阅表删 `sub_id` | 宿主 |
| `ConfigWritten` | 配置写入成功 | 恢复旧值，原本没有则删键 | 宿主调 core-settings |
| `SidecarStarted` | 侧车进程起来 | 结束进程 | 宿主 |
| `DeactivateHook` | 登记停用回调 | 调该回调 | 插件 |

线程与文件句柄不单独入账：它们随进程或库的生命周期结束，宿主无法代为管理。

### 3.3 按激活代分段

插件会被反复停用与激活。账本若只增不减，几十次激活就撞上 10000 条上限，而每一代的效应其实早撤销完了。

| 规则 | 内容 |
|---|---|
| 新代开始 | 新建段，`generation` 取当前装载代号，`count` 归零 |
| 撤销 | 只撤当前段，倒序 |
| 撤销完成 | 整段丢弃，不保留历史 |
| `seq` | 段内 1 至 10000，换段后重新从 1 开始 |
| 查历史 | 看内核日志，不看账本 |

### 3.4 容量与越界

上限 10000 条。第 10001 次登记：

1. 返回 `E_LEDGER_FULL`。
2. 本次修改不生效——**先检查容量再改表**。
3. 已登记的前 10000 条不受影响。

顺序必须如此：先改表再记账的话，容量满时表已改、账没记，这个效应永远撤不掉。

### 3.5 单写多读

| 操作 | 谁做 | 保证方式 |
|---|---|---|
| 追加 | 只有内核线程 | 检查容量 → 写 `entries[count]` → `count.fetch_add(1, release)` |
| 读 | 任意线程 | `count.load(acquire)` 后只读前 `count` 条 |
| 换段 | 内核线程 | 拿 `swap_mu` 短暂独占 |

读者只会看到「某时刻之前的全部条目」，不会看到写了一半的条目。

## 4. 撤销

### 4.1 倒序规则

严格按 `seq` 递减执行。倒序不是随意选择：效应之间有依赖，正序撤销会出现「先删配置、再删方法」的中间窗口，而方法正指向那个键。

### 4.2 单条失败

1. 记 `E_UNDO_FAILED` 与 `seq`、`desc` 到内核日志。
2. 继续执行剩余条目。
3. 最终返回 `E_UNINSTALL_INCOMPLETE`，`detail` 列出未撤销条目。

不中断的理由：让其余效应卡住，会让停用变成「既没停干净、也没恢复原状」的状态。

### 4.3 重复撤销的行为

同一条目撤两次：第二次检查已完成标记，直接返回成功。撤销期间再登记效应：拒绝，返回 `E_PLUGIN_MISSING`。段已丢弃后再撤：返回成功，不报错。

### 4.4 停用、卸载、重载的差别

| 操作 | 撤销 | 段 | 文件 | 四张表 |
|---|---|---|---|---|
| 停用 | 全部 | 丢弃 | 保留 | 保留条目，状态 `Deactivated` |
| 卸载 | 全部 | 丢弃 | 删工件留 `data/` | 移出全部条目 |
| 重载 | 先按停用撤销，新版装载后建新段 | 旧弃新建 | 换产物 | 先移旧再加新 |

三者共用同一套撤销实现。

## 5. 撤销函数的三种表达

| 情形 | 撤销函数来源 | `undo_mode` |
|---|---|---|
| 进程内插件注册方法或订阅 | 调用时一并交出的 `undo_fn` | 0 |
| 进程内插件登记停用回调 | 登记的函件，宿主停用时调 | 0 |
| 侧车插件注册方法或订阅 | 交不出函数指针，只做语义声明 | 1，宿主代撤 |
| 侧车插件写配置 | core-settings 记旧值 | 1 |
| 宿主启动侧车 | 结束进程 | 1 |

侧车交不出函数指针，是进程边界决定的。它只要如实声明，撤销由宿主完成；但**清理自己的数据与线程仍要在 `deactivated` 里做**，宿主代撤的只是表里的登记。

## 6. 数据目录与配置写入

### 6.1 `data_dir()`

返回 `plugins/<编号>/data/` 的绝对路径，UTF-8。内核保证该目录在 activate 前已存在，插件直接写文件即可。

跨调用状态必须放这里，内存不留（`LING-REQ-057`）：

| 状态 | 放哪 |
|---|---|
| 索引、缓存、游标 | `data/` 下的文件 |
| 连接、句柄、线程 | 内存，随激活创建随停用释放 |
| 配置项 | 经 `write_config` 交给 core-settings |

### 6.2 配置写入

1. 键名必须以 `<编号>.` 开头，越权返回 `E_NAMESPACE_VIOLATION`。
2. 写前读旧值，把旧值记进账本，再写新值。
3. 实际存储由 core-settings 完成，它被卸载时返回 `E_PLUGIN_MISSING`。
4. 值是不透明字节串，core-settings 不解析。

第 2 步是可撤销的关键：撤销时写回旧值，原本不存在则删键。

### 6.3 配置与数据的分界

需要被别的组件看到、或需要可撤销的，走配置；只属于自己的中间状态，走文件。

卸载时配置随账本还原，`data/` 默认保留；配置按编号前缀隔离，`data/` 完全私有。

## 7. 隔离与越权

### 7.1 账本互不可见

`ledger()` 只返回自己的段，接口上没有「按编号查他人账本」的入口。要查别的插件，只能看内核日志。

### 7.2 命名空间隔离

| 对象 | 违反时 |
|---|---|
| 方法名不带 `<编号>.` 前缀 | `E_NAMESPACE_VIOLATION` |
| 事件主题不带前缀或用 `kernel.` | `E_NAMESPACE_VIOLATION` |
| 配置键不带 `<编号>.` 前缀 | `E_NAMESPACE_VIOLATION` |
| 注销他人方法 | `E_CAPABILITY_DENIED` |

### 7.3 检测不到的情形

插件直接写文件、改全局变量、起子进程、在 `data/` 外建目录，宿主都不检测也不还原。

`doctor` 只报告可观测迹象：越权注册尝试、未撤销条目、命名空间违规。报告里不写「已还原手工操作」。

这条定了项目边界：**ling 不是沙箱，插件是可信代码。宿主的能力限于拒绝、记录、报告，不包括阻止与修复。**

## 8. 时序

### 8.1 注册并登记

校验六步 → 容量检查（满则 `E_LEDGER_FULL`，表不变）→ 复制快照插入 → 校验不变式换快照 → 追加账本 → 返回。

容量检查必须在改表之前。

### 8.2 订阅并登记

校验五步 → 容量检查 → 分配 `sub_id` → 改订阅表换快照 → 追加账本 → 返回 `sub_id`。

### 8.3 停用撤销

取当前段（`count = n`）→ 从 n 倒序到 1，按 `undo_mode` 分派 → 失败记 `E_UNDO_FAILED` 并继续 → 整段丢弃、新建空段 → `Context` 失效 → 有失败项则返回 `E_UNINSTALL_INCOMPLETE`。

### 8.4 撤销失败

失败条目 → 日志记 error（含 `seq`、`desc`、插件编号）→ 继续下一条 → 汇总未撤销清单 → **状态仍然改 `Deactivated`**。

状态仍然改是刻意的：留在 `Deactivating` 会一直占着依赖图里的位置，下游永远无法激活。

|---|---|---|
