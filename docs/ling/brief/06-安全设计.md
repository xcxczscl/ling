# ling 06 安全设计（简要版）

> 状态：初定 | 最后更新：2026-10-29
> 依据：`docs/ling/01-需求规格.md` §3.3、§3.8、§4.5；`docs/ling/02-技术选型.md` §2.2

本文是 `docs/ling/06-安全设计.md` 的简要版。

核心结论：**跨用户能防，同用户不能防。** 能力门禁是审计钩子，不是沙箱。

---

## 1. 目的与范围

### 1.1 覆盖什么

威胁模型与不防清单、管理端口三道防线、侧车握手认证、门禁的真实定位、路径与 zip 防护、日志与转储的取舍、凭证放置、供应链措施。

### 1.2 不覆盖什么

| 内容 | 理由 |
|---|---|
| 恶意插件隔离 | 不在威胁模型内，插件可信 |
| 已被攻破的本机 | 同用户权限无法防 |
| 网络传输加密 | 无远程访问，不引入 TLS |
| 多用户权限分级 | 单用户设计 |
| 密码学实现 | 只用系统随机源，不自研 |

### 1.3 三条前提

插件可信（`02` §2.2）；单机单用户（`00` §2.4）；无远程入口，端口只绑回环（`01` 115）。任一条不成立，本文结论要重做。

## 2. 威胁模型

### 2.1 信任边界

| 层 | 信任程度 |
|---|---|
| 内核 | 完全信任（既是保护对象也是防线执行者） |
| 插件 | 可信但会出错 |
| 本机其他用户 | 不信任 |
| 本机同用户进程 | **无法防**：权限相同 |
| 外部网络 | 不信任，但没有入口 |

第四行最容易被忽略：同账户的其他程序能读 `session.json`、能改插件文件、能 attach 到宿主。

### 2.2 威胁清单

| # | 威胁 | 覆盖 | 措施 |
|---|---|---|---|
| T1 | 局域网或公网访问管理端口 | 是 | 只绑 `127.0.0.1` |
| T2 | 本机其他用户发管理命令 | 是 | 首帧口令 + 0600 |
| T3 | 其他用户读日志与数据 | 部分 | 数据根 0700 |
| T4 | 同用户进程冒充宿主 | 部分 | 无法防，只留痕 |
| T5 | 伪造侧车连上端口 | 是 | 握手口令（本文新增） |
| T6 | 清单用 `..` 或绝对路径越界写 | 是 | 路径校验 + 真实路径确认 |
| T7 | zip 包路径穿越 | 是 | 解压到临时目录后逐项校验 |
| T8 | `--purge` 误删数据 | 是 | 显式参数 + 打印路径 + 二次确认 |
| T9 | 日志泄露内容或口令 | 部分 | 不记载荷原文与口令 |
| T10 | 转储含敏感内存 | 部分 | 0600、不上传、保留 5 个 |
| T11 | 依赖被换成恶意版本 | 是 | baseline 锁版本 |
| T12 | 插件的 Python 依赖有漏洞 | **否** | 插件作者自负 |

### 2.3 明确不防

恶意插件；同账户恶意程序；物理接触；侧信道；拒绝服务（只超时切断，不做配额）；vcpkg 仓库本身被投毒（锁版本只保证版本不变，不保证没被投毒）。

## 3. 管理端口的防线

### 3.1 第一道：只绑回环

监听固定 `127.0.0.1`，不提供配置项。

挡住外部网络与局域网的一切连接；挡不住本机任何进程——回环不区分进程，只区分网络来源。

这条最有效，因为它不依赖口令与权限。也正因如此，拒绝提供「绑 0.0.0.0」的开关：一旦可配，这道防线就降级成「用户记得别开」。

### 3.2 第二道：`session.json` 与口令

| 项 | 规定 |
|---|---|
| 生成 | 每次启动用系统随机源生成 32 字节 |
| 随机源 | Windows `BCryptGenRandom`，Linux 与 Android `getrandom()` |
| 存储 | `<数据根>/session.json`，0600 |
| 校验 | 首帧带 token，**常量时间比较**，失败即断开并记 warn |

权限落地：Linux 创建时就用 `0600`（不是先建再改，中间有窗口）；Windows 设 DACL 只授当前用户，不模拟 POSIX 位。

### 3.3 第三道：数据根权限

整目录 0700 一次解决，不逐个文件设——新加的文件不会因为忘了设而暴露。

`session.json` 最敏感（拿到就能控制宿主），`logs/`、`settings.json`、插件 `data/` 次之。

### 3.4 挡不住的情形与留痕

同用户恶意进程能直接读口令文件。能做的只有留痕：每条命令记来源进程号、按 trace id 全链记录、所有改状态操作都产生日志与事件、没有可关掉的开关。

作用是**事后可查**，不是事前阻止。文档里不能写成「已防护」。

### 3.5 为什么不引入 TLS

端口只绑回环，流量不出本机内核；自签证书的信任、过期、续期对个人工具是纯负担；本机嗅探需要更高权限，而同用户威胁已在 §3.4 承认无法防。

将来真要远程访问，正确做法是在前面放专用代理（SSH 隧道、nginx），把 TLS 交给成熟工具，而不是给管理端口加。

### 3.6 侧车连接的认证（本文补的缺口）

`04/02` §8.4 的握手只校验协议版本与编号，**没有认证**：本机任意进程连上侧车端口发个 `hello` 就能冒充宿主。

补法：

1. 宿主启动侧车时经环境变量 `LING_TOKEN` 传 32 字节随机串，每次重新生成，不落盘。
2. 侧车首帧 `hello` 必须带 `token`。
3. 宿主校验，不符回 `E_AUTH` 并断开。
4. 握手成功后该连接专用，不再校验。

用环境变量而非命令行参数：命令行参数在进程列表里对所有用户可见，环境变量只有同用户与 root 可读。

边界同 §3.4：挡住跨用户，挡不住同用户。

### 3.7 三道防线的合成效果

| 攻击者位置 | 能否控制宿主 | 靠哪道 |
|---|---|---|
| 外部网络、局域网 | 不能 | 回环绑定 |
| 本机其他用户 | 不能 | 口令 + 目录权限 |
| 本机其他用户（侧车端口） | 不能 | 侧车口令 |
| 同用户其他程序 | **能** | 无，只留痕 |
| 用户误操作 | 部分 | `--purge` 的确认门槛 |

要点就是第一行与第四行的差别：跨用户能防，同用户不能防。

## 4. 能力门禁的真实定位

### 4.1 它是什么

两处校验：注册时查方法声明 ⊆ 清单；调用瞬间查生效能力（清单减撤销）是否覆盖。

### 4.2 它防什么

防「用了没声明的能力」（注册时拒）、防「撤销后仍被使用」（调用时拒）、让每次被拒都有记录。

这三条都是**让行为可声明、可追溯**，不是拦住恶意行为。

### 4.3 它不防什么

不管具体路径与网络地址；不管调用频率；不防数据外泄（声明了 `network` 就能把文件内容发出去）；**不防绕过 `Context` 直接调系统 API**——进程内插件与宿主同权限，动态库可以直接 `open`、`socket`，门禁看不到。

最后一条最关键：门禁只约束「经 `Context` 做的事」。

### 4.4 结论

准确定位是**审计钩子与误用拦截**，不是沙箱。

三个后果：挡不住作恶插件（但那不在威胁模型里）；能挡住开发期手滑；让日志能回答「这个插件被允许做什么」。

写成「安全机制」会让人高估它。

## 5. 文件与数据

### 5.1 路径校验

每个清单路径都过四查：不含 `..`；不以 `/` 或盘符开头；侧车可执行文件在插件目录内；解析真实路径后仍在目录内。

第四查是兜底：只做字面检查会被符号链接绕过。

### 5.2 zip 包的解压

防 zip-slip，顺序是：逐条拒绝非法条目名 → 解压到临时目录 → 遍历临时目录做 §5.1 的检查（含真实路径）→ 全部通过再移动到位。

解压到临时目录再搬，是为了校验失败时不留半个插件。

### 5.3 符号链接

插件目录本身是符号链接、或目录内文件是符号链接：拒绝装载。插件运行时自己建链接：不检测（属于绕过 `Context` 的修改）。

前两条的理由：符号链接可以指向任意位置，等于绕开全部路径检查。

### 5.4 数据根权限

创建时即设：Linux `0700`，Windows 设 DACL 只授当前用户与 SYSTEM。子目录继承，不单独设。

发现子目录权限被改宽时 `doctor` 报告但不自动修——自动修会让正在运行的程序写不进去。

### 5.5 卸载与 `--purge` 的门槛

默认不带 `--purge`；必须显式写；执行前打印将删的绝对路径与总大小；删非空目录前要求输入编号确认（`--yes` 跳过）；不跟随符号链接删除。

打印路径的用处：脚本里写错编号时能立刻看出来删的是谁。

### 5.6 安装来源

插件自写或审查过，不做签名校验。仍做两项：包完整性（能读、结构合法）与清单 `id` 与产物文件名一致。

不做校验和比对：记下哈希只增加负担，挡不住「自己重编了一个新的」。

## 6. 日志与崩溃转储

### 6.1 日志里不记什么

不记 token（内核的与侧车的）、不记调用载荷原文、不记文件内容、不记配置值。

debug 级别只记载荷长度与前 32 字节摘要——够判断「两次调用参数是否相同」，不够还原内容。

### 6.2 路径要不要脱敏

三个选项：全部脱敏（排障价值大降）、保留完整路径（泄露目录结构）、保留路径靠权限兜。

**选第三个**：日志主要用途是排障，路径是关键信息；`logs/` 随数据根 0700，非本用户读不到。

这是有意识的取舍，不是疏忽。要把日志发给别人时，由发的人自己先脱敏。

### 6.3 崩溃转储

`.dmp` 含进程内存，含有文件内容、凭证、配置值。措施：0600、放 `logs/`、不上传、保留最近 5 个（不做按天保留）、首次生成时日志提示「含进程内存，分享前自行检查」。

最后一条是给人看的提醒。

### 6.4 日志轮转与磁盘

内核与插件日志都按天分文件、单文件超 64 MB 轮转、保留 7 天；全部日志不超过 512 MB，超出从最旧删。

上限的作用是防止「日志写满磁盘导致宿主启动失败」——那类故障比日志丢失更麻烦。

## 7. 密钥与凭证

### 7.1 宿主自己要管的东西

只有 `session.json` 的 token。侧车的 `LING_TOKEN` 每次启动重新生成，只在环境变量里，不落盘。

### 7.2 插件自己的凭证

| 该放哪 | 不该放哪 |
|---|---|
| `data_dir()` 下的文件（自行加密或依赖系统密钥链） | 配置（会进日志与导出） |
| 系统密钥链（Windows Credential Manager、libsecret） | 日志、错误消息、`detail` |
| 插件自己的环境变量 | 清单（明文，会被复制与展示） |

宿主不做凭证托管。理由是没有多用户、没有远程服务，托管换不来收益。

### 7.3 不做什么

不自研加密算法；不做密钥轮换；不做权限分级；不做审计日志签名。

## 8. 供应链

### 8.1 C++ 依赖

baseline 锁版本；依赖只有三个（Catch2 仅测试、toml++、nlohmann/json）；不需要「万能工具库」。

判断标准：一个依赖能用两百行自己写清，就不引入。

### 8.2 Python 侧车的依赖

插件自己装的东西宿主不管：不扫漏洞、不锁版本、不隔离环境。能做的只有让启动失败的报错带上 Python 原始信息，让作者看出是依赖没装。

### 8.3 插件来源

自己写的不校签名。将来若用别人的插件，需要补的是「来源可追溯」，不是「签名验证」——这个项目没有分发渠道，签名没有信任根。

## 10. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。
| # | 事项 | 结论 |
|---|---|---|
| 1 | 界面端口 8010 要不要加口令 | 要。界面返回插件列表与配置值，不该让同机其他用户直读 |
| 2 | 侧车口令经环境变量传，同用户可读 | 接受，同用户本来就能读 `session.json` |
| 3 | 日志 512 MB 上限是否够 | 按每天几十 MB 估够用 10 天以上，实测后再调 |
| 4 | 要不要加「仅本机进程可连」的凭据校验 | 不做。回环 TCP 拿不到对端凭据，改 Unix socket 的跨平台代价大于收益 |
