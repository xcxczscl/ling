## 2. 测试分层

### 2.1 五层

| 层 | 跑一次多久 | 什么时候跑 | 判定 |
|---|---|---|---|
| 单元测试 | 毫秒到秒 | 每次 precommit | 全绿 |
| 验收脚本 | 十秒到分钟 | 每个切片完成 | 全绿 |
| 性能基准 | 一到五分钟 | 切片完成、改热路径后 | 不超上限 |
| 压力测试 | 五分钟到半小时 | S4、S6 | 无崩溃、无超阈值泄漏 |
| 手工检查 | 十分钟 | S6 与发布前 | 逐项勾选 |

关键不是哪层更重要，是**跑得越快越早跑**。

### 2.2 脚本命名的含义

| 前缀 | 需要的环境 | 典型内容 |
|---|---|---|
| `l1` | 单进程内核，零或一个最小插件 | 清单、路由、事件、能力、调用基准 |
| `l2` | 单插件 + 完整上下文 | 注册与撤销、账本、数据目录 |
| `l3` | 三个以上插件 + 依赖 | 依赖图、调和、图算法基准 |
| `l4` | 命令行与管理端口 | 子命令、认证、事件与日志 |
| `l5` | 五个内置插件齐备 | 预装、卸载、界面 |
| `l6` | 跨进程与系统级 | 侧车、资源、稳定性、平台、升级 |

数字表示「需要多少东西在场」，不表示先后。

### 2.3 测试与需求的映射

一条需求至少一个用例；负向用例数不少于正向的一半；一个用例可覆盖多条需求；无法自动测的进手工清单。

## 3. 环境与夹具

### 3.1 数据根

每个验收脚本用 `run/<preset>/data-test/<脚本名>/`：开始前删掉重建；不用用户真实数据根；结束后保留最近一次供排查；运行前清掉超过 20 个的历史目录。

### 3.2 端口

开发手动起的宿主 7900 起（顺延至 7999）；界面 8010 起；验收脚本 8020 起，每脚本一个。分开是为了避免自动化与手动实例抢端口，把失败指向错误原因。

### 3.3 七个测试插件

| 插件 | 轨道 | 用途 |
|---|---|---|
| `demo-a` | 进程内 | 最小正常插件，兼通用效应夹具：注册 `ping`，参数可开启订阅与写 `file`、`config` |
| `demo-fail` | 进程内 | 激活或注册失败，可配 |
| `demo-slow` | 进程内 | 按参数睡指定毫秒，造超时与重载窗口 |
| `demo-crash` | 进程内 | 空指针或越界，造崩溃 |
| `demo-sidecar-cpp` | 侧车 | C++ 侧车，注册方法并订阅 |
| `demo-sidecar-py` | 侧车 | Python 侧车，验证协议与语言无关 |
| `demo-caller` | 进程内 | activate 时调 `demo-a.ping` 并写日志，不注册方法 |

共同要求：关键行为由清单参数开关，避免为每个场景再编一个插件。

### 3.4 用例的写法

固定四段：准备（起宿主、装插件、等状态）→ 动作（**只允许一个**）→ 断言（返回码、状态、文件、日志、事件）→ 清理。

一个用例做两件事，失败时分不清是哪件坏了。

## 5. 性能基准

### 5.1 环境要求

Release 构建、4 核桌面 CPU（记录型号）、本地 SSD、单线程、空处理函数、笔记本插电并关闭省电模式。

最后一条容易忽略：省电模式降频，P95 能差一倍。

### 5.2 测量方法

预热 1000 次丢弃 → 采样 10 万次（延迟类）或 20 次（装载类）→ 统计 P50/P95/P99 → 重复 5 轮取 P95 的中位数。

### 5.3 八个基准

| 基准 | 上限 | 采样 |
|---|---|---|
| `l1_bench_call` | P95 ≤ 1 微秒，P99 ≤ 3 微秒 | 10 万次 |
| `l1_bench_event` | 10 订阅者 P95 ≤ 10 微秒 | 10 万次 |
| `l1_bench_load` | ≤ 50 毫秒 | 20 次中位数 |
| `l1_bench_snapshot` | 500 条路由复制 ≤ 1 毫秒 | 1 万次 |
| `l3_bench_graph` | 50 插件 100 边 ≤ 1 毫秒 | 1 万次 |
| `l4_bench_cmd` | 端到端 ≤ 500 毫秒 | 20 次中位数 |
| `l6_bench_sidecar` | 往返 P95 ≤ 100 微秒 | 10 万次 |
| 启动段 | 端口可连 ≤ 300 毫秒，20 插件全激活 ≤ 1500 毫秒 | 20 次中位数 |

`l1_bench_snapshot` 是本文补的：`04/01` §4.5 说「超过 1 毫秒就改结构」，原本没有对应基准，等于没有判据。

### 5.4 判定与波动

不超过上限即通过；1.0 到 1.1 倍之间记警告不判失败；超 1.1 倍失败；同机两次差异超 20% 视为测量不可靠，重跑。

容差记在结果里，不静默忽略。

### 5.5 结果记录

每次追加一行到 `run/<preset>/bench-history.csv`，含时间、基准名、三个分位、CPU 型号、构建类型。

保留历史的作用：性能退化往往渐进，单次看不出，十几行能看出趋势。

## 6. 故障注入

十五个场景，全部自动化。手段只有三类：改夹具参数、杀进程、改文件系统状态。

F1 激活失败；F2 注册失败；F3 进程内崩溃（Windows 捕获）；F4 进程内崩溃（Linux 退出）；F5 侧车强杀；F6 侧车不响应停用；F7 撤销失败；F8 账本满；F9 磁盘满（tmpfs，仅 Linux）；F10 权限被改宽；F11 zip 带 `..`；F12 符号链接；F13 依赖成环；F14 重载新版失败；F15 口令错三次。

F3 与 F4 是同一场景的两种平台结果，都要验：一个「捕获后继续」，一个「退出」。

## 9. 什么算通过

### 9.1 三层判定

单条用例：断言全成立、无超时、清理无报错。

一个脚本：全部用例通过，无静默 `skipped`（平台不适用须标出）。

一个切片：本片脚本全绿 + 全量回归全绿 + 基准不超上限 + 手工清单通过。

### 9.2 手工清单

| # | 检查 |
|---|---|
| M1 | 界面能打开、五个页签可切换 |
| M2 | 界面里完成装卸启停各一次 |
| M3 | 界面崩溃后 2 秒内恢复 |
| M4 | Android 真机装插件并调用 |
| M5 | `doctor` 四段输出可读 |
| M6 | 转储能被调试器打开并解析符号 |
| M7 | 打包产物在干净机器能启动 |
| M8 | 24 小时长稳 |

M8 不通过说明资源管理有问题，不是功能 bug，排查方向完全不同。

### 9.3 不通过的处置

| 情形 | 处置 |
|---|---|
| 用例失败，代码有 bug | 修代码 |
| 代码符合设计，设计有问题 | 改设计与文档，再改用例 |
| 判据本身有误 | 改判据，提交信息里说明为什么 |
| 基准在容差内 | 记结果，连续两次则排查 |
| 平台不适用 | 标 `skipped` 并写原因 |

**不许为了通过而放宽判据。** 判据是需求的一部分，改判据等于改需求。

## 10. 不测什么

恶意插件；同用户恶意进程；物理接触；极端并发（几百连接）；界面视觉细节；第三方库自身正确性；长时间高频调用后的内存碎片（无使用场景，测出来也无法判断好坏）。

---

## 11. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 |
|---|---|---|
| 1 | `l1_bench_snapshot` 的 1 毫秒上限 | 先按 1 毫秒判；实测远低于它则收紧到实测三倍 |
| 2 | T2、T3 在 Windows 上怎么换用户 | 另建本地账户跑测试进程，需提权，只在 CI 做 |
| 3 | 24 小时长稳能否用 2 小时替代 | 不能，内存增长常在前几小时看不出 |
| 4 | 基准是否进 precommit | 不进，跑一轮五分钟，提交前跑不动 |
