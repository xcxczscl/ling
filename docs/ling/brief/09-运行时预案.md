# ling 09 运行时预案（简要版）

本文是 `docs/ling/09-运行时预案.md` 的简要版。

`03` 回答「为什么这样设计」，本文回答「现在怎么办」。出问题时先看 §7 的处置表。

## 1. 目的与范围

### 1.1 覆盖什么

启动、运行、关闭三阶段的十六类故障：判据、自动动作、人工动作、证据在哪；数据损坏的恢复顺序；六条不该做的事。

### 1.2 不覆盖什么

| 内容 | 去哪 |
|---|---|
| 设计中如何预防 | `03` §10 |
| 故障怎么注入 | `07` §6 |
| 转储怎么解析 | `05` §8.2 |
| 装不上怎么办 | `08` §4 |
| 命令用法 | `12-用户手册`（未编写） |

### 1.3 一个前提

单机、单用户、有人看着。没有告警通道，也没有远程入口。

所以「自动恢复」的目标不是无人值守地自愈，而是**把问题控制在不扩大、且留下完整证据**。宁可停下来等人，也不要带着可疑状态继续跑。

## 2. 处置原则

### 2.1 四条原则

| # | 原则 | 反面做法 |
|---|---|---|
| 1 | 先保数据，再保可用 | 为「不中断」继续写可疑状态 |
| 2 | 自动只做不破坏的动作 | 自动「清理」损坏的文件 |
| 3 | 失败必须留证 | 只打一行「出错了」 |
| 4 | 不确定就停 | 猜一个原因继续 |

第 2 条的后果：删数据、清配置、降版本、强杀进程，全部要人做。

### 2.2 三级影响

| 级别 | 含义 | 要不要立刻处理 |
|---|---|---|
| L1 | 单个插件不可用 | 可以放着 |
| L2 | 宿主某项功能不可用 | 看依赖程度 |
| L3 | 宿主不可用 | 必须马上动手 |

### 2.3 谁能做破坏性操作

| 操作 | 自动 | 需人确认 |
|---|---|---|
| 标记 `Failed`、拒绝调用 | 可以 | —— |
| 超时后结束侧车 | 可以 | —— |
| 把损坏配置**重命名** | 可以 | —— |
| 删数据、清配置、降版本、强杀 | **不允许** | 必须 |

「重命名可以、删除不行」的理由：重命名保留现场，删除就没了。

## 3. 启动阶段

共同点：宿主还没起来，没人能通过命令行求助，所以错误必须打在 `stderr` 且能直接指向动作。

### 3.1 数据根不可写

判据是 `errno`：`EACCES` 权限不足、`EROFS` 只读、`ENOSPC` 磁盘满、`ENOTDIR` 路径里有文件。

自动：退出，`stderr` 打印「路径 + errno 名称 + 建议动作」三行。此时日志还写不进去，这三行就是全部证据。

### 3.2 端口全占

判据：7900 至 7999 全部 `bind` 失败。

自动：退出码 3，列出试过的端口与失败摘要。人工：关占用进程或用 `--port` 换段。这类失败不写日志——几毫秒内发生，写日志更慢。

### 3.3 配置损坏或版本过高

| 情形 | 自动 | 人工 |
|---|---|---|
| 解析失败 | 重命名为 `settings.json.corrupt-<时间戳>`，空配置启动，记 error | 从备份恢复，或从 `.corrupt` 里捞字段 |
| `schema_version` 高于当前 | **拒绝启动**，不动文件 | 用新版启动或恢复旧备份 |

第二种拒绝启动是刻意的：旧版读到新格式会把不认识的字段丢掉，写回就降级了配置。

### 3.4 `registry.json` 损坏

解析失败或字段类型不对时，按默认值重建并记 warn，**不重命名不备份**——它只存端口与两个名单，可再生。

与 `settings.json` 区别对待的理由：前者可再生，后者含用户配置。

### 3.5 内置插件装不上

记 warn（哪个插件、什么原因），继续装其余四个，宿主照常启动。人工用 `ling install` 补装。

不因一个内置插件失败就拒绝启动：`core-log` 装不上不影响运行，硬退出反而让人连命令行都用不了。

### 3.6 启动卡住

判据：进程在但不在监听端口，超过 30 秒。

常见原因三类：扫描巨大目录、某插件 activate 死循环、多个侧车各等待 10 秒。

自动：不做任何事（没有看门狗进程）。人工：看内核日志最后几条判断卡在哪，再决定等还是强杀。

日志仍在写入（异步队列还在工作），所以它是卡住时最有用的证据。

## 4. 运行阶段

### 4.1 进程内插件崩溃：Windows

自动四步：写调用栈地址到内核日志 → 生成 `.dmp` 到 `logs/` → 标 `Failed` 并拒绝后续调用 → 按账本撤销效应并广播 `crashed`。

人工：解析转储、修插件、重装。**不自动重启该插件**：重装还是同一份代码，反复崩溃只刷日志。

### 4.2 进程内插件崩溃：Linux 与 Android

进程直接退出，没有自动动作。

人工四步：看被什么信号终止 → 用外部守护拉起 → 反复崩溃就改走侧车 → 需要时开 core dump。

这条缺口是已知的（`02` §5.5）。预案不是「修好它」，而是「退出得有痕迹、且能自动拉起来」。

### 4.3 侧车反复重启

判据：连续异常退出 3 次。自动：转 `Failed`，停止重试，记 error。

人工：看 `logs/<编号>-sidecar.log`。常见三类原因：缺依赖、端点连不上、握手 token 不符。

为什么是 3 次：1 次会是启动竞态误判，5 次太多会刷日志。

### 4.4 侧车不响应

判据：`deactivate` 后 5 秒无 `deactivated`。自动：发 `shutdown`，再 5 秒后强杀，记 warn。

人工：查是否死锁（常见于处理函数等一把永远拿不到的锁）。

### 4.5 调用超时堆积

判据：同一插件 5 分钟内 10 次以上 `E_TIMEOUT`。自动：记 aggregated warn，**不停用该插件**。

人工：debug 级别看摘要，判断是插件慢还是数据量大。

为什么不停用：超时常来自数据量波动，自动停用会把「偶尔慢」变成「功能消失」。

这与侧车「连续 3 次崩溃就停」不同：崩溃是确定性错误，超时不是。

### 4.6 账本满

判据：当前激活代已 10000 条又来一次。自动：返回 `E_LEDGER_FULL`，**本次修改不生效**（容量检查在改表之前），记 error。

人工：说明插件在泄漏效应（反复注册不注销，或循环里注册）。修插件，不是调上限。

### 4.7 磁盘满

自动三步：日志退 `stderr` → 拒绝新装载返回 `E_IO` → **已有插件的调用照常**。

人工按序清：旧 `.dmp`（最大）、旧日志、旧私有副本。

第 3 步要说明：磁盘满时最不该做的是全停。用户正需要命令行来清理，把宿主停掉等于把工具也关了。

### 4.8 日志写不进去

自动：退 `stderr`，打一行提示，宿主继续运行。人工：修权限或重建 `logs/`，**不用重启**——下次写入会重试打开。

这是「日志失败不该让业务失败」的直接应用。

### 4.9 界面不可用

自动：按 `on-crash` 2 秒内重启一次，连续 3 次失败转 `Failed`。

人工四选一：查 core-ui 状态、看侧车日志、干脆卸掉、命令行本来就不受影响。

**不要因为界面坏了就回退整个版本。**

## 5. 数据与配置

### 5.1 判定数据损坏的四种迹象

配置解析失败；`doctor` 报告未撤销条目；插件报「读不出自己的数据」；账本序号不连续。

前三条宿主能看见，第四条只能靠插件自查。

### 5.2 恢复顺序

固定三步：停宿主（停不下先记状态再强杀）→ **备份整个数据根**→ 按 `doctor` 报告逐项处理。

第 2 步不是形式：没有备份就动手，改错后没有回退点。

### 5.3 什么情况必须停手

数据被写坏但不知道谁写坏的；崩溃发生在写数据过程中；同一故障连续三次以上；`doctor` 报的问题互相矛盾。

停手之后：备份数据根、收集日志与转储、把现象记入 `docs/log/`，从最小可复现开始查。

## 6. 关闭阶段

### 6.1 关闭卡住

判据：`shutdown` 后 10 秒未退出。自动：打印「未退出，检查日志」，退出码 4，**不自动强杀**。

人工：看卡在七步关闭的哪一步，再决定强杀。

不强杀的理由：强杀会让数据处于半写状态。

### 6.2 撤销失败

自动：记 `E_UNDO_FAILED`，继续撤其余，最后返回 `E_UNINSTALL_INCOMPLETE`，状态仍改 `Deactivated`。

人工：`doctor` 看清单；重装该插件能重新登记干净。

状态仍然改的理由：留在 `Deactivating` 会占着依赖图位置，下游永远无法激活。

### 6.3 强杀的代价

| 代价 | 能不能补救 |
|---|---|
| 账本没撤完 | 能，重启表从空开始 |
| 日志队列内容丢失 | 不能 |
| `settings.json` 有半写风险 | 能，有原子替换与 `.corrupt` 兜底 |
| `registry.json` 有半写风险 | 能，按默认重建 |

实际代价可控，但能不用就不用——强杀会让这次故障的证据丢掉。

## 7. 处置表

| 现象 | 级别 | 自动做了什么 | 人该做什么 | 证据 |
|---|---|---|---|---|
| 数据根不可写 | L3 | 退出，打印路径与 errno | 修权限或换目录 | `stderr` |
| 端口全占 | L3 | 退出，列出端口 | 关进程或 `--port` | `stderr` |
| 配置版本过高 | L3 | 拒绝启动，不动文件 | 用新版或恢复备份 | `stderr` |
| 配置损坏但能起 | L2 | 重命名 `.corrupt`，空配置启动 | 从备份恢复 | `.corrupt` |
| 启动卡住 | L3 | 无 | 看日志最后几条 | 内核日志 |
| 插件崩溃（Windows） | L1 | 转储、标 `Failed`、撤效应 | 解析转储，修插件 | `.dmp` + 日志 |
| 插件崩溃（Linux） | L3 | 无 | 外部守护拉起 | `dmesg` + 日志 |
| 侧车反复重启 | L1 | 3 次后停 | 看侧车日志 | 侧车日志 |
| 侧车不响应 | L1 | 5+5 秒后强杀 | 查死锁 | 两条超时日志 |
| 调用频繁超时 | L1 | 只记 warn | debug 看摘要 | 内核日志 |
| 账本满 | L1 | 拒绝新效应 | 修效应泄漏 | 日志 error |
| 磁盘满 | L2 | 日志退 stderr，拒装载，调用照常 | 按序清 | `stderr` |
| 日志写不进 | L2 | 退 stderr，继续运行 | 修权限，不用重启 | `stderr` |
| 界面打不开 | L2 | 2 秒内重启一次 | 命令行可用，不必急 | 侧车日志 |
| 关闭卡住 | L3 | 等 10 秒后报错 | 看日志再决定 | 内核日志 |
| 撤销失败 | L1 | 继续撤其余，报不完整 | `doctor` 看清单 | 日志 + `doctor` |

## 8. 不该做的事

| 不该做 | 该做什么 |
|---|---|
| 自动清空损坏配置 | 重命名保留现场 |
| 自动停用超时的插件 | 记 warn，等人决定 |
| 自动降级版本 | 人判断后手动回退 |
| 自动修权限 | `doctor` 报告，人来改 |
| 磁盘满时停掉全部功能 | 只拒装载，调用照常 |
| 原因不明时继续跑 | 停手、备份、再查 |

降级那条要展开：降级看似安全，但如果新版本已写过数据，旧版本会读到不认识的格式。必须先看 `schema_version` 再决定。

## 9. 与 03 八条风险的对应

| 03 的风险 | 处置 |
|---|---|
| 1 映射泄漏 | 不单独处置，`doctor` 看内存，30 MB 提示重启 |
| 2 进程内崩溃不可恢复 | §4.1、§4.2 |
| 3 快照替换频率高 | 不单独处置，表现为内存短暂上升 |
| 4 协议分裂 | 不适用（开发期问题） |
| 5 插件绕过上下文 | §5.1 的未撤销条目迹象 |
| 6 撤销函数写错 | §6.2 |
| 7 升级导致不兼容 | 不在本文，装载时就被拒 |
| 8 界面崩溃无法自恢复 | §4.9 |

第 1、3、4、7 条没有对应处置，因为它们要么表现为别的问题，要么在更早环节被拦住。这张表的作用是不留空白。

## 10. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 |
|---|---|---|
| 1 | 超时堆积阈值 5 分钟 10 次无依据 | 保留，实测后调；不自动停用这条不变 |
| 2 | 是否给宿主加看门狗进程 | 不加，非 Windows 靠 systemd，两套机制会打架 |
| 3 | 磁盘满是否自动删旧日志 | 不该，删日志等于毁证据 |
| 4 | 侧车与内核日志时间戳是否同源 | 要，否则对不上时序 |
