# ling 02 技术选型（简要版）

> 状态：草案 | 最后更新：2026-10-28

本文是 `docs/ling/02-技术选型.md` 的简要版。只留结论、关键数字与理由的核心，推理过程在详细版。

结论：**宿主 C++17，进程内插件 C++，侧车插件 Python，边界只用 C ABI。** C# 评分最高但不选，理由见 §6.2。

---

## 1. 判定维度与权重

### 1.1 七个维度

可读性、热更新可靠性、三端支持确定性、崩溃可控性、生态对接、构建复杂度、工具链成熟度。

### 1.2 权重

| 维度 | 权重 | 理由 |
|---|---|---|
| 可读性 | 30% | 上一版失败的直接原因是「代码看不懂，只能全权交给 AI」 |
| 热更新可靠性 | 20% | ling 的核心卖点，01 需求 §3.6 有 7 条硬需求 |
| 三端支持确定性 | 20% | 多平台是目标，不是可选项 |
| 崩溃可控性 | 15% | 宿主机被插件拖死，所有插件一起失效 |
| 生态对接 | 10% | 播放器必须调 C 媒体库 |
| 构建复杂度 | 5% | 只影响起步阶段 |

可读性权重最高不是偏好，是可持续性：内核读不懂，每次改动都要重新理解，改错概率随代码量上升。

## 2. 约束与前提

### 2.1 不变的约束

宿主零内容；单机单用户几十插件；多平台（Windows 主、Linux 对齐、Android 降级）；插件可装卸与热更新；插件之间不直接链接。

### 2.2 可信前提

**所有插件由你自己编写。** 不需要防恶意插件（归 06 安全设计），但需要防意外崩溃（空指针、死循环、越界）。

### 2.3 性能底线分档

| 档位 | 场景 | 可接受上限 |
|---|---|---|
| 交互式 | 界面响应、播放控制 | 50 毫秒 |
| 批量 | 扫描、哈希、转码 | 无要求，耗时由数据量决定 |
| 管理 | 装插件、查状态 | 500 毫秒（LING-REQ-096） |

关键推论：批量操作占实际耗时绝大部分，而它的耗时与调用机制开销无关。真正需要快的只有交互式一档，它有 50 毫秒预算。

### 2.4 上一版失败的原因

上一版约 6300 行 Rust 内核（`old/main/`，27 个文件），结果是「看不懂，出问题查不出」。推测原因按可信程度排序：异步与生命周期标注叠加；trait 对象与 `unsafe` FFI 层叠加；无前置设计文档、边写边改。

待你补充：具体哪一类看不懂。已记入 §10。

## 3. 插件形态

### 3.1 三种形态

纯进程内（动态库）、纯侧车（独立进程）、混合双轨。

### 3.2 对照

| 项 | 纯进程内 | 纯侧车 | 混合双轨 |
|---|---|---|---|
| 调用延迟 | 0.1–1 微秒 | 50–200 微秒 | 按插件分 |
| 崩溃隔离 | 无 | 完全 | 部分 |
| 热更新 | 难 | 易 | 按插件分 |
| 语言自由度 | 必须 ABI 兼容 | 任意语言 | 双轨各自受限 |
| 内核代码量 | 大 | 小 | 最大 |

### 3.3 为什么选混合双轨

交互式场景必须快，只有进程内能满足；批量场景不敏感，而它恰是最需要语言自由的（Python 生态）。纯侧车让所有插件都背 50–200 微秒；纯进程内放弃「小功能用 Python 直接写」。代价是内核维护两套装载路径。

### 3.4 混合双轨的收敛办法

1. 进程内插件只用于交互式热路径，默认侧车，进程内需理由
2. 进程内插件的 ABI 只有一张函数表，全系统只有一个跨语言边界点
3. 进程内插件不允许卸载，热更新改为「加载新版本、不卸旧版本」

第 3 条牺牲一点内存，换可靠性。对个人工具划算。

## 4. 语言对照

### 4.1 排除的候选

Go（`plugin` 包 Windows 不支持）、Java/Kotlin（启动 300 毫秒起、内存 100 MB 起，与 LING-REQ-094/099 冲突）、Node（内存百 MB 起）、Zig（生态与调试资料不足）。这些语言都可以做**侧车插件**。

### 4.2 C++

能做宿主（`dlopen` 是标准能力）。调用约 1–10 纳秒。无内存安全。三端工具链成熟。媒体库零绑定成本（ffmpeg、mpv 都是 C/C++）。热更新有坑（§5.6）。可读性受模板、指针、宏拖累，三样都能用写法约定规避（§8）。构建用 CMake + vcpkg。

### 4.3 Rust

能做宿主，调用同量级。**内存安全止步于 `unsafe` 边界**，而插件宿主的核心全是边界代码，所以这项优势在关键路径上并不存在。三端成熟。热更新最差（§5.6）。可读性最差：所有权、`async`、trait 三层叠在一条调用链上。

不选的理由是权重，不是能力。

### 4.4 C#

分两条路。

#### 4.4.1 路线 A：整个宿主用 C#（托管宿主）

调用 10–30 纳秒；计算约为 C++ 的 50%–90%；**热更新四门语言里最好**（`AssemblyLoadContext` 可回收，GC 负责清理）；内存安全；空载 30–50 MB；自包含 + ReadyToRun 启动 100–200 毫秒。

三端是问题：Windows/Linux 用 CoreCLR，动态加载插件没问题；Android 用 Mono（AOT + 解释器），插件后装必然走解释器，功能可用但性能是解释水平，且 **.NET 11 起 Android 不再提供解释器**，路线在收窄。

**NativeAOT 走不通**：官方明确不支持运行时加载程序集。想要 NativeAOT 的启动与内存，就要放弃动态插件——这是「CIL 高速」最硬的一道墙。

#### 4.4.2 路线 B：C++ 宿主嵌入 CoreCLR

用 `hostfxr` 加载 .NET 运行时，插件用 C#。要处理托管异常不跨边界、GC 句柄与钉住、双向胶水、两套调试器。收益只有语言搭配。不推荐。

#### 4.4.3 C# 的总结

「可读性」「热更新」两项第一，「三端」失分，「生态」居中。技术上最优雅的宿主选择，输在三件事：你不熟 C#、Android 路线收窄、媒体库要经绑定层。

### 4.5 Python

「通过 CPython 实现高速」分三层，答案不同。

#### 4.5.1 作为宿主

不可行。启动 50–150 毫秒、内存 8–15 MB 起，GIL 让所有插件串行。

#### 4.5.2 嵌入宿主进程（C++ 链接 libpython）

调用本身 0.1–0.5 微秒，但**类型转换才是成本主体**：

| 载荷 | 估算成本 |
|---|---|
| 5 字段小 dict | 0.5–2 微秒 |
| 1 KB 字符串 | 1–3 微秒 |
| 1 MB 字节缓冲 | 100–300 微秒 |
| 1 MB JSON | 5–15 毫秒 |

LING-REQ-097 允许 1 MB 载荷，此时转换成本已超过侧车的套接字往返。另外三个硬伤：GIL 让多插件串行；C 扩展段错误杀宿主；从 `sys.modules` 删模块清不干净，热更新不可靠。

3.14 有两个变化：free-threaded 构建转为正式支持（仍需单独构建，生态未全适配）；多解释器进标准库（`PEP 734`，配合 `PEP 684` 可给每个插件独立 GIL），但对不兼容多解释器的 C 扩展有限制。

#### 4.5.3 侧车进程

延迟 50–200 微秒，与语言无关，只与进程边界有关。每插件独立 GIL、真正并行、完全隔离、热更新最易（重启进程）。需要带 Python 运行时（约 15–30 MB 裁剪后）。

**Python 在 ling 里的正确位置是侧车插件**，不是宿主，也不嵌入宿主进程。

### 4.6 总表

评分 1–5，5 最好。

| 维度 | 权重 | C++ | Rust | C# | Python |
|---|---|---|---|---|---|
| 可读性 | 30% | 3 | 2 | 5 | 4 |
| 热更新可靠性 | 20% | 2 | 1 | 5 | 3 |
| 三端支持确定性 | 20% | 5 | 5 | 3 | 3 |
| 崩溃可控性 | 15% | 2 | 3 | 4 | 2 |
| 生态对接 | 10% | 5 | 4 | 3 | 5 |
| 构建复杂度 | 5% | 3 | 4 | 4 | 2 |
| **加权总分** | 100% | **3.25** | **2.85** | **4.20** | **3.30** |

**C# 得分最高，但结论是 C++。** 三条理由不在表里：

1. 可读性 5 分假设你懂这门语言，而你 C++ 有基础、C# 没有；学新语言的前三个月可读性按 0 计
2. 三端的 3 分掩盖了趋势：Android 的 C# 动态加载路线在收窄
3. 评分不反映自由度：C ABI 对任何语言开放，托管边界只对 .NET 开放

## 5. 插件边界技术

### 5.1 为什么必须用 C ABI

C++ 没有稳定二进制接口。编译器不同、大版本不同、运行时库不同（`/MD` 与 `/MT` 两份堆）、异常模型不同、STL 实现不同，任何一项不一致都会「编译通过、运行崩溃」。只能退到 C 语言那部分：函数调用约定、结构体布局、基本类型。

**Rust 处境相同**：两个 Rust 动态库之间也不能直传 `String`、`Vec`、trait 对象。这一层上两种语言没有区别。

### 5.2 唯一入口点

整个系统跨语言边界只有一个函数：

```c
int32_t ling_plugin_entry(const ling_host_api* host, ling_plugin_descriptor* out);
```

其余全部通过 `ling_host_api` 里的函数指针表转发。三个性质：只有一个导出符号（加功能只扩函数表）；`abi_version` 由宿主校验，不匹配直接拒绝而非崩在半路；语言中立，任何能导出 C 函数的语言都能写进程内插件。

胶水约 300 行（装载器 150 + 函数表 100 + 错误映射 50），只写一次。这是混合双轨成本可控的关键。

### 5.3 类型禁区

允许：定宽整数与浮点、不透明句柄 `void*`、指针 + 长度、纯数据定长结构体、函数指针。

禁止：`std::string` / `std::vector` / `std::map`、跨边界抛异常、跨边界 RTTI、移交 C++ 对象所有权、回调里持有引用超过调用期。

硬规则：**谁申请谁释放**。跨边界返回的缓冲区由同一模块提供释放函数，不许调自己的 `free`。

### 5.4 编译器与运行时一致性

| 约束 | 取值 |
|---|---|
| 编译器 | Windows 统一 MSVC 2022；Linux 统一 Clang；Android 统一 NDK Clang |
| C++ 标准 | C++17 |
| 运行时库 | Windows 统一 `/MD` |
| 异常模型 | 统一 `/EHsc` |
| 构建类型 | Debug 插件不能装进 Release 宿主 |

落地办法：宿主与所有插件共用一份编译选项定义，插件作者不自己写编译选项，约束不靠人记。

### 5.5 崩溃捕获

| 平台 | 手段 | 可靠性 |
|---|---|---|
| Windows | `__try` / `__except` 或 `AddVectoredExceptionHandler` | 较高 |
| Linux / Android | `signal` + `siglongjmp` | 低，长跳转破坏栈状态 |

结论：跨平台「崩溃后继续运行」在进程内不可靠。Windows 上捕获后标记插件故障并拒绝后续调用；Linux 与 Android 上宿主会一起退出，靠外部守护重启。**真正可靠的隔离只能是侧车。**

### 5.6 热更新的三条现实路径

#### 路径一：`dlclose` 卸载后重新加载（C++ 名义方案）

四个坑：TLS 未释放则不会真正卸载；同名文件重新 `dlopen` 返回旧句柄；静态对象析构顺序不可控；其他库持有的指针会指向新代码。

#### 路径二：复制到新文件名再加载（工程实践）

绕开坑 2。新版本能加载，旧版本留在内存。代价是每次重载泄漏一个代码映射，按 100–500 KB 估算，100 次重载泄漏 10–50 MB。与 LING-REQ-101（≤ 10 MB）冲突，已记入 §10。

#### 路径三：侧车重启（可靠方案）

杀旧进程起新进程，无卸载问题。重载期间该插件不可用（100–500 毫秒），调用返回 `E_PLUGIN_MISSING`（LING-REQ-054）。

#### 四门语言的热更新能力对照

| 语言 | 路径一 | 路径二 | 路径三 | 综合 |
|---|---|---|---|---|
| C++ | 有坑 | 可行，泄漏 | 可行 | 2/5 |
| Rust | **本质不安全**，社区共识不卸载 | 可行，泄漏 | 可行 | 1/5 |
| C# | 不需要，`AssemblyLoadContext` 可回收 | — | 可行 | 5/5 |
| Python | 嵌入模式不可靠 | — | 可行 | 3/5 |

Rust 得 1 分是语言层面限制：一旦卸载，库里的 `&'static` 引用、字符串字面量、trait 对象虚表全部变悬垂指针，而类型系统无法表达「这个 `'static` 只在本库加载期间有效」。

本文取舍：进程内插件走路径二（复制文件名 + 不卸载），记录泄漏，达阈值提示重启；侧车走路径三。

## 6. 最终组合

### 6.1 结论

| 角色 | 选择 | 版本 |
|---|---|---|
| 宿主内核 | C++ | C++17，MSVC 2022 / Clang / NDK Clang |
| 进程内插件 | C++（同一套 ABI） | 同宿主 |
| 侧车插件（首选） | Python | 3.14 |
| 侧车插件（其他） | 任意能读写本地套接字的语言 | 不限制 |
| 边界技术 | 单个 `ling_plugin_entry` + C ABI 函数表 | `abi_version` 从 1 开始 |
| 构建系统 | CMake + vcpkg、NDK 工具链 | 最新稳定版 |

### 6.2 被否方案与理由

| 方案 | 否掉的理由 |
|---|---|
| Rust 内核 | 可读性权重最高而它该项最低；热更新最差 |
| C# 托管宿主 | 评分最高但你不熟 C#；Android 路线收窄；NativeAOT 与动态插件二选一 |
| C++ 宿主 + Python 嵌入 | GIL 串行、C 扩展崩溃不隔离、热更新不可靠、大载荷转换成本超过侧车 |
| 纯侧车 | 交互式延迟预算被插件数量摊薄 |
| 纯进程内 | 放弃 Python 插件，且 Linux/Android 崩溃不隔离 |
| Go / Java / Node 宿主 | 见 §4.1 |

## 7. 可替换性设计（防止返工）

### 7.1 契约与实现分离

| 层 | 内容 | 换语言时是否重写 |
|---|---|---|
| 契约层 | 清单格式、命名规则、错误码表、消息协议、`ling_host_api` 定义 | **不重写** |
| 内核实现 | 路由表、事件总线、门禁、依赖解析 | 重写 |
| 插件实现 | 插件业务逻辑 | 侧车零改动；进程内需重新编译 |

契约用语言中立写法：定宽类型、JSON schema、表格，不混入 `std::string` 这类类型。

### 7.2 换内核语言的代价估算

内核对 6000 行左右重写是大头；Python 侧车插件零改动；C++ 进程内插件代码不改但要重新编译；文档只改实现部分。

前提是 §7.1 做到了。契约里混进语言相关类型，侧车协议也要跟着改。

### 7.3 一个额外的口子

`ling_host_api` 是 C ABI，所以非 C++ 的进程内插件技术上可行。不承诺、不测试、不写文档，但设计上不堵死。

## 8. 「不耍花招」写法约定

语言选对只是必要条件，写法约定才是「读得懂」的充分条件。

### 8.1 禁用

模板元编程；多继承；运算符重载（除 `==`、`<`）；宏定义控制流；异常跨模块传播；全局可变状态；单文件超 500 行。

### 8.2 允许并鼓励

RAII；`unique_ptr` / `shared_ptr`；`const` / `constexpr`；简单容器与 `optional` / `variant`；早期返回；每函数单一职责且不超 60 行。

### 8.3 命名与注释

类型 `PascalCase`；函数 `snake_case`；成员后缀下划线；常量 `k` 前缀；文件 `snake_case.cpp`；注释写「为什么」不写「在做什么」。

格式由 `clang-format` 配置管，不靠人记。
