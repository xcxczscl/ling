## 2. 里程碑总览

### 2.1 里程碑表

| 编号 | 名称 | 含切片 | 能演示什么 | 版本号 |
|---|---|---|---|---|
| M0 | 设计定稿 | 无 | 二十一份文档全定稿，引用无冲突 | `0.0.1-b1` |
| M1 | 最小闭环 | S0、S1 | 装两个插件（含调用方），都 activated，调用方拿到回应 | `0.0.2-b1` |
| M2 | 可装可卸 | S2 | 卸载后路由清空、账本倒序撤销、`data/` 保留 | `0.0.3-b1` |
| M3 | 能改能换 | S3、S4 | 依赖方自动激活；改插件不重启宿主 | `0.0.4-b1` |
| M4 | 双轨 | S5 | C++ 与 Python 侧车同时在线；强杀 2 秒重启 | `0.0.5-b1` |
| M5 | 可用 | S6 | 浏览器界面里完成装卸启停；`doctor` 查成环 | `0.0.6-b1` |
| M6 | 可发布 | 无 | 三端出包，干净机器装完能用 | `0.1.0-b1` |

### 2.2 为什么这样切

三条判据：每段能演示；每段结束时是可运行的完整程序；三条会让项目停摆的风险分别落在 M1、M4、M6，不堆到最后。

### 2.3 与需求的关系

里程碑不按需求编号切：需求是横向的，里程碑是纵向的。MVP 覆盖哪些条目见 `11`；M2 之后的判定方式是「该段涉及的 `04` 条目全部实现」。

## 3. 各里程碑的定义

### 3.1 M0 设计定稿

二十一份文档写完、自审、全量交叉核对。通过条件五条：两版标题对应、127 条需求无缺漏、错误码无表外取值、跨文档同一事实只有一个值、用户过目无异议。

第四条最容易出问题：写 `04` 时已撞到三次静默错误（字段名两套、端口两个值、子命令表漏两项）。

### 3.2 M1 最小闭环

`install` → `plugins` 显示 activated → 集成测试 `l2_call` 由调用方插件调 `demo-a.ping` 收到 pong。

命令行没有 `call` 子命令：管理端口只接受 `kernel.*` 方法，业务方法只能由插件调用。

验证三件事：三平台能编出可运行二进制；动态库能装进进程并导出唯一入口；编译器与运行时 ABI 约束站得住。第三件要专门造一次「故意混用 `/MD` 与 `/MT`」的失败案例。

### 3.3 M2 可装可卸

装 `demo-a`（注册方法、订阅主题、开文件句柄）、卸载、确认路由与订阅清空、账本倒序撤销、`data/` 保留。

这一段验证「可逆」：注册要注销、订阅要退订、文件要关、配置要还原。少一条就是残留。

### 3.4 M3 能改能换

先装依赖方再装被依赖方，前者自动激活；替换文件后 `reload`，调用进新版。

两个切片合一段：依赖决定「能不能起」，热更新决定「起了能不能换」。风险最高，因为涉及并发——必测「旧回调在新版装载后返回」，确认 `generation` 校验把它丢弃。

### 3.5 M4 双轨

C++ 侧车与 Python 侧车同时在线；强杀 C++ 侧车，宿主不受影响，2 秒内重启。

外部依赖最重：Python 运行时怎么随程序分发。`02` §4.5.3 已定「随程序分发」，但打包时会碰到动态库依赖与 `sys.path` 问题。

### 3.6 M5 可用

浏览器打开 `127.0.0.1:8010`，在界面里装卸启停；`ling doctor` 查成环与残留。

「自己开始用」的起点，从这一段起积累真实使用中的问题。

### 3.7 M6 可发布

只做打包、干净机器验证、Android 验证，不含新切片。

重点不是「能不能打出来」，是「换一台机器还能不能用」。开发机上总有额外运行库与环境变量。

Android 要求与桌面一致：进程内、C++ 侧车、Python 侧车都能装；运行时随 apk 分发，包多约 30 MB。

## 4. 版本号与里程碑的对应

| 时点 | 版本 | 动作 |
|---|---|---|
| 设计基线 | `0.0.1-b1` | 无代码，仅设计快照 |
| 每个里程碑完成 | 次版本 +1，`bN` 归 1 | 打标签 |
| 里程碑内每次构建 | 只加 `bN` | 修 bug、补测试、重打包 |
| 里程碑内加功能 | 次版本 +1 | 如 M3 期间加 `doctor` |
| M6 完成 | `0.1.0-b1` | 首要版本进 1 |
| 项目完成 | `0.1.0` | 去掉 `-bN` |

标签只打在通过判定的提交上；`bN` 是构建序号不是测试轮次；不兼容改动一律进大版本。

## 5. 判定与退回

### 5.1 通过判定的四条

演示脚本跑通并记进 `docs/log/`；该段涉及的 `01` 需求验收标准可判真；测试全绿且基准在容差内；`precommit.sh` 五项全过。

### 5.2 不通过怎么办

不进下一段，也不记成待办。三种处理：实现有 bug 就修到通过；设计有问题就回去改 `04` 或更上游并记 `docs/log/`；需求有问题就改 `01` 并连带改 `04`、`07`。

第三种最容易拖，拖着的结果是需求永远不改、代码永远和文档不一致。

### 5.3 已完成的段可以拆掉重做吗

只在「该段的核心判断被证伪」时可以。不因为「写得不好看」重做——重构属于段内的事。

## 6. 关键路径与风险

### 6.1 关键路径

M1 是唯一的关键路径起点。M3 与 M4 互不依赖，但 M5 依赖 M4。

M6 排在最后但**不依赖 M5**：没有界面的三端包也算可发布。界面最容易拖，不该成为发布前提。

### 6.2 外部风险

| 风险 | 段 | 缓解 |
|---|---|---|
| C++ 与 ABI 边界写不出来 | M1 | 接口收缩到单个导出函数；S0 先跑通三平台构建 |
| 快照复制超 1 毫秒 | M1 后 | `l1_bench_snapshot` 早测，超标改持久化结构 |
| 卸载泄漏累积 | M3 | 放宽到 50 MB，30 MB 提示重启；极端情况改侧车 |
| Python 在 Android 打包做不出来 | M4 | M4 就跑通；做不出来回头改 01 与 02，不在 M6 临时降级 |
| Android 前台服务被杀 | M6 | 通知栏常驻 + 手动加白名单 |
| 文档某处实现不了 | 任意 | 每段出口条件要求实现与文档一致 |

### 6.3 已知的「不会解决」

| 问题 | 为什么不排 |
|---|---|
| 同账户恶意程序能控制宿主 | 应用层无法解决 |
| Linux 与 Android 进程内崩溃带走宿主 | 平台限制 |
| 重载泄漏的映射无法回收 | `dlclose` 限制，重启即清 |
| Android 无原生界面 | 要维护两套界面，收益不足 |

---

## 7. 明确不排进路线图的事

插件市场与在线分发、多用户与权限分级、自动更新宿主、跨设备同步、插件沙箱、界面的可视化配置编辑、性能专项。

最后一条不等于不管性能：八个基准每段都跑，超标就处理；但没有「先做出来再统一提速」这个阶段。

---

## 8. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 |
|---|---|---|
| 1 | M0 的「逐份过目」做到什么程度 | 看简版加变更记录，有异议提，无异议算过 |
| 2 | M6 的 Android 验证要不要真机 | 要，模拟器掩盖权限与前台服务问题 |
| 3 | 里程碑之间要不要留缓冲段 | 不留，缓冲会变成默认延期 |

第三条的理由：一旦允许「没完全过也先进下一段、回头补」，补的动作永远不会发生。
