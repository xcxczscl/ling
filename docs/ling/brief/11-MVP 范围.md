# ling 11 MVP 范围（简要版）

MVP 是 M1 加 M2 两个里程碑的合称，从需求里挑 85 条，不含 42 条。不另设门槛。

## 1. 目的与范围

### 1.1 与 10 的关系

| 概念 | 含义 |
|---|---|
| M1 | 最小闭环：装、看状态、调通一次 |
| M2 | 可装可卸：路由清空、账本倒序撤销 |
| **MVP** | **M1 加 M2**，命令行能完成装卸与调用 |

交付时点就是 M2 通过判定的那一刻，版本 `0.0.3-b1`。不额外打标签，不额外验收。

### 1.2 与 01 的关系

MVP 从 `01` 里挑条目，不改需求。需求没有优先级字段，哪些先进 MVP 是本文的事，需求文档不知道 MVP 的存在。

好处是调整 MVP 范围不必回改 127 条需求；坏处是要维护 §3 的对照表。

### 1.3 判定方式

沿用 `10` §5.1 的四条：演示跑通并记 `docs/log/`；§3 条目的验收标准可判真；适用基准在容差内；`precommit.sh` 五项全过。

## 2. MVP 是什么

### 2.1 一句话定义

能从命令行装一个 C++ 插件、看到它激活、让另一个插件调它的方法、再干净卸掉。四个动词：装、看、调、卸。

### 2.2 演示脚本

```bash
ling serve                                  # 首次启动自动装三个内置插件
ling install <程序目录>/plugins/demo-a       # 被调方
ling install <程序目录>/plugins/demo-caller  # 激活时调 demo-a.ping 并写日志
ling plugins                                # 两个 activated 加三个内置
ling logs demo-caller                       # 期望 pong
ling uninstall demo-a                       # 路由清空，data/ 保留
ling uninstall demo-caller --purge          # 连 data/ 一起删
```

命令行没有 `call` 子命令：管理端口只接受 `kernel.*` 方法（`04/06` §3.3），业务方法只能由插件调用。所以演示用第二个插件当调用方。

### 2.3 不是什么

不是能给别人的东西（无界面、无安装包、Android 不能用）；不是功能完整的宿主；不是稳定版本（`0.x` 清单字段与错误码仍会改）；不是可放心的数据容器（`data/` 要自行备份）。

| 编号 | 完整要求 | MVP 判定范围 | 为什么 |

| 071 | 13 个子命令 | 10 个（缺 reload、restart、doctor） | 前两个靠热更新，第三个靠依赖图 |

### 3.3 为什么先做这 85 条

按「少了它装装卸卸就跑不通」筛：装载卸载是核心；路由与事件让插件不成为孤岛；能力门禁与路由同一路径，硬拆会留一个「先不检查」的分支；账本是卸载可逆的前提；内核日志与可观测是上一版最大的教训。

## 4. 明确不含的

### 4.1 四类功能

| 不含 | 意味着什么 | 何时有 |
|---|---|---|
| 依赖声明与调和 | 不能写 `requires`，装顺序自己保证 | M3 |
| 热更新 | 改插件要重启宿主 | M3 |
| 侧车 | 只能 C++ 写插件 | M4 |
| 界面 | 只有命令行 | M5 |

第二条最影响日常：改一行要重启，重装后状态从 `data/` 重新加载。

内核的手工升级在 MVP 内：084 至 086、088、127 都含；不含的只有 087（侧车协议版本），MVP 没有侧车，无从测。

### 4.2 三条临时实现限制

| 限制 | 行为 | 解除 | 要回改 |
|---|---|---|---|
| `requires` 非空 | 拒绝装载，`E_MANIFEST_INVALID`，message 说明不支持依赖声明 | M3 | `04/02` 清单校验 |
| 含 `[sidecar]` 段 | 拒绝装载，`E_MANIFEST_INVALID`，message 说明只支持进程内 | M4 | `04/02` §8 |
| 内置插件只装三个 | `core-ui`、`core-job` 的源码不进 MVP 构建 | M5 | `04/07`、`01` 的 079 与 081 |

选「拒绝」不选「忽略」的理由：清单写了 `requires` 却不解析，插件会以「以为依赖已满足」的状态激活，出错现象是调用时 `E_PLUGIN_MISSING`，而原因发生在装载那一刻。拒绝装载会在正确的时点报正确的错。

`[sidecar]` 同理：静默忽略会让侧车插件被当作进程内插件装载，然后因找不到导出符号而崩溃。

### 4.3 解除顺序

1. M3 解除 `requires`，同时实现调和——只解除不实现，等于允许装载一个起不来的插件。
2. M4 解除 `[sidecar]`，同时实现协议与握手。
3. M5 加回两个内置插件，更新 079 与 081 的判定。

每次解除记 `docs/log/` 并回改 §4.2 指的文档。这张表在 `0.1.0` 之前必须清空——留着它说明某处限制被忘了。

## 5. MVP 期间的已知缺陷

| 现象 | 原因 | 绕过 |
|---|---|---|
| 改插件要重启 | 无热更新 | 重启后 `ling plugins` 确认 |
| 装顺序错了报 `E_PLUGIN_MISSING` | 无调和 | 先装被调方 |
| 不能用 Python 写插件 | 无侧车 | 用 C++ |
| 没有图形界面 | 无 core-ui | 命令行加 `logs --kernel` |
| 没有 `doctor` | 未实现 | 看内核日志，按 `09` §7 处置表查 |
| Android 用不了 | 未做包 | 只在桌面用 |

## 6. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。
| # | 事项 | 结论 |
|---|---|---|
| 1 | MVP 期间能否当日常工具 | 能，每天备份 `data/`；真实使用是发现问题最快的方式 |
| 2 | 演示脚本要不要留档 | 命令与输出贴进 `docs/log/`，不录屏 |
| 3 | MVP 完成后直接进 M3 还是先停一段 | 先停一段，真实使用暴露的问题最值钱，此时改 04 成本最低 |
