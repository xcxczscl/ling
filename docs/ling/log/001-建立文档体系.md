# 001 建立文档体系

> 日期：2026-10-27
> 类型：结构决策

## 发生了什么

仓库从"只有一个 `old/` 参考目录"的状态，转为正式启动新项目：建立目录骨架、定下文档写法和评审流程。

## 定了什么

| 事项 | 结论 |
|---|---|
| 根目录结构 | 只用 `docs/` `main/` `plugins/` `other/` 四个；`old/` 为历史遗留，只读且不扩展 |
| 文档分类 | `common` 公共、`ling` 宿主、`plugins` 各插件、`log` 日志、`archive` 归档、`other` 其他 |
| 文档粒度 | 每份正式文档写详细版 + 简要版；简版放同级 `brief/` 子目录，文件名相同 |
| 文件命名 | 两位序号 + 中文名（`01-需求规格.md`）；日志用三位序号 + 事件名（`001-建立文档体系.md`） |
| 文档序列 | 00 总览与术语、01 需求规格、02 架构设计、03 详细设计、04 构造与开发指南、05 安全设计、06 测试与验收、07 部署与运维（按需） |
| 项目代号 | `LING` 宿主、`RM` 资源管理、`PLR` 内容执行器，用于需求编号 |
| 评审流程 | 写 → 自审（对清单）→ 提问 → 改 → 复审，循环到用户确认为止 |
| 编码前提 | 对应设计文档未定稿，不写业务代码 |
| 日志规则 | 按事件记，一事一文，只增不改 |
| 归档规则 | 按里程碑建子目录，存入即冻结 |
| 协作准则 | 「多问」为核心：凡需判断先问不猜，提问成组编号并附建议 |

## 为什么

- 旧的 `old/docs` 把设计文档和开发文档混在 `dev/` 下，且缺少安全、测试这两个环节，按软件工程完整序列重排。
- 两种粒度是为了让"快速查结论"和"理解为什么"这两类需求不用翻同一份长文。
- 「多问」上升为核心准则，是因为前期靠猜会带来后期返工，成本高于多问几句。

## 影响

- 新增：`docs/common/00-文档编写规范.md`（草案）、`docs/common/01-术语表.md`（草案）、根 `README.md`（框架）
- 修改：`AGENTS.md`（新增第 0 节核心准则、第 2 节目录规则、第 3 节文档先行）
- 新增目录：`docs/{common,ling,ling/brief,plugins,log,archive,other}`、`main/`、`plugins/`、`other/`

## 遗留

- `README.md` 中项目定位、目标与非目标、许可均为【待补】，等用户说明。
- 技术栈未定，`docs/common/00-文档编写规范.md` §5.1 暂用示例命令占位。
- 规范与术语表目前状态为"草案"，尚未定稿。
