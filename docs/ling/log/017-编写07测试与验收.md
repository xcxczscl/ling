## 这份文档的定位：不重复验收标准

`01` 的 127 条需求每条都带「能判真假」的验收标准，那已经是最细的判据。本文如果再抄一遍，就违反单一事实来源，而且两处会漂移。

所以 07 只做四件事：

1. **分层**：五层测试各自跑多快、什么时候跑。
2. **定判据的形式**：性能怎么量、故障怎么造、什么算通过。
3. **给用例编号**：把 `01` 的验收标准挂到 `07` 的用例号上，形成双向可查。
4. **补 01 没有的**：`l1` 至 `l6` 的含义、性能测量的统一方法、故障注入的具体手段。

## 补了一个此前没定义的东西：`l1` 至 `l6` 的含义

`01` §6 的追溯表里出现 `l1_manifest`、`l6_stability` 这些名字，但从没有一处说明 `l1` 与 `l6` 的区别。写 07 时补上：

| 前缀 | 需要多少东西在场 |
|---|---|
| `l1` | 单进程内核，零或一个最小插件 |
| `l2` | 单插件 + 完整上下文 |
| `l3` | 三个以上插件 + 依赖 |
| `l4` | 命令行与管理端口 |
| `l5` | 五个内置插件齐备 |
| `l6` | 跨进程与系统级 |

数字表示「环境复杂度」，不表示先后顺序。这条不定，后续写测试的人会各按各的理解取名。

## 性能测量方法：不写清环境，数字没有意义

§5 定了六项环境要求与四步测量法：

- Release 构建、4 核桌面、本地 SSD、单线程、空处理函数、**笔记本插电并关闭省电模式**。
- 预热 1000 次丢弃 → 采样 → 统计 P50/P95/P99 → 重复 5 轮取 P95 的中位数。

最后一条容易忽略：省电模式会降频，P95 能差一倍。之前 `02` 里那些纸面数字没有对应的测量方法，现在有了。

判定留 10% 容差，且容差必须记进结果、不静默忽略——连续几次都在容差内，说明该调上限或改实现。

## 补了一个缺失的基准

`04/01` §4.5 说「500 条路由下复制快照若超过 1 毫秒，改成持久化数据结构」，但 `01` 的追溯表里没有对应基准。等于给了一个判据，却没有量它的工具。

新增 `l1_bench_snapshot`：500 条路由复制，1 万次采样，上限 1 毫秒。

## 故障注入十五个，全部自动化

手段只有三类：改夹具参数、杀进程、改文件系统状态。

其中两处是刻意的设计：

- **F3 与 F4 是同一场景的两种平台结果**，不算重复：Windows 上「捕获后继续」，Linux 上「退出」。两个都要验，因为 `02` §5.5 把这两条写成了不同的设计约束。
- **F9（磁盘满）依赖 tmpfs，只在 Linux 跑**，Windows 上标 `skipped`。不允许静默跳过，必须在结果里写明原因。

## 把 06 的威胁转成了检查，并标出三条做不到

十二条威胁里九条能自动化，三条只能手工：

- T4（同用户进程冒充）：应用层无法区分，只验证「日志有留痕」。
- T10（转储敏感）：只能人工检查权限与提示。
- T12（Python 依赖漏洞）：不在范围内。

T9（日志泄露）的检查方式值得单说：跑完一轮完整测试后，`grep` 日志里的 token 值与测试载荷的特征串，命中即失败。比人工看日志可靠。

## 手工清单压到八项

保留的三类：看得见的（界面）、拿不到的（Android 真机）、代价过高的（24 小时长稳）。

理由写在 §1.3：一份五十项的手工检查表，实际执行时会被勾着走。宁可少而真做。
