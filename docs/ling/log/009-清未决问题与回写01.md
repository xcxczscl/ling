## 用户对两条的追问与结论

两条我没有直接给结论，而是先算清代价再让用户定。

### 非 Windows 平台进程内插件崩溃不可恢复

用户问「全部走侧车会损失多少性能」。算下来不是「慢一点」，是违约：

| 项 | 进程内 | 侧车 |
|---|---|---|
| 20 个插件常驻内存 | 约 60 MB | 500–800 MB（超 LING-REQ-099 四到六倍） |
| 20 个插件冷启动 | 约 1 秒 | 2–6 秒（超 LING-REQ-095） |
| 装载策略 | 一套 | Windows 与 Linux 分两套 |

结论：接受外部守护（systemd、计划任务），易崩插件改走侧车，文档写明缺口。全侧车不可行。

### 进程内插件用非 C++ 语言的口子

用户问「不保留有什么影响，保留与侧车比性能如何」。答案有两层：

1. **保留的性能影响严格为零**。跨动态库边界只能用 C ABI，不管支不支持其他语言，接口本来就是 C ABI。
2. **技术上关不掉**。无法阻止别人放一个 C ABI 动态库进插件目录，「明确关闭」只是文档上少一句话。

真正的障碍是内存所有权：不同语言编的动态库有自己的分配器，跨库传「它分配、你释放」的指针会崩。所以结论是「保留但不承诺」——能连上不等于能用，这正是不该承诺的理由。
