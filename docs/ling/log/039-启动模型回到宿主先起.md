# log 039 启动模型回到「宿主先起」

> 日期：2026-10-31
> 触发：`log 038` 定的「界面先起、拉起宿主」不采用

## 一、改成什么

`log 038` 第三节写的「双击 → 界面先起 → 界面拉 `ling serve` 子进程」作废。改回：

**宿主先起，界面后起。** 界面不启动宿主，也不停止宿主——唯一例外是按用户存的选项调一次 `kernel.shutdown`。

于是 `core-ui` 只有一种运行方式：被宿主装载。`log 038` 里那张「两种启动方式」的表格整张作废。

## 二、关闭选项归 core-settings

原来的写法是「界面自己决定关窗口时退不退宿主」。改成分工三段：

| 谁 | 做什么 |
|---|---|
| `core-settings` | 存 `core-ui.close_behavior`；读到不存在时写回默认 `keep-host` |
| 界面 | 设置页读出显示、改了就写回；关窗口时按当前值决定要不要调 `kernel.shutdown` |
| 宿主 | 不参与判断 |

界面不自己另记默认值——那样会出现「配置里是 A、界面按 B 执行」的情况。选项放 `core-settings` 而不是界面的 `data/`，是因为它和别的配置一样要能导出、能随备份还原。

## 四、留下一个未定项

**双击入口怎么不弹控制台窗口。** `ling.exe` 是控制台程序，双击必然带黑框。三种做法各有代价：

| 做法 | 代价 |
|---|---|
| 编成 GUI 子系统 | 命令行输出全没了，命令行模式也没了 |
| 另做一个 GUI 启动器 | 多一个 exe，多一处要打包与维护 |
| 快捷方式最小化启动 | 黑框还在，只是缩起来 |

等打包阶段定。这一条已写进 `core-ui/04-两种形态与启动.md` §6 的「未定」，不藏着。
