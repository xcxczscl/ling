# log 046 减少「不该出现的错误」，M4 从协议层起步

> 日期：2026-10-31
> 关联：`docs/ling/04-详细设计/06-管理端口与命令行.md` §4.4、`docs/ling/04-详细设计/02-插件装载与接口.md` §8

## 1. 我上一轮理解错了方向

上一轮把错误码从屏幕上拿掉了，理由是「用户看到 `E_XXX` 会糊涂」。这条只对了一半：**该做的是减少错误本身，不是把错误码藏起来**。用户说的很准——依赖跟着停之后，「插件明明装着却报 `E_PLUGIN_MISSING`」这种错误就不该出现；而真出错时，错误码、说明、下一步三样都该给全，少一样都不好排查。

改回来：

```
$ ling disable no-such
找不到这个插件：no-such（E_PLUGIN_MISSING）
提示：用 ling plugins 看看装了哪些插件，第一列就是插件名。
```

`--json` 仍然给结构化错误，两条路不冲突。

## 2. 顺手掐掉三条「本来不该发生」的错误

| 场景 | 以前 | 现在 |
|---|---|---|
| 启用一个依赖没满足的插件 | 打印「已启用 X」，实际调和又把它停下，用户去调才知道没跑 | 打印「已启用 X，但它现在没能跑起来」+ 原因 + 「把缺的装上它会自动起来」 |
| 调用一个「装着但没在跑」的插件 | 只回 `E_PLUGIN_MISSING`，看起来像没装 | 回 `E_PLUGIN_MISSING` + 「插件现在没在跑：依赖 demo-a 现在用不了」 |
| 卸载后重装、依赖变化的连锁 | 已经由调和处理，不会再出现 | —— |

第二条靠给 `CallOutcome` 加一个 `detail` 字段：插件之间的调用只认 `code`，给人看的路径才读 `detail`。

## 3. 两处遗留的定性

- **计划没做成可取消的独立对象**：这属于 M3 的设计（`04/04` §6.2），不是 M4。但它只在「先预览、确认、再执行」的两段式交互里才有意义，而那正是界面（M5）要做的事。所以计划排到 M5，与 `core-ui` 的「停用前先告诉我会连带谁」一起做。
- **只换 dll 不改清单时不会自动重算**：小改进，排到 M4 之后。要覆盖它得把 dll 的 mtime 也纳入指纹。

## 4. M4 的起点：先把协议做成纯函数

M4 是跨进程，出错时排查成本比进程内高一个数量级（一个「没反应」可能是没起来、握手失败、管道读错、帧不合法）。所以第一步不碰进程，只做帧：

`main/src/sidecar_proto.cpp` + `main/include/ling/sidecar_proto.hpp`

| 函数 | 作用 |
|---|---|
| `parse(line, &frame, &error)` | 解析一行 jsonl，校验 v、op、1 MB 上限，失败给人话原因 |
| `encode(frame)` | 组装一行，覆盖 v/op/id |
| `encode_result` / `encode_error` | 两种应答，结构与 §5.3 一致 |
| `is_sidecar_op` / `is_host_op` | 七种与五种 op 的分类 |

单测 6 个用例：正常解析、六种不合规（空帧、非 JSON、非对象、缺 v、版本不符、缺 op、超长）、无 id 按 0、编码回合、应答结构、op 分类。总数到 45 用例 293 断言。

## 5. M4 后面的顺序

1. **进程层**：起子进程、两根管道、环境变量（`LING_TOKEN` / `LING_PLUGIN_ID` / 数据目录）、按行读、超时与退出检测。
2. **握手**：读 `hello`、校验 token 与版本与 plugin_id、回 `error` 或发 `activate`。
3. **接入装载**：清单放开 `[sidecar]`，`activate` 按轨道分支，`register_method` 与 `subscribe` 变成宿主代登记（账本记「代注销」）。
4. **调用与事件**：`invoke` / `result` / `error` 与 `event`。
5. **停用与崩溃**：`deactivate` → 等 `deactivated` → 关管道；`on-crash` / `always` / `never` 与 2 秒、3 次上限。
6. **按需启停**：`idle_timeout`（§8.7），默认非常驻。
7. **验收**：一个最小 C++ 侧车 fixture，测握手、调用、崩溃重启、强杀。

先做 1 和 2，因为它们不依赖装载器改造，可以用一个「假侧车」进程单独验证。
