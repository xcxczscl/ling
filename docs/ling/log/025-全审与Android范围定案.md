## 二、Android 与 Python 侧车：三份文档各说一套

查出来的冲突是这样的：

| 文档 | 说法 |
|---|---|
| `01` §5 平台矩阵 | 侧车插件在 Android「支持」，备注「Android 需自带解释器」 |
| `02` §10 第 3 条 | 接受 Python 运行时随程序分发，Android 约 30 MB |
| `08` §2.2、§2.3 | `python/` 目录「仅 Windows 与 Linux」；插件「没有 Python 侧车」 |
| `10` §6.3 | 「已定 Android 不含 Python 侧车」 |

前两份与后两份正相反，而 `10` 自己也不自洽：§3.6 说「随程序分发」，§6.3 说不含。

用户定为**支持**。改动落在四处：

- `08` §2.2 包结构去掉「仅 Windows 与 Linux」，apk 同样带 `python/`；
- `08` §2.3 插件范围改为三类都可以，发布说明从「没有 Python 侧车」改成「包多约 30 MB」；
- `10` §3.7 的 M6 通过条件与风险登记同步：M4 就要在 Android 上跑通 Python 侧车，做不出来则回头改 `01` 与 `02`，不在 M6 临时降级；
- `01` §5 矩阵备注改为「Python 运行时随 apk 分发，包体积增加约 30 MB」。

## 三、常驻配额漏掉了「同时存活」

常驻配额只约束声明 `restart = "always"` 的侧车，而按需侧车激活后也会活到 `idle_timeout`。连装三个 Python 插件，三份进程会同时驻留，约 120 MB，而 `LING-REQ-099` 只限单个进程 40 MB，没有总量口径。

用户决定不加淘汰机制，只把话说清楚：

- `01` 的 099 增加总量口径：同时存活 3 个 Python 侧车时 ≤ 240 MB，超出属配置不当，由 `doctor` 报告，不阻止运行；
- `04/02` §8.7 写明不按 LRU 淘汰的理由——淘汰让被淘汰的插件下次调用多付 200 毫秒，换来的只是几十 MB；
- `07` 补 `TC-D07` 覆盖这个场景。

## 四、这一轮的教训

**「脚本通过」只说明格式没问题。** 六类问题里，只有第 1 类能被机械检查发现（现已补上），其余五类都要靠逐段读与跨文档比对。而跨文档比对能查出的前提，是知道「同一个事实写在哪几处」——这次 Android 的四处、常驻的两处，都是靠手工 grep 关键词找到的。

判断一段文档有没有问题，先问「这句话在别的文档里还有没有人写过」，比逐字读更有效。
