## 二、各插件这一轮定下的事

### core-settings

| 决定 | 理由 |
|---|---|
| 整份重写 + 临时文件替换 | 几十 KB 的文件，重写以微秒计；不会出现改了一半 |
| 账本放内核不放插件 | 插件自己会被卸载，账本放它手里就失去撤销依据 |
| 读到更高版本的配置就拒绝装载 | 按空配置继续会让旧版本覆盖新格式，新数据就没了 |
| `value` 为 `null` 表示删键 | 撤销时「原本不存在」要能表达成删除，而不是写空串 |

**四处与当前实现不符**，写进 `02-设计与接口.md` §7：版本过高要拒绝装载、`null` 要删键、坏文件要记 warn、键要加字符集与长度校验。

### core-plugin-manager

孤儿扫描与占用统计已实现；依赖树、预演、批量要到 M3。判据一句话：**要算依赖图的、要调内核写方法的，都做不了**。

一个刻意的边界：**只列孤儿，不删**。数据是使用者的，删除必须手动。

### core-job

这是本轮唯一一个「设计上做了新决定」的插件。

直觉做法是插件起一个定时线程，到点直接 `call`。本项目不这么做：宿主是单线程内核，路由表由内核线程写，插件线程去读就是数据竞争，出错现象随机且难复现。

改为：**内核主循环每 200 毫秒广播一次 `kernel.tick`，`core-job` 订阅它，在回调里检查并执行**。全程在内核线程上。

代价是精度受节拍限制（200 毫秒），对分钟级 cron 没有影响。好处是不用给 `ling_host_api` 加新字段——用现成的事件机制就够。

这需要动两处：`04/01` §6.4 加第三类内核事件，宿主主循环加一次广播。两处都还没改。

### core-ui

拆五份：总览与边界、需求与用例、服务端与接口、页面与交互、两种形态与启动。

三个关键决定：

1. **界面不直连内核。** 每个操作转成一次管理端口调用，走命令行那条路。这样界面与命令行行为永远一致，错误文案只有一份。
2. **两种形态共用一套代码。** `webui` 与 `desktop` 的差别只在「页面由谁显示」，服务端、页面、API 完全相同。
3. **界面不显示内核日志。** 内核日志是修宿主的工具，不能依赖会坏掉的那个部件。界面崩了的时候命令行还在。

## 三、需要拍板的三件事

| 事 | 选项 | 影响的文件 |
|---|---|---|
| `kernel.tick` 事件加不加进 `04/01` | 加，`core-job` 才能开工；不加，`core-job` 停在文档阶段 | `docs/ling/04-详细设计/01-内核四服务.md` §6.4 |
| WebView2 SDK 这个新依赖要不要引 | 引，`desktop` 版才有窗口；不引，只能开浏览器 | `core-ui/04-两种形态与启动.md` §3.2 |
| 关掉界面之后宿主怎么退出 | 一直在后台跑 / 关界面即退 / 加托盘图标 | `core-ui/04-两种形态与启动.md` §7 |

第二件按项目规矩必须先问过才能动手：WebView2 SDK 是第三方依赖，虽然它带来的是系统自带运行时，SDK 本身要进仓库。
