## 一、core-settings 四处改齐

| 项 | 改前 | 改后 |
|---|---|---|
| `schema_version` 更高 | 按空配置继续 | 拒绝装载，插件状态为启动失败，说明「由更高版本写入」 |
| `value` 为 `null` | 存成 `null` | 删除该键（撤销「原本不存在」时要能表达成删除） |
| 配置文件语法错 | 静默按空配置 | 同样继续，但记一行到 stderr，**不改写原文件** |
| `key` 形状 | 只查前缀 | 不超过 128 字节，只允许字母数字与 `_` `-` `.`，不以点结尾、不含连续点 |

载入结果从 `void` 改成三态枚举（正常 / 坏文件 / 版本过高）。三种结果对应三种处理，用一个 bool 表达不了「继续但要记日志」与「直接拒绝装载」的区别。

实测：

```
# 版本 99
core-settings   1.0.0   启动失败   进程内
  说明：E_INTERNAL 入口返回非 0
[core-settings] ...settings.json 由更高版本的 ling 写入，本次不装载

# 坏 JSON
[core-settings] ...settings.json 解析失败，按空配置继续，文件保持原样
文件内容仍是坏的那份，没被覆盖
```

## 二、kernel.tick 落地

`Kernel::publish_tick()` 构造 `{"now": "...", "epoch_ms": ...}` 并广播。宿主主循环在 `poll(200)` 之后调一次，跟着原有节拍走。

心跳**不写内核日志**：每 200 毫秒一条会把日志刷满，排障时反而找不到东西。

## 三、core-job 实现

五个部分：cron 解析、任务存储、三个方法、心跳回调、补跑判断。

### 3.1 cron 解析

五段（分 时 日 月 周），支持 `*`、`n`、`a-b`、`*/n`、`a,b,c`。日与周都限定时按「或」处理。

错误信息指出段名与合法范围：

```
[core-job] 跳过任务 core-job.bad：cron 的「时」段取值 25 超出范围 0 至 23
```

### 3.2 任务存储

写入走 `Context::write_config`，不走直接调 `core-settings.write`。原因：前者由内核填归属插件，后者要调用方自报——自报等于「自己给自己发身份证」，任何插件都能冒充别人写别人的键。

删除就是写 `null`，正好用上 §一 改的那条。

### 3.3 装载顺序的坑

插件按名字母排装载：`core-job` 在 `core-settings` 之前。所以 `core-job` 激活时 `core-settings` 还没起来，读任务定义必然失败。

处理：把「读任务」推迟到第一次心跳——那时所有内置插件都已激活。失败时每 200 毫秒重试一次，最多 50 次（10 秒）后放弃并记一行说明，避免刷屏。

这条也补进了 `04/07` §2.1 表下面：依赖列的 `core-settings@1` 在本期只是「谁先谁后」的说明，清单里不能写（MVP 拒绝非空 `requires`）。

### 3.4 实测

任务 `* * * * *` 调 `core-log.write`：

```
2026-10-31T19:11:58 [info] probe fired
2026-10-31T19:12:00 [info] probe fired
2026-10-31T19:13:00 [info] probe fired
```

19:11:58 那次是启动当分钟补上的：`* * * * *` 表示「每分钟」，插件在 19:11 装载，这一分钟确实还没跑过。这是 cron 的正确语义，不是 bug。

### 3.5 一处文档修正

`02-设计与接口.md` §5.3 原本写「上一次没跑完就跳过」。实现时发现：心跳是串行的，任务没返回下一次心跳就不会开始，所以「上一次还在跑」这个时刻根本不存在。真实后果是「慢任务把整轮心跳拖住」，不是「跳过」。

标记留着（将来引入线程后仍成立），但文档改成如实描述，`CJ-07` 标为「同步模型下不发生，作为防御性用例保留」。
