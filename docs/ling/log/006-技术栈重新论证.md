# 006 技术栈重新论证

> 日期：2026-10-28
> 涉及文档：新增 `docs/ling/02-技术选型.md` 与简版；`docs/common/00-文档编写规范.md`、`docs/ling/00-总览与术语.md`、`docs/ling/01-需求规格.md` 与各简版、`README.md`

## 发生了什么

用户提出：上一版用 Rust 写，因为自己不懂这门语言，几乎全权交给 AI，结果出现很多问题；代码层面打算从头再来，或改用 C++。

这推翻了此前默认的前提。`docs/ling/00-总览与术语.md` 与 `docs/ling/01-需求规格.md` 都默认沿用 Rust + 双轨装载，而技术栈从未正式论证过——规范 §5 的文档序列里也没有「技术选型」这一项。

## 决定

| 决定 | 内容 |
|---|---|
| 先做选型，后做架构 | 原计划的 02 架构设计暂缓，先论证技术栈 |
| 新增文档类型 | 规范 §5 序列插入 `02 技术选型`，其后编号整体后移一位 |
| 论证范围 | C++、Rust、C#、Python 四门语言都摊开，重点论证「CPython 嵌入」与「CIL 托管」能否高速 |
| 结论 | 宿主 C++17、进程内插件 C++、侧车插件 Python 3.14、边界只用 C ABI |

## 论证的关键事实

以下事实经外部核实，不是凭印象写的：

| 事实 | 对结论的影响 |
|---|---|
| NativeAOT 不支持运行时加载程序集（`Assembly.LoadFile`、`Reflection.Emit` 均不可用） | C# 拿不到 NativeAOT 的启动与内存优势，除非放弃动态插件 |
| Android 的 .NET 用 Mono（AOT + 解释器），`AssemblyLoadContext` 自 .NET 6 起可用；但 .NET 11 起 Android 不再提供解释器 | C# 的三端路线在收窄 |
| Python 3.14 起 free-threaded 构建转为正式支持（PEP 779），多解释器进标准库（PEP 734） | 嵌入 Python 的 GIL 问题有缓解路径，但生态未全适配 |
| Rust 社区共识是动态库不卸载；TLS 槽位未释放时 `dlclose` 常不真正卸载 | 进程内热更新在 Rust 上是语言层面限制，不是实现缺陷 |
| C++ 与 Rust 的跨动态库边界都必须退化到 C ABI | 「Rust 比 C++ 安全」在插件边界这一层不成立 |

## 反直觉的中间结论

加权评分表算出的第一名是 **C#（4.20）**，高于 C++（3.25）、Python（3.30）、Rust（2.85）。

没有按评分选，理由写在文档 §4.6 与 §6.2：评分假设「你懂这门语言」，而用户 C++ 有基础、C# 没有；三端评分掩盖了 Android 的 C# 路线在收窄；评分也不反映「将来加新插件语言」的自由度。

这一点在文档里明写了，不做隐藏。选型的结论可以不同于评分，但差异必须解释。
