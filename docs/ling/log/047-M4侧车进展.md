## 2. 卡在哪：调用发出去了，回包收不到

侧车的方法被调用时，宿主发 `invoke`，侧车也回了 `result`——两边日志都证明：

```
宿主：sidecar invoke #1 demo-sidecar.ping → {"args":{},"id":1,"method":"demo-sidecar.ping","op":"invoke","v":1}
侧车：收到 invoke id=1 / 已回应 id=1
```

但宿主在等待循环里 30 秒一帧都没读到，最后按超时返回，`core-job` 那次 tick 被拖了 30 秒（日志里有「耗时 30037 毫秒」）。

已经排掉的可能：

- 管道不通：同一个管道上 hello 与 event 都正常，说明管道本身没问题。
- 帧内容非法：宿主打印出的 invoke 帧是合法 JSON；侧车也能解析并回应。
- 侧车没回：侧车日志写了「已回应 id=1」，说明 `send_line` 执行了。
- 解析失败被吞：加了一条「无法解析侧车的帧」的 warn，没有出现。

剩下的怀疑集中在 `Sidecar::read()` 在「等回包」这条路径上与「等 hello」那条路径的差别。两处都调同一个函数，唯一不同的是调用时机：等 hello 时主循环还没开始跑，等回包时正处在 `kernel.tick` 的事件派发里。下一步先在这条路径上把每次 `PeekNamedPipe` 的返回值和字节数打出来，确认是「没数据」还是「读到了但没凑成行」。

**这一条不修好，M4 不能算完成**：方法调用是侧车轨道的核心用途，`core-ui` 要靠它，Python 插件也要靠它。

## 3. 另外两处要知道的

1. **POSIX 那一半没做**。`Sidecar::start` 在非 Windows 上直接返回「这个平台还没做」。设计上是 fork + 两根 pipe + exec，但按之前的教训（Linux 分支从没编译过），不写「看起来对但没验证」的代码，等真在 Linux 上编译时一起做。
2. **按需启停（`idle_timeout`）没做**。现在是常驻：激活后一直跑，直到停用或崩溃。§8.7 要求默认按需（空闲超时退出、下次调用再起），这一条依赖调用路径先修好。

## 4. 顺带修的两个真问题

- **读帧会吞掉第二帧**：`read()` 原来每次读一块，取第一行就丢弃剩下的，导致一次读到的两帧只处理一帧。表现是「偶发丢应答」。改成保留残余字节，凑够一行才解析。事件计数从 0 变成正常，就是这条修好之后的事。
- **环境变量拼块失败**：自己拼 `CreateProcessW` 的环境块，一路返回错误码 87（参数无效），没有任何线索。改成「临时设三项 → 起进程 → 还原」，宿主是单线程，不存在并发读写环境的问题。

## 5. 现状与边界

`demo-sidecar` 是仓库里的示例，不会被预装，`ling install` 之后才生效。它的存在价值是把侧车轨道跑通，同时当作以后写 C++ 侧车的模板。

现有 45 个单测用例全过，五个验收脚本、`l3_reconcile` 19 项、`ui_smoke` 20 项、`job_cli` 13 项都不受影响——侧车是新插件，没装就不参与。
