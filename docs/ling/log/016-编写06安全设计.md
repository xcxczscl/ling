## 这份文档最难的地方：先说清不防什么

项目一路留下的结论是「ling 不是沙箱，插件是可信代码」。在这个前提下，安全设计如果只写「要注意安全」「做好校验」，就是凑字数。

所以本文的重心是**划边界**：信任边界四层、十二条威胁、六类明确不防的东西。不防的每一条都写了理由，目的是让读者不会误以为已有防护。

最关键的一句写在 §2.1：**同账户下的其他程序与宿主权限相同**。它能读口令文件、改插件文件、attach 到进程。这类威胁超出应用层能力，本文不承诺防护。所以「跨用户能防，同用户不能防」是全文的结论。

## 补上的真实缺口：侧车握手没有认证

写 §3 时发现 `04/02` §8.4 的握手只校验协议版本与插件编号，**没有认证**。本机任意进程连上侧车端口、发一个 `hello`，就能冒充宿主给侧车下指令。

这不是理论问题：侧车端口是宿主监听的回环端口，本机任何进程都连得上。

补法：宿主启动侧车时经环境变量 `LING_TOKEN` 传一个随机串，侧车首帧 `hello` 必须带 `token`，宿主常量时间比较，不符回 `E_AUTH` 并断开。

用环境变量而不是命令行参数，是因为命令行参数在进程列表里对所有用户可见（Linux 的 `/proc/<pid>/cmdline`），环境变量只有同用户与 root 可读。

已回改 `04/02` 的 §6.2、§8.2、§8.4 两版，握手顺序改为「认证先于版本协商」——未通过认证的连接不能探测协议版本。

这条的边界也写清了：它挡住跨用户，挡不住同用户。

## 一个必须说准的定位：能力门禁不是沙箱

`01` 的 023 至 027 定义了四项能力与两处校验。一路写下来，容易被理解成「这就是安全机制」。本文 §4 专门纠这个：

| 门禁防什么 | 门禁不防什么 |
|---|---|
| 用了没声明的能力（注册时拒） | 具体文件路径与网络地址 |
| 撤销后仍被使用（调用时拒） | 调用频率 |
| 事后追责不清（每次被拒都记 trace id） | 数据外泄 |
| —— | **绕过 `Context` 直接调系统 API** |

最后一条最关键：进程内插件与宿主同权限，动态库可以直接调 `open`、`socket`，门禁完全看不到。所以准确定位是**审计钩子与误用拦截**，写成「安全机制」会让人高估它。

## 三个有意识的取舍

文档里写明「这是取舍不是疏忽」，避免后来者以为是漏掉的：

### 一、日志保留完整路径

日志里会出现 `/home/user/photos/2024/img.jpg`，泄露用户名与目录结构。

三个选项：全部脱敏（排障价值大降）、保留路径（泄露结构）、保留路径靠文件权限兜。**选第三个**——日志的主要用途就是排障，路径是最关键信息；`logs/` 随数据根 0700，非本用户读不到。

要把日志发给别人时，由发的人自己先脱敏。

### 二、不引入 TLS

端口只绑回环，流量不出本机内核；自签证书的信任、过期、续期对个人工具是纯负担；本机嗅探需要更高权限，而同用户威胁已承认无法防。

将来真要做远程访问，正确做法是在前面放专用代理（SSH 隧道、nginx），把 TLS 交给成熟工具，而不是给管理端口加一层半吊子加密。

### 三、debug 级别只记载荷摘要

记前 32 字节的十六进制摘要，不记原文。够判断「两次调用参数是否相同」，不够还原内容——完全记会让日志变成数据副本，完全不记又无法判断传得对不对。

## 防住的具体攻击

| 攻击 | 措施 |
|---|---|
| 端口被局域网访问 | 回环绑定 |
| 本机其他用户控制宿主 | 首帧口令 + 0600 + 数据根 0700 |
| 伪造侧车 | 握手口令（本文新增） |
| 清单里写 `../../etc/passwd` | 字面检查 + 真实路径确认 |
| zip-slip（zip 条目名带 `..`） | 解压到临时目录后逐项校验，通过才移动 |
| 符号链接绕过路径检查 | 插件目录及其文件是链接即拒装 |
| `--purge` 删错数据 | 显式参数 + 打印绝对路径 + 输入编号确认 |
| 依赖被换成恶意版本 | vcpkg baseline 锁版本 |
