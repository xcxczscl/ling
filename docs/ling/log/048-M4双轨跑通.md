## 1. 上一轮那个「卡住」是误判

上一轮记的是「invoke 发出去了，宿主 30 秒读不到回包」。这次先做了隔离实验：新增 `tests/manual/sidecar_probe.cpp`，不经内核、直接用 `Sidecar` 类驱动真的侧车进程，走一遍 hello → activate → invoke。

结果一次全过，调用 26 毫秒返回。

回到内核链路复测，**也是通的**——日志里有 `invoke #1 完成，用时 26 毫秒`。也就是说那个超时是「读帧吞掉第二帧」这个 bug 的残留现象，修完之后就好了，我上一轮没重新验证就下了「卡住」的结论。

教训记这里：修完 bug 要把当时失败的那条路径重跑一遍，否则很容易把「已修但没验」当成「还没修」。

**不是设计问题。** 协议、管道、握手都没有要改的地方。

## 2. 这一轮补完的部分

### 2.1 按需启停

设计里定了「默认没有任何常驻侧车」（`04/02` §8.7），上一轮只做了激活后常驻。这次补齐：

- 清单新增 `sidecar.idle_timeout`（默认 60 秒），无**方法调用**超过这个时长，侧车自己退出。
- 退出走 `shutdown` 帧，让它体面收尾；一秒不退才杀。
- **状态保持 `activated`**：进程没了不等于插件停了，`ling plugins` 里仍然显示已启用。
- 下次调用时冷启动：`invoke_sidecar` 发现进程不在，先重新握手拉起，再发请求。实测 0 毫秒级。
- 路由与订阅在空闲退出时**故意保留**：清掉的话，下次调用只会得到「没有这个方法」，永远走不到冷启动那一步。
- `restart = "always"` 的侧车不因空闲退出。

判断「在用没用」只看方法调用，不看事件。订阅了 `kernel.tick` 的侧车会一直收到事件，如果事件也算使用，就永远退不出去了。

### 2.2 Python 运行时

清单新增两个字段：

```toml
[sidecar]
runtime = "python"
entry = "main.py"
```

两种运行时的协议完全一样，差别只在宿主用什么起这个进程。解释器按 `LING_PYTHON` → `<程序目录>/runtime/python/` → PATH 里的 `python` 找。第三条是过渡手段，正式发布靠第二条（打包时把 Python 放进去）。

配套：

| 文件 | 作用 |
|---|---|
| `main/python/ling_sidecar.py` | Python 侧 SDK：握手、帧分派、方法登记、事件回调、自测 |
| `plugins/demo-py/` | Python 侧车示例，与 C++ 的 `demo-sidecar` 做同一批事 |
| `LING_SDK_DIR` 环境变量 | 插件不必各自拷一份 SDK |

**一个容易踩的坑**：宿主编成「侧车的 stderr 与 stdout 接同一根管道」（这样崩溃信息不会丢），所以侧车往 stdout 打的任何非帧文本都会被当成坏帧，宿主判定不合法后断开。Python SDK 因此把 stderr 重定向到 `<数据目录>/<插件名>.log`，插件打日志用 `host.log()`。

### 2.3 POSIX 管道

`Sidecar` 的 Windows 半边之外，把 POSIX 那半边也写完了：`pipe` + `fork` + `dup2` + `execl("/bin/sh", "-c", …)`，读侧用 `poll`，退出用 `SIGTERM` 再 `SIGKILL`。

**但这段从头到尾没在 Linux 上编译过。** 按之前的教训，不写「看着对但没编译过」还假装验证过的代码——所以这里如实标：代码在，验证没有。第一次上 Linux 的第一件事是编译，第二件事是跑一遍 `l4_sidecar.py`。

## 3. 顺手修的三处

| 问题 | 原因 | 改法 |
|---|---|---|
| 侧车回调宿主时可能崩 | 把返回值直接 `json::parse` 后塞进帧，非 JSON 的返回值（如 `pong`）会变成 `discarded`，序列化时抛异常 | 解析失败就按字符串带回去 |
| 停用后 `ling plugins` 显示「进程内」 | 轨道取自运行时状态 `plugin.sidecar`，停用后进程没了就成了 false | 轨道改看清单里的 `[sidecar]` 段 |
| 侧车的 `restart`、`idle_timeout` 写错不报错 | 只在运行到「该退出时不退出」才发现 | 清单校验时拦住，指出合法取值 |

## 4. 验证

新增 `tests/acceptance/l4_sidecar.py`，32 项：

| 段 | 覆盖 |
|---|---|
| 装载与握手 | 装上即启用、轨道正确、进程在、宿主代登记方法 |
| 调用往返 | 侧车在第一个心跳时自测（侧车 → 宿主 → 侧车），两个运行时各一次 |
| 事件 | 心跳持续送达 |
| 崩溃重启 | `taskkill` 后 2 秒回到 `activated`，宿主全程照常响应 |

| 按需启停 | 空闲 5 秒退出、状态仍 `activated`、被调用时冷启动 |
| 双轨 | C++ 与 Python 两个侧车同时在跑 |
| 卸载 | 进程收走，`data/` 留着 |

全套回归：单测 45 用例 293 断言、五个验收脚本、`l3_reconcile` 19 项、`ui_smoke` 20 项、`job_cli` 13 项、`l4_sidecar` 32 项。

## 5. 没做的

- **常驻配额 `E_RESIDENT_LIMIT`**：设计要求「Python 侧车最多 1 个常驻」，本期没有任何常驻场景（内置插件里没有 Python 侧车），这条随 M5 的 `core-ui` 一起接。
- **Linux 编译与验证**：见 §2.3。
- **随程序分发的 Python 运行时**：现在是找 PATH 里的 `python`。真正打包（M6）时要把运行时放进 `<程序目录>/runtime/python/`，代码已经按这个位置找，不用再改。
