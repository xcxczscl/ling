| 部分 | 位置 | 性质 |
|---|---|---|
| 依赖写法解析、版本约束匹配、依赖图、环检测、拓扑序、三态计划 | `main/src/depgraph.cpp` | 纯函数，不碰装载表 |

## 2. 为什么把计算单独拎出来

依赖这块最容易错的三件事是环、漏边、顺序。它们都不会崩，只会让结果看起来很怪（插件永远不激活、停用顺序反了）。做成 `depgraph.cpp` 里的纯函数后，单测能直接把这些压住：`tests/unit/test_depgraph.cpp` 七个用例，覆盖写法解析、逐段相等、未满足的两种原因、环检测给出具体环路、拓扑序、三态计划（含「先停后起」与「空计划」）。

## 3. 实测链路

新增 `plugins/demo-b`：清单里写 `[requires] plugins = ["demo-a@1"]`，自己只注册一个 `demo-b.hello`。

```
$ ling install plugins/demo-b        # 此时没装 demo-a
已安装 demo-b 1.0.0，但现在还用不了。
  原因：缺 demo-a@1（没装这个插件）
  把缺的装上就会自动启用，不用重启。

$ ling plugins
demo-b   1.0.0   已停用   进程内
  说明：缺 demo-a@1（没装这个插件）

$ ling install plugins/demo-a
已安装 demo-a 1.0.0，现在可以用。

$ ling plugins
demo-a   1.0.0   已启用
demo-b   1.0.0   已启用        # 自动启用，没重启

$ ling uninstall demo-a
$ ling plugins
demo-b   1.0.0   已停用
  说明：缺 demo-a@1（没装这个插件）
```

`tests/acceptance/l3_reconcile.py` 把这条链固化成 9 项检查。

## 4. 两处比设计简化的地方

1. **没有独立的 `Plan` 对象与 `plan_id`**：调和当场算、当场执行，不对外暴露计划，也没有 `kernel.plan.step` 事件。那是 S4 的事——热更新要复用「先停后起」的同一个计划对象，那时再把计划提出来，比现在先摆一个没人用的结构好。
2. **触发点只有三个**：本文的 §7.1 列了七个（安装、卸载、启用、停用、改清单、改版本、启动）。目前启用与停用各自直接处理，没有再跑一遍调和。

## 5. 一处与直觉不同的判定，记下来

依赖是否满足只看「装没装、版本对不对」，**不看目标插件是否激活**（`04/04` §5.1 的三态表）。所以：

```
ling disable demo-a     # demo-b 仍然算「需求满足」，继续激活
```

此时 `demo-b` 调 `demo-a.ping` 会拿到 `E_PLUGIN_MISSING`。这是既定取舍，M3 不改；要改成「依赖停用就跟着停」，需要在 §5.1 加一列并评估对卸载链的影响。已写进 `04/04` §8.1 与 `10` 的后续项。

## 6. 一个环境坑

`l3_reconcile.py` 第一版把宿主输出接到 `subprocess.PIPE` 又从不读取。加到第 9 项时 `shutdown` 之后进程迟迟不退——不是 shutdown 有问题，是宿主写日志时管道缓冲满了，阻塞在写调用上。改成写文件后立刻正常。

教训：验收脚本起长驻进程时，输出要么接到文件，要么起一个读取线程，别用「PIPE 但没人读」。
