## 2. 仓库布局

### 2.1 目录总览

```
ling/
├── AGENTS.md                    协作约定
├── README.md                    项目说明
├── CMakeLists.txt               顶层构建入口
├── CMakePresets.json            三平台构建预设
├── vcpkg.json                   依赖清单
├── vcpkg-configuration.json     vcpkg 基线（锁版本）
├── .clang-format                格式规则
├── .clang-tidy                  静态分析规则
├── docs/                        全部文档（含 brief/ 简版）
├── main/                        宿主源码
│   ├── CMakeLists.txt
│   ├── include/ling/            对外头文件
│   ├── src/                     内核实现，按模块分目录
│   ├── builtin-plugins/         五个内置插件源码
│   └── app/                     可执行入口
├── plugins/                     业务插件源码，一个插件一个子目录
│   ├── demo-a/                  S1 用的最小示例
│   └── demo-b/                  S5 用的侧车示例
├── tests/                       测试，与生产代码完全分离
│   ├── unit/                    单元测试
│   ├── acceptance/              验收脚本（对应 01 里的 l1 至 l7）
│   └── CMakeLists.txt
├── other/                       脚本与工具
│   ├── cmake/                   LingOptions.cmake、LingPlugin.cmake
│   ├── tools/                   check_docs.py、precommit.sh
│   └── stu/                     个人学习材料，与项目无关
├── run/                         构建产物落点，不入库
└── old/                         历史版本，只读参考
```

两个容易混的点先说明：

| 名字 | 含义 |
|---|---|
| 仓库的 `plugins/` | **源码**目录，放各插件的代码 |
| 数据根的 `plugins/` | **安装**目录，放已装插件的产物与 `data/` |

同名不同层：前者进版本库，后者是运行时数据，由宿主自己创建。文档里提到「安装目录」时一律写 `<数据根>/plugins/`。

### 2.2 内核七个模块

| 模块 | 目录 | 职责 | 依赖 | 对应 04 |
|---|---|---|---|---|
| `kernel` | `src/kernel/` | `Kernel` 对象、快照、请求队列、启动与关闭顺序 | 无 | 04/01 §2 至 §4 |
| `route` | `src/route/` | 路由表的读写、注册校验、调用分派 | `kernel` | 04/01 §5 |
| `event` | `src/event/` | 订阅表、主题匹配、派发与超时 | `kernel` | 04/01 §6 |
| `gate` | `src/gate/` | 能力集、两处校验、撤销名单 | `kernel` | 04/01 §7 |
| `depend` | `src/depend/` | 依赖图、版本匹配、环检测、计划计算与执行 | `kernel`、`loader` | 04/04 |
| `loader` | `src/loader/` | 清单解析与校验、两条轨道的装载、侧车客户端 | `kernel`、`route`、`event`、`gate` | 04/02、04/05 |
| `log` | `src/log/` | 内核日志、异步队列、日志级别 | `kernel` | 04/01 §9 |

骨架单列成 `kernel` 模块，因为它被其余六个依赖。若把它混在某个业务模块里，那个模块就会变成「所有人都要 include 的模块」，实质上退化成一个环。

### 2.3 依赖规则

单向，禁止成环：

```
kernel  ←── route / event / gate / log
kernel  ←── depend ←── loader
        ←── route / event / gate
```

允许的额外边只有两条：`depend → loader`（执行计划要调装载）与 `loader → route/event/gate`（装载时注册方法、订阅、校验能力）。

检查方式：每个模块的 `CMakeLists.txt` 只声明自己实际 include 的模块为依赖，配置阶段由 CMake 检查成环。**不靠人看目录判断。**

### 2.4 文件与命名

| 对象 | 规则 | 来源 |
|---|---|---|
| 类型 | `PascalCase`，如 `PluginRegistry` | `02` §8.3 |
| 函数与方法 | `snake_case`，如 `register_method` | 同上 |
| 成员变量 | 后缀下划线，如 `entries_` | 同上 |
| 常量 | `k` 前缀，如 `kMaxPayloadBytes` | 同上 |
| 文件 | `snake_case.cpp`，一个文件一个主要类型 | 同上 |
| 单文件行数 | 不超过 500 行 | `02` §8.1 |
| 单个函数 | 不超过 60 行 | `02` §8.2 |
| 注释 | 写「为什么这么做」，不写「这行在做什么」 | `02` §8.3 |

内部实现放 `detail/` 子目录，`detail/` 里的类型不允许出现在对外头文件中。

### 2.5 两个对外头文件

| 文件 | 语言 | 谁用 | 内容 |
|---|---|---|---|
| `include/ling/plugin_api.h` | 纯 C | 所有插件 | `ling_host_api`、`ling_plugin_descriptor`、`ling_plugin_entry` 的声明、能力位与错误码常量（`04/02` §4） |
| `include/ling/sdk.hpp` | C++17 | 用 C++ 写插件的作者 | 对 `plugin_api.h` 的薄封装：把 `void* ctx` 包成类、把错误码转成异常或 `Result`、提供 `LING_PLUGIN` 注册宏 |

`plugin_api.h` 必须是纯 C 且不包含任何 C++ 头文件——它要能被 Python 的 `ctypes`、Rust 的 `bindgen`、Zig 的 `@cImport` 直接解析。这是「保留语言口子但不承诺」的具体做法（`02` §7.3）。

`sdk.hpp` 里的封装不做任何跨边界的事：它只是把函数指针调用写得更顺手，所有字段与调用约定仍然来自 C 结构体。

## 3. 构建系统

### 3.1 目标划分

| 目标 | 类型 | 产物 | 说明 |
|---|---|---|---|
| `ling_core` | 静态库 | `ling_core.a` / `.lib` | 七个模块编译成一个库，测试与宿主都链接它 |
| `ling` | 可执行文件 | `ling.exe` / `ling` | 命令行入口，链接 `ling_core` |
| `core-ui` | 可执行文件 | `core-ui.exe` / `core-ui` | 侧车形态的内置插件 |
| `core-settings` 至 `core-log` | 动态库 | `.dll` / `.so` | 四个进程内内置插件 |
| `demo-a` | 动态库 | `.dll` / `.so` | 最小示例，S1 用 |
| `demo-b` | 可执行文件 | `demo-b.exe` / `demo-b` | 侧车示例，S5 用 |
| `ling_unit` | 可执行文件 | 测试运行器 | 链接 `ling_core` 与 Catch2 |
| `ling_acceptance` | 可执行文件 | 验收运行器 | 链接 `ling_core`，起真实进程 |

`ling_core` 编成静态库而不是动态库：宿主与插件不该各自带一份内核代码，静态库在链接期把需要的部分合进去，没有装载期开销。

### 3.2 统一编译选项

宿主与所有进程内插件必须完全一致（`02` §5.4）。选项不写在各个 `CMakeLists.txt` 里，而是由 `other/cmake/LingOptions.cmake` 提供两个函数，所有目标都必须调用：

```cmake
ling_set_standard(target)      # C++17、异常模型、运行时库
ling_set_warnings(target)      # 警告全集并视为错误
ling_set_hardening(target)     # 帧指针、栈保护（Release 也开）
```

三个函数的实际内容：

| 项 | MSVC | Clang / NDK Clang | 说明 |
|---|---|---|---|
| 标准 | `/std:c++17` | `-std=c++17` | 三平台统一 |
| 警告 | `/W4` | `-Wall -Wextra -Wpedantic` | 全集 |
| 警告视为错误 | `/WX` | `-Werror` | 不许带着警告提交 |
| 运行时库 | `/MD`（动态 CRT） | 默认 | 不许与 `/MT` 混用 |
| 异常模型 | `/EHsc` | 默认 | 统一，避免跨边界行为不一致 |
| 帧指针 | `/Oy-` | `-fno-omit-frame-pointer` | 崩溃时能出完整调用栈 |
| 栈保护 | `/GS` | `-fstack-protector-strong` | 防栈溢出 |
| 架构 | x64 | x86_64 | Android 用 `arm64-v8a` |

Debug 与 Release 只差三处：代码生成等级（`/Od` 或 `-O0` 对 `/O2` 或 `-O2`）、调试信息（`/Zi` 或 `-g`）、断言（Release 定义 `NDEBUG`）。**其余选项完全一致**——这条是硬性的，混用 Debug 插件与 Release 宿主会因对象布局差异产生未定义行为。

不关闭 RTTI：`std::variant` 在部分实现上依赖它，而请求队列用到了 `std::variant`（`04/01` §8.1）。跨边界不用 RTTI 这条（`02` §5.3）由代码规范保证，不由编译选项强制。

### 3.3 依赖与锁文件

| 依赖 | 用途 | 引入方式 |
|---|---|---|
| Catch2 v3 | 测试框架，只链接测试目标 | vcpkg |
| toml++ | 解析 `plugin.toml` | vcpkg，header-only |
| nlohmann/json | 协议帧、错误结构、日志行的 JSON 编解码 | vcpkg，header-only |

三个都在 `vcpkg.json` 里声明，版本由 `vcpkg-configuration.json` 的 baseline 锁定。

**为什么必须有 baseline**：不锁版本时，今天编出来的程序和三个月后编出来的会用到不同版本的依赖。出了问题无法复现，也无法判断「是代码改坏了还是依赖变了」。`02` §6.1 把这条列为硬要求。

新增依赖的规则（`AGENTS.md` §4）：先说明用途、体积、安全与维护影响，获同意后写入 `vcpkg.json`。本文列出的三个已按此流程确认。

`core-ui` 的 HTTP 服务依赖不在本期定：它在 S6 才动，届时按同一流程引入。

### 3.4 CMake Presets

用 Presets 统一入口，避免每个平台记一套参数：

| Preset | 平台 | 构建类型 | 说明 |
|---|---|---|---|
| `win-debug` | Windows | Debug | 默认开发用，开 ASan |
| `win-release` | Windows | Release | 打包用 |
| `linux-debug` | Linux | Debug | 开 ASan 与 UBSan |
| `linux-release` | Linux | Release | 打包用 |
| `android-release` | Android | Release | NDK 工具链，只出产物不跑测试 |

Presets 里固定三件事：工具链文件、构建目录 `run/build/<preset>/`、`CMAKE_EXPORT_COMPILE_COMMANDS=ON`（clang-tidy 需要）。

### 3.5 产物落点

| 产物 | 落点 |
|---|---|
| 宿主与内置插件 | `run/<preset>/` |
| 动态库插件 | 构建后由 CMake 复制到 `run/<preset>/plugins/<编号>/` |
| 侧车可执行文件 | 同上，复制到 `plugins/<编号>/sidecar/` |
| 测试运行器 | `run/<preset>/tests/` |

构建完直接 `run/<preset>/ling serve --data-dir run/<preset>/data` 就能跑起来，不需要手工拷文件。`--data-dir` 指向构建目录是为了让开发时的数据与实际使用的数据分开，避免调试把用户配置弄坏。

## 4. 质量门

五项，由 `other/tools/precommit.sh` 一条命令串起来。

### 4.1 警告视为错误

已在 §3.2 里由 `ling_set_warnings` 提供。**编译通过即代表零警告**，不需要额外跑一条命令。

新代码若触发警告，只有两种处理：改代码，或在极小范围内用 `#pragma` 局部关闭并写明理由。不允许全局关闭某一类警告。

### 4.2 消毒器

AddressSanitizer（查越界、释放后使用、重复释放）与 UndefinedBehaviorSanitizer（查有符号溢出、空指针解引用、对齐错误）只在 Debug 构建开启。

| 平台 | 开启方式 | 限制 |
|---|---|---|
| Windows | `/fsanitize=address`（MSVC 2019 起，仅 x64） | 不支持 UBSan |
| Linux | `-fsanitize=address,undefined -fno-sanitize-recover=all` | 全支持 |
| Android | 同 Linux，但只在真机或模拟器上跑 | —— |

`-fno-sanitize-recover=all` 让 UBSan 遇错即停，而不是打印一行继续跑。带上它，测试才会因为未定义行为失败。

这条弥补了 Windows 没有 UBSan 的缺口：Windows 上的未定义行为，靠 Linux 侧的同名测试兜住。

### 4.3 静态分析

`clang-tidy`，配置文件 `.clang-tidy` 里启用两组规则：

| 规则组 | 抓什么 |
|---|---|
| `bugprone-*` | 悬垂引用、误用 `sizeof`、复制而非引用、异常安全的资源泄漏 |
| `cppcoreguidelines-*` | 所有权误用、隐式转换、生命周期问题 |

不做的事：不启用 `modernize-*`（会要求用你还没学的特性），不启用 `readability-*`（格式交给 clang-format）。

跑法：`clang-tidy -p run/build/<preset> <源文件>`，或由脚本遍历 `compile_commands.json` 里的全部源文件。

### 4.4 格式化

`clang-format`，配置文件 `.clang-format`。规则基调：

| 项 | 值 | 理由 |
|---|---|---|
| 缩进 | 4 空格，不用 Tab | 与文档里的代码块一致 |
| 列宽 | 100 | 宽屏与分屏都能看全 |
| 大括号 | 左括号不换行 | 行数少，`04` 里的示例也是这个风格 |
| 指针与引用 | `int* p`，星号靠类型 | 强调「类型是指针」 |
| include 排序 | 按字母，分组：自身头文件、标准库、第三方、项目内 | 减少合并冲突 |

格式不靠人记：`precommit.sh` 跑 `clang-format --dry-run --Werror`，不合规即失败。

### 4.5 提交前脚本

`other/tools/precommit.sh`，按顺序跑五项，任一失败即停：

| 序 | 检查 | 失败含义 |
|---|---|---|
| 1 | `check_docs.py` | 文档两版不一致、表格列数错、禁用词、乱码 |
| 2 | `clang-format --dry-run --Werror` | 格式不合规 |
| 3 | 构建（Debug） | 编译不过或有警告 |
| 4 | `ling_unit` | 单元测试失败 |
| 5 | `clang-tidy` | 静态分析报问题 |

验收脚本（`ling_acceptance`）不进这一轮：它要起真实进程，跑一次十几秒，放在每个切片完成时跑，不放在每次提交前。

### 4.6 测试与生产代码的边界

这是本文的硬约束之二。三条规则：

| 规则 | 具体要求 |
|---|---|
| 生产代码不包含测试框架 | `main/src/` 与 `main/include/` 里不出现 `catch2/` 的任何头文件 |
| 测试代码不进生产目录 | 所有测试放 `tests/`，不放在 `src/` 旁边 |
| 不为测试改生产代码的可见性 | 不用 `friend`、不用 `#define private public`、不加 `#ifdef TESTING` 分支 |

需要测内部状态时，走公开的只读接口。`04/01` §2.1 里 `Kernel::snapshot()` 已经是公开方法，测试直接取快照检查表内容，不需要额外开口子。

这条规则的实际代价要说清：某些内部函数（例如不变式校验）无法单独测，只能通过公开行为间接测。这个代价是接受的——**为了可测性把私有实现暴露出去，等于让测试成为设计的主导，长期会把代码结构带偏。**

若某个函数确实需要单独测而它又是纯函数（例如版本匹配、主题匹配），把它放在独立的头文件里、用内部链接之外的普通函数暴露，测试直接调。这类函数本来就该是自由的，不存在「暴露私有实现」的问题。

## 5. 开发顺序

七个切片，每片都能跑起来。前一片是后一片的前提，不跳。

### 5.1 切片表

| 片 | 目标 | 产物 | 验证方式 |
|---|---|---|---|
| S0 | 骨架能编能跑 | 顶层 CMake、三个 Presets 可用、质量门生效、空 `ling --version` | 三平台构建通过；故意写一个未使用变量，断言构建失败 |
| S1 | 最小闭环 | 清单解析、装载一个空插件、注册一个方法、调通一次 | 装 `demo-a` → `plugins` 显示 activated → `l2_call` 由调用方插件调 `demo-a.ping` 收到 `pong` |
| S2 | 上下文与账本 | `Context` 十个方法、账本分段、撤销、数据目录 | 注册三个方法后卸载，账本倒序撤销，路由表清空 |
| S3 | 依赖与调和 | 依赖图、环检测、三态判定、计划、200 毫秒去抖 | 先装依赖方再装被依赖方，前者自动激活；成环被拒且不留残件 |
| S4 | 热更新 | 七步流程、私有副本、重载窗口、回滚 | 100 次重载脚本；新版 activate 故意失败，断言回滚到旧版 |
| S5 | 侧车 | jsonl 协议、握手、C++ 侧车（`demo-b`）、Python 侧车 | 起 `demo-b` 并调通；强杀断言 `crashed` 与 2 秒重启 |
| S6 | 内置插件与界面 | 五个内置插件、`core-ui` 能打开、`doctor` 四项 | 界面里完成装、卸、启、停；成环时 `doctor` 退出码 1 |

### 5.2 每片的出口条件

一片算完成，要同时满足四条：

1. 该片的验证方式跑通，结果记录在 `docs/log/` 的对应条目里。
2. 新增的公开接口有单元测试，负向用例（非法输入、失败路径）不少于正向用例的一半。
3. `precommit.sh` 五项全过。
4. 该片涉及的 04 条目，实现与文档一致；不一致时改文档或改代码，不允许放着。

第 4 条是这套流程里最容易松的一环：代码写着写着发现 04 的某个设计有问题，正确的做法是回去改 04 并记变更，而不是「代码这样写更顺手」。

### 5.3 不做什么

按 `02` §8.1 的禁用清单，S0 到 S6 全程不做：模板元编程、多继承、运算符重载（除显然语义）、宏定义控制流、全局可变状态、单文件超 500 行。

「先把功能做出来，回头再整理」在这里不成立：整理模板元编程的成本远高于一开始就不写。

### 6.2 头文件的三条规矩

| 规矩 | 原因 |
|---|---|
| 头文件里不写实现（除 `constexpr` 与内联小函数） | 编译慢、改动触发全量重编 |

| 模块之间只 include 对方目录下的 `*.hpp`，不 include `detail/*.hpp` | 防止依赖穿透 |

## 8. 调试方法

### 8.1 日志

| 场景 | 参数 | 看什么 |
|---|---|---|
| 日常开发 | `--log-level info`（默认） | 插件状态变化、装载每一步、被拒操作 |
| 查「为什么这次调用没到」 | `--log-level debug` | 每次调用与广播的摘要，含方法名、耗时、返回码 |
| 只看内核自身 | `logs --kernel` | 不依赖任何插件 |
| 追一次操作的全链 | `grep <trace id>` | 从命令行到侧车注册的完整链条 |

trace id 在命令行发起时生成，随请求传到侧车。`install` 的输出里会带上这次的 trace id，方便直接 grep。

### 8.2 Windows 崩溃转储

进程内插件崩溃时（`docs/ling/02-技术选型.md` §5.5 的崩溃分类与向量化异常处理），处理顺序：

1. 异常处理器先把当前线程的调用栈写入内核日志（只写地址，不解析符号）。
2. 再调 `MiniDumpWriteDump` 生成 `.dmp` 到 `<数据根>/logs/`。
3. 然后按 `docs/ling/02-技术选型.md` §5.5 走「标记故障、拒绝后续调用、撤销效应」。

事后解析：

```bash
# 需要与崩溃时同一份二进制与 pdb  [未验证]
cdb -z ling.dmp -y run/win-debug -c "kb; q"
```

`.dmp` 与 pdb 必须匹配，否则只能看到地址。所以打包时保留 pdb，与版本号一起归档。

### 8.3 侧车附加调试

侧车是独立进程，调试要 attach：

| 场景 | 做法 |
|---|---|
| C++ 侧车启动即崩 | 在 `main()` 第一行加 `raise(SIGTRAP)`，用调试器启动而不是 attach |
| 正常运行时看状态 | `gdb -p <pid>` 或 Visual Studio 的「附加到进程」 |
| Python 侧车 | 在入口加 `import debugpy; debugpy.listen(5678); debugpy.wait_for_client()`，然后 attach |

侧车启动时把 pid 写入 `registry.json` 的调试字段，方便直接取到。这条不通过命令行暴露：调试是开发行为，不是用户功能。

### 8.4 常见故障对照

| 现象 | 最常见的原因 | 先查哪 |
|---|---|---|
| 插件装上但状态是 `deactivated` | 依赖未满足 | `ling plugins` 的「未满足原因」列 |
| 插件装载失败，错误码 `E_MANIFEST_INVALID` | 清单字段、目录名、产物组合 | `logs --kernel`，看 message 里的字段名 |
| 装载成功但调用返回 `E_METHOD_MISSING` | 方法名没带前缀，或注册在 activate 之后 | 核对该插件注册的方法名 |
| 调用返回 `E_CAPABILITY_DENIED` | 方法声明超出清单，或能力被撤销 | `ling plugins --json` 看生效能力 |
| Windows 上链接通过、启动即崩 | 编译器或运行时不一致 | 核对宿主与插件是否同一 Preset 构建 |
| 热更新后行为还是旧的 | 私有副本名字没变，加载器返回旧句柄 | 看 `plugins/<编号>/` 下的副本序号是否递增 |
| 侧车起来又立刻退出 | 端点没传进去，或握手失败 | 侧车 stderr 与 `logs --kernel` 里的握手记录 |
| 内存持续增长 | 重载泄漏（正常，有上限）或插件自己泄漏 | `doctor` 看账本条目与副本数量 |
| 界面打不开 | 端口被占或 `core-ui` 崩了 | `registry.json` 的 `ui_port`；`ling plugins` 看 core-ui 状态 |
| 命令行连不上 | 数据根不一致 | 命令行与宿主的 `--data-dir` 是否相同 |

## 9. 写一个最小插件

这一节是给人照抄的样板，从空目录到一个能调用的插件。

### 9.1 目录与清单

```
plugins/demo-a/
├── plugin.toml
└── demo_a.cpp
```

`plugin.toml`：

```toml
id = "demo-a"
version = "1.0.0"
api = "1"
name = "示例插件 A"
description = "最小可运行插件"
capabilities = []
```

字段含义见 `04/02` §3。这里 `capabilities` 留空：这个插件只提供一个方法，不碰文件、网络、界面。

### 9.2 入口函数

```cpp
#include <ling/sdk.hpp>

namespace {

// 处理函数：签名由 04/02 §4.1 的函数表决定
int32_t ping(void* ctx, const uint8_t* args, size_t args_len,
             uint8_t** out, size_t* out_len) {
    static const char kPong[] = "pong";
    *out_len = sizeof(kPong) - 1;
    *out = reinterpret_cast<uint8_t*>(const_cast<char*>(kPong));
    return 0;
}

}  // namespace

LING_PLUGIN("demo-a", "1.0.0") {   // sdk.hpp 提供的宏，展开成 ling_plugin_entry
    auto* c = ling::context();      // 包了 void* ctx 的薄封装
    return c->register_method("demo-a.ping",           // 方法名必须带自己的前缀
                              &ping,
                              nullptr,                 // 撤销函数：注销时由宿主代撤
                              0);                      // 不需要任何能力
}
```

三个要点：

| 要点 | 说明 |
|---|---|
| 方法名必须带 `demo-a.` | 不带则注册返回 `E_NAMESPACE_VIOLATION`（`04/01` §5.1 第 3 步） |
| 撤销函数传 `nullptr` | 注册方法时传空会返回 `E_LEDGER_INVALID`（`04/02` §5.2）。`sdk.hpp` 的封装里对「传空」做了默认代撤处理，这里能传空是因为 SDK 帮你补了一个 |
| 返回的缓冲区是静态字符串 | 插件申请、插件释放；宿主只读，不 `free_buffer` 它 |

第 2 条容易混，单独说清：C ABI 层要求撤销函数非空，SDK 层允许传 `nullptr` 并由 SDK 生成一个「调用 `unregister_method`」的代撤函数。这样写插件的人不需要为每个方法手写撤销。

### 9.3 构建

在 `plugins/CMakeLists.txt` 里加一行：

```cmake
add_ling_plugin(demo-a SOURCES demo_a.cpp)
```

`add_ling_plugin` 由 `other/cmake/LingPlugin.cmake` 提供，自动做四件事：套用统一编译选项、把产物命名为 `<编号>.dll` 或 `.so`、复制到 `run/<preset>/plugins/demo-a/`、同时复制 `plugin.toml`。

插件作者不写编译选项——这是 `02` §5.4「插件作者不自己写编译选项」的落地方式。

### 9.4 安装与验证

```bash
# 起宿主  [未验证]
./run/linux-debug/ling serve --data-dir ./run/linux-debug/data &

# 装插件  [未验证]
./run/linux-debug/ling install ./run/linux-debug/plugins/demo-a --data-dir ./run/linux-debug/data

# 看状态，应为 activated  [未验证]
./run/linux-debug/ling plugins --data-dir ./run/linux-debug/data

# 调用  [未验证]
# 命令行没有 call 子命令：管理端口只接受 kernel.* 方法（04/06 §3.3）
# 业务方法的调用由集成测试承担：l2_call 用一个调用方插件调 demo-a.ping
ctest -R l2_call
# 期望输出：pong
```

### 9.5 常见错误

| 现象 | 原因 |
|---|---|
| `E_MANIFEST_INVALID`，message 说缺字段 | 清单少写 `name` 或 `api`（`04/02` §3.1 四个必填） |
| `E_API_MISMATCH` | `api` 写成 `"2"`，而宿主支持 `"1"` |
| `E_NAMESPACE_VIOLATION` | 方法名写成 `ping` 而不是 `demo-a.ping` |
| 装载成功但 `call` 找不到方法 | 注册写在 activate 之后，或注册失败但没检查返回值 |
| Windows 上装载报「不是有效的 Win32 程序」 | 插件与宿主位数不一致（x64 对 arm64） |
| 崩溃在 `register_method` 里 | 传进去的 `ctx` 不是宿主给的，或用了别的插件的 `ctx` |

最后一条对应 `04/03` §2.4：`ctx` 不能自己造，也不能拿别人的。SDK 的 `ling::context()` 只返回本次激活注入的那个。

## 10. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。
| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | Android 上的单元测试是否完全不跑 | 是。只出产物，功能靠真机手工验证 S1、S3、S5 | §7.3 |
| 2 | `core-ui` 的 HTTP 依赖选哪个 | 到 S6 再定，届时按依赖规则引入。候选是 cpp-httplib（header-only）或 Boost.Beast（重） | §3.3 |
| 3 | 打包时是否带 pdb | 带，与版本号一起归档，否则崩溃转储只能看地址 | §7.5、§8.2 |
| 4 | 是否需要交叉编译 Linux 版（在 Windows 上出 Linux 产物） | 不需要。Linux 版在 Linux 上编，或后续用容器 | §7.2 |
| 5 | `precommit.sh` 在 Windows 上怎么跑 | 用 Git Bash（随 Git 安装）或 WSL，不另写 `.ps1`。两份脚本一定会漂移，一处漏改就是假的通过 | §4.5 |
