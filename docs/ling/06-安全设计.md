# ling 06 安全设计

> 状态：初定 | 最后更新：2026-10-29
> 依据：`docs/ling/01-需求规格.md` §3.3、§3.8、§4.5；`docs/ling/02-技术选型.md` §2.2

本文的难点不是「列出要防什么」，而是**先说清不防什么**。项目一路留下的结论是「ling 不是沙箱，插件是可信代码」，那么安全设计剩下的内容必须是真的能做的，而不是把「注意安全」写满一页。

---

## 1. 目的与范围

### 1.1 覆盖什么

| 内容 | 说明 |
|---|---|
| 威胁模型 | 信任边界在哪、威胁清单、明确不防的清单 |
| 管理端口的防线 | 三道措施各自的强度、多用户系统上的情形 |
| 侧车连接认证 | 本文补的缺口：侧车端口原来没有认证 |
| 能力门禁的真实定位 | 它防误用与越权声明，不防攻击 |
| 文件与数据 | 路径穿越、zip-slip、符号链接、数据根权限、`--purge` 门槛 |
| 日志与崩溃转储 | 哪些敏感信息会进日志、怎么兜 |
| 密钥与凭证 | `session.json` 的生成、插件凭证该放哪 |
| 供应链 | 依赖锁定、Python 依赖、插件来源 |

### 1.2 不覆盖什么

| 内容 | 去哪 / 理由 |
|---|---|
| 恶意插件的隔离 | 不在威胁模型内。插件由作者自己编写（`02` §2.2） |
| 已被攻破的本机 | 同用户权限下的恶意进程无法防，见 §2.3 |
| 网络传输加密 | 没有远程访问，不引入 TLS，见 §3.5 |
| 多用户权限分级 | 单用户设计。多用户情形只说明不保证什么 |
| 密码学实现 | 只用系统提供的随机源，不自研算法 |

### 1.3 三条前提

全文的推理都建立在这三条上，任何一条不成立，本文的结论都要重做：

| # | 前提 | 出处 |
|---|---|---|
| 1 | 插件由作者自己编写或审查过，是可信代码 | `02` §2.2 |
| 2 | 单机、单用户、只在本人账户下运行 | `00` §2.4 |
| 3 | 没有任何远程访问入口：管理端口与界面端口只绑回环 | `01` LING-REQ-115 |

## 2. 威胁模型

### 2.1 信任边界

四层，从内到外信任递减：

| 层 | 谁 | 信任程度 | 说明 |
|---|---|---|---|
| 内核 | 宿主进程本身 | 完全信任 | 它是要保护的对象，也是防线的执行者 |
| 插件 | 进程内插件、侧车插件 | 可信但会出错 | 不防恶意，防意外崩溃与误用 |
| 本机其他用户 | 同一台机器上的其他账户 | 不信任 | 靠文件权限与端口口令挡 |
| 本机同用户进程 | 同账户下的其他程序 | **无法防** | 它和宿主权限相同，读得到 `session.json` |
| 外部网络 | 局域网与互联网 | 不信任 | 没有入口：端口只绑回环 |

最容易误解的是第四行：**同账户下的其他程序与宿主权限相同**。它能读 `session.json`、能改插件文件、能 attach 到宿主进程。这类威胁超出应用层能力，本文不承诺防护。

### 2.2 威胁清单

| # | 威胁 | 攻击面 | 覆盖 | 措施 |
|---|---|---|---|---|
| T1 | 局域网或公网访问管理端口 | 7900 端口 | 是 | 只绑 `127.0.0.1`（§3.1） |
| T2 | 本机其他用户发管理命令 | 7900 端口 | 是 | 首帧口令 + `session.json` 权限 0600（§3.2） |
| T3 | 本机其他用户读日志、数据 | 数据根 | 部分 | 数据根权限 0700（§5.4） |
| T4 | 同账户恶意进程冒充宿主控制插件 | 7900、侧车端口 | 部分 | 无法防。口令文件对它可读，只能在日志里留痕（§3.4） |
| T5 | 伪造的侧车进程连上侧车端口 | 侧车端口 | 是 | 本文新增的握手口令（§3.6） |
| T6 | 恶意清单用 `..` 或绝对路径写到目录外 | 清单、zip 包 | 是 | 路径校验 + 解压后逐项校验（§5.1、§5.2） |
| T7 | zip 包的路径穿越（zip-slip） | 安装来源 | 是 | 解压时拒绝含 `..` 或绝对路径的条目（§5.2） |
| T8 | 卸载 `--purge` 误删用户数据 | 命令行 | 是 | 二次确认 + 打印将删路径（§5.5） |
| T9 | 日志泄露文件内容或口令 | 日志文件 | 部分 | 不记载荷原文与口令；日志文件 0600（§6.1） |
| T10 | 崩溃转储含敏感内存 | `.dmp` 文件 | 部分 | 文件 0600、不上传、到期清理（§6.3） |
| T11 | 依赖被替换成恶意版本 | 构建 | 是 | vcpkg baseline 锁版本（§8.1） |
| T12 | 插件引入的 Python 依赖有漏洞 | 侧车 | **否** | 插件作者自负，宿主不扫描（§8.2） |

### 2.3 明确不防

以下威胁**不在本文范围**，写清是为了避免读者误以为已有防护：

| 不防 | 理由 |
|---|---|
| 恶意插件（提权、逃逸、偷数据） | 插件是可信代码。ling 不提供沙箱 |
| 同账户下的恶意程序 | 权限相同，应用层无法区分「用户自己」与「用户的病毒」 |
| 物理接触攻击（改文件、读内存） | 超出软件范围 |
| 侧信道（时序、缓存） | 单用户单机，无收益 |
| 拒绝服务（插件死循环耗 CPU） | 只做超时切断，不做资源配额（`01` LING-REQ-100 只限账本条目数） |
| 供应链上游（vcpkg 仓库本身被投毒） | 超出本项目能力，只能锁版本降低概率 |

最后一条要说清：锁 baseline 保证「版本不变」，不保证「那个版本没被投毒」。

## 3. 管理端口的防线

### 3.1 第一道：只绑回环

监听地址固定 `127.0.0.1`，不提供配置项（`01` LING-REQ-115）。

**挡住了什么**：外部网络与局域网的一切连接。测试办法：从另一台机器 `curl http://<本机IP>:7900` 必然连接失败。

**挡不住什么**：本机上的任何进程。回环不区分进程，只区分网络来源。

这条是最有效的一道，因为它不依赖任何口令与权限。也正因如此，「提供一个绑 `0.0.0.0` 的开关」被明确拒绝——一旦可配，这道防线立刻降级为「用户记得别开」。

### 3.2 第二道：`session.json` 与口令

| 项 | 规定 |
|---|---|
| 生成 | 每次宿主启动用系统随机源生成 32 字节，转十六进制 |
| 随机源 | Windows 用 `BCryptGenRandom`，Linux 与 Android 用 `getrandom()`。不用 `std::rand`，也不用「时间戳加进程号」这类可猜的组合 |
| 存储 | `<数据根>/session.json`，权限 0600 |
| 生命周期 | 启动时覆盖，退出时删除 |
| 校验 | 首帧带 token，常量时间比较，失败即断开并记 warn |

**为什么用常量时间比较**：普通字符串比较遇到第一个不同字符就返回，比较耗时会随相同前缀长度变化。在本地回环上这个差异极小，但改成常量时间比较的成本只有几行代码，没有理由不做。

**权限怎么落地**：

| 平台 | 做法 | 说明 |
|---|---|---|
| Linux / Android | `chmod 0600` 或创建时 `open(..., 0600)` | 创建时就设对，不要先创建再 chmod（中间有窗口） |
| Windows | 设置 DACL，只授当前用户 | 不模拟 POSIX 权限位。`%APPDATA%` 的默认 ACL 已是当前用户独占，但仍显式设置，不依赖默认值 |

### 3.3 第三道：数据根权限

数据根要 0700（仅当前用户可进入），不只是 `session.json` 一个文件：

| 内容 | 敏感性 |
|---|---|
| `session.json` | 高：拿到就能控制宿主 |
| `logs/` | 中：含文件路径、插件行为 |
| `settings.json` | 中：含插件配置的凭证 |
| `plugins/<编号>/data/` | 中到高：插件自己的数据，如索引或缓存 |
| `registry.json` | 低：端口与名单 |

整个目录 0700 一次解决，比逐个文件设权限可靠——新加的文件不会因为忘了设而暴露。

### 3.4 挡不住的情形与留痕

同账户下的恶意进程可以直接读 `session.json`，然后以合法客户端身份发命令。应用层无法区分它和用户自己。

能做的只有留痕：

| 措施 | 内容 |
|---|---|
| 每条命令记来源进程 | 连接建立时用平台 API 取对端进程号（Windows `GetExtendedTcpTable`，Linux 读 `/proc/net/tcp`），写入内核日志 |
| 命令按 trace id 全链记录 | 每条管理命令的 trace id 与调用结果都进日志 |
| 不提供「静默执行」 | 所有改状态的操作都产生日志与事件，没有可关掉的开关 |

这些措施的作用是**事后可查**，不是事前阻止。文档里不能写成「已防护」。

### 3.5 为什么不引入 TLS

| 理由 | 说明 |
|---|---|
| 没有远程访问 | 端口只绑回环，流量不出本机内核 |
| 证书管理成本高 | 自签证书要处理信任、过期、续期，对个人工具是纯负担 |
| 本机回环的嗅探需要更高权限 | 同账户恶意进程已经在 §3.4 里承认无法防 |

若将来真要开远程访问（例如手机连界面），正确做法不是「给管理端口加 TLS」，而是**在前面放一层专用代理**（SSH 隧道、nginx），把 TLS 与访问控制交给成熟工具。宿主本身不开这个口子。

### 3.6 侧车连接的认证（本文补的缺口）

`docs/ling/04-详细设计/02-插件装载与接口.md` §8.4 的握手只校验协议版本与插件编号，**没有认证**：本机任意进程连上侧车端口，发一个 `hello` 就能冒充宿主。

这不是理论问题：侧车端口是宿主监听的回环端口，本机任何进程能连。

补法：

1. 宿主启动侧车时，除 `LING_SOCKET` 外再通过环境变量 `LING_TOKEN` 传入一个 32 字节随机串。每次启动侧车重新生成，不落盘。
2. 侧车首帧 `hello` 必须带 `token` 字段。
3. 宿主校验，不符则回 `E_AUTH` 并断开，记 warn。
4. 握手成功后这张连接即为该侧车专用，不再校验。

为什么用环境变量而不是命令行参数：命令行参数在进程列表里对同机所有用户可见（Linux 的 `/proc/<pid>/cmdline`），环境变量只有同用户与 root 可读（`/proc/<pid>/environ` 的权限是 0400）。

这条的边界同样要写清：它挡住的是「本机其他用户进程」与「误连上来的程序」，挡不住「同用户的恶意进程」——后者读 `/proc/<pid>/environ` 就行。

### 3.7 三道防线的合成效果

| 攻击者位置 | 能否控制宿主 | 靠哪道挡 |
|---|---|---|
| 外部网络 | 不能 | 3.1 回环绑定 |
| 局域网内其他机器 | 不能 | 3.1 |
| 本机其他用户 | 不能 | 3.2 口令 + 3.3 目录权限 |
| 本机其他用户（侧车端口） | 不能 | 3.6 侧车口令 |
| 同用户的其他程序 | **能** | 无。只能事后查日志 |
| 用户自己误操作 | 部分 | 见 §5.5 的确认门槛 |

第四行与第五行的差别是本节的要点：**跨用户能防，同用户不能防。**

## 4. 能力门禁的真实定位

### 4.1 它是什么

两处校验（`04/01` §7.1）：注册方法时查方法声明的能力是否 ⊆ 清单；调用瞬间查生效能力（清单减撤销）是否覆盖。

### 4.2 它防什么

| 防的是 | 机制 |
|---|---|
| 插件用了没声明的能力 | 注册时拒绝，`E_CAPABILITY_DENIED` |
| 用户撤销能力后仍被使用 | 调用瞬间再查，撤回立即生效 |
| 事后追责不清 | 每次被拒都记 warn，带插件编号与 trace id |

关键点：这三条都是**让行为可声明、可追溯**，不是「拦住恶意行为」。

### 4.3 它不防什么

| 不防 | 原因 |
|---|---|
| 具体文件路径 | 管路径等于在宿主里塞一个沙箱（`01` LING-REQ-027） |
| 网络地址 | 同上 |
| 调用频率 | 没有资源配额，只做超时切断 |
| 数据外泄 | 声明了 `network` 的插件可以把读到的文件内容发出去，宿主管不了 |
| 绕过 `Context` 直接调系统 API | 进程内插件与宿主同权限，动态库可以直接调 `open`、`socket`，宿主检测不到（`04/03` §7.3） |

最后一条最容易被误解：**能力门禁只约束「经 `Context` 做的事」**。插件绕过 `Context` 直接调系统 API，门禁完全看不到。所以它不是安全边界。

### 4.4 结论

能力门禁的准确定位是**审计钩子与误用拦截**，不是沙箱。

这个定位有三个实际后果：

1. 它挡不住想作恶的插件——但那不是威胁模型（§1.3）。
2. 它能挡住「写插件时手滑用了没声明的能力」，这类错误在开发期就会被发现。
3. 它让日志里能回答「这个插件被允许做什么」，出问题时有据可查。

写成「安全机制」会让读者高估它；写成「审计钩子」才是准确的。

## 5. 文件与数据

### 5.1 路径校验

清单里出现的每个路径都过同一套检查（`04/02` §3.4 第 7、9 步）：

| 检查 | 拒绝什么 |
|---|---|
| 不含 `..` 段 | `../../etc/passwd` |
| 不以 `/` 或盘符开头 | `/etc/ling`、`C:\Windows` |
| 侧车的 `executable` 必须在插件目录内 | 指到插件目录之外的任何路径 |
| 解析后的真实路径仍在插件目录内 | 用符号链接绕过前三条 |

第四条是前三条的兜底：先按字面检查，再解析真实路径（`realpath` / `GetFinalPathNameByHandle`）确认没跑出目录。只做字面检查会被符号链接绕过。

### 5.2 zip 包的解压

zip-slip：zip 里的条目名可以是 `../../.bashrc`，按名字直接解压会写到目标目录之外。

防护顺序：

1. 逐个读取条目名，拒绝含 `..`、绝对路径、盘符的条目。
2. 解压到临时目录，而不是直接进 `<数据根>/plugins/`。
3. 解压完成后遍历临时目录，逐个文件做 §5.1 的检查（含真实路径解析）。
4. 全部通过后再整体移动到 `plugins/<编号>/`。

解压到临时目录再搬，是为了「校验失败时不留下半个插件」：直接解压到目标目录的话，第 5 个文件不合法时前 4 个已经写进去了。

### 5.3 符号链接

| 情形 | 处理 |
|---|---|
| 插件目录本身是符号链接 | 拒绝装载，`E_MANIFEST_INVALID` |
| 插件目录内的文件是符号链接 | 拒绝装载 |
| 插件运行时自己创建符号链接 | 不检测（属于绕过 `Context` 的修改，`04/03` §7.3） |

前两条的理由：符号链接可以指向任意位置，等于绕开 §5.1 的全部检查。装载阶段一次性拒绝，比运行时逐个判断简单可靠。

### 5.4 数据根权限

创建时即设权限，不依赖默认值：

| 平台 | 做法 |
|---|---|
| Linux / Android | `mkdir` 时传 `0700`，或创建后立即 `chmod` 并检查返回值 |
| Windows | 创建后设置 DACL，只授当前用户与 SYSTEM |

子目录继承父目录权限，不单独设。若发现某个子目录权限被改宽（例如 `logs/` 变成 0755），`doctor` 报告一条，但不自动修——自动修权限会让正在运行的程序写不进去。

### 5.5 卸载与 `--purge` 的门槛

`--purge` 会连 `data/` 一起删，而 `data/` 里常是唯一的索引（例如媒体库扫描结果，重建要几小时）。

| 措施 | 内容 |
|---|---|
| 默认不带 `--purge` | 卸载只删工件，数据保留（`01` LING-REQ-010） |
| `--purge` 必须显式写 | 没有交互式确认，靠参数显式表达意图 |
| 执行前打印将删的绝对路径 | 一行一条，含总大小 |
| 删到非空目录前再确认一次 | 命令行给 `--yes` 时跳过，否则要求输入编号确认 |
| 不跟随符号链接删除 | 删符号链接本身，不删它指向的内容 |

第三条的用处：脚本里写错一个编号时，输出里能立刻看出来删的是谁。

### 5.6 安装来源

插件是自写或审查过的（§1.3），所以不做签名校验。但两类检查仍要做：

| 检查 | 理由 |
|---|---|
| zip 包与目录的完整性（能读、结构合法） | 防止装到半个包 |
| 清单里的 `id` 与产物文件名一致 | 防止把 A 的产物装成 B（`04/02` §4.3 第 3 步） |

不做校验和比对：自己写的插件，记下哈希只增加负担，挡不住「自己重新编译了一个新的」。

## 6. 日志与崩溃转储

### 6.1 日志里不记什么

| 不记 | 理由 |
|---|---|
| `session.json` 的 token | 记了等于把口令写进明文文件 |
| 侧车的 `LING_TOKEN` | 同上 |
| 调用载荷的原文 | 包含文件内容、凭证、个人数据。debug 级别只记长度与前 32 字节的十六进制摘要 |
| 文件内容 | 从设计上就不进控制面（`04/02` §8.6） |
| 插件的配置值 | 只记键名与长度 |

「debug 级别记前 32 字节摘要」是个折中：完全记会让日志变成数据副本，完全不记又无法判断「传的对不对」。摘要够判断「两次调用参数是否相同」，不够还原内容。

### 6.2 路径要不要脱敏

日志里会出现绝对路径（`/home/user/photos/2024/img.jpg`）。这泄露了用户名与目录结构。

三个选项：

| 方案 | 代价 |
|---|---|
| 全部脱敏成 `<path>` | 排障时看不出是哪个文件，日志价值大幅下降 |
| 保留完整路径 | 泄露目录结构 |
| 保留路径，靠文件权限兜 | 需要保证 `logs/` 是 0700 |

**选第三个**。理由：日志的主要用途就是排障，路径是最关键的信息；而 `logs/` 已随数据根设为 0700，非本用户读不到。风险与收益相比，保留路径更划算。

这条要写进文档，因为它是一个**有意识的取舍**，不是疏忽。若将来需要把日志发给别人分析，由发的人自己先脱敏。

### 6.3 崩溃转储

Windows 的 `.dmp` 含进程内存，其中含有：文件内容、凭证、配置值。

| 措施 | 内容 |
|---|---|
| 文件权限 | 0600，与 `session.json` 同级 |
| 位置 | `<数据根>/logs/`，随数据根 0700 |
| 不上传 | 没有上传通道 |
| 清理 | 保留最近 5 个，超出删最旧。不做按天保留（转储体积大） |
| 生成前提示 | 首次生成时在内核日志里记一条「已生成转储，含进程内存，分享前请自行检查」 |

最后一条是给人看的提醒：转储发给别人排查时，里面含有不该给的东西。

### 6.4 日志轮转与磁盘

| 项 | 规定 |
|---|---|
| 内核日志 | 按天分文件，单文件超 64 MB 轮转，保留 7 天（`01` LING-REQ-111） |
| 插件日志 | 同上，按编号分文件 |
| 磁盘占用上限 | 全部日志不超过 512 MB，超出时从最旧开始删 |

上限的作用是防止「日志写满磁盘」导致宿主无法启动——这类故障排查起来比日志丢失更麻烦。

## 7. 密钥与凭证

### 7.1 宿主自己要管的东西

只有一个：`session.json` 的 token。生成与存储见 §3.2。

侧车的 `LING_TOKEN` 每次启动重新生成，只在环境变量里存在，不落盘，进程退出即消失。

### 7.2 插件自己的凭证

插件若要访问网盘、数据库这类需要凭证的服务。规则：

| 该放哪 | 不该放哪 |
|---|---|
| `data_dir()` 下的文件，由插件自己加密或依赖系统密钥链 | 配置（`write_config` 的值会进日志与导出） |
| 系统的密钥链（Windows Credential Manager、libsecret），插件自行调用 | 日志、错误消息、`detail` 字段 |
| 环境变量（插件自己的启动参数） | 清单文件（清单是明文的，会被复制与展示） |

宿主不做凭证托管：没有「统一密钥库」这种东西。理由是没有多用户、没有远程服务，凭证管理的复杂度换不来实际收益。

### 7.3 不做什么

| 不做 | 理由 |
|---|---|
| 自研加密算法 | 只用系统随机源，加密交给平台或成熟库 |
| 密钥轮换机制 | 没有长期凭证需要轮换 |
| 权限分级（管理员与普通用户） | 单用户 |
| 审计日志签名 | 没有第三方审计需求 |

## 8. 供应链

### 8.1 C++ 依赖

| 措施 | 内容 |
|---|---|
| 版本锁定 | `vcpkg-configuration.json` 的 baseline 固定全部依赖版本（`05` §3.3） |
| 依赖数量 | 三个：Catch2（仅测试）、toml++、nlohmann/json。数量少是刻意的 |
| 不引入的依赖 | 不需要「万能工具库」：HTTP、序列化、日志都有更小的替代或自己写 |

第三行的判断标准：一个依赖如果能用两百行自己写清，就不引入。依赖越多，被上游问题波及的面越大。

### 8.2 Python 侧车的依赖

插件自己 `pip install` 的东西，宿主不管：

| 不管 | 说明 |
|---|---|
| 不扫描漏洞 | 宿主没有漏洞库，也不联网查 |
| 不锁版本 | 插件的 `requirements.txt` 由插件作者维护 |
| 不隔离环境 | 侧车进程用的是宿主随包带的运行时，插件自己决定装什么 |

能力范围内能做的只有一条：侧车启动失败时，错误信息里带 Python 的原始报错，让作者能看出「是依赖没装」。

### 8.3 插件来源

自己写的不校验签名（§5.6）。若将来开始用别人写的插件，需要补的是「来源可追溯」而不是「签名验证」——这个项目没有分发渠道，签名没有信任根。
