# ling 11 MVP 范围

> 状态：初定 | 最后更新：2026-10-29
> 依据：`docs/ling/10-路线图与里程碑.md` §3.2、§3.3；`docs/ling/01-需求规格.md`

本文回答：最早那个能用的东西包含哪些需求、明确不含哪些、拿什么演示。

MVP 是 `docs/ling/10-路线图与里程碑.md` 里 M1 与 M2 两个里程碑的合称。它不是一个独立产品，也不是一个新阶段——判定沿用里程碑门槛，不另设一套。

---

## 1. 目的与范围

### 1.1 与 10 的关系

| 概念 | 含义 |
|---|---|
| 里程碑 M1 | 最小闭环：装插件、看状态、调通一次 |
| 里程碑 M2 | 可装可卸：卸载后路由清空、账本倒序撤销 |
| **MVP** | **M1 加 M2**，一个能用命令行完成装卸与调用的宿主 |

所以 MVP 的交付时点就是 M2 通过判定的那一刻，版本号 `0.0.3-b1`。不额外打标签，也不额外做验收。

### 1.2 与 01 的关系

MVP 从 `docs/ling/01-需求规格.md` 里**挑**条目，不改需求本身。

需求里没有「优先级」字段，这是有意的：需求只回答「必须做到什么」，不回答「先做哪个」。哪些先进 MVP 是本文的事，需求文档不知道 MVP 的存在。

这样处理的好处是：MVP 的范围可以随判断调整，不必回改 127 条需求；坏处是要维护一张对照表（§3），表错了会出现「实现了但不在 MVP 里」或反过来。这张表由本文单点维护。

### 1.3 判定方式

不另设门槛。四条与 `docs/ling/10-路线图与里程碑.md` §5.1 相同：

1. 演示脚本（§2.2）跑通，结果记进 `docs/log/`。
2. 本文 §3 列出的条目，验收标准全部可判真。
3. 适用于 MVP 的基准在容差内。
4. `precommit.sh` 五项全过。

## 2. MVP 是什么

### 2.1 一句话定义

**能从命令行装一个自己写的 C++ 插件、看到它被激活、让另一个插件调它的方法、再把它干净卸掉。**

四个动词：装、看、调、卸。少任何一个都不算 MVP。

### 2.2 演示脚本

```bash
# 1 启动宿主（首次启动自动装三个内置插件）
ling serve

# 2 装被调方
ling install <程序目录>/plugins/demo-a

# 3 装调用方（它在激活时调 demo-a.ping，结果写进自己的日志）
ling install <程序目录>/plugins/demo-caller

# 4 看状态：两个都是 activated，外加三个内置插件
ling plugins

# 5 看调用结果
ling logs demo-caller        # 期望看到 pong

# 6 卸载被调方：路由清空，安装文件消失，data/ 保留
ling uninstall demo-a
ling plugins                 # demo-a 不在列表里
ls <数据根>/plugins/demo-a    # 只剩 data/

# 7 调用方再调时得到 E_PLUGIN_MISSING，不崩溃
ling logs demo-caller

# 8 用 --purge 彻底删除
ling uninstall demo-caller --purge
```

第 3 步为什么要有第二个插件：**命令行没有 `call` 子命令**。管理端口只接受 `kernel.*` 开头的方法（`docs/ling/04-详细设计/06-管理端口与命令行.md` §3.3），业务方法的调用只能来自插件。这是设计决定，不是缺失——命令行是管理通道，不是调试通道。

`demo-caller` 是 MVP 专用的示例插件，源码与 `demo-a` 放在一起。它不注册任何方法，只在 `activate` 里调一次 `demo-a.ping` 并写日志。

### 2.3 不是什么

| 不是 | 说明 |
|---|---|
| 能给别人的东西 | 没有界面、没有安装包、Android 不能用 |
| 功能完整的宿主 | 无依赖声明、无热更新、无侧车 |
| 稳定版本 | `0.x` 阶段，不承诺接口不变；清单字段与错误码还会变 |
| 可长期放心的数据容器 | 卸载与升级路径未全部验证；`data/` 要自行备份 |

第一条要强调：MVP 的价值是「自己能用上」，不是「发布」。发布在 M6。

### 3.2 边界条目

多数条目要么全含要么全不含。下面十条是部分含，判定范围要按这里写的执行，否则测试时无法判断通过与否。

| 编号 | 完整要求 | MVP 的判定范围 | 为什么 |
|---|---|---|---|
| 071 | 13 个子命令 | 10 个：serve、shutdown、plugins、install、uninstall、enable、disable、logs、--version、--help | `reload`、`restart` 依赖热更新；`doctor` 要查依赖图环，而 MVP 没有依赖图 |
| 075 | 卸掉 core-ui 后命令行仍可用 | 卸掉三个内置插件后命令行仍可用 | MVP 没有 core-ui |
| 079 | 首次启动装五个内置插件 | 装三个：core-settings、core-plugin-manager、core-log | 见 §4.2 第三条 |
| 081 | 五个内置插件均可卸载 | 三个均可卸载，卸掉后宿主仍能启动 | 同上 |
| 095 | 冷启动到 20 插件激活（含 2 个 Python 侧车） | 按 5 个进程内插件测，上限仍取 094 的 300 毫秒级判定 | 无侧车，无法按原口径测 |
| 099 | 20 个空载插件 ≤ 120 MB | 按 20 个空载插件测（不含侧车项） | 20 个空载插件不需要依赖与侧车，MVP 能测 |
| 109 | 四个超时 | 两个：方法调用 30 秒、订阅者回调 5 秒 | 另两个是侧车的停用与退出 |
| 113 | 三平台产物 | Windows x64 与 Linux x64 | Android 留到 M6 |
| 118 | 六类日志内容 | 六类全测，但「调和的每一步」在 MVP 里只含装载与卸载两步 | 无依赖调和 |
| 122 | trace id 三个传递点 | 两个：宿主内调用、命令帧 | 侧车帧留到 M4 |

**这张表只用于 MVP 阶段的判定，不改 `07` 的用例与基准。** `docs/ling/07-测试与验收.md` 的用例按完整口径写（例如 TC-901 期望五个内置插件、`l6_resource` 的启动段按 20 插件含 2 侧车），MVP 阶段按本表缩减后跑，对应条目记为「本期不适用」并写明理由；M3、M4、M5 解除限制后恢复完整口径，不加新用例。

### 3.3 为什么先做这 85 条

按「少了这一条，装装卸卸就跑不通」筛：

| 组 | 少了会怎样 |
|---|---|
| 装载卸载 | 没有核心动作 |
| 路由与事件 | 插件之间不能互相调，等于一堆孤岛 |
| 能力门禁 | 与路由同一条路径，硬拆会在路由里留一个「先不做检查」的分支，后面补不回来 |
| 上下文与账本 | 卸载时无法撤销，残留会让第二次装载失败 |
| 内核日志与可观测 | 上一版最大的教训就是没有运行时日志；这一版抽掉它等于重犯 |

最后一行是这份文档里唯一带情绪的判断，但它有据可依：上一版出问题时「只能看现象猜原因」，原因是日志里没有内容可看。MVP 阶段的不确定性最高，最需要能看见发生了什么。

## 4. 明确不含的

### 4.1 四类功能

| 不含 | 意味着什么 | 什么时候有 |
|---|---|---|
| 依赖声明与调和 | 插件之间不能声明 `requires`；装载顺序要自己保证 | M3 |
| 热更新 | 改插件必须重启宿主 | M3 |
| 侧车 | 只能用 C++ 写插件；不能用 Python | M4 |
| 界面 | 只能命令行；没有 `core-ui` | M5 |

第二条最影响日常使用：改一行代码要重启宿主，重装的插件状态要从 `data/` 重新加载。这不是不能忍，但会明显降低改插件的频率。

**内核的手工升级在 MVP 内**：084（停止宿主、替换二进制）、085（重启从 `data/` 恢复）、086（api N/N-1）、088（`data/` 格式不变）、127（`min_host`）都含。不含的只有 087（侧车协议版本字段）——MVP 没有侧车，这条无从测。

### 4.2 三条临时实现限制

这三条不是「不做」，是「这段时间里按更严的规则拒绝」。它们与 `01` 的原文有偏差，必须在 M3、M4 时解除，并回改对应文档。

| 限制 | 具体行为 | 解除时点 | 要回改哪里 |
|---|---|---|---|
| 清单含 `requires` 非空 | 拒绝装载，返回 `E_MANIFEST_INVALID`，message 说明「本版本不支持依赖声明」 | M3 | `docs/ling/04-详细设计/02-插件装载与接口.md` 清单校验步骤 |
| 清单含 `[sidecar]` 段 | 拒绝装载，返回 `E_MANIFEST_INVALID`，message 说明「本版本只支持进程内插件」 | M4 | 同上，以及 `04/02` §8 的侧车协议节 |
| 内置插件只装三个 | `core-ui`、`core-job` 的源码不进 MVP 构建，不是「装了又禁用」 | M5 | `docs/ling/04-详细设计/07-内置插件.md` 与 `01` 的 079、081 |

**为什么选「拒绝」而不选「忽略」**：如果清单写了 `requires` 而宿主不解析，插件会以「以为依赖已满足」的状态被激活，出问题时现象是「调用某个方法返回 `E_PLUGIN_MISSING`」，而真正的原因在装载那一刻就发生了。拒绝装载会在正确的时点报出正确的错。

同样的判断适用于 `[sidecar]`：静默忽略会让一个侧车插件被当作进程内插件装载，然后因为找不到导出符号而崩溃。

### 4.3 解除顺序

三条限制的解除分散在三个里程碑，不集中做：

1. M3 解除 `requires`，同时实现调和。依赖与调和是一体的，只解除限制不实现调和等于允许装载一个起不来的插件。
2. M4 解除 `[sidecar]`，同时实现协议与握手。
3. M5 加回两个内置插件，同时更新 079、081 的判定。

每次解除都要在 `docs/log/` 里记一条，并回改 §4.2 表里指的文档。这张表是临时的，`0.1.0` 之前必须清空——留着它，说明某处限制被忘了。

## 5. MVP 期间的已知缺陷

这些不是 bug，是范围外的东西在 MVP 阶段的表现。用起来会碰到，先说清：

| 现象 | 原因 | 绕过办法 |
|---|---|---|
| 改插件要重启宿主 | 无热更新 | 重启后用 `ling plugins` 确认状态 |
| 装插件顺序错了，调用方报 `E_PLUGIN_MISSING` | 无依赖调和，程序不会自动调整 | 先装被调方，再装调用方 |
| 不能用 Python 写插件 | 无侧车 | 用 C++ 写 |
| 看不到图形界面 | 无 core-ui | 命令行；`ling logs --kernel` 看内核日志 |
| 出问题没有 `doctor` | 未实现 | 看 `logs/kernel-*.log`，按 `docs/ling/09-运行时预案.md` §7 的处置表查 |
| Android 用不了 | 未做 Android 包 | 只在桌面用 |

## 6. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | MVP 期间能不能当日常工具用 | 能，但每天备份 `data/`。真实使用是发现问题最快的方式 | §2.3 |
| 2 | 演示脚本要不要留档 | 把命令与输出贴进 `docs/log/` 对应条目，不录屏 | §2.2 |
| 3 | MVP 完成后直接进 M3 还是先停一段 | 先停一段。真实使用暴露的问题最值钱，此时改 04 的成本也最低 | §4.3 |

第 3 条的理由值得写下来：M3 之后加依赖与热更新，代码结构会变复杂；在简单结构上按真实使用改一轮，比在复杂结构上改便宜得多。
