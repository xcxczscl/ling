# ling 08 部署与发布

> 状态：初定 | 最后更新：2026-10-29
> 依据：`docs/ling/01-需求规格.md` §3.10、§4.5；`docs/ling/04-详细设计/06-管理端口与命令行.md` §5.1；`docs/ling/05-构造与开发指南.md` §7.5

本文是发行方视角：怎么把源码变成能用的包、怎么装、怎么升、怎么退。

用户拿到包之后怎么用，写在 `docs/ling/12-用户手册.md`（未编写）。两者不重复：本文说「包里有什么、装到哪、升级要注意什么」，手册说「点哪里、敲什么命令」。

### 1.3 一个前提

**私人使用，单机部署。** 没有服务端、没有多租户、没有公网分发渠道。这条前提决定了两件事：

| 决定 | 理由 |
|---|---|
| 不做自动更新 | 没有版本服务器，也没有「强制升级」的需求（`01` LING-REQ-084） |
| 不做灰度发布 | 只有一个用户，灰度没有意义 |

代价是每次升级要手动替换文件。这个代价与「自己控制什么时候升」相比是划算的。

## 2. 支持平台与产物形态

### 2.1 三端产物

| 平台 | 产物 | 形态 | 说明 |
|---|---|---|---|
| Windows | `ling-<版本>-win-x64.zip` | 免安装压缩包 | 解压到任意目录即用，不写注册表 |
| Linux | `ling-<版本>-linux-x64.tar.gz` | 压缩包 + `install.sh` | 可解压直接用，也可跑脚本装到 `~/.local` |
| Android | `ling-<版本>-android-arm64.apk` | 应用包 | 只作为宿主启动器与前台服务，不做界面 |

三端都是自包含的：Python 运行时、核心插件、头文件全在包里，不依赖系统装了什么东西。

### 2.2 包内结构

```
ling-<版本>-win-x64/
├── ling.exe                    命令行与宿主
├── plugin_api.h                插件接口头文件（纯 C）
├── sdk.hpp                     C++ 封装
├── core-ui.exe                 界面侧车
├── core-settings.dll
├── core-plugin-manager.dll
├── core-job.dll
├── core-log.dll
├── python/                     Python 运行时（裁剪，仅 Windows 与 Linux）
├── README.md                   首次使用说明
├── LICENSE-第三方.md            依赖的许可证
└── checksums.txt               包内文件的 sha256
```

五个内置插件放在包根目录，而不是 `plugins/` 子目录：首次启动时由宿主复制进数据根的 `plugins/`，放在只读位置也能运行。

Linux 包结构相同，后缀换成无后缀与 `.so`。Android 包是 apk，内部结构由构建工具决定，但装完后数据根在应用私有目录。

### 2.3 Android 的特殊性

这是三端里最粗糙的一块，要写清能做什么、不能做什么。

| 项 | 情况 |
|---|---|
| 界面 | 没有原生界面。宿主起来后用手机浏览器打开 `http://127.0.0.1:8010` |
| 谁拉起宿主 | apk 本身：一个前台服务，启动即拉起宿主进程 |
| 通知栏 | 常驻一条「ling 运行中」，点击可停止 |
| 后台被杀 | 系统回收时宿主一起退出，重新打开 apk 即可 |
| 插件 | 只有进程内插件与 C++ 侧车；**没有 Python 侧车**（运行时体积与系统限制，见 `02` §4.5.3） |
| 文件访问 | 受 Android 分区存储限制，只能访问应用私有目录与用户显式授权的目录 |

「没有 Python 侧车」这条要在发布说明里写清楚，否则用户会以为同一个插件包在三端都能装。

Android 版不做的事：不做原生界面、不做开机自启、不做后台长期驻留的保活手段。理由是这个平台的默认行为（回收后台进程）与「常驻宿主」冲突，硬保活要付出电池与系统限制的代价，而 ling 是个人工具，需要时打开即可。

## 3. 版本与发布

### 3.1 版本号

严格按 `docs/common/02-版本号与兼容约定.md`：

```
0.0.1-b3       修 bug 或重打包一次，bN 加一
0.0.2-b1       功能变化，次版本加一，bN 归 1
0.1.0-b1       阶段性版本，含不兼容变更
0.1.0          项目完成，去掉 -bN
```

`bN` 记的是**构建序号**，不是测试轮次——这两者只能选一个，选了前者。

### 3.2 什么时候算一次发布

| 时机 | 版本动作 | 产物 |
|---|---|---|
| 某个切片完成、跑过全量回归 | `bN` 加一 | 三端包 |
| 一批功能做完、需要验证新能力 | 次版本加一 | 三端包 |
| 改了清单字段、协议帧、错误码语义 | 首要版本加一，`api` 主版本同时加 | 三端包 + 迁移说明 |
| 只改文档 | 不动版本，不打标签 | 无 |

「只改文档不打标签」这条要注意：文档也在同一个仓库里，`git tag` 会带上文档状态，但不需要为此出包。

### 3.3 标签与产物命名

| 项 | 规则 | 例子 |
|---|---|---|
| Git 标签 | `v<版本>` | `v0.0.1-b3` |
| 产物名 | `ling-<版本>-<平台>-<架构>.<扩展名>` | `ling-0.0.1-b3-win-x64.zip` |
| 包内 `checksums.txt` | 包内每个文件的 sha256，一行一条 | —— |
| 发布页附件 | 三端包 + 对应 pdb 压缩包 | `ling-0.0.1-b3-win-x64-pdb.zip` |

pdb 单独打包而不是放进主包：主包给使用者，pdb 只在排查崩溃时需要，放一起会让包大一倍。

## 4. 首次安装

### 4.1 Windows

1. 解压到任意目录，例如 `D:\apps\ling-0.0.1-b3\`。
2. 在该目录打开终端，执行 `ling.exe serve`。
3. 首次运行会自动做三件事（见 §4.4），完成后终端显示端口与口令位置。
4. 浏览器打开 `http://127.0.0.1:8010` 进入界面。

不写注册表、不建开始菜单项、不改 PATH。要方便启动就自己建快捷方式，指向 `ling.exe serve`。

为什么不提供安装包：安装包要处理卸载登记、升级覆盖、权限提升，对个人工具是纯负担；解压即用还能并存多个版本（回滚靠这个，见 §6.1）。

**一处必须注意**：不要解压到 `Program Files` 这类受保护目录。宿主本身只读运行，但插件目录与日志都在数据根，放在受保护目录会让「从命令行跑一次」也需要提权。

### 4.2 Linux

两种用法：

**直接解压使用**：

```bash
tar xzf ling-0.0.1-b3-linux-x64.tar.gz
cd ling-0.0.1-b3-linux-x64
./ling serve
```

**装到用户目录**：

```bash
./install.sh          # 装到 ~/.local/lib/ling 与 ~/.local/bin/ling
```

`install.sh` 只做四件事：复制文件到 `~/.local/lib/ling/`、在 `~/.local/bin/` 建一个软链接、检查 `~/.local/bin` 是否在 PATH 里、打印结果。不碰系统目录，不需要 sudo。

Android 不需要安装脚本：apk 由系统安装。

### 4.3 Android

1. 安装 apk（需要允许「安装未知来源应用」）。
2. 打开应用，点「启动」。
3. 通知栏出现「ling 运行中」，应用内显示一行地址。
4. 用浏览器打开该地址。

apk 不做界面，只做三件事：启动宿主进程、显示地址、提供停止按钮。这个决定与「界面是网页」一致——再做一个原生界面等于两套界面要维护。

### 4.4 首次启动做什么

顺序固定，任一步失败则退出并打印原因（`01` LING-REQ-074）：

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 解析数据根：`--data-dir` > `LING_DATA_DIR` > 平台默认 | 路径不可写则退出 |
| 2 | 创建数据根，权限 **0700**（Linux）或仅当前用户的 DACL（Windows） | 创建失败退出，提示路径 |
| 3 | 创建 `logs/`、`plugins/` 子目录，继承父目录权限 | 同上 |
| 4 | 生成 `session.json`（0600） | 同上 |
| 5 | 选端口（7900 起，占用则顺延），写 `registry.json` | 7900 至 7999 全占则退出 |
| 6 | 扫描 `plugins/`，发现为空则从程序目录安装五个内置插件 | 单个装失败记 warn，继续 |
| 7 | 启动侧车（`core-ui`），写 `ui_port` | 失败记 warn，宿主继续（界面不可用但命令行可用） |
| 8 | 打印「数据根、端口、界面地址、口令文件位置」四行 | —— |

第 2 步的权限由宿主自己设，不依赖安装器（`06` §5.4 的结论）。这样解压即用的包与将来的安装包行为一致。

第 6 步从**程序目录**复制内置插件，而不是解压时就放到数据根：程序目录可以只读（比如放在系统镜像里），数据根必然可写。

第 8 步的四行输出是给人看的，不加 `--quiet` 之外的开关。首次安装最容易卡在「不知道去哪看端口与口令」，这四行解决它。

## 5. 升级

### 5.1 手动替换的步骤

`01` LING-REQ-084 定了「停止宿主、替换二进制、重新启动」，不自动下载。具体六步：

```
1. ling shutdown（或界面上点停止）
2. 确认进程已退出（ling.exe 不在任务列表里）
3. 备份 settings.json（见 §5.2，可选但建议）
4. 解压新版本到新目录（不覆盖旧目录）
5. 用新目录的 ling serve 启动，数据根指向同一位置
6. 跑一次 ling doctor，确认四项正常
```

第 4 步「解压到新目录，不覆盖旧目录」是关键：覆盖会让回滚失去旧文件，且 Windows 上正在被加载的 dll 无法覆盖。

第 5 步的数据根不写就是默认位置，与旧版本相同。**数据根不随版本变**，这是升级能无缝的前提。

### 5.2 数据与配置的兼容

| 内容 | 升级时怎么处理 | 依据 |
|---|---|---|
| `plugins/<编号>/data/` | 内核不迁移，插件自己迁 | `01` LING-REQ-088 |
| `settings.json` | 带 `schema_version` 字段，`core-settings` 启动时按需迁移 | 本文新增 |
| `registry.json` | 缺字段用默认值补齐，多出的字段忽略 | 向后兼容 |
| `logs/` | 不动，文件名与格式不变 | —— |
| `session.json` | 每次启动重新生成，不保留 | —— |

`settings.json` 的 `schema_version` 是本文引入的：

```json
{
  "schema_version": 1,
  "entries": {
    "demo-a.timeout": {"v": 30, "updated_at": "2026-10-29T01:00:00+08:00"}
  }
}
```

迁移规则：

| 情形 | 处理 |
|---|---|
| 文件里没有 `schema_version` | 视为 1 |
| 版本等于当前 | 直接用 |
| 版本低于当前 | 按版本号逐级迁移，迁移前备份为 `settings.json.bak-<旧版本号>` |
| 版本高于当前 | 拒绝启动，提示「配置来自更新的版本」 |

最后一条必须做：旧版本读到新格式的配置时，容易把不认识的字段丢掉，写回时就把用户配置降级了。宁可拒绝。

### 5.3 内置插件的新增与跳过

| 情形 | 行为 |
|---|---|
| 新版本带来新的内置插件 | 自动安装；装前校验 `min_host`，不满足则跳过并记 warn |
| 用户之前主动卸掉的 | 不再装回（`04/07` §8.3） |
| 编号被业务插件占用 | 不装，记 warn，不覆盖 |
| 内置插件版本随宿主升 | 覆盖安装，保留其 `data/` |

第三条的判据要写清：「编号被占用」指 `plugins/<编号>/` 存在但清单里的 `id` 不是内置清单里的那个。

### 5.4 `api` 的兼容范围

宿主支持当前 `api` 主版本与前一版本（`01` LING-REQ-086）。

| 宿主 `api` | 可装载的插件 `api` | 不可装载 |
|---|---|---|
| 1 | 1 | 2 及以上 |
| 2 | 1、2 | 3 及以上 |

升 `api` 主版本是一次**不兼容变更**，同时要求：

1. 首要版本加一（`docs/common/02-版本号与兼容约定.md`）。
2. 写一份迁移说明，列出改了什么、旧插件要改哪几行。
3. 保留对前一版本的支持，至少一个大版本周期。

第三条的实际含义：宿主 `api=2` 时，`api=1` 的插件仍能用。这让升级不必一次性改完所有插件。

## 6. 回滚

### 6.1 保留上一版

做法就是 §5.1 第 4 步：升级不覆盖旧目录，两个版本并排存在。

```
D:\apps\
├── ling-0.0.1-b3\
├── ling-0.0.1-b4\
└── ling-0.0.2-b1\        ← 当前用这个
```

回滚 = 用旧目录的可执行文件启动，数据根不变。

保留几个旧版本不做硬性规定：磁盘上占几百 MB 而已，留两三个即可。删旧版本前确认当前版本已经稳定运行过一段时间。

### 6.2 数据格式回退的风险

这是回滚里唯一有真实风险的地方：新版本写过数据之后，旧版本会读不懂。

| 内容 | 回退风险 | 应对 |
|---|---|---|
| `settings.json` | 新版本升过 `schema_version` 后，旧版本会拒绝启动 | 升级前备份 `settings.json`（§5.2 的迁移也会自动备份） |
| `plugins/<编号>/data/` | 插件自己改过格式，旧版插件读不懂 | 无通用解法。**改格式的插件必须自己保留向下兼容**（`01` LING-REQ-088 的要求） |
| `logs/` | 无风险，只追加 | —— |
| `registry.json` | 旧版本忽略不认识的字段 | 无风险 |

第二条没有宿主层的兜底，这是设计上的取舍：内核不碰插件的数据，也就无法替它做迁移或回退。文档里要写明，让写插件的人知道这条责任在自己。

### 6.3 什么时候该回滚

| 判据 | 说明 |
|---|---|
| 宿主启动不了 | 最明确的信号，立刻回退 |
| 目录或插件加载失败，而旧版本正常 | 同上 |
| 数据被写坏（`doctor` 报告大量异常） | 回退后先恢复备份的 `settings.json` |
| 性能明显退化 | 先看 `bench-history.csv`，确认是版本问题再回退 |
| 界面完全不可用而命令行正常 | 不必回退，卸掉 `core-ui` 重装即可 |

最后一条要单独说：界面出问题不等于版本有问题，因为界面是侧车、可以单独处理。直接回退整个版本是过度反应。

### 6.4 回滚之后要做什么

1. 用旧版本启动，确认 `doctor` 四项正常。
2. 把新版本的问题记入 `docs/log/`，含版本号、现象、复现步骤。
3. 保留新版本的目录，不要删——修好之后还要用。

第 3 条容易被忽略：回滚后顺手删掉新版目录，等问题修好又要重新下载。

## 7. 卸载

### 7.1 两种程度

| 程度 | 做法 | 结果 |
|---|---|---|
| 保留数据 | 删程序目录，数据根留着 | 重装后数据与配置都还在 |
| 彻底清除 | 删程序目录，删数据根 | 干净，不可恢复 |

没有卸载程序，也没有注册表项，因为根本没有装到系统里。

### 7.2 手工清理清单

彻底清除时要删的东西，一个不能少：

| 位置 | 内容 |
|---|---|
| 程序目录 | 解压出来的整个文件夹 |
| `<数据根>` | Windows `%APPDATA%\ling`；Linux `~/.local/share/ling`；Android 应用私有目录 |
| Linux 的软链接 | `~/.local/bin/ling`（若跑过 `install.sh`） |
| Android 的应用数据 | 卸载 apk 时系统会问，选「清除数据」 |

第二项要特别注意：删了程序目录但留着数据根时，下次装新版会「接着用旧数据」，包括旧的 `plugins/` 与 `settings.json`。这有时是想要的（升级），有时不是（想重来一遍）。

### 7.3 卸载前的建议

| 建议 | 理由 |
|---|---|
| 先 `ling plugins` 看一眼装了什么 | 有些插件的数据需要单独留 |
| 备份 `settings.json` | 重装后导入能省去重新配置 |
| 备份重要的 `plugins/<编号>/data/` | 例如媒体库索引，重建要几小时 |

第三条最实际：`data/` 里的索引重建代价高，而它往往只有几十 MB。

## 8. 分发

### 8.1 放哪

| 内容 | 位置 |
|---|---|
| 源码 | 私有仓库 `https://github.com/xcxczscl/ling` |
| 二进制 | 同一仓库的 Releases，每个标签一组三端包 |
| 文档 | 随源码，`docs/` 目录 |

不打公开包管理器（winget、apt、Homebrew）：私人使用，入库要走审核流程，收益为零。

### 8.2 产物清单与校验和

每次发布，Releases 里附：

| 附件 | 内容 |
|---|---|
| 三端包 | 各一个 |
| `checksums.txt` | 三端包的 sha256，一行一条 |
| pdb 压缩包 | 仅 Windows |
| 迁移说明（若升了 `api` 主版本） | 改了哪些字段、旧插件要改什么 |

`checksums.txt` 的作用不是防篡改（自己给自己签名没有意义），是**验证下载完整性**：分包下载或网络不稳时，能确认文件没坏。

### 8.3 不做的事

| 不做 | 理由 |
|---|---|
| CI 自动构建发布 | 个人工具，本地构建三端十分钟，没必要维护流水线 |
| 代码签名证书 | 一年几百到几千元，只买一个「SmartScreen 不警告」，对自用无收益 |
| 自动更新机制 | 没有版本服务器（§1.3） |
| 灰度与分阶段发布 | 只有一个用户 |
| 安装包与注册表项 | 解压即用更简单，且支持多版本并存（§6.1） |

第二条的代价要写清：Windows 上首次运行会弹 SmartScreen 警告，选「仍要运行」即可。这是不做签名的直接后果，不是 bug。

## 10. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | Android 的 apk 值不值得做 | 做，定位为宿主启动器加通知栏，不做原生界面。原生界面是另一个量级的项目 | §2.3 |
| 2 | `settings.json` 的迁移由 `core-settings` 做还是宿主做 | 由 `core-settings` 做。它最清楚每个字段的含义 | §5.2 |
| 3 | 旧版本保留几个 | 留两个。磁盘占用可接受，覆盖「上一版可用」与「上上版可用」 | §6.1 |
| 4 | Linux 是否出 AppImage | 不出。AppImage 要处理挂载与 FUSE 依赖，而 tar.gz 已经够用 | §2.1 |
| 5 | 是否给 `install.sh` 加 `--prefix` | 加，默认 `~/.local`。改动只有几行，能适应不同习惯 | §4.2 |
