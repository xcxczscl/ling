## 1. 判定维度与权重

### 1.1 七个维度

| 维度 | 衡量什么 | 怎么判断 |
|---|---|---|
| 可读性 | 你不借助解释能否读懂内核代码 | 抽样读 200 行，能否说清它在做什么 |
| 热更新可靠性 | 改插件后不重启宿主，能否干净换上 | 100 次连续重载后内存与行为是否正常 |
| 三端支持确定性 | Windows / Linux / Android 是否都有明确可行的路径 | 是否有官方工具链与已知限制 |
| 崩溃可控性 | 插件出错时宿主是否还活着、错误是否可定位 | 故意让插件崩溃，看宿主存活与调用栈质量 |
| 生态对接 | 与 ffmpeg、mpv 这类 C 库的对接成本 | 是否需要自己写绑定层 |
| 构建复杂度 | 新人从零到跑起来的步骤数 | 依赖管理、交叉编译的配置量 |
| 工具链成熟度 | 调试器、性能分析、崩溃转储是否好用 | 三端是否有稳定调试手段 |

### 1.2 权重

权重：可读性 30%、热更新可靠性 20%、三端支持确定性 20%、崩溃可控性 15%、生态对接 10%、构建复杂度 5%。可读性最高，因为上一版失败的直接原因就是「代码看不懂」；热更新与三端各 20%，是核心卖点与目标平台的硬要求；崩溃可控性 15%，宿主被插件拖死等于全部插件失效；生态对接 10%，播放器必须调 C 媒体库；构建复杂度只影响起步。

工具链成熟度不单独计权：它的影响已经体现在「崩溃可控性」与「构建复杂度」里，单列会重复计分。

可读性权重最高是本文最关键的一个判断。理由不是「方便」，是**可持续性**：自己读不懂的内核，每次改动都要重新理解一遍，改错概率随代码量上升。

## 2. 约束与前提

### 2.1 不变的约束

来自 `docs/ling/main/00-总览与术语.md` 与 `docs/ling/main/01-需求规格.md`，本文不重新讨论：宿主零内容，只提供机制；单机、单用户、几十个插件；多平台（Windows 主要、Linux 对齐、Android 受限降级）；插件可独立装载、卸载、热更新；插件之间不直接链接，只经宿主互调。

### 2.2 可信前提

**所有插件都由你自己编写。** 这决定威胁模型边界：不防恶意插件（归 `docs/ling/main/06-安全设计.md`），但要防**意外崩溃**——自己写的插件也会空指针、死循环、越界。因此进程内插件可视为「可信但会出错」，设计重点从「隔离」转向「出错后能恢复、能定位」。

### 2.3 性能底线分档

| 档位 | 场景 | 可接受上限 | 判断依据 |
|---|---|---|---|
| 交互式 | 界面响应、播放控制 | 50 毫秒 | 人感知阈值约 100 毫秒，留一半余量 |
| 批量 | 文件扫描、哈希、批量转码 | 无上限要求 | 耗时由数据量决定，不由调用机制决定 |
| 管理 | 装插件、查状态、看日志 | 500 毫秒 | `docs/ling/main/01-需求规格.md` LING-REQ-096 |

批量操作占实际耗时绝大部分，且耗时与调用机制开销无关；真正需要快的只有交互式一档。这个推论直接决定 §3 的形态选择。

### 2.4 上一版失败的原因

上一版用 Rust 写了约 6300 行内核（`old/main/`，27 个文件），结果是「看不懂，出了问题查不出来」。以下四条已由你确认：

| # | 原因 | 具体表现 | 为什么致命 |
|---|---|---|---|
| 1 | 没有 Rust 基础 | 读代码时没有可对照的先验知识，看不出哪一段写错了 | 判断权全部落在 AI 手里，每一版改动都能自圆其说 |
| 2 | 反复修改仍然有问题 | 每改一版都显得更有道理，但没有标准能判定「这次是对的」 | 缺可判真假的验收标准，改动无法收敛 |
| 3 | 项目没有纠错能力 | 无测试、无基准、无设计基线 | 发现错误的成本高于引入错误的成本 |
| 4 | 知识储备不足 | 读一遍要查一批概念，第二遍仍然要查 | 每次改动都重新理解，进度被理解本身吃掉 |

前两条与语言和流程有关，换语言能缓解；后两条换语言解决不了：换一门有基础的语言只把「看不懂」降为「看得慢」，纠错能力得靠测试与文档基线。

对策与落点：① 换成有基础的语言、写法规避读不懂的构造（§4.2、§8）；② 先定设计再写码、每条需求配可判真假的验收标准（`docs/ling/main/01-需求规格.md` §1.4、本文 §7）；③ 每个需求组挂测试文件、基准先于性能改动（`docs/ling/main/01-需求规格.md` §6）；④ 文档分详细版与简版、每节写「为什么」、需求与技术决定逐条对照（§2.5、附录 A）。

## 3. 插件形态

### 3.1 三种形态

| 形态 | 做法 | 插件与宿主的边界 |
|---|---|---|
| 纯进程内 | 插件编译成动态库（`.dll` / `.so`），`dlopen` 装入宿主进程 | 函数调用 |
| 纯侧车 | 每个插件是独立可执行文件，宿主启动它并用本地套接字通信 | 进程 + 消息 |
| 混合双轨 | 性能敏感的插件进程内，其余侧车 | 两者都有 |

### 3.2 对照

| 项 | 纯进程内 | 纯侧车 | 混合双轨 |
|---|---|---|---|
| 调用延迟 | 0.1–1 微秒 | 50–200 微秒 | 按插件分 |
| 崩溃隔离 | 无，插件崩则宿主崩 | 完全隔离 | 部分 |
| 热更新 | 难，见 §5.6 | 易，重启进程即可 | 按插件分 |
| 语言自由度 | 必须与宿主 ABI 兼容 | 任意语言 | 双轨各自受限 |
| 内核代码量 | 大（装载器、ABI 胶水、崩溃捕获） | 小（协议 + 进程管理） | 最大 |
| 调试难度 | 混合栈，跨语言断点 | 单独进程，可单独附加 | 都要会 |
| 内存共享 | 直接共享 | 必须序列化 | 都要会 |

延迟依据：本地套接字往返含两次系统调用、两次上下文切换、一次请求序列化 + 一次响应反序列化，实测常见 30–100 微秒，取 50–200 微秒；进程内调用约 300–500 纳秒。

### 3.3 为什么选混合双轨

- **交互式场景必须快**：调用链短、频率高，只有进程内能满足预算
- **批量场景不敏感**，且最需要语言自由度（扫描、转码、解析文件格式，Python 生态最方便）
- 纯侧车让所有插件都背上 50–200 微秒；纯进程内强迫所有插件用同一门语言，等于放弃「小功能用 Python 直接写」

代价是内核要维护两套装载路径，§5 说明如何把成本压到可接受。

### 3.4 混合双轨的收敛办法

1. **进程内插件只用于交互式热路径**，默认侧车，进程内是例外，需要理由。
2. **进程内插件的 ABI 只有一张函数表**，见 §5.2，整个系统的跨语言边界只有一个点。
3. **进程内插件不允许卸载**，热更新改为「加载新版本、切换指针、旧版本留在内存」，见 §5.6。

第 3 条牺牲一点内存（每次重载泄漏一个映射），换来可靠性；对个人工具这个交换划算。

侧车进程各自占用独立内存，常驻数量受 `docs/ling/main/01-需求规格.md` LING-REQ-099 约束。每个空载 Python 侧车按 40 MB 算，五个就 200 MB，已超过「内核加 20 个插件 ≤ 120 MB」。因此侧车默认按需启停，常驻上限写在 `docs/ling/plugin-support/01-插件装载与接口.md`，不在本文定。

## 4. 语言对照

### 4.1 排除的候选

| 语言 | 排除理由 |
|---|---|
| Go | 标准库 `plugin` 包只在 Linux 与 macOS 可用；且要求插件与宿主用完全相同的依赖版本，实际无法分发 |
| Java / Kotlin | JVM 启动 300 毫秒起、常驻 100 MB 起，与 LING-REQ-094（冷启动 ≤ 300 毫秒）和 LING-REQ-099（常驻 ≤ 120 MB）冲突；三端分发要带 JRE |
| Node.js / Electron | 运行时内存百 MB 起；适合做界面，不适合做需要直接操作文件与调用 C 库的宿主 |
| Zig | 生态与工具链成熟度不足，绑定 C 库可行但调试与文档资料少，风险高于收益 |

排除不等于永远不用：这些语言都可以作为**侧车插件**的语言，因为侧车只要求「能读写本地套接字、能处理 JSON」。

### 4.2 C++

**能否做宿主**：能，且是原生方案，`dlopen` / `LoadLibrary` 是标准能力。**调用开销**：进程内虚函数或函数指针调用，约 1–10 纳秒。**内存安全**：无，野指针、重复释放、越界会直接破坏宿主进程，这是最大短板。

**三端**：Windows 用 MSVC 2022、Linux 用 GCC 或 Clang、Android 用 NDK（Clang），三端都成熟，Android 需处理 ABI 与 STL 版本。

**生态对接**：ffmpeg、mpv、libvlc 都是 C/C++，零绑定成本，四门语言里最好。**热更新**：`dlclose` 可用但不可靠，见 §5.6。**可读性**：语法直白；模板、指针与手动内存管理、宏三样是阅读负担，都可以通过写法约定规避，见 §8。**构建**：CMake，依赖单文件随仓库走（`third_party/`），配置比 Cargo 长但内容直白，对本项目更好读。

### 4.3 Rust

技术上完全可行（`libloading` 加载动态库，调用开销与 C++ 同量级，`cargo` 三端交叉编译成熟）。它的内存安全保证**止步于 `unsafe` 边界**，而插件宿主的核心恰恰全是 FFI 边界代码，关键路径上的优势并不存在。生态对接的 ffmpeg / mpv 绑定由第三方维护，版本要自己跟；热更新是四门语言里最差（见 §5.6）。可读性上，所有权与生命周期标注、`async` 与 `Send + Sync` 约束、trait 对象与泛型三样叠加，是上一版失败的直接原因。

**结论**：按 §1.2 的权重，可读性 30% 这一项它得分最低，而这一项权重最高。不选它的理由是权重，不是能力。

### 4.4 C#

#### 4.4.1 路线 A：整个宿主用 C#（托管宿主）

调用开销 10–30 纳秒，JIT 后计算性能约 C++ 的 50%–90%，有 GC 停顿；`AssemblyLoadContext` 支持可回收卸载，热更新四门语言里最好；内存安全，但 `StackOverflowException` 与 `OutOfMemoryException` 无法捕获；空载常驻 30–50 MB，与 120 MB 上限能共存但余量不大；自包含 + ReadyToRun 启动约 100–200 毫秒，满足 LING-REQ-094；ffmpeg 需 `FFmpeg.AutoGen`，每次 P/Invoke 约 20–50 纳秒。

三端是问题：Windows / Linux 的 CoreCLR 支持可回收加载；**Android 用 Mono，后装插件无法 AOT 预编译，必然走解释器**，且 `AndroidUseInterpreter` 开关在 .NET 11 起不再存在，路线在收窄。**NativeAOT 走不通**：官方不支持运行时加载程序集，而它正是 C# 启动快、内存小的唯一办法——要 NativeAOT 的性能，就得放弃动态加载。

#### 4.4.2 路线 B：C++ 宿主嵌入 CoreCLR

用 `hostfxr` 把 .NET 运行时加载进 C++ 进程。复杂度高（运行时初始化、托管异常不能跨边界、GC 句柄与钉住、双向调用胶水），调试是两套调试器的混合栈，收益只有「C++ 内核配 C# 插件」这一项语言搭配偏好。**结论**：不推荐，对单人维护的项目代价远大于收益。

#### 4.4.3 C# 的总结

按 §1.2 的权重，C# 在「可读性」与「热更新可靠性」两项第一，在「三端支持确定性」失分，在「生态对接」居中。它是四门语言里**技术上最优雅的宿主选择**，输在三件事：你不熟 C#、Android 路线在收窄、媒体库要经过绑定层。

### 4.5 Python

#### 4.5.1 作为宿主

不可行。CPython 空解释器约 8–15 MB，启动约 50–150 毫秒，加依赖后更高；GIL 会让所有插件串行。

#### 4.5.2 嵌入宿主进程（C++ 链接 libpython）

调用约 0.1–0.5 微秒（不含类型转换），受 GIL 限制；C 扩展段错误会直接杀掉宿主；从 `sys.modules` 删模块不清循环引用、不清 C 扩展状态、不停后台线程，反复重载必然累积残留；打包需带 `python314.dll` 与裁剪标准库（Windows 约 5 MB），Android 需交叉编译 CPython。

**类型转换才是成本主体**：估算依据是 1 MB 内存拷贝 30–100 微秒，JSON 解析 100–300 MB/s。5 字段小 dict 0.5–2 微秒，1 KB 字符串 1–3 微秒，1 MB 字节缓冲 100–300 微秒，1 MB JSON 5–15 毫秒。一旦按 LING-REQ-097 允许 1 MB 载荷，转换成本就超过侧车的套接字往返。**嵌入 CPython 的「高速」只在小载荷、纯数值参数时成立。** GIL 是第二个硬约束：三个 Python 插件嵌入同一解释器时不能真正并行，一个卡住 GIL，其他调用全部排队；3.14 的 free-threaded 构建仍需单独构建且生态未适配。

#### 4.5.3 侧车进程

调用 50–200 微秒（只与进程边界有关）；每个插件一个进程、独立 GIL、真正并行；崩溃完全隔离；热更新最容易；需带 Python 运行时（裁剪后约 15–30 MB）。**结论**：Python 在 ling 里的正确位置是**侧车插件**，不是宿主，也不推荐嵌入宿主进程。

内存要记账：一个空载 Python 侧车 25–40 MB，而 LING-REQ-099 给「内核加 20 个插件」的总预算是 120 MB。所以 Python 侧车默认按需启停，最多允许 1 个常驻；配额与拒绝规则见 `docs/ling/plugin-support/01-插件装载与接口.md` §8.7。

### 4.6 总表

评分 1–5，5 最好。权重见 §1.2。

| 维度 | 权重 | C++ | Rust | C# | Python |
|---|---|---|---|---|---|
| 可读性 | 30% | 3 | 2 | 5 | 4 |
| 热更新可靠性 | 20% | 2 | 1 | 5 | 3 |
| 三端支持确定性 | 20% | 5 | 5 | 3 | 3 |
| 崩溃可控性 | 15% | 2 | 3 | 4 | 2 |
| 生态对接 | 10% | 5 | 4 | 3 | 5 |
| 构建复杂度 | 5% | 3 | 4 | 4 | 2 |
| **加权总分** | 100% | **3.25** | **2.85** | **4.20** | **3.30** |

计算过程：C++ = 0.9 + 0.4 + 1.0 + 0.3 + 0.5 + 0.15 = 3.25；Rust = 0.6 + 0.2 + 1.0 + 0.45 + 0.4 + 0.2 = 2.85；C# = 1.5 + 1.0 + 0.6 + 0.6 + 0.3 + 0.2 = 4.20；Python = 1.2 + 0.6 + 0.6 + 0.3 + 0.5 + 0.1 = 3.30。

**这张表给出一个反直觉的结论：C# 得分最高。** 但评分不等于结论，原因三条都不在表里：① 可读性打分假设「你懂这门语言」，C# 的 5 分建立在会读 C# 之上，学新语言的前三个月可读性按 0 计；② 三端确定性的 3 分掩盖了一个趋势——Android 的 C# 动态加载路线在收窄，而 `docs/ling/main/00-总览与术语.md` §2.4 把 Android 列为长期目标；③ 评分是静态的，不反映「将来想加新插件语言」这个自由度，C ABI 边界对任何语言开放，托管边界只对 .NET 开放。

所以 §6 的结论是：**按评分 C# 最高，按实际条件与长期路线选 C++。**

## 5. 插件边界技术

这是全篇对工程影响最大的一节，最容易出「编译通过、运行崩溃」的问题。

### 5.1 为什么必须用 C ABI

C++ 没有稳定的二进制接口，后果具体：

| 不一致的地方 | 后果 |
|---|---|
| 编译器不同（MSVC 与 Clang） | 名称修饰规则不同，链接时找不到符号 |
| 同一编译器的不同大版本 | 类布局与虚表布局会变化 |
| 运行时库不同（`/MD` 与 `/MT`） | 两份堆，一边申请一边释放，崩溃 |
| 异常模型不同（`/EHsc` 与 `/EHs`） | 跨边界抛异常时栈展开行为不一致 |
| 标准库版本不同（不同 STL 实现） | `std::string` 布局不同，跨边界传它会读错内存 |

规避办法只有一个：**跨动态库边界只用 C 语言的那部分**。C 的函数调用约定、结构体布局、基本类型是各编译器共同遵守的稳定约定；Qt、Chrome、LibreOffice 都这么做。Rust 的处境相同：两个 Rust 动态库之间同样不能直接传 `String`、`Vec`、trait 对象，也要退化到 C ABI 或引入 `abi_stable`。**这一点上两种语言没有区别**，「Rust 比 C++ 更安全」在边界这一层不成立。

### 5.2 唯一入口点

整个系统跨语言边界的地方只有一个：插件导出**一个**函数。

```c
/* 边界契约的示意，完整定义在 docs/ling/plugin-support/01-插件装载与接口.md §5.1、§5.2 */
typedef struct {
    uint32_t abi_version;  const char* plugin_id;  const char* plugin_version;
} ling_plugin_descriptor;
typedef struct {
    void* (*context_alloc)(void);
    int32_t (*register_method)(void* ctx, const char* name, void* fn, void* undo);
    int32_t (*call)(void* ctx, const char* target, const char* method, const uint8_t* args, size_t len, uint8_t** out, size_t* out_len);
} ling_host_api;
int32_t ling_plugin_entry(const ling_host_api* host, ling_plugin_descriptor* out);
```

三个性质：**一个符号**（其余全部经函数表转发，加功能只扩 `ling_host_api`）；**版本可查**（`abi_version` 不匹配直接拒绝，不崩在半路）；**语言中立**（任何能导出 C 函数的语言都能写进程内插件，见 §7）。

胶水规模：宿主侧装载器约 150 行、函数表定义与实现约 100 行、错误映射约 50 行，合计约 300 行，只写一次。这是混合双轨成本可控的关键。

### 5.3 类型禁区

| 允许 | 说明 |
|---|---|
| 定宽整数、浮点 | `int32_t`、`uint64_t`、`double`，布局确定 |
| 不透明句柄 | `void*`，指向谁只有提供方知道 |
| 指针 + 长度 | `const uint8_t* data, size_t len`，不用以 0 结尾的字符串传含 0 字节的数据 |
| 定长结构体（纯数据） | 只用定宽字段，成员顺序与对齐由 `#pragma pack` 或显式填充固定 |
| 函数指针 | 带明确的调用约定 |

| 禁止 | 原因 |
|---|---|
| `std::string`、`std::vector`、`std::map` | 布局依编译器与 STL 实现而变 |
| 抛异常跨边界 | 异常模型不一致，栈展开行为未定义 |
| 跨边界用 RTTI（`dynamic_cast`、`typeid`） | 虚表布局与类型信息格式不保证一致 |
| 传递 C++ 对象的所有权 | 谁申请谁释放，不能跨边界移交 |
| 回调里持有引用超过调用期 | 宿主不保证对象在回调返回后仍存活 |

**内存归属的硬规则**：谁申请谁释放。跨边界返回的缓冲区必须由同一模块提供释放函数，例如 `ling_host_api` 的 `free_buffer`，插件用它释放宿主给的缓冲，不许调自己的 `free`。Windows 上 `/MD` 与 `/MT` 各有一份堆，混用立刻崩。

### 5.4 编译器与运行时一致性

| 约束 | Windows | Linux | Android |
|---|---|---|---|
| 编译器 | 统一用 MSVC 2022 | 统一用 Clang（不用 GCC 混编） | 统一用 NDK 里的 Clang |
| C++ 标准 | `/std:c++17` | `-std=c++17` | 同 Linux |
| 运行时库 | 统一 `/MD`（动态 CRT） | 不涉及 | 不涉及 |
| 异常模型 | 统一 `/EHsc` | 默认 | 默认 |
| 架构 | x64 与 arm64 各自一致 | 同左 | arm64-v8a |
| 构建类型 | Debug 插件不能装进 Release 宿主 | 同左 | 同左 |

落地办法：`docs/ling/main/05-构造与开发指南.md` 提供统一构建脚本，宿主与所有插件共用同一份编译选项定义。**插件作者不自己写编译选项**，约束不靠人记。

### 5.5 崩溃捕获

**进程内插件崩溃不一定导致宿主崩溃，要看是哪种故障。**

| 故障类型 | Windows | Linux / Android | 宿主能继续吗 |
|---|---|---|---|
| 同步异常：访问违例、除零、非法指令 | `AddVectoredExceptionHandler` 能捕获，可隔离该插件 | 信号处理器里唯一安全的动作是 `_exit`；`siglongjmp` 跳回来会留下锁死与分配器损坏 | Windows 能，Linux 与 Android 不能 |
| 栈溢出 | 保护页触发时栈已不可用，捕获了也回不去 | 同左 | 不能 |
| 堆破坏 | 崩溃点滞后于肇事点，捕获处早已不是出事的地方 | 同左 | 不能 |
| 死循环、死锁（不是崩溃） | 靠 30 秒调用超时切断，宿主继续 | 同左 | 能，但那条线程被占住 |
| 写坏宿主的共享结构 | 没有检测手段 | 同左 | 表面活着，结果不可信 |

**「能挡住」不等于「能恢复」。** 捕获到异常时，那条线程持有的锁与堆内部状态都无法确认。恢复动作只能是三件事：标记该插件故障、拒绝后续调用、撤销它登记过的效应——不是「修好它继续跑」，那等于带病运行。

三平台手段：Windows 用向量化异常处理（与 `docs/ling/main/03-架构设计.md` §5.4 一致）；Linux 与 Android 用信号处理器加兜底退出。

由此得到三条约束：① Windows 上的同步异常 → 捕获、记录、标记故障、撤销效应，其余插件不受影响；② Linux 与 Android 上的同步异常，以及任何平台的栈溢出与堆破坏 → 宿主退出，靠外部守护（systemd、计划任务）拉起；③ **真正可靠的隔离只有侧车**，这是混合双轨必须接受的代价。

插件写坏宿主的共享数据结构时，程序不会立刻崩，而在后续某个不相干的调用上出错。这类问题只能靠**进程内插件保持无状态**（§3.4 第 1 条）与**测试覆盖**降低概率，无法用技术手段消除。

### 5.6 热更新的三条现实路径

#### 路径一：`dlclose` 卸载后重新加载（C++ 名义方案）

理论可行，实际有四个坑：TLS 未释放则不会真正卸载；同名文件重新 `dlopen` 返回旧句柄；静态对象析构顺序不可控；其他库持有的指针指向旧代码。

#### 路径二：复制到新文件名再加载（工程实践）

每次重载把插件文件复制成新名字（`plugin_0001.dll`、`plugin_0002.dll`），用不同路径 `dlopen`。新版本能加载，旧版本留在内存不卸载，代价是每次重载泄漏一个代码映射——按典型插件 100–500 KB 估算，100 次重载泄漏 10–50 MB。

`docs/ling/main/01-需求规格.md` LING-REQ-101 原定「100 次连续 reload 后内存增长 ≤ 10 MB」，与私有副本的映射泄漏冲突。已定为放宽到 ≤ 50 MB，达到 30 MB 时 `doctor` 提示重启；两处数值口径一致，都指 100 次累计而非单次增长。

#### 路径三：侧车重启（可靠方案）

杀掉旧进程、起新进程，进程退出由操作系统回收全部资源。代价是重载期间该插件不可用（约 100–500 毫秒），期间调用返回 `E_PLUGIN_MISSING`（`docs/ling/main/01-需求规格.md` LING-REQ-054）。

#### 四门语言的热更新能力对照

| 语言 | 路径一 | 路径二 | 路径三 | 综合 |
|---|---|---|---|---|
| C++ | 有坑 | 可行，泄漏 | 可行 | 2/5 |
| Rust | **本质不安全**，社区共识是不卸载 | 可行，泄漏 | 可行 | 1/5 |
| C# | 不需要：`AssemblyLoadContext` 可回收，GC 负责清理 | — | 可行 | 5/5 |
| Python | 嵌入模式下不可靠（`sys.modules` 清理不彻底） | — | 可行 | 3/5 |

Rust 得 1 分是语言层面的限制：卸载后库里的 `&'static` 引用、字符串字面量、trait 对象虚表指针全部变成悬垂指针，类型系统无法表达「这个 `'static` 只在这个库加载期间有效」。

**本文的取舍**：进程内插件放弃路径一，采用路径二，并在账本里记录泄漏、达到阈值提示重启；侧车插件走路径三。

## 6. 最终组合

### 6.1 结论

| 角色 | 选择 | 版本 |
|---|---|---|
| 宿主内核 | C++ | C++17，MSVC / Clang / NDK Clang |
| 进程内插件 | C++（同一套 ABI） | 同宿主 |
| 侧车插件（首选） | Python | 3.14（含 free-threading 构建） |
| 侧车插件（其他） | 任意能读写本地套接字的语言 | 不限制 |
| 边界技术 | 单个 `ling_plugin_entry` 导出函数 + C ABI 函数表 | `abi_version` 从 1 开始 |
| 构建系统 | CMake（依赖单文件随仓库走，见 `third_party/`）、NDK 工具链（Android） | 构建时固定 |

具体版本（编译器小版本、CMake、第三方依赖、Python 运行时、NDK）不写在这里，构建时确定并写入 `docs/ling/main/05-构造与开发指南.md` 与 `third_party/README.md`。理由：写「最新稳定版」等于没写，不同时间构建会得到不同依赖，出了问题无法复现。

### 6.2 被否方案与理由

| 方案 | 否掉的理由 |
|---|---|
| Rust 内核 | 可读性权重最高而它该项最低（§4.3）；热更新最差 |
| C# 托管宿主 | 评分最高但你不熟 C#；Android 动态加载路线在收窄；NativeAOT 与动态插件二选一 |
| C++ 宿主 + Python 嵌入 | GIL 串行、C 扩展崩溃不隔离、热更新不可靠；大载荷转换成本超过侧车（§4.5.2） |
| 纯侧车 | 交互式场景的延迟预算会被插件数量摊薄（§3.3） |
| 纯进程内 | 放弃 Python 插件这个最大便利，且 Linux/Android 上崩溃不隔离 |
| Go / Java / Node 宿主 | 见 §4.1 |

## 7. 可替换性设计（防止返工）

返工的最大来源不是选错语言，而是**把语言写进了契约定死**。为此有三条设计约束：

### 7.1 契约与实现分离

| 层 | 内容 | 换语言时是否重写 |
|---|---|---|
| 契约层 | 插件清单格式、方法名与事件名规则、错误码表、消息协议、`ling_host_api` 函数表定义 | **不重写**，与语言无关 |
| 内核实现 | 路由表、事件总线、门禁、依赖解析的具体代码 | 重写 |
| 插件实现 | 每个插件自己的业务逻辑 | 不重写（侧车插件完全不用改；进程内插件需重新编译） |

契约层文件放在 `docs/ling/main/04-详细设计/` 与仓库的接口头文件中，用**语言中立的写法**描述：结构体字段用定宽类型，协议用 JSON schema 或表格，不用任何 C++ 特性表达契约。

### 7.2 换内核语言的代价估算

| 部分 | 工作量 |
|---|---|
| 内核 6000 行左右重写 | 大头 |
| 侧车插件（Python） | 零改动，协议没变 |
| 进程内插件（C++） | 不用改代码，但需按新宿主的装载方式重新编译 |
| 文档 | 契约部分不用改，实现部分要改 |

这个估算成立的前提是 §7.1 做到了。若契约里混进了 `std::string` 这类语言相关类型，侧车协议也要跟着改。

### 7.3 一个额外的口子

`ling_host_api` 是 C ABI，意味着**非 C++ 的进程内插件在技术上可行**。将来某个热点插件想用 Rust 写，只要能导出 `ling_plugin_entry` 并填好函数表，就能装进同一个宿主。这条不承诺、不测试、不写文档，但设计上不堵死。

## 8. 「不耍花招」写法约定

语言选对只是必要条件，写法约定才是「读得懂」的充分条件。

### 8.1 禁用

| 禁用项 | 原因 |
|---|---|
| 模板元编程（`std::enable_if`、SFINAE、变参模板递归）、多继承 | 阅读时要在脑内展开，错误信息长达数百行；对象布局与指针调整难以推理 |
| 运算符重载（除 `==`、`<` 这类显然语义）、宏定义控制流 | 读代码时看不出在做什么；调试器单步会跳过 |
| 异常跨模块传播、全局可变状态 | 见 §5.3，行为未定义；无法推理谁在什么时候改了它 |
| 裸 `new` / `delete`、`malloc` / `free`、C 风格数组与指针算术（`p + i`） | 忘记释放、重复释放、两套堆混用；越界与算错单位都编译不出错 |
| `reinterpret_cast`、单文件超过 500 行 | 类型混叠行为未定义（只允许出现在边界层且必须带注释）；超过 500 行说明职责不单一 |

### 8.2 允许并鼓励

| 允许项 | 说明 |
|---|---|
| RAII、`std::unique_ptr` / `std::shared_ptr` | 用析构函数与明确所有权管资源，C++ 里减少出错的最有效手段 |
| `const` 与 `constexpr`、简单模板（容器、`std::optional`、`std::variant`） | 让编译器帮忙检查；只用不改语义的那部分 |
| 早期返回（`if (!ok) return err;`）、每个函数单一职责且不超过 60 行 | 减少嵌套层级，便于单独测试与阅读 |

### 8.3 命名与注释

| 类别 | 约定 |
|---|---|
| 类型 | `PascalCase`，如 `PluginRegistry` |
| 函数与方法 | `snake_case`，如 `register_method` |
| 成员变量 | 后缀下划线，如 `entries_` |
| 常量 | `k` 前缀，如 `kMaxPayloadBytes` |
| 文件 | `snake_case.cpp`，一个文件一个主要类型 |
| 注释 | 写「为什么这么做」，不写「这行在做什么」 |

命名规则不需要你记：`docs/ling/main/05-构造与开发指南.md` 会配 `clang-format` 配置与检查清单，格式问题由工具管。

### 8.4 内存安全靠机制，不靠小心

**写法层**：所有权只有一个表达（`std::unique_ptr` 表示拥有，裸指针与引用只表示观察）；容器替代裸数组（`std::array`、`std::vector`、`std::span`）；不做指针算术，确实要做时封装成函数并单独测试；`std::string_view` 只作入参，禁止存成员、返回或跨异步边界；边界只传「指针 + 长度」；定宽整数（`int32_t`、`uint64_t`、`size_t`）；所有权不跨边界移交，谁申请谁释放。

**工具层**：编译器警告全开且视为错误（MSVC `/W4 /WX`，Clang `-Wall -Wextra -Werror`），每次编译；AddressSanitizer + UndefinedBehaviorSanitizer，每轮测试；`clang-tidy` 的 `bugprone-*` 与 `cppcoreguidelines-*`，提交前；边界函数的负向测试（空指针、超长输入、非法编码），每轮测试。这四项由 `docs/ling/main/05-构造与开发指南.md` 的构建脚本统一提供，**不配就编不过**。

必须承认的边界：这些手段能消除大部分内存错误，但**不能保证没有**。C++ 的未定义行为在测试覆盖不到的地方仍然存在，这也是 §2.4 里「项目缺纠错能力」要靠测试与 ASan 常态运行来补的原因。
