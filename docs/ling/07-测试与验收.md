# ling 07 测试与验收

> 状态：初定 | 最后更新：2026-10-29
> 依据：`docs/ling/01-需求规格.md` §6；`docs/ling/05-构造与开发指南.md` §5；`docs/ling/06-安全设计.md` §2.2

本文回答三件事：测什么、怎么测、什么算通过。

它不重复 `01` 的验收标准——那 127 条的判定条件在需求里已经写死，本文只定义**怎么把它们跑起来**：分几层、用什么夹具、性能怎么量、故障怎么造、失败怎么判。

| 与开发切片的对应 | S0 到 S6 各跑哪些 |

### 1.2 不覆盖什么

| 内容 | 去哪 |

### 1.3 一条原则

**能被自动判定的绝不留给人工。** 人工检查只保留三类：看得见的东西（界面布局）、拿不到的机器（Android 真机）、代价过高的场景（24 小时长稳）。

这条原则的用处是防止「测试清单越长越认真」的错觉——一份五十项手工检查表，实际执行时会被勾着走。

## 2. 测试分层

### 2.1 五层

| 层 | 命令 | 跑一次多久 | 什么时候跑 | 判定 |
|---|---|---|---|---|
| 单元测试 | `ctest -R unit` | 毫秒到秒 | 每次 `precommit.sh` | 全绿 |
| 验收脚本 | `ctest -R acceptance` | 十秒到分钟 | 每个开发切片完成时 | 全绿 |
| 性能基准 | `ctest -R bench` | 一分钟到五分钟 | 每个切片完成、改动热路径后 | 不超上限 |
| 压力测试 | `ctest -R stress` | 五分钟到半小时 | S4、S6 完成时 | 无崩溃、无超阈值泄漏 |
| 手工检查 | 无（清单在 §9） | 十分钟 | S6 与每次发布前 | 逐项勾选 |

分层的关键不是「越往下越重要」，而是**跑得越快越早跑**：单元测试几百条一秒跑完，就能每次改代码都跑；验收脚本要起真实进程，只好放到切片边界。

### 2.2 脚本命名的含义

`01` §6 里出现的 `l1_manifest`、`l6_stability` 这些名字，前缀此前没有定义。这里补上：

| 前缀 | 表示的环境复杂度 | 典型内容 |
|---|---|---|
| `l1` | 单进程内核，零或一个最小插件 | 清单校验、路由、事件、能力、调用基准 |
| `l2` | 单插件 + 完整上下文 | 注册与撤销、账本、数据目录 |
| `l3` | 三个以上插件 + 依赖关系 | 依赖图、调和、图算法基准 |
| `l4` | 命令行与管理端口 | 子命令、认证、事件与日志、命令基准 |
| `l5` | 五个内置插件齐备 | 预装、卸载、界面可用性 |
| `l6` | 跨进程与系统级 | 侧车、资源占用、稳定性、平台、升级 |

数字不代表「先跑哪层」，只表示「这一层需要多少东西在场」。写新脚本时按这个规则取前缀，不再另起一套。

### 2.3 测试与需求的映射

一条需求至少要有一个用例，但不要求一个用例只测一条需求。

| 情况 | 处理 |
|---|---|
| 一条需求一个用例 | 默认做法 |
| 一条需求拆多个用例（正向、多个负向） | 允许。负向用例数不少于正向的一半（`05` §5.2 的出口条件） |
| 一个用例覆盖多条需求 | 允许，用例表里把编号都列上 |
| 需求无法自动测 | 进 §9 的手工清单，写明为什么 |

`01` §6 的追溯表给出「需求组 → 设计文档 → 测试文件」，本文给出「测试文件 → 具体用例」。两者合起来形成双向可查。

## 3. 环境与夹具

### 3.1 数据根

每个验收脚本用独立数据根：`run/<preset>/data-test/<脚本名>/`。

规则：

| 规则 | 理由 |
|---|---|
| 脚本开始前删掉并重建 | 保证每次从干净状态起 |
| 不使用用户的真实数据根 | 防止测试把用户配置删了 |
| 脚本结束后保留最近一次，供排查 | 失败时能直接看日志与插件目录 |
| 每次运行前清掉超过 20 个的历史目录 | 防止长跑把磁盘占满 |

### 3.2 端口

| 用途 | 端口段 |
|---|---|
| 开发时手动起的宿主 | 7900 起（默认） |
| 验收脚本起的宿主 | 从 7980 起，每个脚本一个 |
| 界面 | 8010 起 |

分开的理由：开发时手动起的实例与自动化测试同时跑，共用 7900 会互相抢端口，失败信息会指向错误的原因。

脚本通过 `--port` 指定起始端口；若仍被占用，宿主按 `04/06` §2.2 顺延，脚本从 `registry.json` 读实际端口。

### 3.3 六个测试插件

全部放在 `tests/fixtures/`，只用于测试，不打包。

| 插件 | 轨道 | 用途 | 关键行为 |
|---|---|---|---|
| `demo-a` | 进程内 | 最小正常插件 | 注册 `demo-a.ping`，返回 `pong`；有一个可选参数控制返回值 |
| `demo-fail` | 进程内 | 激活失败 | activate 返回错误码，可配置为注册阶段失败或激活阶段失败 |
| `demo-slow` | 进程内 | 超时与窗口 | 处理函数按参数睡指定毫秒；activate 睡 2 秒用于造重载窗口 |
| `demo-crash` | 进程内 | 崩溃注入 | 处理函数解引用空指针；也可配置为写越界 |
| `demo-sidecar-cpp` | 侧车 | C++ 侧车 | 注册一个方法、订阅一个主题，支持优雅停用 |
| `demo-sidecar-py` | 侧车 | Python 侧车 | 同上，用于验证协议与语言无关 |

六个插件的共同要求：都能通过清单参数开关关键行为（失败方式、睡眠时长），避免为每个场景再编一个插件。

### 3.4 用例的写法

一个验收用例的结构固定四段：

```
1. 准备：起宿主、装哪些插件、等什么状态
2. 动作：发命令或调方法
3. 断言：返回码、状态、文件系统、日志、事件
4. 清理：关宿主、删数据根（可选保留）
```

第 2 段只允许一个动作。一个用例做两件事，失败时分不清是哪件坏了。

## 5. 性能基准

### 5.1 环境要求

不写清测量环境，跑出来的数字没有意义。

| 项 | 要求 |
|---|---|
| 构建 | Release（关闭 ASan 与 UBSan） |
| CPU | 4 核桌面机器，记录型号到结果里 |
| 存储 | 本地 SSD |
| 并发 | 单线程测量，其他程序不占用 CPU |
| 被测处理函数 | 空实现，只返回 0 |
| 电源 | 笔记本插电，关闭省电模式 |

最后一条容易忽略：省电模式会降频，P95 能差一倍。

### 5.2 测量方法

统一四步，所有基准一样：

1. **预热** 1000 次，丢弃结果（让缓存、分支预测、动态链接进入稳定状态）。
2. **采样** 10 万次（延迟类）或 20 次取中位数（装载类），记录每次耗时。
3. **统计** P50、P95、P99。
4. **重复** 5 轮，取 5 轮 P95 的中位数作为最终值。

第 4 步的作用：单轮结果受系统抖动影响大，5 轮取中位数能筛掉偶发尖峰。

### 5.3 八个基准

| 基准 | 对应需求 | 上限 | 采样 |
|---|---|---|---|
| `l1_bench_call` | 089 | P95 ≤ 1 微秒，P99 ≤ 3 微秒 | 10 万次 |
| `l1_bench_event` | 090 | 广播到 10 个订阅者 P95 ≤ 10 微秒 | 10 万次 |
| `l1_bench_load` | 091 | 单插件装载 ≤ 50 毫秒 | 20 次取中位数 |
| `l1_bench_snapshot` | 04/01 §4.5 | 500 条路由下复制 ≤ 1 毫秒（本文定的内部上限） | 1 万次 |
| `l3_bench_graph` | 092 | 50 插件 100 边全量重算 ≤ 1 毫秒 | 1 万次 |
| `l4_bench_cmd` | 096 | install / uninstall / reload 端到端 ≤ 500 毫秒 | 20 次取中位数 |
| `l6_bench_sidecar` | 093 | 控制面一次往返 P95 ≤ 100 微秒 | 10 万次 |
| `l6_resource` 的启动段 | 094、095 | 冷启动到端口可连 ≤ 300 毫秒；到 20 插件全激活 ≤ 1500 毫秒 | 20 次取中位数 |

`l1_bench_snapshot` 是本文补的：`04/01` §4.5 说「若超过 1 毫秒则改持久化数据结构」，但没有对应的基准，等于没有判据。

### 5.4 判定与波动

| 情形 | 判定 |
|---|---|
| 最终值 ≤ 上限 | 通过 |
| 最终值在上限的 1.0 到 1.1 倍之间 | 警告，记入结果，不判失败 |
| 超过上限 1.1 倍 | 失败 |
| 同一台机器两次运行差异超过 20% | 视为测量不可靠，重跑并检查环境 |

留 10% 的容差是因为进程调度与缓存状态无法完全消除。容差记在结果里，不静默忽略——连续几次都在容差内，说明该调整上限或改实现。

### 5.5 结果记录

每次跑基准，把结果写成一行追加到 `run/<preset>/bench-history.csv`：

```
2026-11-02T14:31:07, l1_bench_call, p50=0.42us, p95=0.71us, p99=1.9us, cpu=i5-12400, build=release
```

保留历史的作用：性能退化往往是渐进的，单次结果看不出来，连续十几行能看出趋势。

## 6. 故障注入

十五个场景，全部自动化。注入手段只有三类：改夹具插件的配置、杀进程、改文件系统状态。

| # | 场景 | 怎么造 | 期望 |
|---|---|---|---|
| F1 | 插件激活失败 | `demo-fail` 清单参数 `fail_at = "activate"` | 状态 `Failed`，广播事件，宿主继续服务其他插件 |
| F2 | 插件注册失败 | 同插件 `fail_at = "register"` | 已注册的部分按账本回滚 |
| F3 | 进程内崩溃（Windows） | `demo-crash` 调 `crash` 方法 | 捕获、标记故障、拒绝后续调用、写转储 |
| F4 | 进程内崩溃（Linux） | 同上 | 宿主退出，退出码非 0，有崩溃日志 |
| F5 | 侧车强杀 | `kill -9 <pid>` | `crashed` 事件，2 秒内重启 |
| F6 | 侧车不响应 | 夹具侧车参数 `ignore_deactivate = true` | 5 秒后 shutdown，再 5 秒强杀 |
| F7 | 撤销失败 | 夹具注册一个返回错误的撤销函数 | `E_UNDO_FAILED` 记日志，其余条目继续撤 |
| F8 | 账本满 | 循环注册到 10000 条后再注一次 | `E_LEDGER_FULL`，表未变 |
| F9 | 磁盘满 | 数据根挂到 4 MB 的 tmpfs | `E_IO`，宿主不崩，已有数据不受损 |
| F10 | 权限被改宽 | `chmod 0777 <数据根>/logs` | `doctor` 报告一条，不自动修 |
| F11 | zip 带 `..` | 构造含 `../../evil.txt` 的 zip | 拒装，目标位置外无文件 |
| F12 | 符号链接 | 把 `plugins/<编号>/<编号>.so` 换成链接 | 拒装 |
| F13 | 依赖成环 | 两个夹具互相 require | `E_DEPENDENCY_CYCLE`，回滚，无残件 |
| F14 | 重载新版失败 | 用 `fail_at = "activate"` 的新版本 reload | 回滚旧版，`E_RELOAD_FAILED` |
| F15 | 口令错三次 | 连发三个错 token | 前两次 `E_AUTH`，第三次断开并延迟 1 秒 |

F3 与 F4 是同一场景的两种平台结果，不算重复：一个是「捕获后继续」，一个是「退出」，两个都要验。

F9 依赖 tmpfs，只在 Linux 上跑；Windows 上跳过并在结果里标 `skipped`。

## 7. 安全相关检查

`06` 的十二条威胁里，能被自动化的有九条，其余三条只能手工。

| 威胁 | 自动化 | 用例 |

## 9. 什么算通过

### 9.1 三层判定

| 层 | 通过条件 |
|---|---|
| 单条用例 | 断言全部成立；无超时；清理阶段无报错 |
| 一个脚本 | 该脚本内全部用例通过；无 `skipped`（平台不适用的除外，须在结果里标出） |
| 一个切片 | 本片相关脚本全绿 + 全量回归全绿 + 性能基准不超上限 + 手工清单通过 |

### 9.2 手工清单

只保留三类，共八项：

| # | 检查 | 为什么手工 |
|---|---|---|
| M1 | 界面能打开、五个页签可切换 | 视觉与交互，无法断言 |
| M2 | 界面里完成装、卸、启、停各一次 | 端到端人机路径 |
| M3 | 界面崩溃后 2 秒内恢复，页面刷新可用 | 要观察时间与观感 |
| M4 | Android 真机上装一个插件并调用 | 无自动化环境 |
| M5 | `doctor` 四段输出可读 | 「可读」无法断言 |
| M6 | 崩溃转储能被调试器打开并解析出符号 | 需要人工看栈 |
| M7 | 打包产物在干净机器上能启动 | 环境隔离成本高 |
| M8 | 24 小时长稳（TC-D06） | 代价过高，只在发布前做 |

M8 不通过时不是「功能有 bug」，而是「资源管理有问题」，排查方向完全不同。

### 9.3 不通过的处置

| 情形 | 处置 |
|---|---|
| 用例失败，代码有 bug | 修代码，不改用例 |
| 用例失败，代码符合设计而设计有问题 | 改设计与文档，再改用例 |
| 用例失败，判据本身有误 | 改判据，必须在提交信息里说明为什么 |
| 性能超标但在容差内 | 记入结果，连续两次超标则排查 |
| 平台不适用的用例 | 标 `skipped` 并写明原因，不允许静默跳过 |

第二行与第三行的区别要守住：**不许为了通过而放宽判据**。判据是需求的一部分（`01` 的验收标准），改判据等于改需求，要走改需求的流程。

## 10. 不测什么

| 不测 | 理由 |
|---|---|
| 恶意插件（提权、逃逸、偷数据） | 不在威胁模型内（`06` §1.3） |
| 同用户恶意进程 | 应用层无法区分，只验日志留痕 |
| 物理接触攻击 | 超出软件范围 |
| 极端并发（几百条连接） | 单用户，32 条连接已覆盖（TC-D03） |
| 界面视觉细节（颜色、间距） | 无法断言，且改动频繁 |
| 第三方库自身的正确性 | Catch2、toml++、nlohmann/json 由上游保证 |
| 长时间高频调用的内存碎片 | 无收益：单用户场景下重启即可 |

最后一条要说明：不做「连续调用一亿次看内存是否碎片化」这类测试，因为没有对应的使用场景，测出来也无法判断好坏。
