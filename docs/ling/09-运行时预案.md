# ling 09 运行时预案

> 状态：已定稿 | 最后更新：2026-10-29
> 依据：`docs/ling/03-架构设计.md` §10.2；`docs/ling/07-测试与验收.md` §6；`docs/ling/08-部署与发布.md` §4.4

本文回答「已经出问题了怎么办」。

`03` 的风险登记册做的是设计时分析：什么会出错、设计上怎么预防。本文做的是运行时处置：真的出错了，宿主自动做什么、人要做什么、证据留在哪。

两者不重复：`03` 回答「为什么这样设计」，本文回答「现在怎么办」。

| 关闭 | 关闭卡住、撤销失败、强杀的代价 |
| 边界 | 哪些动作绝不允许自动做 |

### 1.2 不覆盖什么

| 内容 | 去哪 |

### 1.3 一个前提

**所有处置都在「单机、单用户、有人看着」的前提下设计。**

没有告警通道（不发邮件、不推手机），也没有远程运维入口。所以「自动恢复」的目标不是「无人值守地自愈」，而是**把问题控制在不扩大、且留下完整证据让人下次打开时能看懂**。

这条前提决定了一个关键取舍：宁可停下来等人，也不要带着疑似损坏的状态继续跑。

## 2. 处置原则

### 2.1 四条原则

| # | 原则 | 含义 | 反面做法 |
|---|---|---|---|
| 1 | 先保数据，再保可用 | 数据丢了无法恢复，可用性丢了重启就有 | 为了「不中断」而继续写入可疑状态 |
| 2 | 自动只做不破坏的动作 | 记录、隔离、拒绝、退到备用通道可以做；删文件、改配置、降版本不能做 | 自动「清理」损坏的文件 |
| 3 | 失败必须留证 | 日志、转储、当时的表状态，三样至少留两样 | 只打一行「出错了」 |
| 4 | 不确定就停 | 原因不明时停在可诊断的状态 | 猜一个原因然后继续 |

第 2 条是本文最重要的约束。它的直接后果是：**所有破坏性恢复都要人来做**，包括删数据、清空配置、降级版本、强杀进程。

### 2.2 三级影响

| 级别 | 含义 | 典型 | 谁受影响 |
|---|---|---|---|
| L1 | 单个插件不可用 | 插件崩溃被标 `Failed`、激活失败、账本满 | 该插件的功能 |
| L2 | 宿主某项功能不可用 | 界面打不开、日志写不进、`core-log` 被卸 | 依赖该功能的操作 |
| L3 | 宿主不可用 | 起不来、进程退出、关闭卡死 | 全部 |

分级的用处是决定「要不要立刻处理」：L1 可以放着，L3 必须马上动手。

### 2.3 谁能做破坏性操作

| 操作 | 自动 | 需要人确认 |
|---|---|---|
| 标记插件 `Failed`、拒绝后续调用 | 可以 | —— |
| 结束侧车进程 | 可以（超时后） | —— |
| 把损坏的配置**重命名**（不删） | 可以 | —— |
| 删除数据 | **不允许** | 必须 |
| 清空或重置配置 | **不允许** | 必须 |
| 降级到旧版本 | **不允许** | 必须 |
| 强杀宿主进程 | **不允许** | 必须 |

「重命名可以、删除不行」这条区分很实际：重命名保留了现场，删除就没了。损坏的配置被重命名成 `settings.json.corrupt-20261029T0122`，用户事后还能从里面捞出有效字段。

## 3. 启动阶段

启动阶段的故障有一个共同点：**宿主还没起来，没人能通过命令行求助**。所以所有错误必须打在 `stderr`，且信息要能直接指向动作。

### 3.1 数据根不可写

**判据**：创建目录或写第一个文件时失败，`errno` 为以下之一。

| `errno` | 含义 | 提示的动作 |
|---|---|---|
| `EACCES` | 权限不足 | 检查目录属主与权限位 |
| `EROFS` | 只读文件系统 | 换一个可写位置，或改 `--data-dir` |
| `ENOSPC` | 磁盘满 | 清理磁盘，见 §4.7 |
| `ENOTDIR` | 路径中间有一段是文件 | 检查路径拼写 |

**自动**：退出，退出码非 0，`stderr` 打印「路径 + errno 名称 + 建议动作」三行。

**人工**：按提示修。修完重跑，不需要清任何东西。

**留证**：`stderr` 是唯一证据——此时日志文件还写不进去。所以这四行必须写全。

### 3.2 端口全占

**判据**：7900 至 7999 全部 `bind` 失败。

**自动**：退出，退出码 3，`stderr` 列出「试过的端口段 + 每个端口的失败原因摘要」。

**人工**：两种选择——关掉占用进程（`netstat -ano | findstr :79` 或 `ss -ltnp`），或用 `--port` 换一个段。

**留证**：无日志。这类失败通常在几毫秒内发生，写日志反而慢。

### 3.3 配置损坏或版本过高

`settings.json` 有两种坏的：

| 情形 | 判据 | 自动 | 人工 |
|---|---|---|---|
| 解析失败 | JSON 语法错，或根不是对象 | 重命名为 `settings.json.corrupt-<时间戳>`，用空配置继续启动，记 error | 从备份恢复，或从 `.corrupt` 文件里手工捞字段 |
| `schema_version` 高于当前 | 字段值大于宿主支持值 | **拒绝启动**，退出码非 0，`stderr` 提示「配置来自更新的版本」 | 用新版启动，或恢复旧备份 |

第二种拒绝启动是刻意的（`08` §5.2）。旧版本读到新格式时容易把不认识的字段丢掉，写回就把配置降级了。让它起不来，比让它悄悄改坏配置好。

**留证**：第一种情况，`.corrupt` 文件本身就是证据；第二种情况，什么都不改，原样保留。

### 3.4 `registry.json` 损坏

**判据**：解析失败，或字段类型不对（例如 `port` 是字符串）。

**自动**：按默认值重建（端口 7900、空名单），记 warn。**不重命名、不备份**——它只存端口与两个名单，丢了可以重建。

**人工**：一般不需要。若名单（禁用、能力撤销）丢了，`doctor` 会报告，从 `logs/` 里能查到原来的值。

`registry.json` 与 `settings.json` 处理方式不同的理由：前者是可再生数据，后者含用户配置。

### 3.5 内置插件装不上

**判据**：首次启动时从程序目录复制五个内置插件，某一个失败。

**自动**：记 warn（含哪个插件、失败原因），继续装其余四个，宿主照常启动。

**人工**：`ling install <程序目录>/core-xxx.dll` 手动装一次。若反复失败，看 `logs --kernel` 里的 warn。

**留证**：内核日志的 warn 行。

不因一个内置插件失败就拒绝启动：`core-log` 装不上不影响宿主运行，硬要退出反而让用户连命令行都用不了。

### 3.6 启动卡住

**判据**：进程在但不在监听端口，超过 30 秒。

| 常见原因 | 怎么判断 |
|---|---|
| 扫描插件目录时遇到巨大的目录 | `logs --kernel` 里最后一条是「扫描 plugins」 |
| 某个插件 activate 死循环 | 日志停在某个插件的激活步骤 |
| 侧车启动等待超时（10 秒）× 多个侧车 | 日志里有多次「等待侧车连接」 |

**自动**：不做任何事。没有看门狗进程（`02` §5.5 的结论：非 Windows 崩溃靠外部守护，而启动卡住不是崩溃）。

**人工**：先看内核日志的最后几条，判断卡在哪一步；再决定是强杀重启还是等。

**留证**：内核日志会被持续写入（异步队列仍在工作），所以卡住时日志是最有用的证据。

## 4. 运行阶段

### 4.1 进程内插件崩溃：Windows

**判据**：向量化异常处理器捕获到访问违例、除零、非法指令。

**自动**（四步，顺序固定）：

1. 把当前线程的调用栈地址写入内核日志（只写地址，不解析符号）。
2. 调 `MiniDumpWriteDump` 生成 `.dmp` 到 `<数据根>/logs/`。
3. 把该插件标为 `Failed`，拒绝后续对它的调用（返回 `E_PLUGIN_MISSING`）。
4. 按账本撤销它登记过的效应，广播 `kernel.plugin.state`，`state = crashed`。

**人工**：先看 `doctor` 是否报告该插件，再用 `cdb -z <dmp>` 解析栈。修好插件后 `ling install` 或 `reload`。

**留证**：`.dmp` + 内核日志的崩溃行（含插件名、`generation`）。

**不做**：不自动重启该插件。崩溃的插件重装还是同一份代码，反复崩溃只会刷日志。重启由人决定。

### 4.2 进程内插件崩溃：Linux 与 Android

**判据**：宿主进程退出，退出码由信号决定（通常是 `SIGSEGV` 对应 139）。

**自动**：没有自动动作——进程已经没了。

**人工**：

| 步 | 动作 |
|---|---|
| 1 | 看宿主是被什么信号终止的（`dmesg` 或 core dump） |
| 2 | 用外部守护拉起（systemd、计划任务），见 `03` §5.4 |
| 3 | 反复崩溃时，把该插件改走侧车轨道 |
| 4 | 若要 `core dump`，开启 `ulimit -c unlimited` 并确认 `core_pattern` 指向可写位置 |

**留证**：崩溃前内核日志已经刷盘（`04/01` §9 的崩溃场景要求先刷盘），所以日志里能看到崩溃前最后几步。

**这条缺口是已知的**（`02` §5.5）：Linux 与 Android 上进程内插件崩溃不可捕获，宿主会一起退出。预案不是「修好它」，而是「让它退出得有痕迹、且能自动拉起来」。

### 4.3 侧车反复重启

**判据**：同一侧车连续异常退出 3 次（`04/02` §8.5）。

**自动**：第 3 次失败后转 `Failed`，停止重试，广播事件，记 error。

**人工**：看侧车的 `stderr`（宿主会把侧车的输出重定向到 `logs/<插件名>-sidecar.log`）。常见原因三类：缺依赖、端点连不上、首帧握手 token 不符。

**留证**：侧车自己的日志 + 内核日志里三次退出的退出码。

**为什么是 3 次**：1 次不够判断（启动竞态会误判），5 次太多（一个启动就崩的插件会刷 5 条日志）。3 次是折中，且这个值写在清单约束里，可改。

### 4.4 侧车不响应

**判据**：发 `deactivate` 后 5 秒内没收到 `deactivated`。

**自动**：发 `shutdown`，再等 5 秒；仍未退出则结束进程，记 warn（含插件名与两个 5 秒都超时的事实）。

**人工**：查侧车是否死锁（常见于处理函数里等一把永远拿不到的锁）。

**留证**：内核日志的两条超时记录，加上侧车最后一帧的内容。

### 4.5 调用超时堆积

**判据**：同一插件在 5 分钟内出现 10 次以上 `E_TIMEOUT`。

**自动**：在内核日志记一条 aggregated warn（含插件名、次数、最长耗时）。**不停用该插件。**

**人工**：用 `--log-level debug` 看调用摘要是哪一类耗时；判断是插件慢还是数据量大。

**为什么不停用**：超时常来自「这次数据特别大」这类正常波动，自动停用会把「偶尔慢」变成「功能消失」，比不管更糟。停用由人决定（`ling disable`）。

这条与侧车「连续 3 次崩溃就停止重试」不同：崩溃是确定性的错误，超时不是。

### 4.6 账本满

**判据**：某插件当前激活代已登记 10000 条效应，再来一次登记。

**自动**：返回 `E_LEDGER_FULL`，**本次修改不生效**（`04/03` §3.4 的容量检查在改表之前），记 error。

**人工**：说明插件在激活期泄漏效应——反复注册同一方法却没注销，或者在一个循环里注册。修插件，不是调上限。

**留证**：内核日志的 error 行，含插件名与当时的 `count`。

### 4.7 磁盘满

**判据**：写文件返回 `ENOSPC`。

**自动**（按顺序）：

1. 日志改为只写 `stderr`（不再尝试写文件），记一条 error（写 `stderr`）。
2. 拒绝新的装载请求，返回 `E_IO`。
3. 已有插件的调用**照常**，不因磁盘满而停止。

**人工**：按这个顺序清——先删旧 `.dmp`（最大）、再删旧日志、最后删旧私有副本。

**留证**：`stderr` 里的那条 error。

第 3 条要说明：磁盘满时最不该做的是「全部停下」。此时用户正需要命令行来清理，把宿主停掉等于把工具也关了。

### 4.8 日志写不进去

**判据**：日志文件的 `open` 或 `write` 失败（权限、句柄失效、目录被删）。

**自动**：退化到只写 `stderr`，在 `stderr` 打一行「日志文件不可写，已退回 stderr」。宿主继续运行。

**人工**：修权限或重建 `logs/` 目录。修好后**不需要重启**：下一次写入时会重试打开文件。

**留证**：`stderr`。

这条是「日志失败不该让业务失败」的直接应用（`04/07` §7.3 同一条原则）。

### 4.9 界面不可用

**判据**：`core-ui` 处于 `Failed`，或端口连不上。

**自动**：按 `restart = "on-crash"` 在 2 秒内重启一次；连续 3 次失败转 `Failed`。

**人工**：

| 情形 | 动作 |
|---|---|
| 只是界面打不开 | `ling plugins` 看 core-ui 状态；命令行完全可用，不必急 |
| 反复崩溃 | 看 `logs/core-ui-sidecar.log`，多半是端口被占或前端资源缺失 |
| 干脆不用界面 | `ling uninstall core-ui`，命令行不受影响 |

**留证**：内核日志的崩溃事件 + 侧车日志。

**不要做的事**：不要因为界面坏了就回退整个版本（`08` §6.3 同一条）。

## 5. 数据与配置

### 5.1 判定数据损坏的四种迹象

| 迹象 | 怎么看到 | 说明 |
|---|---|---|
| 配置解析失败 | 启动时 `settings.json` 报错 | 已自动重命名，见 §3.3 |
| `doctor` 报告未撤销条目 | 定期跑 `doctor` | 说明某次停用没撤干净 |
| 插件报「读不出自己的数据」 | 插件日志 | 插件的 `data/` 被外部改过或写坏 |
| 账本序号不连续 | `doctor` 或插件自查 | 说明有写入被跳过，通常由崩溃导致 |

前三条是宿主能看见的，第四条只能靠插件自己检查。

### 5.2 恢复顺序

固定三步，不要跳：

```
1. 停宿主（ling shutdown）。停不下就强杀，但先记下当前状态
2. 备份整个数据根（复制一份，别在原地改）
3. 按 doctor 的报告逐项处理：
     配置问题   → 从 .bak 或 .corrupt 里恢复
     未撤销条目 → 记下来，重装该插件让它重新登记
     插件数据   → 删掉该插件的 data/（代价：数据丢失），让插件重建
```

第 2 步的备份不是形式：没有备份就动手，一旦改错就没有回退点。

### 5.3 什么情况必须停手

| 情形 | 为什么停 |
|---|---|
| 数据被写坏，但不知道是谁写坏的 | 继续写入会覆盖证据，也会扩大损坏范围 |
| 崩溃发生在写数据的过程中 | 文件处于半写状态，继续读会读到部分数据 |
| 同一个故障连续出现三次以上 | 说明前面的处理没找到根因，再试也是同样结果 |
| `doctor` 报出的问题互相矛盾 | 说明有更深层的问题（例如内存被写坏），此时任何修复都不可信 |

停手之后做什么：备份数据根、收集日志与转储、把现象记入 `docs/log/`，然后从「最小可复现」开始查。

## 6. 关闭阶段

### 6.1 关闭卡住

**判据**：`ling shutdown` 发出后 10 秒内进程未退出。

**自动**：命令行打印「未在 10 秒内退出，检查日志」，返回退出码 4。**不自动强杀。**

**人工**：看内核日志卡在哪一步（`04/01` §2.3 的七步关闭顺序），判断是「某个插件撤销慢」还是「线程池不退出」，再决定强杀。

**为什么不强杀**：强杀会让数据处于半写状态。宁可多等一会儿，或者由人明确决定强杀。

### 6.2 撤销失败

**判据**：某条撤销返回非 0。

**自动**：记 `E_UNDO_FAILED`（含 `seq` 与 `desc`），继续执行其余条目，最后返回 `E_UNINSTALL_INCOMPLETE`，状态仍改 `Deactivated`。

**人工**：`doctor` 会列出未撤销条目；`ling install` 重装该插件能让它重新登记干净，或手工清理残留（例如路由表里删不掉的方法会在下次重载时被覆盖）。

**留证**：内核日志 + `doctor` 报告。

状态仍然改的原因（`04/03` §8.4）：留在 `Deactivating` 会一直占着依赖图的位置，下游永远无法激活。带着一条未撤干净的方法继续，比卡住整个系统好。

### 6.3 强杀的代价

强杀（`kill -9`、任务管理器结束进程）会跳过关闭流程，代价：

| 代价 | 后果 | 能不能补救 |
|---|---|---|
| 账本没撤销完 | 插件效应残留在表里（下次启动表从空开始，实际影响小） | 能，重启即清 |
| 日志队列里的内容丢失 | 最后几百毫秒的日志没了 | 不能 |
| `settings.json` 有半写风险 | 下次启动解析失败，按 §3.3 处理 | 能，有 `.corrupt` 备份 |
| `registry.json` 有半写风险 | 下次启动按默认重建 | 能 |

四类里最值得担心的是第三类，而它已经有兜底（原子替换 + 损坏时重命名）。所以强杀的实际代价可控——但**能不用就不用**，因为它会让「这次故障的证据」丢掉。

## 7. 处置表

一页看完，出问题时先在这张表里找现象。

| 现象 | 级别 | 自动做了什么 | 人该做什么 | 证据在哪 |
|---|---|---|---|---|
| 启动报「数据根不可写」 | L3 | 退出，打印路径与 errno | 修权限或换目录 | `stderr` |
| 启动报「端口全占」 | L3 | 退出，列出试过的端口 | 关占用进程或 `--port` | `stderr` |
| 启动报「配置来自更新的版本」 | L3 | 拒绝启动，不动文件 | 用新版启动或恢复旧备份 | `stderr` |
| 配置损坏但能起 | L2 | 重命名 `.corrupt`，空配置启动 | 从备份恢复 | `.corrupt` 文件 |
| 启动卡住不动 | L3 | 无 | 看内核日志最后几条 | 内核日志 |
| 插件崩溃（Windows） | L1 | 转储、标 `Failed`、撤效应 | 解析转储，修插件 | `.dmp` + 日志 |
| 插件崩溃（Linux） | L3 | 无（进程已死） | 外部守护拉起，查 core dump | `dmesg` + 日志 |
| 侧车反复重启 | L1 | 3 次后停止重试 | 看侧车日志 | `logs/<插件名>-sidecar.log` |
| 侧车不响应停用 | L1 | 5 秒 + 5 秒后强杀 | 查死锁 | 日志两条超时 |
| 调用频繁超时 | L1 | 只记 warn，不停用 | debug 级别看摘要 | 内核日志 |
| 账本满 | L1 | 拒绝新效应 | 修插件的效应泄漏 | 日志 error |
| 磁盘满 | L2 | 日志退 stderr，拒装载，调用照常 | 按序清转储、日志、副本 | `stderr` |
| 日志写不进 | L2 | 退 stderr，继续运行 | 修权限，不用重启 | `stderr` |
| 界面打不开 | L2 | 2 秒内重启一次 | 命令行可用，不必急 | 侧车日志 |
| 关闭卡住 | L3 | 命令行等 10 秒后报错 | 看日志判断，再决定强杀 | 内核日志 |
| 撤销失败 | L1 | 继续撤其余，报不完整 | `doctor` 看清单 | 日志 + `doctor` |

## 8. 不该做的事

六条，都是「看起来能救急，实际会让情况更糟」：

| 不该做 | 为什么 | 该做什么 |
|---|---|---|
| 自动清空损坏的配置 | 用户配置丢了不可恢复 | 重命名保留现场 |
| 自动停用超时的插件 | 偶发慢会变成功能消失 | 记 warn，等人决定 |
| 自动降级版本 | 数据格式已被新版写过 | 人判断后手动回退（`08` §6） |
| 自动修权限 | 正在运行的程序会写不进去 | `doctor` 报告，人来改 |
| 磁盘满时停掉全部功能 | 用户正需要用命令行清理 | 只拒装载，调用照常 |
| 故障原因不明时继续跑 | 会覆盖证据、扩大损坏 | 停手，备份，再查 |

第三条要展开：降级看似安全（「回到上一个能跑的版本」），但如果新版本已经写过数据，旧版本会读到它不认识的格式。所以必须先看 `settings.json` 的 `schema_version`，再决定能不能降。

## 9. 与 03 八条风险的对应

`03` §10.2 的八条风险，真出问题时对应的处置：

| 03 的风险 | 本文处置 |
|---|---|
| 1 动态库映射泄漏 | §4.5 不适用。用 `doctor` 看内存，达 30 MB 提示重启（`01` 101） |
| 2 进程内插件崩溃不可恢复 | §4.1（Windows）、§4.2（Linux 与 Android） |
| 3 快照替换频率过高 | 不单独处置：注册集中在激活期，出问题时表现为内存短暂上升 |
| 4 侧车与控制面协议分裂 | 不适用（开发期问题） |
| 5 插件绕过上下文 | §5.1 的「未撤销条目」迹象 |
| 6 撤销函数写错 | §6.2 |
| 7 内核升级导致插件不兼容 | 不在本文：装载时就被拒，见 `04/02` §3.4 第 5 步 |
| 8 界面崩溃后无法自恢复 | §4.9 |

第 1、3、4、7 条没有对应的运行时处置，原因是它们要么表现为别的问题，要么在更早的环节就被拦住。这张表的作用是让「风险登记册」与「运行时预案」对得上，不留空白。

## 10. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | 超时堆积的阈值（5 分钟 10 次）没有依据 | 保留，实测后调。关键是不自动停用这条不变 | §4.5 |
| 2 | 是否需要给宿主加一个看门狗进程 | 不加。非 Windows 的崩溃靠系统级守护（systemd），自己再做一个等于两套机制 | §3.6 |
| 3 | 磁盘满时是否该自动删旧日志 | 不该。删日志等于毁掉证据，而且用户正靠它找问题 | §4.7 |
| 4 | 侧车日志与内核日志的时间戳是否要严格同源 | 要。两边都用同一个时钟源与格式，否则对不上时序 | §4.3 |
