# core-log 00 总览与边界

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/builtin-plugins/00-总览与边界.md`（待编写）

本文回答：这个插件是干什么的、不干什么、和内核日志怎么分、没装它的时候会怎样。

---

## 1. 一句话

**把插件写出来的日志收拢到一个地方，按插件名和日期存成文件，并且能查。**

## 2. 它解决什么问题

插件要记日志，但插件不该自己管日志文件：每个插件各写各的路径、各定各的格式，出问题时要翻五个目录、认五种时间格式。`core-log` 把这些统一成一处：所有插件日志都落在 `<数据根>/logs/` 下，行的样子和内核日志一模一样。

## 3. 它不做什么

| 不做 | 谁做 | 理由 |
|---|---|---|
| 写内核自己的日志 | 内核（`main/src/log.cpp`） | 内核日志必须先于所有插件可用，不能依赖插件 |
| 解析日志内容 | 调用方 | 插件日志的格式由插件决定，`core-log` 只负责存和取 |
| 日志轮转与清理 | 暂无 | MVP 阶段先不删任何日志；风险见 `02-设计与接口.md` 第 6 节 |
| 实时推送 | 暂无 | 查询是拉取式。要做实时，用事件广播，不走这里 |
| 采集别的插件的 `data/` 文件 | 插件自己 | `data/` 是插件私有区，不是日志通道 |

**「不解析」这条要强调**：`core-log` 收到什么字符串就存什么字符串，它不知道 `message` 里写了什么，也不做级别过滤之外的任何处理。日志的语义属于写日志的那个插件。

## 4. 与内核日志的关系

两者行格式相同，但各写各的文件、各有各的开关：

| | 内核日志 | `core-log` |
|---|---|---|
| 谁写 | 内核 | 其他插件（经方法调用） |
| 落盘位置 | `<数据根>/logs/kernel-日期.log` | `<数据根>/logs/<插件名>-日期.log` |
| 能不能卸掉 | 不能，是内核的一部分 | 能，卸掉后宿主照常启动 |
| 谁来看 | `ling logs`（不带插件名） | `ling logs <插件名>` |
| 格式 | `<时间> [级别] <模块> <正文>` | `<时间> [级别] <正文>` |

格式一致是刻意的：同一套脚本能解析两边的文件，排障时不用换工具。

## 5. 没装它的时候

`core-log` 是可卸载的内置插件。卸掉之后：

| 场景 | 行为 |
|---|---|
| 插件调 `core-log.write` | 返回 `E_PLUGIN_MISSING`，调用失败 |
| `ling logs <插件名>` | 内核先找不到 `core-log`，退回读该插件 `data/` 下的 `.log` 文件；没有就报「还没有写过日志」 |
| 内核日志 | 不受影响，照常写 |
| 宿主启动 | 不受影响 |

退化路径由内核实现，不由 `core-log` 实现——一个已经卸载的插件没法自己处理「我不在」这种情况。

## 6. 谁在用

- **插件**：在激活时注册方法之后，按需调 `core-log.write`。示例见 `plugins/demo-caller/main.cpp`。
- **命令行**：`ling logs <插件名>` 经 `kernel.logs` 转给它。
- **以后**：`core-ui` 的日志面板会调 `core-log.query`。
