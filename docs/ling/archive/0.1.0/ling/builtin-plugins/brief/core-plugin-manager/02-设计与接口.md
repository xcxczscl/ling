# core-plugin-manager 02 设计与接口

> 状态：已定稿 | 最后更新：2026-10-31
> 详细版：`docs/ling/builtin-plugins/core-plugin-manager/02-设计与接口.md`

## 1. 五个方法

### 1.1 `core-plugin-manager.orphans`

扫 `plugins/` 下「有 `data/`、没有 `plugin.toml`」的目录，返回各自字节数与合计。递归累加，无权限的条目跳过并计数。

### 1.2 `core-plugin-manager.sizes`

列每个已安装插件的目录占用（含 `data/`）。与 `orphans` 的分工：这里列还装着的，那里列只剩数据的。

### 1.3 `core-plugin-manager.tree`

给插件名，返回它依赖谁、谁依赖它（传递闭包）、缺哪些。数据来自内核装载表，不自己扫清单——清单改过而没重载时，自扫会与内核不一致。

### 1.4 `core-plugin-manager.preview`

给操作与插件名，复用调和的计算阶段算出计划，渲染成两张名单后丢掉计划，不改状态。

### 1.5 `core-plugin-manager.apply`

按拓扑序执行（停用先停下游），中途失败停在失败处并报告，**不回滚已执行的部分**：回滚会把一个失败变成一串失败。

## 2. 判定规则

### 2.1 孤儿的判定

有 `plugin.toml` 算已安装；没有但有 `data/` 算孤儿；空目录也算。与 `04/02` §2.1 的「已安装」判定同源。

### 2.2 目录大小的算法

递归累加普通文件大小，无权限的跳过并在返回里带 `skipped` 计数，数字对不上时能看出原因。

### 2.3 拓扑序

停用按依赖深度从深到浅，启用反过来。成环时排序失败，返回 `E_DEPENDENCY_CYCLE` 并带回环路，不猜顺序。

## 3. 失败处理

参数缺或插件不存在报错误码；目录不可读算成功并计 `skipped`；成环报 `E_DEPENDENCY_CYCLE`。**批量执行整体算成功**，某步失败放在 `failed` 字段里——部分成功是常态，用错误码表达会让调用方以为什么都没做。

## 4. 与内核的分工

装卸启停、依赖图、调和都归内核；本插件只把结果整理成人能看的形状。写操作要等 M3 放开「插件可调内核写方法」，原因是现在插件调用没有身份区分，一个业务插件能卸掉另一个。

## 5. 代码位置与实现状态

`main/builtin-plugins/core-plugin-manager/`，只依赖标准库。`orphans` 与 `sizes` 已实现，`tree`、`preview`、`apply` 要到 M3 才实现。
