# core-job 01 需求与用例

> 状态：已定稿 | 最后更新：2026-10-31
> 详细版：`docs/ling/builtin-plugins/core-job/01-需求与用例.md`

## 1. 需求从哪来

挂在 `078`（无特权）、`081`（可卸载）、`017`（调用超时 30 秒）、`031`（登记任务是一次配置写入）之下。

## 2. 场景

### 2.1 登记一个每天凌晨三点跑的任务

登记后立即可查；进账本；定义落在 `settings.json` 的 `core-job.<名字>` 键下，可导出、可还原。

### 2.2 到点了触发

调一次目标方法，参数为空；失败只记 warn，不影响下一次；超时与普通调用一致。

### 2.3 到点时宿主没在运行

默认不补跑；声明 `catch_up = true` 时启动后补跑一次，只补最近一次。

### 2.4 上一次还没跑完，下一次又到点

跳过本次并记 warn，**不排队**——排队会在慢任务上累积成雪崩。

### 2.5 目标插件在触发时没激活

跳过、记 warn、不重试。让插件可用是调和的事。

### 2.6 取消一个任务

列表与配置里都没了；这次删除进账本，卸载调用方时按旧值还原。

### 2.7 时间表达式写错了

拒绝登记，说明哪一段不合法以及合法范围。

## 3. 用例与验收标准

`CJ-01` 至 `CJ-12`：登记、重名、非法 cron、取消、到点触发、目标未激活、上次未结束、停机错过、补跑、执行超时、卸装往返、卸载调用方。`CJ-05` 至 `CJ-10` 依赖内核 tick 广播。

## 3.1 命令行入口

`ling job list` / `add` / `remove` 是建任务与查任务的主要入口。`add` 先调 `core-job.validate` 校验时间表，再调 `core-job.schedule` 落盘——插件失败只带回整数错误码，校验单独走一个返回正文的方法，填错时才能看到「哪一段超范围」。

## 4. 本期明确不做的

秒级定时、任务依赖、执行历史、手动立即执行、时区处理。
