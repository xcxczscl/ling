# core-job 00 总览与边界

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/04-详细设计/07-内置插件.md`

本文回答：这个插件干什么、时间表达式是什么样、为什么它不起自己的线程。

---

## 1. 一句话

**按时间表自动去调别的插件的方法：到点了就调一次，没到就等着。**

## 2. 它解决什么问题

有些事要按时间做：每天凌晨整理一次目录、每小时拉一次数据。让每个业务插件自己起线程做定时，问题一样：

| 各做各的 | 后果 |
|---|---|
| 每个插件一套定时逻辑 | 同一个项目里五种写法，时间表达式格式都不统一 |
| 各自起线程 | 十个插件十个线程，出问题时不知道是谁在跑 |
| 任务定义散在各自 `data/` 里 | 卸载就丢，也没法导出备份 |

`core-job` 把这些收成一处：任务定义存在配置里（走 `core-settings`，可导出、可还原），触发由一处统一调度。

## 3. 它不做什么

| 不做 | 谁做 | 理由 |
|---|---|---|
| 秒级与亚秒级定时 | 不做 | 五段 cron 最短间隔是一分钟。需要更密的，用事件或前台循环，不走定时任务 |
| 保证「一次不漏」 | 不做 | 宿主没运行的那段时间不会补跑，除非任务声明 `catch_up` |
| 让目标插件变得可用 | 内核调和（M3） | 目标未激活时跳过并记 warn，不去触发装载 |
| 排队执行 | 不做 | 上一次没跑完时本次跳过，不排队。排队会在慢任务上累积成雪崩 |
| 执行结果汇总 | 不做 | 被调方法的返回值不存，要看结果让目标插件自己记日志 |

## 4. 为什么不起自己的线程

直觉做法是插件起一个定时线程，到点直接调 `call`。本项目不这么做，原因在架构上：

宿主是**单线程内核**（`docs/ling/03-架构设计.md` §5）：路由表、订阅表这些结构由内核线程写，读路径假设没有别人同时改。插件线程去调 `call`，就是在内核写表的同时读表——数据竞争，出错时的现象是随机的崩溃或错误的处理函数被调到，极难复现。

所以 `core-job` 采用另一种方式：**内核在主循环里定期回调它**，它在回调里检查有没有到点的任务并当场执行。全部发生在内核线程上，不存在并发。

代价是精度受主循环节拍限制（200 毫秒）。对分钟级的 cron 来说，这个误差可以忽略。

这需要内核提供「定期回调」这一条约定，属于要新增的机制，写在 `02-设计与接口.md` §4。

## 5. 没装它的时候

| 场景 | 行为 |
|---|---|
| 已登记的任务 | 定义还在配置里（键 `core-job.*`），但没人触发 |
| 重装回来 | 任务照旧生效，因为定义在配置里，不在插件的 `data/` 里 |
| 宿主启动 | 不受影响 |

这条是「任务定义存配置」的直接好处：插件卸了再装，任务不会丢。

## 6. 谁在用

- **使用者**：经 `core-ui` 的任务页增删任务；命令行暂不提供（`04/06` §4.1 的子命令表里没有任务相关命令）。
- **其他插件**：可以调 `core-job.schedule` 给自己登记任务。
