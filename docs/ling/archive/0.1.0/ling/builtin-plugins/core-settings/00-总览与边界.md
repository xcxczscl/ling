# core-settings 00 总览与边界

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/04-详细设计/07-内置插件.md`

本文回答：这个插件是干什么的、不干什么、配置和插件私有数据怎么分。

---

## 1. 一句话

**给所有插件存配置的公共仓库：写进去的每个值都记着是谁写的、什么时候写的，卸载那个插件时能原样退回去。**

## 2. 它解决什么问题

插件需要记住一些设置，比如「上次打开的目录」「扫描时跳过哪些文件」。三种存法各有毛病：

| 存法 | 毛病 |
|---|---|
| 插件自己写 `data/` 下的文件 | 卸载时没人知道要还原什么；用户想备份设置得翻每个插件的目录 |
| 每个插件自己写一份 JSON 到数据根 | 路径冲突、格式不统一、谁都能改别人的 |
| 塞进环境变量或命令行参数 | 改一次要重启，且没法在界面里编辑 |

`core-settings` 把这件事收成一处：统一的文件、统一的键空间、统一的读写方法，并且**每一次写入都进内核账本**，插件卸载时自动回到写入前的值。

## 3. 它不做什么

| 不做 | 谁做 | 理由 |
|---|---|---|
| 编辑配置的界面 | `core-ui` | 界面是展示层，存储不该关心怎么展示 |
| 配置升级迁移 | `docs/ling/08-部署与发布.md` 的迁移流程 | 迁移要知道新旧两版的字段含义，存储层不知道 |
| 解析配置值的内容 | 写配置的那个插件 | 值是不透明字节串，`core-settings` 只负责存取 |
| 加密 | 暂无 | 单机个人工具，配置明文可读反而方便排查。真正敏感的东西（口令）不该进配置 |
| 管插件的私有数据 | 插件自己写 `data/` | 见下一节的分界 |

## 4. 配置与私有数据的分界

这是使用者最容易混的一处，写清楚：

| | 走 `core-settings` | 写 `data/` |
|---|---|---|
| 谁看得见 | 其他插件按前缀能读、能列 | 只有自己 |
| 卸载时 | 进账本，自动还原到写入前 | 默认保留，加 `--purge` 才删 |
| 能不能导出 | 能，`core-settings.export` | 不能，除非插件自己实现 |
| 适合放什么 | 用户改过的设置、跨插件可见的少量状态 | 索引、缓存、游标、日志、大文件 |

判据一句话：**要还原、要导出、要给别人看的，走配置；只属于自己的中间状态，写 `data/`。**

## 5. 没装它的时候

`core-settings` 可卸载。卸掉之后：

| 场景 | 行为 |
|---|---|
| 插件调 `Context::write_config` | 返回 `E_PLUGIN_MISSING`，写入失败 |
| 插件调 `core-settings.get` | 方法不存在，`E_METHOD_MISSING` |
| 已写过的配置 | 文件还在 `<数据根>/settings.json` 里，只是没人读 |
| 已登记但未撤销的配置效应 | 撤销时 `core-settings` 不在，记 `E_UNDO_FAILED`（`docs/ling/04-详细设计/03-上下文与效应账本.md` §6.2） |
| 宿主启动 | 不受影响 |

重装回来之后，之前的配置还在，插件读得到。

## 6. 谁在用

- **所有插件**：经 `Context::write_config` 写，经 `core-settings.get` 读。
- **内核**：转账本条目时调 `core-settings.write`，撤销时写回旧值。
- **`core-job`**：任务定义存在配置里（键 `core-job.<任务名>`），所以任务可导出、可还原。
- **`core-ui`**：配置页读 `export`、写 `write`。
