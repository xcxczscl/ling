## 2. 输入与输出

### 2.1 依赖声明

`[requires] plugins = ["core-ui@1", "resources-manager@1.2"]`。

`capabilities` 与 `requires.plugins` 分开处理：前者由门禁判定，不满足则装载失败；后者进依赖图，不满足只是待激活，安装本身成功。

### 2.2 图的节点与边

节点是已安装插件，边从需求方指向被需求方。首版 `capabilities` 不进图——能力是宿主固有属性，不是某插件提供的。

### 2.3 输出

计划含 `plan_id` 与有序步骤列表，每步是 `index`、`action`（activate / deactivate / unload）、`plugin_id`、`result`。

没有步骤的计划合法：三态判定全为「不动」时计划为空，不广播任何 `plan.step`。

---

## 3. 版本约束匹配

### 3.1 四种写法

| 写法 | 判定 |
|---|---|
| 无版本 | 任意版本成立 |
| `@1` | 主版本等于 1 |
| `@1.2` | 前两段等于 1、2 |
| `@1.2.3` | 三段全等 |

### 3.2 判定算法

约束按点切段，逐段与目标版本同段比较，全部相同才成立。

一句话：**逐段相等，不是「大于等于」**。`@1` 的意思是「主版本是 1」，不是「至少 1」。

### 3.3 边界

约束超过三段、目标版本段越界都属清单非法，`E_MANIFEST_INVALID`。前导零不改变数值，`@01` 等价 `@1`。

## 4. 依赖图

### 4.1 结构

两张邻接表：正查（需求方 → 被需求方）用于激活顺序，反查（被需求方 → 需求方）用于停用下游。

### 4.2 构建步骤

每次从零重建：取所有已安装插件 → 遍历 `requires.plugins` → 目标不存在记「未满足」，版本不符记「版本不符」，否则加边 → 返回图与未满足清单。

不改增量：几十个插件的全量重算在 1 毫秒内，增量维护要处理多处边失效，容易出错。

### 4.3 环检测

Kahn 算法：反复取出入度为 0 的节点，取不完即有环。失败返回 `E_DEPENDENCY_CYCLE`，`detail` 给完整环路。

环检测在计划计算之前，因为拓扑排序本身要求无环。

### 4.4 重算成本

50 节点 100 边时全量构建、环检测、拓扑排序都是 O(V+E)，实际百微秒量级，`LING-REQ-092` 的 1 毫秒上限有三倍余量。

## 5. 计划计算

### 5.1 三态判定

| 当前状态 | 需求满足 | 判定 |
|---|---|---|
| 未激活 | 是 | 激活 |
| 已激活 | 否 | 停用 |
| 其他 | —— | 不动 |

「需求满足」= 已安装 + 版本对 + 目标本身可用（没停用、没启动失败），且不可用沿依赖往下传。停用 `demo-a` 会让依赖链上的 `demo-b`、`demo-c` 一起停；被停用的那个不记「缺依赖」，只在依赖者的原因里写「依赖 demo-a 现在用不了」。

「不动」不产生任何 `plan.step` 与状态事件，否则每轮调和都在刷事件，事件就成了噪音。

### 5.2 拓扑排序

激活按拓扑序（被依赖者先），停用按反向拓扑序（依赖者先）。同一张图排一次，取正序与逆序即可，不用跑两遍。

### 5.3 计划的步骤顺序

先执行全部停用（反向拓扑序），再执行全部激活（拓扑序）。同一插件升级前后既停又起时，先起后停会出现新旧版本并存的窗口。

### 5.4 计算失败即整体回滚

成环、清单非法、能力未知、内部错误任一发生：本次变化整体不生效，状态回到变化前；安装带来的工件被移除；返回首个错误码。

「整体回滚」是**一步都不做**，不是做到一半再撤——计划在执行前算好，算不出来就不走。

---

## 6. 计划执行

### 6.1 步骤与事件

每步执行完广播 `kernel.plan.step`，字段以 `01` 为准：`plan_id`、`step`、`step_total`、`action`、`plugin`、`ok`、`error`。

`step` 连续递增，跳过与失败也算一步，不断号。

### 6.2 取消与回滚

取消请求到达时，等当前步结束再停，不打断。停止后已执行步骤按账本倒序回滚，计划标 `cancelled`，广播一条 `action = cancel`、`error = E_CANCELLED` 的步骤。

不打断的理由：做到一半被打断会留下账本登记了一半的中间状态。

### 6.3 幂等

对已激活的插件再激活、对已停用的再停用，直接跳过：不新建账本段、不广播事件。同一插件在计划里出现两次的情况在计算阶段就去重，不会进入执行。

## 7. 触发与去抖

### 7.1 七个触发点

`install`、`uninstall`、`enable`、`disable`、`reload`、清单变化、宿主启动。七处都提交同一个 `Reconcile` 请求，走同一队列，无例外通道。

### 7.2 200 毫秒合并

收到请求不立即执行，标记 pending 并记时间戳；已有 pending 则只更新时间戳；内核线程检查「距最后一次变化已过 200 毫秒」才执行。

三个细节：窗口从最后一次变化算；启动的全量调和不等窗口；命令行的 `install` 阻塞到该轮调和结束再返回，否则用户以为装完了去调用，会收到 `E_PLUGIN_MISSING`。

### 7.3 合并的边界

200 毫秒内同时有 install 与 uninstall：合并成一次，计划里两者都体现。合并期间收到取消：取消的是尚未开始的执行，不影响窗口计时。合并期间进程退出：不执行，记一条 warn。

---

## 8. 启动时的全量调和

启动流程：装载表从空开始、账本重建 → 扫描全部插件建图 → 三态判定出计划 → 执行并逐条广播。

失败（成环、清单非法）时退出码非 0，`stderr` 写明失败插件与原因。

**部分插件因缺依赖进入待激活不是失败**：那是正常状态，依赖装上会自动激活。

---

## 8.1 实现状态

版本约束、依赖图、环检测、拓扑序、三态计划已实现（`main/src/depgraph.cpp`，纯函数），调和执行在 `Kernel::reconcile()`，触发点是安装、卸载、启动装载完。`kernel.plan.step` 事件、`reload`/`restart`、预览 `kernel.plan`、200 毫秒合并、改清单后自动重算都已实现。仍未做的是把计划做成可取消的独立对象。

实测：只装 `demo-b`（依赖 `demo-a@1`）显示已停用并说明缺什么；装 `demo-a` 后自动激活；卸掉 `demo-a` 后自动停用；装回来再自动启用，全程不重启。

依赖停用会连带停用：不可用（停用、启动失败）沿依赖往下传，`disable demo-a` 之后 `demo-b` 停用并写明「依赖 demo-a 现在用不了」，`enable demo-a` 后自动恢复。
