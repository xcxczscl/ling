# ling 10 路线图与里程碑

> 状态：初定 | 最后更新：2026-10-29
> 依据：`docs/ling/05-构造与开发指南.md` §5；`docs/ling/08-部署与发布.md` §2、§3；`docs/common/02-版本号与兼容约定.md` §2

本文回答「分几段走、每段结束时能演示什么、什么情况下不许进下一段」。

不回答「第一段要做到什么程度算够」——那是 `docs/ling/11-MVP 范围.md` 的事。两份文档的分工在 §1.1 写清。

路线图不排日历。个人项目按完成度推进，不按周次推进；定死日期只会让「到点了先跳过验证」变成常态。

## 1. 目的与范围

### 1.1 与 05、11 的分工

| 文档 | 回答什么 | 粒度 |
|---|---|---|
| `docs/ling/05-构造与开发指南.md` §5 | 代码按什么顺序写，每片的产物与验证方式 | 七个切片，S0 至 S6 |
| 本文 | 这些切片合成几个阶段，每阶段结束能对外演示什么，通过什么判定才进下一段 | 七个里程碑，M0 至 M6 |
| `docs/ling/11-MVP 范围.md` | 最早那个可用的东西包含哪些需求、明确不含哪些 | 一份需求子集 |

切片与里程碑不是一一对应：M3 含两个切片（S3、S4），因为它们共同构成「插件能改」这件事；M6 不含新切片，只做打包与三端验证。

### 1.2 不做什么

- 不排时间。没有「第几周完成什么」。
- 不排人力。一个人，没有并行。
- 不承诺里程碑之间等距。M1 与 M5 的工作量差几倍，写「每段两周」是假的。

## 2. 里程碑总览

### 2.1 里程碑表

| 编号 | 名称 | 含切片 | 结束时能演示什么 | 版本号 |
|---|---|---|---|---|
| M0 | 设计定稿 | 无 | `docs/` 下二十一份设计文档（`common` 三份、`ling` 十八份，不含 `log/` 与 `archive/`）全部为已定稿，互相引用无冲突 | `0.0.1-b1` |
| M1 | 最小闭环 | S0、S1 | 装两个插件（一个当调用方），`plugins` 列出都是 activated，调用方拿到回应 | `0.0.2-b1` |
| M2 | 可装可卸 | S2 | 卸载后路由表清空、账本倒序撤销、`data/` 保留 | `0.0.3-b1` |
| M3 | 能改能换 | S3、S4 | 先装依赖方再装被依赖方，前者自动激活；改插件不重启宿主 | `0.0.4-b1` |
| M4 | 双轨 | S5 | 一个 C++ 侧车与一个 Python 侧车同时在跑；强杀后 2 秒内重启 | `0.0.5-b1` |
| M5 | 可用 | S6 | 浏览器打开界面，在里面完成装卸启停；`doctor` 能查出成环 | `0.0.6-b1` |
| M6 | 可发布 | 无新切片 | 三端各出一个包，在一台干净机器上装完能用 | `0.1.0-b1` |

`0.1.0-b1` 之后的构建只加 `bN`；项目宣告完成时去掉 `-bN`，成为 `0.1.0`。递增规则见 `docs/common/02-版本号与兼容约定.md` §2。

### 2.2 为什么这样切

三个判据，按优先级：

**① 每段都能演示。** 不能演示的里程碑无法判定是否完成，只能靠「感觉差不多了」。M1 之所以这么早，就是为了让「装插件、调方法」这条链在第一段就打通，后面所有工作都在这条链上加东西。

**② 每段结束时代码是可运行的完整程序。** 不是「编译通过但跑不起来」。M2 结束时宿主能装卸，M3 结束时能改插件，都不需要「等下一段补上才能跑」。

**③ 风险早暴露。** 三条会让项目停摆的风险分别落在 M1（C++ 与 ABI 边界）、M4（侧车协议与 Python 打包）、M6（Android 的进程与权限）。不把它们堆到最后。

### 2.3 与需求的关系

里程碑不按需求编号切，因为需求是横向的（装载、路由、门禁各占一组），而里程碑是纵向的（每段都涉及好几组的一小部分）。

每一段实际覆盖了哪些需求条目，在 `docs/ling/11-MVP 范围.md` 里有 MVP 那张表；M2 之后各段的需求覆盖不单独列表，判定方式是「该段涉及的 `04` 条目全部实现」（`docs/ling/05-构造与开发指南.md` §5.2 第 4 条）。

## 3. 各里程碑的定义

### 3.1 M0 设计定稿

**内容**：`00` 至 `12` 全部写完，逐份自审，再做一次全量交叉核对。

**通过条件**：

1. 二十一份文档的详细版与简版标题逐条对应。
2. 需求编号 001 至 127 无缺号、无重号，每条都有验收标准与平台标记。
3. 错误码只出现 `docs/ling/04-详细设计/02-插件装载与接口.md` §5.2 表内的取值，没有表外码。
4. 跨文档的同一事实只有一个取值：管理端口、性能上限、数据根名称、字段名、错误码语义。
5. 用户逐份过目，无异议。

第 4 条是最容易出问题的一条。写 `04` 的过程中已经撞到三次（`plan.step` 字段两套、管理端口两个值、子命令表漏两项），都是静默错误——不影响阅读，只影响实现。

**这个里程碑为什么单列**：它是唯一一个「不写代码也算进度」的阶段。跳过它直接写代码，等于把设计缺陷留到实现时才发现，那时改一处要动代码、测试、文档三处。

### 3.2 M1 最小闭环

**含切片**：S0（骨架能编能跑）、S1（装载、注册、调用）。

**结束时能做的事**：

```
ling install <plugins>/demo-a
ling plugins            # 看到 demo-a 状态为 activated
l2_call                 # 集成测试：调用方插件调 demo-a.ping，收到 pong
```

命令行**没有** `call` 子命令：管理端口只接受 `kernel.*` 开头的方法（`docs/ling/04-详细设计/06-管理端口与命令行.md` §3.3），业务方法只能由插件调用。所以「调通一次」由集成测试验证，不由命令行验证。

**这一段真正验证的三件事**：

| 验证什么 | 为什么必须在这段验证 |
|---|---|
| 三平台能编出可运行的二进制 | 构建配置错了越晚发现越贵 |
| 动态库能装进进程并导出唯一入口 | `ling_plugin_entry` 这套设计是否成立，只有真跑起来才知道 |
| 编译器与运行时的 ABI 约束站得住 | 混用 `/MD` 与 `/MT` 这类错误只在运行期暴露，且现象是崩溃而非报错 |

第三件事是 `docs/ling/02-技术选型.md` §5.4 列的硬约束。M1 里要专门造一次「故意混用配置」的失败案例，确认它真的会崩——不验证的话，这条约束只是文档上的字。

**通过条件**：三平台构建通过；上述三条命令在一台干净机器上跑通；故意写一个未使用变量能让构建失败（质量门生效）。

### 3.3 M2 可装可卸

**含切片**：S2（上下文与账本）。

**结束时能做的事**：装 `demo-a`（注册方法、订阅主题、开一个文件句柄），卸载，确认路由表与订阅表清空、账本按倒序撤销、`data/` 保留而安装文件消失。

**这一段验证的是「可逆」**。整个项目最难做对的一件事就是撤销：注册了方法要注销、订阅了事件要退订、开了文件要关、写了配置要还原。少一条就是残留，残留累积到几十次装卸之后表现为「路由表里有不存在的方法」。

**通过条件**：`l2_uninstall` 脚本通过；卸载后目录只剩 `data/`；卸载后调该插件的方法返回 `E_PLUGIN_MISSING` 而不是崩溃。

### 3.4 M3 能改能换

**含切片**：S3（依赖与调和）、S4（热更新）。

**结束时能做的事**：先装依赖方、再装被依赖方，前者自动从 `Pending` 转 `Activated`；替换插件文件后 `ling reload`，宿主不重启，调用进到新版本。

两个切片合一段，因为它们共同回答「插件能改」：依赖决定「能不能起」，热更新决定「起了之后能不能换」。

**这一段的风险最高，原因是它涉及并发**：调和发生在内核线程，调用发生在任意线程，热更新要保证旧版本的回调不会进到新版本的表里。`04/01` §5.3 的 `generation` 校验就是为这件事设计的，M3 必须专门验证它——造一个「旧回调在新版本装载后才返回」的场景，确认结果被丢弃。

**通过条件**：成环被拒且不留残件；100 次连续重载后内存增长不超过 `LING-REQ-101` 的 50 MB；新版 `activate` 故意失败时回滚到旧版且旧版仍可用。

### 3.5 M4 双轨

**含切片**：S5（侧车）。

**结束时能做的事**：一个 C++ 侧车与一个 Python 侧车同时在线；强杀 C++ 侧车，宿主不受影响，2 秒内出现新的 `activated`。

**这一段验证「隔离」**。前面所有里程碑里，插件崩溃都会带走宿主；M4 之后有一条轨道能真正隔离。这也是 `core-ui` 选侧车的原因（`docs/ling/03-架构设计.md` A-8）。

**这一段的外部依赖最重**：Python 运行时怎么随程序分发、Android 上怎么处理。`docs/ling/02-技术选型.md` §4.5.3 已定「随程序分发」，但真正打包时会碰到动态库依赖、`.pth` 路径、`sys.path` 之类的问题，这一段专门留时间处理。

**通过条件**：强杀侧车后宿主调用其他插件成功率 100%；重启计数与 `on-crash` 策略生效；Python 侧车在 Windows 与 Linux 上都能起。

### 3.6 M5 可用

**含切片**：S6（内置插件与界面）。

**结束时能做的事**：浏览器打开 `127.0.0.1:8010`，在界面里装插件、看状态、启停；`ling doctor` 能查出成环与残留。

**这一段是「自己开始用」的起点**。之前的里程碑都靠命令行验证，从这一段起可以用界面完成日常操作，也才开始积累真实使用中的问题。

**通过条件**：五个内置插件全部预装且可卸载；卸掉 `core-ui` 与 `core-log` 后宿主仍能启动（`LING-REQ-081`）；界面侧车崩溃后宿主不受影响并在 2 秒内重启（`LING-REQ-116`）。

### 3.7 M6 可发布

**不含新切片**，只做三件事：打包、干净机器验证、Android 验证。

**结束时能做的事**：把包拷到一台没装过开发工具的机器上，解压、运行、装一个插件、调通。

这一段的重点不是「能不能打出来」，是「换一台机器还能不能用」。开发机上总有额外的东西：某个运行库、某个环境变量、某个已装的 Python。`docs/ling/08-部署与发布.md` §9 的发布前十项检查就是为这件事列的。

**通过条件**：三端各出一个包；Windows 与 Linux 在干净机器上装完可用；Android 能启动宿主、能在浏览器打开界面、能装一个纯 C++ 插件；发布检查十项全过。

Android 只要求「能装一个纯 C++ 插件」：`08` §2.3 已定 Android 版不含 Python 侧车，这条限制写进发布说明。

## 4. 版本号与里程碑的对应

| 时点 | 版本号 | 动作 |
|---|---|---|
| 设计基线建立 | `0.0.1-b1` | 无代码，此号仅作设计快照标记 |
| 每个里程碑完成 | 次版本 +1，`bN` 归 1 | 打标签，标签名与版本号相同 |
| 里程碑内的每次构建 | 只加 `bN` | 修 bug、补测试、重打包都加 |
| 里程碑内加功能 | 次版本 +1 | 例如 M3 期间加了 `doctor` 子命令 |
| M6 完成 | `0.1.0-b1` | 首要版本进 1 |
| 项目宣告完成 | `0.1.0` | 去掉 `-bN` |

三条与版本相关的约束：

- **标签只打在通过判定的提交上。** 不通过的里程碑不打标签，避免「这个版本是半成品」这种状态存在。
- **`bN` 是构建序号，不是测试轮次。** 定义见 `docs/common/02-版本号与兼容约定.md` §2。
- **不兼容改动一律进大版本。** 清单必填字段、协议帧格式、`api` 主版本的语义，改任何一项都是大版本，且在 `0.x` 阶段也要走大版本。

## 5. 判定与退回

### 5.1 通过判定的四条

一个里程碑算完成，四条同时成立（与 `docs/ling/05-构造与开发指南.md` §5.2 一致，粒度上移到里程碑）：

1. 该段的演示脚本跑通，结果记进 `docs/log/` 的对应条目。
2. 该段涉及的 `01` 需求，验收标准全部可判真。
3. 该段的测试用例全绿，性能基准在容差内（`docs/ling/07-测试与验收.md` §5.4）。
4. `precommit.sh` 五项全过。

### 5.2 不通过怎么办

**不进入下一段，也不把问题记成待办。** 三种处理：

| 情形 | 处理 |
|---|---|
| 实现有 bug | 修到通过。里程碑之间的门槛不因「快完成了」而放宽 |
| 设计有问题 | 回去改 `04` 或更上游，记 `docs/log/`，再继续。不允许「代码这样更顺手」 |
| 需求本身有问题 | 改 `01`，同步改受影响的 `04`、`07`。需求不是不可动的，但改要留痕 |

第三种情形最容易拖，因为改需求要连带改三处。但把它记成待办的结果是需求永远不改，代码永远和文档不一致。

### 5.3 已完成的段可以拆掉重做吗

可以，但只在一种情况下：**该段的核心判断被证伪**。例如 M4 发现 Python 侧车在 Android 上根本起不来，那 M4 的「随程序分发」这个判断错了，回到 `02` 改，再重做 M4。

不因为「写得不好看」重做。重构属于段内的事，不属于回退。

## 6. 关键路径与风险

### 6.1 关键路径

M1 是唯一的关键路径起点：它不通过，后面全部无法开始。M3 与 M4 之间没有强依赖，可以先做任一个；但 M5 依赖 M4（界面是侧车）。

| 里程碑 | 前置 | 阻塞范围 |
|---|---|---|
| M1 | M0 | 全部 |
| M2 | M1 | M3、M4 |
| M3 | M2 | M6 |
| M4 | M2 | M5 |
| M5 | M4 | 无（M6 不依赖界面） |
| M6 | M3、M4 | 无 |

M6 排在最后但**不依赖 M5**：一个没有界面的三端包也算可发布。这是有意的——界面是最容易拖的一项，不该成为「能不能发布」的前提。

### 6.2 外部风险

| 风险 | 落在哪一段 | 影响 | 缓解 |
|---|---|---|---|
| C++ 与 ABI 边界写不出来 | M1 | 项目停摆 | `02` §5.2 把接口收缩到单个导出函数；S0 阶段先跑通三平台构建 |
| 快照复制超过 1 毫秒 | M1 之后 | 调用延迟达不到 `LING-REQ-089` | `l1_bench_snapshot` 早测；超标改持久化数据结构 |
| 动态库卸载泄漏累积 | M3 | 内存超 `LING-REQ-101` | 已放宽到 50 MB 并在 30 MB 提示重启；极端情况改用侧车 |
| Python 打包在 Android 上做不出来 | M4 | Android 版功能降级 | 已定 Android 不含 Python 侧车，只影响「能不能跑 Python 插件」 |
| Android 前台服务被系统杀掉 | M6 | 宿主无法常驻 | 通知栏常驻 + 用户手动加白名单，写进发布说明 |
| 设计文档某处根本实现不了 | 任意段 | 该段返工 | 每段第 4 条出口条件要求「实现与文档一致，不一致就改文档」 |

第三条要补一句：`02` §3.4 已说明「进程内插件不卸载，热更新复制到新文件名再加载」，代价是每次重载留一个映射。这不是缺陷，是选定的权衡；风险只在于重载次数极多时累积。

### 6.3 已知的「不会解决」

下列问题在路线图里不安排任何里程碑，因为它们的解法超出本项目的范围或收益：

| 问题 | 为什么不排 |
|---|---|
| 同账户下的恶意程序能完全控制宿主 | 应用层无法解决，见 `docs/ling/06-安全设计.md` §2.1 |
| Linux 与 Android 上进程内插件崩溃带走宿主 | 平台限制，见 `docs/ling/02-技术选型.md` §5.5 |
| 重载泄漏的映射无法回收 | `dlclose` 的限制，重启即清 |
| 界面在 Android 上没有原生实现 | 要维护两套界面，收益不足，见 `docs/ling/08-部署与发布.md` §2.3 |

## 7. 明确不排进路线图的事

以下功能不在 `0.1.0` 之前的任何里程碑里。列出来是为了避免「顺便做了」：

| 不做 | 理由 |
|---|---|
| 插件市场与在线分发 | `00` §2.3 的非目标；插件是自己写的 |
| 多用户与权限分级 | 单机单用户 |
| 自动更新宿主 | 手动替换二进制即可，自动更新要处理签名、回滚、断点，收益不足 |
| 跨设备同步 | 与「插件宿主」定位无关 |
| 插件沙箱 | `06` §4 已定不做；进程内插件与宿主同权限 |
| 配置界面的可视化编辑 | `core-ui` 只做状态查看与装卸启停，配置由插件自己管 |
| 性能专项 | 只在基准超标时做，不设单独的提速阶段 |

最后一条要说清：不设提速阶段不等于不管性能。`07` 的八个基准每段都跑，超标就处理；但没有「先做出来再统一提速」这个阶段。

## 8. 未决问题

| # | 问题 | 建议 | 影响 |
|---|---|---|---|
| 1 | M0 的「用户逐份过目」要做到什么程度 | 每份看简版加变更记录，有异议提，无异议算过 | §3.1 |
| 2 | M6 的 Android 验证要不要真机 | 要。模拟器掩盖权限与前台服务问题 | §3.7 |
| 3 | 里程碑之间要不要留「缓冲段」 | 不留。缓冲会变成默认延期 | §5.1 |

第 3 条的理由值得写下来：一旦允许「这一段没完全过也先进下一段，回头补」，补的动作永远不会发生。个人项目没有外部压力，唯一的约束就是这个门槛本身。
