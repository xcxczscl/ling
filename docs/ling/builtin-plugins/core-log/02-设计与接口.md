# core-log 02 设计与接口

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/builtin-plugins/core-log/00-总览与边界.md`

本文回答：它对外提供哪些方法、数据存在哪、出错了怎么办、代码怎么写。

---

## 1. 三个方法

全部进程内轨道，经 `Context::call` 或管理端口调用；参数与返回都是 JSON 文本。

### 1.1 `core-log.write`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `plugin` | 字符串 | 是 | 写日志的插件名 |
| `level` | 字符串 | 否 | `error` / `warn` / `info` / `debug`，默认 `info` |
| `message` | 字符串 | 是 | 正文，不做任何解析 |

返回 `{"written": true}`。

### 1.2 `core-log.tail`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `plugin` | 字符串 | 是 | 取哪个插件的日志 |
| `n` | 整数 | 否 | 取最后几行，默认 40 |

返回：

```json
{"plugin": "demo-caller", "path": "<数据根>/logs/demo-caller-2026-10-31.log", "lines": ["...", "..."]}
```

`path` 是这次实际读的文件。同一个插件跨天会有多个文件，取文件名最大的那个（日期可字典序比较）。

### 1.3 `core-log.query`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `plugin` | 字符串 | 是 | 取哪个插件的日志 |
| `date` | 字符串 | 否 | `YYYY-MM-DD`，默认今天 |
| `level` | 字符串 | 否 | 给了就只返回该级别的行 |

返回 `{"plugin": ..., "date": ..., "lines": [...]}`。

## 2. 文件布局与行格式

```
<数据根>/logs/
  kernel-2026-10-31.log          内核自己写，不归本插件管
  demo-caller-2026-10-31.log     本插件写
  core-settings-2026-10-31.log
```

行格式与内核日志一致：

```
2026-10-31T17:45:01 [info] event demo-a.pinged pong
2026-10-31T17:45:01 [error] 配置写入失败
```

`<ISO 时间> [级别] <正文>`，UTF-8，行尾 `\n`。一边写一边追加，不做缓冲。

**为什么文件名带日期**：按天切文件，查某一天的日志不需要先过滤整份大文件；文件名可字典序比较，取最新一份不需要遍历后解析内容。

## 3. 插件名必须校验

`plugin` 会直接拼进文件名，等于把调用方给的字符串拼进路径。不校验就是目录穿越漏洞（`plugin = "../../evil"`）。

规则：只允许字母、数字、连字符，长度 1 至 64。不符合返回错误码 `E_MANIFEST_INVALID` 那一类，不创建任何文件。

这条在 `01-需求与用例.md` 的 CL-03 有对应用例。

## 4. 失败处理

| 情形 | 返回 | 副作用 |
|---|---|---|
| 参数缺 `plugin` 或 `message` | 错误码 | 无 |
| `plugin` 不合法 | 错误码 | 无 |
| `logs/` 目录不存在 | 建目录再写 | 目录被创建 |
| 建目录或打开文件失败 | **成功** | 内核日志留一条 warn |
| 写入过程中磁盘满 | **成功** | 同上 |
| 查询的文件不存在 | 成功，`lines` 为空 | 无 |

前三行与后三行的区别是刻意的：**参数错误要报给调用方（它能改），环境错误不报（它改不了，报了只会让业务失败）**。日志写不进去是宿主环境的问题，不该由业务逻辑承担。

## 5. 并发

宿主是单线程内核（`docs/ling/03-架构设计.md` §5），方法调用串行进入，同一时刻只有一个 `core-log.write` 在写文件。所以：

- 不需要文件锁。
- 每次写都用追加模式打开、写完立即关闭，进程被强杀时最多丢最后一行，不会写坏前面的内容。

将来引入工作线程池之后要重新评估这一节。

## 6. 大文件

两个方法对文件的读法不同：

| 方法 | 读法 | 内存 |
|---|---|---|
| `tail` | 从文件末尾按 64 KB 块往前读，凑够 N 行就停 | 与 N 成正比，与文件大小无关 |
| `query` | 从头逐行读，匹配的才留下 | 与命中行数成正比 |

`query` 必须从头读，因为过滤条件可以命中任何一行；但它不把整个文件放进内存。

**不做轮转。** 现在的策略是「一直追加，不删除」。风险是长期运行且日志量大的插件把磁盘写满。轮转要定三件事——多大开始切、保留几份、切的时候要不要通知——在没有真实数据之前拍任何一个数都是猜。等有实际日志量再定，`01-需求与用例.md` 第 4 节记了这条。

## 7. 代码位置

| 项 | 位置 |
|---|---|
| 源码 | `main/builtin-plugins/core-log/main.cpp` |
| 清单 | `main/builtin-plugins/core-log/plugin.toml` |
| 产物 | `run/<preset>/plugins/core-log/`（与业务插件同路径，装载时不可区分） |
| 依赖 | 标准库 + `nlohmann/json`；不引第三方日志库 |

只用标准库的理由：日志是宿主最基础的能力之一，不该因为一个日志库的版本问题起不来。

## 8. 已知不足

| 不足 | 影响 | 打算 |
|---|---|---|
| 没有轮转 | 长期运行会把磁盘写满 | 有真实数据后再定阈值 |
| `query` 不支持跨天 | 查一周的日志要调七次 | `core-ui` 的日志面板会需要，届时再加 `from`/`to` |
| 单行长度没有上限 | 一个插件写一行 100 MB 会把查询拖慢 | 写入时截断到 8 KB，超出记一条「已截断」 |
| 时间取本地时区，不带时区偏移 | 跨时区看日志要自己换算 | 单机个人工具，先不加 |
