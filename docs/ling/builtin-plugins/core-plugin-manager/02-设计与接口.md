# core-plugin-manager 02 设计与接口

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/builtin-plugins/core-plugin-manager/00-总览与边界.md`

本文回答：五个方法怎么定义、孤儿怎么判、树与预演拿什么数据算。

---

## 1. 五个方法

### 1.1 `core-plugin-manager.orphans`

无参数。扫 `<数据根>/plugins/` 下每个子目录：**有 `data/`、没有 `plugin.toml`** 的就是孤儿。

返回：

```json
{
  "orphans": [
    {"id": "demo-a", "bytes": 1048576}
  ],
  "total_bytes": 1048576
}
```

`bytes` 是递归累加（含子目录），跳过无权限访问的文件而不是整个中止。

### 1.2 `core-plugin-manager.sizes`

无参数。列出每个已安装插件的目录占用（含 `data/`），返回 `{"plugins": [{"id": "...", "bytes": ...}]}`。

与 `orphans` 的区别：这里列的是还装着的插件，`orphans` 列的是只剩数据的。

### 1.3 `core-plugin-manager.tree`

| 参数 | 类型 | 必填 |
|---|---|---|
| `id` | 字符串 | 是 |

返回：

```json
{
  "id": "demo-a",
  "requires": [{"id": "demo-base", "satisfied": true}],
  "required_by": ["demo-b", "demo-c"],
  "missing": []
}
```

`requires` 是它依赖谁（直接），`required_by` 是谁依赖它（传递闭包），`missing` 是链条里缺的插件名。

数据来源是内核的装载表与依赖图，不由本插件自己扫清单文件。理由：清单被改过而没重新装载时，自己扫会得到与内核不一致的结论。

### 1.4 `core-plugin-manager.preview`

| 参数 | 类型 | 必填 |
|---|---|---|
| `action` | 字符串 | 是，`enable` 或 `disable` |
| `ids` | 字符串数组 | 是 |

返回 `{"activate": [...], "deactivate": [...]}`，**不改变任何状态**。

实现上复用内核调和的计算阶段（`docs/ling/04-详细设计/04-依赖解析与调和.md` §5）：算出计划、渲染成两张名单、丢掉计划。这要求计算与执行分离，04/04 已经这么分了。

### 1.5 `core-plugin-manager.apply`

| 参数 | 类型 | 必填 |
|---|---|---|
| `action` | 字符串 | 是 |
| `ids` | 字符串数组 | 是 |

按拓扑序执行（停用先停下游，启用先启上游），返回：

```json
{"done": ["demo-b", "demo-a"], "failed": {"id": "demo-a", "error": "E_..."}}
```

中途失败就停在失败处，`failed` 里给错误码，剩余的插件不动。**不回滚已执行的部分**：回滚会把「一个失败」变成「一串失败加一串回滚失败」，报告清楚更有用。

## 2. 判定规则

### 2.1 孤儿的判定

| 条件 | 判定 |
|---|---|
| 有 `plugin.toml` | 已安装，不是孤儿 |
| 无 `plugin.toml` 但有 `data/` | 孤儿 |
| 目录为空 | 也算孤儿，`bytes` 为 0 |

这条与 `docs/ling/04-详细设计/02-插件装载与接口.md` §2.1 的「已安装」判定同源：`plugin.toml` 在就是装着，不在就是没装。

### 2.2 目录大小的算法

递归遍历，累加普通文件的 `file_size`。遇到无权限的条目跳过并计数，最后在返回里带一个 `skipped` 字段说明跳了几个——数字对不上时能看出原因。

### 2.3 拓扑序

停用：先算「谁依赖它」，递归展开，按深度从深到浅执行。
启用：反过来，从浅到深。

成环时拓扑排序失败。此时不猜顺序，返回 `E_DEPENDENCY_CYCLE` 并把环路带回去——让使用者看到环，而不是看着一个卡住的命令。

## 3. 失败处理

| 情形 | 返回 | 副作用 |
|---|---|---|
| `id` 不存在 | `E_PLUGIN_MISSING` | 无 |
| `ids` 为空数组 | 成功，空结果 | 无 |
| 目录不可读 | 成功，`skipped` 计数 | 无 |
| 依赖图成环 | `E_DEPENDENCY_CYCLE` | 无 |
| 批量执行中某步失败 | 成功返回，`failed` 里带错误码 | 已执行的不回滚 |

最后一条要注意：批量操作整体算「执行完毕」，不因为某一步失败而返回错误码。调用方要看 `failed` 字段判断有没有问题。这样设计是因为「部分成功」是常态，用错误码表达会让调用方以为什么都没做。

## 4. 与内核的分工

| 事 | 谁做 |
|---|---|
| 装卸、启停的实际动作 | 内核 `kernel.*` |
| 依赖图的维护 | 内核（M3） |
| 调和的计算与执行 | 内核（M3） |
| 把上面的结果整理成人能看的形状 | 本插件 |

本插件调内核只读方法（`kernel.plugins`）拿数据；写操作要等 M3 放开「插件可调 `kernel.*` 写方法」这条限制。现在放开不了，是因为插件调用没有身份区分，一个业务插件能卸掉另一个业务插件，这超出了 MVP 的安全边界。
