# core-ui 00 总览与边界

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/04-详细设计/07-内置插件.md`

本文回答：这个插件是什么、两种形态差在哪、不做什么。

---

## 1. 一句话

**用鼠标就能把 ling 管起来：看装了哪些插件、装上新的、停掉不用的、翻日志、改配置。**

## 2. 它解决什么问题

命令行能做全部事情，但要记命令、记参数、记插件名。对「偶尔用一下」的场景，成本太高：

| 命令行 | 界面 |
|---|---|
| `ling install D:\plugins\my-plugin` | 点「安装」，选目录 |
| `ling plugins` 看英文状态 | 一屏卡片，颜色区分状态 |
| `ling logs demo-a` 看纯文本 | 可筛选、可搜索、可自动刷新 |
| 改配置要手编 `settings.json` | 表单，带类型校验 |

**命令行不删。** 界面是另一条入口，两者共用同一套 `kernel.*` 方法，不各写一套逻辑。

## 3. 两种形态

同一个插件，两种发布形态，二选一：

| | `webui` 版 | `desktop` 版 |
|---|---|---|
| 界面在哪 | 浏览器标签页 | 独立窗口 |
| 怎么打开 | 启动宿主后自动开默认浏览器 | 双击图标直接开窗口 |
| 技术 | 本地 HTTP 服务 + 浏览器 | 同一个 HTTP 服务 + WebView2 容器 |
| 平台 | 三平台 | 目前只有 Windows |
| 适合 | 已有浏览器习惯、想多开标签页对照 | 想要「像普通软件一样」的体验 |

两版**界面代码完全一样**，差别只在「谁来显示这个页面」：浏览器，或一个内嵌 WebView2 的窗口。这条决定让两种形态不必维护两套前端。

发布包决定装哪一版：便携版与安装包各出两种，共四个产物（`04-两种形态与启动.md` §5）。

## 4. 它不做什么

| 不做 | 理由 |
|---|---|
| 局域网或远程访问 | 只绑 `127.0.0.1`。一旦能远程访问，就要做账号、权限、加密，而这是单机个人工具 |
| 多用户 | 同上 |
| 业务功能 | 界面只调别的插件与内核方法，自己不实现任何业务逻辑 |
| 插件市场、在线安装 | 项目非目标，见 `docs/ling/00-总览与术语.md` |
| 移动端适配 | Android 版的界面形态另议，不在这一份里 |

## 5. 它在插件体系里的位置

`core-ui` 是一个**侧车插件**：独立进程，不是装进宿主的动态库。理由：

- 它要跑一个 HTTP 服务，宿主不需要这个能力。
- 界面进程崩了不该拖垮宿主（`LING-REQ-116`）。
- 将来换界面技术，只换这一个可执行文件。

它与宿主的关系只有一条：**以客户端身份连管理端口**（`127.0.0.1:7900`），用 `session.json` 里的口令认证，之后调 `kernel.*` 方法。

**它还能当启动器。** 用户双击图标时，界面进程先起来，探测宿主在不在跑；没跑就自己拉起 `ling serve` 子进程，等宿主就绪后再连上去。这样「双击一个图标就能用」，不需要先开命令行窗口。两种启动方式的判定与顺序见 `04-两种形态与启动.md` §4。

插件模式下它**不读** `session.json`，口令由宿主经环境变量传入；启动器模式下宿主是它自己拉起的，此时读 `session.json` 拿口令。

关掉界面时宿主去留由界面里的设置决定（`04-两种形态与启动.md` §7），宿主不参与这个判断。

## 6. 没装它的时候

| 场景 | 行为 |
|---|---|
| 命令行 | 全部可用，不受影响 |
| `ling plugins` 的列表 | 少一个 `core-ui` 条目 |
| 宿主启动 | 不受影响 |
| 已保存的界面偏好 | 存在配置里（`core-ui.*` 键），重装后还在 |

`LING-REQ-075` 要求「卸掉 core-ui 后命令行仍可用」，每条命令都必须能独立完成自己的事，这是它存在的意义——界面是便利，不是依赖。

## 7. 谁在用

- **使用者**：日常操作的主入口。
- **命令行**：某些场景下给出「去界面上看」的提示。
- **其他插件**：不调它，界面的调用是单向的（界面调别人）。
