# core-ui 04 详细设计 01 服务端与接口

> 状态：初定 | 版本：1.1.0-b1 | 最后更新：2026-11-02
> 依据：`docs/ling/builtin-plugins/core-ui/03-架构设计.md` §5

本文回答：界面进程对外提供哪些地址、怎么认证、每个请求怎么变成一次内核或插件调用、面板文件怎么安全地发出去。

---

## 1. 进程与端口

`core-ui` 是独立进程（侧车轨道），由宿主在装载时拉起。

| 项 | 规定 |
|---|---|
| 监听地址 | `127.0.0.1`，不可配置 |
| 端口 | 从 8010 起，占用则顺延，最多试到 8099 |
| 端口记录 | 写入 `registry.json` 的 `ui_port` 字段，`webui` 版靠它找到地址 |
| 与宿主的关系 | 单向客户端：它调管理端口，宿主不回调它 |
| 静态资源根 | 外壳页面编译期嵌入；面板页面运行时从各插件 `ui/` 目录读 |
| 并发 | 单线程事件循环，请求处理不阻塞超过 20 毫秒 |

端口段 8010 至 8099 与管理端口的 7900 段分开，理由见 `docs/ling/main/04-详细设计/04-管理端口与命令行.md` §2.2：两段混用会让顺延逻辑互相抢端口。

## 2. 认证

### 2.1 口令从哪来

宿主启动界面进程时，把口令放进环境变量：

```bash
LING_UI_TOKEN=<与 session.json 相同的口令>
LING_UI_PORT=8010
LING_UI_ROOT=<数据根>
```

界面进程**不读** `session.json`：口令由宿主经环境变量给。它只用 `LING_UI_ROOT` 拼面板资源路径（§5.1），不自己去推断数据根在哪、也不读数据根下的其它文件。宿主先起、界面后起，这条分工让界面成为一个纯粹的客户端。

### 2.2 浏览器怎么通过认证

浏览器访问 `http://127.0.0.1:8010/?token=<口令>` 打开外壳。外壳做的第一件事是：读 `token`，写进 `sessionStorage`，然后立刻 `history.replaceState({}, "", "/")` 把地址栏里的口令抹掉。之后每个 `/api/*` 请求带 `Authorization: Bearer <token>`。

必须抹掉的理由：地址栏内容会留在浏览器历史与截图里，还会被顺手分享出去。抹掉之后刷新页面靠 `sessionStorage` 里的值恢复，不影响使用。

| 情形 | 处理 |
|---|---|
| 没有 token 参数、也没有已保存的 token | 显示「请从 ling 主程序打开界面」 |
| token 不对 | 返回 401，页面提示「口令已变，请重新从主程序打开」 |
| token 对 | 正常 |

token 只在内存与 `sessionStorage` 里，不写 Cookie、不落盘。关掉标签页就没了，下次从主程序重新打开。

### 2.3 为什么不做登录页

做登录页就要有「用户」这个概念，而 ling 没有用户。口令的意义是「证明你是本机上能读 `session.json` 的那个人」，不是「你是谁」。一个输入框反而会让人以为要设密码。

### 2.4 哪些地址免认证

浏览器加载文档、样式表、脚本、图片时无法带自定义请求头，这些请求拿不到 token。因此下列地址免认证：

| 地址 | 内容 | 为什么可以免 |
|---|---|---|
| `GET /` | 外壳 HTML | 不含口令；没有口令时外壳自己显示提示，不返回数据 |
| `GET /shell.css`、`GET /shell.js`、`GET /views/*.js` | 外壳静态文件 | 同上 |
| `GET /panel/<插件 id>/*` | 面板资源 | 插件前端代码本就在磁盘上，不是秘密 |
| `GET /api/ui/theme.css` | 亮暗两套令牌定义，默认块取当前主题 | 只有颜色与尺寸，不含任何业务数据 |

免认证的地址全部是 `GET`，全部只返回文件或常量，不读写任何状态。**凡是有副作用的请求，一律要求 token**（`CUI-REQ-052`）。

这条取舍的代价写在 `docs/ling/builtin-plugins/core-ui/06-安全设计.md` §7：本机任何进程都能读到插件前端源码，也能知道当前主题。两者都不构成风险，因为读不到 token 就调不动任何方法。

## 3. 路由总表

| 方法 | 路径 | 认证 | 处理 | 返回 |
|---|---|---|---|---|
| `GET` | `/` | 无 | 返回嵌入的外壳 HTML | `text/html` |
| `GET` | `/shell.css` | 无 | 嵌入的外壳样式 | `text/css` |
| `GET` | `/shell.js` | 无 | 嵌入的外壳脚本 | `text/javascript` |
| `GET` | `/views/<名称>.js` | 无 | 嵌入的视图脚本，名称白名单 | `text/javascript` |
| `GET` | `/api/ui/theme.css` | 无 | 拼出亮暗两套令牌定义，`:root` 默认块取当前主题 | `text/css` |
| `GET` | `/panel/<插件 id>/<路径>` | 无 | 读该插件 `ui/` 下的文件 | 按后缀定 MIME |
| `HEAD` | `/panel/<插件 id>/<路径>` | 无 | 同 `GET` 的五道检查，只回头不回正文 | 无正文 |
| `POST` | `/api/<动作>` | 是 | 管理动作，转成一次管理端口调用 | `application/json` |
| `POST` | `/api/panel/call` | 是 | 面板代调，校验命名空间后转成 `kernel.call` | `application/json` |

`/views/<名称>.js` 的名称只允许 `plugins`、`logs`、`config`、`jobs`、`appearance`、`about` 六个，其他一律 404。这条防止把「按名称拼路径」变成任意文件读取。

匹配按下列顺序进行，先命中先返回：

| 序 | 规则 | 说明 |
|---|---|---|
| 1 | 精确路径 `/`、`/shell.css`、`/shell.js` | 三个固定文件，不走通用逻辑 |
| 2 | `/api/ui/theme.css` | 在 `/api/*` 之前判，否则会被当成动作名 `ui/theme.css` |
| 3 | `/api/panel/call` | 在 `/api/<动作>` 之前判，否则会被当成动作 `panel/call` |
| 4 | 其余 `/api/<动作>` | 动作名对照 §4 的表，表外一律 404 |
| 5 | `/views/<名称>.js` | 名称对照白名单 |
| 6 | `/panel/<id>/<路径>` | 走 §5 的五道检查 |

方法不匹配时的返回：`/api/*` 只接受 `POST`，其它方法返回 405 并在 `Allow` 头写 `POST`；`/panel/*` 只接受 `GET` 与 `HEAD`，其它方法同样 405。405 不返回 HTML，用与 §4 相同的 JSON 错误体。

## 4. 管理动作

全部是 `POST /api/<动作>`，请求体与响应体都是 JSON。响应统一是：

```json
{"ok": true, "result": {...}}
{"ok": false, "error": {"code": "E_...", "message": "人话原因", "advice": "下一步"}}
```

文案有两个来源，界面不另写第三份：

| 错误从哪来 | `message` | `advice` |
|---|---|---|
| 宿主转发的（`/api/<动作>` 与 `/api/panel/call` 的下游失败，例如 `E_METHOD_MISSING`、插件自己抛的错） | 原样取管理端口应答里的 `message` | 由 `core-ui` 按 `code` 查自己的表 |
| `core-ui` 自己判定的（`E_UI_*`、`E_PROTOCOL`、`E_PAYLOAD_TOO_LARGE`、`E_TIMEOUT`） | 由同一张表给 | 由同一张表给 |

这张表落在 `main/builtin-plugins/core-ui/src/error_copy.cpp`，键是 `code`，值是 `{message, advice}`。宿主侧的 `docs/ling/main/04-详细设计/04-管理端口与命令行.md` §4.4 只定文案的写作规则、不提供逐码对照，所以 `advice` 必须由 `core-ui` 自己持有，界面层不再写第四份。表要覆盖 `docs/ling/builtin-plugins/core-ui/07-测试与验收.md` §2.4 追溯表里出现过的所有码；加新码时同一个改动里补行。

四个字段的出现条件写死，界面按此判断，不靠猜：

| 字段 | 什么时候有 | 没有时 | 界面怎么用 |
|---|---|---|---|
| `code` | 恒有 | —— | 按码分类：可自行解决的、要看日志的、环境问题 |
| `message` | 恒有（两张来源表里每个键都配了一句） | —— | 主文案，必显示 |
| `advice` | 文案表里该 `code` 配了「下一步」时才有 | **省略字段**，不写 `null`、不写空串 | 有就作为第二行显示，没有就不留空行 |
| `detail` | 只有下游原样返回了结构化补充时才有 | 省略字段 | 默认不显示，用户点「详情」才展开；它是 JSON 值（不是句子），原样透传，展示时序列化后超过 2 KB 只截断显示 |

判断「有没有」用 `"advice" in error`：没有时是整条省略，不是 `null`、也不是空串，用取值判断会把「字段不存在」与「文案为空」混成一件事。

`detail` 与另外三个字段不同，它是**结构化补充**（例如 `{"field":"version"}`），不是给人读的句子：服务端原样透传不裁剪，截断只发生在展示层。它**不参与面向用户的文案排序**，界面上永远折叠，点开看原文。

| 动作 | 参数 | `result` | 转成的调用 |
|---|---|---|---|
| `plugins` | 无 | 插件对象数组，字段同 `ling plugins` | `kernel.plugins` |
| `install` | `path` 字符串，必填 | `{id, version}` | `kernel.install` |
| `uninstall` | `id` 字符串必填；`purge` 布尔，默认 `false` | `{removed:true}` | `kernel.uninstall` |
| `enable` | `id` 字符串，必填 | `{state:"running"}` | `kernel.enable` |
| `disable` | `id` 字符串，必填 | `{state:"stopped"}` | `kernel.disable` |
| `logs` | `plugin` 可选；`level` 取 `debug`/`info`/`warn`/`error`，可选；`lines` 整数默认 `200`、上限 `1000`；`before` 整数可选，用于上翻 | `{lines:[{ts, level, text}]}`，按时间正序 | `kernel.logs`（内核再按有无 `level` 转 `core-log.tail` / `core-log.query`） |
| `config.list` | `prefix` 字符串，必填 | `{items:[{key, value, type}]}`，`type` 取 `bool`/`number`/`string`/`json`/`null` | `core-settings.list` + 逐键 `get` |
| `config.get` | `key` 字符串，必填 | `{key, value, type}` | `core-settings.get` |
| `config.set` | `key` 字符串必填；`value` 任意 JSON | `{saved:true}` | `core-settings.write` |
| `jobs.list` | 无 | `{jobs:[{name, cron, method, params, enabled, last_run}]}` | `core-job.list` |
| `jobs.schedule` | `name`、`cron`、`method` 必填；`params` 对象可选；`catch_up` 布尔可选 | `{next_run}` | `core-job.schedule` |
| `jobs.setEnabled` | `name` 字符串必填；`enabled` 布尔必填 | `{enabled}` | `core-job.enable` / `core-job.disable` |
| `jobs.validate` | `cron` 字符串，必填 | `{ok, next_run}`，不合法时 `ok:false` 并带 `reason`（`core-job` 的原文，见 `docs/ling/builtin-plugins/core-job/02-设计与接口.md` §1.1.1） | `core-job.validate` |
| `jobs.cancel` | `name` 字符串，必填 | `{removed:true}` | `core-job.cancel` |
| `orphans` | 无 | 孤儿数据对象数组 | `core-plugin-manager.orphans` |
| `panels` | 无 | 见 §4.1 | `kernel.plugins` 结果过滤（见 §4.1） |
| `meta` | 无 | `{hostVersion, uiVersion, dataRoot}`，供「关于」页显示 | 无下游调用，服务端自己持有 |

`config.*`、`jobs.*`、`orphans` 这九行转的不是内核方法，而是插件方法，中间过一层 `kernel.call` 受限代理（`docs/ling/main/04-详细设计/04-管理端口与命令行.md` §4.5）。界面这一侧不用关心差别：它只发一次管理端口调用，代理与否在宿主内部完成。

**界面不直连内核。** 每个动作都转成一次管理端口调用，走的是命令行用的那条路（`LING-REQ-072`）。这条决定了三件事：

1. 界面与命令行的行为永远一致，不会出现「命令行能装、界面装不了」。
2. 界面拿到错误码后直接用同一套文案，不另维护。
3. 内核加一个方法，界面与命令行各自决定要不要暴露，但底层只有一份实现。

### 4.1 `panels` 为什么在服务端过滤

`panels` 的数据来源是 `kernel.plugins`，但界面不能自己去读插件目录判断「有没有面板」：那要解析每份 `plugin.toml`，等于在界面上再实现一遍清单解析。

服务端在启动时读一次全部清单，把 `[ui]` 段有效的插件记在内存表里，`panels` 直接返回这张表：

```json
{"ok": true, "result": [
  {"id": "resources-manager", "title": "资源管理", "icon": "/panel/resources-manager/icon.svg", "state": "running"},
  {"id": "player", "title": "播放器", "icon": null, "state": "failed", "reason": "侧车连续退出三次"}
]}
```

| 字段 | 说明 |
|---|---|
| `id` | 插件 id，用于拼面板地址 |
| `title` | 取 `[ui].title` |
| `icon` | 有 `[ui].icon` 时给可访问的地址，没有给 `null` |
| `state` | `running`、`stopped`、`failed` 三值之一 |
| `reason` | 仅 `failed` 时出现，内容来自内核的 `last_error` |

这张表的失效有两条路，都不依赖宿主回调（§1 已定「宿主不回调它」）：

| 触发 | 处理 |
|---|---|
| 服务端自己发出的写动作（`install`、`uninstall`、`enable`、`disable`）返回成功 | 立刻重读清单，下次 `panels` 就是新表 |
| 别处改了插件状态（命令行、插件崩溃） | 按 2 秒 TTL 兜底：距上次重读超过 2 秒时，`panels` 先调一次 `kernel.plugins` 再返回 |

2 秒这个值来自 `CUI-REQ-030` 的验收标准（停用后 2 秒内界面有反应）。TTL 只在有请求时触发，界面没开就不扫盘。

## 5. 面板静态资源

### 5.1 路径映射

```
请求  GET /panel/resources-manager/style.css
      ↓
磁盘  <数据根>/plugins/resources-manager/ui/style.css
```

`[ui].entry` 与 `[ui].icon` 都相对插件目录写，例如 `ui/index.html`。URL 里的路径部分一律相对该插件的 `ui/` 目录，因此：

| `[ui].entry` 取值 | 卡片里显示的面板地址 |
|---|---|
| `ui/index.html` | `/panel/<id>/index.html` |
| `ui/main.html` | `/panel/<id>/main.html` |
| `ui/sub/index.html` | `/panel/<id>/sub/index.html` |

换算规则：URL 路径 = `entry` 去掉开头的 `ui/`。`entry` 必须在 `ui/` 下（装载期已校验），因此去掉前缀后不会出现越界的相对路径。

外壳打开面板时用 `entry` 换算出的地址，不自己拼 `index.html`。

### 5.2 后缀白名单

只有下列后缀会被返回，其他一律 404（不猜 MIME）：

`.html` `.css` `.js` `.mjs` `.json` `.svg` `.png` `.jpg` `.jpeg` `.webp` `.gif` `.ico` `.woff` `.woff2` `.ttf`

白名单之外的请求不返回文件，即使文件存在。这条挡的是「把插件目录里的 `plugin.toml`、数据文件、日志当静态资源读出去」。

### 5.3 路径穿越防护

每次请求按顺序过五道检查，任一不过返回 404（不区分「不存在」与「不允许」，避免探测）：

| 序 | 检查 | 失败处理 |
|---|---|---|
| 1 | URL 解码一次后，路径里不含 `%` 残留（挡二次编码） | 404 |
| 2 | 路径按 `/` 切段后，没有 `..`、没有空段、没有以 `.` 开头的段 | 404 |
| 3 | 路径不以 `/` 或 `\` 开头，不含 `:`（挡 Windows 盘符） | 404 |
| 4 | 拼接后取真实路径（解析符号链接），其前缀必须等于 `<插件目录>/ui` 的真实路径 | 404 |
| 5 | 目标是普通文件，不是目录、不是设备文件 | 404 |

第 4 步是关键：只做字符串前缀比较挡不住符号链接（插件可以在 `ui/` 里放一个指向 `../../` 的链接）。必须先解析真实路径再比。

插件 id 也要校验：只允许 `^[a-z0-9][a-z0-9-]*$`，与清单规则一致，防止用 id 段做穿越。

### 5.4 缓存与 MIME

| 项 | 规定 |
|---|---|
| `Cache-Control` | `no-cache`（允许缓存但每次回源校验） |
| `ETag` | 文件大小与修改时间的组合，命中返回 304 |
| `Content-Type` | 按后缀白名单映射，未知后缀直接 404 |
| `Content-Security-Policy` | 两种页面的取值不同，细则与理由统一在 `docs/ling/builtin-plugins/core-ui/06-安全设计.md` §5.1、§5.2 定义；本节只规定「必须带」，取值不在这里重复 |
| `X-Content-Type-Options` | 一律 `nosniff` |
| `X-Frame-Options` | 外壳页面 `DENY`；面板资源不设，由 CSP 的 `frame-ancestors 'self'` 管（若给面板也加 `DENY`，外壳自己就嵌不进去了） |
| 目录请求 | `/panel/<id>/` 补上 `entry` 的文件名；`/panel/<id>` 301 到带斜杠的形式 |
| 不列目录 | 请求指向目录且没有 `index.html` 时 404 |

`no-cache` 而不是长缓存：插件升级后前端文件会换，长缓存会让用户看到旧界面。ETag 让未变的文件不必重传。

### 5.5 面板不存在

| 情形 | 返回 |
|---|---|
| 插件没有 `[ui]` 段 | 404，响应体是 `{"error":{"code":"E_UI_PANEL_NOTFOUND","message":"这个插件没有面板"}}` |
| `[ui].entry` 指向的文件不存在 | 404，同上；外壳在预检（`HEAD`）时发现，外框内显示错误与「重试」 |
| 插件已卸载但面板还开着 | 404，外壳收到后关闭该面板并提示「插件已卸载」 |

## 6. `/api/panel/call`

### 6.1 请求

```json
{"plugin": "resources-manager", "method": "resources-manager.scan", "params": {"path": "D:/media"}}
```

### 6.2 校验顺序

| 序 | 校验 | 失败返回 |
|---|---|---|
| 1 | 带有效 token | 401 |
| 2 | `plugin` 是已装载且带 `[ui]` 的插件 | `E_UI_FORBIDDEN` |
| 3 | `method` 以 `<plugin>.` 开头 | `E_UI_FORBIDDEN` |
| 4 | 方法在宿主的插件方法表里存在 | `E_METHOD_MISSING` |

第 3 步是能力边界的第二道闸。第 2 步要求插件当前可用：插件被停用后，它的面板即使还开着也调不动任何方法。

请求与响应：

| 情形 | 返回 |
|---|---|
| 成功 | 200，`{"ok":true,"result":<插件方法的返回值>}` |
| `params` 缺省或为 `null` | 当成 `{}` |
| 请求体不是合法 JSON | 400，`code` 为 `E_PROTOCOL` |
| 请求体超过 1 MB | 413，`code` 为 `E_PAYLOAD_TOO_LARGE` |

### 6.3 与 `/api/<动作>` 的区别

| | `/api/<动作>` | `/api/panel/call` |
|---|---|---|
| 调用方 | 外壳自己（管理动作） | 外壳代面板 |
| 能调什么 | 管理动作表中的方法 | 只有该插件命名空间下的方法 |
| 谁决定 `plugin` | 无此参数 | 外壳按消息来源填，面板无法指定 |
| 审计 | 记一条 info | 记一条 info，含来源插件 |

两条通道都带同一枚 token，差别只在服务端允许的方法范围。外壳不与面板共用通道，是因为外壳的管理动作要能调 `kernel.*`，而面板一条都不能调。

## 7. `theme.css` 响应

```http
HTTP/1.1 200 OK
Content-Type: text/css; charset=utf-8
Cache-Control: no-store

:root{--ling-bg:#1b1b1d;--ling-text:#e6e6e6;/* 当前主题 dark，其余 24 个 */}
:root[data-theme="light"]{--ling-bg:#ffffff;--ling-text:#1f2328;/* 亮色全量 26 个 */}
:root[data-theme="dark"]{--ling-bg:#1b1b1d;--ling-text:#e6e6e6;/* 暗色全量 26 个 */}
```

三段：`:root` 是默认块，取当前主题，供还没收到主题信息的面板首屏使用；两个 `[data-theme]` 块各给一套全量，面板收到 `theme` 消息后改属性即可，不必再发请求。`no-store` 是因为主题会变，缓存了就会用旧值。令牌取值不在这里重复，全表见 `docs/ling/builtin-plugins/core-ui/04-详细设计/04-设计令牌与主题.md` §2。

## 8. 启动与就绪

```
1. 宿主装载 core-ui，起进程，传三个环境变量
2. 界面进程绑定端口，写 registry.json 的 ui_port
3. 界面进程用 token 连管理端口，发一次 kernel.plugins 自检
4. 读一遍全部插件清单，建「带面板的插件」内存表（之后按 §4.1 的 TTL 与写动作刷新）
5. 自检通过才算就绪；向标准输出打 {"ready": true, "port": 8010}
6. webui 版：宿主调系统默认浏览器打开 http://127.0.0.1:<ui_port>/?token=...
   desktop 版：进程自己创建 WebView2 窗口，加载同一个 URL
```

第 3 步的自检很重要：只绑上端口不代表能连上宿主。口令不对、宿主正在关闭，都会在这一步暴露，而不是等用户点了按钮才发现。

第 4 步失败（某个插件清单读不了）不阻断就绪：把该插件从内存表里去掉，记一条 warn，其他面板照常可用。

## 9. 失败处理

| 情形 | 行为 |
|---|---|
| 端口 8010 至 8099 全被占 | 进程退出，宿主标记 `core-ui` 启动失败，日志说明端口段占满 |
| 连不上管理端口 | 退出并说明；宿主 2 秒后重启它 |
| token 不对 | 同上（口令来自 `session.json`，只有宿主重启才会换新；界面重启不换） |
| 静态页面请求（`GET`）读文件超过 5 秒 | 在两次分块读之间检查到超时后返回 504；阻塞中的一次读无法打断，最多再等这一次读完。界面提示「ling 没有响应，正在忙或已卡住」 |
| 界面进程崩溃 | 宿主按 `restart = on-crash` 重启，最多 3 次；第 3 次后停 |
| 面板文件读失败（权限、被占用） | 500，外壳在外框内显示「读不到面板文件」与文件路径，附「重试」 |
| 单次管理调用（`POST /api/*`）超过 30 秒 | 断开该次调用并返回超时错误，不阻塞其他请求 |

连续三次失败就停，是因为反复重启一个起不来的进程只会刷日志。停下来之后 `ling plugins` 里能看到「启动失败」与原因。

两个超时分开：静态页面 5 秒（只是读文件，慢了就是真卡住，但阻塞读打断不了，只能到点后再等一次读）；`POST /api/*` 30 秒，比命令行的 5 秒长，因为安装插件要解压、要跑装载检查。若两者都设 5 秒，安装这类调用会先被 504 掐掉。

## 10. 界面与命令行的取舍

| 事 | 界面 | 命令行 |
|---|---|---|
| 装插件 | 选目录 | 敲路径 |
| 看状态 | 卡片、颜色 | 表格 |
| 看日志 | 筛选、自动刷新 | 纯文本 |
| 改配置 | 表单 | 手编 JSON |
| 批量操作 | 多选 | 暂无（`core-plugin-manager` 的 `apply`） |
| 排障 | 看得到现象，看不到内核日志 | `ling logs` 直读文件 |
| 插件自己的功能 | 面板里点 | 调该插件的方法 |

倒数第二行是刻意的：**界面不显示内核日志**。内核日志是「修宿主的工具」，不能依赖会坏掉的那个部件（`docs/ling/main/04-详细设计/04-管理端口与命令行.md` §8.2 的同一条原则）。界面崩了的时候，命令行还在。

最后一行是新加的：命令行能调任何插件的方法，面板只能调自己那个插件的。所以「面板里做不到的事」不等于「ling 做不到」，命令行始终是全集。
