# core-ui 04 详细设计 03 面板挂载与消息协议

> 状态：初定 | 版本：1.1.0-b1 | 最后更新：2026-11-02
> 依据：`docs/ling/builtin-plugins/core-ui/03-架构设计.md` §4、§7

本文回答：插件怎么声明面板、面板怎么被装进来、两面之间发哪些消息、消息怎么防伪造、面板出问题怎么办。

---

## 1. 清单声明

### 1.1 `[ui]` 段

```toml
id = "resources-manager"
version = "1.2.0"
api = "1"
name = "资源管理"
capabilities = ["fs", "ui"]

[ui]
entry = "ui/index.html"
title = "资源管理"
icon = "ui/icon.svg"
```

| 字段 | 必填 | 类型 | 规则 |
|---|---|---|---|
| `entry` | 是 | 字符串 | 相对插件目录的路径，必须位于 `ui/` 下，后缀必须 `.html` |
| `title` | 是 | 字符串 | 1 至 32 字符，显示在侧边栏与面板外框 |
| `icon` | 否 | 字符串 | 相对插件目录的路径，必须位于 `ui/` 下，后缀为 `.svg` 或 `.png` |

一个插件最多一个面板，因此 `[ui]` 是单段，不是数组。要在一个面板里放几块界面，插件在自己的网页内部划分（`docs/ling/builtin-plugins/core-ui/02-技术选型.md` §6）。

### 1.2 校验

`[ui]` 段在清单校验的第 10 步之后追加，顺序如下：

| 序 | 校验 | 失败 |
|---|---|---|
| 1 | `[ui]` 存在时，`capabilities` 含 `ui` | `E_UI_PANEL_DECL`，信息写明「声明了 [ui] 但缺少 ui 能力」 |
| 2 | `entry` 与 `title` 都存在且非空 | `E_UI_PANEL_DECL`，写明缺哪个字段 |
| 3 | `entry`、`icon` 不含 `..`、不以 `/` 或 `\` 开头、不含 `:` | `E_UI_PANEL_DECL`，信息回显原文 |
| 4 | `entry`、`icon` 解析后的真实路径在 `ui/` 目录内 | `E_UI_PANEL_DECL` |
| 5 | `entry` 后缀为 `.html`，`icon` 后缀为 `.svg` 或 `.png` | `E_UI_PANEL_DECL` |
| 6 | `title` 长度在 1 至 32 之间 | `E_UI_PANEL_DECL` |

`entry` 指向的文件**不在校验期检查存在性**：插件存在先装后补文件、或文件放在压缩包里按需解压的情形。文件不存在时的表现见 §8（打开面板才报错，装载成功），对应 `CUI-REQ-056`。

§1.1 与 §1.2 写的是**实现侧**要做什么；给插件作者看的同一套规则在 `docs/ling/plugin-support/ui/01-面板声明与资源.md` §1、§2。两处的字段名、校验顺序、错误码必须一致，**改一处必须同步另一处**，否则会出现「文档说能装、实际装不上」。

### 1.3 与 capability 的关系

`capabilities` 里的 `ui` 是 1.1.0 起有实际含义的取值：**声明它才允许贡献面板**。该载荷已回填到 `docs/ling/plugin-support/01-插件装载与接口.md` §3.2，面向插件作者的写法见 `docs/ling/plugin-support/ui/00-总览与约定.md`。

没有 `ui` 能力的插件即使写了 `[ui]` 段也装载失败，这条挡的是「插件作者复制清单时忘了改能力」，让错误在装载期暴露，而不是在打开面板时白屏。

## 2. 加载流程

```
外壳                          服务端                        磁盘
  │                             │                            │
  ├─ HEAD /panel/<id>/<entry 去掉 ui/ 前缀> ─▶│                            │
  │                             ├─ 五道路径检查 ────────────▶│
  │◀─ 200 / 404 ────────────────┤                            │
  │                             │                            │
  ├─ 建 section.panel + iframe  │                            │
  ├─ iframe.src = /panel/<id>/<entry> ──────────────────────▶│
  │                             │◀─ 读文件 ──────────────────┤
  │◀─ HTML ─────────────────────┤                            │
  │                             │                            │
  ├─ 等 iframe load（上限 10 秒）                            │
  ├─ postMessage {type:"init", …} ──▶ 面板                    │
  │                             │                            │
  │◀─ {type:"call", method:"…"} ─ 面板                        │
  ├─ 校验命名空间 → POST /api/panel/call ─▶ 服务端 → 宿主      │
  ├─ postMessage {type:"result", …} ──▶ 面板                  │
```

### 2.1 为什么先 HEAD 预检

iframe 加载 404 时浏览器照样会触发 `load` 事件，外壳从跨源的 `contentDocument` 里读不到任何东西，无法区分「面板渲染了但空白」与「文件不存在」。

所以在创建 iframe 之前先用 `fetch(url, {method:"HEAD"})` 探一次：

| 结果 | 处理 |
|---|---|
| 200 | 建 iframe |
| 404 | 不建 iframe，外框内直接显示「面板文件不存在：`<路径>`」与「重试」 |
| 5 秒无响应 | 显示「面板文件读取超时」与「重试」 |
| 其他状态码 | 显示状态码与「看日志」 |

服务端对 `HEAD /panel/*` 返回与 `GET` 相同的响应头，不带正文。

### 2.2 10 秒加载上限

预检通过后建 iframe，从设置 `src` 起算 10 秒内没有 `load` 事件，视为加载失败，显示「面板加载超时」与「重试」。计时器在 `load` 时清掉。

预检与加载两道判断各有各的用：预检查「文件在不在」，加载检查「网页能不能跑起来」。

## 3. 消息格式

### 3.1 信封

所有消息是一个 JSON 对象，`type` 字段决定种类：

| 字段 | 出现于 | 说明 |
|---|---|---|
| `type` | 全部 | 七种之一 |
| `id` | `call`、`drag`、`result` | 正整数，面板自增，外壳原样回带 |
| `v` | `init` | 协议版本，当前为 `1` |

### 3.2 七种消息

| 种类 | 方向 | 字段 | 何时发 |
|---|---|---|---|
| `init` | 外壳 → 面板 | `pluginId`、`title`、`theme`、`tokens`、`v` | iframe `load` 之后立即发，只发一次 |
| `call` | 面板 → 外壳 | `id`、`method`、`params` | 面板要调方法时 |
| `result` | 外壳 → 面板 | `id`、`ok`、`result` 或 `error` | 每次 `call` 或 `drag` 必有且仅有一条回复（来源与结构都合法时；被判为非法而丢弃的消息不回包，见 §4.5） |
| `theme` | 外壳 → 面板 | `theme`、`tokens` | 主题变化时广播给所有面板 |
| `event` | 外壳 → 面板 | `name`、`data` | 外壳级手势（拖放）与将来推送共用 |
| `drag` | 面板 → 外壳 | `id`、`kind`、`payload` | 面板内开始一次拖动时 |
| `shutdown` | 外壳 → 面板 | `reason` | 面板即将被移除前 300 毫秒 |

### 3.3 各消息的正文

`init`：

```json
{"type":"init","v":1,"pluginId":"resources-manager","title":"资源管理",
 "theme":"dark","tokens":{"--ling-bg":"#1b1b1d","--ling-text":"#e6e6e6"}}
```

`tokens` 恒为全量 26 个（不随主题只给变化的 15 个），与 `theme.css` 的 `:root` 块一致；两条路都给，是因为面板未必用 `<link>`。面板收到 `init` 之前不应发 `call`。

`call`：

```json
{"type":"call","id":7,"method":"resources-manager.scan","params":{"path":"D:/media"}}
```

`result`：

```json
{"type":"result","id":7,"ok":true,"result":{"files":12}}
{"type":"result","id":7,"ok":false,"error":{"code":"E_UI_FORBIDDEN","message":"面板不能调用其他插件的方法","advice":"改为调用本插件的方法"}}
```

`error` 的字段规则与 `/api/<动作>` 的响应一致（见 `docs/ling/builtin-plugins/core-ui/04-详细设计/01-服务端与接口.md` §4）：`code` 恒有；`message` 与 `advice` 未必齐全；下游带出来的原始描述放在 `detail` 里，界面默认折叠。外壳自己判定的错误（越权、超限、未就绪）只填 `code`、`message`、`advice`，不填 `detail`——外壳不产生堆栈。

`theme`：

```json
{"type":"theme","theme":"light","tokens":{"--ling-bg":"#ffffff"}}
```

`event`：

```json
{"type":"event","name":"drop","data":{"kind":"files","payload":{"paths":["D:/media/a.jpg"]},"from":"resources-manager"}}
```

`shutdown`：

```json
{"type":"shutdown","reason":"disabled"}
```

`reason` 取值：`closed`（用户关掉面板）、`disabled`（插件被停用）、`uninstalled`（插件被卸载）、`evicted`（超过 4 个被挤掉）。

## 4. 外壳侧处理

### 4.1 来源识别

外壳维护一张表：`iframe.contentWindow` → 插件 id。收到任何消息，先按 `event.source` 查表：

| 情形 | 处理 |
|---|---|
| `event.source` 不在表里 | 丢弃，不回复（来源是别的窗口） |
| 在表里，且 `type` 不是 `call` 或 `drag` | 丢弃并记 warn（面板只允许发这两种） |
| 在表里，`type` 是 `call` | 见本文 §4.3 |
| 在表里，`type` 是 `drag` | 见本文 §6.2 |
| 在表里，但该面板尚未收到 `init` | 带 `id` 的回 `result{ok:false, error:{code:"E_UI_NOT_READY"}}`，不带 `id` 的丢弃；两种都记 warn |

**永远不读消息里的 `pluginId` 或 `plugin` 字段来认定调用方。** 面板写什么名字都不影响判定，这是「面板不能冒充别人」的机制来源（`CUI-REQ-014`）。

### 4.2 `event.origin` 只放行「不透明源」

面板的 iframe 不给 `allow-same-origin`（`docs/ling/builtin-plugins/core-ui/04-详细设计/02-外壳页面与布局.md` §3.1），因此它是**不透明源**，`event.origin` 恒为字符串 `"null"`，永远不等于外壳的 `location.origin`。

| 情形 | 处理 |
|---|---|
| `event.origin` 为 `"null"` | 通过（来自隔离画框） |
| `event.origin` 等于 `location.origin` | 丢弃并记 warn（同源页面不该冒充面板） |
| 其他取值 | 丢弃并记 warn |

**这道校验只回答「消息是不是从不透明源来的」，回答不了「这个画框有没有被导航到外部网址」。** 不透明源下无论加载什么页面，`origin` 都是 `"null"`，这是沙箱的固有性质，不是遗漏。

即便被导航到外部，它能做的事与原来一样——只有该插件自己的方法（§4.3 的命名空间校验不依赖 `origin`）。权限边界由 §4.1 的来源表与 §4.3 的命名空间共同决定，这一点对应 `docs/ling/builtin-plugins/core-ui/06-安全设计.md` 的 SEC-02。

### 4.3 命名空间校验

```js
function allowed(pluginId, method) {
  return typeof method === "string" && method.startsWith(pluginId + ".");
}
```

不通过时立即回 `result`：

```json
{"type":"result","id":7,"ok":false,
 "error":{"code":"E_UI_FORBIDDEN","message":"面板不能调用 <method>","advice":"只能调用 <pluginId>.* 下的方法"}}
```

同时记一条 warn：`plugin=<id> method=<method> result=forbidden`。

### 4.4 并发与超时

| 项 | 规定 |
|---|---|
| 单面板在途请求上限 | 16 条 |
| 超过上限 | 立即回 `E_UI_BUSY`，不排队 |
| 单条请求超时 | 35 秒（服务端 30 秒 + 5 秒余量），超时回 `E_TIMEOUT` |
| `id` 重复 | 新条目覆盖旧条目，旧条目立刻回 `E_TIMEOUT`；此后到达的旧应答找不到条目，按 `id` 丢弃 |

上限 16 条的理由：正常面板的并发在 3 至 5 条（列表、详情、计数），16 条留足余量；再多的请求多半是面板写错了循环。

### 4.5 面板发来非法结构

| 情形 | 处理 |
|---|---|
| 不是对象、`type` 不是字符串 | 丢弃 |
| `call` 缺 `id` 或 `id` 不是正整数 | 丢弃并记 warn |
| `method` 不是字符串 | 回 `E_PROTOCOL`（这是结构错误，不是越权） |
| `params` 不是对象 | 当成 `{}` |

外壳不对面板发来的数据做深度校验：`params` 的内容是插件自己的事，越权由命名空间挡住，数据合法性由插件方法自己校验。

## 5. 面板侧接入

### 5.1 最小样板

```js
let pluginId = null, seq = 0;
const pending = new Map();

window.addEventListener("message", (e) => {
  // 面板是不透明源，e.origin 恒为 "null"，不能拿它做白名单；
  // 只认父窗口发出的消息。
  if (e.source !== window.parent) return;
  const m = e.data;
  if (!m || typeof m.type !== "string") return;

  switch (m.type) {
    case "init":
      pluginId = m.pluginId;
      applyTheme(m.theme, m.tokens);
      render();
      break;
    case "theme":
      applyTheme(m.theme, m.tokens);
      break;
    case "result": {
      const cb = pending.get(m.id);
      if (cb) { pending.delete(m.id); cb(m); }
      break;
    }
    case "event":
      onEvent(m.name, m.data);
      break;
    case "shutdown":
      cleanup();
      break;
  }
});

function call(method, params = {}) {
  if (!pluginId) return Promise.reject({ code: "E_UI_NOT_READY", message: "还没收到 init" });
  return new Promise((resolve, reject) => {
    const id = ++seq;
    pending.set(id, (m) => (m.ok ? resolve(m.result) : reject(m.error)));
    parent.postMessage({ type: "call", id, method, params }, "*");
  });
}

// 拖动结束时由外壳回 result，与 call 共用 pending 表
function drag(kind, payload) {
  return new Promise((resolve, reject) => {
    const id = ++seq;
    pending.set(id, (m) => (m.ok ? resolve(m.result) : reject(m.error)));
    parent.postMessage({ type: "drag", id, kind, payload }, "*");
  });
}
```

### 5.2 三条硬要求

| 要求 | 理由 |
|---|---|
| 等 `init` 再渲染 | `init` 之前拿不到 `pluginId`，也拿不到主题，先渲染会白闪（`CUI-REQ-023`） |
| 只接受 `e.source === window.parent` 的消息 | 面板发出的消息 `e.origin` 恒为 `"null"`，而它收到的消息带的是外壳的源；拿 `e.origin` 做白名单会把外壳自己的消息一起挡掉。比父窗口引用才是「只认外壳」 |
| 颜色与尺寸只取 `--ling-*` 令牌 | 否则切主题时面板不跟着变（`CUI-REQ-020` 的主体是外壳，这条是面板侧的对等要求） |

### 5.3 面板不该做的事

| 不做 | 原因 |
|---|---|
| 用 `localStorage` 存状态 | 不透明源下不可用，会抛错 |
| `fetch("/api/...")` | 跨源且无 token，浏览器直接拦（`CUI-REQ-015`） |
| `document.domain = ...` | 不透明源下抛错 |
| 定时轮询自己发 `call` 之外的通道 | 没有别的通道 |

要持久化的数据写进插件自己的配置（`core-settings`），不要指望浏览器存储。

## 6. 事件通道

### 6.1 现在只有一个来源

`event` 消息目前由外壳在一处产生：

| 来源 | `name` | `data` |
|---|---|---|
| 外壳接管的拖放手势 | `drop` | `{kind, payload, from}`，见 §6.2 |

面板被挤掉、被关闭、被停用都不走 `event`，统一用 `shutdown` 加 `reason`（§3.2）。`event` 只有 `drop` 一个来源，位置留给将来的推送。

面板的数据变化（例如资源库多了文件）不走 `event`，面板自己用 `call` 轮询。这是 `docs/ling/builtin-plugins/core-ui/02-技术选型.md` §9 的选择。

### 6.2 拖放怎么发生

原生拖拽跨 iframe 会被 iframe 吞掉：从面板 A 拖到面板 B，`dragover` 只落在 A 的文档里，B 收不到。

外壳的做法是「消息式拖拽」，用 `drag` 消息加 `event` 消息打通：

| 步骤 | 谁做 | 动作 |
|---|---|---|
| 1 | 面板 A | 用户在面板内按下并移动超过 5 像素时，发 `{type:"drag", id, kind, payload}` |
| 2 | 外壳 | 校验来源与字段，进入拖拽模式：在所有 iframe 上盖一层透明遮罩（阻止 iframe 抢事件），显示跟随光标的提示条 |
| 3 | 外壳 | 用户松手时按坐标算出落点面板；不在任何面板上则丢弃 |
| 4 | 外壳 | 给落点面板发 `{type:"event", name:"drop", data:{kind, payload, from:pluginId}}`；给 A 发 `result`，`ok` 只表示**是否已投递**到某个面板，不表示目标处理成功 |
| 5 | 面板 B | 收到 `drop`，调自己的方法处理，例如 `B.play(payload.paths[0])` |

`drag` 的字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | 正整数 | 与 `call` 共用编号空间 |
| `kind` | 字符串 | `files`、`text` 之一 |
| `payload` | 对象 | `kind` 为 `files` 时是 `{paths:[...]}`，为 `text` 时是 `{text:"..."}`；序列化后不超过 8 KB |

三点值得记：

1. **手势由外壳接管，执行由目标面板自己调自己的方法**，与「面板只调自己」一致。
2. 外壳不搬运数据：`payload` 只是路径或文本，真正的读文件由目标插件的插件本体去做，过宿主的能力校验。
3. `payload` 大小上限 8 KB。超过时外壳回 `result{ok:false}`，`error.code` 为 `E_PAYLOAD_TOO_LARGE`，`advice` 为「拖拽内容过大，请传路径而不是内容」。

### 6.3 将来接推送

外壳内部有一个 `EventHub`：面板侧只认「收到 `event` 消息」，不关心它从哪来。将来服务端需要用推送时，加一条「服务端 → 外壳」的常驻通道（SSE 或 WebSocket），收到后调 `EventHub.emit(pluginId, name, data)`。

面板侧代码一行不改。这就是「抽象出事件通道」的实际含义。

## 7. 生命周期

### 7.1 打开

```
预检 HEAD → 建外框 → 建 iframe → load → init → 面板开始工作
```

### 7.2 关闭

```
发 shutdown{reason:"closed"} → 300 毫秒后移除 section 与外框
```

300 毫秒是给面板收尾的窗口（断开自己的定时器、保存草稿）。到期无论如何都移除，不信任面板配合。

### 7.3 插件停用

```
shutdown{reason:"disabled"} → 300 毫秒后移除 → 侧边栏入口变淡保留
```

入口保留而不是消失：插件还在，只是停用了，用户能点开看到「插件已停用」与「启用」按钮。

### 7.4 插件卸载

```
shutdown{reason:"uninstalled"} → 300 毫秒后移除 → 侧边栏入口消失 → 顶部提示
```

### 7.5 重启恢复

启动时读 `core-ui.layout.order`，按顺序逐个预检并打开：

| 情形 | 处理 |
|---|---|
| 插件还在、预检通过 | 打开，宽度取 `widths` 对应值 |
| 插件已卸载 | 跳过，从 `order` 里删掉，不提示（用户卸的时候已经知道了） |
| 插件已停用 | 不打开，入口变淡保留 |
| 预检 404 | 跳过，顶部提示「`<名称>` 的面板文件不在了」 |

恢复最多打开 4 个，与上限一致。

### 7.6 面板卡死

1.1.0 不提供「重启单个面板」按钮。面板卡死时用户能做的：关掉再打开（等于重载 iframe）。

不做自动重启：外壳无法判断卡死与「正在算一个大目录」，自动重载会让用户丢掉正在做的事。

## 8. 失败处理

| 情形 | 显示 | 后续 |
|---|---|---|
| 插件没有 `[ui]` | 不出现在侧边栏 | —— |
| `entry` 文件缺失（预检 404） | 外框内「面板文件不存在：`<路径>`」+「重试」 | 修文件后点重试即可 |
| 预检超时 5 秒 | 「面板文件读取超时」+「重试」 | —— |
| iframe 加载超时 10 秒 | 「面板加载超时」+「重试」 | —— |
| 面板脚本抛错 | 面板自己白屏，外壳不显示错误 | 用户关掉再打开即重载 |
| `init` 前发 `call` | 回 `result` 失败（`E_UI_NOT_READY`）并记 warn | 面板应等 `init` |
| 插件已卸载但面板还开着 | 关闭面板，提示「插件已卸载」 | —— |
| 面板发 1000 条 `call` | 超过 16 条的在途请求回 `E_UI_BUSY` | 面板应降低并发 |
