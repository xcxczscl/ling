# core-ui 02 技术选型

> 状态：初定 | 版本：1.1.0-b1 | 最后更新：2026-11-02
> 依据：`docs/ling/builtin-plugins/core-ui/00-总览与术语.md`、`docs/ling/builtin-plugins/core-ui/01-需求规格.md`

本文回答：把插件界面装进 core-ui 这件事，有哪几种做法、为什么选这套、代价是什么。

---

## 1. 这份文档定什么

1.1.0 新增的每一条技术选择，都在这里给出理由与被否决的方案。结论汇总在 §2，逐条论证在 §3 至 §10。已实现部分的既有选型（侧车进程、端口段、原生 DOM）在 §11 说明为何不变。

## 2. 决策总表

| # | 决策 | 结论 | 主要理由 | 详见 |
|---|---|---|---|---|
| 1 | 插件界面形态 | iframe 整页挂载 | 隔离干净、作者门槛低、能装复杂界面 | §3 |
| 2 | 面板资源由谁 serve | core-ui 服务端统一 serve | 保住同源，主题机制才成立 | §4 |
| 3 | token 位置 | 不进面板，只在外壳 | 面板被攻破也拿不到宿主权限 | §5 |
| 4 | 面板能力边界 | 只能调自己命名空间的方法 | 最小权限；跨插件走插件本体中转 | §5.3 |
| 5 | 面板粒度 | 一插件一面板 | 避开窗口管理器复杂度 | §6 |
| 6 | 面板操作入口 | 面板自带工具栏，无独立首栏 | 不需要维护「焦点面板」 | §7 |
| 7 | 面板与外壳通信 | `postMessage` 固定七种消息 | 同浏览器内唯一的跨源通道 | §8 |
| 8 | 实时刷新 | 轮询，抽象出事件通道 | 本机开销可忽略；推送要新增常驻连接 | §9 |
| 9 | 样式一致 | 设计令牌 `--ling-*` | 只靠变量，不靠共享代码 | §10 |
| 10 | 主题可调 | 令牌的一套取值，亮/暗两套 | 换主题等于换值，一处改全局变 | §10.3 |
| 11 | 外壳前端 | 原生 DOM + `fetch`，不用框架 | 视图数量有限，构建链成本高于收益 | §11.1 |
| 12 | 面板前端 | 不限，作者自选 | 面板是独立网页，与外壳互不影响 | §11.2 |

## 3. 插件界面用哪种形态

四种候选，判据是「能不能装下复杂界面」与「隔离是否天然」：

| 方案 | 做法 | 能装的界面 | 隔离 | 作者门槛 |
|---|---|---|---|---|
| **A. iframe 整页挂载** | 插件交一份网页，外壳用 iframe 加载 | 任意网页，含进度条、拖拽、图表 | 浏览器强制隔离 | 会写网页即可 |
| B. 声明式描述 | 插件声明字段与动作，外壳用内置控件拼界面 | 表单、列表 | 无代码进入外壳，最安全 | 最低 |
| C. 微前端组件 | 插件交 JS 组件，外壳同页面渲染 | 任意 | 需自己画边界，同源即同权 | 需要构建链 |
| D. 各自起端口 | 插件自己 serve 自己的界面，外壳只放链接 | 任意 | 跨源，外壳够不着 | 要写服务端 |

**选 A。** 三条理由：

1. **B 装不下目标场景。** 播放器要进度条与拖拽、资源管理要目录树与文件列表，声明式只能生成规整表单。选 B 等于给插件能力封顶在「填表」。
2. **C 的隔离要自己画。** 组件与外壳同页面、同源，能直接读 `sessionStorage` 里的 token，等于把宿主管理权交给任意插件。要补回隔离就得引入 Shadow DOM 加代码审查加 CSP 组合，成本高于 A。
3. **D 破同源。** 每个插件自己开端口后，外壳在 8010、插件在别的端口，主题广播、样式联动都做不了（§4 展开）。

A 的代价见 §12：拖拽不是桌面软件那种跟手拖拽，而是「松手后发一条消息」。

## 4. 面板资源为什么必须由 core-ui 统一 serve

浏览器的同源策略规定：协议、主机、端口三者全同才算同源，同源页面之间才能自由读写 DOM、共享存储。

| 由谁 serve | 外壳与面板的关系 | 后果 |
|---|---|---|
| core-ui（8010） | 默认同源；再由 `sandbox` 主动降为不透明源（§5.2） | 主题样式表由同一个服务发，面板只需一个相对路径；资源读取、缓存、失败处理都在同一处 |
| 插件自己（各自端口） | 跨源，且随插件数量增加变得不可控 | 每个插件都要处理 CORS 与自己的鉴权；主题样式表跨源加载要额外配许可；外壳无法统一处理加载失败 |

还有一条更硬的理由：**插件是运行时安装的**。它的网页无法在编译 core-ui 时被嵌进可执行文件，只能运行时从磁盘读。既然必须运行时读，由一个已经在跑的服务统一读，比让每个插件各起一个 HTTP 服务省事得多——后者要求每个插件作者都写服务端、处理端口冲突、处理进程退出。

所以 1.0.0 的「页面编译期嵌进 exe」这条只保留给外壳自己；面板改成运行时从 `<插件目录>/ui/` 读。见 `docs/ling/builtin-plugins/core-ui/04-详细设计/01-服务端与接口.md` §5。

## 5. token 为什么不进面板

### 5.1 面板是不可信代码

面板网页由第三方插件提供，内容不受 core-ui 控制。1.0.0 里 `token` 存在外壳的 `sessionStorage` 中，而 `sessionStorage` 按源隔离——只要面板与外壳同源，面板里的任意一行 JS 都能把它读走，然后自己调 `kernel.uninstall`。

因此：**token 只存在于外壳内存中，永不写入面板可访问的任何位置**——不放在 iframe 的 URL 里、不放在 `postMessage` 的消息里、不写进任何面板可读的存储。

### 5.2 面板也无法自己发请求

面板的 iframe 不授予同源（`sandbox` 不含 `allow-same-origin`），浏览器把它的源视为不透明源。带来三个直接结果：

| 结果 | 表现 |
|---|---|
| 面板请求 `127.0.0.1:8010` 属于跨源请求 | 没有 CORS 许可就被浏览器拦下，面板发不出有效请求 |
| 面板读不到外壳的 `sessionStorage`、`localStorage`、Cookie | 即使 token 被写进这些位置也拿不到 |
| 面板内的 `document.domain` 访问抛错 | 无法把自己改成与外壳同源 |

这三条是浏览器强制的，不依赖 core-ui 的代码正确性。面板唯一能与外界通信的通道是 `postMessage`，而这条通道的接收方是外壳。

### 5.3 能力边界怎么落地

面板要做事，只能把意图发给外壳，由外壳带 token 请求服务端。

```
面板 → postMessage{"type":"call","method":"rm.scan"} → 外壳
外壳 → 按 iframe 来源查出 pluginId，校验 method 前缀 → 不符直接回 E_UI_FORBIDDEN
外壳 → POST /api/panel/call {plugin:"rm", method:"rm.scan"} + token → 服务端
服务端 → 再校验一次 method 属于 plugin 命名空间 → kernel.call
```

**调用方身份来自消息来源，不来自面板自报。** 面板在消息里写什么都不影响判定：外壳按「这条消息来自哪个 iframe」查出插件，冒充无从下手。

服务端为什么还要再校验一次：外壳是唯一调用方，但外壳自己也会犯 bug。两道校验的成本是一次字符串比较，收益是「即使外壳被绕开，越权仍被拒」。

被否决的方案：

| 方案 | 否决理由 |
|---|---|
| 面板与外壳同权 | 等于把宿主管理权交给任意插件 |
| 清单白名单声明 | 比最小权限更宽松，且要新增字段与校验；真实需求里没有「面板必须调别人」的场景，跨插件走插件本体中转即可 |
| 只靠外壳校验 | 单点失效，外壳一个 bug 就全线失守 |

## 6. 为什么一插件一面板

「多面板」指一个插件在功能区占多个格子，用户自由增删摆放。它要求外壳实现：面板注册表、格子布局、拖拽重排、跨插件拖放、焦点管理、布局持久化。这是一套窗口管理器。

而这些能力插件自己就能给：插件在自己的网页里用左右分栏、上下分栏、内部标签页，外壳不需要知道。

| 做法 | 外壳复杂度 | 插件自由度 | 同屏多插件 |
|---|---|---|---|
| 一插件一面板 | 低：一个 iframe 一层外框 | 插件内部任意布局 | 支持，多个插件的面板并排 |
| 一插件多面板 | 高：窗口管理器 | 由外壳的格子约束 | 支持 |

**选一插件一面板。** 「两个插件同屏」不受影响：功能区摆的是「多个插件的面板」，不是「一个插件的多个面板」。

## 7. 为什么不要独立首栏

首栏指窗口最上方那条横贯全宽的条。候选做法有两种：首栏放当前焦点面板的操作按钮，或首栏只放全局信息。

否决第一种的理由：要维护「谁是焦点面板」。用户点面板内任意位置、点外框、用键盘 Tab，都会改变焦点；焦点一变，首栏按钮就得换一套。这条状态链比它省下的那点垂直空间贵。

否决第二种的理由：1.1.0 的全局信息只有「宿主是否在跑」与版本号，都放得进侧边栏底部的两行，不值得占一整条。

结论：**面板的操作按钮放在面板自己的网页里**（面板顶部由插件自己画工具栏），外壳只在面板外围画 32 像素高的外框标题条。外框是外壳职责，不是首栏：它跟着面板走，位置固定，不需要同步任何焦点状态。

## 8. 为什么用 postMessage

外壳与面板是两个文档，唯一的合法通道是 `postMessage`。它有三个我们需要的能力：跨源可用、单向投递、可以传结构化的对象。

不用别的通道的理由：

| 通道 | 否决理由 |
|---|---|
| 面板直接调 HTTP | 面板没有 token 且被浏览器拦（§5.2） |
| `BroadcastChannel` | 按源隔离，不透明源的面板用不了；且无法定向到某一个面板 |
| `SharedWorker` | 同源才能共享，面板不在这个源里 |
| URL 参数回传 | 每次传值都要导航，面板状态会丢 |

协议细节见 `docs/ling/builtin-plugins/core-ui/04-详细设计/03-面板挂载与消息协议.md` §3。

## 9. 实时刷新为什么先轮询

| | 轮询 | 推送（SSE/WebSocket） |
|---|---|---|
| 实时性 | 最多迟一个间隔 | 毫秒级 |
| 实现 | 面板定时发一条 `call` | 新增常驻连接、断线重连、事件补发 |
| 本机开销 | 每 2 秒一次空查询 | 长连接常驻 |

本机单用户、面板数量不超过 4 个，2 秒一次空查询的开销测不出来。真正的差别是实现复杂度。

**选轮询，但把「事件通道」抽象出来。** 面板侧统一用「订阅一个事件名 + 收到 `event` 消息」的接口；现在的外壳用轮询实现它，将来换成推送只改外壳与服务端之间的那一段，面板与插件都不用改。

推送将来只能加在「服务端与外壳」之间：面板是不透明源，`EventSource` 与 `WebSocket` 都要跨源许可，且面板没有 token 可带。所以推送的终点是外壳，再由外壳转发给面板——这与现在的消息协议形状一致，是选轮询也不影响将来的原因。

## 10. 样式与主题

### 10.1 问题

面板是插件自己写的网页。若每个插件写死颜色（`background:#fff`），会出现两种难看：

1. 插件之间的观感不统一，侧边栏与面板像两个软件；
2. 切到暗色主题时，外壳变暗而面板仍白，一半亮一半暗。

### 10.2 设计令牌

core-ui 定义一组 CSS 变量，外壳与所有面板只引用变量、不写死具体值。

| 类别 | 令牌举例 | 数量 |
|---|---|---|
| 背景 | `--ling-bg`、`--ling-bg-raised`、`--ling-bg-sunken` | 3 |
| 文字 | `--ling-text`、`--ling-text-dim`、`--ling-text-invert` | 3 |
| 线条 | `--ling-border`、`--ling-border-strong` | 2 |
| 强调与语义 | `--ling-accent`、`--ling-accent-hover`、`--ling-accent-fg`、`--ling-ok`、`--ling-warn`、`--ling-danger` | 6 |
| 字号 | `--ling-fs-sm`、`--ling-fs-md`、`--ling-fs-lg`、`--ling-fs-xl` | 4 |
| 间距 | `--ling-sp-1` 至 `--ling-sp-5` | 5 |
| 形状 | `--ling-radius`、`--ling-radius-sm`、`--ling-shadow` | 3 |

共 26 个。完整取值见 `docs/ling/builtin-plugins/core-ui/04-详细设计/04-设计令牌与主题.md` §2。

为什么用变量而不是共享 CSS 类：变量只约束「色值与尺度」，不约束结构。插件用 `<div>` 还是 `<table>`、怎么排版，自己决定；只要颜色取自令牌，观感自然贴近。共享组件库会把插件锁死在 core-ui 的 DOM 结构上，版本一升就得跟着改。

### 10.3 主题 = 一套取值

```css
:root { --ling-bg:#ffffff; --ling-text:#1f2328; ... }
:root[data-theme="dark"] { --ling-bg:#1b1b1d; --ling-text:#e6e6e6; ... }
```

换主题就是换 `data-theme`，所有引用令牌的地方一起变。主题名存 `core-ui.theme`，由 `core-settings` 保管，与其他配置一样可导出、可还原。

面板怎么拿到令牌：`<link rel="stylesheet" href="/api/ui/theme.css">`。这个地址返回亮色与暗色两套令牌定义，`:root` 默认块取当前主题，免 token（§5.2 已说明面板带不了 token），响应头 `Cache-Control: no-store`。

为什么不把令牌塞进 `postMessage`：样式在首屏渲染前就要到位，等消息会先白闪一下（`CUI-REQ-023` 要求不白闪）。样式表由浏览器在解析 HTML 时同步加载，天然赶在首屏前。

### 10.4 被否决的主题方案

| 方案 | 否决理由 |
|---|---|
| 只支持一套固定主题 | 用户在暗环境下用亮色界面刺眼，且插件写死颜色的问题仍在 |
| 让用户自定义每个色值 | 配置项从 1 个变 20 多个，还要做取色器与对比度校验；1.1.0 只做两套预设 |
| 插件各自维护主题 | 每加一个插件就要维护一套配色，切主题要通知所有插件改自己的常量，必然不一致 |
| 用 CSS `@import` 从插件目录带主题 | 面板样式被插件控制，切换主题时无法统一 |

## 11. 前端技术

### 11.1 外壳不用框架

| 因素 | 判断 |
|---|---|
| 视图数量 | 一级界面 3 块加设置 6 个页签 |
| 数据来源 | 十来个接口，返回 JSON |
| 交互复杂度 | 列表、表单、确认框、拖分隔条 |
| 引入框架的代价 | 需要构建链（打包、依赖管理、产物嵌入 exe），构建链本身要维护 |

**结论：原生 DOM 加 `fetch`。** 1.0.0 已验证这套能撑起全部管理视图，1.1.0 新增的侧边栏、面板外框、分隔条拖拽都是几十行原生代码的量级。

### 11.2 面板不限技术

面板是独立网页，插件作者可以用任意框架，自己打包成一个 HTML 与它引用的静态文件。core-ui 只要求两件事：

1. 入口是一个 HTML 文件，路径写在 `[ui].entry`；
2. 通过 `postMessage` 与外壳通信，遵守七种消息格式。

这条边界让 core-ui 不必为插件的前端技术负责，插件也不必等 core-ui 升级。

## 12. 代价与已知不足

技术选择都有代价，以下四条是明确接受的：

| 代价 | 表现 | 缓解 |
|---|---|---|
| 拖拽不是跟手拖拽 | 面板 A 拖文件到面板 B，松手后才生效，拖动过程中 B 不知道有东西在靠近 | 由外壳统一接管拖动手势并转成 `event` 消息；将来若必须跟手，把面板渲染方式换成同页面组件，消息协议不变 |
| 面板不能直接用浏览器存储 | `localStorage` 在不透明源下不可用 | 面板的持久化数据本就该存在插件的配置里（`core-settings`），不该存在浏览器里 |
| 面板首屏多一次请求 | 主题样式表与自身资源各一次 | 本机请求，耗时可忽略 |
| 外壳代码量增长 | 新增侧边栏、面板管理、消息路由、主题 | 按 `04-详细设计` 的分层切开，每层单独文件 |
