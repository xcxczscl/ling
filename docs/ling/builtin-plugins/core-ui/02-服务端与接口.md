# core-ui 02 服务端与接口

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/builtin-plugins/core-ui/00-总览与边界.md`

本文回答：界面进程对外提供什么、怎么认证、怎么把界面上的点击变成内核调用。

---

## 1. 进程与端口

`core-ui` 是独立进程（侧车轨道），由宿主在装载时拉起。

| 项 | 规定 |
|---|---|
| 监听地址 | `127.0.0.1`，不可配置 |
| 端口 | 从 8010 起，占用则顺延，最多试到 8099 |
| 端口记录 | 写入 `registry.json` 的 `ui_port` 字段，`webui` 版靠它找到地址 |
| 与宿主的关系 | 单向客户端：它调管理端口，宿主不回调它 |

端口段 8010 至 8099 与管理端口的 7900 段分开，理由见 `docs/ling/04-详细设计/06-管理端口与命令行.md` §2.2：两段混用会让顺延逻辑互相抢端口。

## 2. 认证

### 2.1 口令从哪来

宿主启动界面进程时，把口令放进环境变量：

```bash
LING_UI_TOKEN=<与 session.json 相同的口令>
LING_UI_PORT=8010
LING_UI_ROOT=<数据根>
```

插件模式下界面进程**不读** `session.json`：口令由宿主经环境变量给，它不需要知道数据根在哪。

启动器模式（用户双击）下没有这个环境变量，口令只能从 `<数据根>/session.json` 读——这种情况下宿主正是它自己拉起的，数据根就是默认位置，读它不会引入额外的问题。两种模式的判定见 `docs/ling/builtin-plugins/core-ui/04-两种形态与启动.md` §4。

### 2.2 浏览器怎么通过认证

浏览器访问 `http://127.0.0.1:8010/?token=<口令>` 打开页面。页面把 token 记在 `sessionStorage`，之后每个 API 请求带 `Authorization: Bearer <token>`。

| 情形 | 处理 |
|---|---|
| 没有 token 参数、也没有已保存的 token | 显示「请从 ling 主程序打开界面」 |
| token 不对 | 返回 401，页面提示「口令已变，请重新从主程序打开」 |
| token 对 | 正常 |

token 只在内存与 `sessionStorage` 里，不写 Cookie、不落盘。关掉标签页就没了，下次从主程序重新打开。

### 2.3 为什么不做登录页

做登录页就要有「用户」这个概念，而 ling 没有用户。口令的意义是「证明你是本机上能读 `session.json` 的那个人」，不是「你是谁」。一个输入框反而会让人以为要设密码。

## 3. API

全部是 `POST /api/<动作>`，请求体与响应体都是 JSON。响应统一是：

```json
{"ok": true, "result": {...}}
{"ok": false, "error": {"code": "E_...", "message": "人话原因", "advice": "下一步"}}
```

`error` 的 `message` 与 `advice` 直接用命令行那套文案（`docs/ling/04-详细设计/06-管理端口与命令行.md` §4.4），界面不另写一份。

| 动作 | 参数 | 转成的内核方法 |
|---|---|---|
| `plugins` | 无 | `kernel.plugins` |
| `install` | `path` | `kernel.install` |
| `uninstall` | `id`、`purge` | `kernel.uninstall` |
| `enable` | `id` | `kernel.enable` |
| `disable` | `id` | `kernel.disable` |
| `logs` | `plugin`、`level`、`lines` | `kernel.logs` → `core-log.tail` |
| `config.list` | `prefix` | `core-settings.list` |
| `config.get` | `key` | `core-settings.get` |
| `config.set` | `key`、`value` | `core-settings.write` |
| `jobs.list` | 无 | `core-job.list` |
| `jobs.schedule` | 任务定义 | `core-job.schedule` |
| `jobs.cancel` | `name` | `core-job.cancel` |
| `orphans` | 无 | `core-plugin-manager.orphans` |

**界面不直连内核。** 每个动作都转成一次管理端口调用，走的是命令行用的那条路（`LING-REQ-072`）。这条决定了三件事：

1. 界面与命令行的行为永远一致，不会出现「命令行能装、界面装不了」。
2. 界面拿到错误码后直接用同一套文案，不另维护。
3. 内核加一个方法，界面与命令行各自决定要不要暴露，但底层只有一份实现。

### 3.1 静态资源

页面文件（HTML、CSS、JS）编译期嵌进可执行文件，运行时不再读磁盘。

理由：发布包只有一个 exe，不担心「前端文件被删了界面就白屏」；也不需要处理相对路径。

## 4. 启动与就绪

```
1. 宿主装载 core-ui，起进程，传三个环境变量
2. 界面进程绑定端口，写 registry.json 的 ui_port
3. 界面进程用 token 连管理端口，发一次 kernel.plugins 自检
4. 自检通过才算就绪；宿主收到就绪信号后广播 kernel.plugin.state activated
5. webui 版：宿主调系统默认浏览器打开 http://127.0.0.1:<ui_port>/?token=...
   desktop 版：进程自己创建 WebView2 窗口，加载同一个 URL
```

第 3 步的自检很重要：只绑上端口不代表能连上宿主。口令不对、宿主正在关闭，都会在这一步暴露，而不是等用户点了按钮才发现。

## 5. 失败处理

| 情形 | 行为 |
|---|---|
| 端口 8010 至 8099 全被占 | 进程退出，宿主标记 `core-ui` 启动失败，日志说明端口段占满 |
| 连不上管理端口 | 退出并说明；宿主 2 秒后重启它 |
| token 不对 | 同上（宿主重启界面时会换新 token） |
| 页面请求超时（5 秒） | 返回 504，界面提示「ling 没有响应，正在忙或已卡住」 |
| 界面进程崩溃 | 宿主按 `restart = on-crash` 重启，最多 3 次；第 3 次后停 |

连续三次失败就停，是因为反复重启一个起不来的进程只会刷日志。停下来之后 `ling plugins` 里能看到「启动失败」与原因。

## 6. 界面与命令行的取舍

| 事 | 界面 | 命令行 |
|---|---|---|
| 装插件 | 选目录 | 敲路径 |
| 看状态 | 卡片、颜色 | 表格 |
| 看日志 | 筛选、自动刷新 | 纯文本 |
| 改配置 | 表单 | 手编 JSON |
| 批量操作 | 多选 | 暂无（`core-plugin-manager` 的 `apply`） |
| 排障 | 看得到现象，看不到内核日志 | `ling logs` 直读文件 |

最后一行是刻意的：**界面不显示内核日志**。内核日志是「修宿主的工具」，不能依赖会坏掉的那个部件（`docs/ling/04-详细设计/06-管理端口与命令行.md` §8.2 的同一条原则）。界面崩了的时候，命令行还在。
