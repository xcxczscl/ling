## 1. 文件

### 1.1 位置与结构

```
<数据根>/settings.json
```

```json
{
  "schema_version": 1,
  "entries": {
    "demo-a.theme": {
      "v": "dark",
      "updated_at": "2026-10-31T17:20:11"
    },
    "demo-a.follow_symlinks": {
      "v": true,
      "updated_at": "2026-10-31T17:20:15"
    }
  }
}
```

| 字段 | 说明 |
|---|---|
| `schema_version` | 文件格式版本。当前 1 |
| `entries` | 键是 `<插件名>.<键名>`，值是 `v` 与 `updated_at` |
| `v` | 任意 JSON，原样存原样取，不解析 |
| `updated_at` | 本地时间，`YYYY-MM-DDTHH:MM:SS`，只用于展示 |

**键名里的点只用来分两段**：第一段是插件名，后面全部是键。所以 `demo-a.ui.theme` 的归属是 `demo-a`，键名部分是 `ui.theme`。允许插件自己用点分层，`core-settings` 不管。

### 1.2 为什么整份重写

每次写入都把整份文件重新序列化再替换。理由：

- 文件在几十 KB 量级，重写耗时以微秒计。
- 不会出现「改了一半」的中间状态——要么是旧文件，要么是新文件。
- 不需要为「哪一段在文件里的哪个偏移」做维护。

代价是写入成本与文件大小成正比。4 MB 上限就是为这条设的：再大就不能整份重写了。

### 1.3 原子替换

```
1. 序列化到内存
2. 写 settings.json.tmp
3. 刷盘
4. 用 tmp 替换 settings.json
```

第 4 步在两个平台写法不同：Windows 用 `MoveFileExA(..., MOVEFILE_REPLACE_EXISTING)`，其他平台用 `rename`。`std::filesystem::rename` 在 Windows 上不覆盖已存在的目标，直接用会失败。

中途崩溃的结果：要么 `settings.json` 还是旧的，要么已经是新的，不会出现半个文件。残留的 `.tmp` 下次写入时会被覆盖。

## 2. 五个方法

### 2.1 `core-settings.write`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `plugin` | 字符串 | 是 | 键的归属插件，由内核在转发时填，不由调用方自报 |
| `key` | 字符串 | 是 | 完整键，必须以 `<plugin>.` 开头 |
| `value` | 任意 JSON | 是 | 要存的值；`null` 表示删除这个键 |

返回 `{"key": "..."}`。

**`plugin` 由内核填**，这是键空间隔离能成立的关键：插件不能自称是别人。插件走的是 `Context::write_config`，内核知道它真实的编号。

### 2.2 `core-settings.get`

| 参数 | 类型 | 必填 |
|---|---|---|
| `key` | 字符串 | 是 |

返回 `{"key": "...", "value": <原值>, "found": true|false}`。

键不存在时 `value` 为 `null`、`found` 为 `false`，仍算成功。

### 2.3 `core-settings.list`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `prefix` | 字符串 | 否 | 只列这个前缀下的键，不给就列全部 |

返回 `{"keys": ["demo-a.theme", ...]}`，按字典序。

### 2.4 `core-settings.export`

无参数。返回整个 `settings.json` 的内容（与文件结构一致）。给备份用。

### 2.5 `core-settings.import`

| 参数 | 类型 | 必填 |
|---|---|---|
| `entries` | 对象 | 是 |

只补不覆盖：目标里已有的键跳过，返回 `{"added": <新增条数>}`。

## 3. 键空间

| 规则 | 违反时 |
|---|---|
| 键必须以 `<调用方插件名>.` 开头 | `E_NAMESPACE_VIOLATION` |
| 键总长不超过 128 字节 | `E_MANIFEST_INVALID` 那一类 |
| 只允许字母、数字、`_`、`-`、`.` | 同上 |
| 键不能为空、不能以点结尾 | 同上 |

`core-settings` 自己也是插件，它的前缀是 `core-settings.`。

## 4. 与账本的配合

账本不在本插件手里，在内核手里（`docs/ling/04-详细设计/03-上下文与效应账本.md` §6.2）。一次写入的完整路径：

```
插件 → Context::write_config(key, value)
  → 内核读旧值（调 core-settings.get）
  → 内核追加账本条目 ConfigWritten，记下旧值
  → 内核调 core-settings.write 落盘
插件卸载
  → 内核按倒序撤销
  → 撤销动作 = 调 core-settings.write 写回旧值（旧值为空则写 null 删键）
```

**为什么账本不放在本插件里**：`core-settings` 自己会被卸载。账本放在它手里，卸掉它之后所有配置效应就失去了撤销依据。放在内核手里，即使它不在，撤销仍能尝试；撤销时它不在，记 `E_UNDO_FAILED` 并保留现场。

## 5. 失败处理

| 情形 | 返回 | 副作用 |
|---|---|---|
| 缺 `key` 或 `value` | 错误码 | 无 |
| `key` 前缀不属于 `plugin` | `E_NAMESPACE_VIOLATION` | 无 |
| 序列化后超过 4 MB | `E_IO` | 文件不变 |
| 写临时文件失败 | `E_IO` | 文件不变，`.tmp` 残留到下次写入时被覆盖 |
| 替换失败 | `E_IO` | 旧文件仍在 |
| 读文件时语法错 | 成功（空配置） | **不覆盖原文件**，内核日志记 warn |
| `schema_version` 高于当前 | 激活失败 | 原文件不动，见 §6 |

「语法错按空配置继续」只影响本次运行的读取，不会把坏文件写回去——下一次写入才会覆盖它。这条要在日志里说清楚，否则用户会以为配置丢了。

## 6. 版本与迁移

`schema_version` 只有一个用途：防止旧版本覆盖新格式。

| 读到的版本 | 行为 |
|---|---|
| 等于 1 | 正常 |
| 缺失 | 按 1 处理 |
| 大于 1 | **拒绝装载本插件**，日志说明「配置文件由更高版本写入」，原文件不动 |
| 小于 1 | 不存在这种情况 |

拒绝装载而不是「按空配置继续」：按空配置继续会让用户以为配置消失了，而且下一次写入会把新格式的文件覆盖成旧格式，新版本的数据就没了。

`docs/ling/08-部署与发布.md` §5.2 的回滚流程依赖这条：降级回去时旧版本会拒绝装载 `core-settings`，用户能立刻看到「版本不兼容」，而不是配置被悄悄改写。
