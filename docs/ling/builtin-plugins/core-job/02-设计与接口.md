# core-job 02 设计与接口

> 状态：已定稿 | 最后更新：2026-10-31
> 上级：`docs/ling/builtin-plugins/core-job/00-总览与边界.md`

本文回答：三个方法的定义、cron 怎么写、到点靠什么驱动、错过怎么算。

---

## 1. 三个方法

### 1.1 `core-job.schedule`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | 字符串 | 是 | 任务名，在 `core-job.` 前缀下唯一；只允许字母、数字、`-`、`_` |
| `cron` | 字符串 | 是 | 五段表达式，见 §2 |
| `method` | 字符串 | 是 | 到点要调的方法，必须是完整方法名 |
| `args` | 任意 JSON | 否 | 调用时原样传给目标方法，默认 `null` |
| `catch_up` | 布尔 | 否 | 宿主停机期间错过的要不要补跑，默认 `false` |
| `enabled` | 布尔 | 否 | 默认 `true`；设为 `false` 是「保留定义但停用」 |

返回 `{"name": "...", "key": "core-job.<name>"}`。

登记动作是一次配置写入：值落到 `core-job.<name>` 键下，进账本。所以任务定义可导出、可还原、随卸载回退。

### 1.2 `core-job.cancel`

| 参数 | 类型 | 必填 |
|---|---|---|
| `name` | 字符串 | 是 |

把 `core-job.<name>` 写成 `null`，即删除该键（`docs/ling/builtin-plugins/core-settings/02-设计与接口.md` §2.1）。返回 `{"name": "..."}`。

### 1.3 `core-job.list`

无参数。返回本插件前缀下的全部任务：

```json
{
  "jobs": [
    {"name": "cleanup", "cron": "0 3 * * *", "method": "demo-a.cleanup",
     "catch_up": false, "enabled": true, "last_fired": "2026-10-31T03:00:00"}
  ]
}
```

`last_fired` 是**内存状态**，不落盘：重启后清空，第一次到点就触发。落盘的话，改系统时间或跨时区会让它变成错误的依据。

## 2. cron 表达式

五段，从左到右：**分、时、日、月、周**。不支持秒。

| 段 | 范围 |
|---|---|
| 分 | 0 至 59 |
| 时 | 0 至 23 |
| 日 | 1 至 31 |
| 月 | 1 至 12 |
| 周 | 0 至 6，0 是周日 |

每段支持四种写法：

| 写法 | 含义 | 例 |
|---|---|---|
| `*` | 任意值 | `* * * * *` 每分钟 |
| `n` | 单个值 | `0 3 * * *` 每天 03:00 |
| `a-b` | 闭区间 | `0 9-18 * * *` 每天 9 点到 18 点整 |
| `*/n` | 每 n 个单位 | `*/15 * * * *` 每 15 分钟 |
| `a,b,c` | 列举 | `0 8,12,18 * * *` 每天三次 |

**不支持** `L`、`W`、`#`、`?` 这些扩展语法。理由：它们各自解决特定日历问题（月末、第几个周几），实现与测试成本远高于收益，而实际需求里没有。

「日」与「周」同时限定时按**或**处理（与常见 cron 一致）：`0 0 1 * 1` 表示「每月 1 号或每周一」。两者都是 `*` 时不做额外约束。

解析失败时的错误信息要指出段名与合法范围：

```
E_MANIFEST_INVALID cron 的「时」段取值 25 超出范围 0 至 23
```

## 3. 任务存储

任务定义不是本插件的私有文件，而是配置项：

```
settings.json
  entries:
    "core-job.cleanup": {"v": {"cron": "0 3 * * *", "method": "...", ...}, "updated_at": "..."}
```

好处有三个：可导出（`core-settings.export`）、可还原（账本撤销）、删掉本插件不丢（重装后读回来）。

启动时本插件调 `core-settings.list(prefix="core-job.")` 拿到全部键，逐个 `get` 读出定义，建内存索引。之后每次 `list` 读内存，不再查配置。

## 4. 到点靠什么驱动

### 4.1 为什么不用线程

`00-总览与边界.md` §4 已经说了：插件线程调 `call` 会与内核写表并发，属于数据竞争。这里给替代方案。

### 4.2 内核广播 `kernel.tick`

宿主主循环（`main/app/main.cpp` 里 `server.poll(200)` 那一轮）每 200 毫秒广播一次：

```json
{"topic": "kernel.tick", "payload": {"now": "2026-10-31T18:30:00", "epoch_ms": 1793...}}
```

`core-job` 在激活时订阅 `kernel.tick`，回调里做三件事：

```
1. 取 payload 的 now，精确到分钟
2. 与内存里的 last_fired 比，同一分钟就返回（200 毫秒一次回调，一分钟会被叫 300 次）
3. 逐个任务判断：enabled？cron 匹配当前分钟？正在跑？
```

全部发生在内核线程上，与路由表的读写同一个线程，不存在并发。

### 4.3 需要改哪里

| 改哪 | 改什么 |
|---|---|
| `docs/ling/04-详细设计/01-内核四服务.md` §6.4 | 新增第三类内核事件 `kernel.tick`，给出字段 |
| 宿主主循环 | 每轮 `poll` 之后广播一次 tick |

这两处都不改插件接口。用事件而不是新增函数表入口，是因为事件机制已经有了，且插件订阅内核事件的能力在 `04/01` §6.1 修订后已经打通。

**为什么不新增 `register_tick` 函数**：那要给 `ling_host_api` 加字段。能不加就不加——每加一个边界字段，将来侧车轨道的协议就要跟着多一条消息。

## 5. 错过与并发

### 5.1 判断「到点」

一次 tick 里对每个任务判断：当前分钟是否匹配 cron，且与 `last_fired` 不是同一分钟。

这样 200 毫秒一次的 tick 不会让同一分钟内的任务重复触发。

### 5.2 宿主停机期间错过

启动时读一次当前时间，与任务的 cron 比较：

| 情形 | 默认 | `catch_up = true` |
|---|---|---|
| 上一个应触发的时间点早于启动时间 | 不补 | 补跑一次 |
| 错过多次 | 不补 | 只补最近一次 |

只补最近一次是刻意的：停机一周后补跑七次，跟一次性跑七次没区别，只会把宿主启动拖慢。

### 5.3 上一次还没结束

内存里每个任务有一个「正在跑」标记。到点时若标记为真：

- 跳过本次，记 warn，带任务名与已运行时长。
- 不排队。

标记在调用返回后清除。调用超时（30 秒）也算返回，标记一并清除。

### 5.4 任务执行

调用 `Context::call(method, args)`，全程在 tick 回调里同步执行。

这意味着**一个慢任务会拖住整个 tick**：它跑 30 秒，这 30 秒里别的任务都检查不到。这是同步模型的代价，与 `docs/ling/04-详细设计/01-内核四服务.md` §6.3 事件同步派发的取舍一致。要做并行就得引入线程，而线程正是 §4.1 要避开的。

实际影响：任务都是分钟级的，30 秒的延迟落在同一分钟内，不影响下一次判断。

## 6. 失败处理

| 情形 | 返回 | 副作用 |
|---|---|---|
| 缺 `name`、`cron`、`method` | 错误码 | 无 |
| 名字含非法字符 | 错误码 | 无 |
| cron 解析失败 | `E_MANIFEST_INVALID`，说明哪一段 | 无 |
| 同名任务已存在 | `E_PLUGIN_EXISTS` 那一类 | 原定义不变 |
| 取消不存在的任务 | 成功（幂等） | 无 |
| 写配置失败（`core-settings` 不在） | `E_PLUGIN_MISSING` | 无 |
| 触发时目标未激活 | 成功（tick 内部处理） | 记 warn |
| 触发时调用失败 | 成功（tick 内部处理） | 记 warn，带错误码 |

最后两行：tick 回调不向内核返回错误，因为它是批量处理，一个任务失败不该让整轮停止。
