# core-ui 03 架构设计

> 状态：初定 | 版本：1.1.0-b1 | 最后更新：2026-11-02
> 详细版：`docs/ling/builtin-plugins/core-ui/03-架构设计.md`

## 1. 分四块

| 层 | 跑在哪 | 是什么 | 可信度 |
|---|---|---|---|
| 外壳 | 浏览器（或 WebView2）里的一个文档 | 侧边栏、功能区、面板外框、设置二级界面，持有 token | 可信 |
| 面板 | 同一个浏览器里的 iframe | 插件自己写的网页 | 不可信 |
| 服务端 | `core-ui` 进程 | 发外壳与面板资源；`/api/*` 转管理端口 | 可信 |
| 宿主适配 | `core-ui` 进程内 | 管理端口客户端：建连、认证、帧收发、错误翻译 | 可信 |

插件本体不在四块里，它跑在自己的进程，core-ui 经宿主间接调用。

## 2. 全景图

![core-ui 四层通信链路](assets/四层通信链路.svg)

三道边界：

| 边界 | 在哪两者之间 | 靠什么守住 |
|---|---|---|
| 源边界 | 外壳 ↔ 面板 | `sandbox` 不授予同源；面板读不到外壳存储，发不出有效请求 |
| token 边界 | 浏览器 ↔ 服务端 | `/api/*` 校验 bearer token；面板资源与主题样式表例外 |
| 能力边界 | 宿主 ↔ 插件 | 每个方法过能力校验与命名空间校验 |

面板的每条调用都要穿过这三道边界。

## 3. 外壳

### 3.1 由什么组成

| 文件 | 职责 | 大小量级 |
|---|---|---|
| `shell.html` | 骨架：侧边栏、功能区、设置容器 | 100 行以内 |
| `shell.css` | 布局与令牌引用，不写死颜色 | 400 行 |
| `shell.js` | 导航、初始化、设置页挂载 | 600 行 |
| `panels.js` | 面板管理（增删、宽度、恢复）与消息路由 | 400 行 |
| `theme.js` | 主题应用、`theme.css` 拉取、切换广播 | 120 行 |
| `views/*.js` | 六个管理页签 | 每个 150 至 400 行 |

单页应用，切换不刷新——刷新会丢掉所有已开面板的状态。

### 3.2 三个职责

| 职责 | 具体做什么 |
|---|---|
| 渲染 | 按插件列表生成侧边栏入口；按打开集合生成面板与外框；设置按页签切换 |
| 消息路由 | 收 `call`、校验命名空间、代发请求、回结果；广播 `theme` 与 `event` |
| 状态管理 | 维护打开集合、各面板宽度、侧边栏状态，写回 `core-settings` |

### 3.3 不做什么

不解析插件的业务数据。`rm.scan` 返回什么、面板怎么画，外壳不关心，只做原样转发。

## 4. 面板

### 4.1 一份网页

```
plugins/resources-manager/
├─ plugin.toml          [ui] entry = "ui/index.html"
└─ ui/
   ├─ index.html
   ├─ style.css
   └─ app.js
```

### 4.2 与外界的唯一接口

| 事 | 怎么做 |
|---|---|
| 收外壳消息 | `window.addEventListener("message", ...)` |
| 发调用请求 | `parent.postMessage({type:"call", ...}, "*")` |
| 取主题 | `<link rel="stylesheet" href="/api/ui/theme.css">` |

`targetOrigin` 必须是 `"*"`：面板是不透明源，无法指定具体 origin。安全性靠外壳校验 `event.source` 是否为已知 iframe 的 `contentWindow`。

## 5. 服务端

### 5.1 四类路由

| 路由 | 认证 | 谁用 |
|---|---|---|
| `GET /`、`/shell.*`、`/views/*` | 无 | 浏览器首次加载外壳 |
| `GET /panel/<插件 id>/*` | 无 | iframe 加载面板资源 |
| `GET /api/ui/theme.css` | 无 | 外壳与所有面板 |
| `POST /api/*` | bearer token | 外壳 |

免认证的三类只返回静态文件，不含秘密；有副作用的调用全在第四类。

### 5.2 一层薄代理

```
POST /api/plugins → kernel.plugins → JSON
POST /api/panel/call {plugin, method} → 校验命名空间 → kernel.call → JSON
```

`/api/panel/call` 比 1.0.0 的 `/api/<动作>` 多一步：校验 `method` 前缀等于 `plugin`。这是能力边界的第二道闸。

## 6. 宿主适配

只有四件事：建连与认证、请求响应配对、错误码翻译、断线提示。错误分三类显示：用户能解决的（原样显示 `message` 与 `advice`）、需要看日志的（附「看日志」按钮）、环境问题（侧边栏状态变红）。

## 7. 四条关键数据流

### 7.1 打开一个面板

```
1. POST /api/panels → 拿到带 [ui] 的插件列表
2. 侧边栏生成入口（无面板的插件不出现）
3. 用户点入口
4. 插入外框 + iframe src="/panel/<id>/<entry 去掉 ui/ 前缀>"
5. 服务端读 <插件目录>/ui/ 下的文件
6. iframe load → 外壳 postMessage {type:"init", pluginId, theme, tokens}
7. 面板开始渲染
```

### 7.2 面板调一个方法

```
面板 {type:"call", id:7, method:"rm.scan"}
外壳 按 event.source 取 pluginId → 前缀不符回 E_UI_FORBIDDEN
外壳 POST /api/panel/call {plugin, method, params} + token
服务端 再校验前缀 → kernel.call → 宿主路由到插件进程
外壳 {type:"result", id:7, ok:true, result:{...}}
```

### 7.3 换主题

```
1. 设置 → 外观 → 选暗色
2. POST /api/config.set {key:"core-ui.theme", value:"dark"}
3. 外壳自己设 data-theme="dark"
4. 向每个面板广播 {type:"theme", theme, tokens}
5. 面板改自己的 data-theme
```

### 7.4 插件被停用

```
1. 发现状态变化
2. 找到该插件的面板
3. 发 {type:"shutdown", reason:"disabled"}，300 毫秒后移除 iframe
4. 侧边栏入口变淡保留（卸载才移除）
5. 提示「插件已停用：<名称>」
```

## 8. 状态与存储

### 8.1 存在哪

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `core-ui.theme` | 字符串 | `light` | `light` 或 `dark` |
| `core-ui.sidebar` | 布尔 | `true` | 侧边栏是否展开 |
| `core-ui.layout` | 对象 | `{}` | `{"order":["rm","plr"],"widths":[0.5,0.5]}` |
| `core-ui.close_behavior` | 字符串 | `keep-host` | `keep-host` 或 `stop-host` |
| `core-ui.window` | 对象 | 无 | desktop 窗口位置与大小 |

`core-settings` 没装时退化为内存态，界面照常可用。

### 8.2 内存态

| 状态 | 生命周期 | 丢了会怎样 |
|---|---|---|
| 已打开面板集合 | 当前会话，写回 `core-ui.layout` | 重启后按上次恢复 |
| 进行中调用（`id` 到回调） | 单次调用 | 结果丢失，面板显示「没有响应」 |
| 宿主是否在线 | 每 5 秒探测 | 显示旧值，点操作报错 |
| 带面板插件的状态表 | 每 2 秒按 TTL 重读 | 停用或卸载后 2 秒内界面没反应 |

### 8.3 面板自身状态

面板的选中项、滚动位置由面板自己管。1.1.0 不提供跨会话恢复：面板刷新或重开即初始状态。

## 9. 错误模型

| 错误码 | 谁产生 | 含义 | 外壳怎么处理 |
|---|---|---|---|
| `E_UI_FORBIDDEN` | 外壳、服务端 | 面板调了不属于自己的方法 | 回失败结果，记 warn |
| `E_UI_PANEL_DECL` | 装载器 | `[ui]` 字段缺失或非法 | 装载失败，写明字段名 |
| `E_UI_PANEL_NOTFOUND` | 服务端与外壳预检 | 入口文件不存在 | 外框内显示错误与「重试」 |
| `E_UI_NOT_READY` | 外壳 | `init` 之前发 `call` | 回 `result` 失败并记 warn，不报给用户 |
| `E_UI_BUSY` | 外壳 | 单面板在途请求超 16 条 | 立即回失败，面板应降并发 |

`E_UI_` 前缀已在 `docs/ling/plugin-support/01-插件装载与接口.md` §5.2 登记。

## 10. 为什么不多分层

面板生命周期独立成 `panels.js`（约 400 行）：它是外壳里唯一碰 `event.source` 与 `postMessage` 的文件，越权校验只出现在一处，审代码时按文件勾。设置二级界面则相反：六个页签各一个文件，由 `shell.js` 统一挂载，不引入路由库。
