## 2. 插件目录形态

### 2.1 数据根与插件目录

```
<数据根>/                         Windows: %APPDATA%\ling
                                  Linux:   ~/.local/share/ling
                                  Android: 应用私有目录
├── registry.json                 宿主级配置：端口、禁用名单、能力撤销名单
├── session.json                  管理端口口令，权限 0600
├── logs/
│   ├── kernel-2026-10-28.log    内核日志，按天分文件
│   └── <编号>-2026-10-28.log     插件日志，由 core-log 写
└── plugins/
    └── <编号>/                   目录名必须等于清单 id
        ├── plugin.toml           清单，它存在即视为已安装
        ├── <编号>.dll 或 .so     进程内轨道的产物
        ├── 或 sidecar/           侧车轨道的产物目录，含可执行文件
        └── data/                 插件自己的数据，卸载默认保留
```

三条硬规则：

| 规则 | 依据 |
|---|---|
| 目录名与清单 `id` 完全一致，大小写敏感 | `LING-REQ-001` |
| `plugin.toml` 存在即视为已安装；只剩 `data/` 的目录算未安装，可重装并沿用数据 | `LING-REQ-011` |
| 卸载只删安装工件，`data/` 默认保留，`--purge` 才一起删 | `LING-REQ-010` |

### 2.2 一个插件只有一种产物

| 组合 | 结果 |
|---|---|
| 只有 `<编号>.dll` 或 `<编号>.so`，清单无 `[sidecar]` 段 | 进程内轨道 |
| 只有 `[sidecar]` 段且 `executable` 指向的文件存在 | 侧车轨道 |
| 动态库与 `[sidecar]` 段都有 | 拒绝装载，`E_MANIFEST_INVALID` |
| 两者都没有 | 拒绝装载，`E_MANIFEST_INVALID` |

「清单写了 `[sidecar]` 但文件不存在」也算后者。判定先看清单再验文件：清单写法决定轨道，文件存在性只影响能否装载成功。

### 2.3 安装来源

两种来源：目录与 zip 包。

| 来源 | 处理 |
|---|---|
| 目录 | 校验目录内清单后，整目录复制到 `plugins/<编号>/` |
| zip 包 | 解压到临时目录，校验后整目录复制到 `plugins/<编号>/`，再删临时目录 |

一律复制，不建符号链接、不引用原位置。这样删掉原位置不影响已装插件（`LING-REQ-007`）。

安装前检查 `plugins/<编号>/` 是否已存在：存在则拒绝并提示先卸载或升级（`LING-REQ-009`）。

## 3. 清单字段全集

清单文件为 `plugin.toml`，TOML 格式。

### 3.1 必填字段

| 字段 | 类型 | 格式 | 校验规则 | 依据 |
|---|---|---|---|---|
| `id` | 字符串 | `^[a-z0-9][a-z0-9-]*$`，长度 2 至 64 | 不匹配则拒绝；必须等于目录名 | 001、003 |
| `version` | 字符串 | 三段式 `主.次.修`，每段 0 至 65535 | 段数不对或越界则拒绝；宿主不限制递增方式 | 004 |
| `api` | 字符串 | 主版本号，如 `"1"` | 必须等于宿主支持的主版本或前一版本，否则 `E_API_MISMATCH` | 005、086 |
| `name` | 字符串 | 1 至 64 字符，可含中文 | 缺失则拒绝，报缺该字段 | 002 |

四个必填，缺任一项拒绝装载，错误信息里写明缺的是哪个（`LING-REQ-002`）。

### 3.2 可选字段

| 字段 | 类型 | 默认 | 说明 | 依据 |
|---|---|---|---|---|
| `min_host` | 字符串 | 空，表示不限制 | 要求的最低宿主版本；低于要求时拒绝并返回 `E_HOST_TOO_OLD`，信息含双方版本号 | 127 |
| `requires.plugins` | 字符串数组 | 空 | 插件依赖，写法见 §3.3 | 039、040 |
| `sidecar.executable` | 字符串 | 无 | 侧车可执行文件相对路径，必须位于插件目录内 | 006 |
| `sidecar.restart` | 字符串 | `on-crash` | 取 `on-crash`、`always`、`never` | 065 |
| `sidecar.idle_timeout` | 整数，秒 | 60 | 无调用多久后退出，仅对按需侧车生效 | 本文新增 |
| `capabilities` | 字符串数组 | 空 | 声明需要的能力，取值必须是 `fs`、`network`、`ui`、`shell` 之一 | 023 |
| `description` | 字符串 | 空 | 一句话说明，仅供 `ling plugins` 展示 | 本文新增 |

### 3.3 `requires` 段

```toml
[requires]
plugins = ["core-ui@1", "resources-manager@1.2"]
```

版本写法四种，判定规则是「约束的每一段与目标版本的同段逐一相同」：

| 写法 | 匹配 | 不匹配 |
|---|---|---|
| `@1` | 1.4.2 | 2.0.0 |
| `@1.2` | 1.2.9 | 1.3.0 |
| `@1.2.3` | 只匹配 1.2.3 | 1.2.4 |
| 无版本 | 任意版本 | —— |

### 3.4 校验顺序

装载时按此顺序校验，遇第一个失败即停，错误信息用第一条失败的：

| 序 | 校验 | 失败错误码 |
|---|---|---|
| 1 | 目录名等于 `id` | `E_MANIFEST_INVALID` |
| 2 | 四个必填字段齐全 | `E_MANIFEST_INVALID` |
| 3 | `id` 格式与长度 | `E_MANIFEST_INVALID` |
| 4 | `version` 三段式且每段在范围内 | `E_MANIFEST_INVALID` |
| 5 | `api` 在支持范围 | `E_API_MISMATCH` |
| 6 | `min_host` 不高于当前宿主版本 | `E_HOST_TOO_OLD` |
| 7 | 清单内没有绝对路径与 `..` | `E_MANIFEST_INVALID` |
| 8 | 产物组合合法（§2.2） | `E_MANIFEST_INVALID` |
| 9 | `sidecar.executable` 在插件目录内且可执行 | `E_MANIFEST_INVALID` |
| 10 | `capabilities` 取值都在能力集内 | `E_CAPABILITY_UNKNOWN` |

第 5 步在第 6 步之前：`api` 不兼容是协议层问题，`min_host` 是版本策略问题，先报更根本的那个。

### 3.5 两份示例

进程内插件：

```toml
id = "demo-a"
version = "1.0.0"
api = "1"
name = "示例插件 A"
capabilities = ["fs"]
description = "演示进程内轨道"

[requires]
plugins = ["core-ui@1"]
```

侧车插件：

```toml
id = "demo-b"
version = "0.2.1"
api = "1"
name = "示例插件 B"
capabilities = ["network"]

[requires]
plugins = ["demo-a@1"]

[sidecar]
executable = "sidecar/demo-b"
restart = "on-crash"
idle_timeout = 30
```

## 4. C ABI 函数表

### 4.1 三个结构体

```c
/* 边界版本：宿主与插件必须一致，否则拒绝装载 */
#define LING_ABI_VERSION 1

typedef struct {
    uint32_t    abi_version;
    const char* plugin_id;        /* 必须等于清单 id */
    const char* plugin_version;
    const char* api;              /* 接口主版本 */
} ling_plugin_descriptor;

typedef struct {
    uint32_t struct_size;         /* 本结构的字节数，用于向后兼容扩字段 */
    void*    (*context_alloc)(const char* plugin_id, uint64_t generation);
    int32_t  (*register_method)(void* ctx, const char* name, void* fn,
                                void* undo_fn, uint32_t requires_mask);
    int32_t  (*unregister_method)(void* ctx, const char* name);
    int32_t  (*subscribe)(void* ctx, const char* pattern, void* fn,
                          void* undo_fn, uint64_t* out_sub_id);
    int32_t  (*unsubscribe)(void* ctx, uint64_t sub_id);
    int32_t  (*call)(void* ctx, const char* method,
                     const uint8_t* args, size_t args_len,
                     uint8_t** out, size_t* out_len);
    int32_t  (*emit)(void* ctx, const char* topic,
                     const uint8_t* payload, size_t len);
    int32_t  (*write_config)(void* ctx, const char* key,
                             const uint8_t* value, size_t len);
    const char* (*data_dir)(void* ctx);
    void     (*free_buffer)(void* ctx, uint8_t* p, size_t len);
} ling_host_api;

/* 插件唯一导出的符号 */
int32_t ling_plugin_entry(const ling_host_api* host,
                          ling_plugin_descriptor* out_desc,
                          void** out_plugin);
```

三个结构体的关系：宿主给插件一张函数表（`ling_host_api`），插件回给宿主一个描述符（`ling_plugin_descriptor`）与一个不透明句柄（`out_plugin`），之后所有交互都经这张表，插件不再导出第二个符号。

### 4.2 类型与内存归属

| 规则 | 内容 |
|---|---|
| 只允许定宽类型 | `int32_t`、`uint32_t`、`uint64_t`、`size_t`、指针、`const char*` |
| 缓冲区用「指针 + 长度」 | 不以 0 结尾的字符串传二进制；含 0 字节的载荷必须带长度 |
| 谁申请谁释放 | 宿主给的缓冲区由插件调 `free_buffer` 释放；插件给的由插件自己的释放函数回收 |
| 字符串编码 | `const char*` 一律 UTF-8，不以 0 结尾的场合必须同时给长度 |
| 不许跨边界抛异常 | 所有函数返回 `int32_t` 错误码，0 表示成功 |
| 不许跨边界传 C++ 类型 | 无 `std::string`、`std::vector`、虚表指针、引用 |

`struct_size` 的作用：将来给 `ling_host_api` 扩字段时，老插件读到的是旧长度，新宿主按长度判断哪些字段可用，不必升 `abi_version`。真正的破坏性改动（改字段含义、删字段）才升版本。

### 4.3 版本协商

装载时的检查顺序：

1. 调 `ling_plugin_entry`，传入宿主函数表。
2. 读回 `out_desc->abi_version`，与 `LING_ABI_VERSION` 比较，不相同则拒绝装载，错误码 `E_API_MISMATCH`，信息带双方版本。
3. 比对 `out_desc->plugin_id` 与清单 `id`，不相同则拒绝，错误码 `E_MANIFEST_INVALID`。

第 3 步不能省：清单与代码里的编号不一致时，路由表会把方法挂到错误的编号下。

### 4.4 函数表逐项

| 函数 | 谁调 | 返回值 | 失败时 |
|---|---|---|---|
| `context_alloc` | 宿主在 activate 前调 | 插件侧上下文指针 | 返回空表示失败，拒绝激活 |
| `register_method` | 插件 | 0 或错误码 | 见 `04/01` §5.1 六项校验 |
| `unregister_method` | 宿主撤销时调，插件也可主动撤 | 0 或错误码 | 见 `04/01` §5.2 |
| `subscribe` | 插件 | 0 或错误码 | 见 `04/01` §6.1 |
| `unsubscribe` | 宿主撤销时调 | 0 或错误码 | —— |
| `call` | 插件 | 0 或错误码，结果放 `out` | 见 `04/01` §5.3 |
| `emit` | 插件 | 0 或错误码 | 见 `04/01` §6.3 |
| `write_config` | 插件 | 0 或错误码 | 由 core-settings 提供，见 `04/07` |
| `data_dir` | 插件 | `plugins/<编号>/data/` 的绝对路径，UTF-8 | 返回空表示路径不可用 |
| `free_buffer` | 插件 | 无 | —— |

`requires_mask` 是位集：`fs = 1`、`network = 2`、`ui = 4`、`shell = 8`。

`generation` 由宿主生成，插件原样存着并在每次回调里带回，用于 `04/01` §5.3 第 7 步的旧回调拦截。

## 5. 错误码登记表

### 5.1 分族规则

错误码格式 `E_<族>_<具体>` 或 `E_<具体>`。族按职责分：

| 族 | 前缀 | 归属 |
|---|---|---|
| 清单 | `E_MANIFEST_` | 清单格式与路径 |
| 版本 | `E_API_`、`E_HOST_` | 协议版本与宿主版本 |
| 命名 | `E_NAMESPACE_` | 方法名与主题前缀 |
| 能力 | `E_CAPABILITY_` | 能力声明与生效 |
| 插件 | `E_PLUGIN_` | 插件存在性与状态 |
| 方法 | `E_METHOD_` | 方法注册与调用 |
| 依赖 | `E_DEPENDENCY_` | 依赖图 |
| 重载 | `E_RELOAD_` | 热更新 |
| 账本 | `E_LEDGER_`、`E_UNDO_` | 账本与撤销 |
| 协议 | `E_AUTH`、`E_PROTOCOL`、`E_PAYLOAD_` | 端口与侧车通信 |
| 系统 | `E_IO`、`E_INTERNAL`、`E_SHUTTING_DOWN`、`E_TIMEOUT` | 宿主自身 |

新增错误码必须归入已有族；需要新族时先改本节。

### 5.2 全表

24 个，全项目只允许出现这些取值。

| 错误码 | 含义 | 触发场景 | 首次出现 |
|---|---|---|---|
| `E_MANIFEST_INVALID` | 清单非法 | 缺字段、格式错、目录名不符、路径穿越、产物组合非法、描述符编号不符 | 001 |
| `E_API_MISMATCH` | 接口版本不匹配 | `api` 超出支持范围，或 `abi_version` 不相同 | 005 |
| `E_HOST_TOO_OLD` | 宿主版本过低 | `min_host` 高于当前宿主版本 | 127 |
| `E_NAMESPACE_VIOLATION` | 命名越权 | 方法名或主题没带自己的前缀，或占用 `kernel.` | 014 |
| `E_CAPABILITY_UNKNOWN` | 能力不认识 | 清单声明了能力集外的取值 | 023 |
| `E_CAPABILITY_DENIED` | 能力不足 | 声明超出清单、生效能力不足、归属不符 | 024 |
| `E_PLUGIN_MISSING` | 插件不存在或不可用 | 未安装、未激活、重载窗口内、`generation` 过期 | 016 |
| `E_PLUGIN_EXISTS` | 插件已存在 | 安装的编号已有目录 | 009 |
| `E_METHOD_MISSING` | 方法不存在 | 方法未注册或已注销 | 016 |
| `E_DUPLICATE_METHOD` | 方法名重复 | 同一完整方法名二次注册 | 04/01 §5.1 |
| `E_DEPENDENCY_CYCLE` | 依赖成环 | 依赖图有环，`detail` 给完整环路 | 043 |
| `E_RELOAD_FAILED` | 重载失败已回滚 | 新版装载或激活失败 | 055 |
| `E_LEDGER_INVALID` | 账本条目非法 | 撤销函数或处理函数为空 | 029 |
| `E_UNDO_FAILED` | 撤销失败 | 某条撤销执行报错，卸载继续 | 013 |
| `E_UNINSTALL_INCOMPLETE` | 卸载不完整 | 存在未撤销条目，`detail` 给清单 | 013 |
| `E_AUTH` | 认证失败 | 首帧口令不正确 | 070 |
| `E_PROTOCOL` | 协议错误 | 帧不是合法 JSON、跨行 JSON、缺 `op` 或 `v` | 061 |
| `E_PAYLOAD_TOO_LARGE` | 载荷超限 | 调用参数或事件载荷超过 1 MB | 097 |
| `E_TIMEOUT` | 超时 | 调用超 30 秒，或侧车 5 秒未应答 | 017 |
| `E_IO` | 文件读写失败 | 清单读不到、目录不可写、产物复制失败 | 074 |
| `E_INTERNAL` | 宿主内部错误 | 快照不变式校验失败这类自身问题 | 04/01 §5.5 |
| `E_SHUTTING_DOWN` | 正在关闭 | 关闭过程中拒绝新请求 | 04/01 §8.2 |
| `E_LEDGER_FULL` | 账本条目达到上限 | 当前激活代已登记 10000 条 | 100 |
| `E_CANCELLED` | 操作被取消 | 调和执行中被取消，已执行的步骤回滚 | 048 |

### 5.3 错误结构

对外统一为：

```json
{"ok": false, "error": {"code": "E_MANIFEST_INVALID", "message": "缺少必填字段 version", "detail": {"field": "version", "path": "/plugins/demo-a/plugin.toml"}}}
```

| 字段 | 必填 | 内容 |
|---|---|---|
| `code` | 是 | 上表取值之一，不允许自由文本 |
| `message` | 是 | 一句可读的话，含出错对象的名字 |
| `detail` | 否 | 结构化补充，如缺的字段名、环路、未撤销条目清单 |

C ABI 侧没有 JSON，返回 `int32_t` 错误码 + 一个查询接口取最近一次错误的 `message` 与 `detail`（`Context` 的扩展见 `04/03`）。

## 6. 装载流程

### 6.1 进程内轨道

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 校验清单（§3.4 十步） | 返回对应错误码，不装载 |
| 2 | 把动态库复制为私有文件名 `<编号>.<序号>.dll`，再打开副本 | `E_IO`，原件不动 |
| 3 | 解析 `ling_plugin_entry` 符号 | `E_MANIFEST_INVALID`（产物不是 ling 插件） |
| 4 | 调 `ling_plugin_entry`，比对 `abi_version` 与 `plugin_id` | `E_API_MISMATCH` 或 `E_MANIFEST_INVALID` |
| 5 | 调 `context_alloc` 拿插件上下文 | 返回空则 `E_INTERNAL` |
| 6 | 调 activate（经函数表或插件自报到），插件在此注册方法与订阅 | 注册失败则按账本回滚已注册项 |
| 7 | 装载表状态改 `Activated`，广播 `kernel.plugin.state` | —— |

第 2 步复制副本是热更新的前提（`LING-REQ-056`），细节在 `04/05`。

### 6.2 侧车轨道

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 校验清单 | 同上 |
| 2 | 选一个空闲回环端口，拼成 `tcp:127.0.0.1:<端口>` | 无空闲端口则 `E_IO` |
| 3 | 启动可执行文件，环境变量传 `LING_SOCKET` 与 `LING_TOKEN`（每次启动重新生成的随机串） | 启动失败则 `E_IO` |
| 4 | 等待侧车连接，上限 10 秒 | 超时则杀进程并返回 `E_TIMEOUT` |
| 5 | 首帧握手：侧车报 `{"op":"hello","v":1,"id":...}` | `v` 不符返回 `E_API_MISMATCH` 并断开 |
| 6 | 发 `activate`，侧车内注册方法与订阅 | 超时 10 秒则 `E_TIMEOUT` |
| 7 | 状态改 `Activated`，广播事件 | —— |

侧车是「先起进程再握手」，不是「先握手再起进程」：进程起来才知道它监听的端点，端点由宿主给，所以端口先选好再传进去。

### 6.3 失败回滚

任一轨道在第 6 步失败时：

1. 按账本倒序撤销本次激活登记的全部效应。
2. 进程内轨道：不 `dlclose`（理由见 `04/05` §2），只把装载表条目标记为 `Failed`。
3. 侧车轨道：结束进程。
4. 状态改 `Failed`，广播 `kernel.plugin.state`。
5. 返回首个失败的错误码。

## 7. 卸载流程

顺序固定（`LING-REQ-012`）：

| 步 | 动作 |
|---|---|
| 1 | 停用依赖它的下游插件（由调和计算，见 `04/04`） |
| 2 | 调 `on_deactivate`（`LING-REQ-036`） |
| 3 | 账本倒序逐条撤销 |
| 4 | 移出装载表、能力表、路由表、订阅表 |
| 5 | 删安装工件，保留 `data/`；带 `--purge` 连 `data/` 一起删 |
| 6 | 触发一次调和 |

第 3 步中某条撤销失败：记 `E_UNDO_FAILED`，继续执行其余条目，最后返回 `E_UNINSTALL_INCOMPLETE`，`detail` 列出未撤销条目（`LING-REQ-013`）。这种情况下安装工件**仍然删除**——保留一个装不回来的半成品目录，比删掉并保留数据更糟。

侧车轨道额外两步：撤销前先发 `deactivate`，给 5 秒宽限；没回 `deactivated` 则发 `shutdown`，再给 5 秒宽限，仍未退出则结束进程（`LING-REQ-066`）。

## 8. 侧车协议

### 8.1 帧格式

jsonl：每行一个 JSON 对象，UTF-8，以 `\n` 结尾。一行超过 1 MB 视为协议错误（`E_PROTOCOL`）。

公共字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `v` | 整数 | 是 | 协议版本，当前 1 |
| `id` | 整数 | 视消息 | 请求序号，响应带同一个 `id` |
| `op` | 字符串 | 是 | 消息类型 |
| `trace` | 字符串 | 否 | trace id，跨进程追踪用 |

响应帧统一为 `{"v":1,"id":7,"ok":true,"result":{...}}` 或 `{"v":1,"id":7,"ok":false,"error":{...}}`，错误结构同 §5.3。

### 8.2 侧车到宿主七种

| `op` | 何时发 | 字段 |
|---|---|---|
| `hello` | 连接后第一帧 | `v`、`plugin_id`、`plugin_version`、`token` |
| `register_method` | activate 期间 | `name`、`requires`（能力名数组） |
| `subscribe` | activate 期间 | `pattern` |
| `call` | 侧车要调别的插件 | `method`、`args`、`trace` |
| `emit` | 侧车要广播 | `topic`、`payload`、`trace` |
| `result` | 响应宿主的 `invoke` | `id`、`result` |
| `error` | 响应宿主的 `invoke` 或报自身错误 | `id`、`error` |
| `deactivated` | 收到 `deactivate` 且已清理完 | —— |

`register_method` 不带撤销函数：侧车交不出可调用指针。改为语义声明——宿主记下「这个侧车注册了 X」，卸载时由宿主代为注销（`LING-REQ-064`）。这是侧车轨道与进程内轨道在账本上的唯一差别。

### 8.3 宿主到侧车五种

| `op` | 何时发 | 字段 |
|---|---|---|
| `activate` | 装载时 | `plugin_id`、`generation`、`data_dir` |
| `invoke` | 有调用时 | `id`、`method`、`args`、`trace` |
| `event` | 订阅的主题有事件时 | `topic`、`payload`、`trace` |
| `deactivate` | 停用、卸载、重载时 | —— |
| `shutdown` | 强制结束前 | `reason` |

### 8.4 握手与认证

1. 侧车连上后立即发 `hello`，带 `v`、`plugin_id`、`plugin_version` 与 `token`。
2. 宿主先校验 `token`：与启动该侧车时经 `LING_TOKEN` 传入的值做常量时间比较，不符则回 `error`（`E_AUTH`）并断开，记 warn。
3. 再比对 `v` 与自身协议版本：不一致则回 `error`（`E_API_MISMATCH`）并断开，其他插件不受影响（`LING-REQ-087`）。
4. 比对 `plugin_id` 与清单一致。
5. 宿主发 `activate`，进正常消息循环。

第 2 步先于第 3 步：认证在前、协商在后，未通过认证的连接不能探测协议版本。

`LING_TOKEN` 每次启动侧车重新生成，不落盘，只经环境变量传递。用环境变量而不是命令行参数，是因为命令行参数在进程列表里对所有用户可见。理由与防护边界见 `docs/ling/06-安全设计.md` §3.6。

握手前宿主不接受任何其他 `op`，收到即 `E_PROTOCOL`。

### 8.5 崩溃与重启

侧车退出或断连时（`LING-REQ-065`）：

1. 按账本撤销其全部效应（宿主代为注销方法与退订）。
2. 广播 `kernel.plugin.state`，`state = crashed`，`reason` 带退出码或断开原因。
3. 按 `sidecar.restart` 决定：

| 取值 | 行为 |
|---|---|
| `on-crash`（默认） | 正常退出不重启；异常退出在 2 秒内重启一次，连续 3 次失败后进入 `Failed` 并停止重试 |
| `always` | 任何退出都重启，同样 3 次上限 |
| `never` | 保持停止，状态 `Failed` |

「2 秒内重启」与「3 次上限」是本文新增的可判定值，写入清单约束。

### 8.6 数据面不走控制面

控制面只传调用参数、事件载荷、状态。文件内容与大块二进制不放进 JSON 帧（`LING-REQ-067`）：侧车自己读写 `data_dir()` 下的文件，另一侧只传路径。

单条帧上限 1 MB，与控制面载荷上限一致（`LING-REQ-097`）。

### 8.7 常驻与按需

Python 侧车每个进程 25 至 40 MB，而 `LING-REQ-099` 给「内核加 20 个插件」的预算是 120 MB。因此侧车默认按需启停：

| 规则 | 内容 |
|---|---|
| 默认模式 | 按需：装载完成即退出，下次调用时再起 |
| 常驻白名单 | 清单里写 `sidecar.restart = "always"` 视为常驻 |
| 常驻数量上限 | 默认 1 个 Python 侧车；进程内不受此限 |
| 空闲退出 | 无调用超过 `idle_timeout` 秒（默认 60）后退出 |
| 首次调用代价 | 冷启动 200 毫秒左右，计入 `LING-REQ-095` 的启动预算 |

C++ 侧车（如 core-ui）每个进程约 10 至 15 MB，不受上述 1 个的限制，但同样计入总预算。

「常驻 1 个」是保守起点：真要放宽，改这一行并重测 `LING-REQ-099`，不影响其他条款。

## 9. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。
| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | `write_config` 的语义依赖 core-settings，而 core-settings 可被卸载 | 卸载 core-settings 后该函数返回 `E_PLUGIN_MISSING`，插件需自行处理 | §4.4、`04/07` |
| 2 | 侧车 `hello` 只带协议版本，没带能力声明 | 能力声明在 `register_method` 的 `requires` 里体现，`hello` 不重复 | §8.2 |
| 3 | 重启 3 次上限是本文新增，没有需求依据 | 保留，写入清单约束；如需调整改这里一处 | §8.5 **本期设定** |
| 4 | 错误码从 18 个扩到 22 个，新增四个的命名是否与将来冲突 | `E_PLUGIN_EXISTS`、`E_PROTOCOL`、`E_IO`、`E_UNINSTALL_INCOMPLETE` 已按族归位 | §5.2 |
