# ling 04/06 管理端口与命令行

> 状态：初定 | 最后更新：2026-10-28
> 依据：`docs/ling/01-需求规格.md` §3.8

管理端口是宿主唯一的对外通道：命令行与界面都经它管理宿主。本文定帧格式、认证、子命令与 `kernel.*` 方法的映射，以及「修宿主的工具不能依赖被修的对象」这条约束怎么落地。

## 2. 端口与认证

### 2.1 只绑回环

监听地址固定 `127.0.0.1`，不提供配置项，不允许绑 `0.0.0.0`（`LING-REQ-069`、`LING-REQ-115`）。

不提供配置项是刻意的：一旦可配，就会出现「为了局域网访问改成 0.0.0.0」的用法，而 ling 的威胁模型里没有任何一条覆盖局域网暴露。

### 2.2 端口选择

```
候选：7900, 7901, ... 7999
试第一个可绑定的端口 → 成功则用它并写入 registry.json
全部失败 → 启动失败，退出码 3，stderr 说明端口段被占满
```

写 `registry.json` 的字段：

```json
{"port": 7901, "pid": 48213, "started_at": "2026-10-28T17:02:11+08:00"}
```

命令行靠这份文件找端口，不扫端口。

### 2.3 `session.json`

| 项 | 规定 |
|---|---|
| 位置 | `<数据根>/session.json` |
| 内容 | `{"token":"<32 字节随机数的十六进制>"}` |
| 权限 | `0600`（仅当前用户可读写），Linux 与 Android 上由文件模式保证；Windows 上设置为仅当前用户可访问 |
| 生成时机 | 每次宿主启动重新生成，覆盖旧文件 |
| 生命周期 | 宿主退出时删除 |

每次启动重新生成，意味着上一个进程的 token 立即失效——多开场景下后启动的宿主会让先启动的失去控制，这是可接受的：ling 本来只允许一个实例。

### 2.4 认证

连接后第一帧必须是：

```json
{"op":"auth","token":"3f2a...","v":1}
```

| 情形 | 处理 |
|---|---|
| 口令正确 | 回 `{"v":1,"ok":true}`，进入正常命令循环 |
| 口令错误 | 回 `E_AUTH` 并立即断开 |
| 首帧不是 `auth` | 回 `E_AUTH` 并断开，不透露原因 |
| 连续 3 次错误 | 断开连接，同一来源 IP 延迟 1 秒后再接受新连接 |
| 认证超时 | 连接后 5 秒内未收到 `auth` 帧则断开 |

延迟 1 秒只对同一回环地址生效，作用是防止本地脚本疯狂重试刷日志，不是安全机制。

## 3. 帧格式

### 3.1 请求帧

```json
{"v":1,"id":1,"op":"call","method":"kernel.plugins","args":{},"trace":"t-4f2a"}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | 是 | 协议版本，当前 1 |
| `id` | 是 | 请求序号，由客户端自增，应答带回同一个值 |
| `op` | 是 | 目前只有 `auth` 与 `call` 两种 |
| `method` | `call` 时必填 | 必须是 `kernel.*` 开头 |
| `args` | 否 | 方法参数，对象 |
| `trace` | 否 | trace id，用于把命令行操作串进内核日志 |

### 3.2 应答帧

```json
{"v":1,"id":1,"ok":true,"result":{"plugins":[...]}}
{"v":1,"id":1,"ok":false,"error":{"code":"E_PLUGIN_MISSING","message":"插件 demo-a 未安装","detail":{}}}
```

错误结构同 `04/02` §5.3。

### 3.3 版本不匹配

客户端 `v` 与宿主不同时：

- 宿主回 `E_API_MISMATCH`，`detail` 给双方版本，然后断开。
- 不影响其他已连接客户端与所有插件（`LING-REQ-087`）。

### 3.4 协议错误

| 情形 | 处理 |
|---|---|
| 帧不是合法 JSON | 回 `E_PROTOCOL`，断开 |
| 一帧跨多行 | 同左 |
| 单帧超过 1 MB | 回 `E_PAYLOAD_TOO_LARGE`，断开 |
| `op` 不认识 | 回 `E_PROTOCOL`，不断开 |
| `method` 不以 `kernel.` 开头 | 回 `E_NAMESPACE_VIOLATION`，不断开 |

「不断开」的两条是为了让客户端能继续试错；前三条说明这条连接上的数据已经不可靠，必须断开重连。

## 4. 子命令与 `kernel.*` 方法

### 4.1 映射表

| 子命令 | `kernel.*` 方法 | 走端口 |
|---|---|---|
| `serve` | —— | 否，本地启动宿主 |
| `shutdown` | `kernel.shutdown` | 是 |
| `plugins` | `kernel.plugins` | 是 |
| `install <路径>` | `kernel.install` | 是 |
| `uninstall <编号> [--purge]` | `kernel.uninstall` | 是 |
| `enable <编号>` | `kernel.enable` | 是 |
| `disable <编号>` | `kernel.disable` | 是 |
| `reload <编号>` | `kernel.reload` | 是 |
| `restart <编号>` | `kernel.restart` | 是 |
| `logs [编号] [--kernel]` | `kernel.logs` | 是 |
| `doctor` | `kernel.doctor` | 是 |
| `--version` | —— | 否，本地打印 |
| `--help` | —— | 否，本地打印 |

走端口的方法全部经同一条调用路由（`LING-REQ-072`），与插件方法用同一套机制：同一张路由表、同一套超时、同一套错误码。

`restart` 与 `reload` 的区别：`reload` 换版本，`restart` 只是停用再激活（不换产物）。两者在 `01` 的子命令表里都有，本文对齐。

### 4.2 退出码

| 码 | 含义 | 典型场景 |
|---|---|---|
| 0 | 成功 | —— |
| 1 | 检查发现问题 | `doctor` 发现环或未撤销条目 |
| 2 | 参数错误 | 缺编号、未知子命令、`--purge` 用在 `enable` 上 |
| 3 | 宿主不可达 | 端口段占满、`registry.json` 不存在、连接被拒 |
| 4 | 宿主返回错误 | 任意 `kernel.*` 方法返回非 0 |

`doctor` 用 1 而不是 4：它「成功执行了检查」，只是检查结果有问题。

### 4.3 输出格式

默认给人读：一行一条，含编号与状态。加 `--json` 时输出与端口应答相同结构的 JSON，供脚本处理。

```
$ ling plugins
demo-a        1.0.0   activated   process
demo-b        0.2.1   deactivated sidecar   缺 demo-a@1
core-ui       1.0.0   activated   sidecar
```

`--json` 输出：

```json
{"ok":true,"result":{"plugins":[{"id":"demo-a","version":"1.0.0","state":"activated","track":"process"}, ...]}}
```

## 5. 各子命令的行为

### 5.1 `serve`

启动宿主，前台运行，日志同时写 stderr 与文件。参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--port <n>` | 7900 | 起始端口，占用时仍按 §2.2 顺延 |
| `--log-level <级别>` | info | error / warn / info / debug |
| `--data-dir <路径>` | 平台默认 | 覆盖数据根，用于测试 |

`serve` 是唯一不连端口的子命令：它就是要起宿主。

### 5.2 `shutdown`

发 `kernel.shutdown`，宿主按 `04/01` §2.3 的七步关闭。命令等待到连接断开或 10 秒超时；超时返回退出码 4，提示「宿主未在 10 秒内退出，检查日志」。

### 5.3 `plugins`

列全部已安装插件。列：编号、版本、状态、轨道、未满足原因（有则显示）。

状态取值与装载表一致：`installed`、`activated`、`deactivated`、`failed`。**`Activating` 与 `Deactivating` 是瞬时状态，列表时不保证能看到**，因此不单列。

### 5.4 装载类子命令

一个表格说清六个：

| 子命令 | 参数 | 成功后 | 失败时 |
|---|---|---|---|
| `install <路径>` | 目录或 zip，`--no-activate` 可只装不激活 | 插件出现在列表，状态由调和决定 | 返回对应错误码，不留残件 |
| `uninstall <编号>` | 可选 `--purge` | 目录只剩 `data/`（或不存在） | 有未撤销条目时返回 `E_UNINSTALL_INCOMPLETE` 但工件仍删 |
| `enable <编号>` | 无 | 状态转 `activated` | 依赖不满足时仍成功，状态留 `deactivated` |
| `disable <编号>` | 无 | 状态转 `deactivated`，下游一起停 | 撤销失败记 `E_UNDO_FAILED` |
| `reload <编号>` | 新版本已就位 | 七步流程走完，版本号变化 | `E_RELOAD_FAILED`，已回滚 |
| `restart <编号>` | 无 | 停用再激活，版本不变 | 激活失败则回滚到停用前状态 |

`install` 与 `uninstall` 会等该轮调和结束再返回（`04/04` §7.2 最后一条），其他四个命令只等本次操作完成。

### 5.5 `logs` 与 `doctor`

`logs` 有两条路径（`LING-REQ-077`、`LING-REQ-119`）：

| 用法 | 走哪条 | 依赖 |
|---|---|---|
| `logs --kernel` | 直接读 `<数据根>/logs/kernel-YYYY-MM-DD.log` | **不依赖任何插件** |
| `logs <编号>` | `kernel.logs` → core-log | core-log 未安装时返回错误，`message` 含「core-log 未安装」 |

加 `--follow` 时持续输出（只对 `--kernel` 生效，插件日志由 core-log 决定是否支持）。

`doctor` 见 §7。

### 5.6 `--version` 与 `--help`

`--version` 打印宿主版本（`0.0.1-bN` 形式），不连宿主，不读数据根。

`--help` 打印子命令列表与每个命令的一行说明。参数错误时也打印这一段，退出码 2。

## 6. 命令行与宿主的连接

### 6.1 找端口与口令

```
1. 读 <数据根>/registry.json 拿 port
2. 读 <数据根>/session.json 拿 token
3. 连 127.0.0.1:port，5 秒超时
4. 发 auth 帧，等应答
5. 发 call 帧，按 §4.1 的方法名
```

数据根的顺序：`--data-dir` 参数 > 环境变量 `LING_DATA_DIR` > 平台默认。命令行与宿主必须用同一个数据根，否则会连到不同的实例。

### 6.2 宿主未运行时

| 情形 | 输出 | 退出码 |
|---|---|---|
| `registry.json` 不存在 | 「宿主未运行（找不到 registry.json）」 | 3 |
| 端口连接被拒 | 「宿主未运行（端口 7901 无响应）」 | 3 |
| `session.json` 不存在 | 「宿主正在启动或已退出」 | 3 |
| 认证失败 | 「口令不匹配，宿主已重启过」 | 4 |

第三条与第四条的区别要保留：前者是没拿到口令，后者是拿到了但不对，排查方向不同。

### 6.3 超时

| 阶段 | 超时 |
|---|---|
| 连接 | 5 秒 |
| 认证应答 | 5 秒 |
| 普通命令 | 30 秒（与 `LING-REQ-017` 一致） |
| `install` / `uninstall` / `reload` | 60 秒（等调和结束，比普通命令宽） |
| `shutdown` | 10 秒 |

超时返回退出码 4，`message` 写明是哪个阶段的超时。

## 7. `doctor`

### 7.1 四项检查

`LING-REQ-076` 定四项，只报告不改：

| 检查 | 判定 | 输出 |
|---|---|---|
| 依赖图环 | 用 `04/04` §4.3 的环检测 | 有环时列出环路；无环时一行「依赖图无环」 |
| 未撤销条目 | 扫描已停用插件的账本段，`count > 0` 视为未撤净 | 列出插件编号与条目数 |
| 端口与口令文件 | `registry.json` 的端口是否仍可连、`session.json` 权限是否为 0600 | 两项各一行 |
| 越权记录 | 内核日志中 `E_NAMESPACE_VIOLATION` 与越权注册尝试的条数 | 有则列出最近 10 条 |

### 7.2 退出码与输出

| 结果 | 退出码 |
|---|---|
| 四项全部正常 | 0 |
| 任一项发现问题 | 1 |
| 检查本身执行失败（如日志文件读不到） | 4 |

输出固定四段，每段一行结论加必要的明细。**不写「已修复」类内容**：`doctor` 只报告，不做自动修复（`LING-REQ-076`）。

## 8. 与插件的关系

### 8.1 命令行不依赖任何插件

`LING-REQ-075` 要求卸掉 core-ui 后命令行全部子命令仍可用。

| 能力 | 由谁提供 | 卸掉 core-ui 后 |
|---|---|---|
| 端口监听 | 内核 | 可用 |
| 子命令方法 | 内核 | 可用 |
| 状态查询、装载卸载、调和 | 内核 | 可用 |
| 网页界面 | core-ui 侧车 | 不可用，但命令行不受影响 |
| 插件日志 | core-log 插件 | 不可用，`--kernel` 不受影响 |

这条是「修宿主的工具不能依赖被修的对象」的落地：命令行是修宿主的工具，它只能依赖内核。

### 8.2 两条日志路径为什么必须分开

`logs --kernel` 直读文件，不经过 core-log。理由是 core-log 本身正是会出问题的对象：它没装、装坏了、或者它的日志说「一切正常」。

同理，`doctor` 的所有检查都在内核里实现，不调用任何插件方法。

## 9. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。
| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | `kernel.restart` 与 `kernel.reload` 是否合并成一个方法 | 不合并。语义不同，合并后参数要带「是否换版本」的布尔，反而歧义 | §4.1 |
| 2 | Windows 上 `0600` 权限怎么落到 ACL | 用「仅当前用户」的 ACL 设置，不模拟 POSIX 模式 | §2.3 |
| 3 | `--json` 是否为所有子命令都实现 | 是。成本低，且脚本化是常用需求 | §4.3 |
| 4 | `logs --follow` 只对内核日志生效，插件日志不支持 | 接受。插件日志的实时性要求低，`--kernel` 才是排障主路径 | §5.5 |
