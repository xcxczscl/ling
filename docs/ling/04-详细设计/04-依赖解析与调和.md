# ling 04/04 依赖解析与调和

> 状态：已定稿 | 最后更新：2026-10-28
> 依据：`docs/ling/01-需求规格.md` §3.5；`docs/ling/03-架构设计.md` §4.1 服务④

本文写内核第四项服务：把「插件之间的需求关系」变成「一串按顺序执行的激活与停用动作」。

调和（reconcile）不是定时任务，也不是第五项服务——它是「环境变了」到「该做哪些步骤」的翻译过程，是服务④内部的执行方式。

## 2. 输入与输出

### 2.1 依赖声明

清单的 `[requires]` 段（字段定义见 `04/02` §3.3）：

```toml
[requires]
plugins = ["core-ui@1", "resources-manager@1.2"]
```

`capabilities` 段是另一类需求：它声明插件需要哪些能力，由门禁判定，不参与依赖图。**两类需求分开处理**（`LING-REQ-039`）：

| 需求类型 | 由谁判定 | 不满足时 |
|---|---|---|
| `capabilities` | 能力门禁（`04/01` §7） | 装载就失败，不进依赖图 |
| `requires.plugins` | 本文的依赖图 | 进入待激活状态，安装本身成功（`LING-REQ-042`） |

### 2.2 图的节点与边

| 元素 | 是什么 | 例子 |
|---|---|---|
| 节点 | 已安装的插件、已声明的能力 | `demo-a`、`core-ui`、`capability:fs` |
| 边 | 从需求方指向被需求方 | `demo-b → demo-a` |
| 环 | 有向图上的回路 | `a → b → a` |

首版的边只有插件节点之间的：`capabilities` 不进图，因为能力是宿主的固有属性，不是某个插件提供的。**若将来出现「某插件提供某能力」的设计，才需要把能力节点接进来。**

### 2.3 输出

一次调和的输出是一个计划：

```cpp
struct PlanStep {
    uint32_t    index;        // 从 1 开始，连续
    Action      action;       // Activate / Deactivate / Unload
    std::string plugin_id;
    int32_t     result;       // 执行后填：0 = ok，1 = skipped，其他 = 错误码
};

struct Plan {
    uint64_t              plan_id;      // 单调递增
    std::vector<PlanStep> steps;
    bool                  cancelled = false;
};
```

没有步骤的计划是合法结果：环境变了但三态判定全是「不动」时，计划为空，不广播任何 `plan.step`。

## 3. 版本约束匹配

### 3.1 四种写法

| 写法 | 含义 | 判定 |
|---|---|---|
| 无版本 | 任意版本都满足 | 直接成立 |
| `@1` | 主版本相同 | 目标的主版本等于 1 |
| `@1.2` | 主次版本相同 | 目标的前两段等于 1 和 2 |
| `@1.2.3` | 完全一致 | 三段相等 |

### 3.2 判定算法

```cpp
// 约束字符串去掉 @ 后按点切分，得到 segs；目标版本同样切分
bool version_satisfies(const std::vector<uint32_t>& constraint,
                       const std::vector<uint32_t>& target) {
    if (constraint.empty()) return true;               // 无版本
    if (target.size() < 3) return false;               // 目标版本非法
    for (size_t i = 0; i < constraint.size(); ++i) {
        if (i >= 3 || constraint[i] != target[i]) return false;
    }
    return true;
}
```

规则一句话：**约束的每一段与目标版本的同段逐一相同**（`LING-REQ-040`）。不是「大于等于」，是逐段相等——`@1` 的意思是「主版本是 1」，不是「至少 1」。

### 3.3 边界

| 情形 | 判定 |
|---|---|
| 约束段数超过 3 | 清单非法，`E_MANIFEST_INVALID` |
| 目标版本某段超出 0 至 65535 | 装载阶段已被拒（`LING-REQ-004`），不会进图 |
| 约束写成 `@1.2.3.4` | 同上，非法 |
| 约束写成 `@01` | 按整数解析为 1，视为 `@1` |

最后一条要说明：前导零不改变数值，`01` 与 `1` 等价。校验阶段不做拦截，因为解析成整数后没有歧义。

## 4. 依赖图

### 4.1 结构

```cpp
struct DepGraph {
    // 邻接表：需求方 → 它需要的一组插件
    std::unordered_map<std::string, std::vector<std::string>> edges;
    // 反向表：被需求方 → 谁需要它，用于「停用下游」
    std::unordered_map<std::string, std::vector<std::string>> reverse;
};
```

两张表都建，因为调和既需要「激活时先装被依赖者」（正查拓扑序），也需要「卸载时先停下游」（反查）。

### 4.2 构建步骤

每次重算都从零重建，不增量维护：

1. 取装载表里所有状态为 `Installed` 或 `Activated` 或 `Deactivated` 的插件。
2. 对每个插件，遍历 `requires.plugins`：

   - 解析目标编号与版本约束。
   - 目标不存在 → 记一条「未满足」。
   - 目标存在但版本不满足 → 记一条「版本不符」。
   - 都满足 → 加边，同时加反向边。

3. 返回图与两张「未满足清单」。

从零重建的理由：插件数是几十个，重算全图在 1 毫秒内（`LING-REQ-092` 给的上限就是按 50 插件 100 条边算的）。增量维护要处理「某插件被卸载导致多处边失效」，容易出错，收益不明显。

### 4.3 环检测

用 Kahn 算法：反复取出入度为 0 的节点，取不完说明有环。

```cpp
// 返回空表示无环；非空返回一个具体环路，用于错误信息
std::vector<std::string> find_cycle(const DepGraph& g);
```

失败时返回 `E_DEPENDENCY_CYCLE`，`detail` 里给完整环路（`LING-REQ-043`），例如：

```json
{"cycle": ["demo-a", "demo-b", "demo-a"]}
```

环检测在计划计算之前做，因为拓扑排序本身就依赖无环这个前提。

### 4.4 重算成本

| 项 | 量级 | 说明 |
|---|---|---|
| 节点数 | 50 | 需求给定的规模 |
| 边数 | 100 | 同上 |
| 全量构建 | O(V + E) | 哈希表插入 |
| 环检测 | O(V + E) | Kahn |
| 拓扑排序 | O(V + E) | 同一趟可复用 |
| 目标上限 | 1 毫秒 | `LING-REQ-092` |

50 个节点 100 条边时，实际耗时在百微秒量级，1 毫秒的上限有三倍以上余量。

## 5. 计划计算

### 5.1 三态判定

对每个已安装插件，判定结果是三者之一（`LING-REQ-044`）：

| 当前状态 | 需求是否满足 | 判定 |
|---|---|---|
| 未激活（`Installed` 或 `Deactivated`） | 满足 | 激活 |
| 已激活（`Activated`） | 不满足 | 停用 |
| 其他组合 | —— | 不动 |

「不动」的插件**不产生任何 `plan.step` 与状态事件**。这条常被忽略：每轮调和都给所有插件广播一次状态，等于把事件变成了噪音。

### 5.2 拓扑排序

激活按拓扑序（被依赖者在前），停用按反向拓扑序（依赖者在前）（`LING-REQ-045`）。

```cpp
// 一次计算两个顺序，避免重复排序
struct Order {
    std::vector<std::string> activate_order;    // 拓扑序
    std::vector<std::string> deactivate_order;  // 反向拓扑序
};
```

实现上不需要跑两遍：对同一张图做一次拓扑排序，取正序为激活顺序，取逆序即停用顺序。

### 5.3 计划的步骤顺序

一个计划里会出现激活与停用并存的情形。顺序规则：

1. 先执行全部停用步骤（反向拓扑序）。
2. 再执行全部激活步骤（拓扑序）。

先停后起的理由：同一插件在升级前后既停又起时，若先起后停，会在中间窗口里同时存在新旧两个版本。

### 5.4 计算失败即整体回滚

以下任一情形使计划计算失败（`LING-REQ-047`）：

| 情形 | 错误码 |
|---|---|
| 依赖成环 | `E_DEPENDENCY_CYCLE` |
| 清单非法（含版本段数超限） | `E_MANIFEST_INVALID` |
| 能力取值不在能力集 | `E_CAPABILITY_UNKNOWN` |
| 宿主内部错误 | `E_INTERNAL` |

失败时：

1. 本次配置变化整体不生效，依赖图与装载状态回到变化前。
2. 若这次变化本身是安装，已拷贝的工件被移除（`LING-REQ-043`）。
3. 返回首个错误的错误码与 `detail`。

「整体回滚」的含义是：**不做任何一步**，不是「做到一半再撤」。因为计划是在执行前算好的，算不出来就一步都不走。

## 6. 计划执行

### 6.1 步骤与事件

每一步执行完广播一条 `kernel.plan.step`（`LING-REQ-050`）。字段以 `01` 为准：

| 字段 | 内容 |
|---|---|
| `plan_id` | 本次计划的编号 |
| `step` | 从 1 连续递增 |
| `step_total` | 本次总步数 |
| `action` | `activate` / `deactivate` / `unload` / `cancel` |
| `plugin` | 本步作用的插件编号 |
| `ok` | 布尔，成功为 true |
| `error` | `ok` 为 false 时的错误码 |

`step` 连续递增的含义：跳过与失败也算一步，不出现断号。这样消费方可以用 `step` 与 `step_total` 判断是否收全。

### 6.2 取消与回滚

执行中可取消（`LING-REQ-048`）：

| 时点 | 行为 |
|---|---|
| 取消请求到达，当前步正在执行 | 等当前步结束再停，不打断 |
| 停止后 | 已执行的步骤按账本倒序回滚到执行前状态 |
| 计划记录 | 标记 `cancelled = true`，广播一条 `plan.step`，`action` 记为 `cancel`、`ok` 为 false、`error` 为 `E_CANCELLED` |

不打断当前步的理由：激活或停用做到一半被打断，会留下「账本登记了一半」的中间状态，比多等一会儿更糟。

### 6.3 幂等

停用与激活可重复执行，重复执行不产生额外效应（`LING-REQ-049`）：

| 场景 | 行为 |
|---|---|
| 对已激活的插件再次激活 | 直接跳过，不新建账本段、不广播事件 |
| 对已停用的插件再次停用 | 同上 |
| 计划里同一插件出现两次 | 计算阶段就去重，不会出现 |

去重放在计算阶段而不是执行阶段：执行阶段去重意味着计划与执行不一致，`step_total` 也会对不上。

## 7. 触发与去抖

### 7.1 七个触发点

`LING-REQ-046` 规定七处：

| 触发点 | 由谁提交 |
|---|---|
| `install` | 管理端口命令 |
| `uninstall` | 同上 |
| `enable` | 同上 |
| `disable` | 同上 |
| `reload` | 同上（重载流程内部也会触发一次） |
| 清单变化 | 扫描发现 `plugin.toml` 的修改时间变化 |
| 宿主启动 | §8 |

七处都提交同一个 `Reconcile` 请求，走同一个队列（`04/01` §8.1），没有例外通道。

### 7.2 200 毫秒合并

连续变化在 200 毫秒窗口内合并为一次调和（`LING-REQ-049`）。

实现：

```
收到 Reconcile 请求 → 不立即执行，标记 pending 并记下时间戳
  → 若已有 pending，只更新时间戳，不新建
  → 内核线程每轮检查：now - last_change >= 200ms 且 pending
       → 清 pending，算计划，执行
```

三处细节：

| 细节 | 规定 |
|---|---|
| 窗口从最后一次变化算 | 连续 5 次变化只产生 1 次调和 |
| 启动时不受窗口限制 | 启动的全量调和立即执行，不等 200 毫秒 |
| 命令行的 `install` 要等结果 | 提交后阻塞到该轮调和结束，再返回 |

最后一条决定了命令行的体验：`ling install` 不能立刻返回「已安装」然后后台慢慢调和，用户会以为装完了去调用，结果是 `E_PLUGIN_MISSING`。

### 7.3 合并的边界

| 情形 | 行为 |
|---|---|
| 200 毫秒内同时有 install 与 uninstall | 合并成一次，计划里两者都体现 |
| 合并期间有取消请求 | 取消的是「尚未开始的执行」，不影响窗口计时 |
| 合并期间进程退出 | 不执行，只在日志记一条 warn |

## 8. 启动时的全量调和

宿主启动执行一次全量调和（`LING-REQ-051`）：

1. 装载表从空开始，账本重建（`LING-REQ-085`）。
2. 扫描全部已安装插件，建图。
3. 对每个插件按三态判定，得到计划。
4. 执行计划，逐条广播 `plan.step`。

失败时：退出码非 0，`stderr` 写明失败的插件与原因（例如成环时给出环路）。

启动调和跳过 200 毫秒窗口，因为它没有「连续变化」的场景。

一个边界情形：启动时部分插件因依赖缺失进入待激活状态，这**不是失败**。只有「算不出计划」（成环、清单非法）才算失败。缺依赖是正常状态，等依赖装上会自动激活（`LING-REQ-042`）。

## 9. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | `E_CANCELLED` 已登记进 `04/02` §5.2 的错误码表 | 归入系统类，含义「操作被取消」 | §6.2、04/02 §5.2 |
| 2 | 清单变化的检测靠修改时间，粒度只有秒 | 够用。同一秒内两次修改会被合并成一次，结果正确 | §7.1 |
