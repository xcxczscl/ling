## 2. 内核对象模型

### 2.1 内核持有哪些对象

```cpp
class Kernel {
public:
    // 只读视图：任何线程都能取
    SnapshotPtr snapshot() const;              // 四张表的不可变快照

    // 写入口：只允许内核线程调用，外部线程经 submit() 排队
    void submit(Request req);

    // 调用热路径
    CallResult call(const std::string& method, const uint8_t* args, size_t len,
                    const std::string& trace_id);
    void emit(const std::string& topic, const uint8_t* payload, size_t len,
              const std::string& trace_id);

private:
    SnapshotPtr snapshot_;          // 原子读写，见 §4
    RequestQueue queue_;            // 见 §8
    ThreadPool workers_;            // 见 §8.3
    LedgerStore ledgers_;           // 每插件一份，接口见 04/03
    Logger logger_;                 // 见 §9
    std::thread kernel_thread_;
    std::atomic<bool> stopping_{false};
};
```

对象职责一览：

| 对象 | 持有者 | 生命周期 | 谁可以改 |
|---|---|---|---|
| 快照 `SnapshotPtr` | 内核 | 随每次写操作替换 | 内核线程构造新快照后原子替换 |
| 请求队列 | 内核 | 进程全程 | 任何线程入队，只有内核线程出队 |
| 工作线程池 | 内核 | 进程全程 | 只有内核线程派发任务 |
| 效应账本 | 内核 | 与插件同生命周期 | 内核线程追加，05 定义的撤销路径消费 |
| 日志器 | 内核 | 进程全程 | 任何线程写，异步队列 |

### 2.2 启动顺序

九步，前一步失败则整体退出并写内核日志：

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 读 `registry.json`（端口、撤销名单、禁用名单），文件不存在则用默认值 | 解析失败 → 退出并报文件路径与错在哪一行 |
| 2 | 初始化日志器（异步队列、当天文件） | 打不开文件 → 退回到只写 stderr，继续启动 |
| 3 | 构造空快照（四张表全空，版本号 0） | 内存不足 → 退出 |
| 4 | 启动内核线程 | 线程创建失败 → 退出 |
| 5 | 扫描数据根的 `plugins/` 目录，逐个读清单并校验（校验规则见 04/02） | 单个插件清单非法 → 跳过该插件并记 warn，不影响其他 |
| 6 | 建依赖图并算出首次激活计划（算法见 04/04） | 存在环 → 拒绝启动并列出环上的插件 |
| 7 | 起管理端口（帧与认证见 04/06） | 端口被占 → 换下一个候选端口并记 warn |
| 8 | 按计划执行激活，每步广播 `kernel.plugin.state` 与 `kernel.plan.step` | 单个插件激活失败 → 标记 Failed，继续后续步骤 |
| 9 | 进入事件循环，等待请求队列与管理端口 | —— |

第 6 步放在第 7 步之前，是因为端口一起来就会有命令进来，那时依赖图必须已经算好。

### 2.3 关闭顺序

七步，与启动相反。**先停插件再排空队列**，顺序反过来会出现「队列里还有装载请求，但插件已经被卸掉」：

| 步 | 动作 | 目的 |
|---|---|---|
| 1 | 管理端口停止接受新连接，已有连接允许完成当前命令 | 不再有新请求进入 |
| 2 | 置 `stopping_`，拒绝新请求入队（返回 `E_SHUTTING_DOWN`） | 队列不再变长 |
| 3 | 排空队列：执行已入队的写请求，不丢弃 | 避免半完成的注册留在表里 |
| 4 | 按反向拓扑序停用并卸载全部插件，逐个撤销效应 | 撤销顺序错误会导致依赖方撤销时目标已消失 |
| 5 | 停工作线程池：让在跑的任务结束，超过 5 秒则放弃并记 warn | 避免线程在快照释放后仍持指针 |
| 6 | 落盘 `registry.json`，刷日志队列 | 保留端口与撤销名单 |
| 7 | 释放快照与装载表，内核线程退出 | —— |

## 3. 数据结构

四张表都放在同一份快照里，保证读方看到的是同一时刻的一致状态。

### 3.1 路由表

```cpp
using CapabilityMask = uint32_t;   // 位集：fs=1、network=2、ui=4、shell=8

struct RouteEntry {
    std::string plugin_id;        // 归属插件编号
    std::string method_name;      // 完整方法名，含前缀，如 demo-a.scan.start
    MethodFn handler;             // 插件侧处理函数
    void* handler_ctx;            // 插件侧上下文句柄，回传时原样交回
    CapabilityMask requires;      // 该方法要求的能力位
    uint64_t register_seq;        // 注册序号，单调递增，用于与账本对账
};

// key 就是完整方法名：方法名必带插件编号前缀，而编号全项目唯一，所以 key 天然唯一
using RouteTable = std::unordered_map<std::string, RouteEntry>;
```

为什么 key 用完整方法名而不是 `(plugin_id, method_name)` 二元组：方法名强制带前缀（`LING-REQ-014`），前缀等于编号，所以二元组的信息已经在字符串里。用单个字符串省一次构造临时键，热路径上每次调用都省。

### 3.2 订阅表

订阅分两级存，因为匹配规则不同：

```cpp
struct SubEntry {
    std::string plugin_id;
    std::string pattern;       // demo-b.* 或 * 或精确主题
    EventFn callback;
    void* callback_ctx;
    uint64_t sub_id;           // 同一插件内唯一，注销时用
    uint64_t register_seq;     // 派发顺序依据
};

struct SubTable {
    // 精确主题 → 订阅者列表，按 register_seq 升序
    std::unordered_map<std::string, std::vector<SubEntry>> exact;
    // 通配订阅单独存一份，数量上限等于插件数 × 每插件通配订阅数
    std::vector<SubEntry> wildcard;
};
```

通配单独存、线性扫描的理由：通配订阅的数量与插件数同阶（几十条），每次广播扫几十条是可接受的开销；若为了快而建前缀树，代码量会翻倍，收益在这个量级上看不出来。

### 3.3 能力表

```cpp
struct CapEntry {
    CapabilityMask declared;   // 清单 capabilities 的位集
    CapabilityMask revoked;    // 用户撤销名单的位集
    CapabilityMask effective() const { return declared & ~revoked; }
};

using CapTable = std::unordered_map<std::string, CapEntry>;
```

能力集首版固定四个：`fs`、`network`、`ui`、`shell`（`LING-REQ-023`）。集合外的取值在清单校验阶段就拒绝，不进这张表。

### 3.4 装载表

```cpp
enum class Track { InProcess, Sidecar };

enum class PluginState {
    Uninstalled,   // 只有目录没有装载
    Installed,     // 清单已通过校验，尚未装载
    Activating,
    Activated,
    Deactivating,
    Deactivated,
    Failed         // 装载或激活失败，或崩溃后被标记
};

struct LoadEntry {
    std::string plugin_id;
    std::string version;       // 三段式，见 docs/common/02-版本号与兼容约定.md
    std::string api;           // 接口主版本，若与宿主不兼容则拒绝装载
    std::string min_host;      // 要求的最低宿主版本，可空
    Track track;
    PluginState state;
    void* dl_handle;           // 进程内轨道：动态库句柄
    int32_t sidecar_pid;       // 侧车轨道：进程号，无则为 -1
    CapabilityMask declared;
    uint64_t generation;       // 每次装载自增，用于拒绝旧回调
};

using LoadTable = std::unordered_map<std::string, LoadEntry>;
```

`generation` 的作用：热更新时同一编号会装载两次，旧版本的函数指针仍被别处持有。给每次装载分配新代号，回调进来时比对代号，不相同则直接拒绝并返回 `E_PLUGIN_MISSING`——这比指望所有旧指针都被清干净可靠。

### 3.5 不变式

写路径每次改完表都要校验这五条，任一条不成立说明写操作有 bug，直接拒绝换快照并把内核日志标为 error：

| # | 不变式 | 违反的例子 |
|---|---|---|
| 1 | 路由表条目的 `plugin_id` 必须在装载表里存在，且状态不是 `Uninstalled` | 卸载时漏了注销方法 |
| 2 | 路由表 key 必以 `plugin_id` 加一点开头 | 前缀校验被绕过 |
| 3 | 同一插件的 `sub_id` 不重复 | 订阅注销时删错对象 |
| 4 | 能力表对每个已装载插件都有条目，可以是全 0 | 缺条目导致门禁判定走空指针 |
| 5 | 订阅表里每条记录的 `plugin_id` 在装载表里存在且状态为 `Activated` 或 `Deactivating` | 停用后订阅未撤销 |

第 5 条允许 `Deactivating`，是因为停用要按账本倒序撤销，撤销过程中状态先变再撤，撤销完成后才变 `Deactivated`。

## 4. 快照机制

### 4.1 为什么用快照

`docs/ling/03-架构设计.md` §5.3 已说明：单线程内核只解决「谁能改状态」，如果读也要排队，一次调用就是两次线程切换，`LING-REQ-089` 的 1 微秒达不到。这里给具体做法。

### 4.2 快照包含什么

```cpp
struct Snapshot {
    uint64_t version;          // 单调递增，每次换快照加一
    RouteTable routes;
    SubTable subs;
    CapTable caps;
    LoadTable plugins;
};
using SnapshotPtr = std::shared_ptr<const Snapshot>;
```

四张表放同一份快照，是因为它们之间有跨表不变式（§3.5）。若拆成四份快照分别替换，读方会拿到「路由表已更新、能力表还是旧的」组合，门禁判定就会用到过期能力。

**账本不在快照里。** 账本追加极频繁（每次注册、订阅各一条），若每次追加都复制整份快照，单次注册成本随账本长度线性上升。账本改用单写多读的追加结构，见 `docs/ling/04-详细设计/03-上下文与效应账本.md`。

### 4.3 换快照的步骤

写操作在副本上做，校验通过才替换：

1. 取当前快照，复制一份（深浅由字段决定：`unordered_map` 浅拷贝即可，`vector<SubEntry>` 会随复制一同复制，条目数是几十到几百，成本可接受）。
2. 在副本上执行改动。
3. 校验 §3.5 的五条不变式。任一条失败：丢弃副本，记 error 日志，返回 `E_INTERNAL`。
4. 副本 `version` 加一。
5. 原子换指针：C++17 用 `std::atomic_store(&snapshot_, new_ptr)`。
6. 旧快照由持有它的读者在读完时释放，内核不主动保留。

### 4.4 读方必须遵守的规则

| 规则 | 原因 |
|---|---|
| 一次操作只取一次快照，全程用这一份 | 同一操作内表结构不能变，否则查到处理函数后能力表已升级 |
| 不得把快照里的指针或引用保存到操作结束之后 | 快照随时会被替换，旧快照一旦无人持有就被释放 |
| 不得在持有快照期间提交写请求并等待结果 | 写请求要由内核线程执行，若内核线程正卡在这把读上，会互锁 |

第三条是硬约束，写进 SDK 的调用约定里。

### 4.5 快照的成本

一次写操作复制四张表。按 50 个插件、每插件 10 个方法、20 条订阅计，路由表 500 条、订阅表 20 条左右，复制耗时在几十微秒量级。写操作发生在装载、注册、调和阶段，不在调用热路径上，可以接受。

若将来插件数上到几百，把 `RouteTable` 换成持久化数据结构（改一条路径只复制 O(log n) 个节点）即可，接口不变。

## 5. 方法路由

### 5.1 注册

```cpp
// 由插件在 activate 阶段经 Context 调用，提交为 RegisterMethod 写请求
int32_t Kernel::register_method(const std::string& plugin_id,
                                const std::string& method_name,
                                MethodFn handler,
                                void* handler_ctx,
                                CapabilityMask requires);
```

校验顺序固定，遇到第一个失败即返回，不继续后面的检查：

| 序 | 检查 | 失败返回 |
|---|---|---|
| 1 | 插件在装载表中存在且状态为 `Activating` | `E_PLUGIN_MISSING` |
| 2 | `handler` 非空 | `E_LEDGER_INVALID` |
| 3 | 方法名以 `plugin_id` 加一点开头 | `E_NAMESPACE_VIOLATION` |
| 4 | 方法名总长不超过 128 字节，只含字母、数字、下划线、点 | `E_MANIFEST_INVALID` |
| 5 | `requires` 是清单 `capabilities` 的子集 | `E_CAPABILITY_DENIED` |
| 6 | 完整方法名在路由表中不存在 | `E_DUPLICATE_METHOD` |

顺序的理由：先确认「这个插件此刻有资格注册」，再确认「参数合法」，最后确认「不冲突」。若把第 6 步放前面，一个已停用的插件来注册时会先报「名字已存在」，误导排查方向。

第 2 步用 `E_LEDGER_INVALID` 而不是新错误码，是因为「撤销函数为空」与「处理函数为空」同属「交上来的东西不完整」，合并成一个码，减少错误码总数。

注册成功后：账本追加一条 `MethodRegistered` 效应，撤销动作是注销该方法。

### 5.2 注销

```cpp
int32_t Kernel::unregister_method(const std::string& plugin_id,
                                  const std::string& method_name);
```

检查两条：方法存在、且归属插件与 `plugin_id` 一致（防止 A 注销 B 的方法）。不存在时返回 `E_METHOD_MISSING`，归属不符返回 `E_CAPABILITY_DENIED`。

注销是幂等的：同一方法连续注销两次，第二次返回 `E_METHOD_MISSING`，不抛错、不改其他条目。

### 5.3 调用路径

```cpp
struct CallResult {
    int32_t code;              // 0 表示成功
    std::vector<uint8_t> data; // 返回载荷
};

CallResult Kernel::call(const std::string& method,
                        const uint8_t* args, size_t len,
                        const std::string& trace_id);
```

步骤：

1. 取一次快照（§4.4 第 1 条）。
2. 若 `len > kMaxPayloadBytes`（1 MB，`LING-REQ-097`），返回 `E_PAYLOAD_TOO_LARGE`。检查在查表之前，避免为超限请求做无用的哈希查找。
3. 在 `routes` 里查 `method`。未命中：先查装载表判断该编号的插件是否存在——存在则返回 `E_METHOD_MISSING`，不存在或未激活则返回 `E_PLUGIN_MISSING`。这次二次查表只在失败路径上发生。
4. 取该插件的 `CapEntry`，若 `entry.requires` 不被 `effective()` 覆盖，返回 `E_CAPABILITY_DENIED`。
5. 按 `track` 分派：
   - `InProcess`：直接调 `entry.handler(entry.handler_ctx, args, len, &out, &out_len)`。这是热路径，没有序列化、没有跨线程。
   - `Sidecar`：把参数封成帧（帧格式见 04/02）写入该侧车的套接字，等待应答。等待上限 5 秒（`LING-REQ-066`），超时返回 `E_TIMEOUT`，并把该侧车标记为可疑，交给 04/07 的善后流程。
6. 调用期间计时。同步调用超过 30 秒（`LING-REQ-017`）时，内核不强行终止处理函数——C++ 没有可移植的线程取消——而是返回 `E_TIMEOUT` 给调用方，并把这次调用的 trace id 与插件编号写入内核日志。处理函数继续在它自己的线程上跑，跑完的结果被丢弃。
7. 校验 `generation`：处理函数返回后，若装载表的 `generation` 已变，说明期间发生了热更新，返回值作废，返回 `E_PLUGIN_MISSING`。
8. 若返回码非 0 且属于「被拒绝」类（门禁、超时、载荷超限），写一条 warn 日志；正常调用不写日志（`LING-REQ-121` 的 debug 级别才记）。
9. 返回结果。

第 6 步需要单独说明：**「超时」是放弃等待，不是停止执行。** 文档里不写「终止插件线程」，因为做不到；写的是「返回超时并把结果丢弃」，实现与描述一致。

### 5.4 命名空间规则

| 对象 | 规则 | 校验点 |
|---|---|---|
| 方法名 | 必以 `<插件编号>.` 开头，点后至少一段 | 注册时（§5.1 第 3 步） |
| 事件主题 | 同理，`kernel.` 前缀保留给内核 | 订阅与广播时（§6） |
| 插件编号 | 小写字母、数字、连字符，长度 2 至 32，全项目唯一 | 清单校验（04/02） |

为什么要求方法名带前缀而不是用二元组隔离：日志与 trace 里只出现方法名字符串，带前缀能一眼看出归属；若靠二元组，日志里就得额外打两列。

### 5.5 本模块用到的错误码

取值与完整定义在 `docs/ling/04-详细设计/02-插件装载与接口.md`，这里只列本模块返回的：

| 错误码 | 本模块何时返回 |
|---|---|
| `E_PLUGIN_MISSING` | 目标插件未装载、未激活，或调用期间发生热更新 |
| `E_METHOD_MISSING` | 方法未注册 |
| `E_NAMESPACE_VIOLATION` | 方法名或事件主题没带自己的前缀，或用了 `kernel.` |
| `E_CAPABILITY_DENIED` | 方法声明超出清单，或调用瞬间生效能力不足 |
| `E_PAYLOAD_TOO_LARGE` | 参数或事件载荷超过 1 MB |
| `E_TIMEOUT` | 同步调用超过 30 秒，或侧车未在 5 秒内应答 |
| `E_DUPLICATE_METHOD` | 同一完整方法名重复注册 |
| `E_INTERNAL` | 不变式校验失败这类内核自身错误 |
| `E_SHUTTING_DOWN` | 关闭过程中拒绝新请求 |

`E_DUPLICATE_METHOD`、`E_INTERNAL`、`E_SHUTTING_DOWN` 是本文新增的三个，需登记进 04/02 的错误码表。

## 6. 事件广播

### 6.1 订阅

```cpp
int32_t Kernel::subscribe(const std::string& plugin_id,
                          const std::string& pattern,
                          EventFn callback,
                          void* callback_ctx,
                          uint64_t* out_sub_id);
```

校验顺序：

| 序 | 检查 | 失败返回 |
|---|---|---|
| 1 | 插件状态为 `Activating` | `E_PLUGIN_MISSING` |
| 2 | `callback` 非空 | `E_LEDGER_INVALID` |
| 3 | 主题非 `kernel.` 开头，或以 `plugin_id.` 开头 | `E_NAMESPACE_VIOLATION` |
| 4 | 通配只允许出现在末尾（`a.b.*`），或整串就是 `*` | `E_NAMESPACE_VIOLATION` |
| 5 | 同一插件下通配订阅不超过 32 条 | `E_CAPABILITY_DENIED` |

第 4 条限制了通配的位置：不允许 `a.*.c` 这种中缀通配。理由是它需要完整模式匹配，代码量与出错面都上升，而实际需求里只用到「某插件全部事件」（`demo-b.*`）与「全部事件」（`*`）两种。

订阅成功后：分配 `sub_id`（插件内自增），账本追加 `EventSubscribed`，撤销动作是退订。

### 6.2 匹配

广播一个主题时，收件人按两步汇总：

1. 查 `subs.exact[topic]`，命中则整条列表加入结果。
2. 扫 `subs.wildcard`：模式为 `*` 的全收；模式为 `<前缀>.*` 且在主题上做前缀比较（要求主题在该前缀之后还有内容）。

结果按 `register_seq` 升序排序，这就是 `LING-REQ-021` 要求的「按订阅登记顺序」。排序发生在每次广播，条目数几十条，用的是插入排序（几乎有序的输入下接近线性）。

### 6.3 派发

```cpp
void Kernel::emit(const std::string& topic, const uint8_t* payload, size_t len,
                  const std::string& trace_id);
```

步骤：

1. 校验主题前缀（同 §6.1 第 3 条），越权则记一条越权记录并丢弃这次广播（`LING-REQ-019`）。
2. 校验载荷大小，超过 1 MB 直接丢弃并记 warn。
3. 按 §6.2 算出收件人列表。
4. 逐个同步调用，每个调用前记下时间戳：
   - 单个回调超过 5 秒（`LING-REQ-021`）→ 跳过该订阅者，把其 `sub_id` 与插件编号写入内核日志，继续下一个。
   - 回调抛出的错误码不中断广播，只记录。
5. 广播结束，不落盘、不重投（`LING-REQ-020`）。

`emit` 由调用方线程同步执行，不排队到内核线程。理由：广播本身不改内核状态（只读快照），若排队就要为每次广播做一次线程切换，与 §4 的目的相反。

代价是「广播是同步的，慢订阅者会拖住广播方 5 秒」。这是 `LING-REQ-021` 明确接受的：宁可让一个慢订阅者拖住一次广播，也不引入异步队列带来的顺序与重投问题。

### 6.4 内核事件字段

字段格式与错误码同属契约，完整定义在 04/02；这里给出本文负责广播的两类事件的字段清单。

`kernel.plugin.state`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `plugin_id` | 字符串 | 插件编号 |
| `state` | 枚举 | `activated` / `deactivated` / `uninstalled` / `crashed` |
| `version` | 字符串 | 事件发生时该插件的版本 |
| `generation` | 整数 | 装载代号，用于区分热更新前后 |
| `reason` | 字符串 | 可选，`crashed` 时带错误码 |

`kernel.plan.step`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `step_index` | 整数 | 从 1 开始 |
| `step_total` | 整数 | 本次计划的总步数 |
| `action` | 枚举 | `activate` / `deactivate` / `unload` |
| `plugin_id` | 字符串 | 本步作用的插件 |
| `result` | 枚举 | `ok` / `skipped` / `failed` |
| `error_code` | 字符串 | `failed` 时带 |

这两类事件的载荷都是 JSON，与其他事件的载荷格式一致。字段名一经发布不改，改则升 `api` 主版本（见 `docs/common/02-版本号与兼容约定.md`）。

## 7. 能力门禁

### 7.1 两处校验

| 位置 | 检查什么 | 数据来源 | 失败返回 |
|---|---|---|---|
| 注册方法时 | 方法声明的 `requires` 是否被清单 `capabilities` 覆盖 | 清单 | `E_CAPABILITY_DENIED` |
| 调用瞬间 | `requires` 是否被「清单声明减用户撤销」覆盖 | 清单与撤销名单 | `E_CAPABILITY_DENIED` |

两处都要，只做一处就能绕过：

- 只做注册时：用户在运行中撤销了能力，已注册的方法照样能调。
- 只做调用时：一个没在清单里声明的能力也能被方法用上，因为注册时不查。

### 7.2 撤销与恢复

```cpp
int32_t Kernel::set_capability_revoked(const std::string& plugin_id,
                                       CapabilityMask add,
                                       CapabilityMask clear);
```

- 撤销与恢复都只改 `CapEntry.revoked` 的位，不改装载表状态，插件保持 `Activated`（`LING-REQ-026`）。
- 撤销状态写入 `registry.json`，重启后仍生效。
- 撤销不触发调和：能力不是依赖，插件不会因为能力被撤销而停用。
- 撤销不广播事件，只写内核日志（`LING-REQ-112` 要求状态变化有事件，能力撤销不是插件状态变化）。

### 7.3 门禁不管什么

| 不管 | 原因 |
|---|---|
| 具体文件路径 | 管路径等于在宿主里塞一个沙箱，违背零内容（`LING-REQ-027`） |
| 网络地址 | 同上 |
| 调用频率 | 属于限流，不在本期范围 |
| 能力语义 | 宿主只知道能力的名字，不知道用它做什么 |

## 8. 内核线程与请求队列

### 8.1 请求类型

```cpp
enum class RequestKind {
    RegisterMethod,
    UnregisterMethod,
    Subscribe,
    Unsubscribe,
    SetCapabilityRevoked,
    LoadPlugin,
    UnloadPlugin,
    Reconcile        // 由 04/04 提交
};

struct Request {
    RequestKind kind;
    std::string plugin_id;
    std::string trace_id;
    std::variant<RegisterArgs, UnregisterArgs, SubscribeArgs,
                 UnsubscribeArgs, CapabilityArgs, LoadArgs, UnloadArgs, ReconcileArgs> args;
    std::promise<int32_t> done;   // 同步调用方等待结果
    bool wait_for_result;         // 装载类请求为 true，通知类为 false
};
```

八种请求覆盖了所有改内核状态的动作。没有第九种：凡是本文没列的改动，都必须先扩这张表，不允许直接改快照——这是「只有内核线程能改状态」的唯一入口。

### 8.2 队列语义

| 性质 | 规定 | 理由 |
|---|---|---|
| 顺序 | FIFO，严格按入队顺序执行 | 注册与订阅的先后会影响派发顺序，乱序会破坏 §6.2 的排序依据 |
| 并发 | 多生产者单消费者，队列本身用互斥锁保护 | 提交都在非热路径上，一把锁的开销无所谓 |
| 重入 | 内核线程执行请求期间不得再提交并等待 | 会自锁，加运行时断言 |
| 失败 | 单条请求失败不影响后续请求 | 一条装载失败不能让整条队列停下 |
| 关闭 | 置 `stopping_` 后拒绝新请求，已入队的执行完 | 见 §2.3 第 3 步 |

### 8.3 工作线程池

数量：`CPU 核数 − 3`，最少 2（`docs/ling/03-架构设计.md` §5.2）。

工作线程可以做的：

- 文件读写、哈希计算、目录扫描这类插件请求的耗时操作
- 侧车进程的启动与等待
- 日志落盘

工作线程不可以做的：**任何改内核状态的操作**。需要改时提交写请求，由内核线程执行。这条用 API 限制：工作线程拿不到 `Kernel` 的可写引用，只能拿到快照与管理端口的只读视图。

## 9. 日志

本文负责的事件与队列都要能进日志，字段与写入实现按 `LING-REQ-117` 至 `LING-REQ-126`：

| 场景 | 级别 | 必记内容 |
|---|---|---|
| 注册、注销、订阅、退订成功 | info | 插件编号、方法名或主题、trace id、`generation` |
| 门禁拒绝、命名空间越权、载荷超限 | warn | 错误码、被拒对象、trace id |
| 调用超时、订阅者超时被跳过 | warn | 超时阈值、实际耗时、插件编号、trace id |
| 内核事件广播 | info | 事件名、`plugin_id`、状态 |
| 不变式校验失败 | error | 违反的是第几条、哪张表 |
| 崩溃捕获 | error | 插件编号、调用栈、`generation` |

正常调用不进日志，开启 debug 级别才记每次调用的摘要（方法名、耗时、返回码）——这就是 `LING-REQ-121` 的实现方式，不需要单独的开关。

## 10. 时序

### 10.1 注册方法

```
插件(Activating) → Context.register_method
  → 校验插件状态 / 处理函数非空 / 前缀 / 长度 / 能力子集 / 不冲突
  → 入队 RegisterMethod 请求，等结果
内核线程 → 复制快照 → 插入 RouteEntry(register_seq = ++seq)
        → 校验不变式 → 换快照
        → 账本追加 MethodRegistered（撤销 = 注销该方法）
        → 返回 0
失败路径：任一步失败 → 不换快照 → 返回对应错误码 → 写 warn 日志
```

### 10.2 调用

```
调用方 → Kernel.call(method, args, trace_id)
  → 取快照（一次）
  → 载荷大小检查 → 超限返回 E_PAYLOAD_TOO_LARGE
  → 查路由 → 未命中：查装载表区分 E_PLUGIN_MISSING / E_METHOD_MISSING
  → 查能力表 → 不覆盖返回 E_CAPABILITY_DENIED
  → 按轨道分派
      进程内：直接调 handler，计时
      侧车：封帧 → 写套接字 → 等应答，5 秒超时
  → 返回后校验 generation → 变了返回 E_PLUGIN_MISSING
  → 返回结果（同步调用超过 30 秒则在计时点直接返回 E_TIMEOUT）
```

### 10.3 广播

```
调用方 → Kernel.emit(topic, payload, trace_id)
  → 校验主题前缀（越权则记录并丢弃）
  → 载荷大小检查
  → exact[topic] + wildcard 匹配 → 按 register_seq 排序
  → 逐个同步调用：单个超过 5 秒 → 跳过并记录，继续下一个
  → 不落盘、不重投
```

### 10.4 门禁拒绝

```
调用方 → Kernel.call("demo-b.write", ...)
  → 查路由命中
  → 查能力表：declared = fs，revoked = fs，effective = 0
  → requires 含 fs，不被覆盖 → 返回 E_CAPABILITY_DENIED
  → 写 warn 日志（含 trace id）
  → 插件状态不变，仍为 Activated
```

### 10.5 卸载时批量注销

```
内核线程 → 执行 UnloadPlugin 请求
  → 插件状态改 Deactivating
  → 按账本倒序逐条执行撤销（账本细节见 04/03）
      每条 MethodUnregistered → 从路由表删条目
      每条 EventUnsubscribed  → 从订阅表删条目
      撤销失败 → 记 error，继续下一条，不中断
  → 全部撤销完 → 从能力表、装载表删条目 → 状态改 Uninstalled
  → 校验不变式 → 换快照
  → 广播 kernel.plugin.state(uninstalled)
```
