# ling 04/07 内置插件

> 状态：已定稿 | 最后更新：2026-10-28
> 依据：`docs/ling/01-需求规格.md` §3.9

五个内置插件随宿主分发、默认预装。**每个插件的详细设计在 `docs/ling/builtin-plugins/<插件名>/` 下，本文只保留共同规则与边界。**它们**没有任何特权**：与业务插件用同一套清单、同一条路由、同一套门禁，也可以被卸载。

本文写清每个插件做什么、边界在哪、卸载后宿主退化成什么样。

## 2. 五个插件一览

### 2.1 全表

| 编号 | 名称 | 轨道 | 职责 | 依赖 |
|---|---|---|---|---|
| `core-ui` | 本机网页界面 | 侧车（C++） | 提供浏览器可访问的操作界面 | 无 |
| `core-settings` | 配置存储 | 进程内 | 为其他插件提供键值配置的读写与撤销 | 无 |
| `core-plugin-manager` | 插件管理器 | 进程内 | 依赖树展示、孤儿数据清理、批量操作 | `core-settings@1` |
| `core-job` | 定时任务 | 进程内 | 按时间表达式触发对插件方法的调用 | `core-settings@1`（本期不声明，见下注） |
| `core-log` | 日志收集 | 进程内 | 收集插件日志、提供查询 | 无 |

> **依赖列怎么理解**：`core-plugin-manager` 与 `core-job` 都需要 `core-settings` 提供配置存储。MVP 期间清单里不能写 `requires`（`11-MVP 范围.md` §4.2 第一条），所以这份依赖只作为「谁先谁后」的说明，不体现在清单里。装载顺序按插件名字母排，`core-job` 排在 `core-settings` 之前，因此它把「读任务定义」推迟到第一次心跳——那时所有内置插件都已激活。`core-plugin-manager` 不读配置，没有这个问题。

### 2.2 为什么是这五个

| 插件 | 不做会怎样 |
|---|---|
| `core-ui` | 只能用命令行，看不到状态变化与日志流 |
| `core-settings` | 插件无处存配置，只能全塞进 `data/`，而配置需要「可撤销、可导出、可查」 |
| `core-plugin-manager` | 装卸与状态查询命令行已有，但「哪些插件在等依赖」「哪些 `data/` 是孤儿」这类问题没有入口 |
| `core-job` | 没有定时能力，所有周期性工作要靠插件自己起线程 |
| `core-log` | 插件日志只能写 stderr，重启后丢失 |

这五项的共同点：**它们是「给其他插件用的公共服务」，不是业务功能**。业务插件不该各自实现一遍日志收集或定时器。

### 2.3 编号与版本

| 项 | 规定 |
|---|---|
| 编号前缀 | 一律 `core-` |
| 编号占用 | `core-` 前缀保留给内置插件，业务插件不得使用；清单校验时检查 |
| 版本起点 | 1.0.0，随宿主版本一起升 |
| 版本兼容 | 内置插件的 `api` 与宿主一致；宿主升 `api` 主版本时，内置插件同版本一起换 |

前缀保留的判定放在清单校验（`04/02` §3.4）里，新增一条检查：`id` 以 `core-` 开头且不在内置清单里时拒绝装载，返回 `E_MANIFEST_INVALID`。

## 3. `core-ui`

本机界面：看插件、装卸启停、翻日志、改配置、管定时任务。侧车轨道，独立进程，只绑回环。

详细设计见 `docs/ling/builtin-plugins/core-ui/` 下五份：`00-总览与边界.md`、`01-需求与用例.md`、`02-服务端与接口.md`、`03-页面与交互.md`、`04-两种形态与启动.md`。

发布分 `webui` 与 `desktop` 两种形态，界面代码相同，差别只在由浏览器还是由 WebView2 窗口显示。

---

## 4. `core-settings`

给所有插件存配置的公共仓库：键值存储、按插件名前缀隔离、每次写入进账本、卸载时自动还原。

详细设计见：

| 文档 | 内容 |
|---|---|
| `docs/ling/builtin-plugins/core-settings/00-总览与边界.md` | 定位、与插件私有数据的分界 |
| `docs/ling/builtin-plugins/core-settings/01-需求与用例.md` | 场景、用例 `CS-01` 至 `CS-12` |
| `docs/ling/builtin-plugins/core-settings/02-设计与接口.md` | 五个方法、文件格式、原子替换、版本迁移 |

一句话记：`write_config` 由内核记账、本插件落盘；账本不在插件手里，因为插件自己会被卸载。

---

## 5. `core-plugin-manager`

补命令行不做的四件事：依赖树、孤儿数据扫描、批量启停、变更预演。

详细设计见 `docs/ling/builtin-plugins/core-plugin-manager/` 下三份。

本期只实现孤儿扫描与目录占用统计；依赖树、预演、批量都要到 M3 才能做，前提是依赖图与内核写方法。

---

## 6. `core-job`

按五段 cron 触发对插件方法的调用，任务定义存在配置里（可导出、可还原）。

详细设计见 `docs/ling/builtin-plugins/core-job/` 下三份。

**它与直觉做法的区别**：不起自己的线程。宿主是单线程内核，插件线程调 `call` 会与内核写表并发。改为内核每 200 毫秒广播一次 `kernel.tick`，本插件在回调里检查并执行，全程在内核线程上。

---

## 7. `core-log`

收集插件日志，写入 `<数据根>/logs/<插件名>-日期.log`，并提供查询。

详细设计见：

| 文档 | 内容 |
|---|---|
| `docs/ling/builtin-plugins/core-log/00-总览与边界.md` | 定位、不做什么、没装它时的降级 |
| `docs/ling/builtin-plugins/core-log/01-需求与用例.md` | 场景、用例 `CL-01` 至 `CL-10`、本期不做的 |
| `docs/ling/builtin-plugins/core-log/02-设计与接口.md` | 三个方法的参数与返回、文件布局、失败处理、大文件 |

与内核日志的分工只有一句：**行格式相同，文件各写各的；内核日志不能卸，本插件能卸。**

**本期偏差**：`docs/ling/04-详细设计/03-上下文与效应账本.md` 的 `Context` 十个方法里没有日志接口，所以 MVP 阶段插件直接调 `core-log.write`。等 `Context` 补上日志方法后改为经内核转发，两条路径并存一段时间再收敛。

## 8. 无特权与可卸载

### 8.1 同规范的具体含义

`LING-REQ-078` 要求内置插件不获得内核特权。具体到五处：

| 方面 | 内置插件 | 业务插件 |
|---|---|---|
| 清单字段 | 同一套，无额外字段 | 同一套 |
| 方法注册 | 经 `Context`，过门禁 | 同上 |
| 能力声明 | 必须在 `capabilities` 里声明 | 同上 |
| 命名空间 | 必须以 `core-xxx.` 开头 | 以自己的编号开头 |
| 账本 | 有，停用同样撤销 | 同上 |

唯一区别在装载时机：内置插件由宿主在首次启动时自动安装，业务插件由用户安装。

### 8.2 卸载后果矩阵

| 卸掉 | 宿主能启动吗 | 命令行能用吗 | 丢什么 |
|---|---|---|---|
| `core-ui` | 能 | 能 | 网页界面 |
| `core-settings` | 能 | 能 | 配置读写（插件改用 `data/`），已登记配置效应撤销时记 `E_UNDO_FAILED` |
| `core-plugin-manager` | 能 | 能 | 依赖树、孤儿清理、批量、预演 |
| `core-job` | 能 | 能 | 定时任务不再触发 |
| `core-log` | 能 | 能 | 插件日志退化到 stderr，`logs <编号>` 不可用 |
| 五个全卸 | 能 | 能 | 上述全部；内核与其他插件不受影响 |

`LING-REQ-081` 只点名了 `core-ui` 与 `core-log`，本文把矩阵补全：五个都可以卸，都能启动。

### 8.3 预装与升级

| 场景 | 行为 |
|---|---|
| 首次启动且 `plugins/` 为空 | 安装全部五个（`LING-REQ-079`） |
| 升级带来新内置插件 | 自动安装；安装前校验 `min_host`，不满足则跳过并记 warn（`LING-REQ-080`） |
| 用户主动卸掉某个内置插件 | 升级不再自动装回；只有用户手动 `install` 才恢复 |
| 内置插件编号被业务插件占用 | 内置插件不装，记 warn，不覆盖业务插件 |

第三条是「尊重用户意图」：用户卸掉 `core-log` 说明他不要，升级时硬装回去等于跟用户对着干。

## 9. 源码与产物

### 9.1 源码位置

| 插件 | 源码 |
|---|---|
| `core-ui` | `main/builtin-plugins/core-ui/` |
| `core-settings` | `main/builtin-plugins/core-settings/` |
| `core-plugin-manager` | `main/builtin-plugins/core-plugin-manager/` |
| `core-job` | `main/builtin-plugins/core-job/` |
| `core-log` | `main/builtin-plugins/core-log/` |

`LING-REQ-082` 要求源码在 `main/builtin-plugins/<编号>/`，构建产物按普通插件路径进入 `plugins/<编号>/`。

### 9.2 为什么不放在 `plugins/` 下

`plugins/` 目录是运行时的安装位置，构建产物在那里；源码放在 `main/builtin-plugins/` 是因为它们与内核同仓库、同构建、同版本发布。

若源码也放 `plugins/`，会与「`plugins/` 是安装目录」的语义冲突：用户会看到既有源码又有产物的目录，无法判断哪个是「已安装的」。

### 9.3 构建后的一致性检查

内置插件的产物进入 `plugins/<编号>/` 后，与业务插件不可区分——这是刻意的。要验证「内置插件确实无特权」，最直接的办法就是让它走一遍普通插件的装载路径。

因此不设置任何「内置标记」字段：清单里没有 `builtin = true` 这样的字段。需要知道哪些是内置时，读内置清单列表（编进宿主的常量表）。

### 9.4 MVP 阶段的实际范围

MVP 只做三个内置插件（`11-MVP 范围.md` §4.2 第三条），每个插件也只做与「宿主能跑起来、能被使用者用上」直接相关的方法：

| 插件 | MVP 已实现 | 后补 |
|---|---|---|
| `core-settings` | `write`、`get`、`list`、`export`、`import` | —— |
| `core-log` | `write`、`tail`、`query` | 与 `Context` 日志接口打通（MVP 的 `Context` 没有日志方法，插件直接调 `core-log.write`） |
| `core-plugin-manager` | `orphans`、`sizes` | 依赖树、变更预演、批量操作（依赖 M3 的调和计算与内核写方法） |

`core-plugin-manager` 后三项的共同前提是「能拿到一份计划」与「能调内核的写方法」。MVP 既无依赖图，也不允许插件调 `kernel.*` 的写方法（那是管理端口的权限），所以这三项留到 M3。

## 10. 已定结论

本节原为未决问题，2026-10-29 逐条按建议结案。结论里标「本期设定」的，是没有需求依据、由本文估定的取值——写代码时觉得不对可以改，改这里一处即可，不影响需求与接口。

| # | 事项 | 结论 | 落点 |
|---|---|---|---|
| 1 | `core-` 前缀的占用检查要加进 `04/02` §3.4 的校验顺序 | 加为第 11 步，失败返回 `E_MANIFEST_INVALID` | §2.3、04/02 |
| 2 | `core-job` 的时间表达式格式未定（cron 还是简化写法） | 用五段 cron，生态熟、文档多；不支持秒级 | `docs/ling/builtin-plugins/core-job/02-设计与接口.md` 第 2 节 **本期设定** |
| 3 | 界面端口段 8010 起是否够用（多实例场景） | 单实例设计，够用 | `docs/ling/builtin-plugins/core-ui/02-服务端与接口.md` 第 1 节 |
| 4 | `core-settings` 4 MB 上限没有依据 | 按「几百个键、每键几十字节」估，留两个数量级余量 | `docs/ling/builtin-plugins/core-settings/02-设计与接口.md` 第 1 节 **本期设定** |
