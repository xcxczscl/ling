# ling 04/07 内置插件

> 状态：初定 | 最后更新：2026-10-28
> 依据：`docs/ling/01-需求规格.md` §3.9

五个内置插件随宿主分发、默认预装。它们**没有任何特权**：与业务插件用同一套清单、同一条路由、同一套门禁，也可以被卸载。

本文写清每个插件做什么、边界在哪、卸载后宿主退化成什么样。

## 2. 五个插件一览

### 2.1 全表

| 编号 | 名称 | 轨道 | 职责 | 依赖 |
|---|---|---|---|---|
| `core-ui` | 本机网页界面 | 侧车（C++） | 提供浏览器可访问的操作界面 | 无 |
| `core-settings` | 配置存储 | 进程内 | 为其他插件提供键值配置的读写与撤销 | 无 |
| `core-plugin-manager` | 插件管理器 | 进程内 | 依赖树展示、孤儿数据清理、批量操作 | `core-settings@1` |
| `core-job` | 定时任务 | 进程内 | 按时间表达式触发对插件方法的调用 | `core-settings@1` |
| `core-log` | 日志收集 | 进程内 | 收集插件日志、提供查询 | 无 |

### 2.2 为什么是这五个

| 插件 | 不做会怎样 |
|---|---|
| `core-ui` | 只能用命令行，看不到状态变化与日志流 |
| `core-settings` | 插件无处存配置，只能全塞进 `data/`，而配置需要「可撤销、可导出、可查」 |
| `core-plugin-manager` | 装卸与状态查询命令行已有，但「哪些插件在等依赖」「哪些 `data/` 是孤儿」这类问题没有入口 |
| `core-job` | 没有定时能力，所有周期性工作要靠插件自己起线程 |
| `core-log` | 插件日志只能写 stderr，重启后丢失 |

这五项的共同点：**它们是「给其他插件用的公共服务」，不是业务功能**。业务插件不该各自实现一遍日志收集或定时器。

### 2.3 编号与版本

| 项 | 规定 |
|---|---|
| 编号前缀 | 一律 `core-` |
| 编号占用 | `core-` 前缀保留给内置插件，业务插件不得使用；清单校验时检查 |
| 版本起点 | 1.0.0，随宿主版本一起升 |
| 版本兼容 | 内置插件的 `api` 与宿主一致；宿主升 `api` 主版本时，内置插件同版本一起换 |

前缀保留的判定放在清单校验（`04/02` §3.4）里，新增一条检查：`id` 以 `core-` 开头且不在内置清单里时拒绝装载，返回 `E_MANIFEST_INVALID`。

## 3. `core-ui`

### 3.1 职责

提供浏览器可访问的界面：插件列表与状态、装载卸载、调和过程、日志查看、配置编辑。

**它不承担任何业务功能。** 界面里出现的一切都来自调用其他插件的方法或内核方法。

### 3.2 形态与端点

| 项 | 规定 |
|---|---|
| 轨道 | 侧车（C++ 可执行文件，见 `02` §A-8） |
| 监听 | `127.0.0.1` 上从 8010 起选空闲端口 |
| 端口记录 | 写入 `registry.json` 的 `ui_port` 字段 |
| 与管理端口的关系 | 界面内部以客户端身份连管理端口，不用自己的端口转发 |

界面端口从 8010 起，与管理端口的 7900 至 7999 段隔开：管理端口会顺延到整段末尾，若界面也落在这一段，宿主顺延时就会抢走界面端口，排查时难以分辨。

界面连管理端口要认证：宿主在启动 `core-ui` 时经环境变量传入口令，界面不读 `session.json`——读文件意味着界面必须知道数据根，而它不需要知道。

### 3.3 它提供的方法

| 方法 | 作用 |
|---|---|
| `core-ui.open` | 在默认浏览器里打开界面（命令行与界面互跳用） |
| `core-ui.status` | 返回界面进程的状态（监听地址、连接数、启动时间） |

界面本身不注册业务方法。它调用的方法包括内核的 `kernel.*` 与其他插件公开的方法。

### 3.4 崩溃与重连

`LING-REQ-116`：界面崩溃不影响宿主与其他插件，2 秒内自动重启并可重连。

| 项 | 规定 |
|---|---|
| 崩溃检测 | 宿主发现界面进程退出，广播 `kernel.plugin.state`，`state = crashed` |
| 重启 | 按 `sidecar.restart = "on-crash"`，2 秒内重启一次 |
| 重连 | 新进程重新握手、重新注册方法；浏览器侧刷新即可，无需重启宿主 |
| 页面上正在进行的操作 | 丢失，需要用户重做 |

页面上的操作不做断点续传：界面的定位是「看状态、点按钮」，不是长事务编辑器。

## 4. `core-settings`

### 4.1 存储格式

| 项 | 规定 |
|---|---|
| 文件 | `<数据根>/settings.json` |
| 结构 | 顶层两个键：`schema_version`（整数）与 `entries`；`entries` 的键为 `<插件编号>.<键名>`，值为 `{"v": <任意 JSON>, "updated_at": "<时间>"}` |
| 写入 | 全量重写 + 原子替换（写临时文件、`fsync`、`rename`） |
| 读取 | 启动时全量载入内存，之后读内存 |
| 大小上限 | 单文件 4 MB，超出时写入返回 `E_IO` |

全量重写对小文件最简单：几百个键的文件在几十 KB 量级，每次重写耗时可忽略，而且不会出现「写了一半」的中间状态。

`schema_version` 用于升级时的配置迁移：读到高于当前的版本号则拒绝启动，避免旧版本把不认识的字段丢掉。迁移规则见 `docs/ling/08-部署与发布.md` §5.2。

### 4.2 键空间与隔离

| 规则 | 内容 |
|---|---|
| 前缀 | 键必须以 `<调用方编号>.` 开头 |
| 越权 | 前缀不符返回 `E_NAMESPACE_VIOLATION` |
| 列举 | 插件只能列出自己前缀下的键 |
| 删除 | 值写为 `null` 视为删除该键 |

`core-settings` 自己也是一个插件，它的配置键前缀是 `core-settings.`。

### 4.3 与账本的关系

`write_config` 走的是 `Context`（`04/03` §6.2）：

1. 调用方交旧值与新值给内核。
2. 内核记账本条目 `ConfigWritten`，含旧值。
3. 内核调 `core-settings.write` 落盘。

撤销时内核按账本把旧值写回。**账本由内核持有，不由 `core-settings` 持有**——这样即使 `core-settings` 被卸载，已登记的配置效应仍可撤销（撤销时若 `core-settings` 不在，返回 `E_PLUGIN_MISSING` 并记 `E_UNDO_FAILED`）。

### 4.4 导出与导入

| 方法 | 作用 |
|---|---|
| `core-settings.export` | 导出全部键为 JSON，供备份 |
| `core-settings.import` | 导入，只补充不存在的键，不覆盖已有值 |

导入不覆盖是刻意的：覆盖会让「用户误导入一份旧备份」直接冲掉当前配置。

## 5. `core-plugin-manager`

### 5.1 职责

命令行已经能做装卸与状态查询。`core-plugin-manager` 补的是命令行不做的四件事：

| 能力 | 说明 |
|---|---|
| 依赖树展示 | 给定编号，列出它的上游与下游，标注未满足项 |
| 孤儿数据清理 | 找出只剩 `data/` 的目录，列出占用空间，确认后删除 |
| 批量操作 | 一次启用或停用一组插件，按拓扑序执行 |
| 变更预演 | 给定一次操作，先算出会连带激活或停用哪些插件，不执行 |

### 5.2 与内核方法的分工

| 能力 | 谁提供 | 理由 |
|---|---|---|
| 装载、卸载、启用、停用、重载、状态查询 | 内核 `kernel.*` | 卸掉界面也要能用，必须在内核 |
| 依赖树、孤儿清理、批量、预演 | 本插件 | 便利功能，可以没有 |

判据：**「没有它宿主就不成立」的能力归内核，「让操作更省事」的能力归插件**（`00` §2.1 的零内容边界）。

### 5.3 变更预演的实现

预演不执行任何动作，只调调和的计算阶段（`04/04` §5）拿一份计划，把它渲染成「将会激活这几个、停用那几个」的列表，然后丢弃计划。

这要求调和的计算与执行可分：本文档体系里它们是分开的（§5 计算、§6 执行），所以预演能直接复用计算，不需要另写一套模拟逻辑。

## 6. `core-job`

### 6.1 职责

按时间表达式触发对插件方法的调用。

| 方法 | 作用 |
|---|---|
| `core-job.schedule` | 登记一个任务：表达式、目标方法、参数、是否补跑 |
| `core-job.cancel` | 取消一个任务 |
| `core-job.list` | 列出本插件登记的任务 |

任务登记产生账本条目（属于 `MethodRegistered` 之外的类别吗？不——它是配置写入）。**任务定义存在配置里**（键 `core-job.<任务名>`），所以登记任务就是一次 `write_config`，可撤销、可导出。

### 6.2 错过与并发

| 情形 | 行为 |
|---|---|
| 到点时宿主不在运行 | 不补跑（默认），除非任务声明 `catch_up = true` |
| 到点时目标插件未激活 | 跳过本次，记 warn，不重试 |
| 上一次还没跑完，下一次到点 | 跳过本次，记 warn，不排队 |
| 任务执行超过 30 秒 | 按调用超时处理，返回 `E_TIMEOUT`，任务继续存在 |

「跳过不排队」是关键：定时任务排队会在慢任务上累积成雪崩。宁可漏一次，不要堆积。

### 6.3 与调和的关系

`core-job` 只在目标插件**已激活**时发调用。它不触发调和，也不等待调和——目标插件因为依赖缺失而停用时，任务静默跳过。

这条划清了边界：任务调度不负责「让插件变得可用」，那是调和的事。

## 7. `core-log`

### 7.1 职责

收集插件日志，写入 `<数据根>/logs/<编号>-YYYY-MM-DD.log`，并提供查询。

| 方法 | 作用 |
|---|---|
| `core-log.write` | 接收一条日志（由 `Context` 的日志接口调用） |
| `core-log.query` | 按编号、日期、级别查询 |
| `core-log.tail` | 返回最近 N 条 |

插件不直接调 `core-log.write`，而是调 `Context` 的日志接口；内核判断 `core-log` 是否在，在则转发，不在则写 stderr。

### 7.2 与内核日志的关系

| | 内核日志 | `core-log` |
|---|---|---|
| 谁写 | 内核 | 其他插件（经内核转发） |
| 落盘 | `<数据根>/logs/kernel-YYYY-MM-DD.log` | `<数据根>/logs/<编号>-YYYY-MM-DD.log` |
| 可卸载 | 不可 | 可 |
| 查看 | `logs --kernel` 直读文件 | `logs <编号>` 经本插件 |
| 字段与格式 | 同一套 | 同一套 |

格式统一由 `04/02` 的字段定义约束，两边的行结构相同，可以拿同一个脚本解析。

### 7.3 未安装时的降级

`core-log` 不在时：

1. 插件调日志接口不报错，返回成功。
2. 日志写到 stderr，每条带 `<编号> ` 前缀。
3. `logs <编号>` 返回 `E_PLUGIN_MISSING`，`message` 含「core-log 未安装」。

第 1 条要说明：日志写失败不该让业务逻辑失败。日志是诊断手段，不是业务流程的一环。

## 8. 无特权与可卸载

### 8.1 同规范的具体含义

`LING-REQ-078` 要求内置插件不获得内核特权。具体到五处：

| 方面 | 内置插件 | 业务插件 |
|---|---|---|
| 清单字段 | 同一套，无额外字段 | 同一套 |
| 方法注册 | 经 `Context`，过门禁 | 同上 |
| 能力声明 | 必须在 `capabilities` 里声明 | 同上 |
| 命名空间 | 必须以 `core-xxx.` 开头 | 以自己的编号开头 |
| 账本 | 有，停用同样撤销 | 同上 |

唯一区别在装载时机：内置插件由宿主在首次启动时自动安装，业务插件由用户安装。

### 8.2 卸载后果矩阵

| 卸掉 | 宿主能启动吗 | 命令行能用吗 | 丢什么 |
|---|---|---|---|
| `core-ui` | 能 | 能 | 网页界面 |
| `core-settings` | 能 | 能 | 配置读写（插件改用 `data/`），已登记配置效应撤销时记 `E_UNDO_FAILED` |
| `core-plugin-manager` | 能 | 能 | 依赖树、孤儿清理、批量、预演 |
| `core-job` | 能 | 能 | 定时任务不再触发 |
| `core-log` | 能 | 能 | 插件日志退化到 stderr，`logs <编号>` 不可用 |
| 五个全卸 | 能 | 能 | 上述全部；内核与其他插件不受影响 |

`LING-REQ-081` 只点名了 `core-ui` 与 `core-log`，本文把矩阵补全：五个都可以卸，都能启动。

### 8.3 预装与升级

| 场景 | 行为 |
|---|---|
| 首次启动且 `plugins/` 为空 | 安装全部五个（`LING-REQ-079`） |
| 升级带来新内置插件 | 自动安装；安装前校验 `min_host`，不满足则跳过并记 warn（`LING-REQ-080`） |
| 用户主动卸掉某个内置插件 | 升级不再自动装回；只有用户手动 `install` 才恢复 |
| 内置插件编号被业务插件占用 | 内置插件不装，记 warn，不覆盖业务插件 |

第三条是「尊重用户意图」：用户卸掉 `core-log` 说明他不要，升级时硬装回去等于跟用户对着干。

## 9. 源码与产物

### 9.1 源码位置

| 插件 | 源码 |
|---|---|
| `core-ui` | `main/builtin-plugins/core-ui/` |
| `core-settings` | `main/builtin-plugins/core-settings/` |
| `core-plugin-manager` | `main/builtin-plugins/core-plugin-manager/` |
| `core-job` | `main/builtin-plugins/core-job/` |
| `core-log` | `main/builtin-plugins/core-log/` |

`LING-REQ-082` 要求源码在 `main/builtin-plugins/<编号>/`，构建产物按普通插件路径进入 `plugins/<编号>/`。

### 9.2 为什么不放在 `plugins/` 下

`plugins/` 目录是运行时的安装位置，构建产物在那里；源码放在 `main/builtin-plugins/` 是因为它们与内核同仓库、同构建、同版本发布。

若源码也放 `plugins/`，会与「`plugins/` 是安装目录」的语义冲突：用户会看到既有源码又有产物的目录，无法判断哪个是「已安装的」。

### 9.3 构建后的一致性检查

内置插件的产物进入 `plugins/<编号>/` 后，与业务插件不可区分——这是刻意的。要验证「内置插件确实无特权」，最直接的办法就是让它走一遍普通插件的装载路径。

因此不设置任何「内置标记」字段：清单里没有 `builtin = true` 这样的字段。需要知道哪些是内置时，读内置清单列表（编进宿主的常量表）。
