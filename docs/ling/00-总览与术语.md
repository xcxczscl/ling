## 1. ling 是什么

### 1.1 一句话

ling 是一个**零内容的插件宿主**：它自己不提供任何功能，只负责让插件能安全地装上、调用、卸载和替换。

### 1.2 "零内容"的边界

| ling 有（机制） | ling 没有（内容） |
|---|---|
| 加载、卸载、热更新插件 | 窗口、导航、主题、图标 |
| 转发插件之间的调用 | 任何界面页面 |
| 广播事件 | 设置页面 |
| 检查插件声明的能力 | 插件管理的操作界面 |
| 解析依赖、自动激活与停用 | 任何业务概念（什么是文件、什么是账单） |
| 管理端口（供命令行连接） | 业务逻辑 |
| 可逆效应账本（保证卸载干净） | 文件存储、数据库、网络协议 |

判断标准：**少了它宿主就不成立**的功能属于 ling；**用户能感知到的某个用途**属于插件。

### 1.3 为什么这么分

- 功能都在插件里，加功能不用改宿主；
- 宿主代码量小，长期维护成本可控；
- 插件出问题只影响自己，宿主负责隔离与恢复。

## 2. 定位、目标与非目标

### 2.1 定位

**插件宿主 + 功能插件**。ling 本体只做宿主，全部实用功能由插件提供。

### 2.2 目标

| 目标 | 具体含义 |
|---|---|
| 个人使用 | 单机、单用户；不需要账号体系、多用户权限、云端同步 |
| 当工具用 | 解决自己实际要做的事，不追求成为通用框架 |
| 插件可独立演进 | 单个插件坏了或改坏了，宿主和其他插件不受影响 |
| 装了就能用 | 装插件不重启宿主，改插件不重启宿主 |
| 多平台 | 同一套插件生态在多个操作系统上可用；平台清单见 2.4 |

### 2.3 非目标

| 非目标 | 说明 |
|---|---|
| 不做大型系统 | 插件数量按几十个规划，不做分布式部署、不做多节点协同 |
| 不做多人协作平台 | 不做多人同时使用、不做权限分级 |
| 不做插件市场 | 不做在线分发、评分、付费 |
| 不做通用开发框架 | 只为自己的插件服务，不为第三方生态设计向后兼容承诺 |

### 2.4 平台

多平台是目标，不是"以后再说"。三个平台的角色不同：

| 平台 | 角色 | 说明 |
|---|---|---|
| Windows | 主要开发与使用平台 | 优先保证功能完整、优先做 MVP |
| Linux | 次要运行平台 | 功能对齐 Windows，沙箱能力更完整 |
| Android | 受限运行平台 | 受系统权限限制，部分功能降级；具体降级范围待定 |

插件在不同平台上的产物不同（Windows 是 `.dll`，Linux 是 `.so`，Android 是 `.so`），宿主负责按当前平台装载对应产物。

### 2.5 规模参照

设计按以下量级校验，超出即视为跑偏：

| 维度 | 量级 |
|---|---|
| 插件数量 | 几十个 |
| 单机数据量 | TB 级 |
| 同时在线用户 | 1 人 |

## 3. 谁在用 ling

| 角色 | 与 ling 的接触点 |
|---|---|
| 插件作者（我自己） | 按插件接口规范写动态库或侧车程序，放进插件目录 |
| 使用者（我自己） | 通过插件提供的网页界面操作；通过 `ling` 命令行管理宿主与插件 |
| 插件（彼此） | 通过宿主互相调用、订阅事件；不直接通信 |
| 维护者（我自己） | 读运行时预案排查故障；用 `ling reload` 更新插件 |

## 4. 贯穿示例：装一个插件的全过程

后续文档都用这个例子说明机制。

| 步骤 | 做了什么 | 触发的机制 |
|---|---|---|
| 1 | 装好 ling，首次启动 | 内核启动、管理端口监听 |
| 2 | 内置插件自动加载 | 清单解析 → 依赖解析 → 依次激活 |
| 3 | 打开浏览器看到插件管理页 | 界面由 core-ui 插件提供（ling 本身不开窗口） |
| 4 | 把 resources-manager 插件目录放进去，执行 `ling install resources-manager` | 重算依赖 → 激活 → 界面出现入口 |
| 5 | 早已装好但停用的记账插件自动恢复工作 | 它依赖的能力满足 → 自动激活 |
| 6 | 改了 resources-manager 的代码，执行 `ling reload resources-manager` | 停用旧版 → 按账本撤销效应 → 装载新版 → 重新激活；宿主不重启 |
| 7 | 执行 `ling uninstall ledger` | 倒序执行账本：注销方法、退订事件、撤下界面、停止侧车 |
| 8 | 卸载了 resources-manager，记账插件的"归档文件"按钮消失 | 依赖失效 → 自动停用（挂起，不是卸载）；装回后自动恢复 |

这个例子回答三个核心问题：

| 疑问 | 答案 |
|---|---|
| 卸载会不会留垃圾 | 不会，账本逐条撤销 |
| 装新插件要不要重启 | 不用，重算依赖后自动激活 |
| 改插件代码要不要重启全局 | 不用，只换那一个插件 |

## 5. 术语

### 5.1 分级说明

- **公共术语**（宿主、插件、能力、事件、侧车、上下文、热更新）统一登记在 `docs/common/01-术语表.md`，本文不重复。
- **ling 专属术语**在本节定义，其他文档直接引用本节，不再各自解释。

术语格式：定义 + 例子 + 它不是什么。最后一项用于排除常见误解。

### 5.2 与加载相关

| 术语 | 定义 | 例子 | 它不是什么 |
|---|---|---|---|
| 清单 | 插件目录里的 `plugin.toml`，写明插件编号、版本、需要的能力、依赖谁 | resources-manager 的清单声明需要读写文件能力 | 不是说明文档，是给程序解析的配置 |
| 动态库 | 能被别的程序在运行时打开的代码文件：Windows 是 `.dll`，Linux 是 `.so` | Rust 插件产物 `resources_manager.dll` | 不是可执行程序，它不能独立运行 |
| 卸载 | 把插件从系统中移除：按账本撤销全部效应 → 删除或停用其文件 | `ling uninstall ledger` | 不等于停用，停用只是暂停 |
| 停用 | 插件暂停工作但保留安装：撤销效应，文件仍在 | resources-manager 缺失时记账插件处于停用 | 不是卸载，可随时恢复 |
| 激活 | 停用的插件恢复工作：重新登记效应、恢复依赖 | 装回 resources-manager 后记账插件被激活 | 不是"启动"；ling 里激活专指依赖满足后进入工作状态 |

### 5.3 与上下文相关

| 术语 | 定义 | 例子 | 它不是什么 |
|---|---|---|---|
| 效应账本 | 宿主为每个插件单独记的账：注册过什么、每项怎么撤销 | 账上记着"第 1 条：注销方法 scan.start" | 不是操作日志；日志给人看，账本给机器执行 |
| 逆操作 | 撤销某次修改的那个函数，随修改一起登记 | 注册方法时同时交出"注销该方法"的闭包 | 不是删除数据，是把状态精确恢复到修改前 |
| 效应种类 | 被登记的修改类型：注册方法、订阅事件、配置写入、启动侧车、登记停用回调 | 一个插件最多 5 类效应 | 不是业务动作；界面贡献记在 core-ui 自己的账上 |
| 隔离命名空间 | 每个插件的效应带自己的编号前缀，互不可见 | 记账插件的方法都在 `ledger.` 前缀下 | 不是安全沙箱；内存仍共享，这是逻辑隔离 |
| 违规效应 | 插件绕过上下文直接做的修改 | 直接调用系统删除文件而不登记 | ling 检测不到，视为插件作者违约 |

### 5.4 与依赖相关

| 术语 | 定义 | 例子 | 它不是什么 |
|---|---|---|---|
| 需求声明 | 清单里的 `requires` 段：需要哪些能力、需要哪个插件的哪个版本 | `requires = ["capability:fs", "plugin:resources-manager@1.x"]` | 不是编译期依赖，是运行时每次重判的需求 |
| 满足 | 某条需求当前成立 | resources-manager 已安装且已激活 → 满足 | —— |
| 依赖图 | 所有插件需求连成的有向图，节点是插件或能力，边是依赖 | 装卸插件后图会变 | 不是文件目录树 |
| 调和 | 把当前插件状态与需求声明重新对齐的过程：先算出该激活谁、该停用谁，再按顺序执行 | 装上 resources-manager 后，记账插件由停用转为激活 | 不是定时任务；它由事件触发，且同一段连续变化合并成一次 |
| 激活计划 | 调和算出的执行清单：按什么顺序激活谁、停用谁 | 先 core-ui，再 resources-manager，最后 ledger | 不是任务队列，是一次性推导出的有序步骤 |
| 传递依赖 | A 依赖 B、B 依赖 C，则 A 间接依赖 C | 记账 → resources-manager → core-ui | —— |
| 拓扑序 | 按依赖先后排出的顺序：被依赖的排在前面，依赖它的排在后面 | 激活时先 core-ui、再 resources-manager、最后记账 | 不是字母序，也不是安装时间顺序 |
| 循环依赖 | A 依赖 B、B 又依赖 A，图上成环 | —— | 不允许的状态，检测到即拒绝加载并报错 |

### 5.5 与热更新相关

| 术语 | 定义 | 例子 | 它不是什么 |
|---|---|---|---|
| 重载 | 换某插件新版本的完整流程：停用 → 撤销效应 → 替换产物 → 装载 → 重新激活 | `ling reload resources-manager` | 不是重启整个程序；其他插件不受影响 |
| 持久文件 | 插件自己存在 `plugins/<编号>/data/` 下的状态文件 | resources-manager 的目录数据库 | 不是插件的可执行产物本身 |
| 装载失败回滚 | 新版本装载出错时把旧版本装回，回到重载前状态 | 新清单写错 → 自动回滚到旧版 | 不是留下半新半旧的中间状态 |

### 5.6 与日志相关

| 术语 | 定义 | 例子 | 它不是什么 |
|---|---|---|---|
| 内核日志 | 宿主自己写的运行记录，内置实现，不依赖任何插件 | 装插件失败时记下 `E_MANIFEST_INVALID` 与缺哪个字段 | 不是插件日志；也不是效应账本——账本给机器执行撤销，日志给人排查 |
| 插件日志 | 插件通过 `Context` 交出来的运行记录，由 core-log 收集 | resources-manager 记下"扫描了 3 万个文件" | 不是内核日志；宿主不替插件判断该记什么 |
| core-log | 内置插件，为其他插件提供日志收集与查询的公共服务 | `ling logs resources-manager` 读它 | 不是内核日志的载体；卸掉它不影响宿主自身记录 |
| trace id | 一次操作分配到的短编号，随请求传递，串起它引发的全部日志 | 一条 `install` 命令引发的调和、激活、侧车启动共用同一个 id | 不是会话编号；它只覆盖一次操作，不覆盖一次连接 |
| 日志级别 | 日志的重要程度：error / warn / info / debug | 默认 info，排查时开 debug 记每次调用 | 不是分类标签；级别决定是否输出，来源字段才决定属于谁 |

### 5.7 与运行管理相关

| 术语 | 定义 | 例子 | 它不是什么 |
|---|---|---|---|
| 能力门禁 | 两道检查：注册方法时查清单里声明了什么，调用瞬间查当前还有效的能力 | 方法要用 `fs` 能力而清单没声明，注册即被拒 | 不是沙箱；它只管资格，不管具体访问哪条路径 |
| 管理端口 | 宿主监听在本机回环地址上的命令通道，命令行与界面都经它管理宿主 | 默认端口 7950 | 不是对外服务；不监听任何非回环地址 |
| 命令帧 | 管理端口上一条命令的完整报文，含命令名、参数与 trace id | 一条 `plugins` 查询 | 不是 HTTP 请求，帧格式由 `docs/ling/04-详细设计/06-管理端口与命令行.md` 定义 |
| 数据根 | 宿主存放插件、插件数据与日志的根目录，按平台取不同位置 | Windows 上是 `%APPDATA%\ling` | 不是源码目录，仓库里不存在这个路径 |
| 内核事件 | 宿主自己广播的事件，主题以 `kernel.` 开头 | `kernel.plugin.state`、`kernel.plan.step` | 不是插件事件，不由任何插件产生 |
