## 2. 架构总览

### 2.1 五层

```
┌──────────────────── 表现层（全部由插件提供，宿主零界面）──────────────┐
│  浏览器 ──HTTP──▶ core-ui 侧车（页面 + 数据接口）                     │
│  窗口视图（可选，系统 WebView 指向 core-ui 端口）                      │
│  ling 命令行 ──本机 TCP──▶ 管理端口                                   │
├──────────────────── 插件层 ────────────────────────────────────────┤
│  内置插件（随宿主发行，可卸载）：                                      │
│    core-ui（侧车）· core-settings · core-plugin-manager                │
│    core-job · core-log  （后三个按需安装）                            │
│  业务插件：resources-manager · player · 其他自有插件                   │
│  插件之间：只经内核路由互调，只经内核事件互听，不直接链接                │
├──────────────────── 内核层（4 项服务 + 3 个机制）───────────────────┤
│  服务：① 方法路由  ② 事件广播  ③ 能力门禁  ④ 依赖解析与调和          │
│  机制：上下文 Context · 可逆效应账本 · 配置调和（是④的执行方式）        │
├──────────────────── 通道层 ────────────────────────────────────────┤
│  装载通道：dlopen 进程内动态库 / 拉起侧车进程                          │
│  管理端口：只监听 127.0.0.1，首帧口令认证                              │
├──────────────────── 平台层 ────────────────────────────────────────┤
│  C++17 运行时 · 系统动态库装卸载 · 本地 TCP · 文件系统                 │
└───────────────────────────────────────────────────────────────────┘
```

### 2.2 组件全景

```
插件代码 ──只能碰到──▶ Context（唯一的门）
                         │ 门后：
                         ├─ 效应账本：门每办一件事记的账
                         ├─ 方法路由：大表「谁提供什么方法」
                         ├─ 事件广播：大表「谁订阅了什么主题」
                         ├─ 能力门禁：查方法表时顺手查资格
                         ├─ 配置调和：环境变了重算该激活谁
                         └─ 依赖解析：调和用的图算法
                         │ 对外两条通道：
                         ├─ 装载通道：代码怎么进来
                         └─ 管理端口：命令行怎么管理运行中的宿主
```

### 2.3 组件清单

| 组件 | 所在层 | 职责一句话 | 没有它会怎样 |
|---|---|---|---|
| 方法路由 | 内核 | 登记「哪个插件提供哪些方法」，把调用转给目标 | 插件得直接链接彼此的代码，无法单独卸载 |
| 事件广播 | 内核 | 收一个广播，按主题匹配投给所有订阅者 | 广播方得自己维护「完成后通知谁」的名单 |
| 能力门禁 | 内核 | 注册时校验声明、调用瞬间核对生效能力 | 装上插件就等于给了它全部权限 |
| 依赖解析与调和 | 内核 | 读清单建依赖图，算出该激活谁并逐步执行 | 装卸引发的连锁反应只能靠人工重启 |
| 上下文 | 内核机制 | 插件访问共享环境的唯一入口 | 插件随手改全局，卸载无法还原 |
| 效应账本 | 内核机制 | 记录每一次效应及其撤销方式 | 卸载后留下死方法、残留订阅、跑飞的线程 |
| 装载通道 | 通道 | 把代码送进进程（`dlopen` 或拉起侧车） | 代码进不来 |
| 管理端口 | 通道 | 让命令行管理运行中的宿主 | 只能杀进程重启 |
| core-ui 侧车 | 插件 | 提供本机网页界面 | 无界面，命令行仍可用 |

## 3. 设计原则

### 3.1 四条基本原则

| # | 原则 | 一句话 | 违反后果 |
|---|---|---|---|
| P1 | 零内容 | 宿主只提供机制，不提供用户能感知的功能 | 宿主变回「什么都有」的大程序，插件失去意义 |
| P2 | 一切经上下文 | 插件对共享环境的修改必须经 `Context` | 记不了账，卸载不干净、热更新不可用 |
| P3 | 修改必可逆 | 每次修改必须同时给出撤销方式 | 同 P2 |
| P4 | 需求必声明 | 依赖写进清单 `requires`，宿主据此激活与停用 | 依赖变化靠人工重启，插件多了管不过来 |

这四条互相咬合：P1 保证边界，P2 与 P3 是一对（能记账的前提是每次修改都带撤销），P4 让 P2 记录的信息能被自动使用。

### 3.2 两条补充原则

这两条来自 01 的非功能需求，old 里没有单列，本轮补上。

| # | 原则 | 一句话 | 违反后果 | 依据 |
|---|---|---|---|---|
| P5 | 单一状态源 | 同一个事实只存一处，其他位置只存放引用或快照 | 两处不一致时无从判断谁对，修 bug 变成猜谜 | LING-REQ-105、LING-REQ-112 |
| P6 | 失败可观测 | 任何被拒绝或失败的操作都留下可查的记录，不静默吞掉 | 出问题时只能看到「没生效」，看不到为什么 | LING-REQ-110、LING-REQ-112 |

P5 的典型应用：插件状态只存在装载表里，界面与命令行都是读它，不各自维护一份。P6 的典型应用：能力门禁拒绝调用时必须返回错误码并留记录，而不是返回空结果。

## 4. 内核职责边界

### 4.1 四项服务

| # | 服务 | 做什么 | 不做什么 |
|---|---|---|---|
| 1 | 方法路由 | 维护「插件 × 方法名 → 处理函数」的映射；把调用转给目标；同进程直调，跨进程走本地套接字 | 不理解方法含义；不做业务参数校验 |
| 2 | 事件广播 | 按主题模式匹配订阅者；同步派发；单个订阅者超时则跳过并记录 | 不落盘、不重投、不保证送达 |
| 3 | 能力门禁 | 注册时校验方法声明 ⊆ 清单；调用瞬间核对目标插件的生效能力 | 不解释能力语义；不限制具体路径与地址（LING-REQ-027） |
| 4 | 依赖解析与调和 | 建依赖图、校验版本与环、计算激活计划、按拓扑序执行 | 不保存插件业务数据；不替插件迁移数据 |

四项服务都留内核，但代码按模块组织（路由 / 事件 / 门禁 / 依赖），一个模块一个目录。模块化的意义在编译期可替换，不在运行期。

### 4.2 三项机制与两条通道

| 项 | 类型 | 说明 |
|---|---|---|
| 上下文 | 机制 | 插件看到的全部接口；由内核在激活时注入，插件不能自己构造（LING-REQ-028） |
| 效应账本 | 机制 | 每插件一份、只增不改、不落盘、卸载时倒序撤销（LING-REQ-032、033） |
| 配置调和 | 机制 | **不是第五项服务**，是服务④的执行方式：任何配置变化都触发一次「重算计划并逐步执行」 |
| 装载通道 | 通道 | `dlopen` 或拉起侧车进程；动态库装卸必须串行 |
| 管理端口 | 通道 | 只监听 `127.0.0.1`；首帧口令认证；不是第五项服务，是服务①的传输通道 |

「配置调和不是第五项服务」这条要单独强调，因为 old 版把它和四项服务并列，读起来像是五项。它没有独立的职责边界，唯一的作用是把「环境变了」翻译成「该执行哪些步骤」，属于服务④内部。

### 4.3 为什么不把服务做成插件

| 服务 | 做成插件会怎样 | 结论 |
|---|---|---|
| 路由 | 路由表是插件互调用的数据结构本身；做成插件等于把门装在另一个插件里，每次调用多一跳，且该插件崩溃则全系统瘫痪 | 留内核 |
| 事件 | 同路由 | 留内核 |
| 门禁 | 门禁与路由查同一张方法表，拆开要跨插件查询，成本上升且无收益 | 留内核 |
| 依赖解析 | 它驱动装载器，属于特权操作；做成插件需要引入「特权插件」概念，还要解决「谁先加载它」的引导问题 | 留内核 |

代价是内核不可在运行期替换。缓解方式是模块化：真有需要时把某个模块抽成独立动态库，仍然编译进内核。对个人工具的量级，这个代价可以接受。

## 5. 进程与线程模型

### 5.1 四类进程

| 进程 | 内容 | 生命周期 | 崩溃的后果 |
|---|---|---|---|
| ling 主进程 | 内核 + 全部进程内插件 | 常驻，直到 `ling shutdown` | 全部功能停止 |
| 侧车进程 ×N | 每个侧车插件一个可执行文件，含 core-ui | 随插件装载启动，随停用或卸载结束 | 只有该插件失效，宿主与其他插件不受影响 |
| ling 命令行 | 独立小进程，连管理端口 | 执行一次命令即退出 | 无影响 |
| 窗口视图（可选） | 系统 WebView 指向 core-ui 端口 | 用户开关 | 无影响 |

core-ui 走侧车是本文的一条实质决定，理由见 A-8：界面是改动最频繁、最容易出 bug 的部分，放在最需要稳定的进程里是反着来。

### 5.2 主进程内的线程

| 线程 | 数量 | 职责 | 能否改内核状态 |
|---|---|---|---|
| 内核线程 | 1 | 消费状态变更队列，串行执行装载、卸载、注册、记账、调和 | **唯一可以** |
| IO 线程 | 2 | 管理端口收帧解帧、侧车套接字收发 | 不能，解出的请求投给内核线程 |
| 工作线程池 | CPU 核数 − 3，最少 2 条 | 执行插件处理函数、哈希、文件读写 | 不能，需要变更时投给内核线程 |
| 侧车监控线程 | 1 | 阻塞至子进程退出、按 `restart` 策略定时重启 | 不能，退出事件投给内核线程 |

四核机器上是 1 + 2 + 2 + 1 = 6 条线程。这个数量与 LING-REQ-098 的空闲 CPU 预算无关：空闲时四条角色都停在各自的阻塞点上，没有轮询。

**硬约束：动态库的 `dlopen` 与 `dlclose` 只能在内核线程执行。** 原因是装载表只有内核线程能改，而动态库装卸必须与装载表变更处于同一个串行序列中，否则会出现「表里说已装、库里还没加载」的中间态。

插件自己的耗时任务（扫描、转码）在工作线程或插件自开的线程里跑，内核不干预，只要求插件在停用时自行收敛（LING-REQ-036）。

### 5.3 读路径与写路径

这是本文最关键的一节。单线程内核只解决「谁能改状态」，如果连读也要排到内核线程，一次调用会变成两次线程切换，`LING-REQ-089` 的 1 微秒达不到。

所以把操作分成两条路径：

| 路径 | 包含的操作 | 谁执行 | 加锁吗 | 延迟量级 |
|---|---|---|---|---|
| 读路径 | 查路由表找处理函数、查订阅表找订阅者、查能力表判断资格、插件读自己的账本 | 任意线程 | 不加锁 | 纳秒到微秒 |
| 写路径 | 注册方法、订阅事件、写账本、改装载表、改依赖图、装载与卸载 | 只有内核线程，请求先入队 | 不加锁（单线程） | 微秒到毫秒 |

读路径不加锁的实现方式：所有被读的表都是**不可变快照**。内核线程要改表时，构造一份新表，然后把原子指针换过去；正在读旧快照的线程继续用旧快照读完，不受影响。C++17 用 `std::shared_ptr` 配合 `std::atomic_load` / `std::atomic_store` 即可，不需要读写锁。

C++20 取消了 `std::atomic_load(std::shared_ptr*)` 这一组自由函数。当前定在 C++17，可以直接用；若将来升到 C++20，改为手写带引用计数的快照指针，或改用 `std::shared_mutex` 的读多写少方案——后者的代价是读操作也要抢锁，需要重新实测 `LING-REQ-089`。

由此得到的结论：

- 一次同进程调用 = 原子读一次指针 + 两次哈希查找 + 一次函数指针调用，不需要任何跨线程同步。
- 写操作会排队，延迟比读高一个数量级，但写操作发生在注册、装卸、调和阶段，不在调用热路径上。
- 账本只由内核线程写，插件通过 `ledger()` 读到的是最近一次快照，会落后几微秒——账本只用于调试，这个偏差无害。

这条设计也解释了为什么不用「每个服务一把锁」：加锁方案里读操作要抢锁，热路径上的锁竞争会把 1 微秒吃掉，而快照方案里读操作根本看不到写操作。

### 5.4 崩溃与失效边界

| 失效点 | 会连带什么 | 能否恢复 |
|---|---|---|
| 侧车崩溃（含 core-ui） | 只有该插件失效 | 能，账本撤销其效应后按 `restart` 策略重启 |
| 进程内插件在处理函数里崩溃 | 视平台而定：Windows 可捕获并记录，Linux 与 Android 只能记录后终止整个进程 | Windows 能记录后由外部守护重启；其他平台整体退出 |
| 内核线程崩溃 | 全部功能停止 | 只能重启宿主 |
| 管理端口连接断开 | 无 | 重连即可 |
| 动态库卸载失败 | 该插件标记为「已卸载但内存未释放」 | 记录后继续，重启宿主才彻底释放 |

进程内插件崩溃在 Linux 与 Android 上不可捕获，这是平台事实，不是实现缺陷。这条缺口已定下的处理方式有三条：

| 措施 | 内容 |
|---|---|
| 外部守护 | 宿主由 systemd、计划任务或启动脚本看护，退出后自动拉起 |
| 易崩插件改侧车 | 处理二进制数据、解析外部输入、调用第三方库的插件优先走侧车轨道 |
| 崩溃留证 | 无论哪个平台，崩溃时先把调用栈与当前插件编号写入 `logs/`，再终止进程 |

Windows 上的捕获手段定为**向量化异常处理**（`AddVectoredExceptionHandler`），因为它能在捕获点拿到线程与模块信息，而 SEH 的 `__try` 只能得到异常码。

LING-REQ-116 已补入 `docs/ling/01-需求规格.md`，约束界面侧车崩溃后宿主的反应。

## 6. 状态与数据布局

### 6.1 内存态

| 状态 | 所在位置 | 生命周期 |
|---|---|---|
| 路由表（方法名 → 处理函数） | 内核，快照 | 随装载与卸载变化，进程结束即失 |
| 订阅表（主题模式 → 订阅者） | 内核，快照 | 同上 |
| 能力表（插件 → 生效能力） | 内核，快照 | 随清单与撤销名单变化 |
| 装载表（插件 → 状态） | 内核 | 从空开始，启动时按调和重建（LING-REQ-085） |
| 依赖图 | 内核 | 每次配置变化重算 |
| 效应账本 | 内核，每插件一份 | 不落盘，激活时重建（LING-REQ-033） |
| 调和计划与进度 | 内核 | 一次调和的生命周期 |

**插件不得在内存里保留跨调用状态**（LING-REQ-057）。这条是热更新能成立的前提：重载会丢弃旧动态库的全部内存，任何留在内存里的状态都无法迁移。

### 6.2 落盘

```
<数据根>/
  registry.json              管理端口、禁用名单、能力撤销名单、ui_port
  session.json               管理端口口令（0600，每次启动重新生成）
  logs/
    kernel-YYYY-MM-DD.log    内核日志，按天分文件
  plugins/
    <插件编号>/
      plugin.toml            清单；它存在即视为「已安装」（LING-REQ-011）
      <插件编号>.dll|.so     进程内插件的原件，重载时从这里复制
      <插件编号>.<序号>.so   私有副本，装载时复制出、卸载时删除
      sidecar/               侧车插件的可执行文件与资源
      data/                  插件自己的数据，卸载默认保留（LING-REQ-010）
```

只有三处是宿主写的：`registry.json`、`session.json`、`logs/`。插件目录下的内容由插件自己管理，宿主只负责创建 `data/` 目录（LING-REQ-035）。

### 6.3 数据根目录

| 平台 | 默认位置 | 备注 |
|---|---|---|
| Windows | `%APPDATA%\ling` | 程序可放在只读位置 |
| Linux | `~/.local/share/ling` | 遵循 XDG 惯例 |
| Android | 应用私有目录 | 无外部存储权限也能用 |

两种模式并存：默认用系统标准目录；启动参数 `--data-dir` 可以切到程序目录下的 `data/`，用于整个文件夹拷走即迁移的场景。切换时宿主不迁移已有数据，由使用者自己搬——自动迁移要处理跨设备的部分写入失败，收益不抵成本。

## 7. 关键流程的架构视图

本节只写「谁参与、什么顺序、哪一步会失败」，不写函数名与数据结构。

### 7.1 安装插件

| 步 | 参与者 | 动作 | 失败会怎样 |
|---|---|---|---|
| 1 | 命令行 → 管理端口 | 提交来源（目录或压缩包） | 返回错误，宿主无变化 |
| 2 | 内核线程 | 校验清单：编号、版本、api、能力、路径 | 拒绝并在错误信息里指出哪一项（LING-REQ-002） |
| 3 | 内核线程 | 拷贝到 `plugins/<编号>/` | 拒绝；已拷贝的部分删除（LING-REQ-043） |
| 4 | 内核线程 | 重建依赖图，检查版本与环 | 成环则回滚到安装前（LING-REQ-047） |
| 5 | 内核线程 | 计算激活计划 | 计算失败则回滚 |
| 6 | 内核线程 + 工作线程 | 按拓扑序装载与激活，每步广播 `kernel.plan.step` | 依赖缺失则该插件停在待激活，安装本身仍算成功（LING-REQ-042） |

### 7.2 卸载插件

顺序由 LING-REQ-012 固定，架构上的关注点是「每一步都在内核线程里串行」：

1. 按依赖图找出因它才激活的下游，先停用
2. 调它的 `on_deactivate`
3. 账本按序号倒序撤销
4. 从装载表移除，删安装工件，保留 `data/`
5. 触发一次调和

任何一条撤销失败都记录后继续，最后返回「卸载不完整 + 未撤销清单」（LING-REQ-013）。这条决定了账本撤销必须是逐条容错的，不能整体回滚——否则一条坏记录会让卸载永远卡住。

### 7.3 热更新

七步由 LING-REQ-053 固定。架构上的三处要点：

| 要点 | 做法 | 原因 |
|---|---|---|
| 重载窗口内的调用 | 立即返回 `E_PLUGIN_MISSING`，不排队 | 排队会让调用方跟着卡住（LING-REQ-054） |
| 文件替换 | 复制为私有文件名再打开，原件保留 | 直接覆盖原件会让已映射的库出现 SIGBUS（LING-REQ-056） |
| 失败回滚 | 新版装载或激活失败则恢复旧版与下游 | 不能留下半新半旧状态（LING-REQ-055） |

私有副本每次重载留下一个映射，这是 `LING-REQ-101` 需要放宽的直接原因，处理方式见 `docs/ling/02-技术选型.md` 附录 A。

### 7.4 调和与回滚

```
配置变化（安装/卸载/启停/重载/清单变化/启动）
  → 重建依赖图
  → 校验：版本匹配？成环？能力未知？
      ├─ 有错 → 整次变化回滚，图与装载状态回到变化前
      └─ 无错 → 计算计划
  → 执行：激活按拓扑序，停用按反拓扑序，每步一条事件
  → 收敛
```

三条性质决定了实现方式：原子性（计划算不出来就整体回滚）、可观察（每步发事件）、可取消（已执行步骤按账本倒序回滚）。连续变化在 200 毫秒窗口内合并为一次（LING-REQ-049）。

## 8. 横切关注点

### 8.1 六道闸门

只标位置与拦截对象，威胁分析与具体措施归 `docs/ling/06-安全设计.md`。

| 闸门 | 位置 | 拦什么 | 失败错误码 |
|---|---|---|---|
| 清单校验 | 装载通道 | 编号格式、版本格式、api 范围、路径穿越 | `E_MANIFEST_INVALID`、`E_API_MISMATCH` |
| 能力取值校验 | 装载通道 | 清单声明了宿主不认识的能力 | `E_CAPABILITY_UNKNOWN` |
| 命名空间校验 | 路由注册 | 方法名或事件主题没带自己的编号前缀 | `E_NAMESPACE_VIOLATION` |
| 能力注册校验 | 门禁 | 方法声明的 `requires` 超出清单 | `E_CAPABILITY_DENIED` |
| 能力调用校验 | 门禁 | 调用瞬间生效能力不覆盖方法声明 | `E_CAPABILITY_DENIED` |
| 首帧认证 | 管理端口 | 连接后第一帧不是正确口令 | `E_AUTH` |

六道闸门里前五道都在内核线程上串行执行，不存在并发绕过的窗口。

### 8.2 可观测

| 手段 | 内容 | 归属 |
|---|---|---|
| 错误码分层 | 按来源分族：清单、插件、方法、能力、依赖、重载、侧车、认证、超时、载荷 | 取值见 `docs/ling/04-详细设计/02-插件装载与接口.md` |
| 内核事件 | `kernel.plugin.state`（激活、停用、卸载、崩溃）、`kernel.plan.step`（调和每步一条） | 内核广播，任何插件可订阅 |
| 内核日志 | stderr 与 `logs/kernel-YYYY-MM-DD.log`，按天分文件、超 64 MB 轮转、保留 7 天 | 内核自己写 |
| 插件日志 | 由 core-log 插件统一收集 | 未装 core-log 时插件自己落 stderr |

状态变化只以事件为准，不从日志推断（LING-REQ-112）。这条是 P5 单一状态源的直接应用。

### 8.3 平台差异

三端的能力差异与降级方向见 `docs/ling/01-需求规格.md` §5 的平台差异矩阵，本节只记架构层面的三处：

| 差异 | 架构影响 |
|---|---|
| 进程内崩溃捕获 | Windows 可捕获记录，Linux 与 Android 只能终止进程，影响 §5.4 的恢复策略 |
| 动态库后缀与格式 | 装载通道按平台选后缀，不跨平台复用（LING-REQ-114） |
| 管理端口与命令行 | Android 上默认关闭，界面改走进程内直接调用 core-ui 侧车的接口 |

## 9. 架构决策记录

格式统一为：决定 → 被否方案 → 代价 → 理由。前七条沿用 `old/docs/ling/01-宿主设计.md` 附录 A 并逐条重判，A-8 至 A-10 为新增。

### A-1 双向装载形态

- **决定**：进程内插件用 C++ 动态库，其他语言的插件走侧车进程；一个插件只属于一条轨道。
- **被否**：全进程内（非 C++ 语言无法参与）；全侧车（进程内调用从微秒级退化到百微秒级）。
- **代价**：装载器维护两条路径；侧车插件多一次本地套接字往返。
- **理由**：把控制面与数据面分开——侧车的重活在自己进程里干，只有注册、调用、事件过套接字，进程内插件之间的直调不受影响。
- **重判结论**：形态不变，语言由 Rust 改为 C++，理由见 `docs/ling/02-技术选型.md`。

### A-2 内核只做四项服务

- **决定**：路由、事件、门禁、依赖解析留内核；配置存储、作业调度、日志做成内置插件。
- **被否**：三项也塞进内核（内核变胖，违背 P1）；只留路由与事件（门禁与依赖改为插件，遇到特权与引导问题）。
- **代价**：内核不可运行期替换；内置插件未安装时相关功能降级。
- **理由**：前三项是互调用的数据结构本身或与路由共用同一张表；后三项不在关键路径上、多插件共享有价值。

### A-3 内置插件从属宿主

- **决定**：内置插件源码放 `main/builtin-plugins/<编号>/`，随宿主发行，与普通插件同规范、同通道、可卸载。
- **被否**：各自独立仓库（版本匹配复杂）；混进内核代码（会获得特权通道，违背 A-2）。
- **代价**：宿主仓库包含插件代码，发行包略大。
- **理由**：目录从属表达「随宿主发行但彼此独立」，新增内置插件只需加一个子目录。

### A-4 首轮即实现热更新

- **决定**：第一版就要支持单插件重载。
- **被否**：先做可逆效应与依赖解析，热更新后置。
- **代价**：要正面处理动态库重复装载的映射泄漏，`LING-REQ-101` 的内存阈值必须放宽。
- **理由**：热更新的价值集中在开发期，越早有越早受益；而且它与可逆效应共用同一套账本，后做要返工。

### A-5 插件状态放持久文件

- **决定**：插件跨调用状态一律放 `data/`，内存不保留。
- **被否**：允许内存状态并做序列化迁移（要处理格式兼容与失败恢复，复杂易错）。
- **代价**：插件每次需要状态都要读文件或自建缓存。
- **理由**：让「重载等于干净重来」天然成立。

### A-6 命令行经管理端口

- **决定**：内核自带只监听回环的管理端口，命令行连它。
- **被否**：走 core-ui 的网页端口（界面坏了就无法修界面）；命令行自己拉起进程（管不到已在运行的宿主）。
- **代价**：内核多一个监听端口。
- **理由**：修宿主的工具不能依赖被修对象。

### A-7 采纳论文机制的务实子集

- **决定**：采纳可逆效应、响应式调和、上下文范式三项工程机制，不做形式化演算。
- **被否**：完整形式化实现（对工程无直接价值）；不采纳（要自己重新发明卸载干净的机制）。
- **代价**：卸载是否干净取决于实现正确性与测试覆盖，没有数学保证。
- **理由**：机制部分正好回答「一切皆插件」最难的三件事：卸载干净、依赖传导、热更新。

### A-8 core-ui 走侧车

- **决定**：core-ui 编译成独立可执行文件，作为侧车运行，用 C++ 写，不引入 Python 运行时。
- **被否**：进程内 C++ 插件（界面崩溃会带走宿主，且 01 里没有条款能约束界面崩溃）；侧车用 Python 写（Android 上要多带约 30 MB 运行时）。
- **代价**：界面取数据要过本地套接字，一次往返 50–200 微秒；构建多一个可执行目标；调试要 attach 到侧车进程。
- **理由**：界面是改动最频繁、最容易出 bug 的部分，放在最需要稳定的进程里是反着来；延迟代价在界面场景下可以忽略（每秒几十次查询合计几毫秒）；顺带让侧车轨道在第一版就有一个真实用户。

### A-9 多平台同一套插件接口

- **决定**：三端共用同一套接口与清单格式，平台差异只出现在装载与产物层（后缀、编译器、崩溃捕获手段）。
- **被否**：各平台分别设计接口（维护三套，插件无法跨端复用）。
- **代价**：接口只能用三端都支持的能力（例如不能依赖某个平台的特定 API）。
- **理由**：多平台是 00 定的目标，不是可选项（`docs/ling/00-总览与术语.md` §2.4）。

### A-10 内核线程串行改状态，读路径走快照

- **决定**：只有一条线程能改内核状态，全部变更请求排队；被读的表一律用不可变快照加原子指针替换。
- **被否**：每个服务各自加锁（热路径上读操作也要抢锁，1 微秒目标达不到，且死锁与锁顺序问题全要自己保证）；全部操作都排到内核线程（一次调用两次线程切换，同样达不到）。
- **代价**：写操作延迟从纳秒升到微秒级；快照替换会短暂多占一份内存。
- **理由**：把「谁能改」和「谁能读」分开，读写都不加锁，是同时满足「代码容易推理」与「调用快到 1 微秒」的唯一做法。

## 10. 架构约束与风险

### 10.1 五条硬约束

违反任意一条，后面的设计与代码都要重做，不接受变通。

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | 插件之间不直接链接，只经内核路由互调 | 卸载一个插件会让另一个链接失败或崩溃 |
| 2 | 动态库的装载与卸载只在内核线程，且串行 | 装载表与内存状态不一致 |
| 3 | 插件不得保留跨调用内存状态 | 重载后状态丢失或串行化失败 |
| 4 | 宿主与进程内插件使用同一编译器版本族、同一运行时链接方式 | 链接成功但运行崩溃（见 `docs/ling/02-技术选型.md` 附录 A.3） |
| 5 | 状态变化只以事件为准，界面与命令行不各自维护副本 | 三处状态不一致，无从判断谁对 |

### 10.2 风险登记册

本节只做设计时分析：什么会出错、设计上怎么预防。运行时已经出错了怎么处置，归 `docs/ling/09-运行时预案.md`。

| # | 风险 | 触发条件 | 影响 | 设计对策 |
|---|---|---|---|---|
| 1 | 动态库重复装载的映射泄漏 | 反复重载同一插件 | 内存缓慢增长 | 私有文件名加载；`LING-REQ-101` 放宽并提示重启；长稳测试覆盖 |
| 2 | 进程内插件崩溃不可恢复 | 插件处理函数越界或空指针，运行在 Linux 或 Android | 整个宿主退出 | 易崩插件改侧车；外部守护拉起；崩溃信息落盘 |
| 3 | 快照替换的频率过高 | 短时间内大量注册或订阅 | 内存短暂翻倍、分配器压力上升 | 注册集中在激活期；调和合并 200 毫秒内的变化 |
| 4 | 侧车与控制面协议分裂成两套 | 侧车轨道与进程内轨道各自演进 | 维护成本翻倍 | 帧格式统一由 `docs/ling/04-详细设计/02-插件装载与接口.md` 定义，进程内只是省掉序列化 |
| 5 | 插件绕过上下文 | 开发者图省事直接改全局 | 卸载不干净、热更新失效 | 代码审查清单；`doctor` 检查可观测迹象（LING-REQ-038） |
| 6 | 撤销函数写错导致卸载报错 | 插件作者的撤销逻辑有缺陷 | 卸载不完整 | 账本逐条容错并报告清单；`doctor` 列出未撤销项 |
| 7 | 内核升级导致插件不兼容 | api 主版本变更 | 插件全部装载失败 | 支持 api N 与 N-1，不匹配只影响该插件（LING-REQ-086） |
| 8 | core-ui 侧车崩溃后界面无法自恢复 | 界面进程崩溃且重启策略为 `never` | 用户失去界面，但命令行仍可用 | 默认 `restart="on-crash"`；命令行不依赖界面（LING-REQ-075） |

| 3 | 工作线程池数量公式 | 采纳「CPU 核数 − 3，最少 2」。双核机器上退化为 2，语义不变 | §5.2 |
| 4 | Windows 崩溃捕获用哪种机制 | 向量化异常处理，能在捕获点拿到线程与模块信息 | §5.4 |
| 5 | 快照替换在 C++20 下的替代方案 | 当前用 C++17 的 `atomic_load(shared_ptr)`；升级时改手写引用计数或 `shared_mutex`，后者要重测 LING-REQ-089 | §5.3 |
