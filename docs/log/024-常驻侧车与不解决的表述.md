## 意见一：`04/02` 说「常驻默认 1 个 Python 侧车」，判断错了

用户的原话是「确认常驻除了内置插件不是应该没有吗」。这是对的，我原来的写法把两件事混在一起：

- **上限** 1 个 —— 允许 1 个常驻，给那些值得付内存的插件；
- **默认** 1 个 —— 读起来像「装完就会有一个常驻侧车」。

而且内置插件里根本没有 Python 侧车（`core-ui` 是 C++ 侧车，其余四个是进程内动态库），所以「默认就有 1 个」这件事在实现上也不会发生——它只可能出现在「默认值被写成实例化」的误解里。

原表格还有一处含糊：「常驻白名单」这个词看不出默认是空的。

### 改法

`04/02` §8.7 重写，把三件事分开说：

| 项 | 改成 |
|---|---|
| 默认常驻数量 | **0 个**，宿主不预设、不主动把任何插件改成常驻 |
| 常驻是否启用 | 只有清单写 `sidecar.restart = "always"` 才常驻 |
| 上限 | Python 侧车最多 1 个；第 2 个声明 `always` 的装载被拒 |

并补了三条说明：内置插件里没有 Python 侧车，所以默认一个都没有；上限留 1 是给监听类插件；第 2 个被拒而不是静默降级（静默降级会让插件以为自己常驻，实际每次调用都冷启动）。

### 连带改动

- 新增错误码 `E_RESIDENT_LIMIT`，登记进 `04/02` §5.2。这是本轮唯一新增的码，全库 24 个变 25 个，11 处计数同步。
- `04/02` §3.4 的清单校验从 10 步扩到 12 步：第 11 步检 `core-` 前缀，第 12 步检常驻配额。
- 顺带发现：`04/07` 的结论早就说「`core-` 前缀检查加为第 11 步」，但 §3.4 的表里一直没有这一步——**结论写了，落地动作没做**。这次补上。

## 意见二：提审包里「已知不解决」是什么意思

用户问「03 的 5 这里不解决是怎么回事」。原文只有一句「已知不解决：同账户恶意程序、Linux 与 Android 进程内崩溃」，没说清这是待办还是结论。

它是**结论**：这四件事在「个人自用工具」的前提下投入产出不成立，所以明确不做，各自给了替代措施。已在提审包里补一张表：

| 缺口 | 替代措施 | 真要做的代价 |
|---|---|---|
| 同账户恶意程序 | 无，只能事后查日志 | 要沙箱或换权限模型，不是插件宿主能解决的 |
| Linux 与 Android 进程内崩溃 | 刷盘留证、systemd 拉起、易崩插件改侧车 | 全走侧车则内存与启动双双违约 |
| 重载泄漏的映射 | 50 MB 上限 + `doctor` 提示重启 | `dlclose` 不可靠是平台问题 |
| Android 无原生界面 | 浏览器打开本机地址 | 维护两套界面 |

并补了一句定性：**「不解决」不是待办，也不表示后面会补。**

## 这轮暴露的模式

两次都是同一类问题：**结论写对了，但读起来像在推脱**。

- 「常驻默认 1 个」——把上限写成了默认值。
- 「已知不解决」——把边界写成了待办。

写的人知道自己在说什么，读的人只能靠猜。文档的读者没有上下文，只有字面。以后凡出现「默认」「已知」「暂不」，都要问一句：这句话单独看，会不会被理解成相反的意思。
