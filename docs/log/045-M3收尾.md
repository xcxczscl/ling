# log 045 M3 收尾：预览、合并、自动重算

> 日期：2026-10-31
> 关联：`docs/ling/04-详细设计/04-依赖解析与调和.md` §7.2、§8.1；`docs/ling/04-详细设计/06-管理端口与命令行.md` §5.9

## 1. 三件事一起做的原因

上一轮把 M3 的主干做完了（依赖图、三态、自动启停、reload/restart），剩三条都指向同一个动作——**调和**。它们的共同前提是「调和能只算不做」，所以先把计算从执行里拆出来，再谈预览、合并、自动重算。

## 2. 拆出 `current_graph`

`reconcile()` 原来把「扫盘、建快照、算图」和「执行计划」写在一个函数里。现在前半段抽成 `Kernel::current_graph(&active)`，调和与预览都调它。

抽的理由很实际：预览如果自己再扫一遍盘、自己再算一次图，迟早会和实际执行分叉——两边各写一份，改了一边忘了另一边就是「预览说会停 A，实际停了 B」。共用一份，分叉不可能发生。

## 3. `ling plan`：只看不做

```
$ ling plan
下次会自动做 2 件事：
  1. 启用 demo-a
  2. 停用 demo-b

这些插件暂时起不来：
  demo-c  缺 demo-x@1（没装这个插件）
```

`steps` 与 `blocked` 分开给：前者回答「点下去会发生什么」，后者回答「为什么它没在跑」。界面的「停用前先告诉我会连带停谁」直接用这个方法。

## 4. 200 毫秒合并

主循环每轮（本来就是 200 毫秒一轮）扫一遍 `plugins/<id>/plugin.toml` 的最后修改时间，与上一轮记下的指纹比对：

```
变了 → 记「待重算」，把时钟推到现在，本轮不动
没变且已安静 200 毫秒 → 调和一次
```

连续几次改动（比如一次装两个插件）只会在安静下来之后算一次。没上文件系统通知，因为 Windows 与 Linux 的通知机制不通用，为这点需求引两套不值；几十个插件的 `stat` 每轮成本可以忽略。

## 5. 改清单后自动重算

这条与第 4 条是同一件事的两面：改依赖声明、换版本、换产物都会碰 `plugin.toml`，指纹一变就重算。实测：

```
1. 装 demo-b（依赖 demo-a@1）→ 显示已停用，原因「缺 demo-a@1」
2. 手改 demo-b 的清单，删掉 [requires]
3. 等 1.5 秒（合并窗口 + 一轮轮询）
4. ling plugins → demo-b 已启用；ling plan → 什么都不用做
```

改回来（加回依赖）同样会自动停用。不需要 `reload`，也不需要重启宿主。

## 7. M3 判定

`10-路线图与里程碑.md` 对 M3 的判定是两句话：

| 判定 | 状态 |

## 8. 与设计的两处偏差，记在这里

1. **计划没有做成可取消的独立对象**：现在是「算完立刻执行」，`kernel.plan.step` 的 `plan_id` 每次都从 1 递增，但没有 `Plan` 结构给外部持有，也没有取消入口。`04/04` §6.2 的取消与回滚因此没实现——回滚目前靠「卸载时账本倒序撤销」兜底。
2. **合并窗口只看清单的修改时间**：换产物（dll）但不动清单，指纹不变，不会自动重算。这种情形仍要 `ling reload`。要覆盖它得把 dll 的修改时间也纳入指纹，代价是多几次 `stat`，等真有人这么用再加。
