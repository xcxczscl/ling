`emit` 在调用方线程同步执行，不排队。理由与 `04/01` §6.3 一致：广播只读订阅表，排队反而多一次线程切换。

## 二、写的时候发现的两个契约缺口

**① 事件回调拿不到主题。** `ling_event_fn` 原本只有 `(ctx, payload, len)`。一个插件完全可以只用一个回调函数挂多条订阅（`demo-a.*` 和 `kernel.plugin.state`），没有主题就分不清收到的是哪一类事件，载荷本身也不带主题字段。已在 ABI 里加上 `const char* topic`，并同步 `04/02` §4.1。

**② 订阅校验把内核事件挡在门外。** `04/01` §6.1 原本第 3 条要求「主题非 `kernel.` 开头，或以 `plugin_id.` 开头」。按字面执行，`kernel.plugin.state` 既以 `kernel.` 开头、又不以订阅方编号开头，任何插件都订不到内核事件，而内置的 `core-plugin-manager` 正是靠它刷状态。已改为「只管形状、不管归属」，前缀约束只留在广播一侧。这条如果不修，后面写内置插件时会绕一大圈才回到这里。

顺带确认了回调首参的语义：`register_method` 与 `subscribe` 的接口上没有让插件传自己上下文的入口，所以回调首参是**宿主的**上下文句柄，插件把它当不透明值原样传回。`demo-a` 第一版按「插件自己的结构」写了，结果是读了一处无关内存、函数指针为空、ASan 报 `pc = 0`。已在 `plugin_api.h` 与 `04/02` §4.1 写清。

## 三、取舍

**5 秒是告警阈值，不是切断点。** 同步派发时，回调不返回就没有插回控制权的时机，抢占式切断要给插件另起线程并强杀，代价远大于收益。所以进程内轨道上超时只记一条带 `sub_id` 与耗时的 warn，真正能「跳过」的是侧车轨道（宿主等应答，超时即放弃）。`04/01` §6.3 已按此改写。

**派发前复制收件人。** 回调里退订或新增订阅都会改动订阅表，持有指针或引用必然失效。复制一份 `SubEntry` 的代价是几十个 `std::string`，与「回调里退订导致崩溃」相比微不足道。已有单元测试覆盖这个场景。

## 四、当前可复现的验证

```
ling install run/win-debug/plugins/demo-a --data-dir run/tmp-e2e
ling install run/win-debug/plugins/demo-caller --data-dir run/tmp-e2e
ling plugins --data-dir run/tmp-e2e
```

`demo-caller.log` 的内容：

```
event demo-a.pinged pong
reply=pong
event kernel.plugin.state {"generation":2,"plugin_id":"demo-caller","state":"activated",...}
event kernel.plugin.state {"generation":1,"plugin_id":"demo-a","state":"deactivated",...}
event kernel.plugin.state {"generation":2,"plugin_id":"demo-caller","state":"deactivated",...}
```

第一行是 `demo-a.ping` 里 `emit` 的 `demo-a.pinged`，`demo-caller` 用 `demo-a.*` 收到；后三行是内核状态事件，`demo-caller` 用 `kernel.plugin.state` 收到。进程退出时两条 `deactivated` 来自 `Kernel` 析构统一停用——常驻宿主（`serve`）下只有真正退出才看得到。

单元测试 31 个用例、163 个断言全绿（新增 12 个用例覆盖主题形状、模式匹配、订阅上限、退订、派发顺序、回调内退订）。

## 五、一个已知的不顺

`install` 之后新插件不会立刻激活，要等下一次启动装载。因为命令行是「一次性进程」，`install` 里先 `load_all` 再拷贝，拷贝完就退出了。`serve` 起来之后这条路径改为经管理端口下发，装完即激活，届时一并解决。
