# log 033 控制台中文乱码

> 日期：2026-10-31
> 触发：实际运行时 `ling serve` 的输出显示为「鏁版嵁鏍?」这类乱码

## 一、现象与判断

```
2026-10-31T17:00:24 [info] kernel 鏁版嵁鏍?run\win-release\data-demo
```

「鏁版嵁鏍?」是「数据根」三个字的 UTF-8 字节被按 GBK 解读的结果。反推一下就能确认：

| 环节 | 猜的 | 实际 |
|---|---|---|
| 源码编码 | 源文件是 UTF-8，编译加了 `/utf-8` | 对 |
| 内存里的字符串 | UTF-8 字节 | 对 |
| 写日志文件 | `fprintf` 原样写字节 | 对，文件里是 UTF-8 |
| 写 stderr | 原样写字节 | 对 |
| **终端解读** | 按 UTF-8 | **错，Windows 控制台默认 936（GBK）** |

所以日志文件本身没问题，用 VS Code 或较新的记事本打开是正常的中文；乱码只发生在控制台显示这一步。

## 二、修法

`main` 一开始就把控制台输入输出代码页切到 `CP_UTF8`（65001），退出时还原原值。

```cpp
class ConsoleUtf8Scope {
public:
    ConsoleUtf8Scope() {
        previous_input_ = ::GetConsoleCP();
        previous_output_ = ::GetConsoleOutputCP();
        if (previous_output_ != CP_UTF8) ::SetConsoleOutputCP(CP_UTF8);
        if (previous_input_ != CP_UTF8) ::SetConsoleCP(CP_UTF8);
    }
    ~ConsoleUtf8Scope() { /* 还原 */ }
};
```

三个细节：

1. **必须放在任何输出之前。** `Kernel` 构造时就会往 stderr 打「数据根」那一条；放到参数解析之后，第一行仍然是乱码。
2. **退出要还原。** 代码页是控制台的状态，不是进程的状态。不还原会把用户同一个窗口里后续运行的其他程序一起带歪。
3. **只在 Windows 上做。** Linux 终端的编码由 locale 决定，程序不该插手。

## 三、为什么不在写文件这一侧改

有人会想「干脆按 GBK 写日志」。不行的原因有三条：

1. 日志文件一旦是 GBK，跨平台解析脚本、VS Code、Git 的 diff 全都要额外判断编码。
2. `core-log` 与内核日志用同一套行格式（`04/07` §7.2），改一处就得改两处，还得处理混合编码的历史文件。
3. 数据根路径里可能有 GBK 表示不了的字符。UTF-8 是唯一不会丢字的写法。

正确的分工是：**程序只产出一种编码（UTF-8），显示端的编码由程序在启动时对齐。** 谁解读谁负责，这是 `SetConsoleOutputCP` 存在的理由。

## 四、验证与遗留

- 单元测试 31 用例 163 断言全绿；验收脚本五个全过（`--preset win-release`）。
- 日志文件仍是 UTF-8 无 BOM。Win10 1903 之后的记事本、VS Code 都能正确识别；更老的编辑器需要手动选编码。这一条不打算靠加 BOM 解决——BOM 会混进日志首行，给解析脚本添麻烦。

## 五、给使用者的两条提示

1. 已经在跑的宿主用的是旧二进制，得先 `ling shutdown`，重新编译后再 `ling serve`。
2. 如果切换后中文变成方块而不是乱码，那是字体问题不是编码问题：换成 Windows Terminal，或给当前控制台换一个中文字体。
