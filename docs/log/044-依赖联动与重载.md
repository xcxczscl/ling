# log 044 依赖联动停用、错误码不上屏、重载与计划事件

> 日期：2026-10-31
> 关联：`docs/ling/04-详细设计/04-依赖解析与调和.md` §5.1、`docs/ling/04-详细设计/06-管理端口与命令行.md` §4.4、§5.7

## 1. 依赖停用要跟着停

上一版按 `04/04` §5.1 的三态表实现：需求满足只看「装没装、版本对不对」。结果是 `ling disable demo-a` 之后，依赖它的 `demo-b` 仍算满足、继续激活，调 `demo-a.ping` 拿到 `E_PLUGIN_MISSING`——用户看到的是「明明装着的插件突然不能用了」。

改法：`build_graph` 多收一个「不可用」集合（被停用的、启动失败的），并**沿依赖往下传**——`demo-c → demo-b → demo-a` 里 `demo-a` 不可用，两个下游都要停。

两条细节：

- 被停用的那个插件自己不记「缺依赖」：那是用户主动做的，不是缺失。
- 依赖者的原因写成「依赖 demo-a 现在用不了，所以它也停着」，与「缺 demo-a@1（没装这个插件）」区分开，用户能看出是两种不同情况。

`enable` / `disable` / `install` / `uninstall` 之后都会调和一次，所以这一串不需要重启宿主。

## 2. 错误码不再出现在屏幕上

以前失败时打印 `找不到这个插件（E_PLUGIN_MISSING）`。错误码是内部标识，摆在用户面前只会更糊涂，而且会让人以为要拿它去搜。

现在分两条路：

| 路径 | 输出 |
|---|---|
| 默认 | 一句人话 + 一条下一步，不出现错误码 |
| `--json` | `{"ok":false,"error":{"code":"E_...","message":"人话"}}` |

顺带补了六条提示：依赖成环、撤销失败、能力未知、方法重名、换版本失败、正在退出。验收脚本改成从 `--json` 里取 `code` 判定，不再依赖屏幕文本。

## 3. `reload` 与 `restart`

`04/06` §4.1 里早就列了这两个子命令，代码一直没有。这次补上，两者走同一条路：

```
标记「重载中」→ 调和（依赖方停）→ 卸下 → 重新装载 → 去掉标记 → 再调和（依赖方回来）
```

「先停依赖方」不能省：先换产物再停，中间会有一个窗口，依赖方拿着刚被换掉的函数指针。

新版本清单不合法时不卸旧的——否则会出现「旧的没了、新的装不回来」。

## 4. `kernel.plan.step` 事件

调和不再是「悄悄执行一串动作」，每一步广播一次：

```json
{"plan_id":1,"step":1,"step_total":2,"action":"activate","plugin":"demo-a","ok":true}
```

同时每一步记一行内核日志（`plan 计划 1 第 1/2 步：启用 demo-a 成功`）。计划不常发生，这几行在排查「为什么这个插件没起来」时最有用。

## 5. 验收脚本改用系统临时目录

以前每个脚本 `rmtree(run/<preset>/data-test/<脚本>)` 再重建。既然测试产物不必保留，改成 `tempfile.mkdtemp()`，跑完不删（留给排查），也不碰仓库里的目录。四个脚本都改了。

另外踩到一个坑：脚本里起宿主时输出接到 `subprocess.PIPE` 又没人读，宿主日志写满管道缓冲后阻塞在写调用上，表现为「shutdown 之后进程不退」。改成写文件即好。

## 7. 还没做的

- 200 毫秒去抖：连续多次变化合并成一次调和。现在的实现是「每个动作调和一次」，插件少时无所谓，插件多了会重复算。
- 独立的 `Plan` 对象与取消：现在算完立刻执行，没有「先预览再执行」的入口（`core-plugin-manager` 的 `preview` 要用它）。
- 改清单或改版本后自动重算：现在要显式 `reload`。
